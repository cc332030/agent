= 公共任务提示词：项目重构

面向任何项目的一次性**全量重构**任务提示词。非规范内容，不随 `specs/` 分发、不进规范加载链，供用户在给 AI 下达任务时复制使用。适用于已接入 agent 规范的项目（AI 读项目规范入口即可），正文措辞通用、不依赖具体技术栈。

**本提示词的重点是"重构"**：检查在本任务中同样是必须的（逐模块分析现状、定位结构问题，是重构的前提），但**检查是手段、重构是目标**——须真正改动结构（拆分/合并/抽象/消除重复/调整职责与依赖等），不得以"检查提报告"替代重构、不得只出报告或建议就收尾。与同目录的**检查修复提示词** link:review.adoc[]（`prompts/review.adoc`，非 `specs/general/review.adoc` 规范）的分工：**它以"检查修复问题"为目标**（检查出问题就修，无问题即结束，原则上不重构）；**本提示词以"重构"为目标**（检查服务于重构，产出必须是结构改动）。

== 用法

将下方代码块内的文字**完整原样**复制给 AI 作为任务指令。

**给 AI 的读取说明（保证内容完整）**：正文由 link:_common.txt[] 的公共片段（`intro-rules` / `baseline` / `final-verify` / `delivery`）组装。若你读到的是**文本形式**、其中 `include::_common.txt[tag=…]` 指令**未被展开**，请先读取同目录的 link:_common.txt[]（远程：https://agent.c332030.com/prompts/_common.txt），取出对应 tag 的内容补齐后再执行——**不得因指令未展开就跳步或漏掉公共步骤**。

----
对本项目执行一次全量重构。
include::_common.txt[tag=intro-rules]
**本次以重构为目标：检查必须做（逐模块分析现状、定位结构问题是重构的前提），但检查服务于重构，产出必须是真正落地的结构改动，不得只检查、只分析、只出报告或只给建议就收尾**；若判定"确无可重构点"，须给出逐模块的判定依据与理由，经用户确认后方可结束。

include::_common.txt[tag=baseline]
2. 现状检查与重构方案：逐模块检查代码现状（这是重构的前提，须做全、不得跳过），定位需重构的结构问题（重复代码、职责不清、过长/过复杂方法、类与模块耦合、坏味道、难扩展的实现等；检查中发现的其他问题一并记录，但**处理方式与本任务定位一致——能随重构一并修复的随重构处理，与重构无关的按 link:review.adoc[]（检查修复提示词）处理或记入重构清单**），按优先级排序成重构清单写入 tmp/ 作核对依据，不得遗漏模块；每项写明重构目标、方式与预期收益（可维护性/可读性/扩展性/性能），有取舍的给出备选方案与取舍依据。对每处性能相关重构判定是否需性能测试：命中任一特征才需——①关键路径/高频调用（每请求/循环反复执行）②大数据量或规模可增长（批量/全量遍历聚合）③昂贵资源（IO/网络/DB/缓存/线程/锁/序列化）④多方案选型需数据佐证；未命中为普通重构、直接实施、不加性能测试，不得一律加、也不得漏掉真敏感点；对需测试的敏感点先测并记录重构前结果作基线。
3. 实施重构：按清单实施结构改动（抽离/下沉公共逻辑、拆分职责、消除重复、调整依赖与调用关系、简化复杂实现等），遵循规范、做最小必要改动，不擅自扩大改动范围；**不得借重构之机顺手改动与重构目标无关、且本身无问题的代码**（无问题处保持原样，仅在重构确有必要改动时才动并说明理由）。
4. 完善补齐：同步补注释、更新设计/测试文档、补齐缺失功能用例（行为变更处必须补）；仅对第 2 步判定需性能测试的敏感点补性能用例（对比测试、独立于单元测试），其余不加。
5. 性能迭代优化：仅对第 2 步判定需性能测试的敏感点执行——对每处输出对比结果：重构前 vs 重构后、并与其他可行方案（含常见最佳实践）对比，评估是否接近最佳实践、提升是否显著；不理想则分析瓶颈、继续优化并重新测试，反复直至接近最佳实践或优化收益收敛并明确取舍，不得一次重构就收尾；结果与迭代结论写入 tmp/。
6. 回归自检：逐一复查全部重构点，确认未引入新问题（无新增编译/静态警告、**不破坏既有行为与用例**、不影响调用方；重构须保持可观测行为不变，行为变更须单独说明并征得确认）。
include::_common.txt[tag=final-verify]
include::_common.txt[tag=delivery]

完成后汇报：各步骤执行情况、重构清单（编号）与实施状态、重构前后结构对比与收益、性能对比结果与迭代结论、验证结果、改动文件清单与**交付情况**（本地场景：改动保留在本地工作空间、未提交未推送；自动化场景：已提交推送的分支与 PR）。
