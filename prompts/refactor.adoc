= 公共任务提示词：项目重构体检

面向任何项目的一次性**全量重构体检 + 修复**任务提示词。非规范内容，不随 `specs/` 分发、不进规范加载链，供用户在给 AI 下达任务时复制使用。适用于已接入 agent 规范的项目（AI 读项目规范入口即可），正文措辞通用、不依赖具体技术栈。

== 用法

将下方代码块内的文字**完整原样**复制给 AI 作为任务指令。

对本项目执行一次全量重构体检并修复。要求不漏步、不偷懒、高质高效：严格按下述步骤完整执行，任一步未完成不得进入下一步；全部完成并验证通过后才允许提交，不得提前收尾或中途提交。

1. 规范与基线：先读取并遵守项目规范；将主分支更新到最新并同步到当前分支，确保基于最新代码工作。
2. 全量检查：逐模块检查全部代码的常规与性能问题（常规：规范符合性、重复/坏味道、命名、注释、异常与边界、安全隐患等；性能：低效实现、循环内重复开销、集合/IO/线程/缓存隐患等），分级编号成清单写入 tmp/ 作核对依据，不得遗漏模块与文件。对每处性能问题判定是否需性能测试：命中任一特征才需——①关键路径/高频调用（每请求/循环反复执行）②大数据量或规模可增长（批量/全量遍历聚合）③昂贵资源（IO/网络/DB/缓存/线程/锁/序列化）④多方案选型需数据佐证；未命中为普通问题、修复即可、不加性能测试，不得一律加、也不得漏掉真敏感点；对需测试的敏感点先测并记录修复前结果作基线。
3. 直接修复：方案明确的直接修复并遵循规范；有取舍的在代码注释与设计/测试文档记录依据与边界，不擅自扩大改动范围。
4. 完善补齐：同步补注释、更新设计/测试文档、补齐缺失功能用例；仅对第 2 步判定需性能测试的敏感点补性能用例（对比测试、独立于单元测试），其余不加。
5. 性能迭代优化：仅对第 2 步判定需性能测试的敏感点执行——对每处输出对比结果：修复前 vs 修复后、并与其他可行方案（含常见最佳实践）对比，评估是否接近最佳实践、提升是否显著；不理想则分析瓶颈、继续优化并重新测试，反复直至接近最佳实践或优化收益收敛并明确取舍，不得一次修复就收尾；结果与迭代结论写入 tmp/。
6. 回归自检：逐一复查全部修复点，确认未引入新问题（无新增编译/静态警告、不破坏既有行为与用例、不影响调用方）。
7. 最终验证：提交前跑**全量编译与全量测试**，须完全通过且满足规范——编译/构建无错误无警告、全量测试按实际统计全部通过、无规范违规；不满足不得进入提交步骤，须先修复再重跑。
8. 提交并创建 PR：**不允许直接提交或推送分支（为 PR 建的分支除外）**——改动一律在为本次改动新建的 PR 分支上本地提交并推送，不得直接向目标分支（主分支等）提交/推送/合并；目标分支只能通过 PR 经**人工 review** 通过后合入，不得跳过 review。全部完成并验证通过后在 PR 分支统一提交（一次或合理分批），提交前核对无 tmp/ 等临时产物与无关文件，随后推送 PR 分支并创建 Pull Request。若本地环境无法推送/创建 PR（如无权限、远程不可达），则提交保留在本地 PR 分支上、不推送不合并，说明 PR 未创建及原因，交由人工后续处理；仅在 CI 等自动化流程中执行而未合入的改动，本次内容会随之丢失，须以 PR/人工确认的方式合入保留。

完成后汇报：各步骤执行情况、问题清单（编号）与处理状态、性能对比结果与迭代结论、验证结果、提交信息。
