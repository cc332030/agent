= 公共任务提示词：项目重构

面向任何项目的一次性**全量重构**任务提示词。非规范内容，不随 `specs/` 分发、不进规范加载链，供用户在给 AI 下达任务时复制使用。适用于已接入 agent 规范的项目，正文措辞通用、不依赖具体技术栈。

**主侧重（方向性前提，先读）**：**"重构"**——检查必须做（逐模块分析现状、定位结构问题是重构的前提），但**检查是手段、重构是目标**：**产出必须是真正落地的结构改动**（拆分/合并/抽象/消除重复/调整职责与依赖等），**不得以"检查提报告"替代重构、不得只出报告或只给建议就收尾**；确无重构点时才允许以"逐模块判定依据 + 经用户确认"结束。检查范围、产出形态、收尾条件一律以本侧重判定；**侧重不符即方向错误**（只想检查修问题请用 `prompts/review.adoc`，二者分开、不得混用）。

== 用法

将下方代码块内的文字**完整原样**复制给 AI 作为任务指令。

**给 AI 的读取说明（保证内容完整，先做）**：正文由 `prompts/_common.txt` 的公共片段（`intro-rules` / `primary` / `priority-rules` / `isolation` / `env-guard` / `scope-boundary` / `baseline` / `baseline-and-compat` / `compat` / `final-verify` / `delivery`）组装。**判据是"内容有没有被 AsciiDoc 处理器装配过"，不是"看起来像不像渲染过的页面"**：取到**原始文件**（远程原始文件地址、本地/工作区直接读文件）时 `include::_common.txt[tag=…]` 指令**不会被展开**，看到该指令即说明**尚未装配**——请**先读取同目录的 `prompts/_common.txt`（远程：https://agent.c332030.com/prompts/_common.txt）取出全部 tag 的内容补齐，再按补齐后的全文执行**，不得因指令未展开就跳步或漏掉公共步骤；**不得**以"这是站点的渲染视图、片段已展开"为由跳过补齐。正文按以下顺序组成，`primary` / `priority-rules` / `isolation` 三段是**方向与观念的前提**，须先于其他步骤读入：

1. `primary`：本任务唯一主侧重（方向，不符合即方向错误）——片段中的 `{主侧重}` 取本提示词的值『重构』；
2. `priority-rules`：优先级规则（按业界共识分级执行，指明哪里是重点）；
3. `isolation`：隔离要求（不混用其他提示词、不做跨任务顺手改动）；
4. `intro-rules` / `baseline` / `final-verify` / `delivery` 与第 2-6 步：其余公共步骤与任务步骤；**`baseline-and-compat`**（动手前）在「规范与基线」（第 1 步）之后读入，**`compat`**（改动后）在「最终验证」之前读入；
5. `scope-boundary`：**变更范围只限当前项目**（未声明即拒绝越界改动，引用不等于授权）；
6. `env-guard`：**按环境标志选执行口径**——只在命中标志（`printenv CNB_EVENT` 非空 且 触发内容含 `@<Agent名>`）的环境里生效，未命中按其末尾中性口径执行。

2. 现状检查与重构方案（**动手重构前：先定基线 + 先调研最佳方案，L1**——既有校验手段须先扫描、**既有用例完整可用的必须先跑通并留证**；每处结构改动须给出**备选方案与取舍依据**，不得只给一个写法；**调整内容一类需求（含新增与调整）须先检索现成可参照的标准与更优设计**——业界标准/权威约定（只写标准名/编号）、通行设计范式、本项目既有先例三者都查一遍，有**更优的设计**的用更优的设计、查不到要能说出查证方式（**上面 `baseline-and-compat` 片段里的同项要求已写明，此处不重复其正文**；同一件事只在一处完整定义，别处一行引用）；**要替换/废弃既有流程或既有做法时先向用户确认**）：逐模块检查代码现状（这是重构的前提、**必须做全、不得跳过（L1）**），定位需重构的结构问题（重复代码、职责不清、过长/过复杂方法、类与模块耦合、坏味道、难扩展的实现等；检查中发现的其他问题一并记录，但**只记录、不改动**——与重构无关的修复交 `prompts/review.adoc` 处理或记入重构清单，不属本任务范围），按优先级排序成重构清单写入 tmp/ 作核对依据，不得遗漏模块；每项写明重构目标、方式与预期收益（可维护性/可读性/扩展性/性能），有取舍的给出备选方案与取舍依据。对每处性能相关重构判定是否需性能测试：命中任一特征才需——①关键路径/高频调用（每请求/循环反复执行）②大数据量或规模可增长（批量/全量遍历聚合）③昂贵资源（IO/网络/DB/缓存/线程/锁/序列化）④多方案选型需数据佐证；未命中为普通重构、直接实施、不加性能测试，不得一律加、也不得漏掉真敏感点；对需测试的敏感点先测并记录重构前结果作基线。
3. 实施重构（**本任务的核心产出，不得以"只出报告/只给建议"替代（L1）**）：按清单实施结构改动（抽离/下沉公共逻辑、拆分职责、消除重复、调整依赖与调用关系、简化复杂实现等），遵循规范、做最小必要改动，不擅自扩大改动范围；**不得借重构之机顺手改动与重构目标无关、且本身无问题的代码（L1）**。若本步判定确实无可实施的结构改动，须给出**逐模块的判定依据与理由**、经用户确认后方可结束——不得跳过本步直接出报告收尾。
4. 完善补齐：同步补注释、更新设计/测试文档、补齐缺失功能用例（行为变更处必须补）；**老用例不得为迁就重构而改判**——除相关功能被显式移除（先经确认）外，既有用例须原样通过，**新老用例同时成立**；仅对第 2 步判定需性能测试的敏感点补性能用例（对比测试、独立于单元测试），其余不加。
5. 性能迭代优化（**有结论的工程实验，L1**）：仅对第 2 步判定需性能测试的敏感点执行——对每处输出对比结果：重构前（基线）vs 重构后、并与其他可行方案（含当前实现作为基准、含常见最佳实践）对比；**每组至少 3 次有效采样并报离散度**，**组间差异小于离散度即视为无显著差异**、不得据此宣称胜出；不理想则分析瓶颈（卡在 CPU/内存/IO/锁/序列化/复杂度/调用次数哪一处、依据哪次实测）、继续优化并复测，反复直至接近最佳实践或**收益收敛（边际收益小于离散度）并写明取舍**，不得一次重构就收尾；**成绩与迭代记录落进性能测试文档或测试类的文档注释（长期产物）**，同时把过程明细写入 tmp/ 供本次核对；记录内容**只记结论 + 取值 + 来源**（方案组合与成绩、未选方案与原因、瓶颈归因与下一步方向），**不记原始日志与调试过程、不为对称预建空行**。
6. 回归自检：逐一复查全部重构点，确认未引入新问题（无新增编译/静态警告、**不破坏既有行为与用例**、不影响调用方；重构须保持可观测行为不变，行为变更须单独说明并征得确认）。

9. **不得自行发评论唤起自己（L1，防无限派发）**：**不得在本次执行中再发一条评论去点名本任务的实例名（`@<实例名>`）重新发起一次执行**（也不得转由他人/其他执行者代发）——**一次评论 = 一次派发**，**发起下一次是派发者的动作、不是执行者的动作**；判据是**这条评论发出去没有**，不是"这次执行有没有因此结束"。**想分步的唯一正当形态**：**先停**、只输出一次"必须停下确认"（把"已做完哪段、下一步要什么"一次性写清），由**人**另发一条评论决定要不要再来一次；"分两步更清楚""上一轮没做完"都不是理由。**它同样不是"少做一步"的许可（L1）**：**不自派 ≠ 不许复核**——本次执行里拿不到另一个同 Agent 执行者时，**在本次执行内**按降级路径补复核（执行者本人按同一判据串行核对并**标注独立性边界**，或标悬置 + 写剩余风险），**交付照常**、结论里如实写明"可信的独立复核不可得 + 已做的替代核对 + 剩余风险"；**不得**用"为了复核"去 @ 自己（那是自派）、**不得**据此跳过复核或把任务停在中间等下一轮。
10. 交付即汇报（**交付与汇报是同一个动作，L1——不得只交付不汇报，也不得只冒一句、没有交付**）：**本提示词的输出只有一种**——即步骤 8 的**交付结果**加本步的**结论汇报**，**合起来给出一次完整汇报后结束**（在平台上即**一条评论**）。①**输出通道只有两条**——最终的一次完整汇报、或"必须停下确认"（须一次性说清"停在哪、缺什么、要你定什么"）；**此外任何中间话一律不发**（过程性叙述、把规范条文/检查依据当结论念一遍、只为表明"我在按规范做"的复述都不算例外，判据与落点见上方 `delivery` 片段的「报告落点」条）；②**本次有改动**时，交付形态就是「改动 + 提交推送 + PR」，汇报里须**落成可核对的事实**（改动文件清单、分支与 PR 链接、验证结果）——**不得出现"说了却不交付"**；③**本次无改动**时须**显式说明**"本次检查未发现问题"（这是合法完成态），**不得**把"无改动"含糊带过、也**不得**为凑产出而动手；④**方向错、步骤没走完、验证没过，不得汇报"已完成"**——经尽力仍不满足 L1 时须**如实写明停在哪一步、缺什么**（唯一允许的中途输出）。

完成后汇报：**先回报主侧重（"重构"）的达成情况**——本次做了哪些**结构改动**、改动前后的结构对比与收益（若判定确无可重构点，须给出逐模块判定依据与用户确认结果，不得用"检查报告"充当产出）。随后汇报：各步骤执行情况、重构清单（编号）与实施状态、**性能对比结果与迭代结论（含各方案组合与成绩、离散度、未选方案与原因、瓶颈归因与下一步方向；单轮即收敛时说明收敛依据，不硬造轮次表）**、验证结果、改动文件清单与**交付情况**（本地场景：改动保留在本地工作空间、未提交未推送；自动化场景：已提交推送的分支与 PR；**两种情况都不执行合并**——合入目标分支只由人工完成，即使被要求合并/直授也拒绝）。
