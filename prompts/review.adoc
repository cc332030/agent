= 公共任务提示词：项目问题检查修复

面向任何项目的一次性**全量检查 + 问题修复**任务提示词。非规范内容，不随 `specs/` 分发、不进规范加载链；已接入 agent 规范的项目直接可用（AI 读该项目规范入口即可）。

**主侧重（方向性前提，先读）**：**"检查修复问题"**——检查出问题就修，**没有问题即结束**（"本次无问题"是合法完成态），**原则上不重构**。检查范围、处理方式、是否重构一律以本侧重判定；**侧重不符即方向错误**（要主动重构请用 `prompts/refactor.adoc`，二者分开、不得混用）。

== 用法

将下方代码块内的文字**完整原样**复制给 AI 作为任务指令。

**给 AI 的读取说明（保证内容完整，先做）**：本文档不是自足全文，正文由本文各步与 `prompts/_common.txt` 的公共片段拼成，**片段清单**：`primary` / `priority-rules` / `isolation` / `intro-rules` / `env-guard` / `scope-boundary` / `baseline` / `baseline-and-compat` / `timeout` / `build-parallel` / `compat` / `final-verify` / `delivery` / `no-self-dispatch`（次序见下）。
**装配状态按内容判定**："这份内容有没有被 AsciiDoc 处理器装配过"是判据，页面像不像渲染过不是；未经装配的原始文本里 `include\::_common.txt[tag=…]` 不会被展开、只是普通文字，须先读同目录的 `prompts/_common.txt`、把各 tag 正文补齐后再执行（**`build-parallel` 也在须引入之列**，漏列即漏读）；原始文件的两条路径与"站点渲染视图**不是**跳过补齐的理由"那条实测，**唯一落点＝`prompts/_common.txt` 顶部的「查看与复制方式」**，本处不复述。`primary` / `priority-rules` / `isolation` 三段是**方向与观念的前提**、须最先读入：

1. `primary`：本任务唯一主侧重（方向，不符合即方向错误）——片段中的 `{主侧重}` 取本提示词的值『检查修复问题』；
2. `priority-rules`：优先级规则（按业界共识分级执行，指明哪里是重点）；
3. `isolation`：隔离要求（不混用其他提示词、不做跨任务顺手改动）；
4. `intro-rules` / `baseline` / `final-verify` / `delivery` 与本文档第 2-6 步：其余公共步骤与任务步骤；**`baseline-and-compat`**（动手前）接在「规范与基线」（第 1 步）之后，**`timeout`**（每次操作的超时与超时后处置）紧随其后，**`build-parallel`**（要跑构建/测试时）接在「回归自检」之后，**`compat`**（改动后）接在「最终验证」之前；
5. `scope-boundary`：**变更范围只限当前项目**（未声明即拒绝越界改动，引用不等于授权）；
6. `env-guard`：**只在命中环境标志时按专用口径执行**（`printenv CNB_EVENT` 非空 且 触发内容含 `@<Agent名>`），未命中就按其末尾的中性口径办。

2. 全量检查：逐模块检查全部代码与文档的问题（代码：规范符合性、重复/坏味道、命名、注释、异常与边界、安全隐患、日志、资源与缓存生命周期等；文档：内容与代码不符、描述缺失/过时、格式与命名不规范等；测试：用例缺失/断言无效/编号与文档不一致等），分级编号成清单写入 tmp/ 作核对依据（每项须标明类型：代码问题/文档问题/测试问题，以及判定"明确"还是"待确认"），不得遗漏模块与文件。**本步只检查与记录，不改任何代码或文档**（改动一律在第 3、4 步进行）。
3. 直接修复（仅下述两类，其余不动）：**动手前须已定基线**（既有校验手段已扫描、既有用例完整可用者已跑通并留证）；**调整内容一类改动（含新增与调整）动手前须先检索现成可参照的标准与更优设计**——本步的触发点＝凡是"新增与调整"性质的修复都先查一遍有没有现成的标准与设计，有更优的设计就用它；查证范围与判定标准在 `baseline-and-compat` 片段，本步不重述；**明确有问题的、无争议的问题直接修复（L1）**——适用：违反项目规范、明确的缺陷或错误（编译/运行错误、逻辑错误、NPE、资源未释放、并发问题、性能隐患等），以及**文档问题与测试用例问题**（内容与代码不符、描述缺失/过时、格式命名不规范、用例缺失或断言无效、编号与测试文档不一致等，此类直接修复、无需确认；但若该修复会改变既有行为或对外契约，则转第 4 步待确认）。修复须遵循规范、做最小目标改动，不擅自扩大改动范围；有取舍的在代码注释与设计/测试文档记录依据与边界。**没有问题的不重构（L1）**：不得修改无问题的代码，不得做与问题无关的"顺手重构/优化/重命名/挪动代码/调整格式"；仅当不重构就无法修复该问题、或重构本身就是该问题的修复手段时，才允许改必要部分并说明理由。**重构性质、非问题驱动的改动不得在本任务中夹带（L1）**——需要时改用重构提示词。
4. 待确认问题：**问题不明确、有争议、或可修可不修的，一律先确认、不直接改（L1）**——如是否属于问题的判断有分歧、有多种可选方案、规范未明确、会改变既有行为或兼容性、影响面不清（如涉及既有对外契约/公共 API/其他模块调用）等；"可修可不修"指不影响正确性与可维护性、属风格偏好或收益极低的改动（过于细节、无实际影响的问题按矫情原则不作提示）。对此类问题：在 tmp/ 清单中整理出**确认清单**（逐条写明：问题描述、涉及文件与位置、疑似原因、可选方案与各自影响、建议与理由、若不处理的后果），**一次性集中向用户确认（L1）**，不得擅自改动、不得只确认一部分就动手、不得边改边问；未获确认前保持原状，确认后再按第 3 步规则修复，可在本任务内继续完成。判断不准时按"待确认"处理，宁可确认也不要误改。
5. 完善补齐：同步补注释、更新设计/测试文档、补齐缺失用例（文档与用例问题按第 3 步直接修复，但**既有用例不得为迁就改动而改判**——除相关功能被显式移除（先经确认）外，既有用例须原样通过、**新老用例同时成立**）；不新增与本次问题无关的内容。
6. 回归自检：逐一复查全部修复点，确认未引入新问题（无新增编译/静态警告、不破坏既有行为与用例、不影响调用方）；对第 4 步确认后修复的部分一并复查。

完成后汇报：**先回报主侧重（"检查修复问题"）的达成情况**——本次检查了哪些模块、查出多少问题、各问题的处理状态（已修复/待确认/不处理及原因）；**"本次检查未发现问题、按主侧重结束"也是完整结论**（不得为"有产出"而动手重构）。随后汇报：各步骤执行情况、问题清单（编号）与处理状态、待确认清单的确认结果、验证结果、改动文件清单（未发现问题时应为空，且须说明）
