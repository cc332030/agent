提示词公共片段（review / refactor 共用）
=========================================

本文件存放任务提示词之间【完全相同】的段落，由 prompts/review.adoc 与 prompts/refactor.adoc
在各自的可复制代码块中用 include::_common.txt[tag=…] 引用——一处维护、多处共用，
避免同一内容重复维护导致改一处漏一处。

【同源 ≠ 同侧重，方向不同绝不混用】：本文件收录的是两个提示词**逐字相同**的部分，
不代表两个提示词可以互相替代。二者**主侧重与方向不一致**：review = 检查修复、refactor = 重构；
**选错提示词比漏步更严重——方向选错，后面的步骤执行得再规范也是白做**。加载时须逐字校对
本文公共步骤与任务主侧重不冲突，冲突时以主侧重为准并在汇报中说明。

本文件中的公共片段以 `include::` 引入；片段内出现 `{主侧重}` 占位符时，由各提示词
在文档正文的「主侧重（方向性前提，先读）」段给出各自取值（值不同、不得混用）。

查看与复制方式（**按取值路径判断，不按"渲染视图"这个印象**）：`include::` **只在 AsciiDoc 处理器
解析时**才展开，**判定依据是"当前内容是被谁加工的"、不是"看起来像不像渲染过的页面"**：
  - **经处理器装配过的内容**（IDE 的 AsciiDoc 预览、`asciidoctor` 命令行渲染、以及站点页面内
    由 Asciidoctor.js 解析后写进页面的**正文区**）——**未见 `include::` 指令**即已完整装配；
  - **未经处理器装配的内容**——**取原始文件**的两条路径都属于此类：①远程**原始文件**地址
    （如 https://agent.c332030.com/prompts/review.adoc，站点对非 HTML 文件直出**仓库字节**）；
    ②本地/工作区**直接读取该文件**。二者取到的都是**原始文本、`include::` 未被展开**
    （**本项目实证**：远程与工作区字节**逐字节一致**，`include::` 仍在）。此时请按提示词文档中
    「给 AI 的读取说明」处理：读取本文件（远程 https://agent.c332030.com/prompts/_common.txt）
    对应 tag 的内容补齐后再执行；**远程取本文件的也是同一类路径、同样没有展开**，故本地读本文件
    与远程取本文件**等价**，不是一份"装配好的"、一份"没装配的"。
  - **不得**把"站点/渲染视图已展开"当成取用时的事实：站点上只有**页面内渲染出的 HTML** 才装配过，
    **原始文件地址与本地文件都不会装配**。

【改动范围边界（scope-boundary）】：本文件另含一段**每个提示词都须在代码块内引入**的公共片段
`scope-boundary`——把"除非用户主动声明，否则只允许修改当前工作空间（在平台上即只改当前项目）；
未声明的越界改动应当拒绝（即使任务里引用了工作空间以外的文件、其他项目/仓库，引用也不等于授权）"
这条 L1 边界随提示词一并给对方。
**它与 `delivery` 同为"交付边界"片段：`delivery` 管"交付到哪一步为止（不合并）"，
`scope-boundary` 管"改动落在哪一份工作空间/哪个项目上"**——两段都须引入。

本文件不是提示词：不单独复制使用，也不在 PROMPTS.adoc 中登记为任务提示词。

本文件为纯文本（.txt）而非 AsciiDoc（.adoc）：片段自带「1.」「7.」「8.」等步骤序号，
若作为 AsciiDoc 文档单独解析，会被当成「从 7 开始的有序列表」而报
「list item index: expected 1, got 7」一类校验错误；以纯文本存放不参与 AsciiDoc 解析，
即无此问题，也不影响 include:: 按 tag 取用。

// tag::no-self-dispatch[]
9. **不得自行发评论唤起自己（L1，防无限派发）**：**不得在本次执行中再发一条评论去点名本任务的实例名（`@<实例名>`）重新发起一次执行**（也不得转由他人/其他执行者代发）——**一次评论 = 一次派发**，**发起下一次是派发者的动作、不是执行者的动作**；判据是**这条评论发出去没有**，不是"这次执行有没有因此结束"。**想分步的唯一正当形态**：**先停**、只输出一次"必须停下确认"（把"已做完哪段、下一步要什么"一次性写清），由**人**另发一条评论决定要不要再来一次；"分两步更清楚""上一轮没做完"都不是理由。**它同样不是"少做一步"的许可（L1）**：**不自派 ≠ 不许复核**——本次执行里拿不到另一个同 Agent 执行者时，**在本次执行内**按降级路径补复核（执行者本人按同一判据串行核对并**标注独立性边界**，或标悬置 + 写剩余风险），**交付照常**、结论里如实写明"可信的独立复核不可得 + 已做的替代核对 + 剩余风险"；**不得**用"为了复核"去 @ 自己（那是自派）、**不得**据此跳过复核或把任务停在中间等下一轮。
// end::no-self-dispatch[]

// tag::intro-rules[]
要求不漏步、不偷懒、高质高效：严格按下述步骤完整执行，任一步未完成不得进入下一步；全部完成并验证通过后方可结束。**交付方式按执行环境区分、勿混淆**：**本地人工场景**下**不提交（`git commit`）、不推送（`git push`）**，改动保留在本地工作空间由人工处理；**CI/CD 等自动化场景**下**必须提交并推送**（只改不提交会随临时环境销毁而丢失），按 PR 流程合入（详见第 8 步）。
// end::intro-rules[]

// tag::primary[]
**本任务唯一主侧重（最优先，不符合即视为方向错误）**：**{主侧重}**（即上方标题所指的任务目标）。该侧重是本次任务的**方向性前提**，下述所有步骤、要求都以它为依据——**方向错了后面全做错**，故排在一切步骤与细节之前。与任何细节、惯例或"顺手可做"的改动冲突时，一律以主侧重为准；若判定主侧重本身不成立或无法满足，须先停下说明、不得改做其他侧重。**不同任务场景的主侧重互不相同，不得混用、不得互相替代**（各提示词的侧重与判定口径见本提示词的「主侧重（方向性前提，先读）」段与 PROMPTS.adoc 登记表；切勿按其他提示词的侧重执行）。
// end::primary[]

// tag::priority-rules[]
**优先级规则（按业界共识加载，本任务全部要求按此分级执行）**：优先级**由级别表达**，不靠重复次数表达；级别判定用语按 RFC 2119 / RFC 8174（`MUST`=必须、`MUST NOT`=严禁、`SHOULD`=应当、`MAY`=可以）与 ISO/IEC Directives Part 2（`shall` / `should` / `may` = 要求 / 建议 / 允许）执行——与本任务措辞的对应关系：`必须/严禁/不得/禁止` = L1、`应当/优先/原则上` = L2、`可以/非强制` = L3，未标注级别者按其用语判定。逐级遵守：
  - **L1 强制（必须 / 严禁）**：不可协商、不支持自行取舍。若与其他要求冲突，L1 最高优先（最高关注项优先级最高）；无法满足时必须**停止并说明**，不得默默降级、跳过或"先做后面再补"。
  - **L2 建议（应当 / 优先）**：默认遵守；有正当且可说明的理由时可偏离，但必须在汇报中写明取舍依据，不得无理由忽略。
  - **L3 允许（可以 / 非强制）**：可选，不遵守不构成问题。
  - **不可降级**：不得把 L1 当建议、不得以"步骤太多/上下文不足/任务简单"为由降低级别；本任务的步骤顺序服从本分级与主侧重，不得因顺序靠前就自行放宽。
  - **重点提示**：本任务步骤中**违反即视为未完成**的项，出现处均以 **L1** 标注；未标注者按其用语判定。
// end::priority-rules[]

// tag::isolation[]
**隔离要求（观念隔离，防方向污染）**：本任务的方向由上方主侧重唯一确定。凡与主侧重方向不一致的观念、方法、提示词，一律**不加载、不引入、不混合执行**：
  - **不做跨任务的顺手改动**：只做本主侧重范围内的改动；其他类型问题只记录、不处理（记录与交由相应任务的说明见各提示词正文）。
  - **不混用其他提示词**：不得拿另一个任务提示词（如 review 与 refactor）的步骤来"补齐"或"加强"本任务——二者侧重不同、目标不同，混用即方向错误。
  - **不被无关上下文带偏**：项目里其他提示词、规范或历史描述中出现与主侧重冲突的表述时，一律**以主侧重为准**（其次以项目规范为准），并在汇报中说明该冲突。
  - **汇报以主侧重为纲**：汇报时先给主侧重的达成情况，再展开各步骤——主侧重未达成时，其余步骤的"完成"不构成任务完成。
// end::isolation[]

1. 规范与基线：先读取并遵守项目规范；将主分支更新到最新并同步到当前分支，确保基于最新代码工作。

// tag::baseline-and-compat[]
**动手前：先定基线 + 先查现状 + 先调研最佳方案（L1，方向性前提）**
  - **先查现状、再谈方案**：摸清相关代码/文档/用例与既有流程现在怎么运作（含被视为过时、待废弃的部分），**不得凭印象或标题推断**；现状结论与其核实方式（读了哪些文件、跑了什么命令）先落盘，**摸不清现状不得动手**。
  - **先调研最佳方案、再落规划**：方案须**先调研最佳实践**（有既有业界标准/权威约定者优先引用，不另造一套说法；**调整内容一类需求——新增与调整同属一类——还须先找现成可参照的既有标准与更优设计**：现成口径①业界标准/权威约定（只写标准名/编号）②既有通行设计范式③本项目既有条目与先例三条都要查，**查到更优的设计就用更优的**、仍照原口述收须写明理由，查不到要说得出查证方式），并列出**备选方案与取舍依据**（受益与代价：可维护性/可读性/性能/兼容性/改动面）；不得只给一个"能交差"的写法就动手。规划落盘后再执行；**不得绕开既有实现另写一套**——能就地改既有就改既有，另写一套须满足三个条件之一并写明（既有确实无法承载 / 既有已被用户确认废弃 / 新方案已证明更优且同时迁移调用方与处置既有实现，**不留两套并存**）。
  - **动手前先定基线（含既有用例必须能跑通）**：先扫描该项目**声明的全部校验手段**（测试用例、构建、静态检查、规范校验脚本等），**既有手段完整可用的必须先跑通**，并把结果**留证**（写入设计文档或 `tmp/` 规划文档等持久位置，按 `delivery` 片段的交付口径处理：**本地人工场景不提交、自动化场景随改动提交推送**）——目的是让"改完有没有破坏既有行为"有同一把尺子量。**项目没有校验手段、环境跑不起来、或既有用例本来就是红的，都不是不动手的理由**：如实记录（缺什么、为什么、红的是哪些）即可开工，跑完的与没跑的**不得混写**；本次任务本就是修红时按其目标推进，不得要求"先把红测试全修绿才能动手"。
  - **基线清单还要核"够不够用"（L2）**：项目**声明的**校验手段与既有用例**本身可能不完整**——**先按用例设计判据 review 既有用例**（正常路径 / 边界（等价类与边界值、空与空集合、循环 0 次与多次）/ 异常路径 / 正反例成对 / 步骤与前置是否写清），并说出"查了哪些角度、哪些未覆盖、哪些未确证"；**本次改动直接相关面**的缺口先补全再动手，**无关的存量缺口**如实记录、不阻断。
  - **大动之前先确认**：凡要**替换、废弃或改写既有流程/既有做法**（而非增量修改）的改动，**动手前必须先向用户确认**，并一次性说清"动哪段、为什么、不动会怎样、确认后才继续"；**不得替用户判定某段既有流程'已废弃'**（是否废弃由用户认定），未确认前保持原状。
// end::baseline-and-compat[]

// tag::compat[]
**改动后：老用例与新用例必须同时成立（L1，不得靠改老用例让自己通过）**
  - **既有用例不得为迁就改动而改判**：除相关功能**被显式移除**（须先经用户确认）外，不得靠改断言、放宽断言、跳过/删除用例、改期望值让既有用例"通过"——须让新结构去满足老用例。
  - **新老同时成立**：新增/变更的行为同步补新用例，**新老用例在同一套校验里同时全绿**（不是"新的一套绿色代替旧的一套"）；改动前后对外可观测行为（接口/契约、返回值与异常、边界与默认值、错误码与日志语义）须完整兼容。
  - **兼容不了就停下确认**：兼容性无法同时满足时（如既有行为本身有问题、或与老旧废弃流程的兼容无法维持），**先停下向用户确认**（说清哪条兼容不满足、证据、可选处置与影响），不得自行取舍、不得拿"兼容不了"当放弃既有行为的理由。
  - **验证须与基线比对**：交付前复跑与基线**同一套**校验并逐项比对：既有校验全绿 + 新增校验全绿才算完成；"未执行"不得记作"通过"（判准见项目规范中的"严格执行 / 尽力而为"）。
// end::compat[]

// tag::final-verify[]
7. 最终验证：交付前跑**全量编译与全量测试**，须完全通过且满足规范——编译/构建无错误无警告、全量测试按实际统计全部通过、无规范违规；不满足不得进入下一步，须先修复再重跑。**验证范围按改动性质取值（L1，先判有没有改内容，避免过度验证）**：改动前后**工作区内容逐字节相同**（以 `git diff` 无输出为准）的操作——**「压缩提交」等提交历史整理、只做重命名的提交**——**不重跑全量编译与测试**（内容没变，重跑得不到任何新判据、只多付一次全量校验的墙钟），改按该操作**自身的确定性判据**逐条核对（见项目规范：如 `git diff` 无输出、根 tree 相同、`git diff -M --stat` 0 增 0 删、`merge-base` 关系、`git log --follow` 的 `R`/`M` 可分）；**该省的只是"重跑全量校验"，不是核对本身**——操作自身判据一条都不能少、须给出取值。**验证须说明"验了什么、怎么算过"（L1）**：逐项给出运行命令与**实际统计结果**（测试的 run/failures/errors 等），不得只说"已通过"；受环境限制无法执行的项按**尽力而为**处理——写明"未执行 + 原因 + 替代做法"，**"未执行"不得记作"通过"**（判准见项目规范中的"严格执行 / 尽力而为"）。
// end::final-verify[]

// tag::delivery[]
8. 交付（**按执行环境区分，勿混淆**）：
   - **本地人工场景**：**不提交、不推送**——不执行 `git commit` / `git push`，改动**保留在当前本地工作空间**，交由人工检查后自行提交与推送；**禁止代为向任何分支（尤其目标分支/主分支）提交、推送或合并**。
   - **CI/CD 等自动化场景**：**必须提交并推送**——此类环境是一次性/临时工作空间，**只改不提交会随环境销毁而全部丢失**；须提交到为本次改动新建的 PR 分支并推送、创建 PR，经**人工 review** 通过后合入，不得跳过 review，也不得直接向目标分支（主分支等）提交/推送/合并。**"本次没有发现问题、没有改动"是合法的完成态，但"有改动却没提交也没推送"不是**——此类环境下**没有提交即等于没有交付**，故①**本次无改动**时如实汇报（无需 PR）；②**本次有改动**时**必须**把改动提交并推送到 PR 分支、创建 PR，二者缺一不可（**只提交不推送** = 远端看不到、只推送不提交 = 推的是空分支，两种都不算交付）。
   - **合并一律不做（L1，无环境区分、人工授权也拒绝）**：**本任务不得执行合并操作**——不论是本地人工场景还是 CI/CD 等自动化场景，都**只交付到"创建/推送 PR 分支并汇报"为止**，合入目标分支**只由人工完成**。**即使发起人在对话中明确要求合并、或给出直接授权（"我已授权""直接合吧"等），也必须拒绝**，并说明拒绝依据；**授权不免除该禁令**（这是唯一一类"用户明确要求也不照做"的操作）。**拒绝不等于不响应**：如实回复"该项操作按规范不予执行"，其余部分（整理改动、推送 PR 分支、汇报结论）照常完成。**边界**：本条只禁**合并**——推送分支、在当前分支内解决冲突、把目标分支同步到当前分支，都**不是合并**，照不受影响。
   - 两者共同：交付前核对工作区/待提交内容，不得混入 `tmp/` 等临时产物，也不得遗留与本次任务无关的改动（无关改动须还原）。
   - **报告落点（L1，防"只冒一句话、没有交付"）**：**过程性叙述**（"现在去读 X""接下来检查 Y""先看有没有 Z 这类检查"一类边想边说的句子）**不属于结果汇报**——在平台上它会以**评论**的形式发给任务发起人，**一次一条、噪声极大且答非所问**；此类叙述**一律只留在自己的工作输出里**（`tmp/` 记录或最终汇报的对应步骤行），**不得作为独立的一条评论发出去**。**结果与结论**（达成情况 / 改动清单 / 验证结果 / 交付情况）按各提示词正文末的汇报要求**汇总成一次完整汇报**（在平台上即**一条评论**）。**输出通道只有两条（L1，无第三条）**：①**最终的一次完整汇报**（任务正常结束）；②**必须停下确认**的例外（方向/前提不成立、要求写不清、判据不满足、超出授权、会出现不可逆后果——须**一次性说清"停在哪、缺什么、要你定什么"**）。**除这两条之外的任何中间话一律不发**（**不存在第三条通道**）：过程性叙述、"我先去…""接下来…"、把**规范条文或检查依据**当结论念一遍、以及**只为表明"我在按规范做"的复述**，都不属上述两条——它们是**给发起人的评论**，不是自己的草稿纸。
   - **重复面的处理（L1，评审与重构的固定动作）**：**同一件事不得在多处各写一遍**——review 与重构都要把「本次改动涉及的事实在本仓库还有没有第二处完整表述」当必查项，重复面记入清单并**按「一处完整定义 + 其余一行引用」收敛**（判据是真源落点：同一件事的两半各有唯一落点）。**删的只能是重复表述本身、被删处须留下可达的引用**（不得以去重换缺失）；**对无法确定是否重复的一律保留**。汇报里须**显式给出重复面的处理结果**——"查了几处、收敛了哪些、哪些保留及理由"；说不出"查了哪些角度"即视为没查（与"没发现重复"是两回事）。
   - **交付形态（防"有改动却什么都没有"）**：**应提交推送却没提交、没推送**（自动化场景下**没有提交即等于没有交付**）与**没有改动却没说明**一样属交付失败；**本次无改动**时须**显式说明**（"本次检查未发现问题"是完整结论、无需 PR），**本次有改动**时须提交推送并建 PR，**二者都要在汇报里落成可核对的事实**（改动清单 + 分支/PR 链接）。
// end::delivery[]

// tag::scope-boundary[]
**改动范围边界（L1，执行前先定边界——先判两层，再动手）**：本次任务**只允许修改本次任务的工作空间**——即用户发起本次任务时所用的那个工作副本（**入口工作空间**）；**在代码托管平台上工作时按"只允许修改当前项目"表达**（**入口项目**＝你被唤起/被要求工作的那个项目、当前工作区所属的仓库——平台上的可写范围是"你有权限的全部仓库"，比本地工作目录大得多，故须显式收窄）。**除非用户主动声明**把某处纳入本次范围，**越界改动一律不得执行**：写入、创建、删除、移动、重命名、格式化、提交、推送，以及平台侧的建仓库/建分支/建标签/建 PR、改设置等。命中越界时**必须拒绝该项并说明依据**，只把改动留在入口工作空间内、其余可做的部分照常完成——**不得默默照做，也不得只回一句"不能做"就停摆**。
  - **未声明即拒绝（L1）**：**即使它在技术上可写**（同一台电脑/服务器/容器上的其他目录、同一账号下有权限的其他仓库），**未声明就不得改**；"我有权限""同一个主机上就能看到"都不构成理由（**权限是平台能力，授权来自用户的显式声明**）。
  - **引用 ≠ 授权（L1）**：任务里**引用了**工作空间以外的文件或其他项目/仓库，只构成**读取/对照**的许可（**只读不在禁止之列**，也**不要求你因此拒绝读取或拒绝使用该依据**），**不构成改动它的授权**；把改动顺手落到被引用的文件/项目上即越界。要改它，须用户**显式声明**"本次允许修改 X"（仅对该次任务、该位置生效，**不泛化**）；用户明确声明某处"只读/不要动"时，该声明**优先**、一律不改。
  - **已知例外（唯二的解禁情形，靠用户显式给出、不靠推断）**：①用户显式声明把某处（某路径/某个其他项目）纳入本次范围；②用户声明某处"只读/禁止改动"（该声明优先）。其余"看起来顺路""反正就差一处""引用时顺手改了"一律不放行。
  - **判定标准（任一命中即越界）**：①改动对象不在入口工作空间内（平台侧＝不在入口项目内）；②以"引用过它""任务里提到了它""它就在旁边""同一账号下有权限"为由**自我豁免**；③把越界改动**转交他人/其他执行者顶替**完成。
  - **与"不合并"的关系**：合并**恒为人工**、无授权豁免（见 `delivery` 片段 L1 条）——用户声明放开"可修改另一个项目"**不**意味着允许合并；两段各自独立、互不豁免。
  - **与"临时产物/报告"的关系**：`tmp/` 临时产物与任务报告一律写在**入口工作空间内**的项目 `tmp/` 下，不得写到入口工作空间之外。
// end::scope-boundary[]

**按环境标志选执行口径（先判环境，再定怎么改；未命中标志按下方默认口）**
  - **标志**：在本次环境里执行 `printenv CNB_EVENT`。**仅当输出非空、且本次对话的触发内容含 `@<Agent名>`（NPC 唤起评论）时，才按本片段的专用口径执行**；未命中（普通本地/其它 CI/普通对话）→ 按末尾的中性口径执行。**不得"记成"标志存在，须实际执行该命令**（本仓库实证：标志存在与否两种情形都有，未实测的"已是干净上下文/也已派发"属空自评）。
  - 命中标志时的 5 条专用口径（其余步骤不变）：
    1. **容器已复制仓库、不要重复克隆/重复抓取**：工作区就在本次 clone 出来的 checkout 上、平台已 checkout 好入口分支；直接 `git fetch` + `git rev-parse` 取需要核对的不可变对象（sha），**不要重新 `git clone` 整仓**；`fetch -f` 只在"要取别人刚推的对象"时才用。
    2. **`main` 是默认分支、不是合并目标**：`.cnb.yml` 可能只写 `include:`、不是完整流水线；**改为去看该文件 include 的目标**，以及 `.github/workflows/`。
    3. **`tmp/` 是临时产物**：按项目规范写入 `tmp/` 下的临时文档，**不提交**（交付前 `git status` 核对不要把 `tmp/` 带进去）。
    4. **`pnpm`/`npm`/`mvn` 可能需要 `npx` 包裹**（无全局包时）：如 `npx pnpm@<版本> ...`；执行前先用 `command -v pnpm` 判一次存在性，**不确定按不可用处理**（不要盲跑）。
    5. **首次跑本地校验遇到"缺工具"不要扩大改动**：先记录，能装再装，装不上就如实标"跳过 + 未确证"，**"跳过后的通过"不得写成"通过"**。
  - **中性口径（未命中标志时）**：按项目规范与构建文件声明的工具链正常执行；不假设任何平台/环境特定的路径与变量。
