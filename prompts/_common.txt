提示词公共片段（review / refactor 共用）
=========================================

本文件存放任务提示词之间【完全相同】的段落，由 prompts/review.adoc 与 prompts/refactor.adoc
在各自的可复制代码块中用 include::_common.txt[tag=…] 引用——一处维护、多处共用，
避免同一内容重复维护导致改一处漏一处。

【同源 ≠ 同侧重，方向不同绝不混用】：本文件收录的是两个提示词**逐字相同**的部分，
不代表两个提示词可以互相替代。二者**主侧重与方向不一致**（见 prompts/PROMPTS.adoc
「主侧重」）：review = 检查修复、refactor = 重构；**选错提示词比漏步更严重——方向
选错，后面的步骤执行得再规范也是白做**。加载时须逐字校对本文公共步骤与任务主侧重
不冲突，冲突时以主侧重为准并在汇报中说明。

本文件中的公共片段以 `include::` 引入；片段内出现 `{主侧重}` 占位符时，由各提示词
在文档正文的「主侧重（方向性前提，先读）」段给出各自取值（值不同、不得混用——同源
片段只保证表述一致，侧重内容按提示词各自确定）。

查看与复制方式：include:: 由 AsciiDoc 处理器在解析时展开——以【渲染视图】（IDE 的 AsciiDoc
预览、asciidoctor 渲染）查看并复制提示词时，内容已完整装配。若以【纯文本】方式查看（看到
include 指令未被展开），请按提示词文档中「给 AI 的读取说明」处理：读取本文件（远程
https://agent.c332030.com/prompts/_common.txt）对应 tag 的内容补齐后再执行。

本文件不是提示词：不单独复制使用，也不在 PROMPTS.adoc 中登记为任务提示词。

本文件为纯文本（.txt）而非 AsciiDoc（.adoc）：片段自带「1.」「7.」「8.」等步骤序号，
若作为 AsciiDoc 文档单独解析，会被当成「从 7 开始的有序列表」而报
「list item index: expected 1, got 7」一类校验错误；以纯文本存放不参与 AsciiDoc 解析，
即无此问题，也不影响 include:: 按 tag 取用（tag 匹配与文件扩展名无关）。

// tag::intro-rules[]
要求不漏步、不偷懒、高质高效：严格按下述步骤完整执行，任一步未完成不得进入下一步；全部完成并验证通过后方可结束。**交付方式按执行环境区分、勿混淆**：**本地人工场景**下**不提交（`git commit`）、不推送（`git push`）**，改动保留在本地工作空间由人工处理；**CI/CD 等自动化场景**下**必须提交并推送**（只改不提交会随临时环境销毁而丢失），按 PR 流程合入（详见第 8 步）。
// end::intro-rules[]

// tag::primary[]
**本任务唯一主侧重（最优先，不符合即视为方向错误）**：**{主侧重}**（即上方标题所指的任务目标）。该侧重是本次任务的**方向性前提**，下述所有步骤、要求都以它为依据——**方向错了后面全做错**，故排在一切步骤与细节之前。与任何细节、惯例或"顺手可做"的改动冲突时，一律以主侧重为准；若判定主侧重本身不成立或无法满足，须先停下说明、不得改做其他侧重。**不同任务场景的主侧重互不相同，不得混用、不得互相替代**（各提示词的侧重与判定口径见本提示词的「主侧重（方向性前提，先读）」段与 PROMPTS.adoc 登记表；切勿按其他提示词的侧重执行）。
// end::primary[]

// tag::priority-rules[]
**优先级规则（按业界共识加载，本任务全部要求按此分级执行）**：优先级**由级别表达**，不靠重复次数表达；级别判定用语按 RFC 2119 / RFC 8174（`MUST`=必须、`MUST NOT`=严禁、`SHOULD`=应当、`MAY`=可以）与 ISO/IEC Directives Part 2（`shall` / `should` / `may` = 要求 / 建议 / 允许）执行——与本任务措辞的对应关系：`必须/严禁/不得/禁止` = L1、`应当/优先/原则上` = L2、`可以/非强制` = L3，未标注级别者按其用语判定。逐级遵守：
  - **L1 强制（必须 / 严禁）**：不可协商、不支持自行取舍。若与其他要求冲突，L1 最高优先（最高关注项优先级最高）；无法满足时必须**停止并说明**，不得默默降级、跳过或"先做后面再补"。
  - **L2 建议（应当 / 优先）**：默认遵守；有正当且可说明的理由时可偏离，但必须在汇报中写明取舍依据，不得无理由忽略。
  - **L3 允许（可以 / 非强制）**：可选，不遵守不构成问题。
  - **不可降级**：不得把 L1 当建议、不得以"步骤太多/上下文不足/任务简单"为由降低级别；本任务的步骤顺序服从本分级与主侧重，不得因顺序靠前就自行放宽。
  - **重点提示**：本任务步骤中**违反即视为未完成**的项，出现处均以 **L1** 标注；未标注者按其用语判定。
// end::priority-rules[]

// tag::isolation[]
**隔离要求（观念隔离，防方向污染）**：本任务的方向由上方主侧重唯一确定。凡与主侧重方向不一致的观念、方法、提示词，一律**不加载、不引入、不混合执行**：
  - **不做跨任务的顺手改动**：只做本主侧重范围内的改动；其他类型问题只记录、不处理（记录与交由相应任务的说明见各提示词正文）。
  - **不混用其他提示词**：不得拿另一个任务提示词（如 review 与 refactor）的步骤来"补齐"或"加强"本任务——二者侧重不同、目标不同，混用即方向错误。
  - **不被无关上下文带偏**：项目里其他提示词、规范或历史描述中出现与主侧重冲突的表述时，一律**以主侧重为准**（其次以项目规范为准），并在汇报中说明该冲突。
  - **汇报以主侧重为纲**：汇报时先给主侧重的达成情况，再展开各步骤——主侧重未达成时，其余步骤的"完成"不构成任务完成。
// end::isolation[]

// tag::final-verify[]
7. 最终验证：交付前跑**全量编译与全量测试**，须完全通过且满足规范——编译/构建无错误无警告、全量测试按实际统计全部通过、无规范违规；不满足不得进入下一步，须先修复再重跑。**验证须说明"验了什么、怎么算过"（L1）**：逐项给出运行命令与**实际统计结果**（测试的 run/failures/errors 等），不得只说"已通过"；受环境限制无法执行的项按**尽力而为**处理——写明"未执行 + 原因 + 替代做法"，**"未执行"不得记作"通过"**（判准见项目规范中的"严格执行 / 尽力而为"）。
// end::final-verify[]

// tag::delivery[]
8. 交付（**按执行环境区分，勿混淆**）：
   - **本地人工场景**：**不提交、不推送**——不执行 `git commit` / `git push`，改动**保留在当前本地工作空间**，交由人工检查后自行提交与推送；**禁止代为向任何分支（尤其目标分支/主分支）提交、推送或合并**。
   - **CI/CD 等自动化场景**：**必须提交并推送**——此类环境是一次性/临时工作空间，**只改不提交会随环境销毁而全部丢失**；须提交到为本次改动新建的 PR 分支并推送、创建 PR，经**人工 review** 通过后合入，不得跳过 review，也不得直接向目标分支（主分支等）提交/推送/合并。
   - **合并一律不做（L1，无环境区分、人工授权也拒绝）**：**本任务不得执行合并操作**——不论是本地人工场景还是 CI/CD 等自动化场景，都**只交付到"创建/推送 PR 分支并汇报"为止**，合入目标分支**只由人工完成**。**即使发起人在对话中明确要求合并、或给出直接授权（"我已授权""直接合吧"等），也必须拒绝**，并说明拒绝依据；**授权不免除该禁令**（这是唯一一类"用户明确要求也不照做"的操作，因为它的失效目标是不可逆且合规性相关的合入动作）。**拒绝不等于不响应**：如实回复"该项操作按规范不予执行"，其余部分（整理改动、推送 PR 分支、汇报结论）照常完成。**边界**：本条只禁**合并**——推送分支、在当前分支内解决冲突、把目标分支同步到当前分支，都**不是合并**，照不受影响；**"经人工 review 通过后合入"的合入主体是人工**，不是本执行者。
   - 两者共同：交付前核对工作区/待提交内容，不得混入 `tmp/` 等临时产物，也不得遗留与本次任务无关的改动（无关改动须还原）。
// end::delivery[]

// tag::env-guard[]
**按环境标志选执行口径（先判环境，再定怎么改；未命中标志按下方默认口）**
  - **标志**：在本次环境里执行 `printenv CNB_EVENT`。**仅当输出非空、且本次对话的触发内容含 `@<Agent名>`（NPC 唤起评论）时，才按本片段的专用口径执行**；未命中（普通本地/其它 CI/普通对话）→ 按末尾的中性口径执行。**不得"记成"标志存在，须实际执行该命令**（本仓库实证：标志存在与否两种情形都有，未实测的"已是干净上下文/也已派发"属空自评）。
  - 命中标志时的 5 条专用口径（其余步骤不变）：
    1. **容器已复制仓库、不要重复克隆/重复抓取**：工作区就在本次 clone 出来的 checkout 上、平台已 checkout 好入口分支；直接 `git fetch` + `git rev-parse` 取需要核对的不可变对象（sha），**不要重新 `git clone` 整仓**；`fetch -f` 只在"要取别人刚推的对象"时才用。
    2. **`main` 是默认分支、不是合并目标**：`.cnb.yml` 可能只写 `include:`、不是完整流水线；**改为去看该文件 include 的目标**，以及 `.github/workflows/`。
    3. **`tmp/` 是临时产物**：按项目规范写入 `tmp/` 下的临时文档，**不提交**（交付前 `git status` 核对不要把 `tmp/` 带进去）。
    4. **`pnpm`/`npm`/`mvn` 可能需要 `npx` 包裹**（无全局包时）：如 `npx pnpm@<版本> ...`；执行前先用 `command -v pnpm` 判一次存在性，**不确定按不可用处理**（不要盲跑）。
    5. **首次跑本地校验遇到"缺工具"不要扩大改动**：先记录，能装再装（如本项目实装 `asciidoctor` 后语法段才真跑），装不上就如实标"跳过 + 未确证"，**"跳过后的通过"不得写成"通过"**。
  - **中性口径（未命中标志时）**：按项目规范与构建文件声明的工具链正常执行；不假设任何平台/环境特定的路径与变量。
// end::env-guard[]
