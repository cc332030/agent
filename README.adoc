= Agent 相关

本仓库用于存储 agent 相关信息，内容包括 **agent 执行规范** 与 **公共任务提示词**（后者为复制即用的任务指令，见下）。

== 一键安装（复制给 AI）

安装只需执行一次：把下面这一行提示词复制给 AI，AI 会读取 link:INSTALL.adoc[]（安装文档），并在目标项目根目录创建入口文档（指向远程通用规范入口 `AGENTS_COMMON.adoc`），从而把规范**持久化**到项目里——后续任意会话只需读取该入口即可重新加载并持续遵守规范，无需再次重复安装。入口**默认命名 `AGENTS.adoc`**；根目录**已存在 `AGENTS.md`** 时就地融合到 `AGENTS.md`（不重命名、不删除、不另建），以兼容各平台对 `AGENTS.md` 的固有识别。

将下方这一行提示词复制给任意 AI 即可完成接入（通用任意平台）。AI 直接阅读本 README 时，也可按该提示词自行接入：

[listing]
----
请按 https://agent.c332030.com/INSTALL.adoc 完成本项目 agent 规范安装。
----

== 引用方式

规范适用于任何语言、任何项目，将 `AGENTS_COMMON.adoc` 作为规范入口交给 agent 即可。入口引用方式二选一：

* https 公网静态路径：https://agent.c332030.com/AGENTS_COMMON.adoc
* 本地相对路径或绝对路径：直接使用本仓库内的 `AGENTS_COMMON.adoc`

`AGENTS_COMMON.adoc` 与其 `specs/` 目录始终位于同一目录，文中 `specs/...` 均相对入口所在目录解析，故两种引用方式下规范都能正常解析加载。**引用方只需要 `AGENTS_COMMON.adoc` 与 `specs/`**：公共内容自足——规则一律在入口与 `specs/` 内表达，不指向引用方看不到的私有落点（引用了只会读到死链）。本仓库另有一层只对"维护这类规范集合的项目"成立的维护方自查层，**不随公共内容分发、由本仓库自己的项目规范入口登记**，普通引用方无需也不应引入。

**首次接入（安装）**：给项目接入时，走 link:INSTALL.adoc[] 的安装流程——让 AI 在项目根目录创建入口文档（指向远程规范），实现持久化；后续会话只需读取该入口。**入口文件名默认 `AGENTS.adoc`**，若根目录**已存在 `AGENTS.md`**（其他平台/工具的默认命名）则就地融合到 `AGENTS.md`——**不重命名、不删除、不另建**，避免打断既有的平台识别或分叉出两个入口。若入口已存在，`INSTALL.adoc` 会保留原文档并在其开头融合，不覆盖（项目自身规范优先于通用规范）。

== 任务提示词（复制给 AI）

除安装外，本仓库还提供**公共任务提示词**：按任务场景组织的、复制即可直接使用的 agent 指令，用于让 AI 干活时不漏步、不偷懒、高质高效。**非规范**内容，不随 `specs/` 分发、不进规范加载链。

统一入口 link:PROMPTS.adoc[]（`PROMPTS.adoc`，登记全部提示词及其用途、二者分工与维护约定，网站右上角"提示词"链接指向它；**提示词的说明以该文件为唯一落点，此处不重复**）；具体提示词文档存放于 `prompts/` 目录。用法：打开对应提示词文档，把其中 `[listing]` 代码块内的文字**完整复制**给 AI 即可（与上方"一键安装"用法一致）。

== 目录结构

* `INSTALL.adoc`（根目录） — **安装文档**（面向目标项目接入）：指导 agent 在目标项目根目录创建入口文档（指向远程 `AGENTS_COMMON.adoc`），把规范**持久化**到项目，避免仅当前会话遵守、下次丢失；**入口文件名默认 `AGENTS.adoc`，并兼容 `AGENTS.md`**——已存在 `AGENTS.md` 时就地融合到该文件、不重命名/不删除/不另建（`AGENTS.md` 同为各平台固有命名）；对**已存在**入口文档的项目做兼容处理——保留原文档、开头融合、不覆盖。其中作为入口模板的代码块要求**逐字原样保留**（含换行与空行，防止 AI 折叠导致样式改变），该要求由本仓库的机械校验钉住。不随 `specs/` 分发，供引用方接入使用。
* `AGENTS_COMMON.adoc` — **通用规范**入口与加载调度器（必加载）：定义规范的分类、懒加载与"按项目类型加载且不漏"的规则，并登记全部规范文件。本文件及其 `specs/` 会被**引用方项目引入**。*与仓库根目录 `AGENTS.adoc`（本项目自身规范入口）区分——根目录 `AGENTS.adoc` 会被平台自动识别为"当前项目自身规范"，而通用规范入口 `AGENTS_COMMON.adoc`（同样位于仓库根目录，但以 `AGENTS_COMMON.adoc` 命名避开平台识别）供引用方项目引入*。
* `AGENTS.adoc`（根目录） — **Agent 项目自身规范**（本仓库维护专用，不随规范集合分发）：声明公共内容、项目自身维护层与本仓库工具的隔离，并收录规范集合的维护规则（规范管理）与检查脚本/CI 的使用说明。普通引用方项目无需也不应引入本文件。本文件采用 `AGENTS.adoc` 命名、位于仓库根目录，会被平台自动识别为本仓库的 agent 规范。
* `library/`（根目录） — **图书馆**（**本仓库私有、不随规范分发**；按需加载、不进任何常驻层）：集中存放本项目**需要找依据**的东西——规则与决策背后的**可逐字核对的依据**（外部标准原文摘录与"标准确实支持该条"的映射、当初的失效与实证、反例），以及技术选型与组织约定的依据；入口 link:library/README.adoc[]（`library/README.adoc`，登记全部主题）。**放在仓库根而非 `specs/` 下**：`specs/**` 是随规范分发给引用方的公共内容，而图书馆天然含**只对本项目成立**的内容（当初的失效、取舍、实证、选型理由）；项目自己的依据库就是项目自己的内容。规则本体仍在 `specs/` 各文件，图书馆只补依据、**不复制规则**
* `specs/` — **公共内容**分类目录，按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储（以下各层面向**任意项目**，随入口分发给引用方）：
  ** `specs/core/` — 必加载层（每次会话都加载，**只放底线**）：执行原则（含规范变更的存量处理、范围控制、破坏性操作、自检落点、**任务生命周期与节点自查**）
  ** `specs/general/` — 通用层：通用编码（含**既有实现与先例优先**：编码前先查项目已有能力与先例、有则复用并跟随先例，禁止用手写原生写法绕过项目自有工具类与已引入库；含**配置类不写逻辑**：`@ConfigurationProperties` 一类承载配置的类只保持 POJO 基本功能，逻辑下沉到 utils/service；含**抽象与接入成本**：对外能力的可替换点须有唯一装配点、须有可用默认，不得要求多个使用点各提供一遍同一实现/配置）、文档、变更日志（changelog）、git、code review、agent 协作、编码与语言无关（encoding，含**换行符权威判据**：仓库 LF 基准、`.bat`/`.cmd` 必须 CRLF、由 `.gitattributes` 固定）、代码安全（security）、依赖管理（dependency）、测试、脚本、**CI/CD（`ci-cd.adoc`，含校验链完整、触发与作用范围、依赖与外部资源可用性、超时与资源）**、验证（`verify.adoc`，含验证与运行契约）；项目类型层规范（如 doc-tool.adoc）也存放于本目录，按项目主动声明懒加载
  ** `specs/stack/` — 技术栈层：java、java 语法（含**工具类使用优先级**：项目自有工具类/已引入库优先于 JDK 原生写法）、spring、maven、java 测试（含测试类命名契约 `Tests`/`BootTests`/`PerfTests`/`IT`）、bash/python/powershell 脚本（按项目类型加载，各自写明行尾要求：bash/python 用 LF、powershell 含 `.bat` 启动脚本用 CRLF）
  ** `specs/platform/` — 平台层：cnb（CNB 平台上的分支与合并请求统一、冲突处理、**对象钉定与可追溯**（派发与复核钉定 commit sha、压缩提交/强推的对应关系、CI 状态按 sn+sha 定位）、**协作与执行者可用性**）
* 维护方自查层（本仓库内另置一层目录）— **不由公共入口登记、不随公共内容分发**；由本仓库自己的项目规范入口 `AGENTS.adoc` 登记，**只在维护规范集合/共享资产集合的项目中加载**，普通引用方项目不加载。内容为：最高关注项与不可降级清单（P1-P6 级别、依据行）、规范集合自身的维护（归属判定、准入九问、定级口径、自身重构、拆分判据、提案校验）、维护方的验证义务（三视角动作、硬超时、三态台账、维护方侧的具名抓手）、公共内容被加载时的可控性清单（影响面/成本/可控性三维）。
* `CHANGELOG.adoc`（根目录） — **统一变更日志**（时间倒序，最新在上）：集中记录本规范集合的对外变更（只记影响、不记过程，见 link:specs/general/changelog.adoc[]），是变更记录的唯一落点（机制见 link:specs/general/doc-design.adoc[]「版本与变更记录」）。
* `script/` — 配套脚本目录（多数为 Agent 项目自身工具，见根目录 `AGENTS.adoc`）：
  ** `clean_tmp.py` — 清理目标项目 `tmp/` 临时产物的安全脚本（以当前工作目录为项目根，内置路径穿越防护）；无需下载到目标项目，可远程加载执行（详见脚本头部用法）
* `PROMPTS.adoc`（根目录） — **公共任务提示词入口**（非规范，不随 `specs/` 分发、不进规范加载链）：登记全部任务提示词及其用途，是提示词的统一入口（网站右上角"提示词"链接指向本文件）；具体提示词文档存放于 `prompts/` 目录
* `prompts/` — 公共任务提示词文档目录（**非规范**）：面向不同任务场景、可复制直接使用的 agent 任务指令，用于让 AI 干活时不漏步、不偷懒、高质高效。如 link:prompts/review.adoc[]（项目问题检查修复）、link:prompts/refactor.adoc[]（项目重构），完整清单见 link:PROMPTS.adoc[]；`_` 前缀文件为**公共片段**（如 link:prompts/_common.txt[]），由提示词 `include::` 引用共用、非提示词不单独使用
* `index.html` — 网站首页，渲染方式见「网站首页」一节

== 使用要点

* 规范按分类懒加载，但"按项目类型加载且不漏"是底线——如 Java 项目写代码必须加载 Java 编码规范；**公共内容自足**：`AGENTS_COMMON.adoc` 与 `specs/` 里的规则一律在公共内容内表达，**不引用引用方看不到的私有落点**；只对维护这类规范集合成立的内容另置维护方自查层（由本仓库自己的项目规范入口登记），普通引用方项目不加载。
* 规范条目分 **L1 强制 / L2 建议 / L3 允许** 三级，并有**最高关注项**（不可降级、重构首保）：分级定义、各级遵守要求与最高关注项见 link:specs/core/execution.adoc[]「分级与最高关注项」（依据 RFC 2119 / RFC 8174、ISO/IEC Directives Part 2）。强调用「升级别 + 单一定义 + 引用」，不靠重复书写。
* **常驻层只放底线**：必加载层每次会话都无条件加载，故只放 L1 底线、最高关注项及其引用落点；**方法论、依据论证、示例与元规范一律放通用层**（用到才加载）；只对维护这类规范集合成立的维护类规范另置维护方自查层（普通引用方不加载）——规范写得多不等于管得住，**放错层会直接挤占每次会话的上下文、反过来捆住执行者**。
* **同一条规则有两种读法**：**执行**时只给"怎么走"（规则 + 判定标准 + 依据名），多出来的"为什么走这条路"是占注意力的噪音；**思考与决策**（新增/调整/定级/重构规范、有取舍或争议、复盘）时才需要依据与取舍。两形态同源、不复制两份，**依据只压缩为名称/编号、不得整段删除**；重构的验收除"内容不丢"外还须核对**有效性未被改坏**（判据未被压成口号、依据仍在、可见性仍在）。
* 提示词**侧重点不同、属方向性前提**：各提示词显式标注**主侧重**并按上述分级引入优先级（让 AI 按业界共识判断"哪里是重点"），并做观念隔离（不混用另一提示词的步骤）；登记表见 link:PROMPTS.adoc[]「优先级与隔离」。
* 通用规则与某技术栈专属规则分层存放，通用规则不重复收录进各栈。
* 换行符（行尾）按解释器分流、由仓库 `.gitattributes` 固定：内容以 **LF** 为基准，**Windows 批处理 `.bat`/`.cmd` 必须 CRLF**（LF-only 在 Windows 上直接执行失败）、PowerShell `.ps1` 用 CRLF；判据见 link:specs/general/encoding.adoc[]「换行符」「跨平台检出」，不靠人工手动调整。
* **改完规范的语义复核是"验证三视角一起过"**（判据在公共 link:specs/general/verify.adoc[]「验证与运行契约的落点」）：①**完整性**（改动的对象在改动前后是否等价、要点是否全保留）②**有效性与认知质量**（规范本体是否说得对、说得清、跑得动、判得了：判据可判定、依据仍在且说对了、机制在当前环境真会发生、从属者可加载、放对层且常驻代价在预算内、代价说得清）③**接纳面**（**被未知项目加载后的影响面/成本/可控性**：不静默推翻引用方约定、不默认改其工作区、不引入无降级路径的依赖、体积可控）；三视角**由同一个干净子 agent 一并回答**（一次读取、结论分栏，不重复派发），都过、各自留证才算完成。**"验证了什么、怎么算过、依据哪个标准"须能逐项枚举**（判据与标准出处见同节「验证总纲」「规范验证」「运行契约」）。
* **验证对象不止规范文件**：`prompts/`（会被未知项目复制执行）、随规范分发的工具（如 `script/clean_tmp.py`）等"会被外部执行"的产物同样按上述三视角核对。
* **从属者与能力：两处易漏的执行侧机制**：①**加载由已加载入口驱动**——子 agent、被主 agent 派发的分步任务不得以"没被派发这份规范"为由跳过加载，"上级已读过"不构成下级免责（约束随入口传递、不随上下文传递）；②**执行环境能力先自评**——能否新开会话/清空上下文、能否派发子 agent 等机制**不是每个环境都有**，须先判定（不确定按"不可用"），缺失时走降级路径并**如实记录**，不得照抄"已清洁上下文/已委派"式的空自评（判据见 link:specs/general/self-check.adoc[]「环境能力自评」）。
* **判准要分清"严格执行 / 尽力而为"**：L1/L2/L3 答"要求有多强"，"严格执行"（须逐次达成并给证据）与"尽力而为"（须尝试、须说明未达原因、不记通过）答"执行到什么程度算做到"——两者都须留证，"未执行"与"通过"不得混写；判准有疑问按"严格执行"处理并补判据（判据与判定动作见 link:specs/general/verify.adoc[]「判准维度：严格执行 / 尽力而为」）。
* **子 agent 复核必须自带硬超时、留证按三态台账**：语义复核派给子 agent（或外部复核者）时**必须设可判定的时限**，到点即视为失联并"**放弃 + 如实标悬置**"，**不得无限等待**（实证：把复核派给外部评审 NPC，多轮停在同一步 1 小时以上、结论未回传，只能人工中止）；**子任务一律由与执行者相同的 Agent 承担（不得点名外部 Agent/NPC）**——同 Agent 的子执行者不可用时，由发起方按同一判据组织等价复核（本地串行），并如实标注独立性边界（判据见 link:specs/general/collab.adoc[]「资源限制与感知」「协作方式」）。留证须是**可机械核对的三态台账**：**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附原因与剩余风险），三态各占一栏、不得合并——**"查不出"与"没做"须能分辨**（判据见 link:specs/general/verify.adoc[]「验证的效力等级」）。
* **合并一律不做（L1，人工授权也拒绝）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求**——不论本地人工场景还是自动化场景，都只交付到"创建/推送 PR 分支并汇报"为止，合入目标分支**只由人工完成**；**即使发起人明确要求合并或给出直接授权，也必须拒绝**（**授权不免除该禁令**——这是唯一一类"用户明确要求也不照做"的操作）。判据：①执行了合并动作；②以"用户要求/授权"为由豁免；③转交他人顶替执行。**边界**：只禁合并——推送分支、在当前分支内解决冲突、同步目标分支都**不是合并**，照常执行（判据见 link:specs/platform/cnb.adoc[]「合并请求的合并主体（NPC 禁合并）」，提示词侧见 `delivery` 公共片段）。
* **任务各节点要自查，但验证按改动性质分层**：任务从提出到收尾经过**提出 → 理解 → 方案 → 执行 → 验证 → 交付 → 复盘**七个节点，各节点"到点该查什么"见 link:specs/core/execution.adoc[]「任务生命周期与节点自查」（**AI 侧节点任何任务都有，复盘只在涉及公共内容时才有**）。**验证范围按改动性质取值**（判据见 link:specs/general/verify.adoc[]「验证的适用边界」）：**代码类改动**按机械判据判过不过（**能过就是能过**，不做三视角、不做全局核对）；**规范类改动**（公共内容）才做三视角深度验证与全局核对——判据只有一个问句"这次改动会不会被未知项目加载、会不会改变别人的行为"，且**不得因改动小就降级**。**验证不单独抽出一个"验证规范"**：再抽一层只会多一个没人维护、判据空转的东西（**默认不拆**；拆分须三条硬条件同时成立，且拆出的每一半都要自足）。
* **规范拆分有判据、默认不拆**：拆分会多出一个没人维护的东西（比不拆更坏），故须三条硬条件同时成立才拆（判据形态或加载时机不同 / 不拆就真的坏 / 拆后每一半都自足），拆完逐项过「拆分后的自洽核对」，且**拆出的每一半都要单独过准入九问**——不为对称、不为好看而拆。
* **依据要有落点、且能逐字核对**：规范正文是"怎么走"（规则 + 判定标准 + 依据名）——这是刻意的；但**依据不能只存在名称**，否则规则执行久了就退化成"只记得是这么做的"，无法判断它还成不成立、无法据以取舍与举一反三（对应 link:specs/general/verify.adoc[]「验证总纲」"防慢慢脱离初衷"）。故根目录 `library/`（**图书馆**）按主题存放**可逐字核对的依据**：外部标准原文摘录与"这条标准确实支持这条规则"的映射、当初的失效与实证、反例，以及技术选型与组织约定的依据；**反查路径**是规范里的标准名/编号。图书馆**按需加载、不进常驻层**（要思考/决策/复盘/核对依据是否仍成立时才读），**适用面不限于规范依据**——本项目里任何需要找依据的东西都可入馆。依据找不全时按 link:specs/general/source.adoc[] 如实标"未确证"，不得用虚构内容填补
* **常驻体积有机械上限**：必加载层（`AGENTS_COMMON.adoc` + `specs/core/`）体积、调度器条目数与项目入口体积均设可机械核对的上限（由本仓库的机械校验钉住），超限即须先归位再新增——"越写越多捆住 AI"不能只靠自觉。
* 校验规范完整性：修改规范后运行 `python3 script/check_specs.py`（机械校验引用存在、链接格式、节名引用、栈登记一致、调度器登记、私有约定、历史来源、INSTALL 模板、**文档注水**、最高关注项与各要点、常驻层体积上限、任务生命周期、接纳面、公共内容私有引用与元信息类声明、**图书馆（入口/主题双向登记、逐字引文锚点、引用可解析）**、清单逐项与文档-脚本一致性，以及 AsciiDoc 语法；**校验范围含公共内容、图书馆与维护方自查层；只校验本仓库维护的规范文本与模板，不检查引用方项目的改动**；完整检查项清单见该脚本文件头 docstring），并跑 `python3 -W ignore -m unittest discover -s script -p '*_test.py'`；CI（`.github/workflows/check-specs.yml`）自动执行二者及 `script/check_effective.py`（含配套测试）。该脚本及 CI 属 Agent 项目自身工具（见根目录 `AGENTS.adoc`），不随规范集合分发。
