= Agent 相关

本仓库用于存储 agent 相关信息，内容包括 **agent 执行规范** 与 **公共任务提示词**（后者为复制即用的任务指令，见下）。

== 一键安装（复制给 AI）

安装只需执行一次：把下面这一行提示词复制给 AI，AI 会读取 link:INSTALL.adoc[]（安装文档），并在目标项目根目录创建入口文档（指向远程通用规范入口 `AGENTS_COMMON.adoc`），从而把规范**持久化**到项目里——后续任意会话只需读取该入口即可重新加载并持续遵守规范，无需再次重复安装。入口**默认命名 `AGENTS.adoc`**；根目录**已存在 `AGENTS.md`** 时就地融合到 `AGENTS.md`（不重命名、不删除、不另建），以兼容各平台对 `AGENTS.md` 的固有识别。

将下方这一行提示词复制给任意 AI 即可完成接入（通用任意平台）。AI 直接阅读本 README 时，也可按该提示词自行接入：

[listing]
----
请按 https://agent.c332030.com/INSTALL.adoc 完成本项目 agent 规范安装。
----

== 引用方式

规范适用于任何语言、任何项目，将 `AGENTS_COMMON.adoc` 作为规范入口交给 agent 即可。入口引用方式二选一：

* https 公网静态路径：https://agent.c332030.com/AGENTS_COMMON.adoc
* 本地相对路径或绝对路径：直接使用本仓库内的 `AGENTS_COMMON.adoc`

`AGENTS_COMMON.adoc` 与其 `specs/` 目录始终位于同一目录，文中 `specs/...` 均相对入口所在目录解析，故两种引用方式下规范都能正常解析加载。**引用方只需要 `AGENTS_COMMON.adoc` 与 `specs/`**：公共内容自足——规则一律在入口与 `specs/` 内表达，不指向引用方看不到的私有落点（引用了只会读到死链）。本仓库另有一层只对"维护这类规范集合的项目"成立的维护方自查层，**不属公共入口的加载项、由本仓库自己的项目规范入口登记**（本仓库内容全部会发布——"不按公共入口加载"与"不外发"是两件事），普通引用方无需也不应引入。

取文件的抓手随规范分发：link:script/fetch-specs.py[]（配同名入口 `fetch-specs.sh` / `fetch-specs.bat`）在目标项目根目录运行一次即把入口与 `specs/` 自动解析清单并一次取到 `tmp/agent-specs/`，引用方不必自己拼逐条下载命令（用法见 link:INSTALL.adoc[]「下载规范到临时目录」）。

**首次接入（安装）**：给项目接入时，走 link:INSTALL.adoc[] 的安装流程——让 AI 在项目根目录创建入口文档（指向远程规范），实现持久化；后续会话只需读取该入口。**入口文件名默认 `AGENTS.adoc`**，若根目录**已存在 `AGENTS.md`**（其他平台/工具的默认命名）则就地融合到 `AGENTS.md`——**不重命名、不删除、不另建**，避免打断既有的平台识别或分叉出两个入口。若入口已存在，`INSTALL.adoc` 会保留原文档并在其开头融合，不覆盖（项目自身规范优先于通用规范）。

== 任务提示词（复制给 AI）

除安装外，本仓库还提供**公共任务提示词**：按任务场景组织的、复制即可直接使用的 agent 指令，用于让 AI 干活时不漏步、不偷懒、高质高效。**非规范**内容，不随 `specs/` 分发、不进规范加载链。

统一入口 link:PROMPTS.adoc[]（`PROMPTS.adoc`，登记全部提示词及其用途、二者分工与维护约定，网站右上角"提示词"链接指向它；**提示词的说明以该文件为唯一落点，此处不重复**）；具体提示词文档存放于 `prompts/` 目录。用法：打开对应提示词文档，把其中 `[listing]` 代码块内的文字**完整复制**给 AI 即可（与上方"一键安装"用法一致）。

== 目录结构

* `INSTALL.adoc`（根目录） — **安装文档**（面向目标项目接入）：指导 agent 在目标项目根目录创建入口文档（指向远程 `AGENTS_COMMON.adoc`），把规范**持久化**到项目，避免仅当前会话遵守、下次丢失；**入口文件名默认 `AGENTS.adoc`，并兼容 `AGENTS.md`**——已存在 `AGENTS.md` 时就地融合到该文件、不重命名/不删除/不另建（`AGENTS.md` 同为各平台固有命名）；对**已存在**入口文档的项目做兼容处理——保留原文档、开头融合、不覆盖。其中作为入口模板的代码块要求**逐字原样保留**（含换行与空行，防止 AI 折叠导致样式改变），该要求由本仓库的机械校验钉住。不随 `specs/` 分发，供引用方接入使用。
* `AGENTS_COMMON.adoc` — **通用规范**入口与加载调度器（必加载）：定义规范的分类、懒加载与"按项目类型加载且不漏"的规则，并登记全部规范文件。本文件及其 `specs/` 会被**引用方项目引入**。*与仓库根目录 `AGENTS.adoc`（本项目自身规范入口）区分——根目录 `AGENTS.adoc` 会被平台自动识别为"当前项目自身规范"，而通用规范入口 `AGENTS_COMMON.adoc`（同样位于仓库根目录，但以 `AGENTS_COMMON.adoc` 命名避开平台识别）供引用方项目引入*。
* `AGENTS.adoc`（根目录） — **Agent 项目自身规范**（本仓库维护专用，不在默认引用面内）：声明公共内容、项目自身维护层与本仓库工具的隔离，并收录规范集合的维护规则（规范管理）与检查脚本/CI 的使用说明。普通引用方项目无需也不应引入本文件。本文件采用 `AGENTS.adoc` 命名、位于仓库根目录，会被平台自动识别为本仓库的 agent 规范。
* `library/`（根目录） — **图书馆**（**不在默认引用面内**；按需加载、不进任何常驻层）：集中存放本项目**需要找依据**的东西——规则与决策背后的**可逐字核对的依据**（外部标准原文摘录与"标准确实支持该条"的映射、当初的失效与实证、反例），以及技术选型与组织约定的依据；入口 link:library/README.adoc[]（`library/README.adoc`，登记全部主题）。**放在仓库根而非 `specs/` 下**：`specs/**` 属**默认引用的公共规范**（引用方按入口加载、其内容即引用方的输入），而图书馆天然含**只对本项目成立**的内容（当初的失效、取舍、实证、选型理由）；项目自己的依据库就是项目自己的内容。**注意：本仓库所有内容都会被发布**（站点见「网站首页」一节；**站点上的 `include::` 只在页面内由 Asciidoctor.js 解析时才展开，原始文件地址与本地读取都直出仓库字节、指令仍在**，见 `PROMPTS.adoc`「取值路径与装配状态」）——落在这里**不是"不外发"**，而是**引用方不按它加载**、其工作区里也没有本仓库的文件（"默认引用公共规范"与"不予发布"是两件事）。规则本体仍在 `specs/` 各文件，图书馆只补依据、**不复制规则**。**馆无体量与范围上限、可能特别大**，故引用方在不全量下载的前提下定位依据靠**一份定位协议**：**入口是常驻层里的固定地址**（**取用侧是只有 https 的游客**，不需要 git、不需要版本号）、索引是入口的「主题登记」表、取值是"取一份文件 + 文件内按依据名定位段"；**文件名不承担定位**（**短词命名、≤32 字符**，名字不是检索键，馆内平铺、分类靠主题表——名字长了白占上下文，且改名不等于断档）；**内容主键**（文件会改名/搬迁、内容不会，Git 按内容寻址）只用于**可选的版本固化**，**不得**写成取用前置（协议与依据见 link:library/usage.adoc[]；站点与平台原始文件视图均未实测到 HTTP Range 生效，故现阶段不依赖它——见 link:library/README.adoc[]、link:library/sources.adoc[]）
* `specs/` — **公共内容**分类目录，按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储（以下各层面向**任意项目**，随入口分发给引用方）：
  ** `specs/core/` — 必加载层（每次会话都加载，**只放底线**）：执行原则（含规范变更的存量处理、范围控制、破坏性操作、自检落点、**任务生命周期与节点自查**）
  ** `specs/general/` — 通用层：文档（含**类型指代**：文档与文档注释里提到某个类型时优先写**类名 + `import`**、不写**类全名**——包路径只写一次、其余按短名读，判据与例外见该文件「注释与文档」；并含**依赖关系文档**）、通用编码（含**既有实现与先例优先**：编码前先查项目已有能力与先例、有则复用并跟随先例，禁止用手写原生写法绕过项目自有工具类与已引入库；含**配置类不写逻辑**：`@ConfigurationProperties` 一类承载配置的类只保持 POJO 基本功能，逻辑下沉到 utils/service；含**对象转换**：多层嵌套对象之间的转换**优先**用既有转换库的声明式映射完成、**建议不手写逐字段搬运**（深拷贝/结构复制工具、序列化中转等等价路径同样合规——判据是「同一转换只有一处来源、结构变化不静默漏字段」；除主动声明外在代码注释备注手写原因；**无嵌套（单层）不在本条范围内**，非 JVM 无对应库的情形同样不受限定）；含**抽象与接入成本**：可替换点须有唯一装配点、须有可用默认，不得要求多个使用点各提供一遍同一实现/配置；含**跨服务/对外调用的请求响应类优先移动复用**：给已有接口加新的内部调用接口（如 Feign）时优先把请求/响应类移动并沿用、不新建一套（两种例外：数据库实体类除用户声明外不移动、引用了第三方类型的类；本项目自身的模块依赖不算三方依赖，仍可一起移动），移动后同步更新原引用；含**持久化访问**：持久化操作须走该技术给定的**统一入口**并优先用**类型安全/声明式**查询构造 API（以方法引用/属性名引用表达列名、声明式方法名或类型化 Criteria），禁止用字符串写列名表名，技术给出的替代写法强制优先（框架专名与禁止清单落在 `specs/stack/` 对应文件）；含**跨语言执行脚本的落点**：SQL/Lua 等被调语言的脚本须独立成文件放资源文件夹、扩展名取被调语言自身的扩展名（MyBatis 的 SQL 写 `.xml`），按资源读取执行，不得用字符串拼接或字符串模板内联；含**HTTP 接口语义**（仅对外提供或调用 HTTP 接口的项目）：`GET`/`HEAD`/`OPTIONS`/`TRACE` 是**安全方法**、**不得**承载写/删/状态流转等有副作用的动作，幂等语义（`PUT`/`DELETE`）与重试须对齐（非幂等请求不得配自动重试），状态码按语义使用（**不得**把错误一律包成 `200` 再在响应体里写失败标记），对外错误体**可以**统一为 Problem   ** `specs/stack/` — 技术栈层：java（含**对象转换**：多层嵌套对象转换**优先用 MapStruct**（`@Mapper` 映射接口声明、嵌套与集合由映射方法表达）、**建议不手写转换代码**（**非强制**：等价路径同样合规，单层不管）、不并存两套转换写法；含 **MyBatis-Plus 持久化访问**（**框架专名与禁止清单的唯一落点**）：强制走 `IService` 的 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()`，**禁止** `new QueryWrapper` 及其子类（含 `new LambdaQueryWrapper`）；含**Feign 接口命名**：前缀 + 接口业务名 + `Api`，前缀取所属域固定前缀、无先例按项目名取词首字母组合，通用判据见通用层「Feign 接口命名带所属域/项目前缀」，**只约束 Feign 接口**；含**构造方法不手写**：无参/必参/全参构造一律用 lombok 注解生成（`@NoArgsConstructor`/`@RequiredArgsConstructor`/`@AllArgsConstructor`，需要多个就同时标），注解表达不了才可手写并写明原因）、java 语法（含**工具类使用优先级**：项目自有工具类/已引入库优先于 JDK 原生写法）、spring（含**HTTP 接口路径优先用中划线**：路由路径片段用小写 + `-`，不得用 `_` 或驼峰，服务路由/网关前缀与已发布的对外路径照旧）、maven（含**仓库与镜像**：**未配置过仓库/镜像、且外网出口 IP 在中国大陆**时，动手构建前**必须先用**指定中央仓库 `https://mirrors.cloud.tencent.com/nexus/repository/maven-public/`、不得自行另挑，**仅当它不可用**才允许改用其他**在境内**的镜像站；已配置过沿用既有配置、不覆盖、不重配）、java 测试（含测试类命名契约 `Tests`/`BootTests`/`PerfTests`/`IT`，**一个被测类可按需求/分类拆多个类、同分类或同属性须归一类，不得滥拆**）、java 的**跨语言执行脚本**（`sql`/`lua` 放 `src/main/resources/` 下按资源加载；Redis 用 `DefaultRedisScript` **按静态常量加载 `.lua`**、不是每次调用读一遍；加载时机按性能敏感度定性）、bash/python/powershell/批处理脚本（按项目类型加载，各自写明行尾要求：bash/python 用 LF、批处理与 powershell 用 CRLF；**`.bat`/`.cmd` 有独立栈文件**——批处理专属规则（行尾 CRLF、纯 ASCII 不写 BOM、`@echo off`、块语句延迟展开、路径加引号、`exit /b %errorlevel%`、不混写 PowerShell 语法）的唯一落点，避免「写 bat 时找不到规范文件」）
  ** `specs/platform/` — 平台层：cnb（CNB 平台上的分支与合并请求统一、冲突处理、**变更范围只限当前项目（未声明即拒绝，通用口径见通用层 `specs/general/scope.adoc`）**、**评论唤起新实例（平台侧的派发入口：在 Issue/PR 里新增一条评论、@ 某个 NPC 并说清要求即发起一次执行；一次评论 = 一次派发，可要求用干净上下文——要求须写清、且不等于清约束；**执行者不得自行发评论唤起自己**、**评论不得删除**——任何情况下不得删除 Issue/PR 的评论（含 NPC 生成的），**编辑同效**，发错了**再发一条更正**）**、**压缩提交（提交历史整理：判据与禁止形态、**压缩对象不含「改名提交 + 内容修改提交」**、须先确认无人在用旧对象、force-with-lease、与「NPC 禁合并」互不豁免）**、**对象钉定与可追溯**（派发与复核钉定 commit sha、压缩提交/强推的对应关系、CI 状态按 sn+sha 定位）、**执行吞吐（平台侧：一次唤起=一次完整加载、状态与用量按汇总先取再下钻、不空转等待）**、**协作与执行者可用性**（含**同 Agent 复核的适用面**："须由与执行者相同的 Agent 承担"**只在本平台上成立**，平台层未写明该前提时**不得据此拒做或停任务**、环境不提供同 Agent 子执行者时照做该职责并按降级路径留证））

== 使用要点

* 规范按分类懒加载，但"按项目类型加载且不漏"是底线——如 Java 项目写代码必须加载 Java 编码规范；**公共内容自足**：`AGENTS_COMMON.adoc` 与 `specs/` 里的规则一律在公共内容内表达，**不引用引用方看不到的私有落点**；只对维护这类规范集合成立的内容另置维护方自查层（由本仓库自己的项目规范入口登记、不属公共入口的加载项），普通引用方项目不加载。
* 规范条目分 **L1 强制 / L2 建议 / L3 允许** 三级，并有**最高关注项**（不可降级、重构首保）：分级定义、各级遵守要求与最高关注项见 link:specs/core/execution.adoc[]「分级与最高关注项」（依据 RFC 2119 / RFC 8174、ISO/IEC Directives Part 2）。强调用「升级别 + 单一定义 + 引用」，不靠重复书写。
* **常驻层只放底线**：必加载层每次会话都无条件加载，故只放 L1 底线、最高关注项及其引用落点；**方法论、依据论证、示例与元规范一律放通用层**（用到才加载）；只对维护这类规范集合成立的维护类规范另置维护方自查层（普通引用方不加载）——规范写得多不等于管得住，**放错层会直接挤占每次会话的上下文、反过来捆住执行者**。
* **同一条规则有两种读法**：**执行**时只给"怎么走"（规则 + 判定标准 + 依据名），多出来的"为什么走这条路"是占注意力的噪音；**思考与决策**（新增/调整/定级/重构规范、有取舍或争议、复盘）时才需要依据与取舍。两形态同源、不复制两份，**依据只压缩为名称/编号、不得整段删除**；重构的验收除"内容不丢"外还须核对**有效性未被改坏**（判据未被压成口号、依据仍在、可见性仍在）。
* **提示词要"看完就走"，不得只冒一句话**：提示词的输出只有一种——**交付结果 + 结论汇报**合起来的一次完整汇报（在平台上即**一条评论**）：**输出通道只有两条**（**最终的一次完整汇报**、或**必须停下确认**），**除这两条之外的任何中间话一律不发**——**过程性叙述**（"现在去读 X""先看有没有 Z 这类检查"）**不得作为独立评论发出去**（会一条条冒给发起人、答非所问；**只写"例外只有某种"而不写"其余一律不发"，执行者就会自造第三条通道**）；**有改动须提交推送并建 PR**、汇报里落成可核对的事实（改动清单 + 分支/PR 链接），**无改动须显式说明"本次未发现问题"**——**"报告说完成了、却没有任何提交"与"没有改动却不说"同属交付失败**（**本项目实证**：一轮任务唯一对外的输出就是一条过程性废话，既无汇报、也无提交）。口径见 link:PROMPTS.adoc[]「优先级与隔离」与 `prompts/_common.txt` 的 `delivery` 片段。
* 提示词**侧重点不同、属方向性前提**：各提示词显式标注**主侧重**并按上述分级引入优先级（让 AI 按业界共识判断"哪里是重点"），并做观念隔离（不混用另一提示词的步骤）；登记表见 link:PROMPTS.adoc[]「优先级与隔离」。
* **文档里写类名、不写类全名**：文档与代码内文档注释提到某个类型时，先直接写**类名**（`CUnauthorizedException`），需要解析时在**就近的代码示例**里写一条 `import com.c332030.ctool4j.core.exception.CUnauthorizedException;`；**不得**用**类全名**充当标识（包路径属“去哪找”的信息、只该出现一次）；classpath 内能 `import` 到的类型一律如此，**不在 classpath 内才写类全名**。**“如果有必要”仅三态**：同名类冲突、无代码示例可承载 `import`、**不在本仓库 classpath 内**（外部或他仓类型）。**三处不属禁止对象**：路径与坐标（链接、`@see` 的文件路径）不是类型名；字符串与配置里必须全限定的场合（`@ConditionalOnClass` 类名、`main-class`、反射按名加载、`import` 本身）；`{@link}`/`@see` 的成员引用（javadoc 要求合法引用、必须全限定）。**为 L2、不做存量一次性替换**（随动调整）。Java 落点见 link:specs/stack/java.adoc[]「javadoc」。
* **性能测试是有结论的工程实验，不是"跑一次看看谁快"**：命中性能敏感特征（关键路径/高频调用、大数据量或规模可增长、昂贵资源、多方案选型需数据佐证）才做，**不得一律加、也不得漏掉真敏感点**；测量须**排除初始化干扰**、写明**预热/轮次/批量/计时区间/运行环境**、**每组至少 3 次采样并报离散度**，**组间差异小于离散度即视为无显著差异**（不得据此宣称胜出），并**含当前实现作基准**（否则"要不要换"无从判起）；**成绩与结论必须有落点**——跨类级进独立性能测试文档、用例级进测试类文档注释，形态是**方案组合与成绩**（`方案编号 | 组合 | 终值 | 离散度 | 与基线之比 | 结论`）+ **优化日志**（含失败的尝试与"此路不通"）+ **瓶颈归因与下一步方向**；**不需要完整记录 ≠ 可以不记录**：**只记结论 + 取值 + 来源，不记原始日志与调试过程**，单轮即收敛时不硬造轮次表；**优化不得改变行为**（既有功能用例须全绿）。判据见 link:specs/general/testing.adoc[]「性能测试」，Java 承载见 link:specs/stack/java-testing.adoc[]，依据见 `library/performance.adoc`（不在默认引用面内）。
* 通用规则与某技术栈专属规则分层存放，通用规则不重复收录进各栈。
* 换行符（行尾）由仓库配置固定、不靠人工手动调整：行尾按解释器分流——内容以 **LF** 为基准，**Windows 批处理 `.bat`/`.cmd` 必须 CRLF**（LF-only 在 Windows 上直接执行失败）、PowerShell `.ps1` 用 CRLF。行尾写进仓库根 `.gitattributes`、编辑器侧约定写进 `.editorconfig`（**缺任一个即按规范补齐**）；判据见 link:specs/general/encoding.adoc[]「换行符」「跨平台检出」，不靠人工手动调整。
* **改完规范的语义复核是"验证三视角一起过"**（判据在公共 link:specs/general/verify.adoc[]「验证与运行契约的落点」）：①**完整性**（改动的对象在改动前后是否等价、要点是否全保留）②**有效性与认知质量**（规范本体是否说得对、说得清、跑得动、判得了：判据可判定、依据仍在且说对了、机制在当前环境真会发生、从属者可加载、放对层且常驻代价在预算内、代价说得清）③**接纳面**（**被未知项目加载后的影响面/成本/可控性**：不静默推翻引用方约定、不默认改其工作区、不引入无降级路径的依赖、体积可控）；三视角**由同一个干净子 agent 一并回答**（一次读取、结论分栏，不重复派发），都过、各自留证才算完成。**"验证了什么、怎么算过、依据哪个标准"须能逐项枚举**（判据与标准出处见同节「验证总纲」「规范验证」「运行契约」）。
* **动手前先定基线、改完老用例不得为新用例让路**：动手前先**扫描项目声明的全部校验手段**（测试用例、构建、静态检查、规范校验脚本），**既有手段完整可用时必须先跑通**、并把结果**落盘留证**（随改动提交推送）；**扫出的清单还要先核"够不够用"**——项目**声明的**手段与其既有用例**本身可能不完整**（边界未覆盖、正反例缺一侧、缺步骤与前置），须**先按用例设计判据 review 既有用例**、说出"查了哪些角度、哪些未覆盖、哪些未确证"，**本次改动直接相关面**的缺口先补全再动手、无关的存量缺口如实记录不阻断——基线是「改完有没有破坏既有行为」的唯一尺子；**大范围替换/废弃既有流程前先经用户确认**（是否废弃由用户认定），**不得绕开既有实现另写一套**（新写一套即使能满足需求，也会留下两套实现/配置/文档，达不到最佳实践）；改动后**既有用例不得为迁就改动而改判**（除相关功能被显式移除且先经确认），**老用例与新用例须同时成立、行为完整兼容**，**兼容不了先停下确认**（判据见 link:specs/general/planning.adoc[]、link:specs/general/testing.adoc[]「执行与验证」，提示词侧见 `baseline-and-compat` 与 `compat` 片段）。
* **验证对象不止规范文件**：`prompts/`（会被未知项目复制执行）、随规范分发的工具（如 `script/clean_tmp.py`、`script/fetch-specs.py`）等"会被外部执行"的产物同样按上述三视角核对。
* **从属者与能力：两处易漏的执行侧机制**：①**加载由已加载入口驱动**——子 agent、被主 agent 派发的分步任务不得以"没被派发这份规范"为由跳过加载，"上级已读过"不构成下级免责（约束随入口传递、不随上下文传递）；②**执行环境能力先自评**——能否新开会话/清空上下文、能否派发子 agent 等机制**不是每个环境都有**，须先判定（不确定按"不可用"），缺失时走降级路径并**如实记录**，不得照抄"已清洁上下文/已委派"式的空自评（判据见 link:specs/general/self-check.adoc[]「环境能力自评」）。
* **判准要分清"严格执行 / 尽力而为"**：L1/L2/L3 答"要求有多强"，"严格执行"（须逐次达成并给证据）与"尽力而为"（须尝试、须说明未达原因、不记通过）答"执行到什么程度算做到"——两者都须留证，"未执行"与"通过"不得混写；判准有疑问按"严格执行"处理并补判据（判据与判定动作见 link:specs/general/verify.adoc[]「判准维度：严格执行 / 尽力而为」）。
* **子 agent 复核必须自带硬超时、留证按三态台账**：语义复核派给子 agent 时**必须设可判定的时限**（**同 Agent 强制**，不得点名外部 Agent/NPC，故不把外部复核者当选项；**该前提只在本平台成立**——平台层未写明时不得据此拒做或停任务，环境不提供同 Agent 子执行者时按降级路径照做并留证），到点即视为失联并"**放弃 + 如实标悬置**"，**不得无限等待**（实证：把复核派给外部评审 NPC，多轮停在同一步 1 小时以上、结论未回传，只能人工中止）；**子任务一律由与执行者相同的 Agent 承担（不得点名外部 Agent/NPC）**——同 Agent 的子执行者不可用时，由发起方按同一判据组织等价复核（本地串行），并如实标注独立性边界（判据见 link:specs/general/collab.adoc[]「资源限制与感知」「协作方式」）。留证须是**可机械核对的三态台账**：**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附原因与剩余风险），三态各占一栏、不得合并——**"查不出"与"没做"须能分辨**（判据见 link:specs/general/verify.adoc[]「验证的效力等级」）。
* **派活入口：评论即一次派发**：本平台下**在 Issue/PR 里新增一条评论、@ 某个 NPC、并把要求写清**，即发起一次新的执行；**一次评论 = 一次派发**——要求须在评论里写清（做什么、边界、产物形态、验证口径），未写清的不得自行假定后开工，仅 @ 一下/只有寒暄不构成派发；**执行者不得在本次执行中自行发评论点名唤起自己**（想分步就**先停**、输出一次"停下确认"，由**人**另发一条评论决定再来一次——判据是**这条评论发出去没有**，发了即违规，"分两步更清楚"不构成理由）。评论里**可以显式要求"使用干净上下文"**（当作全新任务、不复用此前评论的结论、按对象钉定重新取值）；但**"上下文干净"只清历史对话、不清约束**（规范仍须按入口重新加载），且该要求**不是保证**——须如实说明本次实际读到的上下文范围。该入口**不放宽任何派发判据**（同 Agent 强制、钉定对象、硬超时照判），也**不构成"可以点名外部 Agent"的例外**（判据见 link:specs/platform/cnb.adoc[]「评论唤起新实例（平台侧的派发入口）」与 link:specs/general/collab.adoc[]「派发入口」）。
* **评论不得删除**：任务单下的评论是**派发的对象钉定与留证落点**，**删除不可逆**、**编辑同效**——故**任何情况下不得删除 Issue/PR 的评论**（含 NPC/执行者生成的、含"看起来只是过程性叙述"的那条），**也不得转交他人/CI 代删**；"发错了"**再发一条更正**或回复补充（**不禁改正、只禁抹掉**），确需清理时由**人**在平台上自行处理；清理本地 `tmp/` 与构建产物照旧（判据见 link:specs/platform/cnb.adoc[]「评论不得删除」、link:specs/core/execution.adoc[]「破坏性操作」、link:specs/general/collab.adoc[]「派发入口」）。
* **压缩提交要照做、合并仍不做**：用户要求“压缩提交/压成一个提交”时**按 `specs/platform/cnb.adoc`「压缩提交」执行**——它属提交历史整理、不是合并（对象只限本次任务尚未合入的临时中间提交、内容逐字节不变、只动本 PR 源分支、先确认无人在用旧对象、推送用 `--force-with-lease`、执行后写明新 sha 并作废旧 sha）；**"改名提交 + 内容修改提交"不在压缩对象内**——用户未点名重命名那一条时，它们原样保留（见下「重命名与内容修改分两个提交」）。但**压缩提交不构成“可以合并”的依据**，合入目标分支的禁令与口径不变（见下条）。
* **合并一律不做（L1，人工授权也拒绝）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求**——不论本地人工场景还是自动化场景，都只交付到"创建/推送 PR 分支并汇报"为止，合入目标分支**只由人工完成**；**即使发起人明确要求合并或给出直接授权，也必须拒绝**（**授权不免除该禁令**——这是唯一一类"用户明确要求也不照做"的操作）。判据：①执行了合并动作；②以"用户要求/授权"为由豁免；③转交他人顶替执行。**边界**：只禁合并——推送分支、在当前分支内解决冲突、同步目标分支都**不是合并**，照常执行（判据见 link:specs/platform/cnb.adoc[]「合并请求的合并主体（NPC 禁合并）」，提示词侧见 `delivery` 公共片段）。
* **任务各节点要自查，但验证按改动性质分层**：任务从提出到收尾经过**提出 → 理解 → 方案 → 执行 → 验证 → 交付 → 复盘**七个节点，各节点"到点该查什么"见 link:specs/core/execution.adoc[]「任务生命周期与节点自查」（**AI 侧节点任何任务都有，复盘只在涉及公共内容时才有**）。**验证范围按改动性质取值**（判据见 link:specs/general/verify.adoc[]「验证的适用边界」）：**代码类改动**按机械判据判过不过（**能过就是能过**，不做三视角、不做全局核对）；**规范类改动**（公共内容）才做三视角深度验证与全局核对——判据只有一个问句"这次改动会不会被未知项目加载、会不会改变别人的行为"，且**不得因改动小就降级**。**验证不单独抽出一个"验证规范"**：再抽一层只会多一个没人维护、判据空转的东西（**默认不拆**；拆分须三条硬条件同时成立，且拆出的每一半都要自足）。
* **规范拆分有判据、默认不拆**：拆分会多出一个没人维护的东西（比不拆更坏），故须三条硬条件同时成立才拆（判据形态或加载时机不同 / 不拆就真的坏 / 拆后每一半都自足），拆完逐项过「拆分后的自洽核对」，且**拆出的每一半都要单独过准入九问**——不为对称、不为好看而拆。
* **依据要有落点、且能逐字核对**：规范正文是"怎么走"（规则 + 判定标准 + 依据名）——这是刻意的；但**依据不能只存在名称**，否则规则执行久了就退化成"只记得是这么做的"，无法判断它还成不成立、无法据以取舍与举一反三（对应 link:specs/general/verify.adoc[]「验证总纲」"防慢慢脱离初衷"）。故根目录 `library/`（**图书馆**）按主题存放**可逐字核对的依据**：外部标准原文摘录与"这条标准确实支持这条规则"的映射、当初的失效与实证、反例，以及技术选型与组织约定的依据；**反查路径**是规范里的标准名/编号。**馆可能特别大**（无体量上限），故定位另走一份协议（主键与路径无关、不全量下载，见上条目录说明）。图书馆**按需加载、不进常驻层**（要思考/决策/复盘/核对依据是否仍成立时才读），**适用面不限于规范依据**——本项目里任何需要找依据的东西都可入馆。依据找不全时按 link:specs/general/source.adoc[] 如实标"未确证"，不得用虚构内容填补
* **单个规范文件有"软阈值"，只提醒不阻断**：**非必加载**的单个规范文件（公共规范 `specs/**` 与本仓库维护方自查层）超过**约 30 KB** 时，机械校验**打印提醒**（该评估优化了：先判归属与层级、再判是否该拆），但**不报错、不阻断提交、不强制拆分**——硬上限会逼出"为压体积删规则"或"为达标拆出没人维护的空壳"，与"内容不得减少"的完整性底线冲突。它与上条的常驻体积硬上限**判据对象与强度都不同**（那条管**每次会话无条件加载的合计量**、超限即失败；本条管**单个文件**的体量提醒），**不得互相替代**；判定与固定动作见本仓库另一层（只对维护方成立、不在公共引用面内）的规范文件「单个规范文件的软阈值」一节。
* **常驻体积有机械上限、且限额以"合计量"为准**：必加载层（`AGENTS_COMMON.adoc` + `specs/core/`）体积、调度器条目数与项目入口体积均设可机械核对的上限（由本仓库的机械校验钉住），超限即须先归位再新增——"越写越多捆住 AI"不能只靠自觉。**上限的判据不是"单个文件多大"而是"每次会话无条件加载的合计量多大"**：入口及**其逐条引用的必加载落点**都会在每次会话被实际读入，故公共侧须显式声明"每次会话都加载的部分含哪些"、并给出**可机械核对的合计预算**（公共内容不写本仓库的私有脚本名，只保留这一要求）；"引用方只下载入口与 `specs/`"是最小下载面，**不等于"只读一个文件"**——读入面按加载链算。
* 校验规范完整性：修改规范后运行 `python3 script/check_specs.py`（机械校验引用存在、链接格式、节名引用、栈登记一致、调度器登记、私有约定、历史来源、INSTALL 模板、**文档注水**、最高关注项与各要点、常驻层体积上限与单文件软阈值提醒、任务生命周期、接纳面、公共内容私有引用与元信息类声明、**图书馆（入口/主题双向登记、逐字引文锚点、引用可解析）**、**Feign 接口命名带所属域前缀**、**开发流程（先查现状/最佳方案/基线、大范围改动先确认、不得绕开既有体系另写一套、老用例不得为迁就改动而改判）**、清单逐项与文档-脚本一致性、**性能测试（测量与记录的要点、两处落点与依据主题）**，以及 AsciiDoc 语法；**校验范围含公共内容、图书馆与维护方自查层；只校验本仓库维护的规范文本与模板，不检查引用方项目的改动**；完整检查项清单见该脚本文件头 docstring），并跑 `python3 -W ignore -m unittest discover -s script -p '*_test.py'`；CI（`.github/workflows/check-specs.yml`）自动执行二者及 `script/check_effective.py`（含配套测试）。该脚本及 CI 属 Agent 项目自身工具（见根目录 `AGENTS.adoc`），不随规范集合分发。
