= Agent 相关

本仓库用于存储 agent 相关信息，内容包括 **agent 执行规范** 与 **公共任务提示词**（后者为复制即用的任务指令，见下）。

== 一键安装（复制给 AI）

安装只需执行一次：把下面这一行提示词复制给 AI，AI 会读取 `INSTALL.adoc`（安装文档），并在目标项目根目录创建入口文档（指向远程通用规范入口 `AGENTS_COMMON.adoc`），从而把规范**持久化**到项目里——后续任意会话只需读取该入口即可重新加载并持续遵守规范，无需再次重复安装。入口**默认命名 `AGENTS.adoc`**；根目录**已存在 `AGENTS.md`** 时就地融合到 `AGENTS.md`（不重命名、不删除、不另建），以兼容各平台对 `AGENTS.md` 的固有识别。

将下方这一行提示词复制给任意 AI 即可完成接入（通用任意平台）。AI 直接阅读本 README 时，也可按该提示词自行接入：

[listing]
----
请按 https://agent.c332030.com/INSTALL.adoc 完成本项目 agent 规范安装。
----

== 引用方式

规范适用于任何语言、任何项目，将 `AGENTS_COMMON.adoc` 作为规范入口交给 agent 即可。入口引用方式二选一：

* https 公网静态路径：https://agent.c332030.com/AGENTS_COMMON.adoc
* 本地相对路径或绝对路径：直接使用本仓库内的 `AGENTS_COMMON.adoc`

`AGENTS_COMMON.adoc` 与其 `specs/` 目录始终位于同一目录，文中 `specs/...` 均相对入口所在目录解析，故两种引用方式下规范都能正常解析加载。**引用方只需要 `AGENTS_COMMON.adoc` 与 `specs/`**：公共内容自足——规则一律在入口与 `specs/` 内表达，不指向引用方看不到的私有落点。本仓库另有一层只对"维护这类规范集合的项目"成立的维护方自查层，**不属公共入口的加载项、由本仓库自己的项目规范入口登记**（本仓库内容全部会发布——"不按公共入口加载"与"不外发"是两件事），普通引用方无需也不应引入。

取文件的抓手随规范分发：`script/fetch-specs.py`（配同名入口 `fetch-specs.sh` / `fetch-specs.bat`）在目标项目根目录运行一次即把入口与 `specs/` 自动解析清单并一次取到本地副本，引用方不必自己拼逐条下载命令。**副本落点、取回与更新方式、解释器兜底**以 `INSTALL.adoc`「取规范到本地副本」为唯一真源（本文件不复述；副本**只落在用户家目录下的一处**，没有第二个落点）。

**首次接入（安装）**：给项目接入时走 `INSTALL.adoc` 的安装流程——让 AI 在项目根目录创建入口文档（指向远程规范），实现持久化；后续会话只需读取该入口。**入口文件名默认 `AGENTS.adoc`**，若根目录**已存在 `AGENTS.md`**（其他平台/工具的默认命名）则就地融合到 `AGENTS.md`。若入口已存在，`INSTALL.adoc` 会保留原文档并在其开头融合，不覆盖（项目自身规范优先于通用规范）；**本流程可重复执行、且以远程为准**——入口占位与最新模板不一致时就地更新那几行、副本按远程内容刷新，判别据是内容而不是时间。

== 任务提示词（复制给 AI）

除安装外，本仓库还提供**公共任务提示词**：按任务场景组织的、复制即可直接使用的 agent 指令，用于让 AI 干活时不漏步、不偷懒、高质高效。**非规范**内容，不随 `specs/` 分发、不进规范加载链。

统一入口 `PROMPTS.adoc`（登记全部提示词及其用途、二者分工与维护约定，网站右上角"提示词"链接指向它；**提示词的说明以该文件为唯一落点，此处不重复**）；具体提示词文档存放于 `prompts/` 目录。用法：打开对应提示词文档，把其中 `[listing]` 代码块内的文字**完整复制**给 AI 即可（与上方"一键安装"用法一致）。

== 目录结构

* `INSTALL.adoc`（根目录） — **安装文档**（面向目标项目接入）：指导 agent 在目标项目根目录创建入口文档（指向远程 `AGENTS_COMMON.adoc`），把规范**持久化**到项目；其中作为入口模板的代码块要求**逐字原样保留**。**入口文档是本流程唯一持久化到目标项目的产物**：只放『这是什么、在哪』——**规范路径、安装文档路径、取规范脚本路径**、规范副本位置、取回与更新方式、以及本项目要跨会话保留的约定。写入判据见 `specs/general/entry-doc.adoc`。不随 `specs/` 分发，供引用方接入使用。
* `AGENTS_COMMON.adoc` — **通用规范**入口与加载调度器（必加载）：定义规范的分类、分层、懒加载与"按项目类型加载且不漏"的规则，并登记全部规范文件。本文件及其 `specs/` 会被**引用方项目引入**。*与仓库根目录 `AGENTS.adoc`（本项目自身规范入口）区分——根目录 `AGENTS.adoc` 会被平台自动识别为"当前项目自身规范"，而 `AGENTS_COMMON.adoc`（同样位于仓库根目录，但以此命名避开平台识别）供引用方项目引入*。
* `AGENTS.adoc`（根目录） — **Agent 项目自身规范**（本仓库维护专用，不在默认引用面内）：声明公共内容、项目自身维护层与本仓库工具的隔离，并收录规范集合的维护规则与检查脚本/CI 的使用说明。普通引用方项目无需也不应引入本文件。本文件采用 `AGENTS.adoc` 命名、位于仓库根目录，会被平台自动识别为本仓库的 agent 规范。
* `specs/` — **公共内容**分类目录，按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储（以下各层面向**任意项目**，随入口分发给引用方）：
** `specs/core/` — 必加载层（每次会话都加载，**只放底线**）
** `specs/general/` — 通用层：编码（`coding.adoc`；含抽象与接入成本、**既有实现与先例优先**、持久化访问、对象转换、**跨语言执行脚本的落点**、HTTP 接口语义、**请求响应类优先移动复用**、**Feign 接口命名带所属域前缀**、**链式调用一律换行**、代码质量）、脚本（`script.adoc`；含**文档头先行**的脚本头部注释（文档头）、**文档默认写进脚本自身**的脚本文档承载位置、跨环境脚本）、文档（`doc.adoc`；含必记录项、文档质量、组织与导航、索引页判据、引用路径、类型指代写类名 + import）、设计文档（`doc-design.adoc`；含信息归属、版本与变更记录、依赖关系文档）、文档生命周期（`doc-lifecycle.adoc`）、模块文档（`doc-module.adoc`）、git（`git.adoc`；含文件移动与重命名、重命名与内容修改分两个提交、行尾与检出归一、提交信息）、变更日志（`changelog.adoc`）、code review（`review.adoc`；含问题记录备注落点、改动后的 review）、协作（`collab.adoc`）、编码与语言无关（`encoding.adoc`；含换行符权威判据）、**数据字典（`terminology.adoc`；含只引名称不引定义、作用域分档与每档唯一落点（当前文档的定义写在该文档开头）、条目形态、新增与调整内容时即生效）**、安全（`security.adoc`）、依赖（`dependency.adoc`；含包源与镜像源选用）、测试（`testing.adoc`；含用例设计、测试有效性、性能测试）、规划（`planning.adoc`；含现状与最佳方案——**调整内容一类需求须先检索可参照的业界标准/通行范式/本项目先例、有更优的用更优的**、不得另写一套、大动先确认、动手前先定基线）、自检（`self-check.adoc`）、改动范围（`scope.adoc`）、上下文与读取范围（`context.adoc`；含执行吞吐、生成效率、token 纪律、运行契约索引）、依据与来源（`source.adoc`）、入口文档（`entry-doc.adoc`）、验证（`verify.adoc`；含验证适用边界、效力等级、验证总纲、规范验证、运行契约、改完规范必做的五件事）、CI/CD（`ci-cd.adoc`；含运行环境须与项目声明一致、校验链完整、超时与资源）、项目类型层（`doc-tool.adoc`，按项目主动声明懒加载）

* `script/` — 配套脚本目录（多数为 Agent 项目自身工具，见根目录 `AGENTS.adoc`）：

* `library/`（根目录） — **图书馆**（**不在默认引用面内**；按需加载、不进任何常驻层）：集中存放本项目**需要找依据**的东西——规则与决策背后的**可逐字核对的依据**（外部标准原文摘录与"标准确实支持该条"的映射、当初的失效与实证、反例），以及技术选型与组织约定的依据；入口 `library/README.adoc`（登记全部主题）。**放在仓库根而非 `specs/` 下**：`specs/**` 属**默认引用的公共规范**，而图书馆天然含**只对本项目成立**的内容。规则本体仍在 `specs/` 各文件，图书馆只补依据、**不复制规则**。**馆无体量与范围上限**，故定位靠一份定位协议（入口是常驻层里的固定地址、索引是入口的「主题登记」表、取值是"取一份文件 + 文件内按依据名定位段"）
* `index.html` — 网站首页（渲染方式见「网站首页」一节）

== 使用要点

* 规范按分类懒加载，但"按项目类型加载且不漏"是底线——如 Java 项目写代码必须加载 Java 编码规范；**公共内容自足**：规则一律在公共内容内表达，**不引用引用方看不到的私有落点**。
* 规范条目分 **L1 强制 / L2 建议 / L3 允许** 三级，并有**最高关注项**（不可降级、重构首保）：分级定义、各级遵守要求与最高关注项见 `specs/core/execution.adoc`「分级与最高关注项」（依据 RFC 2119 / RFC 8174、ISO/IEC Directives Part 2）。强调用「升级别 + 单一定义 + 引用」，不靠重复书写。
* **常驻层只放底线**：必加载层每次会话都无条件加载，故只放底线类内容；**方法论、依据论证、示例与元规范一律放通用层**（用到才加载）——规范写得多不等于管不住，**放错层会直接挤占每次会话的上下文、反过来捆住执行者**。逐条判据属维护方自查层，本文件不重复。
* **同一条规则有两种读法**：**执行**时只给"怎么走"（规则 + 判定标准 + 依据名），多出来的"为什么走这条路"是占注意力的噪音；**思考与决策**时才需要依据与取舍。两形态同源、不复制两份，**依据只压缩为名称/编号、不得整段删除**。
* **提示词要"看完就走"**：输出只有一种——**交付结果 + 结论汇报**合起来的一次完整汇报（在平台上即**一条评论**）：**输出通道只有两条**（最终的一次完整汇报、或必须停下确认），**除这两条之外的任何中间话一律不发**（过程性叙述**不得作为独立评论发出去**；"报告说完成了、**却没有任何提交**"与"没有改动却不说"同属交付失败）；**有改动须提交推送并建 PR**、汇报里落成可核对的事实，**无改动须显式说明**。
* **文档里写类名、不写类全名**：文档与代码内文档注释提到某个类型时，先直接写**类名**，需要解析时在就近的代码示例里写一条 `import`；**不得**用类全名充当标识。**为 L2、不做存量一次性替换**。
* **性能测试是有结论的工程实验**：命中性能敏感特征才做；**每组至少 3 次采样并报离散度**，**组间差异小于离散度即视为无显著差异**；**成绩与结论必须有落点**；**优化不得改变行为**。
* **换行符（行尾）由仓库配置固定、不靠人工手动调整**：内容以 **LF** 为基准，**Windows 批处理 `.bat`/`.cmd` 必须 CRLF**、`.ps1` 用 CRLF。行尾写进仓库根 `.gitattributes`、编辑器侧约定写进 `.editorconfig`（**缺任一个即按规范补齐**）。
* **改完规范的语义复核是"验证三视角一起过"**：**三视角**（①完整性 ②有效性与认知质量 ③接纳面）的定义与逐条判据属公共内容——见 `specs/general/verify.adoc`「本文件的字典」与「规范验证」（本文件不重复其判据）；本仓库的落点在"只有维护方成立的那一层"（本文件第 41 条已说明该层不随公共入口分发）。
* **动手前先定基线、改完老用例不得为新用例让路**：动手前先**扫描项目声明的全部校验手段**，既有手段完整可用时必须先跑通、并把结果落盘留证；扫出的清单还要先核"够不够用"；**大范围替换/废弃既有流程前先经用户确认**；改动后**既有用例不得为迁就改动而改判**、**老用例与新用例须同时成立**。
* **入口是"门"、不是"施工队"**：跨环境脚本的入口只做**薄壳**（定位解释器或逻辑代码、原样转交参数、原样返回退出码），**不得**为"让逻辑跑起来"安装/下载/解压运行时、包或依赖。**该职责要么由人按本平台既有的软件分发方式完成、要么在能看见命令与报错的会话里由 agent 完成**。
* **验证对象不止规范文件**：`prompts/`、随规范分发的工具同样按三视角核对。
* **从属者与能力：两处易漏的执行侧机制**：① **加载由已加载入口驱动**——子 agent、被派发的分步任务不得以"没被派发这份规范"为由跳过加载；② **执行环境能力先自评**——能否新开会话/清空上下文、能否派发子 agent 不是每个环境都有，须先判定（不确定按"不可用"），缺失时走降级路径并**如实记录**。
* **判准要分清"严格执行 / 尽力而为"**：L1/L2/L3 答"要求有多强"，"严格执行"（须逐次达成并给证据）与"尽力而为"（须尝试、须说明未达原因、不记通过）答"执行到什么程度算做到"；两者都须留证，"未执行"与"通过"不得混写。
* **子 agent 复核必须自带硬超时、留证按三态台账**：语义复核派给子 agent 时**必须设可判定的时限**（**同 Agent 强制**，不得点名外部 Agent/NPC；**该前提只在本平台成立**），到点即"放弃 + 如实标悬置"，**不得无限等待**；留证须是**三态台账**：通过／未发现问题／悬置，三态各占一栏、不得合并。
* **派活入口：评论即一次派发**：在 Issue/PR 里新增一条评论、@ 某个 NPC、并把要求写清，即发起一次新的执行；**一次评论 = 一次派发**——要求须写清（做什么、边界、产物形态、验证口径），未写清的不得自行假定后开工；**执行者不得在本次执行中自行发评论点名唤起自己**（发起下一次是派发者的动作，不是执行者的动作；"分两步更清楚"不是理由）。评论里**可以显式要求"使用干净上下文"**；但**"上下文干净"只清历史对话、不清约束**。
* **评论不得删除**：任务单下的评论是**派发的对象钉定与留证落点**，**删除不可逆**、**编辑同效**——故**任何情况下不得删除 Issue/PR 的评论**；"发错了"**再发一条更正**；确需清理时由**人**在平台上自行处理。
* **压缩提交要照做、合并仍不做**：用户要求"压缩提交/压成一个提交"时按 `specs/platform/cnb.adoc`「压缩提交」执行；**"改名提交 + 内容修改提交"不在压缩对象内**。但**压缩提交不构成"可以合并"的依据**，合入目标分支的禁令与口径不变。
* **合并一律不做（L1，人工授权也拒绝）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求**——都只交付到"创建/推送 PR 分支并汇报"为止，合入目标分支**只由人工完成**；**即使发起人明确要求合并或给出直接授权，也必须拒绝**。
* **任务各节点要自查，但验证按改动性质分层**：任务从提出到收尾经过**提出 → 理解 → 方案 → 执行 → 验证 → 交付 → 复盘**七个节点，各节点"到点该查什么"见 `specs/core/execution.adoc`「任务生命周期与节点自查」。**验证范围按改动性质取值**：**代码类改动**按机械判据判过不过（**能过就是能过**）；**规范类改动**才做三视角深度验证与全局核对。
* **规范拆分有判据、默认不拆**：须三条硬条件同时成立才拆（判据形态或加载时机不同 / 不拆就真的坏 / 拆后每一半都自足），拆完逐项过「拆分后的自洽核对」。
* **依据要有落点、且能逐字核对**：规范正文是"怎么走"（规则 + 判定标准 + 依据名）——但**依据不能只存在名称**。故根目录 `library/`（**图书馆**）按主题存放**可逐字核对的依据**；**反查路径**是规范里的标准名/编号。图书馆**按需加载、不进常驻层**。依据找不全时按 `specs/general/source.adoc` 如实标"未确证"。
