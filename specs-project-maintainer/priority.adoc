= 最高关注项与不可降级清单（维护方自查）

本文件只写**维护方**在维护这套规范集合时的两件事：① **最高关注项清单**（重构/去重/精简/迁移时绝对不能动什么）；② **维护方必须为哪些东西设机械防线**（否则会「只在文本上成立、执行时不会发生」）。

**规则的正文不在这里**：分级定义（L1/L2/L3）、最高关注项的完整判据与「强调的正确做法」已随公共内容写在 `specs/core/execution.adoc`「分级与最高关注项」里——本文件不重复表述，只做维护方侧的自查清单。

== 最高关注项（不可降级，重构/精简时首保）

最高关注项**级别不是同一档**——"最高关注项"与"条款本身是 L1"是两件事：

* **规范性铁律（P1/P2/P3/P5/P6/P7，条款本身 L1）**："该怎么做"没有裁量空间——任何理由都不得偏离；机械防线钉的是铁律本体。
* **纪律性铁律（条款本身 L2）**：约束的是"读多少、在什么上下文里做"这类**行程安排**，存在正当豁免，按定级四问只能到 L2；但它**极易被无声违反**，故与规范性铁律同列最高关注项。**列为最高关注项 ≠ 条款本身是 L1**。

=== P1. 文件移动/重命名必须用 `git mv`，禁止 delete+create

* **要求（L1，最高）**：不得用「新增新文件 + 删除旧文件」代替移动/重命名，否则 git 历史断裂。
* **依据**：rename 跟踪的可追溯性靠版本控制机制原语——delete+create 会永久断链且**事后无法恢复**（ISO 10007 对变更可追溯的要求）。
* **判定标准**：`git diff --cached -M --summary` 对移动显示 `rename`；`git status`/`git diff --name-status` 不应出现"同一批改动里 `D` + `A` 且内容高度相似"。完整规则与自检命令见 `specs/general/git.adoc`「文件移动与重命名」。
* **重构防误改**：本条**不因去重而删除**。多文件/多层重复出现时，**保留一处完整定义**，其余位置用**一行引用**指向它；**禁止以"内容重复"为由删除任何一处引用**。

=== P2. 调整规范必须保证完整性，且校验要真正执行

* **要求（L1，最高）**：调整规范不得丢失规则；**规范类改动**改完必须跑机械校验 + 干净子 agent 语义复核，不得"定义了校验却不执行"。**复核须一并回答三视角、都过才算完成，且由同一个干净子 agent 一次读取、结论分栏**。
* **依据**：规范集合属受配置管理约束的资产，变更须可追溯、防止误删（ISO 10007、ISO 9001）；需求变更须保持完整性并可追溯（ISO/IEC/IEEE 29148）；评审也可作为核验手段（IEEE 1028）。
* **判定标准（两件事分开读）**：① **本条的存在与不可降级对任何改动生效**；② **本条规定的三视角动作只适用于规范类改动**——三视角为 **①完整性 + ②有效性与认知质量 + ③接纳面**，结论强度按「验证的效力等级」标（概念项只到"未发现问题"）。代码类改动不走三视角，按 `specs/general/verify.adoc`「验证的适用边界」的机械判据判过不过；同一提交含两类改动时按更严一侧取验证范围，但三视角只覆盖其中的公共内容部分。**结论强度按对象分档**：概念项复核**只到"未发现问题"**，须标**悬置**并写明已复核角度，**且不得当作阻断交付的条件**。
* **重构防误改**：本条与最高关注项的存在性**必须由机械防线钉住**。**公共内容里不得写某项目私有的抓手名、脚本名与仓库结构**，也不得声明"已由机械防线钉住"——那属维护规范集合的那一方自己的事。**把具名抓手改成泛化要求而项目侧没有对应具名检查，属把"必须 + 判据"压成"原则 + 方向"的可执行性降级**。

=== P3. 文档/注释内容不得减少（迁移只换承载位置）

* **要求（L1，最高）**：文档内容可写在代码文档注释或独立文档，但**要求记录的内容一项不能少**；不得以"精简""去重"为名删简真实内容。
* **依据**：记录内容是事实与决策的载体，删除即失去可追溯性（ISO/IEC/IEEE 29148 的可追溯要求、ISO 9001 的成文信息控制）。**去重针对"重复表述"，不针对"必要内容"**。
* **判定标准**：按 `specs/general/doc.adoc`「注释与文档」的「必记录项」①-⑩ 逐项核对，缺一即未完成。
* **重构防误改**：去重前必须先确认"删的是重复表述、不是必要内容"；对无法确定的内容**保留**（宁可冗余不可缺失）。

=== P4. 读取按最小必要，长会话简单任务须在干净上下文执行；执行轮次须合并（少绕）

* **要求（L2 建议，最高关注项）**：任务开始前先定出**最小必要信息集**并只读该集合内的内容；会话执行过多个任务后，切换任务时**应当**把历史上下文与新任务隔离，简单任务优先在**干净上下文**中执行。**同列的还有「少绕」**：互相无依赖的调用须一次批量发出、构建与校验的输出须一次取到、长流程不得零信息空转（判据正文见 `specs/general/context.adoc`「执行吞吐」）——它与「少读」是同一件事的两面，同属行程安排、同样只能到 L2。
* **依据**：上下文越长，信息召回与长程推理越差、token 成本与时延越高（注意力预算与 context rot；Anthropic 工程博客《Effective context engineering for AI agents》）；只加载必要的高信号内容（Agent Skills 开放规范的 progressive disclosure）。**完整论证与量化说明见图书馆「上下文与执行吞吐的依据」主题。**
* **判定标准**：① 读前能说出"本次任务的最小必要信息集"，且实际读取未超出；② 已定位文件的任务使用了精确定位读取、未启动全库扫描；③ 任务切换时不沿用旧任务的探索路径；④ 读完后读到的内容全部与任务相关；⑤（**少绕**）本次任务的调用是否已尽量合并。
* **重构防误改**：受不可降级保护——维护规范集合的项目须机械钉住其存在性、必加载层引用落点与『不可降级』声明。

=== P5. 不可逆操作先确认，不得编造事实与来源

* **要求（L1，最高）**：① **删除/清空/覆盖等不可逆操作**执行前须确认目标、可回滚、范围可界定，三项任一不确定即停下提问；② **不得编造事实与来源**——命令/API、依赖坐标、标准编号与名称、链接与路径、数据与结论，不知道就明说并去查证。
* **依据**：两类失效**危害不可逆或会扩散**——误删/强推覆盖的数据与历史无法恢复（ISO 10007）；虚构来源会污染整条下游引用链且事后极难发现。**犯错成本不对称**：做对比做快重要得多。
* **判定标准**：① 不可逆操作前能说出"删的是什么、能否恢复、范围边界"，且实际按此执行；② 本次给出的命令/路径/编号/数据，都能指出**来源或实测依据**；③ 无把握时输出的是"未确证"而非貌似合理的编造内容。
* **重构防误改**：本条**不因去重而删除**；存在性与关键要点**须由机械防线钉住**。

=== P6. 协作执行者选择：子任务一律由同 Agent（**同 Agent 身份**）承担，不得点名外部执行者；不可用时按**降级**路径

* **要求（L1，最高）**：需要子 Agent 时**一律由与执行者相同的 Agent 承担**，**不得点名外部 Agent / 外部 NPC**；**同 Agent 子执行者不可用时，由主 agent 串行承担同一职责**（并在留证中标明独立性边界）、仍不可行则**如实标悬置**，**不换任何外部来源**；派发优先选**一次性、边界明确、可超时**的形式。完整口径见 `specs/general/collab.adoc` 与 `specs/general/verify.adoc`「规范验证」。
* **依据**：评审与被评审须相互独立（IEEE 1028）；变更的核验须可追溯到可核对的对象与判据（ISO 10007）。**本集合的自身取舍**：换成另一个来源**不因"更独立"而成为许可的复核者**——它看不到本执行者已加载的规范，判据一致性与耗时都不可核对。
* **适用面（先定条件再谈强制）**：本条**只在平台层写明该前提成立时按强制判**——本仓库的平台落点是 `specs/platform/cnb.adoc`「评论唤起新实例」；**平台层未写明**时**不得援引本条拒做或把任务停在中间**。
* **判定标准**：① 派发目标是不是外部 Agent/NPC 的标识；② 交换面是否超出本执行者可直接调用的派发；③ 结论回传面是否落在本执行者读不到的地方。任一命中即违规。
* **重构防误改**：本条**不因去重而删除**；口径与 level 由公共侧承载，本处是维护方清单里的一处**完整定义**，不得改回"外部来源可以顶替"的宽松写法；存在性与口径（新口径须在、旧口径不得复活）**须由机械防线钉住**。

=== P7. 重命名与内容修改必须分两个提交

* **要求（L1，最高）**：同一文件在一次改动里**既重命名、又修改内容**时，一律拆成两个提交——第一个只做重命名、内容逐字节不变（**本次涉及改名的文件全收在这一个改名提交里**，不按文件个数分摊），第二个再改内容、不再动路径；分量小、引用少都不是合并的理由。**「压缩提交」的请求不覆盖本条**：用户要求压缩提交/合并成一个提交但**未点名本条**时，只压本次任务尚未合入的临时中间提交，本条的两个提交**原样保留**——两者不是同一类对象，压掉即删掉一条可独立回溯的记录（判据见 `specs/platform/cnb.adoc`「压缩提交」）。完整规则见 `specs/general/git.adoc`「重命名与内容修改须分两个提交」。
* **依据**：一次变更只承载一个可追溯的目的（ISO 10007）。**与 P1 的关系**：P1 保证"git 认得这是一次移动"，P7 保证"这次移动是一条可独立回溯的记录"——同一目的的两道防线。
* **判定标准**：① `git log --follow --name-status <新路径>` 应显示"先 `R`（仅改名、内容 0 增删）、后 `M`（改内容）"两条记录；② `git diff <改名提交>^ <改名提交> -M --stat -- <新路径>` 的增删数为 0/0；③ 同一提交里该文件同时出现 rename 与内容行改动即为不合规；④ `git log --diff-filter=R -M --name-status` 应能看到那**一条批量改名**记录。
* **判据形态（为何不是 P1 的子条）**：本条判的是**提交历史的分量**（rename 与内容改动是否同处一个提交），P1 判的是**工作区里用了哪条命令**（`git mv` 还是 delete+create）——判据对象与形态都不同，合并会让"用对了命令却把两者塞进一个提交"从两条防线之间漏过去。
* **重构防误改**：本条**不因去重而删除**。多处出现时保留一处完整定义，其余位置用一行引用/重申指向它；**禁止以"内容重复"为由删除任何一处引用**。

=== P7 的重申与去重

P7（重命名与内容修改必须分两个提交）与 P1 同列最高关注项，**不可降级**——分级概览与去重时不得漏项。

=== 最高关注项与去重的冲突处理（重点）

最高关注项与其引用**允许、且应当**在多处出现，但**一处是完整定义、其余是引用**。**判重时必须先判定"是不是最高关注项的引用"**：是引用 → 不判为注水、不合并；是**逐字复制的完整定义** → 收敛为一处定义 + 引用。

== 强调的正确做法（避免"写两次"的误解）

**"写两遍同样的完整内容"不等于强调**，反而是反模式：它会让 AI 把它判成"重复内容"而合并/删除，且两份会各自漂移。业界标准做法是**分级 + 单一定义 + 显式引用**：

* **分级**：把条目**升到 L1 / 列为最高关注项**（本文件），优先级由分级表达，不靠重复次数表达。
* **单一定义**：完整定义只写在一个**权威位置**，其余位置**只写一行引用**。
* **显式标题**：权威定义所在小节用**显著标题**承载强调；重要条目在 `AGENTS_COMMON.adoc`「最高优先级铁律」**登记一次**，作为"进门必读"。
* **机械钉住**：对"任何时候都不得消失"的条目，用校验脚本钉住其**存在性**，这比人工重复书写更可靠。

=== 机械防线的核对对象是**判据本体**，不是轴名（L1）

**"条目有『要求/依据/判定标准』三个轴"不等于"判据在"**——最小化重构恰好会从"轴名齐全"的条目里**抽走判据**：轴名、级别、标题全都留着，而"不按文件个数分摊""未点名本条时原样保留"这类**能拿去核对的一句话**不见了。防线若只核轴名，这种条目照样全绿，读者按条文核对时已无从判定。

* **核对对象（L1）**：机械防线须钉**判据本体**——即**判定标准里能拿去核对的那句话**（触发条件、动作、取值、边界、分档），以及轴名所承载的具体要求。**只核"『要求』『依据』『判定标准』『判定形态』等轴名/条目标题在不在"即为防线空转**，等于判据坏了仍报绿。
* **判定标准（逐条可核对，任一命中即未做到）**：① 被钉的是**轴名**（`**要求**`、`**依据**`、`**判定标准**` 一类标签）或**条目标题**，而非条正文里的判据；② 抽掉该条**全部判据句**、只留轴名与口号时，防线**仍不报红**；③ 防线靠**相邻条目的字样**兜住已消失的要求（要求被搬走/并进别条后仍全绿）。
* **必配反例用例（L1）**：每条这类防线须有**一条"轴名齐全、判据被抽走"的反例用例**——按"把判据压成一句骨架"改造后，防线**必须报红**。没有这条反例，防线的实际效力无从证明（正例全绿只能说明它不误报）。

结论：**同一约束只写一次完整定义、其余用引用**；需要更强强调时，用"升级别 + 加显著标题 + 机械钉住"，而不是复制正文。**钉住时钉判据本体、不钉轴名**——"轴名齐全"只是外观。

### 计数类抓手的已知欠账（本仓库自身，如实登记）

`check_guard_manifest` 的三件事（接线数、反例用例数、台账点名）目前**只核数量**，数量本身可被维持而不惊动任何防线。以下两条是**已知、未修**的形态，如实登记在此——**不得**读成"有这三道核对就等于防线不会被摘空"。两条都属"判据要另写一道防线"，不在既有核对的能力范围内（避开"同一约束写两次"）。

* **同文件内改名／增删一进一出可维持用例数（L1，如实标注）**：判据是"`test_*` 方法数不得低于基线"，故把 N 条用例改名、再补 N 条**空占位**即可回满计数——`check_specs_test.py` 报 OK、单测全通过（本仓库实测复现：把整道 `check_java_serial_guard` 的 16 条反例换成 16 条 `pass` 空占位，计数不变、全绿）。**防的是什么**：把"用例数"当成"某条用例仍在"——它只保证**总量**不减少；**某条具体用例**是否还在，机械判不出来。
* **防线数与用例数不同源时长期偏低（已修口径，留档）**：两处都须与**实取总数**同源（接线数＝`CHECKS` 序列、用例数＝`check_specs_test.py` + `check_effective_test.py` 两处相加）。基线若停在旧口径上，会长期低于实际数、删掉若干条仍不报红（本仓库实测：用例基线 995 而实际 998、接线基线 90 而实取 91）——修法是**回填基线**并在此留账，而不是把判据放宽。

**机械核对边界（覆盖不到的两类，一次声明）**

防线的效力有边界，**边界只声明一处**：`script/check_specs.py` 的 `GUARD_CHECK_LIMITS` 给出机械核对**覆盖不到的两类**——① **运行时事实**（某次执行的实际行为、平台侧记录、产物正文）；② **语义判断**（判据是否仍成立、内容质量、机制在真实环境会不会发生）。**凡越出这两类的结论，一律不得由机械防线判定**；防线作者要说明"这一条核不到"就写这两类，**不得在每道防线/每条台账备注里各写一句**"某次是否真的……交人/子 agent 复核"。

* **判据（逐条可核对，任一命中即未做到）**：① 两类边界**没写**（读者无从判断机械到底能核什么）；② 每道防线/每条台账**各自写一句**同类口径（同一句话重复 90 遍＝信息密度判据③的同义反复，且边界随各条措辞漂移）；③ 把越出这两类的结论**记成"通过"**（把复核结论当确定性判据）。
