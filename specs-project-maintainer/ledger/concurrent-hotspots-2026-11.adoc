= 本轮：并行改动仍会撞车的落点（按冲突形态逐个消掉）

**为什么还有这一轮**：上一轮把「三份最热的文件」拆开了，可拆完再量一遍，撞车的落点并没有消完——只是换了几处。本轮按**冲突的形态**（不是按文件）逐个处理，判据补进 `specs/general/coding-file-role.adoc`「文件的角色」的两条（「逐行登记面」加了判定标准④、「规则数据按主题分份」新增一条）。

**本轮实测的撞车落点与处置**

* **防线清单表的表体**（`specs-project-maintainer/guards.adoc` 那张表）：行正文早已按防线名分份，但**表体本身**仍是一百多行手写，序号与「谁在用」两格是执行序列的投影——两条并行的改动都在中段加一道防线时，改的是同一处，没有任何合并策略能解。处置：表体改成**生成物**，`python3 script/check_specs.py --write-guards-table` 按 `CHECKS` 整段重写，判据（`check_guard_order_guard`）按「这一段是否等于现算的那一份」整段核；人不再碰表体。
* **反例用例的记账表**（`script/specs-rules/_guard_test_floor.toml`）：一条防线一行、187 行挤在同一份文件里，往哪个方向加都落在同一片区域。处置：按**主题**分份（`[tokens.guard_test_floor.<主题>]`，11 份），引擎把两层压平成同一张表（判据侧读到的东西一字未变）。
* **接线数常量**（`GUARD_WIRING_BASELINE`）：它与 `CHECKS` 序列是同一个数的两处写法，而近三十次合入里几乎每次都要动那一行。处置：常量删除，现值一律由序列现算；删防线的可见性改由两处承担（清单表少一行、记账表多一格）。
* **规则数据**（`script/specs-rules/*.toml`）：`coding.toml` 一份里堆着 21 道防线、`verify.toml` 9 道……任何一次改判据都要往同一份文件里插一组。处置：按主题建目录、一道防线一份（`<主题>/guards/<防线名>.toml`，90 道已搬完），加载侧按目录**递归扫描**——加一份不必改任何脚本，也不必在别处登记；同一道防线出现在两份文件里时，合并期直接报错（不得后者静默覆盖前者）。

**没有拆、并写明理由的部分**

* `CHECKS` 序列与检查项编号清单：它们记的是**次序**，而次序只有一份——按「独占落点只做一次、且要能被机械核」办（清单表由它现算、逐行对账），不拆。
* 逐轮记账（`ledger/`）：早就一轮一个文件，本来就不撞。

**验证**：`python3 script/check_specs.py` 只剩两条环境/历史类（合并提交、本机无 `asciidoctor`）；`python3 -m unittest discover -s script -p "*_test.py"` 2639 条全绿；`node script/site-link-check.js` 退出码 0。
