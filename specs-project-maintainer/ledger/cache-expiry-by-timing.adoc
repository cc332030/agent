| 本轮（缓存有效期分三类时效口径、逐份声明、按口径判不按名单判） | 无（沿用 `check_cache_guard` 扩面，不另建第二真源） | 219 → **219** | 用户口径：『统一缓存管理，每种缓存的缓存时间不一样，需要按实际需求进行缓存时间设置——有从取回来开始算的，有固定时间到期的（签到一般是第二天 0 点刷新），还有其他的，帮我调研』。既有缓存规范只管「一处入口、先缓存后在线、有变动才更新、来源时间标识」，**每份缓存的有效期怎么取值**没有判据。**调研（常设七条）**：① RFC 9111 给 `max-age`（相对）与 `Expires`（绝对）两类新鲜度；② Caffeine 给 `expireAfterWrite`/`expireAfterAccess`/`refreshAfterWrite`；③ Redis 官方文档给 `EXPIRE`（相对 TTL）/`EXPIREAT`（绝对时刻）与刷新续期；反例面是「签到按相对时长写、跨零点不复位」与「全项目一个时长套所有数据」。**改动**：① 判据本体落通用层 `specs/general/coding-runtime.adoc`「缓存（统一管理、先缓存后在线）」新增一条 L1「缓存有效期按数据的时效口径分类取值」——三类口径（相对 TTL / 绝对定点 / 滑动或到期前刷新）按数据实际需要取其一、每份在其入口一处显式声明，四条判定标准（统一时长 / 说不出口径出处 / 跨零点该复位按相对时长 / 本该相对计时按固定时刻写死），边界（与入口唯一、取数次序各自成立；凭据令牌按 security 处理），依据行补 RFC 9111 `max-age`/`Expires` 与本集合取舍声明；② 前端载体 `specs/stack/web.adoc`「缓存（载体）」补「缓存有效期的载体（L1）」——取值写在缓存入口那一处、签到按绝对时刻判；③ 机械侧沿用 `check_cache_guard`：`CACHE_ANCHORS` 补一组（8 组 29 枚 → 9 组 34 枚，下限 29→34）、`cache.toml` 的 web 载体组补一组、`TestCheckCacheGuard` 补两条反例（本体被抽、载体被抽）；脚本注释与规则数据同步；④ 图书馆 `library/sources.adoc` 补逐字依据（RFC 9111/Caffeine/Redis）、`library/adoption.adoc` 补本集合取舍与用户实证；本记账归档。只钉文本与落点——「某份缓存到底该定多长、算不算跨自然边界复位的数据」属运行时事实与语义判断，交人/子 agent 复核。
