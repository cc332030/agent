== 为什么它是可选的

那一套的**全部代价**（落点按份铺开、逐行登记面只留身份、派生件改由生成器产出、`merge=union`）
都是为"**未完工分支并存、要合入同一目标分支**"这一种处境付的。单线顺序开发、或由单一执行者
按序改动的仓库，为它把文件铺开只是平白多出上百个文件，而收益为零——本仓库前几轮实测过：
把一张 187 行的表拆成 187 个单行文件，被当场否掉并整体回滚。

反过来，"可选"**不等于**可以把它删掉：规则可以不用，取值不能不存在——否则下一次有人想启用时，
连"该怎么做"都无处可读。故检查侧的口径是两句话，缺一不可：

* **没声明启用**：只核那一档的**取值**还在不在（判据本体、`[source-management].mode` 那一格、四处派生条的要点），**不要求**本项目真的分份、配策略、上生成器；
* **声明启用**（本仓库是 `mode = "concurrent"`）：按锚点逐项核，缺一项即报红。

== 落到了哪

* 判据本体与取值：`specs/general/coding-file-role.adoc`「文件的角色」的「适用前提」——四档角色与五条 L1 之外单列一格，写明"两档并列、由项目声明取哪一档"、取值在哪、未声明时按原口径办、判定标准三条（① 没声明却按它要求别人；② 声明了却仍按原口径办；③ 把"本项目不启用"读成"这一套错了"）。
* 四处派生条各加一句回指（不复制取值）：`specs/general/version-control.adoc`「冲突处理」的「只增不改的落点按路径声明合并策略」「逐行登记的派生件不由人工手作」，`specs/general/git.adoc` 的 `merge=union` 取值。
* 检查侧：`script/check_specs.py` 的 `file_role_enabled()` 是唯一判别式；`check_git_attributes_merge_guard` 与 `check_ledger_table_generated_guard` 按它决定"要求/不要求"，`check_file_role_guard` 两档都核（核的是取值，不是本仓库有没有铺开）。
* 反例用例：未声明时不配 `merge=union`、不建生成器都放行；而"没声明却把判据取值删了"照样报红——"没启用"与"删掉这条规则"必须分得清。
