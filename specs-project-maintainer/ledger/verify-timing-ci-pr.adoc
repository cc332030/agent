= 逐轮记账：验证时机收尾统一 + CI 找不到承载 PR 直接建

[cols="2,2,1,5", options="header"]
|===
| 轮次 | 新增防线 | 接线数 | 承接了什么

| 本轮（验证时机 + CI 交付载体） | 沿用 `check_dev_flow_guard`、`check_pr_scope_guard`（不新开防线） | 210 → **210**（接线数不变：只补两条既有防线的锚点） | 用户口径：①『哪个有问题就先跑哪个，都没问题再全部执行复验，不要每次都跑所有的』——`specs/general/verify.adoc`「按需验证、不滥验证」补该句与『收尾统一验不等于每步都不验』（中途只跑有问题的那一处、收尾才跑全复验，`check_dev_flow_guard` 补两处锚点）；②『一个 issue 一个 pr，为什么要问我？这是 ci 环境一定要 pr 的』——纠正 `specs/platform/cnb.adoc`「找不到承载它的合并请求」条与 `prompts/_common.txt` delivery 片段：自动化场景找不到承载 PR 时**直接新建分支与 PR 交付、不停下问**（一个 issue 一个 PR 就是交付链本身，没有 PR 即没有交付），本地人工场景才停下问，`check_pr_scope_guard` 两侧锚点同口径改写、反例用例同步。两处均只钉要点文本仍在；具体环境判定与「用户是否已允许」属运行时事实与语义判断，交复核。
| 补漏轮（用户再问「这些做了没有，没有就加上」） | 沿用 `check_dev_flow_guard`（不新开防线） | 210 → **210**（接线数不变：只补既有防线锚点与两条反例） | 复取值发现：上一轮汇报声称的「分阶段交付≠分阶段验证」「编译与测试同口径」**从未落进交付提交**（临时环境回收丢失），承载本次任务的合并请求实际只落了「哪个有问题先跑哪个」与 CI 交付载体纠正。本轮按原文补真缺口：① `specs/general/verify.adoc`「没做完就不验」补『分阶段交付 ≠ 分阶段验证』（边界与取值见该条），`specs/general/git.adoc`「分阶段交付」补同口径边界，`specs/general/context.adoc`「延后验证、一次到位」同步；② `specs/general/verify.adoc`「能合就合」补『编译与用例同口径、不重复付账』（同受不重复验约束、未过期产物复用、完整基线不是频繁重编理由、重编译只限三类），`context.adoc` 同步；`check_dev_flow_guard.toml` 补锚点，`check_specs_test.py` 补两条反例（两处被单独抽掉均实测报红）。「哪个有问题先跑哪个」上一轮已真落、本轮不重复。
| 补漏轮（用户再问「还有哪些漏了」） | 沿用 `check_dev_flow_guard`（不新开防线） | 210 → **210**（接线数不变：只补既有防线锚点与一条反例） | 逐条比对用户原话发现最后一处逐字缺口：诉求『不要反复执行没有问题的用例……但是基线测试也不是频繁执行的原因』里，**『基线不是频繁执行原因』此前只写在编译段（『完整基线也不是频繁重跑编译的理由』），用例/测试语境没有明文**——本轮在 `specs/general/verify.adoc`「哪个有问题就先跑哪个」补『**完整基线不是频繁跑测试的理由**』（即便某套是用例的完整基线/全量，也不得当成隔三差五重跑的借口；反复跑没问题的用例按『先信已验过的、不重复验』处理），`check_dev_flow_guard` 补两处锚点，`check_specs_test.py` 夹具同步 + 一条反例（该句被抽实测报红）。至此用户四条原话诉求逐字都有落点。
