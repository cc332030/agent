| 本轮（汇报须送到发起人手里） | `check_report_delivery_guard`（新增） | 207 → **208** | 用户口径：『你的结果回复到哪里了？需要修复此问题』。**要治的失效（本仓库实证）**：一轮 NPC 任务改动做完、校验跑完、`git push` 也推了，**PR 下一条新评论都没有**——发起人只能再问一次。执行者的最终输出里是有汇报的，但那个输出**没落到任务单的评论上**，读者拿到的仍是零。**缺口的位置**：交付片段管**汇报的内容与通道数**（一条完整汇报 / 必须停下确认），从没说过"这条汇报要**发出去**"；平台层管"往哪派"与"不得自派"，**回程没有对称的一条**——"写了但没发"正好从这两半之间落下去，而当时所有文本防线都报绿。**改动**：① 通用侧 `prompts/_common.txt` 的 `delivery` 片段补一条——**"写了汇报"不等于"发出去"**、平台上**必须在该任务单下新增一条评论**、**判据是这条评论发出去没有**、有改动却没评论**按没有交付判**（片段会被复制到未知项目执行，故判据本体在片段里）；② 平台层 `specs/platform/cnb.adoc`「评论唤起新实例」补**对称的回程条**（送达形态**只有一个**、执行者自己的输出与会话自述与提交说明**都不算送达**、三条判定标准、与「不得以评论派发唤起自己」的分工、内容口径回指交付片段）；③ 公开面 `PROMPTS.adoc` 与 `README.adoc` 同步；④ 规则数据两处：`script/specs-rules/cnb/guards/check_report_delivery_guard.toml`（平台层五组锚点 + 片段两组锚点）与既有 `script/specs-rules/prompts/guards/check_delivery_guard.toml` 的 `delivery` 片段补同一条锚点组（片段是那一份的判据本体，`check_delivery_guard` 也得钉住它，否则抽掉后那道防线仍报绿）+ 行正文随规则数据同层同名（`<防线名>.adoc`，不必另登记哨兵）+ 台账登记 + 清单表重算 + 本表；⑤ 反例用例 `TestCheckReportDeliveryGuard` 7 条（平台条被删、自己的输出不算送达被删、判定标准被删、与自派的分工被删、回指被删、片段那条被删、片段判据被删），`TestCheckDeliveryGuard` 的夹具补上片段那一条。**评审补两处**：① 本格原写反例用例「8 条」而 `TestCheckReportDeliveryGuard` 实为 **7 条**（正例不算）；② 原只提 `check_report_delivery_guard.toml` 一处规则数据，漏了 `check_delivery_guard.toml` 的 `delivery` 片段那一组锚点——片段被抽掉时那道防线仍会报绿。**只钉「要点与落点是否仍在」**；"这次到底发没发那条评论、发的内容算不算汇报"属运行时事实与语义判断，交复核。
