= 逐轮记账：能用现有依赖满足时不新增直接依赖

[cols="1,2,1,5", options="header"]
|===
| 轮次 | 新增防线 | 接线数 | 承接了什么

| 本轮（依赖直接新增） | `check_dependency_direct_add_guard`（新增） | 205 → **206** | 用户口径（Issue）：间接依赖已经带来的能力，不要再补一条直接依赖（Maven 手动写进 `pom.xml` 的那条，往往早已被间接依赖带上）。**要治的失效**：某个类一直在用、却不知道它是被哪条依赖带进来的，于是「顺手补一条」——构建照旧成功、代码一行没变，而同一个能力在**依赖图**与**依赖清单**里各留一处入口（与「模块已间接依赖却又加一次」同一成因、两种载体）。**改动**：① 通用层 `specs/general/dependency.adoc`「引入依赖」新增一条 L1（条文、三条判定标准、三档例外——要钉版本时落版本约束而不是多一条声明、传递路径可能失效、对外编译期契约——以及为什么默认不新增）；② 同节旧的「传递依赖不直接使用」改成**反向口径**（间接依赖带入的库可以直接使用、只是别重复声明），旧写法把间接依赖当成不可用的东西，执行者为了「合法使用」反而去补一条；③ 技术栈层只给**载体**：`specs/stack/maven.adoc`（现有依赖面取解析后的依赖树、要钉版本时落 `<dependencyManagement>`）、`specs/stack/gradle.adoc`（解析结果、`constraints`/`platform`），两份都回指通用层，并删掉 Maven 侧那句没有判定标准的旧建议；④ 依据两侧补齐：`library/sources.adoc` 新增「Maven 依赖机制」段（官方原文，其中一条**恰恰主张显式声明**直接使用的依赖），`library/adoption.adoc` 登记本站偏离与理由；⑤ 判据本体锚点与落点全在规则数据 `script/specs-rules/dependency/guards/` 那一份 + 哨兵 + 台账 + 清单表重算 + 本表。**只钉「要点与落点是否仍在」**——『这次新增的那条依赖，其能力是不是现有依赖面里已有』属运行时事实（要解析依赖树），交人/子 agent 复核。
|===
