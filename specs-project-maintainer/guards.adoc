= 机械防线清单（维护方自查）

本文件是**本仓库机械防线的唯一索引**：`script/check_specs.py` 里每一道防线的**执行次序与它钉住什么**。
它为什么必须存在、以及它承载哪一条规则的判据：

* **执行次序即加载次序即注意力次序**（本文件承载）：防线的**编排顺序应当是刻意的**——同一批次内先跑基础台账（引用存在、链接、节名、登记），再跑要点防线（判据本体），最后跑编译类校验。改顺序的意图须能在此处读出。次序的**值**只有 `CHECKS` 一处：本表逐行按它排开、不写号（由 `check_guard_order_guard` 逐行对账，一侧改了而另一侧没改即报红）。
* **工具与防线的总览**在维护方项目规范入口（`AGENTS.adoc`「Agent 项目自身工具声明」）；本文件承载**逐条清单**，是该入口那一行的展开落点——一份文件一条规则，两处不各写一遍。
* **生成物一览**（这一段由 `script/specs-rules/ledger.toml` 的登记表现算，`check_ledger_table_generated_guard` 核「现场＝重算结果」；加一个生成物只往登记表加一条，这一行自己长出来）：

// BEGIN GENERATED: 生成物一览
* `specs-project-maintainer/guards.adoc`「检查项编号」：检查项编号表的表体（真源 `script/check_specs.py`；重算 `python3 script/gen_derived.py --write`）
* `specs-project-maintainer/guards.adoc`「生成物一览」：生成物逐条一览（真源 `script/specs-rules/ledger.toml`；重算 `python3 script/gen_derived.py --write`）
// END GENERATED: 生成物一览

* **哪一条规范由哪一道防线钉住**的逐条对照是 `script/check_effective.py` 的台账（`MECHANISMS`），**不是**本文件；两者分工：本文件答"有哪些防线、按什么次序跑"，台账答"某条规范有没有抓手"（由 `check_guard_manifest` 与 `script/check_effective.py` 的 `--list` 双向核对）。

== 执行次序与用途（`CHECKS` 序列，唯一来源）

这张表**不写序号**：次序由 `script/check_specs.py` 的 `CHECKS` 序列表达（它才是唯一来源），本表逐行按它排开、序号由读者顺着行读出来。写着数字就有第二份次序——插入一道防线，其后每一行的数字都得改一遍（`specs/general/coding.adoc`「能由规则现算的，就不要列成清单」判定标准③）。「谁在用」那一格同理：调用关系由函数体现算，复制进表里就是同一份事实的第二处写法。

「钉住什么」那一格是**回指**：它指到这道防线旁边的 `<防线名>.adoc`——那份标记与这道防线的规则数据**同层同名**（判据写在脚本里的防线，则是哨兵 `script/specs-rules/guard-scripts.toml` 旁边那一份），文件名即防线名，读者顺着文件名就能找到它，不必先知道它在表里第几行。于是新增/修订一道防线时，改动方只碰**自己那份**规则数据、旁边那份标记与 `CHECKS` 里自己那一行；表体本身是**生成物**（`python3 script/check_specs.py --write-guards-table` 整段重写），落点由判据从规则数据的加载面现算、不另取目录配置（`specs/general/coding.adoc`「文件的角色」的「并行落点按'份'切」）。

== 记账沿革（两个基线的口径与反复出现的教训）

**逐轮流水账进 git 历史**（每一轮的增删与两个基线的位移都在提交记录里）；本节只留**仍会重现的教训**：

* **基线只允许"不低于实测"**：填小了会误报、填大了则静默通过（虚高的基线等于把下一次真删除一并放行）。故动过用例/接线之后，两个基线都按**同源实取**回填、**不按两侧各自数目相加**。
* **口径须一次回填**：用例数口径＝`script/` 下全部 `*_test.py` 里**真正被 `unittest` 收集**到的用例数（唯一实现见 `_count_collectable_tests`）。口径变更必须与该轮的增删一并记全，否则基线长期低于实际数、删掉用例也不报红。
* **同名覆盖**：同一测试类里重名的用例只保留后一个、前一个**从未执行**；净增数按处理后的实取数算。
* **本表整行漏抄与"防线被删"在本层同形**：数量与台账点名两处都不报红，拦下它的是与 `CHECKS` 逐行对账的次序判据。
* **数量类判据的已知欠账**（防线摘除、用例改名/空占位可维持计数）：登记在 `specs-project-maintainer/priority.adoc`「计数类抓手的已知欠账」。
* **本轮起的逐轮记账不在本文件**：新增/删除防线、接线数落到多少，写进 `specs-project-maintainer/ledger/`（**一轮一个文件**，见该目录的 `README.adoc`）。本文件只留"仍会重现的教训"——每轮往同一张表的同一位置插行，两个并行改动必然撞在同一行上，那正是本文件要少犯的错。
* **反例用例的类数不记账**：那个数由测试类名现数（`TestCheckXGuard` → `check_x_guard`），规则数据里不另记一份——记的那份与代码各改一个数时，判据照样全绿。删防线时连它的反例一起删，可见性由落点承担：`<防线名>.adoc` 少一份、`CHECKS` 少一行。

== 检查项编号（生成物：`script/check_specs.py` 头部清单的派生件）

**这一段整段是生成物**：由 `script/gen_derived.py` 按 `script/check_specs.py` 头部的**检查项清单**现算产出，
`check_ledger_table_generated_guard` 核「现场与重算结果**逐字节一致**」——手改这张表、或改了头部清单忘了重算，
都会当场报红。

**判定标准（任一命中即违规）**：① 表里的编号与头部清单不一致（手改过，或少了一段）；② 头部清单改了而本表没重算；
③ 本表被拿去驱动别处（生成物不得成为第二份真源）。**重算**：`python3 script/gen_derived.py --write`。

**为什么它必须生成**：头部那份清单是**连续编号**的，本表逐行抄第二份时，每新增一项都要往中间插一行、其后
编号整体位移——每次改动都落在这两百多行里，两个并行改动必撞在同一片区域。派生件与本体同一次产出（判据本体见
`specs/general/coding.adoc`「分发产物的体积与按需加载」的「派生件与本体同处一个构建步骤」条），改动的落点就
只剩头部那一处。

**这一列"用例总数"不记**：反例的类数由测试类名现数，规则数据里也不另记一份（记的那份与代码各改一个数时，判据照样全绿）。记账只写接线数——由 `CHECKS` 序列定，不另写常量。

历史轮次原样归档在 `ledger/rounds-before-sharding.adoc`（从本文件整段搬过去，逐字未改）；那些行里写着总数，是**当时的记录**，不回溯改（同 `specs/general/changelog.adoc`）。

* **新增一道防线时**：① 在 `script/check_specs.py` 的 `CHECKS` 序列里追加自己那一行（次序就是它，不另写号）；② 在自己那份规则数据旁放零字节的 `<防线名>.adoc` 标记（行正文跟着规则数据走，与它的 `.toml` 同层同名）；判据写在脚本里的防线没有自己的 `.toml`，哨兵 `script/specs-rules/guard-scripts.toml` 旁边的 `<防线名>.adoc` 就是它那一份；③ 跑 `python3 script/check_specs.py --write-guards-table` 重写清单表表体（它是生成物，不手抄）；④ 本轮记账写进 `specs-project-maintainer/ledger/` 的**新文件**（一轮一个）。落点、清单表、`CHECKS` 三处的变动就是"防线增删"在 diff 里的记账。
* **删除一道防线时**：说明删的是哪一道、为什么删、由谁承接，并删掉它那两份落点（`CHECKS` 里那一行、它旁边那一份 `<防线名>.adoc`）——留在目录里那份会成为"旁边没有对应规则数据或哨兵"的尸块，当场报红。
* **两者都由** `check_guard_manifest`（台账点名、接线数、各防线反例用例类、头部编号、逐轮记账引用的接线数、覆盖面清单的覆盖面与单一落点）与 `check_guard_order_guard`（本文件清单表的次序与 `CHECKS` 序列一致）机械核对；**接线本身**（序列里的防线都真实存在、每个已定义防线都可达）由 `check_wiring_guard` 守；"某道防线钉的判据是否仍然成立"越出该范围者交人/子 agent 复核。
