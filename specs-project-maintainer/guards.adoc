= 机械防线清单（维护方自查）

本文件是**本仓库机械防线的唯一索引**：`script/check_specs.py` 里每一道防线的**执行次序与它钉住什么**。
它为什么必须存在、以及它承载哪一条规则的判据：

* **执行次序即加载次序即注意力次序**（本文件承载）：防线的**编排顺序应当是刻意的**——同一批次内先跑基础台账（引用存在、链接、节名、登记），再跑要点防线（判据本体），最后跑编译类校验。改顺序的意图须能在此处读出。`CHECKS` 里改一处位置时必须同步本表次序（由 `check_guard_order_guard` 逐行对账，一侧改了而另一侧没改即报红）。
* **工具与防线的总览**在维护方项目规范入口（`AGENTS.adoc`「Agent 项目自身工具声明」）；本文件承载**逐条清单**，是该入口那一行的展开落点——一份文件一条规则，两处不各写一遍。
* **哪一条规范由哪一道防线钉住**的逐条对照是 `script/check_effective.py` 的台账（`MECHANISMS`），**不是**本文件；两者分工：本文件答"有哪些防线、按什么次序跑"，台账答"某条规范有没有抓手"（由 `check_guard_manifest` 与 `check_effective.py` 的 `--list` 双向核对）。

== 维护约定

**已删除的防线（删除记账，按次序留档）**

|===
| 原编号 | 防线 | 删除原因 | 由谁承接
| 原 69 | `check_orm_boundary_guard` | 与 `check_persistence_access_guard`（持久化访问防线）重复：同一组 API 条文的落点被两处各钉一份，属第二真源；且它把「谁可以调用 `IService` 成员方法」等**形态判据**钉成机械抓手，而该判据是语义判断（某个调用点算不算跨类调，见 `GUARD_CHECK_LIMITS`），钉它等于用文本核对代替语义核对 | `check_persistence_access_guard`（条文与四种成员方法、禁止面、例外与栈层落点）+ 人/子 agent 复核（跨类调用的语义判断）；`specs/stack/java.adoc` 与 `specs/stack/spring.adoc` 的对应条文随该防线一并收回（见 `library/sources.adoc` 与本轮交付说明）
|===

* **新增一道防线时**：在本表末尾追加一行、在 `script/check_specs.py` 的 `CHECKS` 序列相应位置追加一个元素，并同步 `GUARD_WIRING_BASELINE`（接线数）与 `GUARD_TEST_BASELINE`（反例用例数）——两个基线值的变动就是"防线增删"在 diff 里的记账。
* **删除一道防线时**：说明删的是哪一道、为什么删、由谁承接，并同步两个基线（不记账就减数＝防线静默消失）。
* **两者都由** `check_guard_manifest`（台账点名、接线数、用例数、头部编号）与 `check_guard_order_guard`（本表次序与 `CHECKS` 序列一致）机械核对；**接线本身**（序列里的防线都真实存在、每个已定义防线都可达）由 `check_wiring_guard` 守；"某道防线钉的判据是否仍然成立"属语义判断，交人/子 agent 复核。
