= Agent 项目自身规范（本仓库维护专用，不随通用规范分发）

== 两类内容与隔离（先读，防混淆）

本仓库托管两套**相互隔离**的规范，处理前必须先判定**这次动的是哪一类**（本仓库最易出错之处），两类规则不同、不得混用：

* **公共内容**（`AGENTS_COMMON.adoc` + `specs/`）：面向**任意语言、任意项目**，随规范分发给**引用方项目**（其入口恒为 `AGENTS_COMMON.adoc`，只认这一入口）。改动须遵守通用规范本身（link:specs/core/priority.adoc[] 的 L1/L2/L3 与最高关注项）。
* **Agent 项目自身**（本文件 `AGENTS.adoc` + `script/` + `.github/workflows/` + `README.adoc`/`PROMPTS.adoc`/`prompts/`/`INSTALL.adoc`）：只服务**本仓库**（规范集合自身的维护：检查脚本、CI、使用文档），**不分发、引用方无需也不应引入**。

判定口径与要点：

* **按"对谁成立"归类**：规则对"任意项目"成立 → 公共内容（写进 `specs/`）；描述"本仓库的校验/CI/工具如何做" → 项目自身。只对某个项目成立的内容不得写进公共内容。
* **入口识别**：通用规范入口恒为 `AGENTS_COMMON.adoc`；本文件（根目录 `AGENTS.adoc`）会被平台**自动识别为本仓库的 agent 规范**，故本文件不能改名为 `AGENTS_COMMON.adoc`，两者以文件名区分（`AGENTS_COMMON.adoc` 之命名即为其避开平台识别）。
* **加载范围**：本仓库内维护规范集合时，**须同时遵循**通用规范（`AGENTS_COMMON.adoc` + `specs/`）与本文件；引用方项目中**只加载** `AGENTS_COMMON.adoc`（含 `specs/`），不加载本文件。
* **落点约束**：适用于**引用方项目**的规则（如 `git mv` 铁律）只能靠"规范文本写清楚 + 引用方自检"生效，**不得**把"本仓库看不到、管不着"的引用方行为写成机械校验（见下「校验范围」）。

== 规范管理（Agent 项目自身）

以下规范适用于本规范集合本身的维护，属 Agent 项目自身规范。

== 规范分层

* 规范分层：规范只收录通用规则；局部决策/已知取舍写在对应代码注释，不写入全局规范。规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储于 `specs/` 下，分层定义、加载调度与技术栈扩展约定见通用规范 `AGENTS_COMMON.adoc`「分类与懒加载」「技术栈扩展约定」

== 规范组织

* 校验范围（元规范）：本仓库的机械校验**只针对本仓库自己维护的对象**——公共内容（`AGENTS_COMMON.adoc` + `specs/` 的文本、引用、登记与最高关注项）、本仓库自有文档与模板（`README.adoc`、`PROMPTS.adoc`、`prompts/`、`INSTALL.adoc`）、本仓库工具与 CI 的行为。**不得为"引用方项目的工作区形态"设计检查**：本仓库看不到引用方的代码与操作，引用方也不引用本仓库脚本，这类检查对其零作用、只在本仓库凭空报错。**适用于引用方**的铁律（如 `git mv`）以"规范文本写清、判定标准可执行"为落点，不做机械拦截；**最高关注项不得被削弱**，由 `check_priority_guard` 钉住（见下「工具声明」）。
* 规范组织：规范须归纳总结、分组分类组织（按主题分组，如执行原则/文档/代码质量/code review/规范管理/任务与 git），不得遇到情况就零散追加、平铺堆砌——新增或调整规范时先检查是否与现有条目重复、可归纳合并，冗余内容须合并去重；条目按主题归类到对应分组，不重复表述
* 去重与「最高关注项引用」的边界（**防误删最高优先级**）：去重只针对**重复的完整表述**，不针对**最高关注项的引用**。规范中同一最高关注项（如 `git mv` 铁律）会在多处出现，是**刻意保留的强调与可发现性**（进门必读 + 本仓库落点 + 专项规范各指向同一权威定义），**不是重复内容、不得合并删除**；判定口径：**一处完整定义 + 其余一行引用**为正确形态（见 link:specs/core/priority.adoc[]「强调的正确做法」）；多处**逐字复制的完整定义**才是冗余，收敛为"一处定义 + 引用"。调整规范时若把某最高关注项的引用判为"重复"而删除，视为**破坏完整性**、按最高关注项 P2 处理
* 禁止注水（元规范，**新增与存量一并适用**）：规范集合（`specs/`、`AGENTS.adoc`、`AGENTS_COMMON.adoc` 等）**不得加入无意义、划水、凑字数的内容**——新增/扩充前先过"是否可删"三问：①是否与现有条目重复或可归并（重复即合并去重，不新增）；②是否承载可核对的事实/决策/边界/取值（空话套话、复述既有结论、为对称凑数而加的一律不加）；③是否只把临时讨论落盘（临时讨论不是规范）。**未经用户明确要求，不得为"看起来完整"新建规范/文档文件**；**已存在的重复、空壳、过时文档直接删或合并**（模板与既有文档同样适用）
* 规范简洁性（元规范）：规范须在**保证完整性**的前提下**尽可能简洁准确**——表述要点化、少冗余铺垫；**简洁不是删规则**，完整性校验仍是底线。规范会被加载进 AI 上下文，篇幅越大越易挤爆上下文；限制**不宜过多过严**，保留必要边界与自由裁量空间，只约束真正必须统一的点
* 文档质量与冗余（本仓库落点）：文档按通用规范 link:specs/general/doc.adoc[]「注释与文档」执行——质量六条（准确、完整、可执行、有价值、简洁、可验证）与"文档不得注水""多余文档直接去除"三条为准，本条不重复表述
* 规范引用文件必须真实存在：规范文件中引用的 `specs/...` 文件地址必须是**当前真实存在、可追溯**的文件；**不得引用已删除/不存在的旧文件**，也不得添加指向旧文件的历史来源注记（旧文件可能已无法追溯，且会让引用悬空）。引用一律直接指向当前有效的文件地址（迁移/拆分后直接引用新地址），不保留无用的历史来源声明（此条由 `script/check_specs.py` 的 `check_historical_notes` 机械校验拦截，非仅靠自觉）
* 新增规范文件必须同步登记调度器：加载调度器（`AGENTS_COMMON.adoc`）是规范文件的唯一登记处——新增/拆分规范文件时，"写文件"与"在调度器登记"是同一个动作，禁止只建文件不登记（未登记的文件按调度器执行时永远不会被加载，其中规则实际失效）；此条由 `script/check_specs.py` 的 `check_dispatcher_registry` 机械校验（登记集合 ⊇ 被引用集合），非仅靠自觉
* 模板代码块必须逐字保留：`INSTALL.adoc` 等文档中作为“安装/生成模板”的代码块，其内容（含换行与空行）必须逐字原样保留，AI 读取后写入目标项目时不得合并、折叠、删除或重排任何一行（否则会导致生成文档样式改变）。此条由 `script/check_specs.py` 的 `check_install_codeblock` 机械校验拦截（校验必备行各自独立成行、空行分隔完好），非仅靠自觉

== 版本与变更记录（本仓库落点）

* 统一变更日志：本仓库的对外变更集中记录于根目录 `CHANGELOG.adoc`（时间倒序、最新在上），**不分散在各文档**；条目只记影响、不记过程（撰写规则见 link:specs/general/changelog.adoc[]）。
* 适用范围（与规范变更的边界）：该文件记录本仓库**自身**的变更（如跨仓库分发约定、与用户/规划相关的重大调整等）；**`specs/` 规范文件的变更不入 changelog、由其 git 历史承载**（见 link:specs/general/doc-design.adoc[]「版本与变更记录」）。
* 版本线：本仓库无对外版本号载体（脚本与 CI 工具为持续可用的工具链），故版本线集中记录在 changelog 条目中——初始发布为 `1.0`（2026-08-23 规范集合首次对外可引用），此后每次对外发布递增次版本。

== 规范调整

* 依据优先引用业界标准（**调整规范的方向性前提**）：新增/调整规范条目时，须按 link:specs/core/execution.adoc[]「优先站在前人的肩膀上看世界」执行——**优先**为该条**标注广泛、高知名度、高可靠性的业界标准/论文出处**（ISO/IEC/IEEE、RFC、W3C、OWASP 等），让读者知其所以然；**出处只写标准名/编号、不附链接**（链接会失效或指向非官方来源，标准名称唯一、AI 可自行检索；个人项目、知名度很低、仅此一处者除外）；**不得为凑数堆砌不相关标准**，出处须真实可溯源，无法确证则不引。对照标准时须守住**完整性、同义性**（规则与边界不丢、要求不变）；仅当本规范对某标准**有明确的自身取舍/更严要求**时，才显式覆盖并写明理由
* 提示词方向（主侧重）与优先级：公共任务提示词（`PROMPTS.adoc` + `prompts/`）属本仓库自身内容，但其**侧重点是最核心、方向性的内容**——后续所有操作、要求都依据它，方向错了后面全做错。故调整提示词时：**主侧重**与**优先级（L1/L2/L3）**须显式保留、不得省略或降级，登记表（`PROMPTS.adoc`）与各提示词正文的侧重须一致且互不相同（不得把两个提示词的侧重复制成同一个 = 方向混用）；由 `check_prompts_primary` 机械钉住（见下「工具声明」），语义是否被削弱仍由人/子 agent 复核承担
* 规范调整：除非明确要求删除某条规范，否则调整规范时必须保证规范完整性（不因调整丢失规则）。「完整性校验」与「定义未执行核验」相互独立、触发条件不同：
  ** 完整性校验（**每次改完规范后必做**）：核对本次调整未丢失规则、无误删/误改/遗漏。①自动运行 `script/check_specs.py`（及测试 `script/check_specs_test.py`）做机械校验（检查项见下「Agent 项目自身工具声明」）——须**全量扫描**（跨文件交叉敏感，且本地执行毫秒级、无外部成本），**不得**改为"只查有变更的文件"；②对内容实质性调整，在隔离上下文开启干净子 agent 核对要点是否全保留——语义核验**范围限定为本次变更文件及其引用/被引用的受影响文件**。完整性校验不依赖用户提示、不得以"用户未要求/改动很小/项目简单"为由跳过（仅用户明确豁免时除外）
  ** 定义未执行核验（**单独手动执行**）：评估"规范里定义的每条规则是否真正有效、是否被实际遵守、有无可执行抓手"，而非仅存在于文档——规范里写了某条"必须/不得"不代表它必然被遵守，这类"定义未执行"的风险不会随每次调整暴露，故不随每次调整自动运行；由用户决定何时整体执行（如运行 `script/check_effective.py`），并可指定核验范围

== Agent 项目自身工具声明

以下工具属于 **Agent 项目自身**（维护本规范集合用），不属于通用规范、不随 `specs/` 分发：

* `script/check_specs.py` — 规范完整性机械校验（引用存在、链接格式、**节名引用存在**、技术栈一致、**调度器登记完整**、私有约定、历史来源声明、INSTALL 模板、**文档注水**、要点防线、**优先级防线（最高关注项 P1/P2/P3 不得被删/降级）**、**提示词防线（各提示词主侧重/方向与 L1/L2/L3 优先级不得被删/降级）** + AsciiDoc 语法；**只校验本仓库维护的规范/模板文本，不检查 git 工作区状态、不检查引用方项目**，检查项清单见其文件头 docstring）；配套测试 `script/check_specs_test.py`（含 `TestScopeStaysOnCommonContent` 钉住上述范围、`TestCheckPriorityGuard` 钉住最高关注项、`TestCheckPromptsPrimary` 钉住提示词主侧重与优先级）
* `script/check_effective.py` — "定义未执行"深度核验工具；配套测试 `script/check_effective_test.py`
* `.github/workflows/check-specs.yml` — 本仓库 CI：在 push/PR 上运行上述校验及其配套测试（**只做确定性校验**；面向语义的规范审查交人 review，不在 CI 中调用外部 AI）

> 注：`script/clean_tmp.py` 是供**引用方项目**远程加载使用的通用清理工具（见通用规范 `specs/core/execution.adoc`「临时产物」），虽存放在本仓库 `script/` 下，但**不属于** Agent 项目自身规范，随通用规范一起被引用方使用。
