= Agent 项目自身规范（本仓库维护专用，不随通用规范分发）

== 双规范结构与隔离声明（先读）

本仓库（项目名 **Agent**，仓库 `cc332030/agent`）托管两套**相互隔离**的规范，二者定位不同、分发范围不同，不得混淆：

* **通用规范**（会被其他项目引入）：入口 `AGENTS_COMMON.adoc` 及其引用的 `specs/` 目录。面向**任何语言、任何项目**的通用 agent 执行规范，被**引用方项目**作为规范入口引入（路径解析与加载规则见 `AGENTS_COMMON.adoc`「访问与解析」「分类与懒加载」）。
* **Agent 项目自身规范**（本文件 `AGENTS.adoc`，位于仓库根目录）：仅适用于**维护/运营本 Agent 仓库本身**的规则，即"关于这套规范集合自身"的内容——规范集合的维护、检查脚本、CI 等。**不属于通用规范、不随通用规范分发、引用方项目无需也不应引入**。

== 识别方式（排除在通用规范外、但仍可识别）

* 通用规范入口恒为 `AGENTS_COMMON.adoc`——引用方项目只认这一入口，无需知道本文件。
* 本文件（根目录 `AGENTS.adoc`）是 Agent 项目自身规范入口，采用 `AGENTS.adoc` 命名，位于仓库根目录，会被平台**自动识别为本仓库的 agent 规范**：本项目自身规范走 `AGENTS.adoc` 识别路径，通用规范入口 `AGENTS_COMMON.adoc`（同样位于仓库根目录，但以 `AGENTS_COMMON.adoc` 命名，避开平台对 `AGENTS.adoc` 的识别）与其区分，供引用方项目引入。
* 加载范围：
  ** **本仓库内**维护规范集合时：须同时遵循通用规范（`AGENTS_COMMON.adoc` + `specs/`）与本文件（Agent 项目自身规范根目录 `AGENTS.adoc`）。
  ** **引用方项目中**：只加载通用规范 `AGENTS_COMMON.adoc`（含其 `specs/`），**不得**加载本文件。
* 通用规范 `AGENTS_COMMON.adoc`（「访问与解析」）仅说明引用方引入方式（引入本文件 + `specs/`），双规范定位的完整描述见本文件，不再写入通用规范。

== 规范管理（Agent 项目自身）

以下规范适用于本规范集合本身的维护，属 Agent 项目自身规范。

== 规范分层

* 规范分层：规范只收录通用规则；局部决策/已知取舍写在对应代码注释，不写入全局规范。规范按"必加载层 / 通用层 / 技术栈层 / 平台层"分层存储于 `specs/` 下，分层定义、加载调度与技术栈扩展约定见通用规范 `AGENTS_COMMON.adoc`「分类与懒加载」「技术栈扩展约定」

== 规范组织

* 规范组织：规范须归纳总结、分组分类组织（按主题分组，如执行原则/文档/代码质量/code review/规范管理/任务与 git），不得遇到情况就零散追加、平铺堆砌——新增或调整规范时先检查是否与现有条目重复、可归纳合并，冗余内容须合并去重；条目按主题归类到对应分组，不重复表述
* 规范引用文件必须真实存在：规范文件中引用的 `specs/...` 文件地址必须是**当前真实存在、可追溯**的文件；**不得引用已删除/不存在的旧文件**，也不得添加指向旧文件的历史来源注记（旧文件可能已无法追溯，且会让引用悬空）。引用一律直接指向当前有效的文件地址（迁移/拆分后直接引用新地址），不保留无用的历史来源声明（此条由 `script/check_specs.py` 的 `check_historical_notes` 机械校验拦截，非仅靠自觉）
* 模板代码块必须逐字保留：`INSTALL.adoc` 等文档中作为“安装/生成模板”的代码块，其内容（含换行与空行）必须逐字原样保留，AI 读取后写入目标项目时不得合并、折叠、删除或重排任何一行（否则会导致生成文档样式改变）。此条由 `script/check_specs.py` 的 `check_install_codeblock` 机械校验拦截（校验必备行各自独立成行、空行分隔完好），非仅靠自觉
* 机械校验拦截 + AI 校验并调整：规范集合除机械校验（`check_specs.py`，确定性强）外，还需 AI 校验**并调整**——`script/ai-review.sh` 加 `--apply` 时，AI 审查发现问题后直接产出每个文件的修正版内容并落盘；CI 的 `auto-fix-pr` job 把已落盘的修正内容提交到分支并开 PR（PR 内为实际改动而非仅问题清单）。机械拦截保证确定项不回归，AI 校验并调整覆盖需语义判断的项

== 规范调整

* 规范调整：除非明确要求删除某条规范，否则调整规范时必须保证规范完整性（不因调整丢失规则）。「完整性校验」与「定义未执行核验」相互独立、触发条件不同：
  ** 完整性校验（**每次改完规范后必做**）：核对本次调整未丢失规则、无误删/误改/遗漏。①自动运行 `script/check_specs.py`（及测试 `script/check_specs_test.py`）做机械校验（引用存在、文档链接格式、技术栈一致、私有约定、规范要点防线）——机械校验**每次全量扫描所有规范文件**：它纯本地、毫秒级、不消耗外部成本，且天然交叉敏感（删除/改动某文件可能让其余未变更文件的 link 悬空或技术栈登记失配，须全量才能发现），故**不得**改为"只查有变更的文件"；②对内容实质性调整，在隔离上下文开启干净子 agent 核对本次调整要点是否全保留、有无误删/误改/遗漏——语义核验**范围限定为本次变更文件及其引用/被引用的受影响文件**，其成本只随本次变更范围增长、不随规范文件总量增长。完整性校验不依赖用户提示、不得以"用户未要求/改动很小/项目简单"为由跳过（仅用户明确豁免时除外）
  ** 定义未执行核验（**单独手动执行**）：评估"规范里定义的每条规则是否真正有效、是否被实际遵守、有无可执行抓手"，而非仅存在于文档——规范里写了某条"必须/不得"不代表它必然被遵守，这类"定义未执行"的风险不会随每次调整暴露，故不随每次调整自动运行；由用户决定何时整体执行（如运行 `script/check_effective.py`），并可指定核验范围

== Agent 项目自身工具声明

以下工具属于 **Agent 项目自身**（维护本规范集合用），不属于通用规范、不随 `specs/` 分发：

* `script/check_specs.py` — 规范完整性机械校验（引用存在、链接格式、技术栈一致、私有约定、要点防线 + AsciiDoc 语法）；配套测试 `script/check_specs_test.py`
* `script/check_effective.py` — "定义未执行"深度核验工具；配套测试 `script/check_effective_test.py`
* `script/ai-review.sh` — 规范语义 AI 审查脚本
* `.github/workflows/check-specs.yml` — 本仓库 CI：在 push/PR 上自动运行上述检查（含配套测试与 AI 审查）

> 注：`script/clean_tmp.py` 是供**引用方项目**远程加载使用的通用清理工具（见通用规范 `specs/core/execution.adoc`「临时产物」），虽存放在本仓库 `script/` 下，但**不属于** Agent 项目自身规范，随通用规范一起被引用方使用。
