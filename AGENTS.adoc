= Agent 项目自身规范（本仓库维护专用，不随通用规范分发）

== 两类内容与隔离（先读，防混淆）

本仓库托管两套**相互隔离**的规范，处理前必须先判定**这次动的是哪一类**（本仓库最易出错之处），两类规则不同、不得混用：

* **公共内容**（`AGENTS_COMMON.adoc` + `specs/`）：面向**任意语言、任意项目**，随规范分发给**引用方项目**（其入口恒为 `AGENTS_COMMON.adoc`，只认这一入口）。**公共内容必须自足**：其中出现的内容只能引用 `AGENTS_COMMON.adoc` 与 `specs/` 下的文件——引用引用方看不到、拿不到的私有落点即属放错位置。改动须遵守 L1/L2/L3 分级与最高关注项（见 link:specs-project-maintainer/priority.adoc[]）。
* **维护方自查层**（`specs-project-maintainer/` + 本文件 `AGENTS.adoc`）：只对**维护这套规范集合（或同类"共享资产集合"）的项目**成立——规范集合自身的维护（分类准入与定级口径、自身重构）、最高关注项的不可降级清单、维护方的验证义务、公共内容被加载时的可控性清单。它**不随公共内容分发**、也**不由公共入口登记**（`AGENTS_COMMON.adoc` 里没有它的加载项）：普通引用方项目无需也不应引入；同类维护项目按本文件（维护方的项目规范入口）登记加载。
* **Agent 项目自身工具**（`script/` + `.github/workflows/` + `README.adoc`/`PROMPTS.adoc`/`prompts/`/`INSTALL.adoc`/`CHANGELOG.adoc`）：只服务**本仓库**（检查脚本、CI、使用文档），**不分发**。

判定口径与要点：

* **按"对谁成立"归类**：规则对"任意项目"成立 → 公共内容（写进 `specs/`）；只对"维护规范集合这类项目"成立 → `specs-project-maintainer/`（维护方自查层）；描述"本仓库的校验/CI/工具如何做" → 本文件与 `script/`（项目自身工具）。只对某个项目成立的内容不得写进公共内容。
* **入口识别**：通用规范入口恒为 `AGENTS_COMMON.adoc`；本文件（根目录 `AGENTS.adoc`）会被平台**自动识别为本仓库的 agent 规范**，故本文件不能改名为 `AGENTS_COMMON.adoc`，两者以文件名区分（`AGENTS_COMMON.adoc` 之命名即为其避开平台识别）。
* **加载范围**：本仓库内维护规范集合时，**须同时遵循**公共内容（`AGENTS_COMMON.adoc` + `specs/`）、维护方自查层（`specs-project-maintainer/`）与本文件；普通引用方项目中**只加载** `AGENTS_COMMON.adoc`（含 `specs/`）——公共内容里**不含任何指向 `specs-project-maintainer/` 的引用**（该层不随公共内容分发）；同类维护项目才按本文件登记加载它。
* **落点约束**：适用于**引用方项目**的规则（如 `git mv` 铁律）只能靠"规范文本写清楚 + 引用方自检"生效，**不得**把"本仓库看不到、管不着"的引用方行为写成机械校验（见下「校验范围」）。

== 规范管理（Agent 项目自身）

以下规范适用于本规范集合本身的维护，属 Agent 项目自身规范。

== 规范准入与定级（分类、准入、重构的落点）

* 分类、分层与准入：一条规则属公共规范还是项目规范、属哪一层、是否该收进规范集合（准入九问），以及用户提出新增规范时的提案校验（合理性、是否已有标准、是否已有条目、升级与举一反三）见维护方自查层 link:specs-project-maintainer/spec-lifecycle.adoc[]。本仓库维护**公共内容**与**维护方自查层**时按该文件执行；本仓库自有的私有规则写在本文件，不进 `specs/`。
* 定级与级别维护（**本仓库落点**）：新增/调整条目须按 link:specs-project-maintainer/spec-lifecycle.adoc[]「如何给一条规范定级」的四问定级，并按「归类举证」在提交说明中留痕（对象/依据/条款类型/定级结论）——不得按关键词或『感觉重要』直接写死 L1；级别标定后调整时不得静默改动（改了须写明理由，见该文件「级别变更与复盘」），并定期按该节「复盘六查」核对级别混乱。
* 准入与定级判定必须留痕：新增/调整规范条目时，须能逐项回答准入九问（通用性、可执行、非重复、有依据、有承载价值、能定级、有落点、非拆分而膨胀、成本可接受）；不得以"用户要求"为由跳过判定直接收录。
* 准入与定级防线：分类与准入规范文件、调度器登记项、"提案校验（是否已有标准 / 是否已有条目 / 升级举一反三）""定级口径（四问与判定表等）""读法形态（执行侧只给怎么走）""规范自身重构顺序与重构后的有效性核对"要点不得被删或降级，由 `script/check_specs.py` 的 `check_spec_admission_guard` 机械钉住（见下「Agent 项目自身工具声明」）。

== 规范分层

* 规范分层：规范只收录通用规则；局部决策/已知取舍写在对应代码注释，不写入全局规范。规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储在 `specs/` 下（对任意项目成立）；**只对维护规范集合的项目成立**的维护类规范另存于 `specs-project-maintainer/`（维护方自查层，不随公共内容分发）；分层定义、加载调度与技术栈扩展约定见 `AGENTS_COMMON.adoc`「分类与懒加载」「技术栈扩展约定」

== 验证的适用范围（本仓库落点）

* 验证**按改动性质分层取值**（**本仓库落点**）：公共内容被加载时的**可控性清单**（维护方自己在新增/调整公共内容时要逐维核对的"影响面 / 成本 / 可控性"）见 link:specs-project-maintainer/context.adoc[]。判据（代码类改动按机械判据判过不过、涉及公共内容才做三视角与全局核对、唯一判据问句、不得互串）见公共 link:specs/general/verify.adoc[]「验证的适用边界」；**本仓库自己的**验证义务（维护方做哪一步、硬超时取值、三态台账的填写责任、各节点的落点核对）见 link:specs-project-maintainer/verify.adoc[]。

== 规范组织

* 校验范围（元规范）：本仓库的机械校验**只针对本仓库自己维护的对象**——公共内容（入口清单见 link:PUBLIC.adoc[]）、图书馆（见下「依据图书馆」）、维护方自查层、本仓库自有文档与模板、本仓库工具与 CI 的行为；**不得为"引用方项目的工作区形态"设计检查**（本仓库看不到引用方的代码与操作、引用方也不引用本仓库脚本，这类检查对其零作用、只在本仓库凭空报错）。**适用于引用方**的铁律（如 `git mv`）以"规范文本写清、判定标准可执行"为落点，不做机械拦截；**最高关注项不得被削弱**，由 `check_priority_guard` 钉住（见下「工具声明」）。
* 规范组织与自身重构：规范须归纳总结、分组分类组织（按主题分组，如执行原则/文档/代码质量/code review/规范管理/任务与 git），不得遇到情况就零散追加、平铺堆砌；重构按 link:specs-project-maintainer/spec-lifecycle.adoc[]「规范集合的自身重构」的**固定顺序**执行——**先判归属 → 再判层级 → 再判重复 → 最后压缩表述**（顺序不可颠倒），并按其速查区分"删 / 移 / 留"。**判断顺序先于手段**：把归属与层级判清楚，多数"要不要删"的问题会自动有答案。**读的形态**按该文件「同一条规则有两种读法」——执行场景只给"怎么走"（规则 + 判定标准 + 依据名），原因与取舍只在"要思考、要决策"时给；**依据只压缩为名称/编号、不得整段删除**。**是否该拆分**按该文件「一条规范何时该拆分」判定（三条硬条件同时成立才拆，且"不拆就真的坏"须能指出实害；**默认不拆**，拆完逐项过「拆分后的自洽核对」）；**重构的验收**按该文件「重构后须核对规范有效性」——内容不丢之外还须确认**两形态分离 / 可执行性不降级（不得把"必须 + 判定标准"压成"要注意"）/ 可见性不丢**；形态声明与各最高关注项的依据行由 `script/check_specs.py` 机械钉住
* 依据图书馆（**本仓库落点**）：仓库根 `library/` 是本项目的**图书馆**（**本仓库私有、不随规范分发**；按需懒加载、非常驻物），存放本项目里**需要找依据**的东西——规则与决策背后的**逐字可核对依据**（外部标准原文摘录与"标准确实支持该条"的映射、内在依据、真实失效实证与反例）及技术选型/组织约定的依据；入口 link:library/README.adoc[]（`library/README.adoc`）登记全部主题。**落点判据**：`specs/**` 随规范分发给引用方，图书馆含**只对本项目成立**的内容（当初的失效、取舍、实证），写进公共内容只会被改写成空泛表述，故落在仓库根（与 `prompts/`、`script/` 同性质）。维护要求：①依据找不全**如实标"未确证"、不得虚构填补**（见公共 link:specs/general/source.adoc[]「无法确证时的正确做法」）；②图书馆**不复制规则**（规则本体在 `specs/`），只补依据；③**新增主题文件必须同步登记入口主题表**（写文件与登记是同一个动作）；④**独立成篇判据**见入口 link:library/README.adoc[]（与规则本体分离 **且** 按"依据对谁成立"归类；只对本站成立的更严取舍与组织约定须独立成篇，不预建空壳）；⑤以上由 `check_library_guard` 机械钉住（入口/主题文件存在、登记与实际**双向一致**、外部标准**逐字引文锚点仍在**、准入依据主题的**同义性差异要点仍在**、馆内引用**按仓库根可解析**——链接全仓库**只有一个基准**：文档渲染在仓库根、Asciidoctor.js 按文档所在目录解析，故根级相对即仓库根相对）
* 禁止注水与简洁性（元规范，**新增与存量一并适用**）：规范集合（`specs/`、`AGENTS.adoc`、`AGENTS_COMMON.adoc` 等）**不得加入无意义、划水、凑字数的内容**——新增/扩充前先过"是否可删"三问：①是否与现有条目重复或可归并（重复即合并去重，不新增）；②是否承载可核对的事实/决策/边界/取值（空话套话、复述既有结论、为对称凑数而加的一律不加）；③是否只把临时讨论落盘（临时讨论不是规范）。**未经用户明确要求，不得为"看起来完整"新建规范/文档文件**；**已存在的重复、空壳、过时文档直接删或合并**（模板与既有文档同样适用）。简洁**不是删规则**——在保证完整性的前提下尽可能简洁准确（完整性校验仍是底线）；规范会被加载进 AI 上下文，**篇幅越大越易挤爆上下文、限制过严会挤掉合理裁量**，故只约束真正必须统一的点
* 常驻层只放底线（**本仓库落点，防"越写越多捆住 AI"**）：必加载层（`AGENTS_COMMON.adoc` + `specs/core/`）每次会话都无条件加载，**只放**①L1 底线、②最高关注项、③必加载层的引用落点；**方法论、依据论证、示例、元规范（怎么写规范、怎么定级、怎么重构）、维护类规范一律移出常驻层**——通用规则进通用层（用到才加载），只对"维护规范集合这类项目"成立的进 `specs-project-maintainer/`（维护方自查层）。调整后须核对常驻层体量是否反弹：确定项（常驻层结构、最高关注项存在性）由 `script/check_specs.py` 机械钉住，**体量与层级的语义判断由人/子 agent 复核**
* 文档质量与冗余（本仓库落点）：文档按通用规范 link:specs/general/doc.adoc[]「注释与文档」执行——质量六条（准确、完整、可执行、有价值、简洁、可验证）与"文档不得注水""多余文档直接去除"三条为准，本条不重复表述
* 规范引用文件必须真实存在：规范文件中引用的 `specs/...` 文件地址必须是**当前真实存在、可追溯**的文件；**不得引用已删除/不存在的旧文件**，也不得添加指向旧文件的历史来源注记（旧文件可能已无法追溯，且会让引用悬空）。引用一律直接指向当前有效的文件地址（迁移/拆分后直接引用新地址），不保留无用的历史来源声明（此条由 `script/check_specs.py` 的 `check_historical_notes` 机械校验拦截，非仅靠自觉）
* 新增规范文件必须同步登记：公共内容（`specs/`）的规范文件由加载调度器（`AGENTS_COMMON.adoc`）唯一登记；维护方自查层（`specs-project-maintainer/`）的规范文件由**本文件**登记——新增/拆分规范文件时（两类都要），"写文件"与"在调度器登记"是同一个动作，禁止只建文件不登记（未登记的文件按调度器执行时永远不会被加载，其中规则实际失效）；此条由 `script/check_specs.py` 机械校验——`specs/` 下公共内容按 `check_dispatcher_registry`（登记集合 ⊇ 被引用集合）、本维护方自查层按 `check_priority_guard` / `check_spec_admission_guard` 各自核对"已在本文件登记"，非仅靠自觉
* 模板代码块必须逐字保留：`INSTALL.adoc` 等文档中作为“安装/生成模板”的代码块，其内容（含换行与空行）必须逐字原样保留，AI 读取后写入目标项目时不得合并、折叠、删除或重排任何一行（否则会导致生成文档样式改变）。此条由 `script/check_specs.py` 的 `check_install_codeblock` 机械校验拦截（校验必备行各自独立成行、空行分隔完好），非仅靠自觉

== 版本与变更记录（本仓库落点）

* 统一变更日志：本仓库的对外变更集中记录于根目录 `CHANGELOG.adoc`（时间倒序、最新在上），**不分散在各文档**；条目只记影响、不记过程（撰写规则见 link:specs/general/changelog.adoc[]）。
* 适用范围（与规范变更的边界）：该文件记录本仓库**自身**的变更（如跨仓库分发约定、与用户/规划相关的重大调整等）；**`specs/` 规范文件的变更不入 changelog、由其 git 历史承载**（见 link:specs/general/doc-design.adoc[]「版本与变更记录」）。
* 版本线：本仓库无对外版本号载体（脚本与 CI 工具为持续可用的工具链），故版本线集中记录在 changelog 条目中——初始发布为 `1.0`（2026-08-23 规范集合首次对外可引用），此后每次对外发布递增次版本。
* 更新粒度与提交压合：本仓库文档与脚本在**尚未提交之前**的所有调整（含批量重构、多次试跑修正）按 link:specs/core/execution.adoc[]「文档与代码对应同步」之「未提交前的更改归并」处理——**一律直接覆盖演进、不产生中间历史**；用户要求"压缩成一个提交"时，以当前工作区内容为准重做一次提交，中间过程不留在历史里。

== 环境标志与专用口径（本仓库落点）

* 环境专用口径写进提示词片段 `env-guard`（标志 + 专用口径 + 未命中时的中性口径），由 `check_env_marker_guard` 钉住；标志取值登记在此（本仓库私有，公共内容不引用）：NPC 唤起评论 = `CNB_EVENT` 非空（该环境已复制好仓库、`main` 是默认分支，看流水线须看 `.cnb.yml` 的 `include:` 目标）。

== 规范调整

* 依据优先引用业界标准（**调整规范的方向性前提**）：新增/调整规范条目时，须按公共 link:specs/general/source.adoc[]「外部引用」执行——**优先**为该条**标注广泛、高知名度、高可靠性的业界标准/论文出处**（ISO/IEC/IEEE、RFC、W3C、OWASP 等），让读者知其所以然；**出处只写标准名/编号、不附链接**（链接会失效或指向非官方来源，标准名称唯一、AI 可自行检索；个人项目、知名度很低、仅此一处者除外）；**不得为凑数堆砌不相关标准**，出处须真实可溯源，无法确证则不引。对照标准时须守住**完整性、同义性**（规则与边界不丢、要求不变）；仅当本规范对某标准**有明确的自身取舍/更严要求**时，才显式覆盖并写明理由
* 提示词方向（主侧重）与优先级：公共任务提示词（`PROMPTS.adoc` + `prompts/`）属本仓库自身内容，但其**侧重点是最核心、方向性的内容**——方向错了后面全做错。故调整提示词时：**主侧重**与**优先级（L1/L2/L3）**须显式保留、不得省略或降级，登记表（`PROMPTS.adoc`）与各提示词正文的侧重须一致且互不相同（不得把两个提示词的侧重复制成同一个 = 方向混用）；由 `check_prompts_primary` 钉住（见「工具声明」）
* 每次改完规范必做自检与来源核对（**防漏项与虚构，最高关注项保护对象**）：改动规范/文档后，除完整性校验外，还须按公共 link:specs/general/self-check.adoc[]「完成前自检」逐项核对**用户原始要求是否逐条落实、本次改动是否遗漏/越界**；并按公共 link:specs/general/source.adoc[]「内部引用」核对**本次新增的每条引用都指向当前真实存在的文件与节名**（不得凭印象拼路径、不得留下历史来源注记）。两条防线由 `script/check_specs.py` 的 `check_self_check_guard`、`check_source_guard` 机械钉住（见下「Agent 项目自身工具声明」）。
* 规范调整：除非明确要求删除某条规范，否则调整规范时必须保证规范完整性（不因调整丢失规则）。「完整性校验」与「定义未执行核验」相互独立、触发条件不同：
  ** 完整性校验（**每次改完规范后必做**）：核对本次调整未丢失规则、无误删/误改/遗漏。①自动运行 `script/check_specs.py`（及测试 `script/check_specs_test.py`）做机械校验（检查项见下「Agent 项目自身工具声明」）——须**全量扫描**（跨文件交叉敏感，且本地执行毫秒级、无外部成本），**不得**改为"只查有变更的文件"；②对内容实质性调整，在隔离上下文开启干净子 agent 做语义复核——**三视角一并回答、都过才算完成**：**①完整性**（对象在改动前后是否等价、要点是否全保留）、**②有效性与认知质量**（规范本体是否可被合规地执行、依据是否说对、代价说得清：判据可判定、机制在当前执行环境真会发生、**读的形态**（执行侧只给怎么走）、从属者可加载、放对层且常驻代价在预算内）与 **③接纳面**（**被未知项目加载后的影响面/成本/可控性**——不静默推翻引用方约定、不默认改其工作区、不引入无降级路径的依赖、体积可控）；**三视角合用一个子 agent**（同一份 diff、同一批受影响文件，一次读取、结论分栏列，不重复起子 agent；**每次验证都换一个干净上下文**，不得复用发起改动或上一轮验证用过的上下文），语义核验**范围限定为本次变更文件及其引用/被引用的受影响文件**、结论各自留证（①留逐条对照表、②留按判据/依据/机制/形态/层级体积/性能分类的问题清单、③留按影响面/成本/可控性分类的清单）——**三态强制分列**（通过／未发现问题／悬置），**"查不出"与"没做"须能分辨**；**子 agent 复核必须自带硬超时**（到点视为失联，放弃并如实标悬置，不得无限等待）。完整口径与标准出处见公共 link:specs/general/verify.adoc[]「验证总纲」「规范验证」；本仓库自己的落点见 link:specs-project-maintainer/verify.adoc[]；结论强度按对象分档：机械校验只核对确定项（可判对错），三视角复核属启发式——只到"未发现问题"、查不出的标"未确证/悬置"，**不得当作阻断交付的条件**（见公共「验证的效力等级」）。**验证对象不止规范文件**：`prompts/`、随规范分发的工具（如 `clean_tmp.py`）等"会被外部执行"的产物同样按三视角核对。校验不依赖用户提示、不得以"用户未要求/改动很小/项目简单"为由跳过（仅用户明确豁免时除外）
  ** 定义未执行核验（**单独手动执行**）：评估"规范里定义的每条规则是否真正有效、是否被实际遵守、有无可执行抓手"，而非仅存在于文档——规范里写了某条"必须/不得"不代表它必然被遵守，这类"定义未执行"的风险不会随每次调整暴露，故不随每次调整自动运行；由用户决定何时整体执行（如运行 `script/check_effective.py`），并可指定核验范围

== Agent 项目自身工具声明

以下工具属于 **Agent 项目自身**（维护本规范集合用），不属于公共规范、不随 `specs/` 分发：

* `script/check_specs.py` — 规范完整性机械校验（引用存在、链接格式、**节名引用存在**、技术栈一致、**调度器登记完整**、私有约定、历史来源声明、INSTALL 模板、**文档注水**、要点防线 + 优先级防线 + 规范准入防线 + 自检防线 + 来源防线 + Java 测试类命名防线 + 换行符防线 + 提示词防线 + **本仓库自身侧 git mv 自查** + **常驻层体积上限** + **从属者与能力自评防线（含执行者来源选择：强制同 Agent、不得点名外部 NPC、不可用时降级为串行）** + **规范验证防线（三视角）** + **任务生命周期防线（节点齐全 + 验证边界 + 拆分判据 + 分层取向）** + **接纳面防线（运行契约 + 公共内容私有引用 + 公共内容不得声明机械防线）** + **CI/CD 与平台协作防线（校验链完整 / 触发范围 / 依赖与外部资源可用性 / 超时与资源 / 非确定性 AI 不入 CI + CNB 钉定 sha 与强推对应关系、执行者可用性、流水线不无界挂起）** + **清单逐项与文档-脚本一致性防线（准入项数 / 七节点 / `check_*` 名字对得上 / 硬超时与三态留证）** + **NPC 禁合并防线** + **配置类不写逻辑防线** + **既有实现与先例优先防线** + **图书馆防线（含『规范准入与自身取舍』主题要点锚点）** + AsciiDoc 语法；各防线的具体抓手见该脚本文件头 docstring；**校验范围含 `specs/`（公共内容）与 `specs-project-maintainer/`（维护方自查层）；只校验本仓库维护的规范/模板文本，不检查引用方项目工作区**——本仓库自身侧的 git 暂存区状态行（`check_git_mv_selfcheck`）是唯一例外，且不得扩为读工作区文件内容或检查引用方）；配套测试 `script/check_specs_test.py`（`TestScopeStaysOnCommonContent` 钉住上述范围；其余各 `TestCheck*` 分别钉住对应防线，含环境标志与专用口径、NPC 禁合并、配置类不写逻辑、既有实现与先例优先、图书馆（含准入依据主题）、CI-CD 与平台协作）
* `script/check_effective.py` — "定义未执行"深度核验工具；配套测试 `script/check_effective_test.py`
* `.github/workflows/check-specs.yml` — 本仓库 CI：在 push/PR 上运行上述校验及其配套测试（**只做确定性校验**；面向语义的规范审查交人 review，不在 CI 中调用外部 AI）

> 注：`script/clean_tmp.py` 是供**引用方项目**远程加载使用的通用清理工具（见通用规范 `specs/core/execution.adoc`「临时产物」），虽存放在本仓库 `script/` 下，但**不属于** Agent 项目自身规范，随通用规范一起被引用方使用。
