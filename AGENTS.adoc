= Agent 项目自身规范（本仓库维护专用，不在公共入口的登记项里）

== 两类内容与隔离（先读，防混淆）

本仓库托管两套**相互隔离**的规范，动手前须先判定**这次动的是哪一类**（本仓库最易出错之处）：

* **公共内容**（`AGENTS_COMMON.adoc` + `specs/`）：面向**任意语言、任意项目**，是**默认引用面**——被引用方项目按入口加载（入口恒为 `AGENTS_COMMON.adoc`）。**公共内容必须自足**（只能引用入口与 `specs/` 下的文件，不得引用引用方看不到的私有落点）；改动须遵守 L1/L2/L3 分级与最高关注项（见 `specs-project-maintainer/priority.adoc`）。
* **维护方自查层**（`specs-project-maintainer/` 下的 `priority.adoc`、`spec-lifecycle.adoc`、`verify.adoc`、`context.adoc` + 本文件）：只对**维护这套规范集合（或同类"共享资产集合"）的项目**成立——规范集合自身的维护（分类准入与定级口径、自身重构）、最高关注项的不可降级清单、维护方的验证义务、公共内容被加载时的可控性清单。它**不在公共入口的登记项里**：普通引用方项目无需也不应引入。
* **Agent 项目自身工具**（`script/` + `.github/workflows/` + `README.adoc`/`PROMPTS.adoc`/`prompts/`/`INSTALL.adoc`/`CHANGELOG.adoc`）：只服务**本仓库**（检查脚本、CI、使用文档），**不分发**。

判定口径与要点：

* **按"对谁成立"归类**：规则对"任意项目"成立 → 公共内容（写进 `specs/`）；只对"维护规范集合这类项目"成立 → `specs-project-maintainer/`；描述"本仓库的校验/CI/工具如何做" → 本文件与 `script/`。
* **入口识别**：通用规范入口恒为 `AGENTS_COMMON.adoc`；本文件（根目录 `AGENTS.adoc`）会被平台**自动识别为本仓库的 agent 规范**，故本文件不能改名为 `AGENTS_COMMON.adoc`，两者以文件名区分（`AGENTS_COMMON.adoc` 之命名即为其避开平台识别）。
* **加载范围**：本仓库内维护规范集合时，**须同时遵循**公共内容、维护方自查层与本文件；普通引用方项目中**只加载** `AGENTS_COMMON.adoc`（含 `specs/`）。
* **落点约束**：只对**引用方项目**成立的规则（如 `git mv` 铁律）只能靠"规范文本 + 引用方自检"生效，**不得**写成机械校验。

== 规范管理（Agent 项目自身）

=== 规范准入与定级（分类、准入、重构的落点）

* **分类、分层与准入**：一条规则属公共规范还是项目规范、属哪一层、是否该收进集合（准入九问），以及用户提新增规范时的提案校验见 `specs-project-maintainer/spec-lifecycle.adoc`。
* **定级与级别维护**：新增/调整条目须按该文件「如何给一条规范定级」的四问定级，并按「归类举证」在提交说明中留痕（对象/依据/条款类型/定级结论）——不得按关键词或"感觉重要"写死 L1；级别调整不得静默。
* **准入与定级判定必须留痕**：新增/调整规范条目时，须能逐项回答准入九问；不得以"用户要求"为由跳过判定直接收录。

=== 规范分层

规范只收录通用规则；局部决策/已知取舍写在对应代码注释。规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层存储在 `specs/` 下（对任意项目成立）；**只对维护规范集合的项目成立**的维护类规范另存于 `specs-project-maintainer/`；分层定义与加载调度见 `AGENTS_COMMON.adoc`「分类与懒加载」。

=== 规范组织

* **校验范围（元规范）**：机械校验**只针对本仓库自己维护的对象**——公共内容（清单见 `PUBLIC.adoc`）、图书馆、维护方自查层、本仓库文档/模板/工具与 CI 行为；**不得为"引用方项目的工作区形态"设计检查**。**适用于引用方**的铁律（如 `git mv`）以"文本写清、判定标准可执行"为落点，不做机械拦截。
* **规范组织与自身重构**：规范须归纳总结、按主题分组组织，不得零散追加、平铺堆砌；重构按 `specs-project-maintainer/spec-lifecycle.adoc`「规范集合的自身重构」的**固定顺序**执行——**先判归属 → 再判层级 → 再判重复 → 最后压缩表述**（顺序不可颠倒）。**读的形态**按该文件「同一条规则有两种读法」；**是否该拆分**按「一条规范何时该拆分」（三条硬条件同时成立才拆、**默认不拆**）；**重构的验收**按「重构后须核对规范有效性」。
* **依据图书馆（本仓库落点）**：仓库根 `library/` 是本项目的**图书馆**（**不在默认引用面内**：无公共加载项、引用方工作区里也没有），存放规则与决策背后的**逐字可核对依据**；入口 `library/README.adoc` 登记主题。要求：① 依据找不全**如实标"未确证"**；② 馆**不复制规则**；③ **建主题文件与登记主题表是同一动作**；④ **独立成篇判据**见入口；⑤ **何时该写、写什么、怎么反查**见 `library/usage.adoc`；⑥ **馆无体量上限，定位靠常驻层固定地址**（取用侧只有 https、不得把取 commit 当前置）；⑦ **质量与开销类依据独立成篇**；⑧ **名不承担定位**（短词、≤32 字符）。
* **禁止注水与简洁性（元规范，新增与存量一并适用）**：规范集合**不得加入无意义、凑字数的内容**——新增/扩充前先过"是否可删"三问：① 是否与现有条目重复或可归并；② 是否承载可核对的事实/决策/边界/取值；③ 是否只把临时讨论落盘。**未经用户明确要求，不得为"看起来完整"新建规范/文档文件**；**已存在的重复、空壳、过时文档直接删或合并**。简洁**不是删规则**——保证完整的前提下尽可能简洁准确；规范会被加载进 AI 上下文，**篇幅越大越易挤爆、限制过严会挤掉合理裁量**，故只约束必须统一的点。
* **常驻层只放底线 + 单个文件软阈值（本仓库落点）**：**单个规范文件另有约 30 KB 的软阈值、只提醒不阻断**（见 `specs-project-maintainer/spec-lifecycle.adoc`「单个规范文件的软阈值」）。必加载层（`AGENTS_COMMON.adoc` + `specs/core/`）每次会话都无条件加载，**只放**① L1 底线、② 最高关注项、③ 必加载层的引用落点；**预算按无条件加载者的合计量核**；**方法论、依据论证、示例、元规范、维护类规范一律移出**。
* **文档质量与冗余（本仓库落点）**：文档按 `specs/general/doc.adoc`「注释与文档」执行；**多模块项目**须建模块间依赖视图（本仓库单模块、不建）。
* **规范引用文件必须真实存在**：所引 `specs/...` 地址须**当前真实存在、可追溯**；不得引用已删除/不存在的旧文件，也不得加指向旧文件的历史来源注记（悬空引用）。
* **新增规范文件必须同步登记**：公共内容的文件由加载调度器（`AGENTS_COMMON.adoc`）唯一登记；维护方自查层的文件由**本文件**登记——"写文件"与"登记"是同一个动作，禁止只建文件不登记。
* **模板代码块必须逐字保留**：`INSTALL.adoc` 等文档中作为"安装/生成模板"的代码块，内容（含换行与空行）必须逐字原样保留；写入目标项目时不得合并、折叠、删除或重排任何一行。

=== 版本与变更记录（本仓库落点）

* **统一变更日志**：本仓库的对外变更集中记录于根目录 `CHANGELOG.adoc`（**时间倒序、最新在上**），**不分散在各文档**；条目只记影响、不记过程。
* **适用范围（与规范变更的边界）**：该文件记录本仓库**自身**的变更；**`specs/` 规范文件的变更不入 changelog、由其 git 历史承载**。
* **登记时机（主动声明才算）**：**除非用户主动声明，否则一律不新增、不修改本文件**——"主动声明"指用户本次明确要求新增、修改、整理或压缩 changelog（或改写其组织方式/条目形态）；**其余一切情形按"未声明"处理**：未提到该文件、**只要求更新文档或 README**、只说"改动了什么"，均**不得**新增条目、改写既有条目、重排或压缩既有内容（含**顺手补一条**）。由 `check_changelog_timing_guard` 钉住。
* **版本线**：本仓库无对外版本号载体，故版本线集中记录在 changelog 条目中。
* **更新粒度与提交压合**：文档与脚本在**尚未提交之前**的调整按 `specs/core/execution.adoc`「文档与代码对应同步」的『未提交前的更改归并』处理；"压缩提交"按 `specs/platform/cnb.adoc`「压缩提交」执行。

=== 环境标志与专用口径（本仓库落点）

* 环境专用口径写进提示词片段 `env-guard`（标志 + 专用口径 + 未命中时的中性口径）。标志取值登记在此（本仓库私有、公共内容不引用）：NPC 唤起评论 = `CNB_EVENT` 非空（该环境已复制好仓库、`main` 为默认分支，看流水线见 `.cnb.yml` 的 `include:`）。**运行环境须与项目声明一致**：本仓库的校验脚本一律按项目声明的运行时执行（由运行环境防线钉住）。

=== 规范调整

* **依据优先引用业界标准**：新增/调整规范条目时须按 `specs/general/source.adoc`「外部引用」执行——**优先**为该条标注广泛、高知名度、高可靠性的业界标准/论文出处；**出处只写标准名/编号、不附链接**（唯一已知偏离是图书馆）；**不得为凑数堆砌不相关标准**。对照标准时须守住**完整性、同义性**；仅当本规范对某标准**有明确的自身取舍/更严要求**时，才显式覆盖并写明理由。
* **提示词方向（主侧重）与优先级**：公共任务提示词属本仓库自身内容，但其**侧重点是最核心、方向性的内容**。故调整提示词时：**主侧重**与**优先级（L1/L2/L3）**须显式保留、不得降级，登记表（`PROMPTS.adoc`）与各提示词正文的侧重须一致且互不相同；**取值路径也须与实际一致**（装配过的＝IDE 预览/渲染器/站点页面内；未装配的＝远程**原始文件地址**/本地读取，直出仓库字节、指令仍在），故不得留"渲染视图下已展开"这类与路径绑不上的说法（由 `check_prompt_delivery_surface_guard` 钉住）。
* **每次改完规范必做自检与来源核对**：改动规范/文档后，除完整性校验外，还须按 `specs/general/self-check.adoc`「完成前自检」逐项核对**用户原始要求是否逐条落实、有无遗漏/越界**；并按 `specs/general/source.adoc`「内部引用」核对**本次新增的每条引用都指向真实存在的文件与节名**。**改完规范的动作清单以 `specs/general/verify.adoc`「改完规范必做的五件事（机械手段必跑，干净子 agent 复核不可漏）」为准**——① **机械手段**必跑全、② 干净子 agent 的三视角复核不可漏、③ 三视角一次读取分栏、④ 三态台账、⑤ 子 agent 不可用时降级留证，本条不重复其正文。
* **规范调整**：除非明确要求删除某条规范，调整时必须保证规范完整性。「完整性校验」与「定义未执行核验」相互独立、触发条件不同：
** **完整性校验（每次改完规范后必做）**：核对本次调整未丢失规则、无误删/误改/遗漏。① 自动运行 `script/check_specs.py`（及测试 `script/check_specs_test.py`）做机械校验——须**全量扫描**（跨文件交叉敏感、本地毫秒级），**不得**改为"只查有变更的文件"；② 对内容实质性调整，在隔离上下文开启干净 subagent 做语义复核——**三视角（①完整性 + ②有效性与认知质量 + ③接纳面）一并回答、都过才算完成**，且**三视角合用一个子 agent**（一次读取、结论分栏）；概念项只到**未发现问题**、查不出标**悬置**，**不得当作阻断交付的条件**（完整口径见 `specs/general/verify.adoc`「验证总纲」「规范验证」「验证的效力等级」「**验证的适用边界**」，本仓库自己的落点见 `specs-project-maintainer/verify.adoc`）。**验证对象不止规范文件**：`prompts/`、随规范分发的工具同样按三视角核对。**同 Agent 复核的前提只在平台层写明时才成立**。校验不因"用户未要求/改动小"跳过（用户明确豁免除外）。
** **定义未执行核验（单独手动执行）**：评估"规范里定义的每条规则是否真正有效、有无可执行抓手"，而非仅存在于文档——这类风险不会随每次调整暴露，故不自动运行；由用户决定何时整体执行（如 `script/check_effective.py`），并可指定核验范围。
* **校验报红不得留红**：报红须**就地修复**，不得以『不在本次任务范围』放过。
* **调整对象判定（本仓库特有）**：**只有本仓库能调整公共规范**——引用方改不了公共规范，其"调整规范"只指项目自身规范；本仓库提示"调整规范"时**默认改本项目自身规范（根 `AGENTS.adoc`）**，**仅当用户主动声明"是公共规范"时**才动公共规范。

== Agent 项目自身工具声明

以下工具属于 **Agent 项目自身**（维护本规范集合用），不属于公共规范、不随 `specs/` 分发：

* `script/check_specs.py` — 规范完整性机械校验（引用存在、链接格式、**节名引用存在**、技术栈一致、**调度器登记完整**、私有约定、历史来源、INSTALL 模板、**文档注水**、要点等 + 优先级 + 规范准入/自检/来源/测试命名/换行符防线 + 提示词防线 + **自身侧 git mv 自查** + **常驻层体积上限 + 单个文件软阈值** + **规范验证与生命周期/接纳面** + **CI/CD 与平台协作、清单逐项与文档-脚本一致性防线** + **NPC 禁合并与范围边界/合并关系/交付形态** + **配置类不写逻辑、先例优先、Feign 命名带前缀、请求响应类复用与路径中划线、持久化访问、构造不手写、类型指代** + **图书馆防线** + **默认引用面与变更日志（声明优先）/引文段落/依赖视图** + **抽象与接入成本** + **开发流程** + **重命名与内容修改分两个提交** + **防线核对对象是判据本体而非轴名** + **运行环境防线** + **执行吞吐 + 性能测试** + **包源与镜像源防线** + **提交信息与 HTTP 接口语义防线** + **代码质量/生成效率与 token 纪律/改动后复核三道 + 精炼性（同一描述只写一处）** + 跨环境脚本（含批处理栈）+ **脚本文档（自述文档与文档头）** + **评论不得删除** + **规范抓取** + **入口文档持久化 + 安装幂等更新（用户手工编辑不自动改回）** + **防线清单与删除记账** + AsciiDoc 语法）；**校验范围含 `specs/` 与 `specs-project-maintainer/`**。配套测试 `script/check_specs_test.py` 按防线分组钉住。
* `script/check_effective.py` — "定义未执行"深度核验工具；配套测试 `script/check_effective_test.py`。
* `specs-project-maintainer/context.adoc` — 维护方自查：**公共内容被加载时的可控性**（运行契约三维、接纳面须留证）。
* `.github/workflows/check-specs.yml` — 本仓库 CI：在 push/PR 上运行上述校验及配套测试（**只做确定性校验**；语义审查交人 review，不在 CI 中调用外部 AI）。
