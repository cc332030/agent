= 代码质量与生成开销的依据

本文件是依据图书馆的主题之一，承载两类依据：**①代码质量的判据从哪来**（坏味道清单、命名与函数可读性、资源与并发缺陷）与**②生成效率 / token 纪律的材料与取舍**（上下文预算、渐进披露，以及本集合自己的利用率口径）。规则本体落在 link:../specs/general/coding.adoc[]「代码质量（新产出即高质）」、link:../specs/general/context.adoc[]「生成效率（同等质量下最少往返）」「token 纪律（提高利用率与节省开销）」与 link:../specs/general/review.adoc[]「改动后的 review」，本文件不复制规则。

== 当初要解决的失效（本项目实证）

* **"功能写出来了、代码质量比较低"**：用户报告的真实情形——AI 交付的改动功能可用，但同一件事的写法**质量差一个量级**：重复代码、超长函数、嵌套过深、命名靠缩写与数字后缀、吞异常、资源不释放、共享状态没有同步策略、循环里查库。根因是**此前的规范只覆盖形式类要求**（命名约定、工具类优先、格式化等），**"新产出即高质"的整体下限没有成文判据**——执行者按"能跑就行"收敛。
* **"生成效率与 token 怎么用"**：用户同时提出"提高生成效率的规范""不影响功能完整性和代码质量的前提下提高 token 利用率"，并追问**"提高 token 利用率和节省 token 是一回事吗"**。此前的规范只有「执行吞吐」管**调用形态**（该合并的别拆开），不管**做事的安排**（一次做完、延后验证、不靠重试撞对），也**没有 token 维度的判据**，更没有把两者的关系写清——执行者容易把"省 token"理解成"少读少说"，从而**牺牲完整性、质量与验证**（用户明确的前提是：**会影响效率和效果就不加**）。

== 外部材料与逐字依据（业界事实标准与标准编号）

* **ISO/IEC 25010（ISO/IEC 25010:2011 起的产品质量模型）**：把**可维护性（maintainability：模块化、可复用性、可分析性、可修改性、可测试性）**、**可靠性**、**性能效率**与功能适用性并列为**产品质量特性**——"功能写出来了"只满足其中之一，故"功能能跑即完成"不合规。
* **ISO/IEC/IEEE 12207（软件生命周期过程）**：实现过程包含"验证实现满足设计要求"，**评审（review）是常规工程活动**，不必等到专项评审阶段——支撑「改动后的 review」这条（每次改动都在同一轮内复核）。
* **Martin Fowler《Refactoring: Improving the Design of Existing Code》（代码坏味道清单）**：坏味道清单（重复代码 Duplicated Code、过长函数 Long Function、过长参数列表 Long Parameter List、发散式变化 Divergent Change、霰弹式修改 Shotgun Surgery、依恋情结 Feature Envy、数据泥团 Data Clumps、基本类型偏执 Primitive Obsession、被拒绝的遗赠 Refused Bequest 等）与"小步重构"的做法——支撑「新代码不得引入坏味道」的逐条判据。**未逐字取回**：书名与坏味道条目名为公开通行的业界事实标准（要点转述，非逐字摘录）。
* **Robert C. Martin《Clean Code》**：命名表意、函数只做一件事、函数体线性可读、注释是不得已的手段——支撑「职责单一、结构清晰」「命名表意、不用缩写」「可读性优先」。**未逐字取回**（要点转述）。
* **SEI CERT Coding Standards（安全编码标准）**：资源管理（成对释放、确定性释放）与并发缺陷（可见性、锁顺序、双重检查）的分类与实例——支撑「无资源泄漏」「无并发隐患」。**官方网页已取回**（题名与条目分类已核对，未逐字摘录）。
* **ISO/IEC/IEEE 29148（需求与判定须可验证）** 与 **ISO/IEC Directives Part 2（要求须可验证、规范性文件引用现行文件）**——支撑"每条判据都要有判定标准"与"引用依据不复述原文"。
* **Anthropic 工程博客《Effective context engineering for AI agents》**（业界实践，**非标准**）：上下文是**有限资源**（注意力预算），token 越多召回与长程推理越差（context rot），故应只加载高信号内容——支撑「按需读取、不全量预读」「少复述、多引用」。
* **Agent Skills 开放规范**（业界约定，**非标准**）：progressive disclosure（渐进披露）——按需加载、不做全量预载；支撑「约束放在外部、不进上下文」的形态选择。
* **现场量级实证**见 link:throughput.adoc[]（同一仓库的一次任务：180 次模型请求 / 175 万输入 token / 1659 s，模型生成仅 580 s——**约 65% 的墙钟花在轮次之间**，输入 ÷ 产出约 56 : 1）。本主题不复制该数据，只指出它是"为什么把轮次与 token 当成本来管"的本项目实证。

== 同义性差异与覆盖点（本集合自己承认的）

* **"先提高利用率、再谈节省"是本站取舍，不是外部要求**：外部材料讲"注意力预算与渐进披露"（**为什么**上下文越长越差），**未**给出"利用率 / 节省"的区分，也**未**规定"提高利用率优先于节省总量"。本条属本集合按用户前提（"会影响效率和效果就不加"）做的判据化取舍——**先把没被用上的输入砍掉，再考虑总量**。
* **"十项逐条自检"是本集合的判据化取舍**：ISO/IEC 25010 只给质量特性的**定义与方向**，不规定"交付前须逐项自检十项"；坏味道清单属**业界共识而非标准**（Fowler 自述是经验清单）。
* **"不设必须量化 token 的要求"是本站取舍**：ISO/IEC/IEEE 25010 要求性能效率**可度量**，但本集合把度量对象落在**可核对的行为判据**（"每一份读入的内容须能说出用在了哪里"）上，而**不**要求执行者统计 token 数——量化本身会引入新的开销与不可核对的口径。
* **"轮次"与"生成效率"的分工**：公共 link:../specs/general/context.adoc[]「执行吞吐」管**调用形态**（互相无依赖的调用须一次批量发出），「生成效率」管**工作安排**（一次做完、延后验证、不靠重试撞对）——两者**不重复**：前者判"这一批调用有没有拆开"，后者判"这件事该做几轮"。
* **本条严于常规做法的两处**：①**"失败一次就查根因"**——工程上"重试"是常见手段，本集合把它限定为"不得用重试替代根因分析"（只约束**同一问题上的重复执行**，不禁止网络超时一类真正的不确定性重试）；②**"改动后的 review 每次必做"**——IEEE 1028 只要求"评审发生"，本集合把它加严为"**每次都做**、不分改动大小"（依据是本仓库的返工成本实证）。
* **本主题不做"代码质量评分"**：不引入任何复杂度/可维护性指标的阈值（圈复杂度数值等）——阈值依赖语言与团队，写死会变成误伤（属"条条框框过多挤掉合理裁量"，见项目规范入口的注水判据）。
