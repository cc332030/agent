= 外部标准原文摘录（依据图书馆）

本文件是依据图书馆的主题之一：**外部标准的逐字原文**——规范正文里每条"依据（标准名/编号）"背后的**原始表述**。

== 使用与核对

* **怎么用**：规范正文或项目决策引用了某标准时，在本文件按标准名查原文，确认"这条标准确实支持这条规则"（`specs/general/verify.adoc`「规范验证」②要求核对"引用的标准**确实支持该条**"，不得只验证依据行还在）；原文也是**举一反三**的入口。
* **怎么核对**：正文数字编号、字面词、声称类条目附的原文片段都是**逐字摘录**，可追溯到所标来源；本仓库由机械校验核对其中关键片段仍在（见 `specs/general/verify.adoc`「规范验证」）。摘录是**节选**（标注"摘"），不替代标准原文。
* **校对边界（怎么判断"逐字"是否可信）**：每条依据都带**取样来源标记**，可据此复核——①标"**官方文本已取回**"者（RFC 系列、SemVer、Maven 插件文档、SemVer/git 官方文档等），是用命令实际取回官方文本后比对，**可复取**：例如 `curl -s https://www.rfc-editor.org/rfc/rfc2119.txt` 即得到该文件引文所在原文；②标"**官方网页已取回**"者（IEEE/ISO 的题名页），是同法取回题名后比对（**仅题名与版本号**可逐字核对）；③标"**未逐字取回**"者（编写时该官方页返回的是 JS 壳、正文不可取），已**如实标注且不引用其字句**，只保留静态可查的题名/版本/状态。
* **复核的动作（可执行）**：抽查任一条——先看它的取样来源标记，命中 ①/② 时按上述方式取回官方文本比对引文；命中 ③ 时核对"是否确实没有引用字句"（若引用了字句却没标可复取来源，即为不合格）。

* 正式题名（IEEE 标准**摘要页**官方网页已取回）：Software Reviews and Audits。

== RFC 2119 / RFC 8174（要求级别的用语）

* **RFC 2119**（BCP 14）：Key words for use in RFCs to Indicate Requirement Levels。官方文本已取回，两处逐字摘：
  ** 用语清单："The key words `"MUST"`, `"MUST NOT"`, `"REQUIRED"`, `"SHALL"`, `"SHALL NOT"`, `"SHOULD"`, `"SHOULD NOT"`, `"RECOMMENDED"`, `"MAY"`, and `"OPTIONAL"`"（原文用双引号包裹各词）。
  ** 强度语义："1. MUST   This word, or the terms `"REQUIRED"` or `"SHALL"`, mean that the definition is an absolute requirement of the specification."、"2. MUST NOT   This phrase, or the phrase `"SHALL NOT"`, mean that the definition is an absolute prohibition of the specification."（另注："Note that the force of these words is modified by the requirement level of the document in which they are used."）
* **RFC 8174**（BCP 14 的澄清，2017-05）：Ambiguity of Uppercase vs Lowercase in RFC 2119 Key Words。官方文本已取回，逐字摘（第 2 节 NEW 文本）："In many IETF documents, several words, **when they are in all capitals as shown below**, are used to signify the requirements in the specification."（要点：**只有全大写且本身是规范用语时**才具约束力）。
* 用途：`specs/core/execution.adoc`「分级与最高关注项」（L1/L2/L3 的用语归并）、「与条款类型一一对应」、`prompts/_common.txt` 的 `priority-rules`。

== 配置类只做数据持有（POJO）——Spring Boot / Google Java Style / Spring 注解

* 材料：**Spring Boot 官方文档**「Externalized Configuration」（`@ConfigurationProperties` 的定位：把外部配置**绑定**到类型安全的对象上）、**Spring Framework 官方文档**「Java-based Container Configuration」（`@Configuration`/`@Bean` 的定位：**声明** Bean 的定义与装配方式，由容器负责实例化与调用）；**Google Java Style Guide 3.4.2（Class member ordering）**对 POJO 的说明——"A POJO **only** has behavior that **acts on its own fields**"，即数据持有者的行为仅限对自身字段的读写，不含计算与对外访问；《阿里巴巴 Java 开发手册》对 POJO 类（DO/DTO/VO 等）的约定——"POJO **类的属性**不要设定任何**属性默认值**"、"POJO 类**必须写 toString** 方法"等**只针对属性与访问器**的条款。
* 依据要点（**说明：此条为"官方文档定位与风格指南表述"的要点转述、非逐字摘录**，如日后需逐字比对，以 Spring Boot / Spring Framework 参考文档的 Externalized Configuration、Java-based Container Configuration 两节与 Google Java Style Guide 3.4.2 的原文为对照面）：配置类在**框架设计上本就被定义为配置项的数据持有者**——绑定由容器完成，逻辑**不在**它的职责内；这与"纯数据类不写逻辑"是同一条约定的两个用例。
* **须注意的语义差异（同义性）**：上述材料给出的是**职责定位与风格建议**，**未**规定"配置类中任何逻辑一律禁止"；本集合据此推出的是**本项目自身的硬性约定**——**任何情况都不允许，无例外**（`specs/general/coding.adoc`「类设计」"配置类不写逻辑"，`L1`）；**不得**把本节读成"Spring 文档禁止在配置类里写逻辑"。
* 实证反例（**本项目真实记载**）：配置类里做取值兜底/条件判断/派生值拼装时，配置项的**实际行为分散在配置类中**（看不见、测不到），与配置类应承担的"声明配置项"职责混淆；本项目为此在用户明确要求下把该条写成**无例外**并配机械防线（`check_config_class_guard`）。

== 抽象与接入成本（易用性 / 约定优于配置 / 显式装配）

* 材料：**ISO/IEC 25010**（本文件上节；易用性 usability 与可维护性 maintainability 属**产品质量特性**，与功能适用性 functional suitability **并列**）；**ISO 9241-110**（本文件上节；人机交互原则，通用名称含**可控性、符合预期**）；**The Twelve-Factor App**（本文件上节；逐字要素名 **Config**、**Dependencies**）；**Spring Boot 官方文档**「Externalized Configuration」与「Auto-configuration」（`@ConfigurationProperties` 把外部配置**绑定**到类型安全对象、自动配置在**缺少接入方定义时**生效，即**默认即用、配置只用于覆盖**）；**Convention over Configuration**（惯例优于配置，通用业界表述）；**SOLID 的依赖倒置原则（DIP）**与**好莱坞法则（Don't call us, we'll call you）**（使用方面向抽象、由容器反向注入）。
* 依据要点（**说明：此条为"官方文档定位与业界方法论"的要点转述、非逐字摘录**，如日后需逐字比对，以 Spring Boot 参考文档的 Externalized Configuration、Auto-configuration 两节与 The Twelve-Factor App 的 Config/Dependencies 两节原文为对照面）：**可替换点由装配侧一处声明、由容器反向注入**是通行做法；框架侧做法是**给默认实现**（缺接入方定义时才生效）与**约定优于配置**（不写也能跑，写则覆盖）。故"接入方要为每个使用点各提供一遍同一实现/配置"属抽象漏做（同一事实多个来源），而非接入方的问题。
* **须注意的语义差异（同义性）**：上述材料给的是**质量特性归类、原则与方法论**，**未**规定"某类型在接入方只能出现一次"或"必须提供默认实现"；本集合据此推出的是**本项目自身的取舍与更严要求**——`specs/general/coding.adoc`「抽象与接入成本」的 L1 两条（**唯一装配点**、**可替换点须有可用默认或显式必填声明**），其中"唯一"与"必须"是本集合的判据化取值（对照 ISO/IEC/IEEE 29148 的"需求单一、无歧义、可验证"与单一真源要求，见本文件 ISO/IEC/IEEE 29148 节）；**不得**把本节读成"ISO/IEC 25010 要求零配置接入"。
* 实证反例（**本项目真实记载**，来源按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注为"未逐字取回官方原文、来自用户报告与项目对话记录"）：用户报告的功能设计失效形态——"**要求都实现了、功能都实现了，却很难用**"：某抽象定义了 `ISession` 接口，但每个 service 使用点都要业务项目**各自提供一遍 `ISession` 实现类型**（N 个使用点 = N 次重复接入；新增使用点还要再传一遍），导致能力虽在、接入成本随使用点线性增长。该形态即本条 L1「唯一装配点」要防的对象（判定特征与之一一对应）。

== 变更审批与"合并主体"（DORA / GitHub Docs）

* 材料：**DORA**（DevOps Research and Assessment，Accelerate State of DevOps 报告系列）关于交付性能的研究结论——**变更审批（change approval）/代码评审**的**质量**与交付性能相关，而**把审批做成形式化的把关**并不提升性能；以及 **GitHub Docs** 关于**受保护分支（protected branches）与 required pull request reviews** 的官方说明：合入受保护分支的变更**须经独立于改动提出者的评审通过**，且**提交者不得自行绕过**所配置的评审要求。
* 依据要点（**说明：此条为"业界权威实践的公开陈述"，引文为要点转述、非逐字摘录**，如日后需逐字比对，以 DORA 报告原文与 GitHub Docs 的 protected branches / required reviews 页面为对照面）：**让改动方自己去合入、或让同一自动化执行者既改又合**，等于取消独立评审这一环；**"谁提的改动谁负责任地提出、合入由独立的一方（人）确认"**是通行做法。
* **须注意的语义差异（同义性）**：DORA 的结论指向"**审批要有实质、不要形式化**"，本**未**声称"某一类执行者绝对不得合并"；本集合据此推出的是一条**本项目自身的组织约定**——**CNB 平台上的 NPC/CI 执行者一律不得合并**（`specs/platform/cnb.adoc`「合并请求的合并主体（NPC 禁合并）」），其**根因**是：CI 环境是一次性、无合规责任主体的自动执行者，**授权给"同一个自动执行者"不构成独立评审**；**不得**把本节读成"标准规定 AI 不得合并"。
* 实证反例（**本项目真实记载**）：本项目曾发生"由 **AI（CNB NPC/CI 环境中的执行者）实际执行了合并**"的实例——起因是发起人在对话中直接授权；该实例正是本条要防的失效形态：**授权被当成豁免、自动化执行者替人承担了不可逆且合规相关的动作**（本条也因此把"因用户要求/授权故本次合并"单列为判定标准②）。

=== MADR 模板（官方文本已取回，逐字）

Markdown Architectural Decision Records（adr/madr v4.0.0）**最小模板**的章节序列**逐字**如下（官方仓库 `template/adr-template-minimal.md` 已取回）：

[listing]
----
# {short title, representative of solved problem and found solution}

## Context and Problem Statement
## Considered Options
## Decision Outcome
### Consequences
----

要点（据上列**逐字章节名**可判）：一份决策记载 = **问题/背景** + **考虑过的选项** + **选了什么及理由** + **后果**；"为什么选它、放弃了什么"是模板的必备结构，不是可选修饰。

=== "好的记载"的判据（业界资料汇总，官方文本已取回、逐字）

joelparkerhenderson/architecture-decision-record（业界广泛引用的 ADR 资料汇总）「Suggestions for writing good ADRs」逐字三条：

* "Specific: Each ADR should be about one AD, not multiple ADs."
* "Immutable: Don't alter existing information in an ADR. Instead, amend the ADR by adding new information, or supersede the ADR by creating a new ADR."
* "Rationale: Explain the reasons for doing the particular AD. This can include the context (see below), pros and cons of various potential choices, feature comparisons, cost/benefit discussions, and more."

同页「Decision sharing (optional)」另有一句**逐字**："Many ADs recur across projects."，其后接（要点转述）"因而，过往决策的经验无论好坏，都是**在采用明确的知识管理策略时**才成为有价值的可复用资产"。

**它支撑什么**：①"一份记载只讲一个决策、必须写明理由与取舍"→ link:usage.adoc[]「一、什么时候该把依据写进图书馆（触发特征）」把"有取舍或争议的决策"列为入馆触发特征，且要求收**比较与理由**而非只写结论；②"决策一旦定下不改写、变更用新增/取代"→ 本集合的对应做法是**变更由 git 历史承载**（`specs/`）与**统一变更日志只追加**（link:../specs/general/changelog.adoc[]）；③"过往决策**在明确的知识管理策略下**才成为可复用资产"→ 本集合的"明确策略"即 link:usage.adoc[] 的写入判据与反查算法（**光有零散记录不构成依据库**）。
