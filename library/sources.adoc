= 外部标准原文摘录（依据图书馆）

本文件是依据图书馆的主题之一：**外部标准的逐字原文**——规范正文里每条"依据（标准名/编号）"背后的**原始表述**。

== 使用与核对

* **怎么用**：规范正文或项目决策引用了某标准时，在本文件按标准名查原文，确认"这条标准确实支持这条规则"（`specs/general/verify.adoc`「规范验证」②要求核对"引用的标准**确实支持该条**"，不得只验证依据行还在）；原文也是**举一反三**的入口。
* **怎么核对**：正文数字编号、字面词、声称类条目附的原文片段都是**逐字摘录**，可追溯到所标来源；本仓库由机械校验核对其中关键片段仍在。摘录是**节选**（标注"摘"），不替代标准原文。
* **校对边界（怎么判断"逐字"是否可信）**：每条依据都带**取样来源标记**，可据此复核——① 标"**官方文本已取回**"者（RFC 系列、SemVer、Maven 插件文档、git 官方文档等），是用命令实际取回官方文本后比对，**可复取**：例如 `curl -s https://www.rfc-editor.org/rfc/rfc2119.txt` 即得到该文件引文所在原文；② 标"**官方网页已取回**"者（IEEE/ISO 的题名页），是同法取回题名后比对（**仅题名与版本号**可逐字核对）；③ 标"**未逐字取回**"者（编写时该官方页返回的是 JS 壳、正文不可取），已**如实标注且不引用其字句**，只保留静态可查的题名/版本/状态。
* **复核的动作（可执行）**：抽查任一条——先看它的取样来源标记，命中 ①/② 时按上述方式取回官方文本比对引文；命中 ③ 时核对"是否确实没有引用字句"（若引用了字句却没标可复取来源，即为不合格）。

== 变更日志的形态（Keep a Changelog 1.1.0 / Conventional Commits 1.0.0 / Conventional Changelog）

**官方文本已全部取回**——**注意这是业界约定（convention）而非 ISO/IEC 标准**：Keep a Changelog 自述 **"Is there a standard changelog format? Not really."**（"没有真正的标准格式"），故本条**只作依据、不作强制面**。

* **Keep a Changelog 1.1.0 —— 逐字（Guiding Principles）**："Changelogs are for humans, not machines."、"There should be an entry for every single version."、"The same types of changes should be grouped."、"Versions and sections should be linkable."、"The latest version comes first."、"The release date of each version is displayed."、"Mention whether you follow Semantic Versioning."
* **Keep a Changelog 1.1.0 —— 逐字（Types of changes）**："Added for new features."、"Changed for changes in existing functionality."、"Deprecated for soon-to-be removed features."、"Removed for now removed features."、"Fixed for any bug fixes."、"Security in case of vulnerabilities."
* **Keep a Changelog 1.1.0 —— 逐字（Bad Practices 两段）**："Using commit log diffs as changelogs is a bad idea: they're full of noise."；以及 **Inconsistent Changes** 段："A changelog which only mentions some of the changes can be as dangerous as not having a changelog."、"By inconsistently applying changes, your users may mistakenly think that the changelog is the single source of truth. It ought to be."（**"它本该是"**——这句是本集合把"内容不减少"写成条目的依据）。
* **Keep a Changelog 1.1.0 —— 逐字（FAQ，两处）**："Should you ever rewrite a changelog? Sure. There are always good reasons to improve a changelog."（**重写日志是正当动作**，本集合据此允许"按组织方式重组、但不改事实"）；"It's difficult, because people follow wildly different formats and file names."（**机器解析困难**——故本集合的"机械抓手"只钉形态与要素）。
* **Conventional Changelog（preset）—— 逐字（分组与类型映射）**：`constants.js` 里 `group_by` 默认 `"Type"`、`sort_by` 默认 `"Title"`（**该默认是组内再排序、不涉及版本之间**），类型表 `DEFAULT_COMMIT_TYPES` 逐条形如 `{ type: 'feat', section: 'Features', effect: 'bump' }`、`{ type: 'fix', section: 'Bug Fixes', ... }`、`{ type: 'perf', section: 'Performance Improvements', ... }`，并对 `docs`/`style`/`chore`/`refactor`/`test`/`build`/`ci` 标 `effect: 'hidden'`。
* **Conventional Changelog（preset）—— 逐字（破坏性变更的两处落点）**：`templates.ts` 的 `BREAKING_CHANGE_KEYWORDS = ['BREAKING CHANGE', 'BREAKING-CHANGE']`、`BREAKING_CHANGES_TITLE = 'BREAKING CHANGES'`，且 `formatNoteIcon` 对破坏性变更分组返回图标 `'⚠'`；`commitPartial`/`note` 渲染把 `scope` 与 `subject` 分列（`**{{scope}}:** {{subject}}`）。**这就是"表格形态的判据"里『变更点与影响分列』以及『破坏性变更逐条成组』的出处。**
* **Conventional Commits 1.0.0 —— 逐字（摘要与规范条款）**："<type>[optional scope]: <description>"、"The commit message should be structured as follows: <type>[optional scope]: <description> [optional body] [optional footer(s)]"、**逐字（Specification 一节）**："Commits **MUST** be prefixed with a type, which consists of a noun, `feat`, `fix`, etc., followed by the OPTIONAL scope, OPTIONAL `!`, and REQUIRED terminal colon and space."、"The type `feat` MUST be used when a commit adds a new feature to your application or library."、"The type `fix` MUST be used when a commit represents a bug fix for your application."；"feat: a commit of the type feat introduces a new feature to the codebase (this correlates with MINOR in Semantic Versioning)."、"fix: a commit of the type fix patches a bug in your codebase (this correlates with PATCH in Semantic Versioning)."、"BREAKING CHANGE: a commit that has a footer BREAKING CHANGE:, or appends a ! after the type/scope, introduces a breaking API change (correlating with MAJOR in Semantic Versioning)."、"A BREAKING CHANGE can be part of commits of any type."（**破坏性变更可以与任何类型组合**——本集合据此写明"不得把某个类型默认为破坏性的"）。
* **它支撑什么**：`specs/general/git.adoc`「提交信息」（`<type>[(scope)]: <subject>` 首行形态、破坏性变更用 `!` 或 `BREAKING CHANGE:` 页脚、正文写"为什么"与边界——**这是"上游"那一半**）；`specs/general/changelog.adoc`「组织形态」（按版本分组、组内按类型分组、**排序方向恒为时间倒序**、类型闭集、空分组不写）与「表格形态的判据」（分组列按对象、类型列、变更点与影响分列、破坏性变更逐行标注、与 `scope→subject→正文` 的同构）；`specs/general/doc-design.adoc`「版本与变更记录」。
* **须注意的同义性差异与抽样状态（L1，逐条如实标注）**：

== Maven 命令行与并行构建（`-T` / `--threads`、`.mvn/maven.config`）

* 材料：Apache Maven 官方文档——命令行参考（`mvn` 选项表）与《Configuring Apache Maven》（用户/项目级配置）。
* **`-T` / `--threads` 逐字摘**（官方网页已取回，选项表原文）："`-T,--threads Thread count, for instance 4 (int) or 2C/2.5C (int/float) where C is core multiplied`"——**未**规定"默认应为多少"（不给默认值的做法即"默认单线程、不写 `-T` 就没有并行"），也**不区分**"模块间 / 模块内"两层并行（该语义由选项名 Thread count 与其它官方材料的用法界定，本文件按"不替它加结论"处理）。**另：该选项在官方页面里就是一条普通命令行选项**——选项表只给"怎么在命令行上写"，**没有**给"它可以由环境变量携带"的任何路径；**实测的逐字形态**（以下两段为官方页面逐字字节，`<a>` 锚点一并保留）：无空格形态 "`-<a name='T'>T</a>,--<a name='threads'>threads</a>`"（Maven 3.9.9 / 3.9.16 实测），带空格形态 "`-<a name='T'>T</a>, --<a name='threads'>threads</a>`"（Maven 4.0.0-beta-3 ~ 4.0.0-rc-2 实测）——两种形态的**选项说明文字逐字相同**（见上）；该差异是**格式差异、不影响 `-T` 的取值方式**。
* **`.mvn/maven.config` 逐字摘**（官方网页已取回）："It's really hard to define a general set of options for calling the maven command line."、"defining `.mvn/maven.config` file which contains the configuration options for the mvn command line."、"The `.mvn/maven.config` is located in the project's top level `.mvn` directory and also works in the root of a multi module build."；官方给出的例子逐字为 "`-T3 -U --fail-at-end`"，并写明它换来的效果是 "So you only have to call Maven by using `mvn clean package` instead of `mvn -T3 -U --fail-at-end clean package` and not to miss the `-T3 -U --fail-at-end` options on every call."。另（同为官方原文）："Starting with Maven 3.9.0, each single argument must be put on a new line, and lines beginning with `#` are treated as comments."、"Maven 3.8.x and older do not support comments in this file."；官方示例文件逐字为（每行一个参数）："`-T3`"、一行注释、"`-U`"、"`--fail-at-end`"。**该页另给环境变量路径的两条口径**（同为官方原文）："`MAVEN_OPTS` environment variable: This variable contains parameters used to start up the JVM running Maven and can be used to supply additional options to it. E.g. JVM memory settings can be defined with the value `-Xms256m -Xmx512m`."、"`MAVEN_ARGS` environment variable: Starting with Maven 3.9.0, this variable contains arguments passed to Maven before CLI arguments."（**即：`MAVEN_OPTS` 的官方口径是 JVM 启动参数、不要往里放 CLI 参数；`MAVEN_ARGS` 自 3.9.0 起才被读取，更早版本不读**——参数放进去在本集合的语境里等于"看着加了、命令形态无从核对"）。
* 用途：`specs/stack/maven.adoc`「构建并行度」——"配置过即以配置为准"（`.mvn/maven.config` 为项目级落点）、"取值按**当前构建设备的核心数**补齐（命令形态 `mvn -T <核心数>`，**不写怎么取核数**）"、**"取值以命令行参数形态显式传（不得用 `MAVEN_OPTS` 一类环境变量载体）"**与**"命令行再传一次 `-T` 即覆盖（总会覆盖项目配置）"**；也支撑该项目实证：官方把 `-T3` 作为**项目级配置文件**的典型内容，故并行度本就该落在项目配置里而不是每次命令行手打。**规格说明（用户会据此反驳）**：本条的取值口径写"按当前设备核心数"、命令形态**只到 `mvn -T <核心数>`**，**不写 `1C`、也不写"怎么取核数"**——官方把 `C` 定义为 core **multiplied**（`2C` = 2 × 核心数、`0.5C` = 半核心数，字面上是"核心数的倍数"），故 `--threads 1C` **只有在 `C` 恰好等于"可用 CPU 核心数"时才等于"当前设备核心数"**，这是一条**取决于具体实现的假设**，本集合不据此把 `1C` 当成权威取值写法；要与核心数一比一等值，就用**明确的数值**（`-T <核数>`），`*(int/float)*` 字样支持该写法。**"核心数怎么得到"是执行动作、不进规范**（判据本体见 `specs-project-maintainer/spec-lifecycle.adoc`「以对象定义规则、不给具体操作」）。**如实标注**：官方选项表原文只给 `4 (int) or 2C/2.5C (int/float) where C is core multiplied`，**未**给 `C` 与"核心数"等价关系的明文，故"按当前设备核心数取值"是本集合的判据化取值、出处只能标到"本项目实证"。
* **须注意的语义差异（同义性）**：官方文档**只给机制与取值写法**，**未**规定"默认要不要开、没配过时该不该由执行者补一个默认"；也**未**说明"并行会不会让单个模块内的插件/测试并发执行"（官方在 Surefire 侧另有一节讲 fork，见下段）。故"默认启用 + 以配置为准 + 只到模块粒度"是**本集合的判据化取舍**，出处只能标到"本项目实证"，**不得**标成 Maven 官方要求。**"取值必须写在命令行上（不得改用环境变量载体）"与"命令行再传一次 `-T` 即覆盖项目配置"这两条同为本站的判据化取舍**——官方文档给的**是** `.mvn/maven.config` 里可放命令行选项（例子就是 `-T3`，故"配置里已写过 `-T`"这一事实可逐字核对）；**但**官方**未**给"项目配置与命令行同时存在时谁生效"的明文、**也**未说"环境变量能不能携带 `-T`"，故这两条只到"取值以命令行参数形态显式传、且传了就是覆盖"这一层，**不得**标成官方要求、也不得以"命令行总会生效"去反推官方语义。
* **本项目实证（当初要解决的失效；`-T 1C` 是当时报告方人手命令里的写法，不是本条推荐的取值写法）**：同一仓库里，"以 `mvn -T 1C` 构建"与"以无参 `mvn` 构建"**两条路径并存**——并行度只写在人手的命令行里，没有落到项目配置，于是自动化的无参 `mvn` 调用**继承了默认单线程**、多核机器上跑成单线程（用户报告）。结论落在用户口径：**默认就该启用**（"默认会自己启用可以不管"）。

== Maven Surefire 插件的默认值（`forkCount` / `reuseForks` / `parallel`）

* 材料：Apache Maven Surefire 插件官方文档（`surefire:test` 目标参数表）。
* 官方页标注：`surefire:test` **Full name `org.apache.maven.plugins:maven-surefire-plugin:3.6.0:test`**（官方网页已取回，题名与版本号可逐字核对）。
* **逐字摘（官方文档已取回，参数表原文）**：`<forkCount>`——"Option to specify the number of VMs to fork in parallel in order to execute the tests."、"When terminated with `C`, the number part is multiplied with the number of CPU cores."、"Example values: `1.5C`, `4`"、"Default : 1"、"Since : 2.14"；`<reuseForks>`——"Indicates if forked VMs can be reused. If set to `false`, a new VM is forked for each test class to be executed."、"Since : 2.13"、"Default : true"；`<parallel>`——"**By default, Surefire does not execute tests in parallel**"、"You can set the parameter `parallel` to `none` to explicitly disable parallel execution"；`<threadCount>`——"Only makes sense to use in conjunction with the `parallel` parameter"。

* **须注意的差异（如实标注，不替官方下结论）**：官方文档对 **`reuseForks` 与 Surefire 大版本的关系**有两种口径并存——参数表里该参数标 "Since 2.13 / Default : true"，而 3.x 的**迁移说明**（本仓库**未逐字取回**该页，故不引其字句）宣称 3.0.0 起默认改为 `false`。两者**以插件实际版本的文档为准**；本集合据此不下"默认是哪个"的结论，而是要求**该取值显式写进配置**（无论默认如何都不受影响）。**同理**，`reuseForks=false`（每个测试类 fork 一个新 VM）在被**并行执行**时会成倍放大进程与 JVM 启动开销（JVM 启动成本是微基准方法学里公认的大头，见本文件 JMH 段），而**顺序执行**时它等同于"更慢、更隔离"——**"慢"是开销问题、"隔离"是正确性问题，两者不能互相折算**：本集合不据此断言"`reuseForks=true` 更优"，只要求"要依赖哪个取值就显式写出来"。

== Microsoft Learn（Windows 命令参考）

* 材料：Microsoft Learn 上 Windows 命令（`cmd.exe`）的官方参考。
* 依据要点：命令解释器**按字节读取行尾、不做行尾归一化**（LF-only 批处理会直接执行失败：`goto`/标签匹配、`if`/`for` 复合语句、行尾注释与续行都可能失效）；批处理按**系统 ANSI 代码页**解析（简体中文 Windows 为 GBK/CP936）——**带 BOM 的 UTF-8** 会把 BOM 并入首行指令，**含非 ASCII 字符的 UTF-8** 会被按该代码页解析成乱码，故这两类会出现解析/显示异常，而**纯 ASCII 内容与代码页无关**。

* **须注意的语义差异（同义性）**：上述条目只说明 `cmd.exe` **怎么解析与执行**，**未**规定「`.bat` 里不得混写 PowerShell 语法」「未定义变量必须当错误」「每个 `.bat` 只做一件事」；这些是本集合的判据化取舍（写在 `specs/stack/batch.adoc`，按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注）。

== 类成员与注解排序（Google Java Style 3.4.2 原文 + 本集合取舍）

* 材料：**Google Java Style Guide 3.4.2「Ordering of class contents」**（Google 官方，官方文本已取回：`curl -s https://raw.githubusercontent.com/google/styleguide/gh-pages/javaguide.html`，可复取）；《阿里巴巴 Java 开发手册》（作为"下限"，据其现有引用面）。
* **逐字摘录（3.4.2 节，官方文本已取回）**："The order you choose for the members and initializers of your class can have a great effect on learnability. However, **there's no single correct recipe for how to do it**; different classes may order their contents in different ways. What is important is that each class uses **some logical order**, which its maintainer could explain if asked. For example, new methods are not just habitually added to the end of the class, as that would yield 'chronological by date added' ordering, which is not a logical ordering."
* **须注意的语义差异（同义性）**：该节**只要求"存在某种逻辑次序、且维护者能解释"**，**明确否认存在唯一正确配方**，并**点名禁止**一种形态——"new methods are not just habitually added to the end of the class"（新方法不得习惯性追加到类末尾，那属"按加入日期排序"）；但**未**规定成员落点该按什么次序（**未**规定"新增的可插在前面或中间"、**未**规定"重载须相邻"、**未**规定"数据转换方法跟在查询方法之后"），**也未**规定"静态字段在最前"、"实体类按表列序"、"注解按名长排"、"数据库注解排最下"。《阿里巴巴 Java 开发手册》中亦**未**见此数项明文。
* **本集合的取舍（如实标注）**：`specs/general/coding.adoc`「命名与代码质量」的「静态字段排在类最前」「实体类字段按数据库顺序」「注解/装饰器排序（重要性优先——数据库/持久化映射注解排在最下；同重要性再按名长升序）」「成员与方法次序（成员落点按流程次序，字段/方法**新增**时可插前面或中间、重载相邻、数据转换方法跟在查询接口之后，且只对新增成员生效）」四条是**本集合在 Google 上述"须为逻辑次序"下限之上自定的更严取值**，**不是**某标准的明文规定，理由是"整类共享状态集中可见""与表结构逐列对照""数据库关注点收尾扫读"；按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**。Java 落点见 `specs/stack/java.adoc`「编码」。

== 跨语言执行脚本（SQL / Lua 写资源文件，不写字符串拼接）

* **材料与用途（支持 `specs/general/coding.adoc`「跨语言执行脚本的落点」，技术栈落点 `specs/stack/java.adoc`「跨语言执行脚本」）**：
** **OWASP**「SQL Injection Prevention Cheat Sheet」与「Query Parameterization Cheat Sheet」（表名逐字；**官方页面已取回、要点转述**）：SQL 注入的**主防线是参数化查询（prepared statements）**——语句**先被固定为语句**、参数经**绑定**传入，从而**不把输入当作 SQL 文本解析**；反例形态正是"用字符串拼接/格式化把值拼进语句文本"。本集合据此把 SQL 写成**独立文件**（语句本体不在宿主语言字符串里）、由预编译语句绑定参数。
** **MyBatis 官方文档**「Dynamic SQL」：映射文件（`*.xml`）用 `#{}` 生成**预编译参数**（`?`）、用 `${}` 做**字符串替换**；官方明确 `${}` 不防注入。这为"SQL 的合法承载形式是框架支持的 `.xml` 文件"给出**框架侧依据**；本集合据此把 MyBatis 项目列为已知例外（SQL 写 `.xml`），并要求 `${}` 仅用于不由用户输入决定的场景 + 白名单校验。
** **Redis 官方文档**「EVAL」（URL **https://redis.io/docs/latest/commands/eval/**，条目名为逐字；**官方页面已取回、要点转述**）与「Redis Lua API reference」：`EVAL` 以**脚本文本**作为参数执行（`EVAL script numkeys key [key ...] [arg ...]` 形态），官方推荐用 `SCRIPT LOAD` + `EVALSHA` 加载与复用；客户端相应地按 `RedisScript` **从资源加载 `.lua` 文件**。本集合据此要求 Lua 写成 `.lua` 资源文件、按资源加载执行，不内联成宿主语言字符串。
** **MySQL 官方文档**（多值 `INSERT` 的语法形态；**本次未逐字取回、按通行转述标注**）：`INSERT INTO tbl (col, ...) VALUES (...), (...)`——一条语句可插入多行。这为**"同表同类 DML 优先合并"**给出**语法侧依据**；但合并**不是纯等价**（锁的范围与持有时间不同）——故 `specs/general/sql.adoc`「SQL 写法」把它定为**只约束执行者新写的、用户主动写的不动也不告警**。
** **ANSI SQL / ISO/IEC 9075**（限定名称）：`schema.table`（库名写在表名前的限定名称）是 SQL 语法的**一等形态**，不写库名时表名由**当前 schema（默认库）**补齐。这为**"写 SQL 须带库名"**给出**语法侧依据**（语句自身可自足）；**但标准给的是"可写全、也可靠默认 schema"，并未规定"必须写全"**——"DDL/DML 一律强制带库名"是**本集合自己的取舍**（依据 ISO/IEC 25010 可靠性：脚本复用到别的连接时不改错库）。
** **MySQL 官方文档**（`ALTER TABLE` 语法与 Online DDL 章节；条目名为逐字、**官方页面未逐字取回，本次按通行转述标注**）：`ALTER TABLE` 的语法形态是 `ALTER TABLE tbl_name [alter_option [, alter_option] ...]`——**一条语句可并列多个 alter_option**；Online DDL 一节写明确下"each `ADD COLUMN` or `DROP COLUMN` … executed as a separate operation **by default**"，即**可用 INPLACE 的动作默认仍作为一次独立操作执行**。本集合据此要求**同表同类操作合并进一条 ALTER**（`specs/general/sql.adoc`「SQL 写法」）。
** **Hibernate 官方文档**（HQL/JPQL 章节，URL **https://hibernate.org/orm/documentation/**）：查询语句以**独立字符串/命名查询（`@NamedQuery` 等）**承载，官方同样把语句与参数分离。本集合**不**把"命名查询里的字符串"当合规落点，只把它作为"语句应与参数分离"的旁证。
* 依据要点（**要点转述，非逐字摘录**）：① **注入与误用的根因是"把值/语句拼成一段文本"**，参数化与"语句独立于代码"是通行防线；② **各技术栈都支持把脚本作为资源/文件承载并加载执行**，故"必须独立成文件"在这些栈上**有可落点**。
* **加载时机（性能敏感路径不每次读）的依据要点**：Redis 官方文档「EVAL」明确 `EVAL` 以**脚本文本**为参数把脚本正文送到服务端执行，并推荐 `SCRIPT LOAD` + `EVALSHA` **按 sha 复用已加载脚本**；JDBC/MyBatis 侧则是"语句一次准备、多次绑定执行"（`PreparedStatement` 的复用语义）。**本集合据此推出的取值是"按性能敏感度定性"**。**须如实标注**："资源读取次数""必须缓存"**均无标准明文要求**——官方材料给的是机制与推荐做法，"按性能敏感度定性 + 发布后不变即缓存"是**本集合自己的判据化取舍**（依据 ISO/IEC 25010 的性能效率特性）。
* **须注意的语义差异（同义性）**：上述材料给的是**注入防护与参数化**的要求，**未**规定"脚本必须放在资源文件夹""扩展名必须是被调语言的扩展名"；**MySQL 官方文档给的是语法能力（可并列 alter_option、多值 `INSERT`）与代价说明（每动作默认各自执行，合并后锁行为不同），并未规定"同表同类操作必须合并"**；**ISO/IEC 9075 给的是限定名称可写、完全不写源库名时靠当前 schema 补齐，并未规定"库名必须写"**——"ALTER 须合并、不得每个字段一条"、"DML 优先合并且只管执行者新写的"、"DDL/DML 库名强制"均是**本集合据此推出的判据化取舍（用户点名）**（依据 ISO/IEC 25010 性能效率与可靠性）；**后缀为 `.sql` / `.lua` 本身也不是某标准的明文要求**（本集合未找到支持"扩展名必须如此"的标准原文，按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注**未确证**）。
* 实证反例（**本项目真实记载**）：待执行的另一语言的脚本以**字符串拼接/字符串模板**内联在宿主语言代码里——编辑时既**没有高亮**也**没有错误校验**，"容易出错"是用户给出的直接动因。

== 跨环境脚本（一份逻辑 + 薄入口；实现语言取舍）

* **材料与用途（支持 `specs/general/script.adoc`「跨环境脚本」）**：
** **POSIX**：标准名与它支撑的语义见本馆「POSIX」主题（本处不重复），只补一个边界——**这些语义只对 POSIX 系统成立**、`cmd.exe` 与 PowerShell **不遵守**这一点，为"**同一段 shell 逻辑无法在两侧行为一致地复用**"给出**规范侧依据**。
** **Microsoft Learn（Windows 命令参考）**：`.bat`/`.cmd` 按字节读行尾、按系统 ANSI 代码页解析——故批处理**只能 CRLF 落盘、指令用纯 ASCII**。这为"入口文件必须按各自平台规范分别落盘"给出**官方文档依据**。
** **PEP 8 / PEP 20 / PEP 257** 与 **Node.js / Deno / Bun 官方文档**（跨平台运行时，标准库含命令行参数、文件系统、JSON、HTTP；均可直接运行单文件脚本）：为"**Python 3 与 Node.js 并列为首选逻辑层语言**"给出**运行时能力侧依据**。
** **Go / Rust 官方文档**（`go build` / `cargo build` 可产出**无运行时依赖的单文件可执行产物**、支持交叉编译）：为"需要单文件分发时取编译型语言"给出**工具链侧依据**。

== HTTP 接口路径的命名风格（RFC 3986 / Google API 设计指南）

* **材料与用途（支持 `specs/stack/spring.adoc`「分层与职责」的「HTTP 接口路径优先用中划线」（L1））**：
** **RFC 3986**（Uniform Resource Identifier (URI): Generic Syntax）：URI 的**通用语法成分**与**字符分类**——路径由 `pchar` 组成，`-`、`_`、`~` 等属 **unreserved** 字符；`scheme` 与 `host` **大小写不敏感**，而**路径部分大小写敏感**。
** **Google API 设计指南**（官方页面公开）：REST 资源名与路径用**小写连字符（kebab-case）分隔的词**，不用下划线或驼峰。
* 依据要点（**要点转述**）：**路径片段的大小写与 `_`/`-` 之差都不构成语义差**（`-` 与 `_` 同属 unreserved，见 RFC 3986 第 2.3 节），只构成拼写与可读性风险；故本条约束的是**一致性与可读性**，不是协议兼容性。
* **版本关系（L1，引用现行版本）**：RFC 3986 **未被废止**，但已由 **RFC 8820**（*URI Design and Ownership*，**BCP 190**，2020-06，**Updates 3986**）更新——该文件的要点是"URI 的子结构由 scheme 决定，发布独立标准去强制 URI 子结构的特定形态通常是问题做法"。**用途是纠偏读者印象**：不得把 RFC 3986 读成"支持规定 URI/路径必须长什么样"——**"HTTP 路径优先用中划线"是本集合自己的风格取舍**（依据原文可取：`curl -s https://www.rfc-editor.org/rfc/rfc8820.txt`）。
* **须注意的语义差异（同义性）**：上述材料给的是**URI 语法事实与公开的风格约定**，**未**规定必须用中划线、也未禁止下划线；本集合据此推出的是**自己更严的判据化取舍**。**落点只在技术栈层**（`specs/stack/spring.adoc`）：「HTTP 路径」只在 Web 框架语境下有定义，通用层不写具体协议/框架专名。
* 实证反例（**本项目真实记载**）：用户观察到同一项目里内部调用接口的路径**下划线与驼峰混用**，要求「**feign 接口地址优先使用中划线**」。

== HTTP 接口语义与错误响应（RFC 9110 / RFC 9457）

* **材料与用途（支持 `specs/general/coding.adoc`「HTTP 接口语义」的四条）**：**RFC 9110**（*HTTP Semantics*，**STD 97**，2022-06）与 **RFC 9457**（*Problem Details for HTTP APIs*，Standards Track，2023-07，**Obsoletes RFC 7807**）——**两份官方文本均已取回**。
* **逐字（RFC 9110，9.2.1 Safe Methods）**："Request methods are considered "safe" if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource."；"Of the request methods defined by this specification, the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe."；同节的反例与要求："it is common for Web-based content editing software to use actions within query parameters, such as "page?do=delete". If the purpose of such a resource is to perform an unsafe action, then the resource owner **MUST** disable or disallow that action when it is accessed using a safe request method. Failure to do so will result in unfortunate side effects when automated processes perform a GET on every URI reference for the sake of link maintenance, pre-fetching, building a search index, etc."
* **逐字（RFC 9110，9.2.2 Idempotent Methods）**："A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent."；"A client **SHOULD NOT** automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied."
* **逐字（RFC 9110，15 Status Codes）**："The status code of a response is a three-digit integer code that describes the result of the request and the semantics of the response, including whether the request was successful and what content is enclosed (if any)."；五类首位的语义（"1xx (Informational)"…"5xx (Server Error)"）。
* **逐字（RFC 9457，Abstract 与 3.1 成员）**："This document defines a "problem detail" to carry machine-readable details of errors in HTTP response content to avoid the need to define new error response formats for HTTP APIs."；成员 `type`（"a JSON string containing a URI reference"）、`status`（"a JSON number indicating the HTTP status code"，且 "Generators **MUST** use the same status code in the actual HTTP response"）、`title`、`detail`、`instance`；媒体类型 **`application/problem+json`**。
* **它支撑什么**：`specs/general/coding.adoc`「HTTP 接口语义」的四条——安全方法不得产生状态变更（L1）、幂等语义与重试对齐（L2）、状态码按语义使用（L2）、对外错误响应统一结构（L3，可选）。
* **须注意的同义性差异（L1，逐条如实标注）**：
** **标准给的是协议语义，不是"项目必须怎么写"**：RFC 9110 规定的是方法与状态码的**协议语义**，**未**规定项目不许把错误包成 `200`、**未**规定客户端必须用哪种方法——"不得用 `200` 包错误""非幂等请求不得配自动重试"是**本集合按语义推出的判据化取值**。
** **"安全方法不得产生状态变更"这一条**：标准在此处的要求是**资源所有者须在安全方法被访问时禁用该动作**（`MUST disable or disallow`）——与本条同义，属**同一要求的两种写法**。
** **Problem Details 是可选项**：RFC 9457 只定义了一种错误响应**格式**，**未**要求 API 必须采用；本集合据此把它定为 **L3（可选）**。
** **与 `specs/general/security.adoc`「敏感信息」的关系**：RFC 9457 的 `detail` 成员原文是 "ought to focus on helping the client correct the problem, rather than giving debugging information"——与安全条的"不得暴露堆栈/SQL/内部路径"**同向**，两条各自成立、互不替代。
* **本项目实证（用户要求）**：用户在要求"找一找业界知名的公共规范/标准，对比本项目公共规范、取长补短"后确定补入本节——补的两个缺口是**提交信息无规则**与**HTTP 方法/状态码语义未覆盖**。

* **材料与用途（支持 `specs/general/coding.adoc`「警告与弃用」的「不得使用被弃用的类/API，改用替代者」与 `specs/general/dependency.adoc`「升级与废弃」的「弃用类/API 的迁移默认不动依赖面」）**：**Java 官方 API 文档 / `@Deprecated` 注解规范**（被标注弃用的成员「不应再被使用」，且官方在 `@deprecated` 标签与文档中给出**替代者**；**本次未逐字取回**，按公开 API 文档与注解规范定位）；**Semantic Versioning 2.0.0**（弃用属**次版本**内的兼容扩展——新形态以次版本引入、旧形态保留至某个大版本移除，故"用新形态"不必然要求升大版本；**本次未逐字取回**）；**ISO/IEC 25010**（可维护性：同一能力并存旧新两条路径即两条真源）、**ISO/IEC/IEEE 29148**（判定须单一、可验证）。
* 依据要点（**要点转述**）：① 弃用是**给使用者的迁移信号**——被弃用成员本不该再进新代码，官方通常会指出**替代者**；② 弃用的替代者**常在同一依赖版本内**已可用（次版本内引入新 API、旧 API 保留），故迁移**不必**改依赖版本；③ 是否升级依赖是**另一件事**（须读变更说明、评估破坏性变更、跑全量验证）。
* **须注意的语义差异（同义性，L1）**：官方材料只给出「某成员已弃用、有替代者」，**未**规定「必须迁移」，也**未**规定「迁移的范围不得波及依赖面」；「新代码不得使用被弃用者、替代者**优先取升级类/同名新类**，且**默认不调整依赖、也不动依赖版本**」是**本集合自己的判据化取舍**（逐条论证见 `library/adoption.adoc`「同义性差异与覆盖点」）。**不得**把本条读成 JDK 或 SemVer 的要求。
* 实证反例（**本项目真实记录**）：用户原文口径为「调整规范：不用被弃用的类，使用其他类代替（升级类/同名新类最好），默认不调整依赖，也不动依赖版本」。

== 依据的定位与取值（git / RFC 9110）

=== 为什么这里收的是"机制"而不是"某产品的接口"

依据图书馆可以很大，故"引用方怎么在不全量下载的前提下定位到具体文件"本身需要依据——但它依据的是**通用的、稳定的机制**（Git 的内容寻址、HTTP 的分段取值），**不是本站站点某一页的接口**（页面会改版、接口不是标准）。故本节收机制原文与**实测取样状态**，**不收产品接口**（`specs/general/source.adoc`「不臆造行为」）。

=== git（内容寻址与按 blob 取回；官方文本已取回）

* **官方材料**：git 的官方文档（`git-rev-parse`、`git-cat-file`、`git-grep`、`git-clone`；**官方文本已取回**）。
* **逐字（`git-cat-file` 官方文档，Description 首句）**："In its first form, the command provides the content or the type of an object in the repository."
* **逐字（`git-rev-parse` 官方文档，Specifying Revisions 一节）**："`<rev>:<path>`, e.g. `HEAD:README`, `master:./README`"；同处逐字："A suffix `:` followed by a path names the **blob or tree** at the given path in the tree-ish object named by the part before the colon."（即 `<commit>:<path>` 命名的是**该路径处的内容对象**，不是路径本身）。
* **它支撑什么**：`library/README.adoc`「依据的定位协议」把"可靠性"落在**内容可校验**上（**内容主键是终态**，路径与 commit 都只是到达它的写法）、把 commit 降为**可选加固**。
* **本项目实证（可复取）**：`git rev-parse <commit>:<path>` 在同一内容处于不同路径时给出**同一个 blob sha**；文件改名/搬迁后**旧 blob 仍可 `git cat-file` 取回原文**。

=== HTTP 分段取值（RFC 9110；官方文本已取回）

* **标准名**：RFC 9110，*HTTP Semantics*（STD 97，Standards Track，2022-06；**官方文本已取回**）。**版本关系（L1，引用现行版本）**：RFC 9110 **Obsoletes** RFC 2818、7230、7231、**7232**、**7233**、7235、7538、7615、7694 与 7230 的一部分，故**分段取值不再引用 RFC 7233**（它在 2022 年已被取代）。
* **逐字（14.2 节 Range 首句）**："The "Range" header field on a GET request modifies the method semantics to request transfer of only one or more subranges of the selected representation data (Section 8.1), rather than the entire selected representation."；**逐字（14.2 节）**："A server MAY ignore the "Range" header field. However, origin servers and intermediate caches ought to support byte ranges when possible…"；**逐字（15.3.7 节首句）**："The 206 (Partial Content) status code indicates that the server is successfully fulfilling a range request for the target resource by transferring one or more parts of the selected representation."
* **它支撑什么**：`library/README.adoc` 的「分段取值」一段与 `library/usage.adoc`「四、引用方怎么准确定位依据」把"只取一段"写成**标准动作**（`Range` → `206`），依据即此（**当前不可用**，状态见下）。
* **须注意的同义性（L1）**：RFC 9110 规定的是**协议侧的规则**，且明写服务端 `MAY ignore` 该请求头、**未**规定任何托管服务必须支持 Range。故本站**如实标注**：本仓库站点**未实测**到 Range 生效，文中**不得**把"支持 Range"当成既定事实或对引用方的要求。

=== 取样方式（可复取，供日后复核）

* **git（官方文本）**：`git help rev-parse` / `git help cat-file` / `git help clone`，或 git 官方文档站点对应页（注意网页源码里引文所在行会**折行**，逐字比对时先归一化空白）。
* **RFC 9110（官方文本）**：`curl -s https://www.rfc-editor.org/rfc/rfc9110.txt`（引文逐字比对；`Range` 与 `206` 分别在 14.2 与 15.3.7 节）。
* **本项目实证（git 行为，实测、可复现）**：① 在一个临时仓库里两次提交同一文件的不同内容，`git rev-parse HEAD:f.txt` 前后给出**不同 blob sha**；② 旧 blob sha 在后续提交之后仍能 `git cat-file -p <旧 sha>` 取回**旧内容**；③ 对本站远程仓库 `git clone --filter=blob:none --no-checkout` 的克隆体积极小，`git ls-tree HEAD library/` 列出各主题文件的 **blob sha**，`git cat-file -p <blob>` 可按需取回**单个文件**内容。
* **本项目实证（Range，实测）**：对本站站点与平台原始文件视图**两处**发 `Range: bytes=0-99`，**均**返回 `200` 与**整份**内容（未见 `206`；两份内容字节一致，`md5` 相同）——故 `library/README.adoc` 与 `library/usage.adoc` 均**如实写明"当前未实测到 Range 生效"**，取值以整份文件为准。
* **本项目实证（取用侧的取值路径，实测）**：① **站点直链** → `200`、`text/plain`、**纯文本**（`md5` 与**站点发布分支的同名文件逐字节一致**，即取到的是**未经处理器装配的仓库字节**——站点对非 HTML 文件直出原文），即**取用侧只需 https，不需要 git**；② **平台原始文件视图按分支名** → `200`、`text/plain`（分支名、`HEAD`、短/长 commit sha 均可用，不存在的 ref → `404`）；③ **git 客户端**：`git ls-remote <仓库> refs/heads/main` 可取到当前 commit（**这条只有具备 git 的一方走得到**，构成"取用侧与作者侧条件不同"的实证）；④ **"页面里找入口"不成立**：站点首页不暴露 commit、也不书写分支名，仓库页面里嵌的 commit sha **属渲染产物**（改版即变）——故入口**不得**靠解析页面结构取得，**只能**是常驻层里的**固定地址**。
