= 外部标准原文摘录（依据图书馆）

本文件是依据图书馆的主题之一：**外部标准的逐字原文**——规范正文里每条"依据（标准名/编号）"背后的**原始表述**。

== 使用与核对

* **怎么用**：规范正文或项目决策引用了某标准时，在本文件按标准名查原文，确认"这条标准确实支持这条规则"（`specs/general/verify.adoc`「规范验证」②要求核对"引用的标准**确实支持该条**"，不得只验证依据行还在）；原文也是**举一反三**的入口。
* **怎么核对**：正文数字编号、字面词、声称类条目附的原文片段都是**逐字摘录**，可追溯到所标来源；本仓库由机械校验核对其中关键片段仍在（见 `specs/general/verify.adoc`「规范验证」）。摘录是**节选**（标注"摘"），不替代标准原文。
* **校对边界（怎么判断"逐字"是否可信）**：每条依据都带**取样来源标记**，可据此复核——①标"**官方文本已取回**"者（RFC 系列、SemVer、Maven 插件文档、SemVer/git 官方文档等），是用命令实际取回官方文本后比对，**可复取**：例如 `curl -s https://www.rfc-editor.org/rfc/rfc2119.txt` 即得到该文件引文所在原文；②标"**官方网页已取回**"者（IEEE/ISO 的题名页），是同法取回题名后比对（**仅题名与版本号**可逐字核对）；③标"**未逐字取回**"者（编写时该官方页返回的是 JS 壳、正文不可取），已**如实标注且不引用其字句**，只保留静态可查的题名/版本/状态。
* **复核的动作（可执行）**：抽查任一条——先看它的取样来源标记，命中 ①/② 时按上述方式取回官方文本比对引文；命中 ③ 时核对"是否确实没有引用字句"（若引用了字句却没标可复取来源，即为不合格）。

== RFC 2119 / RFC 8174（要求级别的用语）

* **RFC 2119**（BCP 14）：Key words for use in RFCs to Indicate Requirement Levels。官方文本已取回，两处逐字摘：
  ** 用语清单："The key words `"MUST"`, `"MUST NOT"`, `"REQUIRED"`, `"SHALL"`, `"SHALL NOT"`, `"SHOULD"`, `"SHOULD NOT"`, `"RECOMMENDED"`, `"MAY"`, and `"OPTIONAL"`"（原文用双引号包裹各词）。
  ** 强度语义："1. MUST   This word, or the terms `"REQUIRED"` or `"SHALL"`, mean that the definition is an absolute requirement of the specification."、"2. MUST NOT   This phrase, or the phrase `"SHALL NOT"`, mean that the definition is an absolute prohibition of the specification."（另注："Note that the force of these words is modified by the requirement level of the document in which they are used."）
* **RFC 8174**（BCP 14 的澄清，2017-05）：Ambiguity of Uppercase vs Lowercase in RFC 2119 Key Words。官方文本已取回，逐字摘（第 2 节 NEW 文本）："In many IETF documents, several words, **when they are in all capitals as shown below**, are used to signify the requirements in the specification."（要点：**只有全大写且本身是规范用语时**才具约束力）。

== Microsoft Learn（Windows 命令参考）

== EditorConfig 规范（编辑器配置）

* 材料：EditorConfig 规范（EditorConfig Specification，站点 `spec.editorconfig.org`；**官方文本已取回**，编写时为 0.17.2 版）。
* 依据要点（键名与取值清单取自规范正文）：`.editorconfig` 以"按文件路径匹配的 INI 段"声明编辑器行为，键含 `charset`、`end_of_line`、`insert_final_newline`、`indent_style`/`indent_size` 等；`charset` 的取值只有 `latin1`/`utf-8`/`utf-8-bom`/`utf-16be`/`utf-16le`，`end_of_line` 取 `lf`/`cr`/`crlf`；取值为 `unset` 时**移除该键值对的效果**（即使外层段已设置过，要点转述）。
* 用途：`specs/general/encoding.adoc`「跨平台检出」——仓库根须有 `.editorconfig`（缺失即补齐）、其行尾取值须与 `.gitattributes` 一致、`charset` 默认取 `utf-8`（`.ps1` 需要 BOM 时取 `utf-8-bom`；按格式规范须存为非 UTF-8 的文件用 `unset` 移除外层声明）。
* **须注意的语义差异（同义性）**：该规范只定义"键与取值怎么写、如何生效"，**未**规定项目必须提供 `.editorconfig`、也未规定行尾与编码该怎么取值；"仓库根须有该文件、取值须与 `.gitattributes` 一致"是本集合自己的要求（`specs/general/source.adoc`「外部引用」）。

== 跨语言执行脚本（SQL / Lua 写资源文件，不写字符串拼接）

* **材料与用途（支持 `specs/general/coding.adoc`「跨语言执行脚本的落点（资源文件夹，不写字符串拼接/模板）」，技术栈落点 `specs/stack/java.adoc`「跨语言执行脚本（SQL / Lua 等）」）**：
** **OWASP**「SQL Injection Prevention Cheat Sheet」与「Query Parameterization Cheat Sheet」（表名逐字；**官方页面已取回、要点转述**）：SQL 注入的**主防线是参数化查询（prepared statements）**——语句**先被固定为语句**、参数经**绑定**传入，从而**不把输入当作 SQL 文本解析**；反例形态正是"用字符串拼接/格式化把值拼进语句文本"。本集合据此把 SQL 写成**独立文件**（语句本体不在宿主语言字符串里）、由预编译语句绑定参数——字符串拼接在被禁止之列，正是因为它使"值"与"语句"混在一处、且无法被高亮与错误校验覆盖。
** **MyBatis 官方文档**「Dynamic SQL」：映射文件（`*.xml`）用 `#{}` 生成**预编译参数**（`?`）、用 `${}` 做**字符串替换**；官方明确 `${}` 不防注入。这为"SQL 的合法承载形式是框架支持的 `.xml` 文件（而非 Java 字符串）"给出**框架侧依据**；本集合据此把 MyBatis 项目列为已知例外（SQL 写 `.xml`），并要求 `${}` 仅用于不由用户输入决定的场景 + 白名单校验。
** **Redis 官方文档**「EVAL」（URL **https://redis.io/docs/latest/commands/eval/**，条目名为逐字；**官方页面已取回、要点转述**）与「Redis Lua API reference」（URL **https://redis.io/docs/latest/develop/programmability/lua-api/**）：`EVAL` 以**脚本文本**作为参数执行（`EVAL script numkeys key [key ...] [arg ...]` 形态），官方推荐用 `SCRIPT LOAD` + `EVALSHA` 加载与复用；客户端（如 Spring Data Redis）相应地按 `RedisScript` **从资源加载 `.lua` 文件**。本集合据此要求 Lua 写成 `.lua` 资源文件、按资源加载执行，不内联成宿主语言字符串。
** **Hibernate 官方文档**（HQL/JPQL 章节，URL **https://hibernate.org/orm/documentation/**）：查询语句以**独立字符串/命名查询（`@NamedQuery` 等）**承载，官方同样把语句与参数分离。本集合**不**把"命名查询里的字符串"当合规落点（仍是宿主语言字符串、无高亮与错误校验），只把它作为"语句应与参数分离"的旁证。
* 依据要点（**说明：以上为"官方文档定位"的要点转述，非逐字摘录**，如日后需逐字比对，以 OWASP 的两份 Cheat Sheet、MyBatis 官方文档的 Dynamic SQL 页、Redis 官方文档的 EVAL 与 Lua API 页原文为对照面）：①**注入与误用的根因是"把值/语句拼成一段文本"**，参数化与"语句独立于代码"是通行防线；②**各技术栈都支持把脚本作为资源/文件承载并加载执行**（MyBatis 的映射文件、Redis 客户端的脚本资源、JDBC 预编译语句），故"必须独立成文件"在这些栈上**有可落点**、不构成空中楼阁。
* **加载时机（性能敏感路径不每次读）的依据要点**：上述材料给出的是**脚本执行与脚本复用**的机制面——Redis 官方文档「EVAL」明确 `EVAL` 以**脚本文本**为参数把脚本正文送到服务端执行，并推荐 `SCRIPT LOAD` + `EVALSHA` **按 sha 复用已加载脚本**（避免反复传送正文）；JDBC/MyBatis 侧则是"语句一次准备、多次绑定执行"（`PreparedStatement` 的复用语义）。**本集合据此推出的取值是"按性能敏感度定性"**：classpath 资源**打进产物后发布即不变**，故**性能敏感路径**（高频、争分夺秒，典型是 Redis 操作）**第一次使用时读取一次并缓存**、不在每次调用时重复读取（Redis 侧等价的复用手段是 `EVALSHA`/`SCRIPT LOAD`）；**不敏感路径**（启动装配、一次性任务、低频操作）每次读取无妨；**需求要求内容会变**的（如每次渲染前可编辑的 HTML 模板）**不适用缓存**、按是否需重读决定。**须如实标注**："资源读取次数""必须缓存"**均无标准明文要求**——官方材料给的是机制与推荐做法（`EVALSHA` 复用），"按性能敏感度定性 + 发布后不变即缓存"是**本集合自己的判据化取舍**（性能效率维度的取舍，依据 `ISO/IEC 25010` 的性能效率特性），**不得**把本节读成"某标准规定资源必须缓存"。
* **须注意的语义差异（同义性）**：上述材料给的是**注入防护与参数化**的要求，**未**规定"脚本必须放在资源文件夹""扩展名必须是被调语言的扩展名"；**后缀为 `.sql` / `.lua` 本身也不是某标准的明文要求**（本集合未找到支持"扩展名必须如此"的标准原文，按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注**未确证**）。本集合据此推出的是**自己更严的判据化取舍**：跨语言脚本**独立成文件放资源文件夹、扩展名取被调语言自身的扩展名**（取用编辑器/工具链的高亮、补全与错误校验，理由与实证见 link:adoption.adoc[] 同主题条）；**不得**把本节读成"某标准规定 SQL 必须存成 `.sql` 文件"。同理，**不得**把本节读成"某标准规定资源必须缓存/必须只读一次"（缓存与否是本集合按性能敏感度定性的取舍，见上一段的加载时机要点）。
* 实证反例（**本项目真实记载**，来自用户报告与项目对话记录）：待执行的另一语言的脚本以**字符串拼接/字符串模板**内联在宿主语言代码里——编辑时既**没有高亮**也**没有错误校验**（语法错、字段名错、参数个数不匹配都到运行期才暴露），"容易出错"是用户给出的直接动因；用户要求"**所有语言**当有跨语言执行脚本时优先把脚本放资源文件夹，扩展名取**目标语言的扩展名**或该技术支持的文件形式（如 MyBatis 的 XML 能处理 SQL），lua 通过读取文件使用、其他文件也一样"。用户**追加**的第二条要求（同一次对话）：**按不同场景考虑是否性能敏感**——"redis 操作是争分夺秒，不能每次都去读"；**进了 classpath 的资源发布成功后不会变，第一次使用时读取然后缓存即可**，**除非需求要求内容会变**（举例：需要转成 PDF 的 HTML 模板）。

== Feign 接口命名带所属域前缀（Spring Cloud 与《阿里巴巴 Java 开发手册》）

* 材料：**阿里巴巴 Java 开发手册**【命名】章的「方法名/接口名命名规则」（要点转述：接口名与方法名用能望文生义的词、避免歧义与同义混用）；**Spring Cloud OpenFeign 官方文档**对声明式 HTTP 客户端接口的定位（接口定义就是调用契约，接口名直接出现在注入点）；以及**微服务同域多服务的命名实践**（同一领域（如用户中心域）有多个服务各自对外提供类同能力时，同名接口会碰名）。
* 依据要点（**说明：此条为“官方文档定位与风格指南表述”的要点转述、非逐字摘录**，并且本仓库**未逐字取回《阿里巴巴 Java 开发手册》、Spring Cloud OpenFeign 正式文档与典型微服务仓库的原文**，故本条不引用任何加引号的字句，只给出归纳后的要点；如日后需逐字比对，以上三方的原文为对照面）：Feign 接口名是**调用方与检索者最先看到的标识**（需注入、需按名搜索），故命名要能承载“**这个接口属于哪个域/项目**”这一信息；同域多服务各自对外提供类同能力时，无前缀的同名 Feign 接口会碰名（只能靠包名区分）。适用面**只取 Feign 接口这一类**（用户明确限定“目前只需要考虑 feign，不需要考虑其他对外接口”），其余对外接口的命名不在此列。
* **须注意的语义差异（同义性）**：上述材料给的是**命名的下限与理由**（望文生义、避歧义），**未**规定“方法名/接口名必须加所属域前缀”，也**未**规定前缀取词方式；“**前缀 = 域/项目名取词首字母组合**（`user-center` → `Uc`、`open-user-center` → `Ouc`）与“**先例优先**”是本集合据此给出的**自身取舍**（`specs/general/coding.adoc`「命名与代码质量」的「Feign 接口命名带所属域/项目前缀」，`L1`；**另有本集合自身的适用范围限定**：只约束 Feign 接口，不扩及其余对外接口）；**不得**把本节读成“阿里巴巴手册规定了该命名法”。
* 取舍与边界：前缀的目的是“**读名知归属**”，不是把业务信息堆进类名——故业务名仍只写业务本身（`UserApi`），**不拼服务全名**（`UserCenterUserApi` 属判定标准里的反例）；也不为“商标化”而为每个接口另取一套前缀字母。
* 实证反例（**本项目真实记录**，来源按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注为“来用户报告与项目对话记录、未逐字取回原文”）：用户报告的实际失效形态——同一领域下多个服务各自定义的远程调用接口**命名无统一前缀**（同一业务名在不同域下重名；新增接口时“取个不撞名的”全凭当下发挥），用户因此要求“写 Feign 接口时加一个前缀，优先考虑已有的固定前缀，没有先例则取项目名单词的首字词再组合”。

== 持久化访问走类型安全查询构造 API 与统一入口（MyBatis-Plus / 通用 ORM）

* 材料：**MyBatis-Plus 官方文档**对 `IService` 与 `Wrappers` 的说明（`IService` 继承 `IService` 接口提供 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()` 等成员方法；`Wrappers` 提供 `lambdaQuery()`/`lambdaUpdate()` 等静态构造方法；另有非 Lambda 的 `QueryWrapper`/`UpdateWrapper`，其列名以**字符串**书写）；**Spring Data 官方文档**对声明式查询方法（`findByXxx`）的定位；**MyBatis 官方文档**「Dynamic SQL」（`#{}` 预编译参数与 `${}` 字符串替换的差别）；**ISO/IEC 25010**（可维护性——无编译期校验的字符串承载的标识符难维护）。
* 依据要点（**说明：此条为官方文档定位与标准特性的要点转述、非逐字摘录**，本仓库**未逐字取回** MyBatis-Plus 与 Spring Data 的正式文档原文，故本条不引用任何加引号的字句；如日后需逐字比对，以上页面原文为对照面）：①**框架同时提供了"字符串形态"与"类型安全形态"两套查询构造**——官方把 lambda 形态作为推荐的类型安全写法，非 Lambda 形态则以字符串书写列名/表名；②**字符串书写的列名无编译期校验**：重命名重构（IDE 只重写符号引用，不重写字符串字面量）后不报错、到运行期才失败，属可维护性缺陷（ISO/IEC 25010 的可维护性特性）；③**统一入口**（`IService` 的成员方法）是框架自带的、可直接调用的能力，不需自建。
* **须注意的语义差异（同义性）**：上述材料给的是**两套写法都存在、lambda 形态受推荐**，**未**规定"禁止一切查询构造器的 `new`"、"必须只用 `IService` 成员方法"；本集合据此推出的是**自己更严的判据化取舍**——通用层 `specs/general/coding.adoc`「持久化访问（数据库/缓存等）」的三条 L1（**统一入口**、**优先用类型安全/声明式查询构造 API**、**替代优先**），**通用层只写抽象形态与判定标准、不写框架类名**，框架专名与禁止清单的**唯一落点**为技术栈层 `specs/stack/java.adoc`「持久化访问（MyBatis-Plus / JPA 等）」（**强制走 `IService` 的 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()`，除非无法替代，否则禁止 `new QueryWrapper` 及其子类**）；**不得**把本条读成"MyBatis-Plus 官方要求禁止 `new` 构造器"。
* **取值范围与例外**：本条**不**禁止跨语言语句的承载（mapper `*.xml`，见本文件「跨语言执行脚本（SQL / Lua 写资源文件，不写字符串拼接）」），**不**禁止类型安全 API 表达不了的语义（退回 mapper `*.xml` 或 Mapper 接口上封装的默认方法）；存量为**随动迁移**（改到即迁、不发动全库改造）。
* 实证反例（**本项目真实记载**，来源按 `specs/general/source.adoc`「无法确证时的正确做法」如实标注为"来自用户报告与项目对话记录、未逐字取回官方原文"）：用户报告的失效形态——Service 实现类已经 `extends ServiceImpl<XxxMapper, Xxx>`，业务代码里却仍 `new QueryWrapper<>()` / `new LambdaQueryWrapper<>()` 拼条件，**同一项目并存两套写法**（"走哪条路径"全凭当下发挥）；非 Lambda 形态还用字符串写列名（`eq("user_name", ...)`），改名即静默失效。用户据此提出的要求原文口径为："**强制要求使用 IService 的成员方法 lambdaQuery lambdaUpdate ktQuery ktUpdate，除非无法替代，否则禁止使用 new QueryWrapper 及其子类的方式**"。

== HTTP 接口路径的命名风格（RFC 3986 / Google API 设计指南）

* **材料与用途（支持 `specs/stack/spring.adoc`「分层与职责」的「HTTP 接口路径优先用中划线（kebab-case）」（L1））**：
** **RFC 3986**（Uniform Resource Identifier (URI): Generic Syntax）：URI 的**通用语法成分**与**字符分类**——路径（path）由 `pchar` 组成，`-`、`_`、`~` 等属 **unreserved** 字符；`scheme` 与 `host` **大小写不敏感**，而**路径部分大小写敏感**（`A` 与 `a` 是不同的路径）。
** **Google API 设计指南**（Google API Improvement Proposals / API Design Guide，官方页面公开）：REST 资源名与路径用**小写连字符（kebab-case）分隔的词**（如 `users/{userId}/user-events` 一类形态），不用下划线或驼峰。
* 依据要点（**说明：此条为「标准特性与官方风格指南」的要点转述、非逐字摘录**，如日后需逐字比对，以 RFC 3986 第 2-3 章（Characters / Syntax Components）与 Google API 设计指南的资源名一节的原文为对照面）：**路径片段的大小写与 `_`/`-` 之差都不构成语义差**（`-` 与 `_` 同属 unreserved，见 RFC 3986 第 2.3 节），只构成拼写与可读性风险；故本条约束的是**一致性与可读性**，不是协议兼容性。
* **须注意的语义差异（同义性）**：上述材料给的是**URI 语法事实与公开的风格约定**，**未**规定必须用中划线、也未禁止下划线；本集合据此推出的是**自己更严的判据化取舍**——路由路径的路径片段用小写 + `-`，并给出两处照旧（服务路由/网关前缀、已发布且外部依赖的对外路径）与可逐条核对的判定标准（出现 `_` / 路径片段用驼峰或大写 / 同一接口内两种风格混用）；**不得**把本节读成「某标准规定 HTTP 路径必须用中划线」。**落点只在技术栈层**（`specs/stack/spring.adoc`）：「HTTP 路径」只在 Web 框架语境下有定义，通用层不写具体协议/框架专名。
* 实证反例（**本项目真实记载**，来源如实标注为「来自用户报告与项目对话记录、未逐字取回指南原文」）：用户观察到同一项目里内部调用接口的路径**下划线与驼峰混用**，要求「**feign 接口地址优先使用中划线**」——路径风格不统一时，调用方每加一个接口都要先去看既有写法，且拼错风格的概率随接口数量线性上涨。

== 请求/响应类的复用与跨模块移动（ISO/IEC 25010 可维护性）

* **材料与用途（支持 `specs/general/coding.adoc`「代码复用」的「跨服务/对外调用的请求响应类优先移动复用，不新建」（L1））**：**ISO/IEC 25010**（系统与软件质量模型）的**可维护性**（同一信息只有一个来源、改一处不必追多处）；**ISO/IEC/IEEE 29148**（需求/接口契约须单一、无歧义、可验证——同一数据契约出现两个定义即违反「单一」）；**The Twelve-Factor App** 的 **Dependencies**（依赖**显式声明**、不复用实现细节的副本）。
* 依据要点（**说明：此条为标准特性的要点转述、非逐字摘录**）：**同一份数据契约的多个副本必然各自漂移**（字段增删只改一处 → 序列化与校验规则不一致，且没有编译期错误提示）；**「移动而非复制」是使「单一来源」成立的动作**——复制会立刻产生两个可独立演化的定义。
* **须注意的语义差异（同义性）**：上述材料给的是**可维护性与单一来源的原则**，**未**规定请求/响应类必须移动、不得新建，也**未**规定任何例外清单；本集合据此推出的是**自己更严的判据化取舍**——给已有接口加新的内部调用接口时**优先移动并沿用**请求/响应类，只留两种例外（数据库实体类除用户声明外不移动、类里引用了第三方类型的类），并明确**本项目自身的模块依赖不算三方依赖**（仍可一起移动）；**不得**把本节读成「某标准规定了例外清单」。
* 实证反例（**本项目真实记载**，来源如实标注为「来自用户报告与项目对话记录」）：用户报告的失效形态——给已有接口加 Feign 内部接口时**另建了一套请求/响应类**，同一契约出现两个定义；用户据此明确要求：「**当给一个现有的接口添加 feign 内部接口时，优先移动请求和响应类，而不是新增**，除非该类是**数据库实体类**（除声明外不用）或者**有三方依赖**（**本项目依赖不算，可以一起移动**）」。

== 依据的定位与取值（git / RFC 7233）

=== 为什么这里收的是"机制"而不是"某产品的接口"

依据图书馆可以很大（link:README.adoc[]「为什么还要有"定位协议"（馆可以无限大）」），故"引用方怎么在不全量下载的前提下定位到具体文件"本身需要依据——但它依据的是**通用的、稳定的机制**（Git 的内容寻址、HTTP 的分段取值），**不是本站站点某一页的接口**（页面会改版、接口不是标准）。故本节收机制原文与**实测取样状态**，**不收产品接口**（`specs/general/source.adoc`「不臆造行为」：描述某平台行为须有官方文档或实际验证）。

=== git（内容寻址与按 blob 取回；官方文本已取回）

* **官方材料**：git 的官方文档（`git-rev-parse`、`git-cat-file`、`git-grep`、`git-clone`；**官方文本已取回**）与 git 源码仓库自身的实践。
* **逐字（`git-cat-file` 官方文档，Description 首句）**："In its first form, the command provides the content or the type of an object in the repository."
* **逐字（`git-rev-parse` 官方文档，Specifying Revisions 一节）**："`<rev>:<path>`, e.g. `HEAD:README`, `master:./README`"；同处逐字："A suffix `:` followed by a path names the **blob or tree** at the given path in the tree-ish object named by the part before the colon."（即 `<commit>:<path>` 命名的是**该路径处的内容对象**，不是路径本身）。
* **它支撑什么**：link:README.adoc[]「依据的定位协议（入口 + 索引 + 单点取值）」把"可靠性"落在**内容可校验**上（**内容主键是终态**，路径与 commit 都只是到达它的写法）、把 commit 降为**可选加固**——依据是"Git 按内容寻址、`<commit>:<path>` 给的是内容对象"。
* **本项目实证（可复取，见下「取样方式」）**：`git rev-parse <commit>:<path>` 在同一内容处于不同路径时给出**同一个 blob sha**；文件改名/搬迁后**旧 blob 仍可 `git cat-file` 取回原文**。

=== HTTP 分段取值（RFC 7233；官方文本已取回）

* **标准名**：RFC 7233，*Hypertext Transfer Protocol (HTTP/1.1): Range Requests*（Standards Track，2014-06；**官方文本已取回**）。
* **逐字（Abstract）**："This document defines range requests and the rules for constructing and combining responses to those requests."；**逐字（4.1 节首句）**："The 206 (Partial Content) status code indicates that the server is successfully fulfilling a range request for the target resource by transferring one or more parts of the selected representation that correspond to the satisfiable ranges found in the request's Range header field (Section 3.1)."
* **它支撑什么**：link:README.adoc[] 的「分段取值（馆特别大时怎么只取一段）」一段与 link:usage.adoc[]「四、引用方怎么准确定位依据（不全量下载）」把"只取一段"写成**标准动作**（`Range` → `206`），依据即此（**当前不可用**，状态见下）。
* **须注意的同义性（L1）**：RFC 7233 规定的是**协议侧的规则**（服务端**在可满足时**才回 `206`），**未**规定任何托管服务必须支持 Range。故本站**如实标注**：本仓库站点**未实测**到 Range 生效（见下「本项目实证」），文中**不得**把"支持 Range"当成既定事实或对引用方的要求。

=== 取样方式（可复取，供日后复核）

* **git（官方文本）**：`git help rev-parse` / `git help cat-file` / `git help clone`（本机 git 2.39.5），或 git 官方文档站点对应页（本次取回的命令：`curl -sL https://git-scm.com/docs/git-cat-file/2.38.0`；注意网页源码里引文所在行会**折行**，逐字比对时先归一化空白）。
* **RFC 7233（官方文本）**：`curl -s https://www.rfc-editor.org/rfc/rfc7233.txt`（本次已取回，引文逐字比对）。
* **本项目实证（git 行为，2026-09-14 实测、可复现）**：①在一个临时仓库里两次提交同一文件的不同内容，`git rev-parse HEAD:f.txt` 前后给出**不同 blob sha**；②旧 blob sha 在后续提交之后仍能 `git cat-file -p <旧 sha>` 取回**旧内容**（改名/覆盖不影响取回）；③对本站远程仓库 `git clone --filter=blob:none --no-checkout` 的克隆体积极小，`git ls-tree HEAD library/` 列出各主题文件的 **blob sha**，`git cat-file -p <blob>` 可按需取回**单个文件**内容（即"只取一份"的可行路径）。
* **本项目实证（Range，2026-09-14 实测）**：对本站站点（`https://agent.c332030.com/library/README.adoc`）与平台原始文件视图（`https://cnb.cool/<仓库>/-/git/raw/main/library/README.adoc`）**两处**发 `Range: bytes=0-99`，**均**返回 `200` 与**整份**内容（未见 `206`；两份内容字节一致，`md5` 相同）——故 link:README.adoc[] 与 link:usage.adoc[] 均**如实写明"当前未实测到 Range 生效"**，取值以整份文件为准。
* **本项目实证（取用侧的取值路径，2026-09-14 实测）**：①**站点直链**（`https://agent.c332030.com/library/README.adoc`、`.../library/usage.adoc`）→ `200`、`text/plain`、**纯文本**（`md5` 与**站点发布分支（`main`）的同名文件逐字节一致**，即取到的是**未经处理器装配的仓库字节**——站点对非 HTML 文件直出原文、发布的是 `main` 当前内容，页面内装配只发生在 `index.html` 正文区），即**取用侧只需 https，不需要 git**；②**平台原始文件视图按分支名**（`https://cnb.cool/<仓库>/-/git/raw/main/library/README.adoc`）→ `200`、`text/plain`（`main`、`HEAD`、`refs/heads/main` 均可用；**短 commit sha、40 位 commit sha 亦可用**，不存在的 ref → `404`）；③**git 客户端**：`git ls-remote <仓库> refs/heads/main` → 返回 `372c143...` `refs/heads/main`（**这条只有具备 git 的一方走得到**，构成"取用侧与作者侧条件不同"的实证）；④**"页面里找入口"不成立**：站点首页（`index.html`）不暴露 commit、也不书写分支名，`index.html` 自身**按 `./<仓库根相对路径>` 直接 fetch**，仓库页面（平台）里嵌的 commit sha **属渲染产物**（改版即变，且站内不承载）——故入口**不得**靠解析页面结构取得，**只能**是常驻层里的**固定地址**。

== 关于标准版本年份（引用的取舍）

* **本集合的规则**：规范正文引用标准时**只写标准名/编号、不附版本年份**（`specs/general/source.adoc`「只写标准名/编号、不附链接」）——原因：标准会换版，写死年份会让依据失效；"引用现行有效版本"另由 `specs/general/source.adoc`「引用现行版本（L2）」约束。
* **图书馆的规则**：本文件**保留版本与状态信息**，用途不同——这里要回答"**这条依据今天还成立吗**"，故必须暴露换版与取代关系（这是正文不写、而图书馆要写的分工）。
