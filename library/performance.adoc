= 性能测试判据的依据（测量与记录）

本文件是依据图书馆的主题之一，承载 link:../specs/general/testing.adoc[]「性能测试」这一主题的**依据**：为什么"单次采样不构成结论"、为什么"差异小于噪声不得下结论"、为什么"性能数字必须附来源与条件"。**规则本体（判据与级别）在该规范文件内，本文件不复制规则**，只给来源、逐字原文与同义性差异。

== 当初要解决的失效（本项目实证）

用户报告（本项目真实对话）：性能测试此前"跑一次看看谁快"就算完——成绩是**单次采样**、没有离散度、没有可比的基线，结论写"快了 X 倍"却说不清测量条件；优化也多停在"改一版跑一次"，**测出的瓶颈不回头复测**，试过的失败方向不落盘，于是后来的人（与 AI）**重踩同一个坑**。用户的口径是：**"尽可能地进行优化……不断反复进行瓶颈优化，最后需要记录各方案的组合及成绩……以及优劣势，优缺点，选择的依据，优化的方向和思路也要记录，避免以后踩坑"**——本主题因此把"测量口径可核对、成绩取数、组合矩阵、优化日志、瓶颈归因"逐条判据化，并把"记到什么程度"写成可判定的下限（**不需要完整记录 ≠ 可以不记录**）。

== 外部材料：JMH 官方文档（OpenJDK，微基准的行业事实标准）

用途：`specs/general/testing.adoc`「性能测试」的「离散度与样本量」「公平比较」「计时区间界定」三条。**须注意的语义差异（同义性）**：JMH 给的是**微基准方法学**（怎么写、怎么测才对），**未**规定"记录必须写到什么程度""必须留未选方案"这类**工程管理口径**；本集合据此推出的记录判据（方案组合矩阵、优化日志、瓶颈归因格式、落点）是**本集合自己的判据化取舍**，出处只能标到"本项目实证 + 用户要求"，不得标成 JMH 的规定。

* 来源：JMH（Java Microbenchmark Harness）官方示例与文档，OpenJDK Code Tools 项目：https://github.com/openjdk/jmh （示例与教程：`jmh-samples/src/main/java/org/openjdk/jmh/samples/`）。**取样状态：官方网页已取回**（本仓库 2026-09 由执行环境取回该仓库 README 与其 samples 目录的公开说明；**未逐字取回**其官网教程正文——该站点正文为动态渲染，取回的是仓库内文本）。
* 支撑「离散度与样本量」的要点：JMH 把**测量误差**当作微基准的第一问题——误差大于两组差异时**不得下结论**，须用多次迭代（`@Measurement(iterations=...)`）与**误差条/置信区间**比较两组的差异；示例中大量对比都给出误差范围而非单一数字。（要点转述、非逐字摘录）
* 支撑「公平比较」的要点：JMH 的**每一组基准都在同一 JVM 进程内交替测量**（`@Benchmark` 方法同进程轮换执行），**每组各自预热与迭代**（`@Warmup` / `@Fork` / `@BenchmarkMode`），从而消除"一组热、一组冷"与进程间环境差异。（要点转述、非逐字摘录）
* 支撑「计时区间界定」的要点：JMH 明确要求**消费被测结果**（`Blackhole.consume`）并提示 **dead-code elimination**——结果不被使用时 JIT 可能把整段逻辑消除，测出虚假的"零成本"；`@State` 承载的**输入数据在测量外构造与初始化**。（要点转述、非逐字摘录）

== 外部标准（编号）

* **ISO/IEC/IEEE 25010（系统与软件质量模型——质量特性与使用质量）**：性能效率（performance efficiency）是**产品质量特性**之一，须**可度量**、且度量与**使用条件**绑定。支撑本主题"性能结论须附适用条件与验证日期、环境或规模变化后须重新核对"以及"优化须以可度量的结果为准"。**须注意的语义差异**：该标准是质量模型（**特性与子特性的定义**），**未**规定"微基准怎么测、要测几次"——后者来自上条 JMH。
* **ISO/IEC/IEEE 29119-4（软件测试——测试技术）**：测试是**可重复的实验设计**——须说明覆盖对象、测量条件与判定口径，结果须可复现。支撑「测量口径须可核对」（预热/轮次/批量/计时口径/环境须写明）与"未附条件的性能数字按不可引用处理"。
* **ISO/IEC/IEEE 29148（需求工程）**：需求与数据的**适用条件**须明确、可追溯。支撑「结论的落点」（选定理由与代价须进代码文档注释/设计文档，不得只留在性能测试文档）与「结论的时效」。
* **ISO 10007（配置管理指南）/ ISO 9001（质量管理体系——要求）**：变更与**成文信息**须受控、可追溯。支撑「记录落点」（性能测试文档是固定落点、结论反哺基线、旧基线保留并标注已被取代）。
* **ISO/IEC Directives Part 2（ISO/IEC 文件起草规则）**：说明性内容（为什么、背景）**不混入要求**。支撑「只记结果不记过程」——文档里只留"取值 + 来源 + 结论"，原始日志与调试过程不进记录。

== 同义性差异与覆盖点（本集合自己承认的）

* **"每组至少 3 次采样 + 报离散度 + 差异须超过离散度才算胜出"是本集合的判据化取舍**：JMH 给的是"用多次迭代与误差条比较、误差大于差异不下结论"的方法学，**未**规定"3"这个下限，也**未**规定"离散度"必须与终值同表同格；本集合把它写成**可机械核对的下限**（3 次是可用性的最小值、不是充分条件：噪声大时须加采样），并明确"差异小于离散度即无显著差异"。
* **"必留未选方案与原因""优化日志格式""方案组合矩阵的列义"是本集合自定的工程口径**：外部材料只讲**测量**，不讲**记录形态**；这几条来自用户要求（"记录各方案的组合及成绩……以及优劣势、优缺点、选择的依据，优化的方向和思路也要记录，避免以后踩坑"）与本项目的失效实证，属**本集合自己的取舍**，不得读成"某标准规定了性能记录必须长这样"。
* **"单轮即收敛不硬造轮次表"同样是本集合的取舍**：它是对"为记录形态而制造内容"（文档注水）的反向约束——记录的目的是留证，**不是凑格式**；无多轮可记时只写收敛依据即可。
* **"性能测试文档是固定落点"严于"按范围判定是否新建文档"的一般口径**：一般文档遵循"该不该建"的范围判据，性能测试因其跨类跨轮次且结论会被反复反查，本集合固定其落点；这是本集合对一般口径的**有意收窄**，理由在本主题（同一主题只留一处落点，避免成绩散落多处）。
