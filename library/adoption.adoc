= 规范准入与自身取舍的依据（依据图书馆）

本文件是依据图书馆的主题之一：**本集合判定"哪条规则该收进规范集合"的依据**，以及**本集合自己承认的更严取舍与只对本项目成立的内部约定**的依据。

== 本主题为何独立于外部标准主题

link:sources.adoc[] 的口径是：**外部标准的逐字原文**，每条都回答"这条标准确实支持这条规则"。而准入判定与自身取舍里的同主题依据存在一条**不可合并的差异**：标准只给**方向与下限**（层级结构要求、用语强度、可验证性、可控性），而**本项目自己**在此之上有明确的**更严取舍**与**组织约定**——把这些与外部标准正文写进同一份主题文件，会让读者以为"这是某标准规定的"，从而误判其适用范围与可引用性（`library/README.adoc`「放什么、不放什么」：「依据不足时如实标未确证」、`specs/general/source.adoc`「外部引用」：「不得借引用稀释、改写或减弱原有约束」）。

故按**"依据对谁成立"**分篇：**对外部也成立**的（标准原文与"它支持哪一条"）留在 link:sources.adoc[]；**只对本站成立**的（更严取舍、组织约定、本项目实证）落在本文件。分篇判据见 `library/README.adoc`「何时该给一类依据独立成篇（判据）」。

== 准入判定的依据

* **分层定位依据（ISO/IEC/IEEE 29148，需求工程）**：需求须**单一、无歧义、可验证、可追溯**。本集合据此把"一条规则属公共规范还是项目自身内容、属哪一层"写成**可判定的问题**（对谁成立、是否可验证），而不是按"感觉重要"归类；同一依据也是 `specs-project-maintainer/spec-lifecycle.adoc`「如何给一条规范定级」四问与「归属谁」的出处。原文与"未逐字取回摘要"的如实标注见 link:sources.adoc[]「ISO/IEC/IEEE 29148」。
* **用语强度依据（ISO/IEC Directives Part 2 + RFC 2119 / RFC 8174）**：要求（shall）与建议（should）**不得混用**、**要求须可验证**、说明性内容不构成要求；RFC 2119 给出 MUST/SHOULD/MAY 的强度语义，RFC 8174 澄清"**只有全大写**才具约束力"。本集合据此把 L1（必须）/L2（应当）/L3（建议）与条款类型一一对应，并作为"不得把'必须 + 判定标准'压成'要注意'"（`specs-project-maintainer/spec-lifecycle.adoc`「重构后须核对规范有效性」）的依据。原文摘录见 link:sources.adoc[]「ISO/IEC Directives Part 2」「RFC 2119 / RFC 8174」，本集合的落点为 `specs/core/execution.adoc`「分级与最高关注项」「与条款类型一一对应」。
* **被未知项目加载时的可控性依据（ISO 9241-110）**：该标准规定的是**人机交互原则**（通用名称含**可控性与符合预期**等），本集合把它**类推**到"公共内容被未知项目加载"这一"人与规则的交互"——**借用其原则**，**未**声称标准直接规定软件规范；此映射关系须如实说明、不得当标准原文（同义性说明见 link:sources.adoc[]「ISO 9241-110」）。本集合据此要求公共内容**可预期、可关闭、能自行执行、不得阻断**，并作为 `specs/general/verify.adoc`「运行契约」③与维护方"可控性清单"的判断面。
* **外部依据的引用口径（ISO/IEC Directives Part 2）**：规范正文引用标准**只写标准名/编号、不附链接**、**引用现行有效版本**、**不得编造名称与章条**。落点为 `specs/general/source.adoc`「外部引用」；本文件与 link:sources.adoc[] 的分工（正文只写名称/编号、图书馆保留版本与状态）见 link:sources.adoc[]「关于标准版本年份（引用的取舍）」。

== 同义性差异与覆盖点（本集合自己承认的）

以下三类**不是**外部材料的要求，而是**本集合自己的取舍**。每条都写明"标准/材料说了什么"与"本集合加严/新增了什么"，避免读者把本站口径当成标准原文（`specs/general/source.adoc`「外部引用」：同义性、不得借引用改写约束）。

* **配置类不写逻辑（L1）严于框架常规用法**：Spring Boot / Spring Framework 官方文档把 `@ConfigurationProperties` 定位为"把外部配置**绑定**到类型安全对象"、`@Configuration`/`@Bean` 定位为"**声明** Bean 的定义与装配方式"（官方文档定位的要点转述，非逐字摘录）；Google Java Style Guide 3.4.2 对 POJO 的表述是"A POJO **only** has behavior that **acts on its own fields**"（**逐字**，见 link:sources.adoc[]「配置类只做数据持有（POJO）」）。这些都是**职责定位与风格建议**，**未**规定"配置类中任何逻辑一律禁止"——**本集合推出的是自己更严的硬性约定：任何情况都不允许、无例外**。覆盖点与实证反例（配置类里做兜底/判断/派生值导致行为看不见、测不到）见 link:sources.adoc[] 同节；规则本体见 `specs/general/coding.adoc`「类设计」。
* **既有实现与先例优先（L1）严于"工具类使用优先级"的通行直觉**：本项目实证的失效形态是——项目**已有** `IdUtil.fastUUID()`/`CIdUtils.UUID()` 与同类调用点，执行者仍手写 `UUID.randomUUID().toString()`；**已有** `CollUtil.isNotEmpty` 类工具，仍手写 `null != coll && !coll.isEmpty()`。原 `specs/stack/java-syntax.adoc`「工具类使用优先级」把 **JDK 标准库排第 1**、项目自有与第三方库靠后，与"复用既有能力"的方向**相反**，是该失效反复出现的**制度性原因**。**本集合的取舍**：优先级重排为**项目自有工具类 → 已引入第三方工具库 → JDK 原生写法（兜底）**，并新增通用层 L1「既有实现与先例优先」「不得以语言内置写法绕过既有能力」。外部材料只提供"复用既有能力优于重复造轮子"的通行方向，**未**规定此优先级顺序；规则本体见 `specs/general/coding.adoc`「代码复用」、`specs/stack/java-syntax.adoc`。
* **开发流程（先查现状/先调研最佳方案/动手前先定基线/大动先确认/不另写一套）（L1）是本站更严的判据化取舍**：ISO 10007（配置管理指南）与 ISO 9001（成文信息控制）规定的是"**变更须基于受控、可追溯的状态**"，ISO/IEC/IEEE 29148 要求需求"单一、无歧义、可验证、可追溯"（要点转述、非逐字摘录，见 link:sources.adoc[]「ISO 10007」），**它们都没有规定**"动手前必须先把项目既有校验手段全部扫描、跑通并留证"、"没跑通不得动手"、"替换既有流程前须经用户确认"、"不得在既有实现之外另写一套"——**这些是本集合按上述变更控制与可追溯要求做的判据化取舍**（用户的真实失效：不摸现状直接动手、绕开既有实现另写一套、重构后把老用例改掉让它"通过"）。其中"**没有校验手段或既有用例本来就是红的，不阻断动手**"是**有意写死的降级分支**：否则这条会把基线变成引用方的硬性前置（无测试的项目从此动不了手）。规则本体见 `specs/general/planning.adoc` 与 `specs/general/testing.adoc`「执行与验证」。**同条的"基线完整性"（清单够不够用、先 review 既有用例、只补本次直接相关面）同为本站取舍、且定为 L2**：ISO/IEC/IEEE 29119-4（测试技术）与 IEEE 1028（软件评审）给的是**测试技术与评审**的方向与手段，**未**规定"动手前必须先复核既有用例够不够用、并补齐改动直接相关面的缺口"；定 L2 而非 L1 的判据是定级四问的 Q2/Q4——它可以被豁免（成本与改动面），写成"动手前必须补齐一切"会把基线变成引用方的硬性前置（**本项目实证**：用户要求"校验手段可能不完整、测试用例可能不完整、边界可能有问题…最好 review 一下测试用例、补全验证完整后再进行处理"）。规则本体见 `specs/general/planning.adoc`「动手前先定基线」的基线完整性条、`specs/general/verify.adoc`「验证须覆盖项目的全部既定校验手段」、`specs/general/testing.adoc`「执行与验证」的基线复核条。
* **改动范围边界（只改当前工作空间/当前项目）（L1）是本站更严的判据化取舍，不是标准规定**：ISO 10007（配置管理指南）与 ISO 9001（成文信息控制）规定的是"**变更须有明确的对象与范围、且受控可追溯**"，ISO/IEC/IEEE 29148 要求需求"单一、无歧义、可验证"——它们**未**规定"执行者只允许修改某一份工作空间/某一个项目"；GitHub Docs 受保护分支与 required reviews 一类材料讲的是"合入须经独立评审"，也**不**管"改动能落在哪个仓库"（要点转述、非逐字摘录，版本与取样标记见 link:sources.adoc[]「ISO 10007（配置管理指南）」「ISO 9001（质量管理体系——要求）」「DORA（交付性能研究）与 GitHub Docs（合并请求的变更控制）」）。**本集合据此推出的是自己更严的判据化取舍**：执行者**只允许修改本次任务的工作空间**（平台上即**只允许修改当前项目**），**未声明即拒绝**越界改动、**引用 ≠ 授权**（引用了工作空间以外的文件或其他项目只给读取许可、不给改动授权）；解禁情形只有两种（用户显式声明纳入范围、用户声明某处只读/禁止改动）。**同义性差异**：上列标准与材料提供的是"变更受控可追溯"的方向，**不得**把本条读成"某标准规定 AI 只能改一个项目"；本条也是本集合**唯一**一类"用户没明说就必须拒绝"的**改动范围**边界（与「NPC 禁合并」相邻但互不豁免：合并没有授权豁免、本条由用户声明解禁）。**本项目实证**：AI 在一个项目里工作时被"任务引用了另一个项目"带着跑，把改动落到用户并未授权的项目上；用户随后两次收紧——先要求"只改当前项目"，再明确"**这适用于所有项目**：在自己电脑/服务器上就是不得改工作空间以外的文件，CNB 只是可以改你有权限的所有仓库这一特例"。规则本体见 link:../specs/general/scope.adoc[]（平台侧追加口径见 link:../specs/platform/cnb.adoc[]「变更范围只限当前项目（未声明即拒绝）」）。
* **NPC 禁合并（L1）是组织约定、不是标准规定**：DORA 的研究结论指向"**审批要有实质、不要形式化**"（把审批做成形式化把关并不提升交付性能），GitHub Docs 关于受保护分支与 required reviews 的说明是"合入须经独立于改动提出者的评审、提交者不得自行绕过"（**要点转述、非逐字摘录**）。两者**均未**规定"某一类执行者绝对不得合并"；**本集合据此推出的是本项目自身的组织约定**——CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求，即使发起人明确授权也拒绝**（授权不免除，失效目标是不可逆且合规相关的合入动作）。实证反例：本项目曾出现"被发起人直接授权后，AI 执行者实际执行了合并"的实例。完整陈述见 link:sources.adoc[]「变更审批与"合并主体"（DORA / GitHub Docs）」，规则本体见 `specs/platform/cnb.adoc`「合并请求的合并主体（NPC 禁合并）」。
* **规范正文只写依据名、依据全文另有落点（本仓库落点）**：业界做法是"决策记载与依据要写明理由与取舍、集中存放并可达"（MADR 的必备章节序列、"Each ADR should be about one AD"、"Many ADs recur across projects"、AWS 的 "Store ADRs in a central location"——逐字与转述及同义性说明见 link:sources.adoc[]「决策记载（ADR / MADR / AWS Prescriptive Guidance）」）；**本集合据此推出的是一条自己更严的形态约束**：规范正文（会被引用方加载的那一份）**只写标准名/编号或"本项目实证"这类依据名**，**不写依据全文、不写链接**（理由：链接会失效或指向非官方来源、且正文须在"远程规范被加载"与"仓库内阅读"两态同源，见 `specs/general/source.adoc`「外部引用」「路径基准」），全文落图书馆。**引文、取回方式与反查算法见** link:usage.adoc[]「二、依据与规则怎么关联（关联协议）」。**未**有任何外部材料规定"规范正文不得写依据全文"——这是本站的取舍。
* **图书馆不建编号索引，入口主题表即索引（本仓库落点）**：AWS 的做法是"集中存放 + 在项目文档主页引用"（**要点转述**，见 link:sources.adoc[] 同节）；**本集合的取值**是把这条做到**机械可核对**：入口 link:README.adoc[]「主题登记」表为唯一索引（登记与实际主题文件**双向一致**）、入口本身在项目规范入口 `AGENTS.adoc` 登记，故**不建 ADR 式的逐条编号索引与状态机**（`status: superseded by ADR-0123` 那一套，形态见 link:sources.adoc[] 的 MADR 逐字摘录）——本集合的依据段**不做状态标记**，而是**由机械防线钉住引文锚点仍在**、**版本与取代关系写在同一段内**（link:sources.adoc[]「关于标准版本年份」）。**理由**：本集合的"条目"是**主题段落**而非一次性决策记载，编号索引会多出一个没人维护的真源。**"不做编号索引"是本站取舍**，不是外部要求。

* **持久化访问强制走统一入口与类型安全查询构造（L1）严于框架的既有用法**：MyBatis-Plus 官方**同时提供**类型安全的 lambda 形态（`IService` 的 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()`、`Wrappers` 的静态方法）**与非 Lambda 的字符串形态**（`QueryWrapper`/`UpdateWrapper` 以字符串写列名），Spring Data 亦同时支持声明式查询方法与其他构造方式（**官方文档定位的要点转述，非逐字摘录**，见 link:sources.adoc[]「持久化访问走类型安全查询构造 API 与统一入口」）——官方**未**规定"只许用一种形态"、**未**规定"禁止 `new` 构造器"，甚至**类型安全的 lambda Wrapper 也允许 `new`**。**本集合推出的是自己更严的判据化取舍**：**统一入口**（走该技术给定的承载查询/更新的既有抽象，不自建构造器）+ **优先用类型安全/声明式查询构造 API** + **替代优先**（技术自带替代写法时，只在其表达不了时才退回通用构造器且须写明理由）——**通用层只写这三条抽象形态与判定标准、不写具体框架类名**；**框架专名与禁止清单落在技术栈层**，Java 侧落到 **MyBatis-Plus 强制使用 `IService` 的成员方法 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()`，除非无法替代，否则禁止 `new QueryWrapper` 及其子类（含 `new LambdaQueryWrapper`）**。**加严的理由（不是外部要求）**：①同一项目并存两套写法后"走哪条路径"全凭当下发挥，读代码的人无法预期；②字符串列名无编译期校验、改名即静默失效。规则本体见 `specs/general/coding.adoc`「持久化访问（数据库/缓存等）」、技术栈落点 `specs/stack/java.adoc`「持久化访问（MyBatis-Plus / JPA 等）」。**本项目实证**：用户报告"Service 已 `extends ServiceImpl`，业务代码却仍 `new QueryWrapper`/`new LambdaQueryWrapper` 拼条件"，并明确要求"强制要求使用 IService 的成员方法 lambdaQuery lambdaUpdate ktQuery ktUpdate，除非无法替代，否则禁止使用 new QueryWrapper 及其子类的方式"。

* **跨语言执行脚本须放资源文件夹、扩展名取被调语言扩展名（L1）严于"注入防护"的通行要求**：OWASP 的两份 Cheat Sheet（SQL Injection Prevention / Query Parameterization）给的是**参数化查询**这一主防线，MyBatis 官方文档的 Dynamic SQL 讲的是 `#{}` 与 `${}` 的取舍，Redis 官方文档的 EVAL 讲的是脚本执行与 `EVALSHA` 复用（**均为官方页面已取回、要点转述**，见 link:sources.adoc[]「跨语言执行脚本（SQL / Lua 写资源文件，不写字符串拼接）」）——**均未**规定"脚本必须放在资源文件夹""扩展名必须是被调语言的扩展名"，**后缀 `.sql` / `.lua` 本身也不是某标准的明文要求（本集合如实标注：未确证）**。**本集合推出的是自己更严的判据化取舍**：跨语言脚本**独立成文件、放资源文件夹、扩展名取被调语言自身的扩展名**（该技术无通用扩展名时取其明确支持的文件形式，如 MyBatis 的 `*.xml` 承载 SQL），**不得**用字符串拼接/字符串模板/字符串常量内联；取用方式为**按资源读取后执行**。**本条的判据化理由**（不是外部要求）：字符串拼接与模板**没有高亮与错误校验**，语法错、字段名错、参数个数不匹配都到运行期才暴露。**本项目实证**：用户报告"字符串拼接、字符串模板没有高亮与错误校验，容易出错"，并要求**所有语言**都按此处理（含 Lua 写文件读取、MyBatis 的 XML 承载 SQL）。规则本体见 `specs/general/coding.adoc`「跨语言执行脚本的落点（资源文件夹，不写字符串拼接/模板）」、技术栈落点 `specs/stack/java.adoc`「跨语言执行脚本（SQL / Lua 等）」。**本条后半（加载时机）同为更严取舍**：官方材料只给机制与推荐（Redis 的 `EVALSHA` 复用、JDBC/MyBatis 的语句一次准备多次执行），**未**规定"资源读取几次"；本集合按**性能敏感度定性**——**性能敏感路径**（Redis 操作等争分夺秒的调用）须**第一次使用时读取一次并缓存**、不每次读；**不敏感路径**每次读无妨；**需求要求内容会变**的（如转 PDF 的 HTML 模板）**不缓存**、按是否需重读决定。**本项目实证**：用户追加要求"redis 操作是争分夺秒，是不是不能每次都去读？如果进了 classpath，发布成功后不会变，第一次使用时读取然后缓存就行，除非需求要求内容会变，比如需要转成 pdf 的 html 模板"。
* **「不得自行发评论唤起自己」是本站更严的取舍，不是标准规定**：ISO 9241-110 给的是人机交互原则（可控性、符合预期），IEEE 1028 给的是"评审与被评审相互独立"，ISO 10007 / ISO 9001 要求变更与工作可追溯、受控（均属**方向与下限**，要点转述、非逐字摘录，版本与取样标记见 link:sources.adoc[]「ISO 9241-110（交互原则）」「变更审批与"合并主体"（DORA / GitHub Docs）」）——**没有任何外部材料规定"执行者不得再发一条评论唤起自己"**。**本集合据此推出的是自己更严的判据化取舍**："评论唤起"是平台侧的派发入口（评论 + 点名 + 说清要求 = 新增一次执行），**既然一次评论就是一次派发，发起下一次就只能是派发者（人）的动作**；执行者在执行中再发一条评论唤起自己，等于**自派**——每唤起一次都要按入口重新加载规范、重新建上下文并付一次调用与等待，而**跨轮分步该由人来决定**（"分两步更清楚""上一轮没做完"都不是理由）。**本项目实证**：用户明确要求"不能艾特自己"（该形态就发生在本仓库的会话里：NPC 在 Issue 下自行发评论点名唤起自己）。规则本体见 `specs/platform/cnb.adoc`「评论唤起新实例（平台侧的派发入口）」（通用侧同口径条见 `specs/general/collab.adoc`「派发入口」）。
* **「同 Agent 承担验证」只适用于 CNB，不是平台无关的通用前提（L1）**：外部材料（IEEE 1028 软件评审、ISO 10007 配置管理的变更控制、ISO 9241-110 交互原则，**要点转述、非逐字摘录**）给的都是**方向与下限**——评审须与被评审相互独立、变更须可追溯受控、交互应可控可预期；**没有任何材料规定"验证/复核须由与执行者相同的 Agent（同一 AI 产品）承担"**。本集合先前的取舍是"**强制同 Agent**"（禁把复核派给外部来源），其**前提是执行环境里确实找得到同 Agent 的子执行者/复核者**——该前提由**承载任务的平台**给出：**CNB 上的唤起形态（评论唤起一个与执行者同产品的 NPC）使之成立**。**据此推出的取舍**（**本集合更严，且带适用面**）：①**平台层（CNB）写明该前提成立** → 按"强制同 Agent"判，**不得为图省事换外部来源**；②**平台层未写明**（其他平台、本地人工环境、跨产品协作）→ **不得援引该条拒做或把任务停在中间**，环境不提供同 Agent 子执行者时**照做该职责**（本人串行 + 标独立性边界，或如实标悬置），**验证与交付不因此缺失**。**本项目实证**：用户澄清"要求使用自己相同的 agent 来验证，这个只适用于 cnb"——即**该要求的外推面被限定在平台层**，非 CNB 环境不因"做不到同 Agent"而拒做。规则本体见 `specs/platform/cnb.adoc`「评论唤起新实例（平台侧的派发入口）」的同名 L1 条、`specs/general/collab.adoc`「同 Agent 的适用面」、`specs/general/verify.adoc`「执行者选择」。

* **运行环境须与项目声明一致（L1）是本集合更严的判据化取舍**：外部材料只给**方向与下限**——ISO/IEC/IEEE 29148（需求须单一、无歧义、可验证、可追溯）支持"用哪个版本须可追溯到项目声明"、The Twelve-Factor App 的 dev/prod parity 支持"开发与运行环境一致"、Semantic Versioning 2.0.0 界定了"行为有变即不是同一版本"（**要点转述、非逐字摘录**，见 link:sources.adoc[]「ISO/IEC/IEEE 29148」）。**它们都没有规定**"执行者必须严格使用项目声明的那一个运行环境、**即使换个版本也能跑通也不得换**"，也没有给出"声明落点怎么取"（`pom.xml` 的 `java.version`、`.nvmrc`、`.python-version` 等）与"声明环境不可得时怎么办"的判据——**这些是本集合按上述方向做的判据化取舍**。**本条与本集合其它条目的差别**：它把"结果导向的自我豁免"（"另一个版本也跑通了"）明确列为**不算理由**，因为跑通只说明"这次没暴露"，而产物、行为与验证结论的可信度已经变了。其中"**声明环境不可得或项目未声明时不阻断、但结论不得记为通过**"是**有意写死的降级分支**：否则本条会把引用方卡死在装不出声明环境的场景上（而环境可用性属"尽力而为"）。规则本体见 link:../specs/general/ci-cd.adoc[]「运行环境须与项目声明一致」。**本项目实证**：用户明确要求"各项目中都会声明使用的运行环境，比如 jdk1.8、python2 等，需严格使用完全相同的环境进行开发和验证，严禁使用不同的运行环境，即使能正常跑通流程"。

* **请求/响应类优先移动复用、HTTP 接口路径优先中划线（L1）两条均为本集合自己的判据化取舍**：可援引的外部材料只给**方向与下限**——ISO/IEC 25010 的可维护性与 ISO/IEC/IEEE 29148 的"契约须单一、无歧义、可验证"支持"同一数据契约只有一个来源"（**要点转述、非逐字摘录**，见 link:sources.adoc[]「请求/响应类的复用与跨模块移动」）；RFC 3986 只说明路径片段的字符分类与大小写敏感性（`-` 与 `_` 同属 unreserved，两者之差**不构成语义差**，见 link:sources.adoc[]「HTTP 接口路径的命名风格」），Google API 设计指南给的是**公开的风格约定**（REST 资源名路径用小写连字符）。**没有任何材料规定**"请求/响应类必须移动、不得新建"、"例外只能是数据库实体类与含三方类型的类"、"项目自身的模块依赖不算三方依赖"，也**没有**规定"HTTP 路径禁止下划线或驼峰"——**这些判据化取值与例外清单都是本集合自己的取舍**（**不得**读成某标准的规定）。两条的落点：通用层 `specs/general/coding.adoc`「代码复用」的「跨服务/对外调用的请求响应类优先移动复用，不新建」、技术栈层 `specs/stack/spring.adoc`「分层与职责」的「HTTP 接口路径优先用中划线」。**本项目实证**：用户在同一次要求里给出两条——"当给一个现有的接口添加 feign 内部接口时，优先移动请求和响应类，而不是新增，除非该类是数据库实体类（除非声明，否则不用）或者有三方依赖，本项目依赖不算，可以一起移动"与"feign 接口地址优先使用中划线"；前者要防的失效是**同一数据契约出现两个定义**（字段增删只改一处、序列化与校验各自漂移），后者要防的是**同一项目里路径风格混用**（`_` 与驼峰并存）。

* **图书馆自身的落点裁定**：`library/` 放**仓库根**——**本仓库所有内容都会被发布**，区别只在**默认引用什么**：`specs/**` 属**默认引用的公共规范**（按入口加载、其内容即引用方的输入），而图书馆**不在默认引用面内**（没有加载项把它列为待读文件）；它又天然含只对本项目成立的内容（当初的失效、取舍、实证）。该裁定的完整论证与"已分发路径被撤回"的兼容性事件记录见 `CHANGELOG.adoc` 与 `AGENTS.adoc`「依据图书馆」，本文件不重复（`specs/general/doc.adoc`「注释与文档」：不复制既有结论）。
