= 规范准入与自身取舍的依据（依据图书馆）

本文件是依据图书馆的主题之一：**本集合判定"哪条规则该收进规范集合"的依据**，以及**本集合自己承认的更严取舍与只对本项目成立的内部约定**的依据。

== 本主题为何独立于外部标准主题

link:sources.adoc[] 的口径是：**外部标准的逐字原文**，每条都回答"这条标准确实支持这条规则"。而准入判定与自身取舍里的同主题依据存在一条**不可合并的差异**：标准只给**方向与下限**（层级结构要求、用语强度、可验证性、可控性），而**本项目自己**在此之上有明确的**更严取舍**与**组织约定**——把这些与外部标准正文写进同一份主题文件，会让读者以为"这是某标准规定的"，从而误判其适用范围与可引用性（`library/README.adoc`「放什么、不放什么」：「依据不足时如实标未确证」、`specs/general/source.adoc`「外部引用」：「不得借引用稀释、改写或减弱原有约束」）。

故按**"依据对谁成立"**分篇：**对外部也成立**的（标准原文与"它支持哪一条"）留在 link:sources.adoc[]；**只对本站成立**的（更严取舍、组织约定、本项目实证）落在本文件。分篇判据见 `library/README.adoc`「何时该给一类依据独立成篇（判据）」。

== 准入判定的依据

* **分层定位依据（ISO/IEC/IEEE 29148，需求工程）**：需求须**单一、无歧义、可验证、可追溯**。本集合据此把"一条规则属公共规范还是项目自身内容、属哪一层"写成**可判定的问题**（对谁成立、是否可验证），而不是按"感觉重要"归类；同一依据也是 `specs-project-maintainer/spec-lifecycle.adoc`「如何给一条规范定级」四问与「归属谁」的出处。原文与"未逐字取回摘要"的如实标注见 link:sources.adoc[]「ISO/IEC/IEEE 29148」。
* **用语强度依据（ISO/IEC Directives Part 2 + RFC 2119 / RFC 8174）**：要求（shall）与建议（should）**不得混用**、**要求须可验证**、说明性内容不构成要求；RFC 2119 给出 MUST/SHOULD/MAY 的强度语义，RFC 8174 澄清"**只有全大写**才具约束力"。本集合据此把 L1（必须）/L2（应当）/L3（建议）与条款类型一一对应，并作为"不得把'必须 + 判定标准'压成'要注意'"（`specs-project-maintainer/spec-lifecycle.adoc`「重构后须核对规范有效性」）的依据。原文摘录见 link:sources.adoc[]「ISO/IEC Directives Part 2」「RFC 2119 / RFC 8174」，本集合的落点为 `specs/core/execution.adoc`「分级与最高关注项」「与条款类型一一对应」。
* **被未知项目加载时的可控性依据（ISO 9241-110）**：该标准规定的是**人机交互原则**（通用名称含**可控性与符合预期**等），本集合把它**类推**到"公共内容被未知项目加载"这一"人与规则的交互"——**借用其原则**，**未**声称标准直接规定软件规范；此映射关系须如实说明、不得当标准原文（同义性说明见 link:sources.adoc[]「ISO 9241-110」）。本集合据此要求公共内容**可预期、可关闭、能自行执行、不得阻断**，并作为 `specs/general/testing.adoc`「验证与运行契约」③与维护方"可控性清单"的判断面。
* **外部依据的引用口径（ISO/IEC Directives Part 2）**：规范正文引用标准**只写标准名/编号、不附链接**、**引用现行有效版本**、**不得编造名称与章条**。落点为 `specs/general/source.adoc`「外部引用」；本文件与 link:sources.adoc[] 的分工（正文只写名称/编号、图书馆保留版本与状态）见 link:sources.adoc[]「关于标准版本年份（引用的取舍）」。

== 同义性差异与覆盖点（本集合自己承认的）

以下三类**不是**外部材料的要求，而是**本集合自己的取舍**。每条都写明"标准/材料说了什么"与"本集合加严/新增了什么"，避免读者把本站口径当成标准原文（`specs/general/source.adoc`「外部引用」：同义性、不得借引用改写约束）。

* **配置类不写逻辑（L1）严于框架常规用法**：Spring Boot / Spring Framework 官方文档把 `@ConfigurationProperties` 定位为"把外部配置**绑定**到类型安全对象"、`@Configuration`/`@Bean` 定位为"**声明** Bean 的定义与装配方式"（官方文档定位的要点转述，非逐字摘录）；Google Java Style Guide 3.4.2 对 POJO 的表述是"A POJO **only** has behavior that **acts on its own fields**"（**逐字**，见 link:sources.adoc[]「配置类只做数据持有（POJO）」）。这些都是**职责定位与风格建议**，**未**规定"配置类中任何逻辑一律禁止"——**本集合推出的是自己更严的硬性约定：任何情况都不允许、无例外**。覆盖点与实证反例（配置类里做兜底/判断/派生值导致行为看不见、测不到）见 link:sources.adoc[] 同节；规则本体见 `specs/general/coding.adoc`「类设计」。
* **既有实现与先例优先（L1）严于"工具类使用优先级"的通行直觉**：本项目实证的失效形态是——项目**已有** `IdUtil.fastUUID()`/`CIdUtils.UUID()` 与同类调用点，执行者仍手写 `UUID.randomUUID().toString()`；**已有** `CollUtil.isNotEmpty` 类工具，仍手写 `null != coll && !coll.isEmpty()`。原 `specs/stack/java-syntax.adoc`「工具类使用优先级」把 **JDK 标准库排第 1**、项目自有与第三方库靠后，与"复用既有能力"的方向**相反**，是该失效反复出现的**制度性原因**。**本集合的取舍**：优先级重排为**项目自有工具类 → 已引入第三方工具库 → JDK 原生写法（兜底）**，并新增通用层 L1「既有实现与先例优先」「不得以语言内置写法绕过既有能力」。外部材料只提供"复用既有能力优于重复造轮子"的通行方向，**未**规定此优先级顺序；规则本体见 `specs/general/coding.adoc`「代码复用」、`specs/stack/java-syntax.adoc`。
* **NPC 禁合并（L1）是组织约定、不是标准规定**：DORA 的研究结论指向"**审批要有实质、不要形式化**"（把审批做成形式化把关并不提升交付性能），GitHub Docs 关于受保护分支与 required reviews 的说明是"合入须经独立于改动提出者的评审、提交者不得自行绕过"（**要点转述、非逐字摘录**）。两者**均未**规定"某一类执行者绝对不得合并"；**本集合据此推出的是本项目自身的组织约定**——CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求，即使发起人明确授权也拒绝**（授权不免除，失效目标是不可逆且合规相关的合入动作）。实证反例：本项目曾出现"被发起人直接授权后，AI 执行者实际执行了合并"的实例。完整陈述见 link:sources.adoc[]「变更审批与"合并主体"（DORA / GitHub Docs）」，规则本体见 `specs/platform/cnb.adoc`「合并请求的合并主体（NPC 禁合并）」。
* **规范正文只写依据名、依据全文另有落点（本仓库落点）**：业界做法是"决策记载与依据要写明理由与取舍、集中存放并可达"（MADR 的必备章节序列、"Each ADR should be about one AD"、"Many ADs recur across projects"、AWS 的 "Store ADRs in a central location"——逐字与转述及同义性说明见 link:sources.adoc[]「决策记载（ADR / MADR / AWS Prescriptive Guidance）」）；**本集合据此推出的是一条自己更严的形态约束**：规范正文（会被引用方加载的那一份）**只写标准名/编号或"本项目实证"这类依据名**，**不写依据全文、不写链接**（理由：链接会失效或指向非官方来源、且正文须在"远程规范被加载"与"仓库内阅读"两态同源，见 `specs/general/source.adoc`「外部引用」「路径基准」），全文落图书馆。**引文、取回方式与反查算法见** link:usage.adoc[]「二、依据与规则怎么关联（关联协议）」。**未**有任何外部材料规定"规范正文不得写依据全文"——这是本站的取舍。
* **图书馆不建编号索引，入口主题表即索引（本仓库落点）**：AWS 的做法是"集中存放 + 在项目文档主页引用"（**要点转述**，见 link:sources.adoc[] 同节）；**本集合的取值**是把这条做到**机械可核对**：入口 link:README.adoc[]「主题登记」表为唯一索引（登记与实际主题文件**双向一致**）、入口本身在项目规范入口 `AGENTS.adoc` 登记，故**不建 ADR 式的逐条编号索引与状态机**（`status: superseded by ADR-0123` 那一套，形态见 link:sources.adoc[] 的 MADR 逐字摘录）——本集合的依据段**不做状态标记**，而是**由机械防线钉住引文锚点仍在**、**版本与取代关系写在同一段内**（link:sources.adoc[]「关于标准版本年份」）。**理由**：本集合的"条目"是**主题段落**而非一次性决策记载，编号索引会多出一个没人维护的真源。**"不做编号索引"是本站取舍**，不是外部要求。

* **图书馆自身的落点裁定**：`library/` 放**仓库根**——**本仓库所有内容都会被发布**，区别只在**默认引用什么**：`specs/**` 属**默认引用的公共规范**（按入口加载、其内容即引用方的输入），而图书馆**不在默认引用面内**（没有加载项把它列为待读文件）；它又天然含只对本项目成立的内容（当初的失效、取舍、实证）。该裁定的完整论证与"已分发路径被撤回"的兼容性事件记录见 `CHANGELOG.adoc` 与 `AGENTS.adoc`「依据图书馆」，本文件不重复（`specs/general/doc.adoc`「注释与文档」：不复制既有结论）。
