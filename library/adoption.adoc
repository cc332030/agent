= 规范准入与自身取舍的依据

本文件是依据图书馆的主题之一：**本集合判定"哪条规则该收进规范集合"的依据**，以及**本集合自己承认的更严取舍与只对本项目成立的内部约定**的依据。

== 本主题为何独立于外部标准主题

`library/sources.adoc` 的口径是：**外部标准的逐字原文**，每条都回答"这条标准确实支持这条规则"。而准入判定与自身取舍里的同主题依据存在一条**不可合并的差异**：标准只给**方向与下限**（层级结构要求、用语强度、可验证性、可控性），而**本项目自己**在此之上有明确的**更严取舍**与**组织约定**——把这些与外部标准正文写进同一份主题文件，会让读者以为"这是某标准规定的"，从而误判其适用范围与可引用性。故按**"依据对谁成立"**分篇：**对外部也成立**的留在 `library/sources.adoc`；**只对本站成立**的（更严取舍、组织约定、本项目实证）落在本文件。

== 准入判定的依据

* **分层定位依据（ISO/IEC/IEEE 29148，需求工程）**：需求须**单一、无歧义、可验证、可追溯**。本集合据此把"一条规则属公共规范还是项目自身内容、属哪一层"写成**可判定的问题**（对谁成立、是否可验证），而不是按"感觉重要"归类；同一依据也是定级四问与「归属谁」的出处。原文与"未逐字取回摘要"的如实标注见 `library/sources.adoc`「ISO/IEC/IEEE 29148」。
* **用语强度依据（ISO/IEC Directives Part 2 + RFC 2119 / RFC 8174）**：要求（shall）与建议（should）**不得混用**、**要求须可验证**、说明性内容不构成要求；RFC 2119 给出 MUST/SHOULD/MAY 的强度语义，RFC 8174 澄清"**只有全大写**才具约束力"。本集合据此把 L1/L2/L3 与条款类型一一对应，并作为"不得把'必须 + 判定标准'压成'要注意'"的依据。原文摘录见 `library/sources.adoc`「ISO/IEC Directives Part 2」「RFC 2119 / RFC 8174」。
* **被未知项目加载时的可控性依据（ISO 9241-110）**：该标准规定的是**人机交互原则**（通用名称含**可控性与符合预期**等），本集合把它**类推**到"公共内容被未知项目加载"这一"人与规则的交互"——**借用其原则**，**未**声称标准直接规定软件规范；此映射关系须如实说明、不得当标准原文。本集合据此要求公共内容**可预期、可关闭、能自行执行、不得阻断**。
* **外部依据的引用口径（ISO/IEC Directives Part 2）**：规范正文引用标准**只写标准名/编号、不附链接**、**引用现行有效版本**、**不得编造名称与章条**。落点为 `specs/general/source.adoc`「外部引用」。

=== 分级与不可降级的依据

本集合把规范条目按 **L1 强制 / L2 建议 / L3 允许** 分级，并单列**"最高关注项"**（跨重构、去重、精简、迁移只能保持或加强、不得削弱）。这不是本集合自创，全部取自业界成熟做法：

* **用语强度依据（RFC 2119 / RFC 8174，IETF）**：以 `MUST`/`MUST NOT`/`SHOULD`/`SHOULD NOT`/`MAY` 划分约束强度；RFC 8174 澄清"**只有全大写且本身是规范用语**"才具约束力，避免"必须"与"应当"的歧义。原文摘录见 `library/sources.adoc`「RFC 2119 / RFC 8174」。
* **要求/建议/允许之分（ISO/IEC Directives Part 2）**：以 `shall`/`should`/`may` 区分**要求/建议/允许**，且"要求"必须**可验证**。本集合据此把 L1/L2/L3 与条款类型一一对应。
* **关键性分级（航空航天 DO-178C、功能安全 IEC 61508 的 SIL、汽车 ISO 26262 的 ASIL）**：安全关键领域以"完整性等级"固化需求——**级别越高、验证强度越高**，高等级需求不可降级、须逐条追溯。本集合据此把"最高关注项"写成**不可降级的不变量**（只能保持或加强），并要求其存在性与引用由机械防线钉住。**同义性说明**：本集合**借用其"分级 + 不可降级 + 逐条追溯"的原则**，其适用对象是软件/系统安全完整性等级，**未**声称这些标准直接规定软件规范文档的分级（不得当标准原文）。
* **不变量（invariant）**：核心约束以"不变量"固化，改动只能**保持或加强**，不得因重构/去重/精简而降级——这是"最高关注项"的直接来源。
* **单一事实来源（SSOT）**：同一约束只在**一处**给完整定义、其余位置只**一行引用**不复述（复述会各自漂移）——本集合据此把"最高关注项"的保留形态定为"一处完整定义 + 其余一行引用"，并明确把**对最高关注项的多处引用**排除在"重复/注水"之外。这也是本集合"正文只写依据名、依据全文入馆"这一取舍的同源理由（见 `library/sources.adoc`「决策记载（ADR / MADR / AWS Prescriptive Guidance）」）。
* **测试与评审视角（ISO/IEC/IEEE 29119、IEEE 1028）**：软件测试与评审相关条目的分级依据另见这两项；IEEE 1028 的"评审与被评审须相互独立"是"复核须另起独立上下文"的依据。
* **失效（无分级会长成什么样）**：① **关键约束被稀释**——"必须"与"建议"一视同仁，重构时顺手削弱最高约束（本集合实证：同一最高关注项因"多处出现"被 AI 判为"重复"而合并删除）；② **约束过载**——条条框框过多，执行者束手束脚、读者抓不住重点。

=== 存量随动迁移的依据

`specs/core/execution.adoc`「规范变更的存量处理」要求"不一次性变更所有存量、存量随动迁移"，其依据是**工程先例**（不是外部标准的规定）：

* **大范围一次性机械改造的代价**：会**批量污染提交历史**——真实变更淹没在机械改动里，难以定位与回溯；拉大改动面而**放大回归风险**。
* **小步增量重构**：违背"小步快跑、持续重构"的工程实践。依据名与规则落点见 `specs/core/execution.adoc`「规范变更的存量处理」的依据行；本处只补这两条材料说的是什么：前者要求先备好可核对的既有测试与净工作区、再小步改；后者要求小步、短周期、频繁验证，二者都只给**工程方向**、未规定"规范本身不得一次性收敛存量"。
* **同义性说明**：这些材料给的是**工程方向**（小步、可回溯），**未**规定"规范本身不得一次性收敛存量"——"存量随动迁移"是本集合据此做的**工程取舍**（`specs/general/doc-lifecycle.adoc`「存量文档迁移」/`specs/general/doc-design.adoc`「存量文档收敛」是其一致先例：碰到哪迁哪、不做全库一次迁移）。

== 同义性差异与覆盖点（本集合自己承认的）

以下**不是**外部材料的要求，而是**本集合自己的取舍**。每条都写明"标准/材料说了什么"与"本集合加严/新增了什么"，避免读者把本站口径当成标准原文。

* **配置类不写逻辑（L1）严于框架常规用法**：Spring Boot / Spring Framework 官方文档把 `@ConfigurationProperties` 定位为"把外部配置**绑定**到类型安全对象"、`@Configuration`/`@Bean` 定位为"**声明** Bean 的定义与装配方式"；Google Java Style Guide 3.4.2 对 POJO 的表述是 "A POJO **only** has behavior that **acts on its own fields**"。这些都是**职责定位与风格建议**，**未**规定"配置类中任何逻辑一律禁止"——**本集合推出的是自己更严的硬性约定：任何情况都不允许、无例外**。规则本体见 `specs/general/coding.adoc`「类设计」。
* **既有实现与先例优先（L1）严于"工具类使用优先级"的通行直觉**：本项目实证的失效形态是——项目**已有** `IdUtil.fastUUID()`/`CIdUtils.UUID()` 与同类调用点，执行者仍手写 `UUID.randomUUID().toString()`；**已有** `CollUtil.isNotEmpty` 类工具，仍手写 `null != coll && !coll.isEmpty()`。原规范把 **JDK 标准库排第 1**、项目自有与第三方库靠后，与"复用既有能力"的方向**相反**，是该失效反复出现的**制度性原因**。**本集合的取舍**：优先级重排为**项目自有工具类 → 已引入第三方工具库 → JDK 原生写法（兜底）**，并新增通用层 L1「既有实现与先例优先」「不得以语言内置写法绕过既有能力」。外部材料只提供"复用既有能力优于重复造轮子"的通行方向，**未**规定此优先级顺序；规则本体见 `specs/general/coding.adoc`「代码复用」、`specs/stack/java-syntax.adoc`。
* **开发流程（先查现状/先调研最佳方案/动手前先定基线/大动先确认/不另写一套）（L1）是本站更严的判据化取舍**：ISO 10007 与 ISO 9001 规定的是"**变更须基于受控、可追溯的状态**"，ISO/IEC/IEEE 29148 要求需求"单一、无歧义、可验证、可追溯"，**它们都没有规定**"动手前必须先把项目既有校验手段全部扫描、跑通并留证"、"没跑通不得动手"、"替换既有流程前须经用户确认"、"不得在既有实现之外另写一套"——**这些是本集合按上述变更控制与可追溯要求做的判据化取舍**（用户的真实失效：不摸现状直接动手、绕开既有实现另写一套、重构后把老用例改掉让它"通过"）。其中"**没有校验手段或既有用例本来就是红的，不阻断动手**"是**有意写死的降级分支**：否则这条会把基线变成引用方的硬性前置。**同条的"基线完整性"（清单够不够用、先 review 既有用例、只补本次直接相关面）同为本站取舍、且定为 L2**：ISO/IEC/IEEE 29119-4 与 IEEE 1028 给的是**测试技术与评审**的方向与手段，**未**规定"动手前必须先复核既有用例够不够用"；定 L2 而非 L1 的判据是定级四问的 Q2/Q4——它可以被豁免，写成"动手前必须补齐一切"会把基线变成引用方的硬性前置。规则本体见 `specs/general/planning.adoc`。
* **改动范围边界（只改当前工作空间/当前项目）（L1）是本站更严的判据化取舍，不是标准规定**：ISO 10007 与 ISO 9001 规定的是"**变更须有明确的对象与范围、且受控可追溯**"，ISO/IEC/IEEE 29148 要求需求"单一、无歧义、可验证"——它们**未**规定"执行者只允许修改某一份工作空间/某一个项目"；GitHub Docs 受保护分支与 required reviews 一类材料讲的是"合入须经独立评审"，也**不**管"改动能落在哪个仓库"。**本集合据此推出的是自己更严的判据化取舍**：执行者**只允许修改本次任务的工作空间**（平台上即**只允许修改当前项目**），**未声明即拒绝**越界改动、**引用 ≠ 授权**；解禁情形只有两种。**本项目实证**：AI 在一个项目里工作时被"任务引用了另一个项目"带着跑，把改动落到用户并未授权的项目上；用户随后两次收紧。规则本体见 `specs/general/scope.adoc`（平台侧追加口径见 `specs/platform/cnb.adoc`「变更范围只限当前项目」）。
* **NPC 禁合并（L1）是组织约定、不是标准规定**：DORA 的研究结论指向"**审批要有实质、不要形式化**"，GitHub Docs 关于受保护分支与 required reviews 的说明是"合入须经独立于改动提出者的评审、提交者不得自行绕过"。两者**均未**规定"某一类执行者绝对不得合并"；**本集合据此推出的是本项目自身的组织约定**——CNB 平台上由 NPC/CI 环境唤起执行的 agent **严禁合并合并请求，即使发起人明确授权也拒绝**。实证反例（**两次，形态不同**）：① 本项目曾出现"被发起人直接授权后，AI 执行者实际执行了合并"的实例；② **第二次的形态更隐蔽**——发起人原话要求的是"合并提交"（本意是按压缩提交处理 PR 最后一步），执行者把它读成"合并 PR"、直接调平台合并并回"已合并 ✅"，**原话里真正要求的那件事一件没做**，而当时三道**文本**防线全部报 OK。故本集合据此固定的不只是禁令本身，还有两条**可执行的形态**：① **"合并"这个词不可作为动作依据**——压缩提交、解冲突、同步目标分支、合并 PR 四件事共用一个词，缺少"PR"二字即不得推出"可以合并"；② **"按执行环境保证"**——禁令不能退化成"某个 agent 守规矩"，须落成可核对判据（提交说明/分支状态）并**尽可能收回自动执行环境的合并权限**。规则本体见 `specs/platform/cnb.adoc`「合并请求的合并主体（NPC 禁合并）」。
* **规范正文只写依据名、依据全文另有落点（本仓库落点）**：业界做法是"决策记载与依据要写明理由与取舍、集中存放并可达"（MADR 的必备章节序列、"Each ADR should be about one AD"；AWS 的 "Store ADRs in a central location"——逐字与转述见 `library/sources.adoc`「决策记载」）；**本集合据此推出的是一条自己更严的形态约束**：规范正文**只写标准名/编号或"本项目实证"这类依据名**，**不写依据全文、不写链接**（理由：链接会失效或指向非官方来源、且正文须在"远程规范被加载"与"仓库内阅读"两态同源）。**未**有任何外部材料规定"规范正文不得写依据全文"——这是本站的取舍。
* **图书馆不建编号索引，入口主题表即索引（本仓库落点）**：AWS 的做法是"集中存放 + 在项目文档主页引用"；**本集合的取值**是把这条做到**机械可核对**：入口的主题登记表为唯一索引（登记与实际主题文件**双向一致**），故**不建 ADR 式的逐条编号索引与状态机**——本集合的依据段不做状态标记，而是**由机械防线钉住引文锚点仍在**、**版本与取代关系写在同一段内**。**理由**：本集合的"条目"是**主题段落**而非一次性决策记载，编号索引会多出一个没人维护的真源。
* **持久化访问强制走统一入口与类型安全查询构造（L1）严于框架的既有用法**：MyBatis-Plus 官方**同时提供**类型安全的 lambda 形态（`IService` 的四个成员方法、`Wrappers` 的静态方法）**与非 Lambda 的字符串形态**；官方**未**规定"只许用一种形态"、**未**规定"禁止 `new` 构造器"，甚至**类型安全的 lambda Wrapper 也允许 `new`**。**本集合推出的是自己更严的判据化取舍**：**统一入口** + **优先用类型安全/声明式查询构造 API** + **替代优先**——通用层只写三条抽象形态与判定标准、不写具体框架类名；框架专名与禁止清单落在技术栈层（Java 侧落到 MyBatis-Plus 强制使用 `IService` 的成员方法、禁止 `new QueryWrapper` 及其子类）。**禁止面**经用户追加后**再扩一档**：`Wrappers.lambdaQuery()`/`Wrappers.lambdaUpdate()` 一类**静态构造方法**虽同样类型安全，**也属禁止面**（它绕过的正是"统一入口"——入口须是本实体自己 Service 的成员方法），落点只在 Mapper 接口的注解/映射文件或默认方法；**官方文档把静态工厂与成员方法并列为两种可用形态**，本集合**取后者一种**，是更严的一侧。**加严的理由**：① 同一项目并存两套写法后"走哪条路径"全凭当下发挥，读代码的人无法预期；② 字符串列名无编译期校验、改名即静默失效；③ 静态工厂与成员方法并存时"统一入口"名存实亡。**本项目实证**：用户报告"Service 已 `extends ServiceImpl`，业务代码却仍 `new QueryWrapper`/`new LambdaQueryWrapper` 拼条件"，并明确要求强制走 `IService` 成员方法；**追加**要求"也在禁用范围内：`Wrappers.lambdaQuery()` 等，使用 `service.lambdaQuery()` 等"。
* **分页查询两侧各用哪种包装体、转换一律走 `convert`（L1）是本集合自己的判据化取舍**：MyBatis-Plus 官方只给**能力面**——有分页容器（`IPage`）与 `convert`（元素级映射、容器与元数据不变），**未**规定"普通接口返回 `IPage`、声明式客户端接口返回自定义分页类"，也**未**规定"禁止新建 page 再逐字段搬运"、**未**规定"分页元素不许是实体类"（后者归「数据契约的载体」那条）。**本集合据此推出的是自己更严、也更可判定的形态约束**：普通接口 `Result<IPage<Rsp>>`、Feign 接口 `Result<自定义Page<Rsp>>`（跟随先例）、**转换走 `page.convert` 而不是新建 page**。**理由**：① 同一项目并存两套分页模型后"这个接口该返回哪种"全凭当下发挥；② `convert` 由容器内部完成元素替换，**分页元数据原样保留**，而新建 page 时元数据要逐项手工搬运，**漏一项既不报错也不提示**，只在运行期表现为"总页数一直是 0、翻页失效"——属静默缺陷。**本项目实证**：用户口径为"如果是普通接口，分页查询时返回 `Result<IPage<Rsp>>`；如果是 feign 接口（`Result<自定义Page<Rsp>>`），字段转换时，使用 `page.convert` 而不是新建 page"。规则本体见 `specs/stack/java.adoc`「持久化访问（MyBatis-Plus / JPA 等）」。

Not really."**，Conventional Commits 是 "a lightweight convention on top of commit messages"、**只约束提交信息、不约束 changelog 展示形态**）。**本集合据此推出的是自己的形态取舍**：① **排序方向恒为时间倒序**——版本号单调递增时**版本倒序与时间倒序是同一件事**，故"按版本分组"与"按时间流水"只是**分组口径**之别；② **版本号即发布标识、日期取发布日期**（**tag 创建日优先**）；③ **两种条目形态择一**（流水式 / 表格式），**表格式的列义与判据依赖关系**是本集合的判据化取值；④ **要素齐备底线（四项：类型 / 变更点 / 影响 / 标记）**由本集合提出；⑤ **不维护 `Unreleased` 区段**是对 Keep a Changelog 推荐做法的**显式不采用**。规则本体见 `specs/general/changelog.adoc`。**本项目实证**：用户在一个工具库项目上对比最后两个 tag 后要求"根据模块和功能分类，做成一个表格……如果一条条的写的话可读性很差"。
* **无参/必参/全参构造一律由 lombok 生成、不手写（L1）是本集合更严的判据化取舍**：外部材料只给**方向与下限**——ISO/IEC 25010 的可维护性支持"同一样板只有一处来源"，ISO/IEC/IEEE 29148 要求判定可验证；Project Lombok 官方文档给出三个注解的职责与共存方式——**均未**规定"构造方法必须由 lombok 生成、禁止手写"。**取该取向的理由**：类上已标 `@Data` 却另写构造方法时，**同一构造出现两个来源**。**本项目实证**：用户原文口径为"**无参、必参、所有参优先使用 lombok 而不是手写**"。规则本体见 `specs/stack/java.adoc`「编码」。
* **`serialVersionUID` 默认取 `1L`、局部变量「优先 `val`、可变才 `var`」、链式调用「哪怕很短也要换行」三条均为本集合自己的判据化取舍**：可援引的外部材料只给**方向与下限**——Java Object Serialization Specification 给的是**版本化机制**（不显式声明时 UID 由类结构推导、结构一变即不兼容；声明后由作者掌握），**未**规定「必须显式声明」、**未**规定默认值取多少；Google Java Style Guide 的局部变量类型推断与换行两节给的是**可读性判据与行宽判据**（推断结果不清时写显式类型；按行宽决定是否换行），**未**规定「必须用 `val`/`var`」、**也未**规定「链式调用哪怕很短也必须换行」。**本集合推出的是自己更严的单一形态**：① 已实现 `Serializable` 的类型**必须显式声明** `serialVersionUID`、**无配置时默认取 `1L`**、JDK 14+ 补 `@Serial`，且**不得**为未实现该接口的类型补字段或顺手加 `implements Serializable`、**不得**以 `@SuppressWarnings` 代替显式声明；② 局部变量**先取 `val`**、**确实需要重新赋值才用 `var`**（不是「`val`/`var` 二选一都行」）；③ 链式调用**一律换行、长度不是判据**。**取更严的单一形态的理由**：三处的裁量点都在「多短算短」「哪种更可读」上，留给临场发挥时同一项目里会并存两种形态、读代码的人无法预期（与「先例优先」同源）。**本项目实证**：用户原文口径为「java 下调整规范 serialVersionUID 给个默认值 1L？避免老是报警告，自动加（仅限已经实现了 Serializable 的类型，没实现不自动加 Serializable 实现）」「java 下优先使用 val（lombok） var（jdk or lombok）」「链式调用哪怕很短也要换行（所有语言）」。规则本体见 `specs/stack/java.adoc`「编码」与「序列化（`Serializable`）」、`specs/general/coding.adoc`「表达式与调用写法」。

* **「成员与方法次序（新增成员按流程次序落点、可插前面或中间、重载相邻、数据转换方法跟在查询接口之后）」是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**方向与下限**——Google Java Style Guide 3.4.2 明确"成员次序**没有唯一正确的配方**"，只要求"每类使用某种**逻辑次序**、维护者能解释"，并**点名禁止**"新方法习惯性追加到类末尾"（那属按加入日期排序）；ISO/IEC 25010 的可维护性支持"位置本身承载次序信息"；ISO/IEC/IEEE 29148 要求判定**单一、无歧义、可验证**——**没有任何材料规定**"新增成员按流程次序落点、并且**允许**加到已有成员的前面或中间"，**也**没有规定"重载成员须相邻""数据转换方法写在查询方法之后"。**本集合据此推出的取值**：① **调用方在前、被调用方在后**（先初始化、先被用到的在前，被依赖者在前，如 `ObjectMapper` 在 `RestTemplate` 之前）；② **允许插到前面（含最前面）或中间**，不得一律追加到末尾；③ **重载紧邻已有同名成员**、重载之间同样按流程次序；④ **转换跟随查询**（把数据库实体与返回模型互转的方法默认写在查询它的那个接口/方法之后，不按"被调用者在前"提前）；⑤ **只对新增成员生效**，既有成员不动、不发动全库重排，**review 时对既有成员的位置不提出问题**。**为什么取"流程次序 + 允许插前面/中间"**：位置是读者唯一的次序线索，按"改动追加到末尾"摆放会让同一个类里出现多套互相无关的次序（历史追加序、随手序），且**新增的位置不报错**、只是次序无声漂移；而"只能往末尾加"这条常见做法正是 Google 点名禁止的形态。**本项目实证**：用户原文口径为"**新增方法/函数时，按照业务流程的先后顺序进行排序，越底层流程越靠后越在后面（即允许按照流程前后顺序，把新增方法加在已有方法的前面（包括最前面）或者中间），如果有重载方法，直接加在重载方法的附近（重载方法的排序同样按照先后顺序），先初始化的在前面，先用到的在前面，后面的依赖前面的，比如 resttemplate 依赖 objectmapper，objectmapper 在前面。例外：接口查询数据时，要对数据库实体和返回模型做转换，转换方法默认写在查询接口后面。此规范只适用于新增方法/函数，不对已有方法生效，review 时不算问题不提出**"。规则本体见 `specs/general/coding.adoc`「命名与代码质量」的「成员与方法次序」，Java 落点见 `specs/stack/java.adoc`「编码」。
* **「链式赋值顺序随字段顺序（链式调用里的赋值环节按字段顺序书写）」是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**方向与下限**——ISO/IEC 25010 的可维护性支持“同一份字段清单只有一个次序来源”，ISO/IEC/IEEE 29148 要求判定**单一、无歧义、可验证**，Google Java Style Guide 3.4.2 只要求成员次序是**逻辑次序**、维护者能解释即可（并明确成员次序“没有唯一正确的配方”），《阿里巴巴 Java 开发手册》只给“字段与表结构逐列对照”这一通行做法——**没有任何材料规定**“赋值环节的书写次序须跟随字段次序”，也**没有**规定“以哪一处为准”。**本集合据此推出的取值**：① **字段顺序不另定**——沿用本集合既有的两条（实体类跟随映射表列序、其他类按成员排序规则），本条只管“赋值时按它走”，不成为第二个次序来源；② **赋值顺序不一致即违规**（含按字母序、按使用频率、按改动追加排列）；③ **例外只在语义要求时开口**（后一次赋值覆盖前一次、后设的值依赖前设的值），部分赋值时按所选字段的**相对先后**核对。**为什么取“跟随字段顺序”而不是“随书写者方便”**：赋值次序与字段次序是同一份字段清单的两处呈现，各自成序时读的人与评审者要回看类定义才能建立对应；且**只改了字段、忘了赋值处时不报错**（次序无声漂移）。**赋值的载体**（链式 setter、builder 的 `.xxx(...)`）、**链式风格**（`@Accessors(chain = true)`）与**取值落点**（模板文件与 Java 栈层）分别见 `specs/stack/java.adoc`「编码」与 `specs/stack/java-object.adoc`。**本项目实证**：用户原文口径为“链式调用时，比如赋值，顺序 和字段、数据库顺序保持一致”。规则本体见 `specs/general/coding.adoc`「命名与代码质量」的「链式赋值顺序随字段顺序」。
* **「Maven 默认启用多线程构建、以项目配置为准」是本站的判据化取舍，不是 Maven 官方要求**：Maven 官方命令行参考只给**机制与取值写法**（`-T`/`--threads` 接受 `4`（整数）或 `2C`/`2.5C`（核心数倍率）；`.mvn/maven.config` 放项目级命令行选项、官方举例即 `-T3 -U --fail-at-end`），**未**规定"默认该不该开并行"、**未**说明"并行会不会连带让单个模块内的测试并发"；Surefire 官方参数表给了 `forkCount`（默认 `1`，自 2.14）、`reuseForks`（参数表标默认 `true`、自 2.13；3.x 迁移说明另有「3.0.0 起改为 `false`」的口径，**本项目未逐字取回该页，故不裁定哪个为准**）与 `parallel`（**默认不并行执行测试**）的取值，也**未**规定"构建并行与测试并行该不该一起开"。**本集合据此推出的是自己的判据化取舍**：① 未配置过并行度时**默认开 `-T`、取值＝当前构建设备的核心数**（命令形态 `mvn -T <核心数>`）——`C` 是 core **multiplied**，`--threads 1C` **不必然等于**当前设备核心数，故取值只定义到「核心数」这一层、不写成任何一个固定写法（**这个量怎么取是执行动作，规范不写**）；② **配置过即沿用、不覆盖**；③ 并行只到**模块粒度**（与『同一模块禁止并行构建』并存）；④ **只启用构建并行、不因本条开测试并行**——测试并行是另一项改动、须先确认，并要求 `reuseForks` 显式写进配置（**理由**：`reuseForks` 的默认值在官方文档里两种口径并存，**依赖默认值等于把某个版本的行为当成既定事实**）。**为什么落在 Maven 栈层而不是通用层**：并行构建的开关、模块语义与"配置优先"的落点（`.mvn/maven.config`）都是 Maven 专名，通用层只保留了"本地缓存与镜像就近取用"这类跨语言口径。**本项目实证（`-T 1C` 为当时报告方人手命令中的写法，非本集合推荐的取值写法）**：同一仓库里"以 `mvn -T 1C` 构建"与"无参 `mvn` 构建"两条路径并存——并行度只写在人手的命令行里、没落到项目配置，自动化的无参 `mvn` 调用因此继承了默认单线程（用户报告），用户口径是"**默认会自己启用可以不管**"。规则本体见 `specs/stack/maven.adoc`「构建并行度」。

* **「Java 数据对象模板」的三处取值（补注解时已提交的类默认不加 `@Accessors`、无参不加 `@AllArgsConstructor`、集合默认加 `@Singular`）与「review 不计问题」这一生效面是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**机制与下限**——Spring Framework 官方文档说明 `BeanUtils` 的批量属性拷贝按 setter 发现属性，Project Lombok 官方文档说明 `@Accessors(chain = true)` 让生成的 setter 返回实现类型本身、`@Singular` 给 builder 一个单元素入口、三个构造注解各自的职责——**没有任何材料规定**「给既有对象补注解时不得加 `@Accessors(chain = true)`」「无实例字段时不得标 `@AllArgsConstructor`」「POJO 的集合字段一律加 `@Singular`」，也**没有**规定「数据对象该标哪几个注解」、更**没有**规定「补注解时该以什么划线」「review 该不该把这类缺失报成问题」。**本集合据此推出的是自己的判据化取舍**：① 链式 setter 的返回类型带类自身的泛型 ⇒ `BeanUtils` 一类按 setter 找属性的拷贝会**跳过**它、数据静默丢失，故**新增加、补注解时以「类是否已提交」分档**——**已提交的默认不补**（该类可能已被别处按 `BeanUtils` 一类拷贝使用，补上即让原本可被拷贝的属性静默不再被拷贝）、**未提交的可以补**（还没有任何调用方，补上不产生本条要防的那种丢失）；② 无字段时全参构造与无参构造是同一个构造，多标一个注解只会误导读者；③ 集合字段默认给单元素入口，判据是"builder 侧能不能一次加一个元素"。**生效面两档**：新增对象整段适用、既有对象**主动声明才补**、存量不告警不整改（同本集合「存量随动迁移」的通行口径）；**review 不计问题**已升为全局口径（`specs/general/review.adoc`「review 的默认检查面」——review 默认只查代码/文档/用例三类问题、存量不动、主动声明才查），本条不再单列一面。模板本体（整段照抄的清单）见 `specs/stack/java-object.adoc`，判据本体见 `specs/stack/java.adoc`「编码」的「数据对象模板」条。**本项目实证**：用户原文口径为「java 数据对象模板，应该属于规范模板，但是感觉不要进 java 规范文件，这种属于要么不读，要么读全部的，应该算模板文件」「都是新增时生效，现有对象主动声明才补」「新增对象时加 Accessors，补注解时不加（因为 spring beanutils 会忽略有泛型类型的 set 方法，导致会出现丢失数据，各个地方都可能出问题）」「AllArgsConstructor 无参数时不加」「除非有问题，否则 pojo 里的集合默认加 lombok 注解 `@Singular`」；补充轮口径为「java-object.adoc 中的内容，只有在主动声明要补的情况下，才补，review 时不算问题不提出」「`@Accessors` 补的时候，如果类已经提交，默认不补（未提交时可以补）」。
* **「纯取值转换的空 `catch`（`Enum.valueOf` 与自写枚举工具）」（条件例外，L2）是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**机制**——Java 官方 API 文档说明 `Enum.valueOf` 在"指定名字的枚举常量不存在"时抛 `IllegalArgumentException`，ISO/IEC 25010 把可维护性列为质量特性，ISO/IEC/IEEE 29148 要求判定单一、可验证；**没有任何材料规定**"该处可以空 `catch`"，也**没有**规定"什么条件下才允许"——"不得吞异常"这条 L1 的**唯一放宽口**（"异常只有一种原因 + 取不到即无值 + 默认值取自同一 API"三条准入）是本集合自己的取值。**为什么仍写条件例外而不是直接判合规**：`catch` 后空块体**在代码表面不可区分**于"吞了真失败"（判据是语义的：该 API 的异常是否只有一种原因、该调用点的失败是否另有出口），故把它写成**带准入条件的例外**、由执行者按三条核对并在代码注释里写明依据；**扩大的两个方向**（类级空 `catch`、`try` 里其他语句的异常）在规则里显式排除。**本项目实证**：用户原文口径为"**规范里「不得吞异常（catch 后空实现）」是 L1……调整规范：java 下 Enum.valueOf 例外，这里的异常只有可能是值没匹配上，还有其他自己写的枚举工具，允许空 catch**"。规则本体见 `specs/general/coding.adoc`「代码质量（新产出即高质）」的「显式处理失败与边界」与 `specs/stack/java.adoc`「健壮性」。
* **「方法名与逻辑删除的对应（默认面随技术是否自动附加删除标志条件而变、非默认面须带特征词）」是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**方向与下限**——《阿里巴巴 Java 开发手册》【命名】章要求方法名**望文生义、避免歧义与同义混用**，ISO/IEC 25010 把**可维护性**列为产品质量特性，ISO/IEC/IEEE 29148 要求判定**单一、无歧义、可验证**；MyBatis-Plus 官方文档只给**能力面**（`@TableLogic` 声明逻辑删除字段、框架据此为查询附加条件；另有"查全部/绕过该条件"的形态），**未**规定方法名的命名口径、**未**规定"默认面是含已删还是只取未删"。**本集合据此推出的是自己更可判定的形态约束**：① **默认面由该技术是否自动附加删除标志条件决定**——不自动附加时默认＝含已删、自动附加时默认＝只取未删；② **非默认面须在方法名上带特征词**（或等价的显式参数/调用形态）；③ 同一实体上同一删隐面**只许一个名字**，**不得**"一个带特征 + 一个不带特征"并存（同一件事两个来源，改一处必漏另一处）。**为什么"默认"要按技术取值而不是按习惯**：同一条 `list()` 在未启用逻辑删除的库里返回**含已删**数据、在启用的库里返回**只含未删**数据，**名字一个字都没变**——删隐面只能从技术配置反推、读代码的人与评审者都无从预期；统一成"约定俗成的那一面"则等于**给同一句契约配两套含义**。**边界（防扩大）**：① **框架自带**的方法名（如框架的按主键查询）按其自身契约生效、不要求改名；② 非查询方法名、局部变量与参数名、非实体的数据结构名**不在本条范围内**；③ 载体名（布尔列、时间戳、状态列、注解）、具体特征词取值与框架专名落在各技术栈层（Java 侧见 `specs/stack/java.adoc`「持久化访问（MyBatis-Plus / JPA 等）」）。**本项目实证**：用户原文口径为"**未使用 mybatis plus 逻辑删除时，没有前缀后缀的方法名默认查询且不带删除标志，如果要查询已删除/未删除（带了删除标志的条件）的数据时，要带特征；使用 mybatis plus 逻辑删除时（因为会默认带删除标志），没有前缀后缀的方法名默认查询逻辑删除数据，如果要查询已删除和忽略删除标志的数据时，要带特征。不仅限 mybatis plus，其他类似的也生效（自己实现的逻辑删除逻辑和框架也算），适用所有语言**"。规则本体见 `specs/general/coding.adoc`「持久化访问（数据库/缓存等）」的「方法名与逻辑删除的对应」。
* **多层嵌套对象转换优先声明式映射、JVM 下优先 MapStruct 是本集合自己的取向（L2 建议，非强制）**：外部材料只给**方向与下限**——ISO/IEC 25010 的可维护性支持"同一份映射只有一处来源"；**没有任何材料规定**"多层嵌套对象转换必须用某个库"、"禁止手写转换代码"，也**没有**规定"JVM 下优先用 MapStruct"。**取该取向的理由**：① 手写逐字段搬运**没有编译期保障**；② 多层嵌套时手写代码随模型数量增长。**用户明确要求不做强制性限制**，故条文写成 **L2 建议**。**本项目实证**：用户原文口径为"**多层嵌套对象转换时，优先使用 mapstruct（jvm下），不允许手动写转换代码——不是强制，但是建议**"。规则本体见 `specs/general/coding.adoc`「对象转换」、`specs/stack/java.adoc`「对象转换（MapStruct）」。

* **「不得新增只做条件取值的方法 + 没有现成工具方法就加一个通用方法、不就地抽专用方法」是本集合自己的判据化取舍，不是标准规定**：可援引的外部材料只给**方向与下限**——Martin Fowler《Refactoring》的「重复代码」与「数据泥团」指向"同一份逻辑收敛到一处"、ISO/IEC 25010 的可维护性支持"同一取值只有一处来源"；**没有任何材料规定**"方法体只剩一处条件取值时不得新增该方法"，也**没有**规定"没有现成工具方法时的去向是通用工具方法、而非就地抽专用方法"。**本集合的取值**是把这个下限收紧成两条可核对的动作：① 方法体只剩一处条件取值（三元、`if/else` 后 `return`、`??`/`or` 兜底之一，且一支只是"取另一个来源的同一个值"）时**不得新增该方法**；② 「空则取默认值」有现成入口时强制用它、**没有时去加一个通用工具方法**（一处定义、全项目复用）。**本项目实证**：用户原文口径为"严禁新增一个里面只有三元判断取值的方法，适应任何语言，有很多类似的 `defaultIfNull` `defaultIfEmpty` 的方法，没有可以加"；要治的失效是——就地为一次调用抽一个只做条件取值的方法，名字只是把那次挑选复述一遍、每次取值多跳一次，同一份取值逻辑散在多处。
