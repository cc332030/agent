= 依据的写入与关联（图书馆使用协议）

本文件是依据图书馆的主题之一，也是图书馆的**使用协议**：回答三件图书馆此前没有完整判据的事——①**什么时候该把一条依据写进图书馆、写什么、什么时候不写**；②**依据与规则（规范正文、提示词、脚本、决策）之间怎么互相关联、怎么反查**；③**馆可以无限大（没有体量与范围上限）时，引用方怎么在不全量下载的前提下准确定位到"具体哪个文件"**（**取用侧是只有 https 的游客**：不需要 git、不需要版本号，入口是常驻层里的固定地址）。图书馆的落点、放什么不放什么、独立成篇判据见 link:README.adoc[]；本条补"写入时机""关联协议"与"定位与取值"。

== 为什么需要本协议（本站失效）

* **写入时机此前无判据**：图书馆的边界（link:README.adoc[]「放什么、不放什么」）与"何时该独立成篇"（link:README.adoc[]「何时该给一类依据独立成篇（判据）」）都只回答**形态**问题（"这类依据该不该单独一个文件""该放哪"），不回答**触发**问题（"我现在这条规范/这次决策，要不要入馆""入馆要写哪几项"）。缺触发判据的后果与本项目多处同形：**AI 不主动写**——依据仍在各文件就地承载、无人补入馆；真写时**写什么全凭发挥**（要么把规则抄一遍、要么只写一行标准名），要么**该写不写**，要么**不该写硬写**（把讨论过程、把复述既有结论的段落塞进来，即 link:../specs/general/doc.adoc[]「注释与文档」的注水）。本协议把这三问写成可判定的判据。
* **关联此前只有约定、没有算法**：规则侧（规范正文）给的是"依据名"入口，馆侧（link:sources.adoc[]、link:adoption.adoc[]）给的是"这条标准支撑哪些条目"的逐条映射——**方向本来就有，但只到"可按标准名检索"这个人的约定**：机器（AI 在执行任务时读规范）拿到的规范正文里**只有标准名**，没有"到馆里取哪一份"的解析步骤；也没有写明"要不要遍历整个项目去全文检索"（外部项目引入公共规范时**根本不能**这么干）。本协议补上**只取一份、不遍历**的解析算法，并把"默认引用面 / 非引用面"的边界写清（引用方项目默认只按公共规范加载、其工作区里没有本仓库的文件，故其解析必须在规范正文处终止）。

== 一、什么时候该把依据写进图书馆（触发特征）

**判据是问句，不是印象**：**"这条规则/这个决策，将来有人问'它还成立吗'时，需要什么才能回答？"**——需要**回到当初的原始表述或当初的事实**才能回答的，就该有依据落点；只靠"规矩就是这么定的"就能回答的，不必入馆。

命中以下任一即**应当**入馆（L2）：

* **首次引入的规则**：本次新增/调整了一条 L1 或最高关注项条目——其依据（外部标准名/编号、本集合的更严取舍与覆盖点、当初的失效）须有落点，使日后能核对"它今天还成立吗"（link:../specs/general/verify.adoc[]「验证总纲」的"防慢慢脱离初衷"）。
* **有取舍或争议的决策**：在多个方案之间做了选择、或曾被质疑/推翻过——须收**当初的比较与理由**（选了哪个、放弃了哪个、接受什么代价、依据什么）；只写"决定用 X"等于没写依据。
* **首次出现的实证/反例**：本项目真实发生的失效（用户报告、线上问题、真实误用）首次被用于支撑某条要求时——须收**失效长什么样**（可复述的现象 + 与要求的对应关系），它是"这条要求针对什么"的可信锚点。
* **外部标准的首次引用**：规范正文首次引用某标准（只写名称/编号，见 link:../specs/general/source.adoc[]「外部引用」）时——须收**该标准的原文摘录或如实标注未取回**、以及"它确实支持哪一条"的映射（形态与标注口径见 link:README.adoc[] 与 link:sources.adoc[]「使用与核对」）。
* **技术选型与组织约定**：选型（为什么用这个库/这个结构）、组织约定（本项目自定的硬性约束）——须收**选型依据与约定来源**，并写明它是本站取舍还是外部规定（后者不得冒充，见 link:adoption.adoc[]「同义性差异与覆盖点」）。

以下情形**不写**（L1，与 link:../specs/general/doc.adoc[]「注释与文档」"文档不得注水"同源）：

* **规则本体的复述**：图书馆**只补依据、不复制规则**（规则本体在 `specs/`，见 link:README.adoc[]「放什么、不放什么」）——把规范条文抄进图书馆，等于制造第二真源，改一处必漏一处。
* **没有出处的观点、推测、印象**：无法确证的结论按 link:../specs/general/source.adoc[]「无法确证时的正确做法」**如实标"未确证"并写明已查证方式**，不得用虚构内容填补；但"标未确证"本身是图书馆要收的内容，不等于"不写"。
* **只把讨论过程落盘的记录**：会议记录、多轮试错的过程、被放弃的中间稿——只留结论与依据（谁在何时说过什么不构成依据）。
* **临时产物**：任务进度、检查清单、扫描中间结果按 link:../specs/core/execution.adoc[]「临时产物」进 `tmp/`，**不入馆**（会被清理、无出处可追溯）。
* **靠文件名承载依据内容**：主题文件名只做**唯一标识**，**不写内容描述、不写限定语与来源**（名字长只让每次链接与每次目录列举都多占上下文，且**名字本来就不是检索键**——检索键只有依据名，见本文件「四、引用方怎么准确定位依据（不全量下载）」的「文件名不承担定位」）。
* **依据齐备但无人会问"还成立吗"**的常识性做法：如"文件名用 kebab-case"这类无争议的局部约定，落在对应规范正文或代码注释即可（link:../specs/general/doc.adoc[]「注释与文档」）。

**写入的落点与形态**（与 link:README.adoc[] 的分篇判据一致）：

* **仍在规则所在地承载**（默认，多数情形）：依据与规则**同处一处**最不易漂移（各规范文件自身的说明性段落与依据行、提示词正文、脚本注释）——独立成篇不是"依据必须离开规则所在地"的强制动作。故"该有依据"**不等于**"该新建一个主题文件"（link:README.adoc[]「何时该给一类依据独立成篇（判据）」）。
* **独立成篇**：同时满足"与规则本体分离"与"按依据对谁成立归类"两条判据时才另建主题文件，并在入口登记（写文件与登记是同一个动作，见 link:README.adoc[]「主题登记」）。
* **入库必写项**（承 link:sources.adoc[]「使用与核对」）：①**出处**（标准名/编号或"本项目实证/组织约定"）；②**逐字原文或如实标注的取样状态**（三类标记：官方文本已取回 / 官方网页已取回 / 未逐字取回）；③**它支撑哪一条**（写清落点文件与条目，这是反查的锚）；④**取回方式**（可复取的命令或来源，供日后复核）；⑤有取舍/有覆盖点时另写**同义性差异**（标准说了什么、本站加严了什么，见 link:adoption.adoc[]）。

== 二、依据与规则怎么关联（关联协议）

**关联靠两侧各写一半、互相指向**——两侧都不完整，缺任一侧就查不到：

* **规则侧只写入口**：规范正文/提示词/脚本注释里给出**依据名**（标准名/编号，或"本项目实证"）——**不写全文、不写链接**（原因见 link:../specs/general/source.adoc[]「外部引用」：链接会失效或指向非官方来源；且正文要跨"远程规范被加载"与"仓库内阅读"两态同源）。依据名就是**入口键**。**本集合的落点约定**：`specs/**`（**默认引用的公共规范**）只能写**标准名/编号**这一形态；"到本项目图书馆的哪一份主题"只写在项目规范入口 link:../AGENTS.adoc[] 与图书馆内部，**不进默认引用项**——引用方按公共输入执行时取不到它，写进去等于给出一条它走不通的路径（边界见本文件「三、默认引用面与非引用面」）。
* **依据侧写全反查**：图书馆主题文件按**依据**组织（一条依据一段），段内逐条列出它支撑的规范条目，即"**使用位置**"（写法不限，**须点出落点文件与条目**；link:sources.adoc[] 用"用途"行、link:adoption.adoc[]「准入判定的依据」用编号条目，两者均可）——这就是**反查表**：拿到依据可反查它被谁用。
* **两侧一致、同一处定义**：同一件事别在两侧展开（正文给规则、馆里给依据）；**依据只压缩为名称/编号、不得整段删除**（`specs-project-maintainer/spec-lifecycle.adoc`「重构后须核对规范有效性」）——正文里删掉依据名，馆里那段就再也无人反查到，等于依据不存在。

=== 反查解析算法（只取一份，不遍历）

**目标**：从**规范正文**（外部项目能拿到的那一份）出发，只读**一份**文件就走到依据；**不遍历项目、不做全文检索**。四步：

. **（前置）判断馆是否可达**：图书馆路径**相对仓库根**书写（形如 `library/README.adoc`），它**不在默认引用面内**（本仓库内容虽全部发布，但没有指向它的加载项），且执行者未必工作在本仓库内（在引用方项目里按远程规范执行、或无仓库访问权）。故**先在工作区里看它是否真的可达**（能读到 `library/README.adoc`）：**可达**（= 工作在本仓库内）才继续下一步；**不可达**（= 在引用方项目里按公共规范执行）即按「终止条件」停止——正文里的依据名已足够，不必也**不得**为取依据去克隆/下拉本仓库或遍历工作区。
  **可达不等于可预期**：即便本仓库内容在公网可达，引用方项目按公共输入执行时**无从知道该找这一份**（没有加载项把它列为待读文件）；它的依据落点由**它自己的项目规范**约定（link:../PROMPTS.adoc[]「优先级与隔离」已写明该分工），不是本项目图书馆。
. **取依据名**：读规范正文中该条目的依据行（如 `依据：RFC 2119 / RFC 8174`、`依据：本项目实证`）。这是本次唯一需要的检索键——**不需要读第 2 个文件来找"依据在哪"**。
. **判定依据类型**：是**外部标准**还是**本站取舍/实证**（正文的措辞已区分：标准名/编号 vs "本项目实证""组织约定"）。
. **定位图书馆的对应主题**（**仅在一次任务里需要依据全文时才做，且只做一层**）：读图书馆入口 link:README.adoc[] 的「主题登记」表——它按"覆盖的依据"列出主题与覆盖范围，**判断该依据属哪一张表只需读入口这一份**；入口自足，不存在"必须整目录读"的情形（link:README.adoc[]「放哪、怎么用、何时加载」）。**外部标准原文**归 link:sources.adoc[]、**本站取舍/组织约定/准入判定**归 link:adoption.adoc[]、**写入与关联本身**归本文件。
. **取一份主题文件、按依据名定位段落**：主题文件的组织方式就是"一条依据一段"，段首即依据名——按名匹配段落即可，**不读整份也可定位**（如按标准编号 grep 该文件）。
* **终止条件（L1）**：依据链到**标准名/编号**（外部）或**本项目实证/组织约定**（内部）即终止；**图书馆在本次工作区不可达**（在引用方项目里按公共规范执行、或无本仓库文件）时**同样终止**——**不再向下展开**（标准原文不在本仓库，本项目实证的原始记录也在本仓库的既有文档/对话里，不在馆内再套一层）。**不得为找依据而遍历项目、不得把图书馆当全文检索引擎**。
* **依据找不到时的正确做法**（L1）：按 link:../specs/general/source.adoc[]「无法确证时的正确做法」如实标"未确证"并写明已查证方式，**不得用虚构内容填补**，也不得"因为查不到就顺手编一条标准号"（最高关注项：不得编造事实与来源）。

== 三、默认引用面与非引用面（外部项目怎么处理）

**为什么这条必须写清**：整个项目被托管为静态资源，**本仓库所有内容都会被发布出去**（站点见 link:../README.adoc[]）——**不存在"只在本站内"的内容**；区别只在**默认引用什么**：**公共规范**（`AGENTS_COMMON.adoc` + `specs/`）由引用方按入口加载，是**默认引用面**；图书馆（link:README.adoc[] 及其主题文件）**不在默认引用面内**（没有加载项、不被任何入口取到），且**引用方项目的工作区里没有本仓库的文件**（`AGENTS.adoc`「依据图书馆」）。于是同一件事在两类读者面前落点不同：

* **引用方项目（按公共输入执行）**：其行为**不依赖图书馆**——公共内容自足是其底线（link:../AGENTS_COMMON.adoc[]「访问与解析」）；正文里的依据名足够它知其所以然与举一反三（AI 可自行检索标准名）。它**不遍历本仓库、不全文检索**：依据名是检索键，检索面是**它自己的检索能力与公开标准**，不是本项目仓库。**若引用方自己的项目规范也设了依据落点**，按其自身约定处理（link:../PROMPTS.adoc[]「优先级与隔离」已写明该分工）——图书馆不是对引用方的要求。
* **本仓库（维护方与在馆内的执行者）**：按上节算法反查，只取一份文件，**不遍历**。
* **因此正文侧只允许"标准名/编号"这一种入口形态**（L1）：把"到图书馆某主题文件取"写进 `specs/**` 即给出一条引用方走不通的路径（其工作区里没有本仓库的文件、也没有加载项指示去找），也违反公共内容自足；图书馆的路径只出现在 `AGENTS.adoc`（项目规范入口）、根 `README.adoc`、`PROMPTS.adoc`、`PUBLIC.adoc` 与图书馆内部这几处**不属默认引用面**的位置——**不是"这些文件不发布"**（它们同样在站点上，见 link:../README.adoc[]），而是**引用方不按它们加载**。

== 四、引用方怎么准确定位依据（不全量下载）

**问题**：馆**没有限制内容的大小与长度、也没有限制要存的内容的范围**（link:README.adoc[]「放什么、不放什么」），将来可能特别大。于是"另一个项目要查这条依据"时，**不可能把整馆下载下来**，也不能靠"遍历后 grep"——需要一条**可机械执行**的路径，**且在取用侧的现有条件下就能走通**。

**先分清两端（本站失效的根因）**：**作者侧**有本仓库的工作副本（可 `git`、可读工作区）；**取用侧是游客**——**只有 https、没有仓库、没有 git**。协议**只能建立在取用侧成立的条件上**。本仓库**不发布版本号、也不维护"当前 commit 是哪个"的登记**，故凡以"先取 commit / 先取版本号"为前置的路径，**作者自己能走、游客走不通**——本条正是被这个失效逼出来的（把 commit 写进取值路径）。

**解法（三步；落点与取值细节见 link:README.adoc[]「依据的定位协议（入口 + 索引 + 单点取值）」）**：

. **入口（常驻层里的固定地址，不要自己拼地址）**：公共规范（`AGENTS_COMMON.adoc` / `AGENTS.adoc`）指向图书馆入口的那条链接**就是入口**，`https` 直接可达（实测返回**纯文本**）。取用侧**不需要**知道地址形态、**不需要**任何版本号——**这是"取用侧取得到什么"的唯一来源**，故也是全协议唯一必须写进常驻层的落点，且必须是**不随提交滚动的固定地址**。
. **键（依据名 → 文件）**：依据名即**检索键**（正文里只写这一种形态，见本文件「二、依据与规则怎么关联（关联协议）」），由图书馆入口的「主题登记」表映射到**主题文件**——**只读入口这一份**即得映射，不遍历主题目录、不列目录清单。
. **段（文件内的段）**：主题文件按"**一条依据一段**"组织，**段首即依据名**——按名匹配段即可定位，不读整份。落到段即达终止条件（本文件「反查解析算法（只取一份，不遍历）」）。

**文件名不承担定位（短、无语义，L1）**：上一步的"依据名 → 文件"**只由入口登记表解析**，文件名**不是检索键、也不承担内容语义**——故主题文件名取**单个短词、小写 ASCII、不带分隔的说明语**（`sources.adoc`、`usage.adoc` 这形态），**长度上限 32 字符**（含扩展名，与 link:../specs/general/doc-module.adoc[] 的模块文件名上限同口径），**不得**写成"依据的来源与定位协议"这类短语；读者**不需要**"望名知义"，也不该用文件名替代依据名去猜内容（检索键只有依据名）。理由有两条、都在取用侧：①**上下文**——名字会被读进每一次链接与每一次目录列举，长名等于让每个读者反复多读那几个字，而**它并不因此更好用**（馆一大，没人靠文件结构或文件名找依据，都是**从已有内容反查到馆**，触发来自规范正文的依据行）；②**定位可靠性**——名字一旦被当成"查找依据"的依据，改名就会"断档"，而真正的终态是**内容主键**（见下条）。故：把省下的名字用在内容上，馆内**平铺、不建多层子目录**（分类由入口登记表承担），**不改名搬文件也不影响定位**（改名只改登记表一行）。

**主键是内容、不是路径**：文件会改名/搬迁，**内容不会**——Git 按内容寻址（`<commit>:<path>` 给出的是内容 blob 的 sha），**同一份内容在任何路径下是同一个 blob**，改名/搬迁后**旧 blob 仍可按 sha 取回原文**（实测记录见 link:sources.adoc[]「依据的定位与取值」）。故"这条依据具体到哪个文件"的终态答案是**该文件的内容版本**，路径只是"怎么走到它"的中间产物；**commit 也不是取用前置**——默认取**入口所在分支的当前内容**即可定位（要的是"哪儿有这条依据"，不是某个历史快照），**需要钉住某一版时**才由**能取到 commit 的一方**（作者侧、有 git 的调用方）补一次 `git ls-remote` 与 `commit:path` 取值（见 link:README.adoc[]的「版本固化（可选加固，不得写成前置）」一段）。这也是本站**不建编号索引**、也**不发布版本号**的同一理由：入口登记表即索引，"旧依据取回"由 Git 内容寻址保证，而"取用侧先说出 commit"这条**在游客那里永远不成立**（link:adoption.adoc[] 中「图书馆不建编号索引、入口主题表即索引」一条）。

**只取一段（馆特别大时）**：HTTP 的分段取值是标准化动作——发 `Range` 请求头、服务端可满足时回 `206 (Partial Content)` 并只传请求的字节（RFC 7233）。**须如实说明（L1）**：本仓库站点与平台原始文件视图当前**均未实测**到 Range 生效（`Range: bytes=0-99` 仍回 `200` 与整份内容），故现阶段取值以"**取整份文件 + 文件内定位段**"为准；**Range 是托管服务支持时的优化、不是当前可用路径**，引用方要用它须**先在自己那边实测拿到 `206`**，不得假定。

**协议不承载的东西（形态约束，L1）**：入口与本节**只给入口、键与步骤**，**不承载"这条依据在第几行/落在哪个提交"这类派生的落点表**——落点随文件与 commit 变化，写进规范只会立刻过时，也把"内容主键"降级成"行的位置"；**发现落点只许写成不随提交滚动的固定地址**（把具体 commit 或"自取 commit 再拼地址"写进常驻层，等于给取用侧一条它走不通的路径）；**文件名不承担定位**——不用长名/短语式命名承载内容描述、不建多层子目录（见上条「文件名不承担定位」）。本仓库**不提交任何存放这类落点的临时产物**（link:../specs/general/doc.adoc[]「注释与文档」：只把讨论/过程落盘者不收；link:../specs/core/execution.adoc[]「临时产物」：检查清单与扫描中间结果进 `tmp/`、不入馆）。

**终止条件（L1，同上）**：定位到**具体文件与文件内的段**即达终止条件——**不再向下展开**（打包成索引文件、编成编号目录等都会多出第二真源）；**取用侧只凭 https 与常驻层入口就到此为止**（不必也不得为定位依据去克隆仓库、遍历工作区、或先求一个 commit）。**不得为定位依据而遍历项目或整馆下载。**
