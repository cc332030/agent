= 依据的写入与关联（图书馆使用协议）

本文件是依据图书馆的主题之一，也是图书馆的**使用协议**：回答三件图书馆此前没有完整判据的事——① **什么时候该把一条依据写进图书馆、写什么、什么时候不写**；② **依据与规则之间怎么互相关联、怎么反查**；③ **馆可以无限大时，引用方怎么在不全量下载的前提下准确定位到具体哪个文件**。图书馆的落点、放什么不放什么、独立成篇判据见 `library/README.adoc`。

== 为什么需要本协议（本站失效）

* **写入时机此前无判据**：图书馆的边界与"何时该独立成篇"都只回答**形态**问题，不回答**触发**问题（"我现在这条规范/这次决策，要不要入馆""入馆要写哪几项"）。缺触发判据的后果同形：**AI 不主动写**；真写时**写什么全凭发挥**（要么把规则抄一遍、要么只写一行标准名），要么**该写不写**，要么**不该写硬写**（把讨论过程、复述既有结论的段落塞进来）。
* **关联此前只有约定、没有算法**：规则侧给的是"依据名"入口，馆侧给的是"这条标准支撑哪些条目"的逐条映射——方向本来就有，但只到"可按标准名检索"这个人的约定：机器拿到的规范正文里**只有标准名**，没有"到馆里取哪一份"的解析步骤；也没有写明"要不要遍历整个项目去全文检索"（外部项目引入公共规范时**根本不能**这么干）。本协议补上**只取一份、不遍历**的解析算法。

== 一、什么时候该把依据写进图书馆（触发特征）

**判据是问句，不是印象**：**"这条规则/这个决策，将来有人问'它还成立吗'时，需要什么才能回答？"**——需要**回到当初的原始表述或当初的事实**才能回答的，就该有依据落点；只靠"规矩就是这么定的"就能回答的，不必入馆。

命中以下任一即**应当**入馆（L2）：

* **首次引入的规则**：本次新增/调整了一条 L1 或最高关注项条目——其依据（外部标准名/编号、本集合的更严取舍与覆盖点、当初的失效）须有落点，使日后能核对"它今天还成立吗"。
* **有取舍或争议的决策**：在多个方案之间做了选择、或曾被质疑/推翻过——须收**当初的比较与理由**（选了哪个、放弃了哪个、接受什么代价、依据什么）；只写"决定用 X"等于没写依据。
* **首次出现的实证/反例**：本项目真实发生的失效首次被用于支撑某条要求时——须收**失效长什么样**（可复述的现象 + 与要求的对应关系），它是"这条要求针对什么"的可信锚点。
* **外部标准的首次引用**：规范正文首次引用某标准时——须收**该标准的原文摘录或如实标注未取回**、以及"它确实支持哪一条"的映射。
* **技术选型与组织约定**：须收**选型依据与约定来源**，并写明它是本站取舍还是外部规定（后者不得冒充）。

以下情形**不写**（L1）：

* **规则本体的复述**：图书馆**只补依据、不复制规则**——把规范条文抄进图书馆等于制造第二真源。
* **没有出处的观点、推测、印象**：无法确证的结论按 `specs/general/source.adoc` 如实标"未确证"并写明已查证方式；但"标未确证"本身是图书馆要收的内容，不等于"不写"。
* **只把讨论过程落盘的记录**：会议记录、多轮试错的过程、被放弃的中间稿——只留结论与依据。
* **临时产物**：任务进度、检查清单、扫描中间结果按 `specs/core/execution.adoc`「临时产物」进 `tmp/`。
* **靠文件名承载依据内容**：主题文件名只做**唯一标识**，不写内容描述、不写限定语与来源。
* **依据齐备但无人会问"还成立吗"**的常识性做法：如"文件名用 kebab-case"这类无争议的局部约定，落在对应规范正文或代码注释即可。

**写入的落点与形态**：

* **仍在规则所在地承载**（默认，多数情形）：依据与规则**同处一处**最不易漂移（各规范文件自身的说明性段落与依据行、提示词正文、脚本注释）——独立成篇不是"依据必须离开规则所在地"的强制动作。
* **独立成篇**：同时满足"与规则本体分离"与"按依据对谁成立归类"两条判据时才另建主题文件，并在入口登记。
* **入库必写项**：① **出处**（标准名/编号或"本项目实证/组织约定"）；② **逐字原文或如实标注的取样状态**（三类标记：官方文本已取回 / 官方网页已取回 / 未逐字取回）；③ **它支撑哪一条**（写清落点文件与条目，这是反查的锚）；④ **取回方式**（可复取的命令或来源）；⑤ 有取舍/有覆盖点时另写**同义性差异**（标准说了什么、本站加严了什么）。

== 二、依据与规则怎么关联（关联协议）

**关联靠两侧各写一半、互相指向**——两侧都不完整，缺任一侧就查不到：

* **规则侧只写入口**：规范正文/提示词/脚本注释里给出**依据名**（标准名/编号，或"本项目实证"）——**不写全文、不写链接**。依据名就是**入口键**。**本集合的落点约定**：`specs/**`（默认引用的公共规范）只能写**标准名/编号**这一形态；"到本项目图书馆的哪一份主题"只写在维护方的项目规范入口与图书馆内部，**不进默认引用项**——引用方按公共输入执行时取不到它。
* **依据侧写全反查**：图书馆主题文件按**依据**组织（一条依据一段），段内逐条列出它支撑的规范条目，即**使用位置**——这就是**反查表**：拿到依据可反查它被谁用。
* **两侧一致、同一处定义**：同一件事别在两侧展开；**依据只压缩为名称/编号、不得整段删除**——正文里删掉依据名，馆里那段就再也无人反查到，等于依据不存在。

=== 反查解析算法（只取一份，不遍历）

**目标**：从**规范正文**出发，只读**一份**文件就走到依据；**不遍历项目、不做全文检索**。五步：

. **（前置）判断馆是否可达**：图书馆路径**相对仓库根**书写，它**不在默认引用面内**，且执行者未必工作在本仓库内。故**先在工作区里看它是否真的可达**：**可达**（= 工作在本仓库内）才继续下一步；**不可达**（= 在引用方项目里按公共规范执行）即按终止条件停止——正文里的依据名已足够，不必也**不得**为取依据去克隆本仓库或遍历工作区。
. **取依据名**：读规范正文中该条目的依据行。这是本次唯一需要的检索键。
. **判定依据类型**：是**外部标准**还是**本站取舍/实证**（正文的措辞已区分）。
. **定位图书馆的对应主题**（仅在一次任务里需要依据全文时才做，且只做一层）：读图书馆入口的「主题登记」表——它按"覆盖的依据"列出主题与覆盖范围，**判断该依据属哪一张表只需读入口这一份**。
. **取一份主题文件、按依据名定位段落**：主题文件的组织方式就是"一条依据一段"，段首即依据名——按名匹配段落即可，**不读整份也可定位**。
* **终止条件（L1）**：依据链到**标准名/编号**（外部）或**本项目实证/组织约定**（内部）即终止；**图书馆在本次工作区不可达**时**同样终止**——不再向下展开。**不得为找依据而遍历项目、不得把图书馆当全文检索引擎**。
* **依据找不到时的正确做法（L1）**：按 `specs/general/source.adoc`「无法确证时的正确做法」如实标"未确证"并写明已查证方式，**不得用虚构内容填补**，也不得"因为查不到就顺手编一条标准号"。

== 三、默认引用面与非引用面（外部项目怎么处理）

**为什么这条必须写清**：整个项目被托管为静态资源，**本仓库所有内容都会被发布出去**——**不存在"只在本站内"的内容**；区别只在**默认引用什么**：

* **引用方项目（按公共输入执行）**：其行为**不依赖图书馆**——公共内容自足是其底线；正文里的依据名足够它知其所以然与举一反三。它**不遍历本仓库、不全文检索**：依据名是检索键，检索面是**它自己的检索能力与公开标准**。若引用方自己的项目规范也设了依据落点，按其自身约定处理——图书馆不是对引用方的要求。
* **本仓库（维护方与在馆内的执行者）**：按上节算法反查，只取一份文件，**不遍历**。
* **因此正文侧只允许"标准名/编号"这一种入口形态（L1）**：把"到图书馆某主题文件取"写进 `specs/**` 即给出一条引用方走不通的路径（其工作区里没有本仓库的文件、也没有加载项指示去找），也违反公共内容自足；图书馆的路径只出现在**不属默认引用面**的位置——**不是"这些文件不发布"**，而是**引用方不按它们加载**。

== 四、引用方怎么准确定位依据（不全量下载）

**问题**：馆**没有限制内容的大小与长度**，将来可能特别大。于是"另一个项目要查这条依据"时，**不可能把整馆下载下来**，也不能靠"遍历后 grep"。

**先分清两端（本站失效的根因）**：**作者侧**有本仓库的工作副本；**取用侧是游客**——**只有 https、没有仓库、没有 git**。协议**只能建立在取用侧成立的条件上**。本仓库**不发布版本号、也不维护"当前 commit 是哪个"的登记**，故凡以"先取 commit / 先取版本号"为前置的路径，**作者自己能走、游客走不通**。

**解法（三步；落点与取值细节见 `library/README.adoc`「依据的定位协议」）**：

. **入口（常驻层里的固定地址，不要自己拼地址）**：公共规范指向图书馆入口的那条链接**就是入口**，`https` 直接可达（实测返回**纯文本**，即未经装配的仓库字节）。取用侧**不需要**知道地址形态、**不需要**任何版本号——这是"取用侧取得到什么"的唯一来源，故也是全协议唯一必须写进常驻层的落点，且必须是**不随提交滚动的固定地址**。
. **键（依据名 → 文件）**：依据名即**检索键**，由图书馆入口的「主题登记」表映射到**主题文件**——**只读入口这一份**即得映射，不遍历主题目录、不列目录清单。
. **段（文件内的段）**：主题文件按"**一条依据一段**"组织，**段首即依据名**——按名匹配段即可定位，不读整份。落到段即达终止条件。

**文件名不承担定位（短、无语义，L1）**：上一步的"依据名 → 文件"**只由入口登记表解析**，文件名**不是检索键、也不承担内容语义**——故主题文件名取**单个短词、小写 ASCII、不带分隔的说明语**，**长度上限 32 字符**（含扩展名），不得写成"依据的来源与定位协议"这类短语；读者不需要"望名知义"，也不该用文件名替代依据名去猜内容。理由有两条、都在取用侧：① **上下文**——名字会被读进每一次链接与每一次目录列举；② **定位可靠性**——名字一旦被当成"查找依据"的依据，改名就会"断档"，而真正的终态是**内容主键**。故馆内**平铺、不建多层子目录**（分类由入口登记表承担），**改名搬文件也不影响定位**（改名只改登记表一行）。

**主键是内容、不是路径**：文件会改名/搬迁，**内容不会**——Git 按内容寻址，同一份内容在任何路径下是同一个 blob，改名/搬迁后**旧 blob 仍可按 sha 取回原文**。故"这条依据具体到哪个文件"的终态答案是**该文件的内容版本**，路径只是"怎么走到它"的中间产物；**commit 也不是取用前置**——默认取**入口所在分支的当前内容**即可定位，需要钉住某一版时才由**能取到 commit 的一方**补一次 `git ls-remote` 与 `commit:path` 取值。

**只取一段（馆特别大时）**：HTTP 的分段取值是标准化动作——发 `Range` 请求头、服务端可满足时回 `206 (Partial Content)` 并只传请求的字节（RFC 9110；该标准明写服务端 `MAY ignore` 该请求头）。**须如实说明（L1）**：本仓库站点与平台原始文件视图当前**均未实测**到 Range 生效，故现阶段取值以"**取整份文件 + 文件内定位段**"为准；**Range 是托管服务支持时的优化、不是当前可用路径**。

**协议不承载的东西（形态约束，L1）**：入口与本节**只给入口、键与步骤**，不承载"这条依据在第几行/落在哪个提交"这类派生的落点表；**发现落点只许写成不随提交滚动的固定地址**；**文件名不承担定位**。本仓库**不提交任何存放这类落点的临时产物**。

**终止条件（L1，同上）**：定位到**具体文件与文件内的段**即达终止条件——不再向下展开（打包成索引文件、编成编号目录等都会多出第二真源）；**取用侧只凭 https 与常驻层入口就到此为止**。**不得为定位依据而遍历项目或整馆下载。**
