= 执行吞吐的依据（轮次是上下文的乘数）

本文件是依据图书馆的主题之一，承载**"Agent 为什么慢、为什么要把执行轮次当成本来管"**这一条依据：它**只对本项目成立的实证**（一次真实任务的用量与耗时拆解）与**业界权威实践**（上下文工程的注意力预算）。规则本体落在 `specs/general/context.adoc`「执行吞吐」，本文件不复制规则。

== 当初要解决的失效（本项目实证）

用户报告："Agent 跑得很慢，检查一下有没有优化点……主要是要提高速度，太慢了现在"。**慢的是墙钟，不是模型**——把一次真实任务（Issue 评论派发、同一执行者）的平台侧用量与阶段耗时拆开后：

[cols="1,1,1,3", options="header"]
|===
| 构建号 | 模型请求数 | 输入 token | 墙钟拆解

| `cnb-eb8-1k2q570bv` | 180 | 175 万 ~ 239 万 | 总计 1659 s，其中**模型生成 580 s（35%）**、轮次之间的工具执行与等待约 1084 s（**65%**）
| `cnb-k7g-1k2q7hgk1` | 157 | 167 万 ~ 175 万 | 总计 979 s，模型生成 443 s，其余为轮次间隔
| `cnb-ghg-1k2qcchcp` | 135 | 168 万 | 总计 470 s（该次以模型往返为主）
| `cnb-o88-1k2qe8ev5` | 26 | 114 万 | 总计 76 s（**把同样的校验做完，只用了 26 次请求**）
|===

（数据来源：平台侧「流水线 AI 用量汇总」的 `prompt_tokens` / `request_count` / `generation_duration_ms`，与「构建状态」各阶段 `duration`；**请求数少、墙钟短**的那次与请求数多、墙钟长的那次做的是同类工作，差异来自任务被切成了多少轮。）

推导出的两条事实，构成本条规则的由来：

* **轮次是上下文的乘数**：每次请求都**重发一遍整段上下文**——同一份工作被切成 N 轮，就付 N 次全上下文输入（实测输入 token 总量 175 万，而模型真正产出的只有 3.1 万 token，输入 ÷ 产出约 **56 : 1**）。故"少绕"与"少读"是同一件事的两面。
* **墙钟在轮次之间，不在模型里**：该次任务的轮次间隔合计约 1084 s，**其中 28 段间隔超过 10 s、合计约 859 s**（最长一段近 100 s）——这些是工具执行、命令重启、状态轮询与"先看一步再决定下一步"的试探式往返。把可合并的调用合并、一次取到构建输出，直接削掉的是这 65%。

== 同一次观察里的另两处形态（支持"超时与进展可判定"）

* `cnb-o9q-1k2qgm38e`：流水线停在 `pending`、`npc go` 阶段耗时 **0** 已推进 3038 s（50 分钟以上）——"在跑"与"卡住"无法分辨，只能人工中止。这是"每次执行须有可判定的超时"那条的现场。
* `cnb-o5o-1k2qem0e6`：运行 2010 s 后**以 `error` 结束**（不是超时、不是校验失败），属"长流程没有可判定的收敛信号"的另一面——同样的墙钟代价换来零信息。

== 同义性差异与覆盖点（本集合自己承认的）

* **"合并调用"不是标准规定**：外部材料讲的是**上下文工程**（怎么让模型在有限注意力里保持高信号），**未**规定"互相无依赖的调用必须一次批量发出"这类执行侧判据——**本条是本集合按现场用量把"轮次成本"判据化的结果**：外部材料解释"为什么越长越差"，本条补"在给定执行环境里怎么少付"。判定标准（一次调用只做一件事、且下一件事在动手前就已可判定，即违规）也属本集合自定。
* **量级只对本项目/本执行环境成立**：上面的请求数、token 数与时间占比取自本平台的真实流水线，**环境、任务规模、模型都变了这些数字就会变**；可复用的是一个**比值形态**（输入 token 远大于产出 token、墙钟主要落在轮次间隔），不是具体数值。
* **镜像就近与"已配置过即不重配"**：下载量大的依赖选就近镜像站这一条，本项目已在 Maven 侧单独判据化（见 `specs/stack/maven.adoc`「仓库与镜像」）；本主题只解释"为什么反复重试/重配本身也是轮次成本"，不另行给选源判据。
* **凭据固化用的是各平台自己的机制**：本条只要求"开始时固化一次、后续复用"，**不指定**用什么形态——平台机制属执行环境，公共内容不替它规定。

== 业界依据（权威实践）

* **Anthropic 工程博客《Effective context engineering for AI agents》**：上下文是**有限资源**（注意力预算），token 越多召回与长程推理越差（业界称 context rot），故应只加载必要的高信号内容。本集合的"读取最小必要"用其前半段，本主题的"轮次是乘数"用其后半段——**每多一轮，整段上下文被重发一次**，代价随会话变长而放大。（博客为业界实践声明，**非标准**。）
* **Agent Skills 开放规范**：progressive disclosure（渐进披露）——技能与说明按需加载、不做全量预载；本集合的懒加载调度器与图书馆定位协议同源。（规范为业界约定，**非 ISO/IEC 标准**。）
* **ISO/IEC/IEEE 25010（性能效率）**：性能是质量属性、须可度量与可核对——本主题因此把"几轮、多少 token、墙钟落在哪"写成可核对的现场取值，而不是"感觉慢"。
