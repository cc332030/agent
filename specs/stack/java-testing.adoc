= Java 测试规范（技术栈层，JUnit）

适用于 **Java 项目**的测试（JUnit 5）。公共测试设计原则见 `specs/general/testing.adoc`；本文件只收录 Java/JUnit 专属规则。加载触发特征：项目存在 `.java` 源文件、测试依赖（JUnit 等）。涉及 Spring/Spring Boot 的启动型测试（`BootTests`）须一并加载 `specs/stack/spring.adoc`。

本文件把测试分成五类并给出各自的后缀**推荐**：分类与后缀是**全项目统一的推荐名**，照着走能让类别与构建工具的执行边界天然对齐；命名不自洽会让测试被构建工具误跑、误跳过或误判为失败，故**推荐**沿用、自造后缀时须在构建配置一侧自行兜住执行边界。**五类后缀一律以 `Tests` 结尾**，取值全部命中 JUnit 自己的类名规则（JUnit 平台默认类名过滤 `^(Test.*|.+[.$]Test.*|.*Tests?)$`）；规范里不出现任何不命中这条规则的推荐名。**名字只管类别、不管执行**：`*Tests` 全部落在 Maven Surefire 的默认 includes 内，「谁跑它」由构建配置与 JUnit 自己的标记（`@Tag`/`@Disabled`）决定（见下「测试分类与执行边界」）。

== 框架与目录

* **测试框架**：单元测试使用 JUnit 5。
* **目录结构与包路径（L1 强制）**：测试类（`src/test/java`）的**包路径与对应源类（`src/main/java`）保持相同**，不额外加 `test` 段等路径层（源类 `com.example.core.util.StringUtils` 的测试类应位于同包 `com.example.core.util`）；**并须为同一目录**——同一包路径在源码树中只允许出现一处与测试树中一处，不得为区分测试类再追加包路径层级。

== 测试类命名（推荐）

测试类名**推荐**用「**被测类名 + 测试类型后缀**」（如 `StringUtils` → `StringUtilsTests`），以此与源类区分；这是**推荐、非必须**——类名允许自定义（如按分类限定语命名 `CCacheAspectCacheKeyTests`）。**AI 生成测试类名时用默认名字**（AI 生成的默认名字＝「被测类名 + 测试类型后缀」，见下「AI 生成时的默认名字」）。**每个被测对象一对一（推荐，与「可拆」并存）**：一个被测类**首选**一个 `<被测类名><后缀>` 测试类；确按需求/分类拆分时见下条（拆分同样合规）。后缀按**测试运转形态**选用，**优先级自下而上**——能跑常规单元测试就走 `Tests`：

[cols="1,2,2,2", options="header"]
|===
| 后缀 | 承载什么 | 何时用 | 是否纳入常规 `test` 阶段

| `<被测类名>Tests` | 可执行、可重复运行的常规测试：单元测试、切片测试、以及需要容器但能自启的集成测试（`@SpringBootTest`、Testcontainers） | **默认**，只要不违反"独立、可重复、无外部人工依赖" | 是（surefire 默认 includes 收走）
| `<被测类名>BootTests` | 需 Spring Boot 启动类承载、须特定 profile/环境/启动参数（嵌入式容器、测试专用数据源与配置）的启动型测试 | 不能与普通测试同一次启动跑通、须显式指定启动方式 | 是，但**须按 Boot 方式启动**（`@Tag("boot")` 分组）
| `<被测类名>PerfTests` | 性能/基准对比测试（`perf`） | 对比性能的基准与方案对比（公共规范「性能测试」要求） | **否**——须在构建配置里排除（`excludedGroups` 或 `excludes`）、独立触发
| `<被测类名>IntegrationTests` | 端到端/冒烟，依赖部署好的真实外部环境（真实 DB/消息队列/第三方服务/已运行的应用） | 无法自包含、必须有外部环境才能跑通 | **否**——须在构建配置里排除，由独立执行（Maven Failsafe 等 IT 插件）承接
| `<被测类名>SandboxTests` | 留在 `src/test/java` 下、但**任何构建/CI 阶段都不得自动执行**的实验/复现代码——随手试验、临时复现、跑一遍看结果的脚本式用例 | 写的时候就不打算让它进任何自动执行集合（与"要不要测"无关） | **否**——类级 `@Tag("sandbox")` + 构建配置排除 + 类级 `@Disabled`，三重落点
|===

* **不用默认名字时，须能读出类别（推荐）**：类名用默认名字，或**自定义**（含加分类限定语，如 `CCacheAspectCacheKeyTests`、`CBeanUtilsDeepCopyTests`）都可以——**自定义不是违规**；**推荐**使类名仍能读出被测对象与类别（推荐形态＝默认名字里带上表某一类后缀），好让人与工具一眼看出它测什么、归哪一类。
* **AI 生成时的默认名字（推荐）**：AI 新建测试类**用默认名字**——被测量的类若叫 `StringUtils`，生成的测试类就叫 `StringUtilsTests`（Java 源类与测试类常同名，此时**依赖 `Tests` 后缀与源类区分**）；不得因"名字与源类太像"改用别的写法。用户或项目另有命名约定时按其取值。
* **后缀沿用上表的五类（推荐）**：新增测试**推荐**归入上表某一类，**不另造上表之外的后缀**——**这是推荐、不是禁令**，照着走能让类别与构建工具的执行边界天然对齐；**自造后缀时该测试可能被误跑、误跳过或误判为失败**（它的执行边界只能全靠构建配置兜，没有任何默认值可依）。**构建配置一侧的取值不变（L1）**：要进常规 `test` 阶段的测试须用 surefire 能识别的默认名字（`Test*`/`*Test`/`*Tests`/`*TestCase`），否则须在构建配置里显式列入、并注明依据。确有一种测试无法归入上表时，先按项目自身规范（或与维护方约定）的准入判定处理（判定是否真为新形态、给出执行边界），再动手写类。
* **`SandboxTests` 是"永不自动执行"的唯一后缀（L1）**：留在 `src/test/java` 下、但**任何构建/CI 阶段都不得自动执行**的代码，后缀**一律**用 `SandboxTests`（如 `OrderServiceSandboxTests`）。**取名口径**：不叫 `Manual*`/`*ManualTests` 一类"手动"字样的名字——"手动"描述的是**怎么跑**（同样可以手工触发 `IntegrationTests`、`PerfTests`），而这一类要表达的是**任何自动集合都不许收它**，故取"沙盒"这一语义：写在这里的代码就是隔离在自动执行之外、自己跑着看的，不承担任何自动执行的契约。
* **命名面只取 JUnit/Maven 约定内的名字（L1）**：上表五类后缀**一律以 `Tests` 结尾**，全部命中 JUnit 平台的默认类名过滤（`^(Test.*|.+[.$]Test.*|.*Tests?)$`）与 Maven Surefire 的默认 includes（`**/Test*.java`、`**/*Test.java`、`**/*Tests.java`、`**/*TestCase.java`），**规范里不出现任何不命中它们的推荐名**。**判定标准（任一命中即违规）**：① 上表出现一个**不命中**上面那条默认类名规则（不以 `Test` 开头、也不以 `Test`/`Tests`/`TestCase` 结尾）的后缀；② 正文把某个不命中默认 includes 的后缀写成**命名推荐**；③ 为让某类测试"不进常规阶段"而改用认不出的名字——那是把名字当执行开关，见下条。
* **执行边界不靠名字承担（L1）**：名字只说「它是什么」，「谁跑它」一律落在**构建配置 + JUnit 自己的标记**上——`Tests`/`BootTests` 由 surefire 默认 includes 收走；`PerfTests`/`IntegrationTests` 虽同样命中默认 includes，但**须在构建配置里显式排除**（surefire `excludedGroups` 含对应 `@Tag`，或 `excludes` 含对应文件模式），再由独立执行承接（Maven Failsafe 的 `includes` 显式列入 `**/*IntegrationTests.java`、`perf` 走独立 profile）。**判定标准（任一命中即违规）**：① **靠换名来换执行阶段**——某类的名字换成不命中默认类名规则的形态后就不再有构建配置侧的排除或单独 includes，它的执行边界实际由那个名字承担；② 某一类既没在构建配置里排除、也没有单独的 includes，靠"记得别跑它"守住；③ 某类的执行范围只写在某个人的命令行历史里。
* **`SandboxTests` 的执行边界须三重落点（L1）**：光有名字不够——它与其他四类一样命中 surefire 默认 includes，故须**三层同时成立**：① **类级 `@Tag("sandbox")`** 作分类标识；② **surefire 与 failsafe 的 `excludedGroups` 都含 `sandbox`**，让它根本不被扫进任何自动集合（统计里也不出现）；③ **类级 `@Disabled("原因")`**，保证"即使被某个自定义 includes 扫到，用例也不会执行"——**它的边界要写清**：类级 `@Disabled` 只挡用例方法与方法级回调，**不挡类的实例化与 `@BeforeAll`/`@AfterAll`**（JUnit 官方文档明说），故它是最后一层兜底、不能拿来替掉前两层。三层各挡一种失效：① 编造不出筛选口径、② 自定义扫描把它收进来、③ 配置被改坏后被真跑一遍。**判定标准（任一命中即违规）**：① 该类出现在任一自动执行集合（`mvn test`/`verify`/CI 流水线跑到了它）；② 上述三层缺任一层；③ 为让它"不跑"而把它移除出 `src/test/java`（那就不是这一类了——留在这里、用名字 + 标记 + 配置隔离，才是这条的形态）。
* **`SandboxTests` 不得混入其他后缀（L1）**：一个类要么是 `SandboxTests`、要么是 `Tests`/`BootTests`/`PerfTests`/`IntegrationTests`，**不得**同时带上（如 `XxxSandboxIntegrationTests`、`XxxTestsSandbox`）——混出来的名字读不出归属，执行边界当场变成"看谁先扫到"。
* **`BootTests` 中的 B 大写**（`Boot` + `Tests`）。
* **存量随动迁移、不一次性收敛**：不合上述包路径与命名的存量测试类**不发动全库改造、不要求一次性改齐**（见 `specs/core/execution.adoc`）——**碰到哪个改哪个**：该测试类本次因需求而变动时，随动调整为定式（重命名按 `specs/general/git.adoc`「文件移动与重命名」用 `git mv` 保留历史）；本次不变动则保持原样。用户明确要求一次性全库收敛时按其声明执行。
* **测试类不存在时**须按上述包路径**新增**；类名用**默认名字**（"被测类名 + 测试类型后缀"），或按项目/用户既有约定命名（**两种都合规**）。
* **一个被测类的测试可拆成多个测试类，但只按需求/分类拆、不按场景滥拆（L2）**：同一被测类可按**需求**（用户提出的不同测试诉求）或**分类维度**（业务功能、行为类别、外部依赖形态）拆成多个测试类。**拆分后的每个类都须自足**：类名用默认名字、或在默认名字外加**分类限定语**表明该类管哪一类（如 `OrderServiceCreateTests`、`CCacheAspectCacheKeyTests`），类级文档注释声明本类覆盖的分类，且**分类之间不得重叠**。
* **分类或属性相同的用例必须归入同一个测试类（L1，与类名无关）**：同一分类（同一需求/同一行为类别/同一 `@Nested` 主题）或同一属性（同类前置条件、同类外部依赖、同类数据形态）的用例**不得拆到多个类**，须用 `@Nested`/用例分类就地组织；**不得为"每个用例一个类""每个场景一个类"而拆**（**禁止滥拆**）。**一个被测类同时有多类测试时，各类各一个类**（如 `OrderServiceTests` + `OrderServiceIntegrationTests`），不得合并成一个类后混用标签。**判定标准（命中即过度拆分）**：拆出的多个类**分类维度说不清**、**用例可在类间任意搬动**、或**每类只有一两个用例且无独立分类含义**。

== 测试分类与执行边界

* **常规测试类的取舍顺序**：先判定测试**是否自包含**（不依赖外部人工准备的环境、不依赖外部服务、可重复执行）。自包含 → `Tests`；确需容器/外部服务但能由测试自身启动（`@SpringBootTest`、Testcontainers、嵌入式实现）→ 仍用 `Tests`；**不能自包含、须人工准备真实环境** → 才用 `IntegrationTests`（依据：ISTQB Glossary 的 "test double"/"integration testing"；JUnit 的 `@Tag` 过滤机制）。
* **`SandboxTests` 与上面这条取舍无关**：这一类判的不是「能不能自包含」，而是**写的时候就不打算让它进任何自动执行集合**——即便它能自包含、跑起来也很快，只要作者的意图是「只自己跑、不许任何自动阶段碰」，就用 `SandboxTests`；反之，凡是**该被自动验证**的，一律归 `Tests`（不得为图省事用 `SandboxTests` 让它逃过 CI）。
* **BootTests 的启动型判定**：满足任一即归 `BootTests`——① 须由 Spring Boot 启动类/完整上下文承载，且**不能与常规测试在同一次启动内跑通**（须单独指定 profile/环境/启动参数）；② 需要测试专用启动依赖（嵌入式容器、测试专用数据源/配置）；③ 被启动的应用本身包含需隔离的初始化。**仅"用了 `@SpringBootTest`"不构成 BootTests**——能自启、可重复的 Spring 测试仍属 `Tests`。
* **类标识与过滤的配套（L2）**：可按分类在类上打标记（`@Tag("boot")`/`@Tag("perf")`/`@Tag("integration")`/`@Tag("sandbox")`），**只作分类标识、不替代后缀**（后缀才是类别判据；打了标记不改类别的归属）。这些标记**正是执行边界的抓手**：构建配置按标记写 `excludedGroups`/`includeTags`（见下条），故标记值须与后缀一一对应、不得各自发挥。
* **执行要求（L1）**：`PerfTests`、`IntegrationTests`、`SandboxTests` 均**不得**混入常规 `test` 阶段的执行集合——三者都命中 surefire 默认 includes，故**一概须在构建配置里排除**，不靠名字天然落空也不靠人工记忆：`PerfTests` 与 `IntegrationTests` 由 surefire 的 `excludedGroups` 排除、再以独立方式执行（`IntegrationTests` 由 Maven Failsafe 的 `includes` 显式列入，`PerfTests` 走独立 profile 显式触发）；`SandboxTests` 由 surefire/failsafe 的 `excludedGroups` 排除、**没有任何自动执行入口**（见「测试类命名」的「执行边界须三重落点」）。
* **构建配置落点（L2）**：surefire/failsafe 的 includes/excludes/`excludedGroups` 与 `@Tag` 分组须在 `pom.xml`（或 `build.gradle`）中显式配置并注释写明依据（测试分类 → 执行阶段 → 命令）；配置只允许"把某类测试放进对应阶段、把某类排除出某阶段"，不得借配置放宽"`PerfTests`/`IntegrationTests` 不随常规测试执行"这一条。

落点一览（取值以构建配置为准，此处只给对应关系）：

[cols="1,1,2", options="header"]
|===
| 后缀 | 类级标记 | 执行边界落点（构建配置侧）

| `*Tests` | 无（默认） | 无须配置——surefire 默认 includes 收进 `test` 阶段
| `*BootTests` | `@Tag("boot")` | 随 `test` 阶段执行；须按 Boot 方式启动时，surefire `<groups>` 或 `-Dgroups=boot` 选定
| `*PerfTests` | `@Tag("perf")` | surefire `<excludedGroups>perf</excludedGroups>`；独立 profile 用 `-Dgroups=perf` 显式触发
| `*IntegrationTests` | `@Tag("integration")` | surefire `<excludedGroups>integration</excludedGroups>`；failsafe `<includes><include>**/*IntegrationTests.java</include></includes>`
| `*SandboxTests` | `@Tag("sandbox")` + `@Disabled("原因")` | surefire 与 failsafe 的 `<excludedGroups>` 都含 `sandbox`；**没有任何 include 入口**
|===


== 扩展新测试类型（新增后缀前先过准入）

出现上表未覆盖的测试形态时，**不得就地自创后缀**，按项目自身规范（或与维护方约定）的准入判定流程处理：① 先判定是否**真为新形态**（多数情况只是"该用 `Tests` 还是 `IntegrationTests`"的归类问题、"永不自动执行"这一类已由 `SandboxTests` 覆盖）；② 确需新后缀时，给出形态判据（何时用/何时不用）、执行边界与**业内既有约定或标准依据**；③ 扩表后同步落点：本文件表格、机械校验、公共测试规范、CHANGELOG（若影响引用方项目）。

可选形态与候选后缀（**仅作备选示意，不是规范许可用后缀**）：

* **架构与依赖结构测试**（ArchUnit 等）：并入 `Tests`，类名由自身语义决定。
* **契约测试**（Pact、Spring Cloud Contract 等）：消费方校验并入 `Tests`；需要提供者或代理服务才能跑的组合测试归 `IntegrationTests`。
* **消费方驱动的端到端验收**：归 `IntegrationTests`；确需与"技术集成冒烟"区分时，先按准入判定扩表。
* **迁移/一次性校验测试**：写成测试方法（**以后还要再验一次的场景一律如此**，见下条）；确属一次性、不会再跑的才写成独立一次性校验程序，不为其新增测试类后缀。
* **用例只在本机跑（Java 侧的载体，不构成 Java 专属规则）**：判据本体（本机之外不依赖任何电脑/服务器、判据问句、唯一例外、判定标准、边界与存量口径）见 `specs/general/testing.adoc`「环境与兼容」，本节只答"落到哪些配置项"：① **替代品优先选进程内**——内存数据库（H2 等）、嵌入式服务、进程内假实现；确需独立进程时起在**本机回环地址**（`127.0.0.1`、`localhost`）、端口由测试自选不写死共享环境；② **不得把远端地址写进测试配置**——含内网 IP、域名、共享环境的连接串与凭据；③ **`IntegrationTests` 同样受此约束**：它是"独立执行的一类测试"、不是"可以去连远端环境"的许可（两者是不同维度，别互相顶替）。
* **断言把落点限在本机（Java 侧的载体，不构成 Java 专属规则）**：判据本体（判据问句、断言形态、判定标准、边界与例外）见 `specs/general/testing.adoc`「环境与兼容」，本节只答"断言落在哪、怎么取地址"：① 断言写在**共用**的位置（基类/扩展/共享夹具），让同一套里每个发出的请求都过一遍，不必逐条重复；② 取值来自**运行时**——把配置里那个地址解析成 `InetAddress`，判 `isLoopbackAddress()`，**不比** `"localhost"`、`"127.0.0.1"` 这类字面量（`localhost` 只是名字、落点由解析结果决定）；③ **命中即失败**：断言的就是"越界"这件事，发现非回环即让这条用例红；解析不出地址同样按失败处理、不得静默跳过；④ **连得上目标服务不构成豁免**——"远端也能连通"说明它本来就在本机之外，是违规的证据而不是理由。
* **验证场景要复用就写成测试方法（Java 侧的载体，不构成 Java 专属规则）**：通用判据（判据问句「这个场景以后还要不要再验一次」、会重复就写成用例、只有一次性才可留临时产物、判不准按会重复、随动迁移）见 `specs/general/verify.adoc`「编译/运行验证」（判据不因语言而变）；本节只答"这句话在 Java 工程里对应到哪个文件、哪种形态"，判据取值一律回那边看：① **落点**——`src/test/java` 下的测试类里，按分类编号写进类级文档注释、用例方法带断言；② **不得落在**——`tmp/`、`/tmp`、随手写的 `verify.sh`/`demo.py`、`main` 里的 `main` 方法或 `CommandLineRunner`；③ **真不该进自动阶段的**——`SandboxTests` 后缀（见本节「测试类命名」），**不得**为此留在 `tmp/`。

== 断言

* **异常断言用 `assertThrowsExactly` 精确匹配异常类型**，不用 `assertThrows`（避免父类异常掩盖子类语义）。

== 用例编写

* **测试代码与主代码同等遵守全部 Java 规范**（`specs/stack/java.adoc`）：lombok 使用、构造器/字段修饰符、对象创建、命名与注释、工具类等一律按主代码标准执行；语言层面按项目目标版本约束，禁用项目目标版本不支持的新语法糖。
* **按公共测试规范跳过某参数的异常输入用例时，该参数必须标注 `@NonNull` 注解写明约定**，防止后续误判为可空、再次生成异常输入用例。
* **涉及 lombok 等语法糖时注意实际展开结果**（`val` 的类型推断），避免用例预期与实际不符。
* **含 null 元素的集合字面量需显式泛型**（`Arrays.<Integer>asList`），避免类型推断歧义。
* **依赖反射/序列化（Jackson、hutool 等）的测试注意资源释放**（generator 需 close）与构造器可见性（反射默认只取 public 构造器）。

== 执行与验证

* **验证以 Maven 结果为准**（surefire 的 `Tests run/Failures/Errors/Skipped` 统计），具体见 `specs/stack/maven.adoc`。
* **按类别分别取统计**：常规测试看 surefire 统计，`IntegrationTests` 看 failsafe 统计（`verify` 阶段），`PerfTests` 看性能测试自身的对比结果（不并入常规测试结论），`SandboxTests` **不在任何统计里**（它不被执行，`Skipped` 也不该出现——出现了就说明排除失效）；哪一类没跑就**不得**声称其通过。

== 启动型与端到端测试

* **`BootTests`（Spring Boot 启动型）**：须有 Spring Boot 启动类/完整上下文承载，测试专用配置（profile、数据源、嵌入式容器）放**测试资源**（`src/test/resources`）或测试内部配置类，**不得**改主代码配置迁就测试；启动失败的用例须给出可诊断的启动日志（不得静默 `catch` 后跳过）。命名与被测类一对一（如 `OrderApplicationBootTests`）。
* **`IntegrationTests`（端到端/冒烟）**：依赖**外部已就绪环境**（真实 DB/消息队列/第三方服务/已部署应用），须在测试类或项目配置中**显式标注环境依赖**（所需服务、连接方式、缺失时如何跳过），环境不可用按其声明跳过并**在验证结论中如实说明未执行**（不得记为通过）；用例围绕端到端业务路径与冒烟场景，不做穷举覆盖。
* **`PerfTests`（性能）**：测量与记录要求统一见 `specs/general/testing.adoc`「性能测试」，本节不重复其判据。Java 专属落点只有两点：① **类名与承载**按 `<被测类名>PerfTests`（`perf`），**不混入常规 `test` 阶段**、仅在显式触发时执行；② **结果与结论写进该类的文档注释**（类上放方案目录、测量口径与结论，方法上放细节），**跨类/功能级**的内容进独立性能测试文档；结果分析须写明对比的各类实现与原因。

== 覆盖与变异测试

* **覆盖率统计用 JaCoCo**（`jacoco-maven-plugin`），排除 lombok 生成、getter/setter、POJO/DTO/VO 样板等自动生成的代码（`excludes` 配置），只统计手写业务逻辑；公共测试规范「覆盖率与充分性」中分支覆盖率 ≥ 80% 的要求，Java 中对应 JaCoCo 的 branch coverage 指标。
* **变异测试用 PIT**（`pitest-maven-plugin`），对关键/高风险代码（核心业务逻辑、安全敏感、数据转换）执行变异测试，评估突变得分；PIT 的存活变异体须按公共测试规范「测试有效性」逐个分析处理。
