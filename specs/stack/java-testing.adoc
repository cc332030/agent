= Java 测试规范（技术栈层，JUnit）

适用于 **Java 项目**的测试（JUnit 5）。公共测试设计原则见 `specs/general/testing.adoc`；本文件只收录 Java/JUnit 专属规则。加载触发特征：项目存在 `.java` 源文件、测试依赖（JUnit 等）。涉及 Spring/Spring Boot 的启动型测试（`BootTests`）须一并加载 `specs/stack/spring.adoc`。

本文件的测试分类与后缀是**全项目统一的命名契约**：命名不自洽会让测试被构建工具误跑、误跳过或误判为失败，故后缀不得自创。

== 框架与目录

* **测试框架**：单元测试使用 JUnit 5。
* **目录结构与包路径（L1 强制）**：测试类（`src/test/java`）的**包路径与对应源类（`src/main/java`）保持相同**，不额外加 `test` 段等路径层（源类 `com.example.core.util.StringUtils` 的测试类应位于同包 `com.example.core.util`）；**并须为同一目录**——同一包路径在源码树中只允许出现一处与测试树中一处，不得为区分测试类再追加包路径层级。

== 测试类命名（L1 强制）

测试类名一律为「**被测类名 + 测试类型后缀**」（如 `StringUtils` → `StringUtilsTests`），以此与源类区分。**每个被测对象一对一**：一个被测类对应一个 `<被测类名><后缀>` 测试类。后缀按**测试运转形态**选用，**优先级自下而上**——能跑常规单元测试就走 `Tests`：

[cols="1,2,2,2", options="header"]
|===
| 后缀 | 承载什么 | 何时用 | 是否纳入常规 `test` 阶段

| `<被测类名>Tests` | 可执行、可重复运行的常规测试：单元测试、切片测试、以及需要容器但能自启的集成测试（`@SpringBootTest`、Testcontainers） | **默认**，只要不违反"独立、可重复、无外部人工依赖" | 是（surefire 执行）
| `<被测类名>BootTests` | 需 Spring Boot 启动类承载、须特定 profile/环境/启动参数（嵌入式容器、测试专用数据源与配置）的启动型测试 | 不能与普通测试同一次启动跑通、须显式指定启动方式 | 是，但**须按 Boot 方式启动**
| `<被测类名>PerfTests` | 性能/基准对比测试（`perf`） | 对比性能的基准与方案对比（公共规范「性能测试」要求） | **否**，独立于常规测试、仅显式触发
| `<被测类名>IT` | 端到端/冒烟，依赖部署好的真实外部环境（真实 DB/消息队列/第三方服务/已运行的应用） | 无法自包含、必须有外部环境才能跑通 | **否**，独立执行（failsafe 等 IT 插件）
|===

* **后缀与后缀之内不得自创变体（L1）**：新增测试必须归入上表某一类，不得自造后缀（`UnitTests`、`IntegrationTests`、`BenchmarkTests`）或把类型塞进类名前缀；确有一种测试无法归入上表时，先按项目自身规范（或与维护方约定）的准入判定提案**扩表**，再动手写类。
* **`IT` 是与业内约定刻意对齐的唯一非 `Tests` 后缀**（依据：Maven Failsafe Plugin 的默认 includes 约定：`**/IT*.java`、`**/*IT.java`、`**/*ITCase.java`），以便开箱被识别、避免被 surefire 误跑。
* **`BootTests` 中的 B 大写**（`Boot` + `Tests`）。
* **存量随动迁移、不一次性收敛**：不合上述包路径与命名的存量测试类**不发动全库改造、不要求一次性改齐**——**碰到哪个改哪个**：该测试类本次因需求而变动时，随动调整为定式（重命名按 `specs/general/git.adoc`「文件移动与重命名」用 `git mv` 保留历史）；本次不变动则保持原样。用户明确要求一次性全库收敛时按其声明执行。
* **测试类不存在时**须按上述包路径与命名**新增**。
* **一个被测类的测试可拆成多个测试类，但只按需求/分类拆、不按场景滥拆（L2）**：同一被测类可按**需求**（用户提出的不同测试诉求）或**分类维度**（业务功能、行为类别、外部依赖形态）拆成多个 `<被测类名><后缀>` 测试类。**拆分后的每个类都须自足**：类名在「被测类名 + 测试类型后缀」之外可加**分类限定语**表明该类管哪一类（如 `OrderServiceCreateTests`），类级文档注释声明本类覆盖的分类，且**分类之间不得重叠**。
* **分类或属性相同的用例必须归入同一个测试类（L1）**：同一分类（同一需求/同一行为类别/同一 `@Nested` 主题）或同一属性（同类前置条件、同类外部依赖、同类数据形态）的用例**不得拆到多个类**，须用 `@Nested`/用例分类就地组织；**不得为"每个用例一个类""每个场景一个类"而拆**（**禁止滥拆**）。**一个被测类同时有多类测试时，各类各一个类**（如 `OrderServiceTests` + `OrderServiceIT`），不得合并成一个类后混用标签。**判定标准（命中即过度拆分）**：拆出的多个类**分类维度说不清**、**用例可在类间任意搬动**、或**每类只有一两个用例且无独立分类含义**。

== 测试分类与执行边界

* **常规测试类的取舍顺序**：先判定测试**是否自包含**（不依赖外部人工准备的环境、不依赖外部服务、可重复执行）。自包含 → `Tests`；确需容器/外部服务但能由测试自身启动（`@SpringBootTest`、Testcontainers、嵌入式实现）→ 仍用 `Tests`；**不能自包含、须人工准备真实环境** → 才用 `IT`（依据：ISTQB Glossary 的 "test double"/"integration testing"；JUnit 5 的 `@Tag` 过滤机制）。
* **BootTests 的启动型判定**：满足任一即归 `BootTests`——① 须由 Spring Boot 启动类/完整上下文承载，且**不能与常规测试在同一次启动内跑通**（须单独指定 profile/环境/启动参数）；② 需要测试专用启动依赖（嵌入式容器、测试专用数据源/配置）；③ 被启动的应用本身包含需隔离的初始化。**仅"用了 `@SpringBootTest`"不构成 BootTests**——能自启、可重复的 Spring 测试仍属 `Tests`。
* **类标识与过滤的配套（L2）**：可按分类在类上打标记（`@Tag("boot")`/`@Tag("perf")`/`@Tag("it")`），**只作分类标识，不替代后缀**（后缀才是类别判据，二者须一致）。
* **执行要求（L1）**：`PerfTests` 与 `IT` 均**不得**混入常规 `test` 阶段的执行集合（surefire 默认 includes 为 `**/Test*.java`、`**/*Test.java`、`**/*Tests.java`、`**/*TestCase.java`，`IT` 天然被排除）；须以**独立执行**方式运行（Maven Failsafe 的 `integration-test`/`verify`，或按 `@Tag` 过滤），并在项目构建配置中固定好分组，不靠人工记忆。
* **构建配置落点（L2）**：surefire/failsafe 的 includes/excludes 与 `@Tag` 分组须在 `pom.xml` 中显式配置并注释写明依据（测试分类 → 执行阶段 → 命令）；配置只允许"把某类测试放进对应阶段"，不得借配置放宽"`PerfTests`/`IT` 不随常规测试执行"这一条。

== 扩展新测试类型（新增后缀前先过准入）

出现上表未覆盖的测试形态时，**不得就地自创后缀**，按项目自身规范（或与维护方约定）的准入判定流程处理：① 先判定是否**真为新形态**（多数情况只是"该用 `Tests` 还是 `IT`"的归类问题）；② 确需新后缀时，给出形态判据（何时用/何时不用）、执行边界与**业内既有约定或标准依据**；③ 扩表后同步落点：本文件表格、机械校验、公共测试规范、CHANGELOG（若影响引用方项目）。

可选形态与候选后缀（**仅作备选示意，不是规范许可用后缀**）：

* **架构与依赖结构测试**（ArchUnit 等）：并入 `Tests`，类名由自身语义决定。
* **契约测试**（Pact、Spring Cloud Contract 等）：消费方校验并入 `Tests`；需要提供者或代理服务才能跑的组合测试归 `IT`。
* **消费方驱动的端到端验收**：归 `IT`；确需与"技术集成冒烟"区分时，先按准入判定扩表。
* **迁移/一次性校验测试**：属一次性脚本化产物，写成测试方法或独立一次性校验程序，不为其新增测试类后缀。

== 断言

* **异常断言用 `assertThrowsExactly` 精确匹配异常类型**，不用 `assertThrows`（避免父类异常掩盖子类语义）。

== 用例编写

* **测试代码与主代码同等遵守全部 Java 规范**（`specs/stack/java.adoc`）：lombok 使用、构造器/字段修饰符、对象创建、命名与注释、工具类等一律按主代码标准执行；语言层面按项目目标版本约束，禁用项目目标版本不支持的新语法糖。
* **按公共测试规范跳过某参数的异常输入用例时，该参数必须标注 `@NonNull` 注解写明约定**，防止后续误判为可空、再次生成异常输入用例。
* **涉及 lombok 等语法糖时注意实际展开结果**（`val` 的类型推断），避免用例预期与实际不符。
* **含 null 元素的集合字面量需显式泛型**（`Arrays.<Integer>asList`），避免类型推断歧义。
* **依赖反射/序列化（Jackson、hutool 等）的测试注意资源释放**（generator 需 close）与构造器可见性（反射默认只取 public 构造器）。

== 执行与验证

* **验证以 Maven 结果为准**（surefire 的 `Tests run/Failures/Errors/Skipped` 统计），具体见 `specs/stack/maven.adoc`。
* **按类别分别取统计**：常规测试看 surefire 统计，`IT` 看 failsafe 统计（`verify` 阶段），`PerfTests` 看性能测试自身的对比结果（不并入常规测试结论）；哪一类没跑就**不得**声称其通过。

== 启动型与端到端测试

* **`BootTests`（Spring Boot 启动型）**：须有 Spring Boot 启动类/完整上下文承载，测试专用配置（profile、数据源、嵌入式容器）放**测试资源**（`src/test/resources`）或测试内部配置类，**不得**改主代码配置迁就测试；启动失败的用例须给出可诊断的启动日志（不得静默 `catch` 后跳过）。命名与被测类一对一（如 `OrderApplicationBootTests`）。
* **`IT`（端到端/冒烟）**：依赖**外部已就绪环境**（真实 DB/消息队列/第三方服务/已部署应用），须在测试类或项目配置中**显式标注环境依赖**（所需服务、连接方式、缺失时如何跳过），环境不可用按其声明跳过并**在验证结论中如实说明未执行**（不得记为通过）；用例围绕端到端业务路径与冒烟场景，不做穷举覆盖。
* **`PerfTests`（性能）**：测量与记录要求统一见 `specs/general/testing.adoc`「性能测试」，本节不重复其判据。Java 专属落点只有两点：① **类名与承载**按 `<被测类名>PerfTests`（`perf`），**不混入常规 `test` 阶段**、仅在显式触发时执行；② **结果与结论写进该类的文档注释**（类上放方案目录、测量口径与结论，方法上放细节），**跨类/功能级**的内容进独立性能测试文档；结果分析须写明对比的各类实现与原因。

== 覆盖与变异测试

* **覆盖率统计用 JaCoCo**（`jacoco-maven-plugin`），排除 lombok 生成、getter/setter、POJO/DTO/VO 样板等自动生成的代码（`excludes` 配置），只统计手写业务逻辑；公共测试规范「覆盖率与充分性」中分支覆盖率 ≥ 80% 的要求，Java 中对应 JaCoCo 的 branch coverage 指标。
* **变异测试用 PIT**（`pitest-maven-plugin`），对关键/高风险代码（核心业务逻辑、安全敏感、数据转换）执行变异测试，评估突变得分；PIT 的存活变异体须按公共测试规范「测试有效性」逐个分析处理。
