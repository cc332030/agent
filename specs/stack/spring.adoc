= Spring 规范（技术栈层）

适用于 **Spring/Spring Boot 项目**。加载触发特征：项目存在 Spring 依赖、`@SpringBootApplication` 等 Spring 注解。依据：Spring Framework 官方文档的依赖注入与声明式事务两节。通用编码规则见 `specs/general/coding.adoc`；本文件只收录 Spring 专属规则。

== 注入

* **依赖注入默认使用构造器注入**；无注入字段时添加 `@AllArgsConstructor` 属正常写法，不作问题提醒。
* **禁止字段注入（`@Autowired` 直接标注字段）、setter 注入**：构造器注入保证依赖不为 null、便于测试与不可变，除非确有必要（循环依赖等）并说明原因。
* **注入的 Bean 优先用接口/抽象类型声明**：面向接口注入便于替换实现与测试，除非确无多实现。

== Bean 定义

* **Bean 的获取**：业务代码中不得直接 `ApplicationContext.getBean(...)`（绕开依赖注入、隐藏依赖关系），一律用构造器注入声明依赖。
* **`@Bean` 方法仅在配置类中使用**，业务类不定义 `@Bean`；`@Bean` 方法所在配置类须标注 `@Configuration`。
* **条件化装配用 `@ConditionalOnXxx` 系列注解**，不手写 `if` 判断后返回 null；对外提供的可替换点用 `@ConditionalOnMissingBean` 给默认实现、接入方一处覆盖即全局生效（接入成本见 `specs/general/coding.adoc`「抽象与接入成本」）。

== 配置

* **配置项统一用 `@ConfigurationProperties` 绑定（L1）**：外部配置**只允许**绑定到 `@ConfigurationProperties` 类（类型安全、集中管理、可校验），**禁止使用 `@Value`**——包括业务代码与配置类中的字段注入、构造参数与方法参数上的 `@Value`；SpEL 取值（`#{...}`）不受本条约束（它不属外部配置绑定）。**判定标准（任一命中即违规）**：① 新增或改动的代码中出现 `@Value` 注解（任意用途）；② 为绕开本条把配置项塞进 `@Configuration` 类的字段而不走 `@ConfigurationProperties`。**存量处理（L1）**：已有项目中的存量 `@Value` **不属违规、按原样保留**，按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**（改到的文件顺带调整，不发动全库改造），**code review 也不对存量 `@Value` 作问题提示**（存量长期不合规范不视为违规）。依据（标准名/编号）：Spring Boot 官方文档「Externalized Configuration」（`@ConfigurationProperties` 是类型安全配置绑定的推荐方式，`@Value` 仅适合零散单值）；The Twelve-Factor App（配置外置与集中管理）。
* **配置类不写逻辑（任何情况都不允许，L1）**：`@ConfigurationProperties` 类与 `@Configuration` 类只承载"配置项声明 + 按配置装配对象"，逻辑一律下沉到工具类或 Service——取值兜底、条件判断、格式转换、派生值与数据加工**一律不在配置类中做**，只放字段与访问器（判定标准见 `specs/general/coding.adoc`「类设计」）。
* **`@ConfigurationProperties` 类须提供校验**（`@Validated` + JSR-303 注解），启动即校验配置合法性，避免运行期才发现配置错误。
* **校验注解只做声明式校验**：校验逻辑写在自定义 `ConstraintValidator` 或工具类中，不得在配置类里写校验/判空逻辑。
* **配置项须有默认值或显式必填声明**；必填项缺失时启动失败（fail-fast），不静默使用空值。
* **与框架既有做法的边界（防静默推翻）**：本条**严于** Spring 的常规用法——官方允许在配置类里放派生 getter、在 `@Bean` 方法内做条件装配（`@ConditionalOnXxx` 除外）；本规范要求这类加工下沉到工具类/Service，已有项目按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**（改到的文件顺带调整，不发动全库改造）。

== 参数校验

* **方法参数校验统一用 `@Validated`（L2）**：方法参数**校验入口统一用 `@Validated`**（`org.springframework.validation.annotation.Validated`），**不把 `@Valid` 用作方法参数校验的入口**——`@Valid` 无分组参数，只承担**对象内部字段的级联校验**这一正当用途。**判定标准（任一命中即违规）**：① 方法参数上以 `@Valid` 作校验入口（该处需要**指定校验分组**时更是如此——`@Valid` 无分组参数）；② **类级/方法级校验入口**（非「对象内部字段级联」）以 `@Valid` 承载；③ 同一项目里两种校验入口并存，且未按「参数入口 / 字段级联」划出各自边界。**影响面（L2）**：本条严于「参数上直接用 `@Valid`」这一常见做法，**引用方项目自身规范另有约定时以其为准**。**存量**按 `specs/core/execution.adoc`「规范变更的存量处理」随动迁移。依据（标准名/编号）：Spring Framework 官方文档（`@Validated` 可指定校验分组，`@Valid` 无此参数）、Jakarta Bean Validation 官方规范（分组由约束声明与校验入口共同决定）。

== 事务

* **事务用 `@Transactional` 声明式管理**，不在业务代码中手动 `begin/commit/rollback`。
* **`@Transactional` 须显式指定 `rollbackFor`**（默认只回滚 `RuntimeException`，受检异常不回滚，易埋坑）。
* **事务方法须为 public 且由 Spring 代理调用**：同类内部方法直接调用（`this.xxx()`）不走代理、事务失效。
* **事务范围尽量小**：不在事务内做远程调用、耗时 IO 等操作，避免长事务占用连接。

== 跨语言执行脚本（资源文件夹）

* **执行其他语言的脚本按资源加载，不内联字符串（L1）**：`@Sql`、`ScriptUtils`、Redis `DefaultRedisScript`、JDBC 语句等，一律**从资源文件夹加载 `.sql`/`.lua` 等文件**后执行，不用字符串拼接或字符串模板在 Java 里组装脚本；落点与判定标准见 `specs/stack/java.adoc`「跨语言执行脚本（SQL / Lua 等）」与 `specs/general/coding.adoc`「跨语言执行脚本的落点」。
* **加载时机按性能敏感度定性（L1）**：读进来的脚本**发布后不变**，性能敏感路径（Redis 操作、热点查询）须"读一次、反复用"——静态常量声明 `DefaultRedisScript`、静态初始化块里载入一次；**需求要求内容会变**的模板不适用缓存、按重读决定。判据与 Java 落点见 `specs/stack/java.adoc`「跨语言执行脚本」的「加载时机」。

== 分层与职责

* **分层职责清晰**：Controller 只做参数校验与协议转换、Service 承载业务逻辑、Repository/Mapper 只做数据访问，不跨层调用、不在 Controller 写业务逻辑。
* **一个实体的数据访问归它自己的 Service，跨表的业务服务另建（L2，不禁用）**：涉及**多张表**的业务操作**优先新建业务服务**（`XxxBizService` 一类）来编排各实体的 Service；**职责边界的判据本体的唯一落点＝`specs/stack/java.adoc`「持久化访问」**（实体 Service 的职责边界、禁止的三种形态都在那一条里），本文件只留**分层取向**，不复制其条文。**强度等级、豁免面（"不建议、不禁用"与三条可核对形态）、判定标准与存量口径一律同 `specs/stack/java.adoc`「持久化访问」**——它们只在那一条里写一份，本文件不复制（本轮收敛：本处曾把豁免三形态与三条判定标准逐条抄回，与"职责边界的判据本体在 `java.adoc`"的定位相抵）。**落点说明**：MyBatis-Plus 侧的具体类形态（`IService` 成员方法只能在本子类内调用、`XxxService`/`XxxServiceImpl`/`XxxMapper` 的归属）同样以 `specs/stack/java.adoc`「持久化访问」为唯一落点；本条只管**分层的职责边界**（跨技术栈成立的 Spring 语境）。
* **与 `specs/general/coding.adoc`「持久化访问」的分工**：调库前判空、集合返回空集合的判据在通用层（跨语言成立）；本条与上一条只管**访问点归谁**（分层职责），两者同向、互不替代。
* **HTTP 接口路径优先用中划线（kebab-case）（L1）**：路由路径（Feign 等内部调用接口与控制器的 `@RequestMapping`/`@GetMapping` 一类路径）的**路径片段**须用小写 + 中划线（`-`），**不得**用下划线（`_`）或驼峰/大写：写 `/user-center/get-user`，不写 `/user_center/getUser`。**理由与依据**：路径片段是大小写敏感的 URI 成分，`-` 与 `_` 都是 RFC 3986 的 unreserved 字符——两者之差**不构成语义差、只构成拼写风险**（依据：RFC 3986 的 URI 语法；Google API 设计指南的 REST 资源名路径以小写连字符分隔）。**两处照旧**（沿用既有，不按本条改名）：① **服务路由前缀/网关前缀**——它由服务名或注册中心决定、与本条无关；② **已发布、外部依赖的对外路径**——改动即破坏既有调用方，属契约变更。**判定标准（任一命中即违规）**：① 新增或改动的路径里出现 `_`；② 路径片段用驼峰/大写字母分段；③ 同一接口内两种风格混用。存量路径按 `specs/core/execution.adoc`「规范变更的存量处理」随动迁移，不发动全库改名。**与命名规则的分工**：本条只管**路径字符串**；接口类名、DTO 类型等 Java 标识符的命名按 `specs/stack/java.adoc`「命名」与 `specs/general/coding.adoc`「命名与代码质量」执行。**本条只在技术栈层**（"HTTP 路径"只在 Web 框架语境下有定义，通用层不写协议/框架专名）。
* **Controller 统一用 `@RestController`**，返回体统一封装；异常统一由全局异常处理器（`@RestControllerAdvice`）处理，不在业务代码中逐处 try-catch 后手工拼错误响应。

== HTTP 接口（控制器与声明式客户端）

**适用范围**：提供或调用 HTTP 接口的项目；其中**契约接口**（声明式客户端与提供方）三条以项目**使用声明式 HTTP 客户端**为前提，未使用者不适用。

* **控制器方法须显式声明 HTTP 方法（L2）**：路由须由**指明 HTTP 方法**的注解映射，**不得**用不限定方法的映射承载接口——不限定方法时同一个路径对**全部** HTTP 方法开放，读写语义混在一起（方法语义见 `specs/general/coding.adoc`「HTTP 接口语义」）。**判定标准（任一命中即违规）**：① 新增或改动的路由用不限定 HTTP 方法的映射；② 以「调用方反正只发一种方法」为由不限定。**存量**按 `specs/core/execution.adoc`「规范变更的存量处理」随动迁移。依据（标准名/编号）：Spring Framework 官方文档（不限定方法的映射默认匹配全部方法）、RFC 9110（方法语义：读写与副作用须由方法表达）。**「路由须显式声明 HTTP 方法」是本集合的判据化取值**。
* **声明式客户端与提供方共用同一份契约接口（L2）**：内部调用接口**只定义一份契约**——**客户端继承该契约、提供方实现该契约**，两侧不各写一份方法签名；同一契约两份写法时，改一侧必漏另一侧。**判定标准（任一命中即违规）**：① 客户端与提供方各自声明方法签名、不共用同一契约类型；② 以「两侧写的就是一回事」为由不抽契约。依据（标准名/编号）：Spring Cloud OpenFeign 官方文档（声明式客户端以接口声明契约）、ISO/IEC 25010（可维护性：同一契约只有一处来源）。
* **契约的路径前缀只定义一次（L1）**：前缀写在**客户端声明的路径**与**提供方的路由映射**处（两侧各一处），**契约方法上只写相对路径**——方法上重复写前缀即同一事实出现两个来源，改前缀必漏方法上的那一份。**判定标准（任一命中即违规）**：① 契约方法的路由里出现与前缀重复的路径段；② 前缀只写在契约方法上、而不写在客户端声明与提供方映射处。**存量**按 `specs/core/execution.adoc`「规范变更的存量处理」随动迁移。依据（标准名/编号）：ISO/IEC 25010（可维护性：同一事实只有一个来源）、ISO/IEC/IEEE 29148（判定须可验证）。
* **内部调用接口的参数以请求体承载，不逐个散参（L2）**：契约方法的参数**以请求体承载该接口自己的参数对象**；确需按查询参数传递时**以整对象映射**（`@SpringQueryMap` 一类，由框架把对象字段展开为查询参数），**不得**把该接口的参数清单**逐个声明**（入请求体或作查询参数均属逐个声明）——参数清单散落在方法签名里时，增删参数要改多处、键名只能靠字面约定。**判定标准（任一命中即违规）**：① 契约方法把该接口的一组参数逐个声明，而该组参数本可由同一个参数对象承载；② 同一契约里两种承载方式并存，而无明确边界。**例外与边界（L2）**：路径变量、请求头一类本身不是参数对象的绑定不受本条约束。**存量**按 `specs/core/execution.adoc`「规范变更的存量处理」随动迁移。依据（标准名/编号）：Spring Cloud OpenFeign 官方文档（`@SpringQueryMap` 支持 POJO 查询参数）、ISO/IEC/IEEE 29148（契约须单一、可验证）。
