= 构建工具迁移规范（技术栈层）

适用于**任一构建工具迁移到任一构建工具**（Maven ↔ Gradle ↔ Bazel ↔ Ant ↔ npm/pnpm 等任意组合）。加载触发特征：要把项目/模块的构建方式从一种构建工具换成另一种、要判定迁移后"哪些旧形态该留、哪些该丢、哪些必须换算"、或要评审一次迁移的产物形态。源构建工具与目标构建工具的专属规则见 `specs/stack/` 对应文件（Maven 见 `specs/stack/maven.adoc`，Gradle 见 `specs/stack/gradle.adoc`）。

== 核心口径：以目标构建工具的规范为基准

迁移不是"把旧构建工具的写法翻译成新工具能跑的等价写法"，而是"**让构建结果在目标构建工具的规范下重新表达一遍**"。

* **以目标构建工具的规范为基准（L1）**：迁移后的形态**按目标构建工具的规范定义**，**不得**为目标工具能跑起来而保留源构建工具的形态。**判定标准（任一命中即违规）**：① 出现"目标工具里本来不存在的结构"，只是为了对应源工具的同名结构（典型：把 Maven 的父子关系照搬成目标工具里的同名层级，而目标工具不靠它构建）；② 为迁就源工具的写法而在目标工具里引入通用性缺失的补丁式配置（只为在一个模块里凑出源工具才有的行为）；③ 迁移说明里以"这样写更像原来的 pom"为保留理由。依据：ISO 10007（配置项须有单一、受控的来源——保留源工具的形态即等于把旧构建模型当成了第二真源）、ISO/IEC/IEEE 25010（可维护性）。
* **效果不变指的是构建结果，不是形态（L1）**：迁移要保住的是**构建结果**（产物、坐标、发布的元数据内容、构建期行为、对外可见的构建入口），**不是源构建工具的形态**。**"效果不变"不得被读成"形态不变"**：凡不影响构建结果的源工具特有结构（继承层次、聚合结构、仅为对应源工具有而存在的模块关系），一律按目标工具规范重新表达、**不保留**；凡**构建结果会变**的部分（产物坐标、发布元数据、对外可见的入口名称、构建期行为），按「构建结果不变」处置。**判定标准（任一命中即违规）**：① 以"效果不变"为由保留目标工具用不上的结构；② 以"换成新工具的写法"为由改变构建结果而不作声明。
* **不得强凑源构建工具的结构（L1）**：源构建工具**不需要**的**继承关系与层级**不得为了对应源工具而保留或新造。**Maven 的父子关系是 Maven 的机制、不是"需要保留的语义"**：目标工具不靠层级表达构建时，**不把父子关系搬过去**（这也是本集合用户在本次迁移上点名的形态）。**判定标准（任一命中即违规）**：① 目标工具里出现"只为对应源工具某层"的空壳模块/空壳目录；② 出现只被层级关系引用、不承载任何构建职责的节点；③ 以"保留继承层次便于对照原来"为由不删。**依据**：ISO/IEC/IEEE 29148（结构应单一、无歧义；保留多余层级即多出一个可漂移的来源）。
* **迁移后必须显式区分「机制」与「形态」（L1）**：源构建工具里**靠某结构承担的构建职责**（依赖的传递与覆盖、scope 的映射、编译期与发布期的差异、产物坐标的推导），在目标工具里**由该工具的既有机制承担**，该机制下**优先声明式写法**。**不得**为该职责保留某个源工具特有的载体（如把"源工具里由层级承担的依赖注入"照抄成目标工具里的一个同名结构）。**判定标准（可核对）**：逐项问"删掉这个结构后构建结果是否变化"——不变化的即**不保留**；变化的须在目标工具里找到承担该职责的**规范形态**（该形态见目标工具的栈文件）。
* **多环境/多档位的差异按目标工具的表达能力表达（L1）**：源构建工具里靠 profile、继承档、构建器专属条件之类承担的"一套源码对多个环境/版本"要求，迁移后按目标工具的规范表达（如把差异部分拆成**互斥**的多份实现、由该工具的构建期参数选用其一），**不得**按源工具的 profile 形态照搬。**判定标准（任一命中即违规）**：① 目标工具里以"仿 profile"的自造结构承载环境差异；② 差异实现**不互斥**（同一实现落在多处、靠选取规则兜）。**边界**：本条只管**表达方式**，"该不该做这种多档位"属既有设计，迁移不改变它。
* **存量边界（L1）**：本条适用于**迁移的那一次改动**及其**改到的构建脚本**；**不构成**对引用方其它未迁移项目的改造要求（随动迁移，见 `specs/core/execution.adoc`）。
* **"以目标工具的规范为基准"是本集合的判据化取舍**：外部标准与各构建工具官方文档只给各自的机制与推荐用法，**不给**"迁移时该按哪一侧定义"的口径；本集合取"目标工具侧"，理由是构建结果只由目标工具解释，保留源工具的形态等于让源工具的模型继续当第二真源。
* 依据（标准名/编号）：ISO 10007、ISO/IEC/IEEE 25010、ISO/IEC/IEEE 29148。

== 构建结果不变（迁移的验收面）

* **坐标不变（L1）**：迁移前可被引用方按坐标取用的产物，迁移后**坐标不变**（groupId / artifactId / version 的取值形态不变；需要随构建工具变化的**仅有**产物类型与元数据文件名）。**判定标准**：逐模块核对坐标，出现"迁移时顺手改了名字/版本"而无用户声明即违规。
* **发布元数据的内容不变（L1）**：发布到仓库的元数据（依赖声明与其作用域、可选用标记、版本约束的**实际解析结果**、父/继承载荷的**有效语义**）须与迁移前**等价**——即引用方按迁移前的方式取用，解析结果不变。**判定标准（任一命中即违规）**：① 迁移后引用方解析到的版本发生变化且未声明；② 迁移前"声明了但没生效"的作用域（如源工具的死配置）被当成需要保留的语义；③ 迁移前由源工具机制隐式产生的元数据项（继承来的依赖、由构建工具推导的父声明）在迁移后缺失，而引用方依赖它。
* **构建期行为不变（L1）**：编译/资源处理/测试/打包/发布的**行为**不变——含编码、编译参数、失败的处置（该失败的仍失败）、默认跳过的部分。**判定标准**：逐项列出源构建工具在用的构建期配置，迁移后要么等价生效、要么**显式声明为不再需要**（如源工具的死配置、其行为在新工具下无对应物且无实际作用）——**不得静默丢失**。
* **对外可见的构建入口不变（L1）**：项目既有的构建入口（构建器包装脚本一类）**仍然可用且仍以之为准**；入口的**名称与用法**是声明面的一部分，迁移**不得**靠"让使用者改命令"来绕过（若确需变更，须先向用户确认）。
* **运行环境声明（L1）**：运行环境与构建工具版本的声明落点、以及"验证一律用声明版本"的口径，按 `specs/general/ci-cd.adoc`「运行环境须与项目声明一致」执行——迁移**不得**顺手变更声明版本，也**不得**出现"迁移后 CI 与本地各用一个版本"的形态。
* **不得顺手改动的面（L1）**：迁移**不是**重构 —— 依赖的增删与升级、源码结构调整、模块职责调整、命名变更一律**另行处理**；迁移的那一次改动只承载"换成目标构建工具、结果不变"。**判定标准（任一命中即违规）**：① 迁移提交里混入依赖版本变更；② 以"顺手整理"为由移动/改名的源码与模块；③ 以"反正要改"为由顺带废弃既有构建流程（那样须按「大动之前先确认」先经用户确认，见 `prompts/_common.txt` 的 `baseline-and-compat` 片段）。
* **依据行**：The Twelve-Factor App（构建/发布/运行分离）、ISO 10007。

== 迁移的验收与留证

* **基线是迁移前的构建产物与元数据（L1）**：迁移**必做**基线（属"规范类/结构类改动"的取严档，见 `specs/general/verify.adoc`「验证的适用边界」）：动手前把源构建工具产出的**产物清单、坐标、发布元数据（含依赖与作用域的实际解析结果）、构建期配置**取一份留证，迁移后**逐项对照**。**"能编译过"不是验收**——迁移最典型的失效是**编译通过而元数据变了**（依赖少一项、作用域换了一档、父声明丢失），只有逐项对照能发现。
* **验收留证的落点（L2）**：留证随本次迁移的交付物落地（设计文档、变更日志或提交说明之一）。**取值＝"比较结果与差异项已可核对"**，不规定记录载体与格式。
* **未确证不得记作通过（L1）**：迁移前未取到基线、或某项无法对照时，按 `specs/general/verify.adoc` 如实标注"未确证 + 原因"，**不得**记为通过、**不得**以"构建成功"顶替。
