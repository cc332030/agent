= Gradle 规范（技术栈层）

适用于 **Gradle 构建**。加载触发特征：项目存在 `settings.gradle`/`settings.gradle.kts`、`build.gradle`/`build.gradle.kts`、`gradlew`/`gradlew.bat`、`gradle/libs.versions.toml`。构建/依赖调整前须加载本文件。Node 等其它构建工具按对应栈文件规范；从其它构建工具迁移来的项目还须加载 `specs/stack/build-tool-migration.adoc`。

== 仓库与镜像

* **未配置过仓库/镜像时的换源口径按 `specs/general/dependency.adoc`「包源（包仓库/镜像站）的选用」执行**（次序、逐级降级、先实测再启用三条与其它构建工具同源，本文件不另立一套）。Gradle 侧只有一处**取值形态**差异：仓库声明是 `mavenCentral()`/`maven { url }` 一类**脚本表达式**而非 URL 文本，故"取到构件"这一实测判据在 Gradle 上以**解析结果**核对（依赖能不能被解析出来），不以"写了哪个地址"核对。
* **已配置过即沿用（L1）**：项目已有仓库配置（含 `settings.gradle`/`build.gradle` 里的 `repositories`、`buildSrc` 自带的仓库、以及项目自身的初始化脚本）时**一律沿用**，不覆盖、不重配。

== 依赖

* **版本集中在版本目录（L2）**：项目使用 Gradle 版本目录（`gradle/libs.versions.toml`）时，第三方依赖的版本**只在版本目录里声明**；模块构建脚本通过别名取用、**不写死版本号**（版本由平台/BOM 约束提供时不写版本，见下条）。
* **同一依赖只有一个版本声明落点（L1）**：同一个构件在两个档位/两个模块取值不同时，用**同一别名 + 档位后缀**的成对登记表达（如 `<别名>-jdk8` 与无后缀的 `<别名>`），**不得**在模块脚本里写 `if` 判断档位、也不得把取值散到多处。**判定标准**：抽掉任一处档位判断后，若某档位会静默取到另一档位的版本，即违规。
* **BOM 与版本约束用平台（platform）表达（L1）**：需要"以某份 BOM 的版本为准"时用 `platform(...)`/`enforcedPlatform(...)`（`enforcedPlatform` 对应"以 BOM 为准"的强约束语义）；**该 BOM 自身不得落在参与发布的配置上**（会泄漏给消费者、发布会被拒）。**判断标准**：某份 BOM 出现在参与发布的配置里即违规。
* **项目的显式取值须压过上游 BOM（L1）**：项目在版本目录里**显式覆盖**了某个与上游 BOM 同名的构件时，须让该取值**真的生效**（`enforcedPlatform` 未覆盖的构件用逐构件对齐，或在该模块用 `strictly` 钉住）——**Gradle 的默认冲突策略是"取最高版本"，与"以 BOM 为准"不是一回事**。**判定标准**：迁移或升级后出现"声明了 A 版本、实际解析到 B 版本"而无声明即违规。**Maven 迁移的对应面**：Maven 的 `dependencyManagement` 以 BOM 为准，迁移后逐项核对解析结果（见 `specs/stack/build-tool-migration.adoc`「发布元数据的内容不变」）。
* **模块间依赖用项目依赖（L1）**：同一构建内的模块间依赖用**项目依赖**表达，**不得**改用仓库坐标取本项目的构件——后者会取到上一次发布的旧产物（"上游改了没重装"的静默失效），而项目依赖由构建工具自动保证顺序与新鲜度。**需要以发布形态验证**时才另做一次发布到本地仓库的动作，且不得把它当成日常构建路径。
* **不得默认使用本地仓库解析（L1）**：依赖解析**不得**默认把本机用户仓库（如 `mavenLocal()`）纳入解析面——本地仓库里的同名同版本产物会被就近取用，同一提交在不同机器上解析到不同构件、构建不可重现；缺构件时还会静默回退到本地那份、掩盖远端源的问题。**判定标准**：解析仓库清单里出现本机用户仓库即为违规（项目显式声明为用户要求时除外）。
* **可选/编译期能力须在发布元数据里可见（L2）**：以"编译期可见、不向下游传递"的方式声明的依赖，其在**发布元数据**里的表达须让使用方能看到该能力与解析后的版本（不可用时用"可选用"标记一类形态）。**判定标准**：使用方拿到的元数据里该能力**完全消失**即违规（"能编译"不等于元数据对）。
* **严禁私自调整依赖**：依赖的增删与升级按 `specs/general/dependency.adoc` 执行；构建工具迁移**不构成**改依赖的理由（见 `specs/stack/build-tool-migration.adoc`「不得顺手改动的面」）。

== 构建与产物

* **构建产物目录按用途/档位分家（L2）**：同一项目有多个构建档位（多 JDK 档位、多渠道、多侧）时，**各档位的产物目录不得互相覆盖**；目录名取"顶层容器 + 末级构建目录"的分层形态即可。**不可用默认构建目录**——默认目录名与档位无关，切档位构建会覆盖上一次的产物。**判定标准**：切一次档位再构建，前一档位的产物是否仍在。
* **构建产物目录的落点用目录名表达（L2）**：在子项目统一配置里设置产物目录时，路径用**目录名**表达、**不拼**子项目的相对目录属性——该属性在根项目的上下文里解析基准不同，跨上下文会解析失败（构建脚本执行期才会暴露）。**取值＝"在根项目与子项目两侧都解析得到同一处"**。
* **档位差异源码目录须互斥（L1）**：多档位下必须使用不同底层 API 的类，按档位分放**同包同名**的互斥源码目录（如 `src/main/java-<档位>`），由档位参数决定纳入哪一个；**公共类不落任何档位专属目录**（落进去即等于"只在一个档位存在"）。**判定标准（任一命中即违规）**：① 同一份源码同时落进多个档位目录、或一份实现被复制到多处**仅靠"当前选的是哪一份"兜住**（漏选即静默取到另一档，不报错）；② 档位专属目录里出现只与公共面有关的类。**不得**用"追加源码目录 + 排除同名文件"实现互斥：排除对**全部**源码目录生效，会把专属目录里的同名文件一并排除、类彻底消失。
* **档位由构建期输入决定、取值口径只认一处（L1）**：档位取值只从**项目声明的输入**读取（系统属性 > 环境变量 > 项目属性文件一类的固定次序），**不得**改成从当前运行环境推导的取值（那会让"默认档位"随构建机变化、既有产物形态随之漂移）。**判定标准**：出现"读当前运行环境的版本号当作档位"即违规。
* **测试默认执行、专项测试默认跳过且按命名契约（L2）**：专项测试（性能测试、集成测试一类）按**命名契约**识别，默认不执行；需要时用**显式构建期开关**放开。**判定标准**：跑构建会把专项测试一并跑起来（或反之：常规测试被默认跳过）即违规。
* **构建选项与源工具对齐（L2）**：编译参数、编码、文档生成等构建期选项须与迁移前**等价生效**（见 `specs/stack/build-tool-migration.adoc`「构建期行为不变」）。
* **同一模块禁止并行构建**（通用规则见 `specs/general/testing.adoc`「执行与验证」）。
* **验证以构建结果为准**：构建失败须依据**构建工具报出的失败项**（编译错误、失败用例数）判断，**不得仅凭退出码**；输出重定向到文件、"获取统计一步到位"等通用验证规则见 `specs/general/verify.adoc`「编译/运行验证」。

== 发布

* **仓库注册的条件是"地址可用"、不是"凭据齐全"（L1）**：发布仓库须**只要地址配置了即注册**；凭据缺失交给发布任务**如实报错**。**判定标准**：以凭据为条件注册时，缺少凭据会让发布变成**无任何动作的空任务**、构建照旧成功——"构建成功但一个制品都没上传"（最隐蔽的一类假绿）。
* **凭据来自项目声明的配置面、不写死（L1）**：发布凭据从项目声明的输入读取（环境变量、项目属性一类），**不得**写进构建脚本。取值＝"凭据面可配置"，具体载体按项目既有做法（见 `specs/general/security.adoc`）。
* **配置缓存友好（L2）**：需要与构建配置缓存共存时，凭据取**延迟解析**形态；**回退到显式凭据**的写法要与构建配置缓存互斥，故该回退须是**显式取舍**、不得当成默认路径。
* **迁移来的项目须核发布元数据（L1）**：源构建工具靠**继承**或父级声明产生的元数据内容（父声明、继承来的依赖与作用域、插件配置），在目标工具里**不会自动带出**——须按 `specs/stack/build-tool-migration.adoc`「发布元数据的内容不变」逐项对照，把确实需要的**有效语义**显式写进产出元数据。
