= Java 规范（技术栈层）

以下规范适用于 **Java 项目**。加载触发特征：项目存在 `.java` 源文件、`pom.xml`/`build.gradle`、lombok 配置等。Java 项目写代码必须加载本文件及 link:../stack/java-syntax.adoc[]、link:../stack/java-testing.adoc[]（见 AGENTS_COMMON.adoc 加载调度规则）。

跨语言通用编码规则见 link:../general/coding.adoc[]（含命名通用规则）；本文件只收录 Java 专属规则。

遵守《阿里巴巴 Java 开发手册》；与本规范冲突时，以本规范定义为准。命名与代码风格另参考 Google Java Style Guide 与 Oracle Java 命名约定。

== 命名

* 类重名：除非类全名（全限定类名）冲突不可避免，否则不使用类重名；发现类重名的需调整优化
* 工具类命名**优先用复数 `Utils` 结尾**：**仅限工具类**（承载通用静态工具方法、提供项目自有功能的类，如字符串/集合处理 `CStrUtils`），类名优先以 `Utils` 结尾（参考 Apache Commons/Spring `StringUtils`/`ObjectUtils`），单数 `Util` 仅在既有一致约定等情况下采用，不混用。**非工具类不受此约束**——即使静态使用或加 `@UtilityClass`，下列不算工具类，命名由自身语义决定（跟随所替代/扩展的对象），不得套用 `Utils`/`Util` 结尾：
  ** 常量类（只放常量）；
  ** **低版本 JDK 替代/补齐类**：复刻 JDK 静态能力为低版本补齐（如 JDK8 无 `List.of`，提供 `CList.of(...)`）；
  ** **JDK 现有类的扩展类**：JDK 现有静态类亦为静态使用，其扩展/对应类非工具类（如对应/扩展 `Collectors` 的 `CCollectors`）

== 编码

* 强制优先使用 lombok：能用 lombok 代替的绝不手写——getter/setter、构造器、builder、toString/equals/hashCode 等一律用 lombok 生成，禁止移除 lombok 的使用
* 局部变量强制使用 lombok val、var（硬性要求）：局部变量声明必须且一律使用 `val`/`var`（类型由初始化表达式推断，`val` 不可变、`var` 可变），不得为显式写出类型而放弃 val/var；val/var 仅适用于局部变量，字段不得使用；唯一例外：类型推断结果不清晰（复杂泛型、联合类型推断等）等确需显式类型提示的场景可写显式类型，此类例外须克制使用
* lombok.config 实时读取：lombok.config 内容可能调整，规范不固化具体配置项；使用 lombok 或涉及 lombok 默认行为时，实时读取项目根目录 `lombok.config`，按当前配置执行，不得在规范或代码注释中固化其具体配置内容
* 对象创建统一用 builder、构造器统一用 lombok：禁止 `new Xxx(参数...)` 创建对象，创建一律使用 builder（优先 @SuperBuilder 而非 @Builder，支持继承场景）；无参、必参、全参构造方法一律用 lombok 注解生成，禁止手写任何构造器；实体类用 @Data、@NoArgsConstructor、@AllArgsConstructor；@AllArgsConstructor 等构造注解仅用于框架注入或序列化等特殊场景，业务创建对象不得依赖其生成的构造器
* 纯数据结构类识别特征（补充通用编码规范）：除通用编码规范中"以 bean/model/pojo/dto/vo/entity 等命名"的识别外，**仅使用 `@Data`/`@Getter`/`@Setter` 等 lombok 访问器注解的类同属纯数据结构类**，方法中不得出现非字段读写的计算/转换/组装逻辑（通用规则见 link:../general/coding.adoc[]「类设计」）
* 配置类识别特征（`@ConfigurationProperties` 等，补充通用编码规范）：除通用编码规范中"以 Config/Properties/Options/Settings 等命名"的识别外，**标注 `@ConfigurationProperties` 的类一律属配置类**（无论类名如何）——只放配置项字段与 lombok 访问器注解，**不得含任何逻辑**（无例外），校验注解与绑定注解属声明、不属逻辑（通用规则与判定标准见 link:../general/coding.adoc[]「类设计」）
* 定义方法时参数换行：多参数且整行宽度（含缩进）临近或超过 80 字符时，参数需换行——左括号 `(` 紧跟方法名后换行，每个参数单独一行，右括号 `)` 单独一行收尾；参数较少或整行宽度未达阈值时保持单行
* JSON 处理全局统一使用 Jackson，禁止引入其他 JSON 库（如 Gson、fastjson）
* 既有工具类/先例优先（补充通用编码规范「代码复用」）：Java 项目写代码前先查项目自有工具类（如 ctool4j 的 `CList`/`CStrUtils`/`CIdUtils`）与已引入工具库（如 hutool 的 `IdUtil`/`CollUtil`/`StrUtil`）是否已覆盖该操作，并跟随项目内同类调用的先例；**已有等价能力时禁止手写 JDK 原生写法**（典型反例：已有 `IdUtil.fastUUID()`/`CIdUtils.UUID()` 仍写 `java.util.UUID.randomUUID().toString()`；已有 `CollUtil.isNotEmpty` 仍写 `null != coll and !coll.isEmpty`）。选择优先级与现成 API 清单见 link:../stack/java-syntax.adoc[]「工具类使用优先级」（通用规则见 link:../general/coding.adoc[]「代码复用」）
* 反射操作优先使用 MethodHandle：访问字段、调用方法、构造对象等反射操作优先使用项目提供的方法句柄工具，避免直接使用 `Field#get/set`、`Method#invoke`、`Constructor#newInstance` 等原生反射调用；没有现成的方法时，可补充后再使用
* 日志打印（禁 println、统一 slf4j 见通用编码规范）：静态文本（无参）不属占位符参数化约束范围，合规；异常日志不得拼 `e.getMessage()`，须将 throwable 作为最后一个参数传入（如 `log.error("msg: {}", arg, e)`）

== 跨语言执行脚本（SQL / Lua 等）

Java 里要执行**其他语言**的脚本时，须按通用编码规范「跨语言执行脚本的落点（资源文件夹，不写字符串拼接/模板）」执行——**独立成文件放资源文件夹、扩展名取被调语言的扩展名、按资源读取后执行**，不得用字符串拼接、字符串模板或字符串常量内联在 Java 代码里。

* **SQL（L1）**：执行 SQL 时**按资源加载 `.sql` 文件**（`src/main/resources/` 下，如 `src/main/resources/sql/order-query.sql`），用 `PreparedStatement` 参数化执行——SQL 本体不写在 Java 字符串里。**MyBatis 项目是已知例外**：SQL 写在 mapper 的 `*.xml` 映射文件里（MyBatis 支持的文件形式），**不再另建 `.sql`**；MyBatis 给出的 **`${}` 是字符串拼接**（直接替换进 SQL 文本），仅可用于不由用户输入决定的场景（如动态排序字段）、且须对取值做**白名单校验**，其余一律用 `#{}`（预编译参数）。
* **Redis / Lua（L1）**：Lua 脚本**写成 `.lua` 文件**放 `src/main/resources/lua/` 下，用 `DefaultRedisScript`（或项目的等价封装）**按资源加载**后执行，**禁止**把 Lua 内联成 Java 字符串、也禁止在 Java 里拼 Lua 片段（依据：Redis 官方文档的 "EVAL" 与 "Redis Lua API reference"）。
* **加载时机（L1，与通用编码规范「跨语言执行脚本的落点」的「加载时机」同条，此处给 Java 落点）**：classpath 资源打进产物后**发布即成常量**，**不得在每次调用时都读**——
** 性能敏感路径（如 Redis 操作）：按"读一次、反复用"定性**——`.lua` 用 `DefaultRedisScript` 时**按静态常量声明**（`private static final DefaultRedisScript<...> SCRIPT = new DefaultRedisScript<>(...)`，在静态初始化块或静态构造方法里 `setLocation`/`setScriptSource` + 载入一次），**禁止在方法内 `new DefaultRedisScript` 后逐次读资源**；`.sql` 若属热点查询，同样把"读一次"与"执行多次"分开（读入后缓存 `String` 或缓存预编译 `PreparedStatement`/`DataSource` 侧对象，按框架能力与并发安全取舍）。Redis `EVAL` 反复把脚本正文送到服务端亦属重复开销，等价的复用手段是 `EVALSHA`/`SCRIPT LOAD`（是否适用按项目的客户端封装与部署形态定）
** **不敏感路径**（启动装配、一次性任务、低频操作）：每次读取无妨
** **需求要求内容会变**：如每次渲染前可编辑、需要热更新的 HTML 模板（转 PDF 等场景）——**不缓存**，按"是否需重读"决定（按变更重读或使用带失效策略的缓存），**不得**为省一次读取而让需求要求的可变内容被冻结在首次读到的版本上
** **判定标准（任一命中即违规）**：①热点路径的调用体内出现 `getResourceAsStream`/`ClassPathResource` 读取（如 `new DefaultRedisScript` 在方法内、`ScriptUtils` 每次调用执行脚本读取）；②Redis 热点操作每次都把脚本正文重发服务端且不做 `EVALSHA` 复用；③反向误用——把需求要求可变的模板/脚本按静态常量一次性读死
* **`@Sql` / `ScriptUtils`（L2）**：测试里的 `@Sql`、`ScriptUtils.executeSqlScript(...)` 等同样指向 `.sql` 资源，不内联 SQL。
* 依据（标准名/编号）：OWASP SQL Injection Prevention Cheat Sheet、OWASP Query Parameterization Cheat Sheet、Redis 官方文档（EVAL / Redis Lua API reference）、MyBatis 官方文档（Dynamic SQL 的 `${}` 与 `#{}`）、ISO/IEC 25010 性能效率（资源重复读取的取舍）。

== 健壮性

* 公共方法对边界输入显式处理：null 入参、无匹配结果必须返回空集合/默认值或快速失败（requireNonNull/断言），不得让调用方遇到隐式 NPE
* 禁止修改调用方传入的可变入参（数组、集合、对象内容）；确需就地处理时，API 契约必须显式声明
* 消费输入流必须保证后续可用：读取后重新缓冲再返回，异常路径不得返回已消费且未重缓冲的对象
* 资源生命周期归属一致：static 线程池等全局资源不得由实例 @PreDestroy 关闭，防止多上下文互相影响
* 字节数组转字符串必须显式指定字符集；HTTP 文本内容优先从 Content-Type 解析 charset，未声明才使用默认值
* 链式字符串替换使用占位符或一次性正则，避免替换产物被后续规则二次改写；缓存键命名不得与输入空间可能出现的值冲突
* 按标准协议（如 HTTP 报文）拼接日志或输出时，结构须符合协议规范（首行即协议行，不得以空行开头、不得插入非协议内容）
* 需要内存回收（弱引用/软引用语义）的缓存统一使用 Caffeine 的 weakKeys/weakValues/softValues，禁止手写 WeakHashMap/软引用自实现

== javadoc

注释需满足发布私服 / Maven 中央仓库的 javadoc 检查（doclint）要求：

* 多行注释永远写多行：`/**` 单独一行、注释内容逐行书写、`*/` 单独一行，禁止单行写法 `/** xxx */`；javadoc 使用完整多行块，包含 `@param`、`@return`、`@throws`、`@since`
* **所有 public/protected 方法与字段必须有 javadoc**（**明文要求，非仅靠 doclint 推导**）：每个公共成员一条 javadoc——**方法**含职责说明与 `@param`（与参数一一对应、名称一致；泛型用 `@param <T> 描述`）/`@return`（非 void 必须）/`@throws`（受检异常必须）；**字段**说明含义、默认值及配置方式（无参无返回值，不标注 `@param`/`@return`/`@throws`）；**不得因"编译能过、doclint 不报"而省略**——缺少 javadoc 即视为未完成
* 从独立文档迁移时**逐方法落位**：原文档"方法列表/功能说明"里的每个方法条目都要落到对应方法的 javadoc（不得只补类级描述，映射清单见 link:../general/doc-design.adoc[]「存量文档收敛」）；**文档并入 javadoc 后移除对应 `@see`**——某类/方法的内容已完整并入、独立文档随之删除后，`@see` 指向的文档已不存在，须同步移除该 `@see`（`@see` 仅指向仍需保留的功能/模块级设计文档，即"有对应设计文档则保留、文档没了则去掉"）
* 版本号用 `@version` 维护：类级 javadoc 用 `@version` 标注源文件版本，随行为/接口/默认值/已知缺陷等变更递增（初始 `1.0`）；**变更摘要统一写入项目根的统一 changelog（时间倒序）**，不在源码或设计文档中另行维护变更日志（机制见 link:../general/doc-design.adoc[]「版本与变更记录」；**写入时机见 link:../general/changelog.adoc[]「何时记录（由明确要求触发）」**——未被要求时不写条目，但 `@version` 仍按本条随变更递增）
* 特殊字符必须转义：`< > &` 使用 `&lt; &gt; &amp;`，或使用 `{@code ...}` 包裹；HTML 标签必须闭合：`<p>` 换行、`<ul><li>` 列表正确嵌套闭合
* 构建器 setter 方法注释须标注 `@param`、`@return this`
* 代码与设计文档双向引用：类/方法的 javadoc 用 `@see "..."` 指向对应的设计文档（**文档承载该功能/模块的总结与规划，不要求逐类同名的设计文档**；类级描述本身写在类 javadoc：一句话定位 + 能力目录）、如有对应测试设计文档一并 `@see`（独立成篇的测试设计文档取测试类名，如 `FooTests` → `FooTests.adoc`）；**路径基准统一为"相对模块根"的路径**（即从该源文件所属模块的根目录起算，不受源文件所在包层级影响）——落点按文档规范（多模块项目为 `<模块>/doc/...`，业务系统单模块为 `doc/<设计阶段>/<模块>/...`，见下），**无论引用方源文件位于哪层包，路径都从模块根写起**（如模块根下 `doc/3-design/core/xxx.adoc`，则 `@see "doc/3-design/core/xxx.adoc"`）；**不写 `../` 形式的"相对当前文件"路径**（写 `../` 会随包层级变化而失效）。这是对通用文档规范「引用路径」（文档中的 link 引用用相对当前文件所在目录的相对路径）的**显式例外**：javadoc `@see` 由 IDE/javadoc 解析，模块根相对使路径不受文件所在包层级影响、模块内一致且利于 IDE 跳转，同一仓库不得混用"相对当前文件"的 `../` 形式；**路径以实际存在的文档为准**：有对应设计文档则 `@see`，**没有则不写 `@see`**（不得写指向不存在文件的路径），**也不得以"补 `@see`"为由强制新建文档**——javadoc 本身就是文档，是否另设功能/模块级设计文档按 link:../general/doc-design.adoc[]「信息归属」的内容范围决定（内容已并入代码文档注释的按上条移除 `@see`）。本条的"不强制新建文档"只针对**独立文档的存在性**，**不得据此减少 javadoc 自身的内容要求**（见上「所有 public/protected 方法与字段必须有 javadoc」）；落点：业务系统单模块写 `doc/<设计阶段>/<模块>/`、多模块项目写各模块 `doc/`（见 link:../general/doc-design.adoc[]、link:../general/doc-lifecycle.adoc[]、link:../general/doc-module.adoc[]）；注意 javadoc 的 `@see` 标签要求合法引用，故文档路径须用英文双引号包裹，裸 `@see doc/...adoc`（不带引号）会被 javadoc 当作类/成员引用解析并报错（failOnError 会中断构建），不可使用
* 源类与各类测试类在 javadoc 中互相引用：源类 javadoc `@see` 其各类测试类（`Tests` / `BootTests` / `PerfTests` / `IT`，如有）；各类测试类 javadoc `@see` 源类与同被测类的其他测试类（性能测试类须指向源类与功能测试类，见 link:java-testing.adoc[]「测试类命名」）——使"源类 ↔ 测试/性能测试"的关系由代码互引表达、可被 IDE 与工具遍历，不依赖文档目录索引（通用规则见 link:../general/doc-design.adoc[]「类间关系与双向引用」）
* 测试类 javadoc 与主类对称：测试类类级 javadoc 同样"一句话定位 + 用例目录（覆盖场景清单）+ 该测试的整体设计思路与覆盖取舍"，方法级 javadoc 写该用例细节——**测试意图、该用例的设计思路与依据、边界与断言取舍、测试数据选择理由**（用例编号与文档对应见 link:../general/testing.adoc[]「测试文档」）；这些内容**须完整进代码、不得因放入注释而省略**（原写在测试文档的类/方法级用例设计思路等也一并迁入，见 link:../general/testing.adoc[]「测试文档」）
* javadoc 等文档性缺陷直接修复遵循通用文档规范（link:../general/doc.adoc[]「文件格式与编码」）
* 非文档注释（`//` 行注释、`/* */` 块注释）仅限方法体内使用，用于说明局部逻辑实现；类、字段、方法签名等结构说明一律用 javadoc（`/** */`），不得用普通注释（通用注释定位规则见 link:../general/coding.adoc[]「注释」）
