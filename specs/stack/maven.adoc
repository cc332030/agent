= Maven 规范（技术栈层）

适用于 **Maven 构建**。加载触发特征：项目存在 `pom.xml`、`mvnw`/`mvnw.cmd`。构建/依赖调整前须加载本文件。Node 等其它构建工具按对应栈文件规范。

== 仓库与镜像

* **未配置过 Maven 仓库/镜像、且外网出口 IP 在中国大陆时（L1）**：**动手构建前**，用腾讯云 `https://mirrors.cloud.tencent.com/nexus/repository/maven-public/` 作为 Maven 中央仓库。**必须先用这个仓库**，不得自行另挑镜像站；**仅当它不可用**（连不上、代理不到、报错取不到构件，配置后实测确认）才允许改用**其他在境内的镜像站**。**已配置过即不做**：沿用引用方既有配置，不覆盖、不重配。
* **推荐源（同一级里可互换）**：腾讯云（首选，见上条）、阿里云 `https://maven.aliyun.com/repository/public/`、华为云 `https://repo.huaweicloud.com/repository/maven/`。**中央仓的官方源**（`repo1.maven.org`，经由全球边缘加速）属**更远一级的兜底**，仅在境内源全部实测不可用时才用。**注意**：清华 TUNA、中科大等高校镜像站**没有** Maven Central 目录（实测无 `maven`/`maven-central` 路径），不要把它们当中央仓镜像写进配置。
* **先实测可用再启用、一次配置到位（L1）**：动手构建前候选源须**已实测可取到构件**（取值＝"以真实请求取到构件"这一状态；怎么实测属执行动作，不写进规范）；**已配置过即沿用**；**不得**每轮重试同一个源。判定标准、选源次序与降级条件见 `specs/general/dependency.adoc`「包源（包仓库/镜像站）的选用」。
* **`<mirrorOf>` 取值（L1）**：镜像代理中央仓时 `mirrorOf` 写 `central` 或 `*`；**已经指向私服/其他源的 `repository` 不得被 `*` 整体吞掉**（`mirrorOf` 写成 `*` 会把私服也镜像走，导致私有构件取不到）——私服存在时按 `<mirrorOf>central</mirrorOf>` 或 `external:*` 一类写法把它排除在外。
* **Clojure/Clojars 构件**：`clojure`、`clojars` 的第三方构件不在中央仓，须另加 Clojars 源；境内可用的镜像与实测结论见 `specs/stack/java.adoc`「依赖与仓库（Clojars）」（**中央仓镜像不能替代 Clojars**，但可能已代理该构件——**取值要求＝已实测可取到该构件**）。

== 依赖

* **严禁私自调整依赖**（依赖声明与传递依赖解析规则见 Maven 官方文档的依赖机制一章）。
* **除非有必要**（避免传递依赖版本漂移、传递路径可能失效），否则不重复声明依赖；传递依赖已满足时不显式声明。

== 构建并行度

* **默认启用多线程构建（L2）**：未配置过并行度时，本规范自己发起的 Maven 构建（裸 `mvn`、命令行构建）**默认开 `-T`，取值＝当前构建设备的核心数**，即命令形态 `mvn -T <核心数>`——**本条到此为止：核心数怎么得到是执行动作，不写进规范**（这是本集合对**所有**规则一视同仁的写法：取值只定义到占位符那一层）。**这不是「取一个固定值」**：`-T`/`--threads` 按官方口径支持 `4`（整数）与 `2C`/`2.5C`（核心数倍率）两种写法，而 `C` 被官方写作 core **multiplied**、**未**给「`C` 等于可用核心数」的明文，故取值只到「核心数」这一层、不写成任何一个固定写法。**不写 `-T` 即默认单线程、拿不到多核**。项目已有构建入口（`mvnw`/`mvnw.cmd`）时用入口构建、参数照传。**本条只管多模块构建**：单模块时开 `-T` 拿不到模块级并行，按『改单模块不主动开』（见 `prompts/_common.txt` 的 `build-parallel` 片段）处理。
* **配置过即以配置为准（L2）**：项目已在 `.mvn/maven.config`（或构建入口脚本、`MAVEN_OPTS`/`MAVEN_ARGS` 一类既有配置、工程内 `pom.xml` 的插件配置）里配过并行度时**一律沿用**，**不得覆盖、不得重复追加**：**凡在命令行上再补一次 `-T`，都是覆盖**——同一参数取最后出现者，入口再传一次 `-T` 会压掉项目配置。**项目级配置的落点**＝项目顶层 `.mvn` 目录下的 `.mvn/maven.config`（对多模块构建根生效）——本集合把并行度优先落在这里，而非每次命令行手打（怎么知道配没配过属执行动作，不写进规范）。本项目实证（历史记录：报告方当时的命令是 `mvn -T 1C`，本条取值口径已不再取该写法）：以 `mvn -T 1C` 为默认的仓库，其并行度只写在人手的命令行里、没有落到项目配置，自动化的无参 `mvn` 调用因此继承了默认单线程。
* **并行度只到模块粒度（L1）**：Maven 的 `-T` 是**模块间**并行（反应堆内模块并行构建）。**同一模块内部仍按『同一模块禁止并行构建』串行执行**（该条即下条，通用规则见 `specs/general/testing.adoc`「执行与验证」）。
* **测试并行与并行构建默认为两件事（L2）**：`-T`、Surefire `forkCount`（默认 `1`）与 Surefire 的 `parallel`/`threadCount` **互不替代**——**默认只启用构建并行，不因本条去开测试并行**：Surefire 默认不并行执行测试，启用测试并行是**另一项改动**（作用域从模块内并发扩到测试进程与用例之间），按「**大动之前先确认**」（`prompts/_common.txt` 的 `baseline-and-compat` 片段）先向用户确认后另行落地：须与既有测试兼容（并发用例、共享外部资源、端口与临时目录冲突）、并**显式设 `reuseForks`**：Maven 官方文档对 `reuseForks` 的默认值有两种口径并存（参数表标 `Since 2.13 / Default : true`，3.x 的迁移说明则称 3.0.0 起改为 `false`——每个测试类 fork 一个新 VM；本项目未逐字取回该页）。**依赖默认值等于把「复用 fork」当成既定事实**，故本集合**不裁定哪个默认值为准**，只要求该取值显式写进配置。
* **构建产物不得因并行而退化（L2）**：开启并行后仍须满足**验证以 Maven 结果为准**与 `specs/general/coding.adoc`「无并发隐患」——出现"并行才失败、串行就通过"且无法通过修配置消解时，按 `specs/general/context.adoc`「生成效率」的「失败一次就查根因，不靠重试撞对」条定位到具体模块/插件，并**在该模块收窄并行度**、不得整体退回单线程、也不得靠重试撞过。
* 依据（标准名/编号）：Maven 官方命令行参考（`-T`/`--threads`、`.mvn/maven.config` 的官方说明）、Apache Maven Surefire 插件文档（`forkCount`/`reuseForks`/`parallel` 的默认值与版本）、ISO/IEC/IEEE 25010（性能效率——构建时长是可度量的质量效率）。**"以既有配置为准、不覆盖不重复追加"是本集合的判据化取舍**（官方文档只给机制与默认值，不给"该不该默认开、怎么改既有配置"的口径）。

== 构建与验证

* **同一 Maven 模块禁止并行构建**（通用规则见 `specs/general/testing.adoc`「执行与验证」）；多 agent 协作时同一模块分阶段执行（先写测试文件，再串行执行验证），避免构建冲突。
* **验证以 Maven 结果为准**：Windows cmd 下编译失败 exit code 可能为 0，不得仅凭 exit code 判断，必须依据 surefire 的 `Tests run/Failures/Errors/Skipped` 统计判断是否通过；输出重定向到文件、"获取统计一步到位"等通用验证规则见 `specs/general/verify.adoc`「编译/运行验证」。
