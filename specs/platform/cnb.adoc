= CNB 规范（平台层）

以下规范适用于 **CNB 平台**上的任务开发与合并请求管理，重点约束同一 issue 内多任务并行的分支与合并策略，以及平台流水线/协作中的可追溯性。加载触发特征：在 CNB 平台（cloudnative 代码托管）上进行任务开发与合并请求管理。

== 分支与合并请求统一

[quote]
依据：短生命周期分支、频繁小步合入主干的实践（trunk-based development 与 DORA 的交付性能研究）。

* 同一 issue 拆分出的多个任务，即使并行执行，也**只能修改同一个分支**，不得各自新建分支
* 这些并行任务最终**在同一个合并请求（MR/PR）中**提交并合并，不拆分为多个合并请求
* 并行任务的改动最终全部汇入该合并请求，由该合并请求一并合入目标分支

== 变更范围只限当前项目（未声明即拒绝）

[quote]
依据：变更须有**明确的对象与范围**、且受控可追溯（ISO 10007 配置管理指南「变更控制」；ISO 9001 成文信息控制）。**同义性差异**：这两项标准规定的是"变更须受控、可追溯"，**未**规定"执行者只允许修改当前项目"——后者是本规范集合据其原则**判据化后的自身取舍**。ISO 9241-110 的相关原则（可控、可预期）属**借用其原则**，映射关系见 link:../general/verify.adoc[]「运行契约」③可控性。**本项目（本规范集合的维护方）实证**：AI 在一个项目里工作时被"引用了另一个项目"带着跑，把改动落到了用户**并未授权**的项目上；用户随后明确要求"除非我主动声明，否则只允许修改当前项目"。

**通用口径（规则本体）在 link:../general/scope.adoc[]「改动范围边界规范」**——工作空间边界、未声明即拒绝、引用 ≠ 授权、判定标准、拒绝的形态、已知例外都在那里（对任何环境成立）。本节只写**平台上的追加口径**，两者同向、不互相削弱：

* **只改当前项目（L1）**：**当前项目**＝本次任务的**入口项目**，也就是用户发起本次任务的那个项目/仓库（会话入口所在的工作空间所属的仓库）。任何**越出该项目**的改动（写入、创建、删除、移动、格式化、提交、推送，以及平台侧的建分支/建标签/建 PR/建 Issue/改设置等）一律**不得执行**。
* **未声明即拒绝（L1）**：**除非用户主动声明**把某个其他项目纳入本次范围，否则不得修改任何其他项目；**用户"引用了"另一个项目、或任务内容涉及另一个项目，都不构成授权**——**引用 ≠ 授权**（引用只是把对象读进来作证据/上下文，不等于允许改动它）。此类情形按其「拒绝的形态」处理：①**明确拒绝**该越界改动并说明依据（只读该项目的证据、把改动留在当前项目内完成）；②**说明要改它需要什么**（请用户显式声明"本次允许修改 X 项目"）；③其余**在当前项目内可做的部分照常完成**，不得因拒绝而停摆。
* **例外（唯二的解禁情形，须用户显式给出，不靠推断）**：①**用户显式声明**把某个其他项目纳入本次范围（如"这次可以改 A 和 B 两个项目""把仓库 X 一起改了"）——须在**这次任务里明确说出**，且仅对该次任务、该项目生效，**不得泛化**；②**用户对项目所作的"只读/禁止改动"声明**——该声明**优先**。除此之外的"看起来顺路""反正就差一处""引用它顺手改了""我有权限"一律不放行（**权限是平台能力，授权来自用户的显式声明**）。
* **与"引用其他项目"的边界**：读取、检索、比对、把引用项目的内容当依据/证据（只读）**不在禁止之列**——本规则禁的是**改动**，不是读取；但**只读之后把结论/改动落到哪里**仍按本条：改动只能落在当前项目，落在被引用项目上即越界。
* **判定标准（任一命中即越界，可逐条核对）**：①**改动对象**不是本次任务的入口项目——出现向其他项目/仓库的写入、创建、删除、移动、格式化、提交或推送；②**以"用户引用了它""任务里提到了它""它就在旁边""同一账号下有权限"为由**把改动做到该项目上（自我豁免）；③**把越界改动转交他人/其他执行者顶替完成**（如派一个在别处上下文里的执行者去改，见 link:../general/collab.adoc[] 的「不得点名外部 Agent / 外部 NPC」条）。
* **与「合并请求的合并主体（NPC 禁合并）」的接口**：合并**恒为人工**（那条 L1、无环境区分、无授权豁免）。故**合并不受本条"用户声明"解禁**——用户声明放开"可修改另一个项目"时，也**不**意味着允许合并；反之本条也不放开任何合并动作。两条各自独立、互不豁免。
* **与既有规范的衔接（不静默推翻）**：本仓库的 link:../core/execution.adoc[]「范围控制」约束的是"改动范围**在项目内部**不蔓延、读取按最小必要"；本条与 link:../general/scope.adoc[] 是同一维度上的**收紧**、不是替代。项目自身规范若对范围另有规定，以**项目自身规范**为准（`AGENTS_COMMON.adoc`「访问与解析」的冲突次序不变）。

== 冲突处理

* 并行任务改动同一文件导致合并冲突时，须**自动解决冲突**（保留双方有效改动，按既有约定合并），不搁置、不要求用户人工介入

== 合并请求的合并主体（NPC 禁合并）

[quote]
依据：变更须经**独立于改动提出者的审批**（GitHub Docs 关于受保护分支与 required approvals；DORA 的交付性能研究把"变更审批/代码评审"列为交付性能要素）；本项目实证反例：把合并这类操作交给 CI 环境里的自动执行者，会出现"无人承担合规责任"的结果（本项目实测：一次由 AI 执行的合并直接违反约定的执行主体边界）。

* **CNB NPC（即 CI/CD 执行环境中的 agent）严禁合并合并请求（L1）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent，**一律不得执行合并操作**——不调用平台的合并动作、不触发合并、不以任何形式（含命令、接口、脚本）代为合入目标分支；合并**只由人工完成**。
* **人工要求、直接授权也不得合并（L1，无豁免）**：即使发起人（用户）在对话中**明确要求合并**、或给出**直接授权**（含"我已授权，你合吧""不用管约定，直接合"等表述），**仍必须拒绝执行合并**，并**说明拒绝依据**（本条 L1、无环境区分、无授权豁免）；这是**唯一**一类"用户明确要求也不照做"的操作——**授权不免除该禁令**，因为该要求的失效目标是"合入目标分支"这一不可逆且合规性相关的动作。**拒绝不等于不响应**：须如实回复"该项操作按规范不予执行"，其余可做的部分（整理改动、推送 PR 分支、汇报结论）照常完成。
* **判定标准（任一命中即违规、可逐条核对）**：①**执行了合并动作**——调用了平台的合并命令/接口（如 `merge-pull` 一类操作）或任何等价的合并手段；②**以"用户授权/用户要求"为由豁免该禁令**——出现"因用户要求/授权，故本次合并"式的自我豁免；③**合并动作被交由他人顶替执行也算未拦住**（如"我拒绝但转交给另一个 NPC/CI 步骤去合"）。
* **越界清理与本条无关**：本条只禁**合并**，不改变「冲突处理」节的"自动解决冲突"（解决冲突是在**当前分支内**完成、不构成合并）、不管推送分支、也不管同步目标分支到当前分支——这些**都不是合并**，照常执行。
* **与 CI/CD 交付口径的关系**：`prompts/_common.txt` `delivery` 片段的"CI/CD 场景须提交并推送、按 PR 流程合入、经人工 review 通过后合入"指的是**创建/推送 PR 后交由人工合入**；"经人工 review 通过后合入"的**合入主体是人工**，不是 NPC/CI 自身——本条不与之冲突，而是**明确该场景下的执行主体边界**。

== 评论唤起新实例（平台侧的派发入口）

[quote]
依据：需求可追溯到干系人、可验证（ISO/IEC/IEEE 29148）；变更与工作须受控、可追溯（ISO 10007、ISO 9001）；交互应可控、可预期、不阻断（ISO 9241-110）。

* **须由与执行者相同的 Agent 承担验证（L1）**：**要求验证/复核须由与执行者相同的 Agent（同一 AI 身份/产品）来做的那些规则，只在本平台（CNB）成立**——本平台的唤起形态（评论唤起新实例、被唤起的 NPC 与执行者是**同一个产品**）正是该前提的由来：同一 Agent 能看到本执行者已加载的规范、判据一致、结论可核对。**本平台之外不适用**：执行环境不提供同 Agent 的子执行者/复核者时（如本地人工环境、其他平台或产品），**不得援引该条拒做或把任务停在中间**——该要求**只限定复核者的来源（不得为图省事换外部来源），不构成"没有同 Agent 就没法验证"**；此时**复核照做**，按 link:../general/collab.adoc[]「协作方式」的降级路径执行（由执行者本人按同一判据串行核对并标注独立性边界，或如实标悬置），**最终验证与交付不因此缺失**。判定标准（须逐条核对）：①**环境里确实有同 Agent 的子执行者/复核者可用**时，**应当**用它（此时改用外部来源仍属违规）；②环境**确实不提供**时，适用降级路径、**不以"非 CNB"为由降级或跳过交付**；③**非 CNB 环境不得照抄本条当作强制前提**——条文的写入面本就在平台层（本文件），**不在公共内容（`AGENTS_COMMON.adoc` + `specs/`）里**，引用方项目按入口加载时不会取到它（这正是本条只属 CNB 而不外推的原因）。依据：评审与被评审须相互独立（IEEE 1028）、变更的核验须可追溯到可核对的对象与判据（ISO 10007）；**"由谁承担、用什么入口承担"是项目自身的取舍**（标准只要求"有独立、可核对的评审发生"，未规定复核者须是同一产品或同一来源）。
* **复核者的来源："谁发起的"与"谁承担"的区分（L1，"不能艾特自己"不等于"没人能复核"）**：**"须由与执行者相同的 Agent 承担"说的是复核者的来源要求，不是复核的发起方式**——`@`/评论派发本身受上两条与通用层「评论是"派发者"的入口，不是"执行者"的手段」「执行者不得自行发评论唤起自己」约束，两条**各自独立、不互相构成例外**。故**执行者不得用"为了满足同 Agent 复核"去 @ 自己**（那是自派：同一实例名、同一点名，属上条禁止形态，不因目的是"复核"而放宽），**也不得据此把复核本身丢掉**。本条要解的是本平台上"**一次执行里拿不到另一个同 Agent 执行者**"这一真实情形，判据两条（须逐条核对）：①**能不能拿到，在动手前判定、不在事后补记**——本平台上核对方式只有两条：**(a)** 加载调度器明示的派发方式（见 `AGENTS_COMMON.adoc` 的 CNB 平台条目：`specs/platform/` 下**本平台自身的文档**，不引用私有落点）；**(b)** 环境标志实测（`printenv CNB_EVENT` 非空且触发内容含本任务的唤起名）；两条都取不到同 Agent 子执行者时，**本条按"拿不到"判**、走降级路径，**不得**据此拒做、停任务或等下一轮（等下一轮就要再发一条评论，即自派）；②**不得把"我还想再要一个复核者"当成再发一条评论的理由**——一个任务只由**人**决定起几次执行，缺的复核按降级路径**在本次执行内**补：按 link:../general/collab.adoc[]「协作方式」由执行者本人按同一判据串行核对、**如实标注独立性边界**，或标悬置并写明剩余风险；**"本平台上也拿不到同 Agent 子执行者"不是改用外部 Agent 的理由**（那会把复核换成不可核对的来源，见 link:../general/collab.adoc[] 开头两条）。**该情形下的交付形态（L1）**：**照常交付**（提交、推送、建 PR 照做），在结论里**如实写明"可信的独立复核在本平台当前不可得 + 已做的替代核对 + 剩余风险"**，交人工决定——**"已交付 + 校验全绿 + 复核缺口如实标出"不等于复核已完成**，两者不得混写。**判定标准（任一命中即违规）**：①用 @ 自己（或请他人 @ 自己）换取一次新执行来做复核；②把"拿不到独立复核"写成"已复核通过"；③以"要等下一轮复核"为由把当前任务停在中间、不交付。
* **评论唤起是平台侧的派发方式，不改变派发判据（L1）**：本平台上，**在 Issue 或 PR 下新增一条评论、@ 某个 NPC（**如 `@CodeBuddy`，此处为本仓库的实例名、仅作举例**）、并在评论里说清要求**，即新增一次执行（下称"评论唤起"）。本条**只把"往哪派"说清楚，不放宽任何派发约束**：派给谁、用不用外部 Agent、派发须钉定对象、须自带硬超时、派发前确认执行者可执行（含确认该 NPC 在本仓库上可用、被唤起后仍须自行按入口加载规范）——**一律按 link:../general/collab.adoc[] 执行**，本条不另立判据、也不构成"可以点名外部 Agent"的例外。
* **一次评论 = 一次派发，任务边界由评论正文界定（L1）**：被唤起者收到的**只有一条评论正文**，Issue/PR 上已有多少条评论、上下文攒得多长，**由同一条评论内的显式要求决定**（见下条）；其余一律以下两条为限。故**要求须在评论里写清**：要做**什么**、**边界**（改哪、不改哪）、**产物形态**（只分析 / 改代码 / 出报告）与**验证口径**——"写清了"由执行者按这四项逐项判定，**缺项或判据不满足时须在原评论下回复"拒绝 + 列出缺失项"或请发起人补一句，不得开工、不得拿"他没写清"当擅自扩大范围的挡箭牌**（留证落点即该条评论下的回复），**未写清的不得自行假定后开工**（"目标、范围、产物形态不明确时不得自行假设"，见 link:../core/execution.adoc[]「指令执行」）。写清的形态就是一次派发的派发指令，故同样须钉定对象、自带时限。
* **要求"用干净上下文"是派发选项，须在评论里显式要求（L1）**：默认情况下一条评论发起的执行**沿用该 Issue/PR 的既有上下文**（此前讨论中的结论与前提会被读到，旧结论、已放弃的方案与无关细节可能先入为主）。评论里**显式要求"使用干净的上下文/不要参考此前评论、按本次要求独立判断"**时，被唤起者须把本次任务**当作一次全新任务**执行：①**不复用**此前讨论中的结论与前提，需要先前的事实一律按**对象钉定**重新取值（钉 commit sha，见下「对象钉定与可追溯」）；②**规范仍须按入口重新加载**（"上下文干净"只清历史对话，**不清约束**，见 `AGENTS_COMMON.adoc`「从属者（子 agent/被引用方）适配由已加载入口驱动、不靠自报」）；③评论里已写明的**本次边界**（如"只评本次 diff""只看这一段"）随之生效。**该要求属降低风险的措施、要求不是保证**：要求了不保证真的发生（执行侧能否新开会话属环境能力，见 link:../general/self-check.adoc[]「环境能力自评」），故**须在结论里如实说明本次实际读到的上下文范围**——不得"记成"已用干净上下文。凡"复核不独立、结论不可核对"的隐患，按 link:../general/collab.adoc[] 处理（该文件开头两条：子任务强制同 Agent、不得点名外部 Agent/NPC）。**边界两句必须一起读**：**该要求不豁免任何派发判据**（同 Agent、钉定对象、硬超时、派发前确认执行者可执行一律照判），**"记住"不构成约束豁免**；反过来**"我说了用干净上下文"也不构成"连本次对象钉定都要另取一套"**——钉的是本次要处理的那个对象。
* **不得以评论派发唤起自己（L1，防无限派发）**：**被评论唤起的执行者不得在本次执行中再发一条评论去点名唤起自己**（同一点名、同一实例名——不论有无"再干一件"的理由，也不论是否写明用干净上下文），**也不得转由他人/其他执行者发布这条评论**。判定标准（任一命中即违规）：①本次执行期间**新增的点名评论指向本条评论上的唤起名**（三性判定见 `specs/core/execution.adoc`「破坏性操作（不可逆，先确认再动手）」：目标是否是要动的那个、能否撤回、范围是否可界定；本条只把**发评论**这一动作显式列为须先确认的一类）；②以"分两步更清楚""上一轮没做完"等理由自我豁免；③实际发了这条评论、把任务在执行中重新发起一次（**不因"不在同一进程内"而不算**：判据是**这条评论发出去没有**，不是这次执行有没有因此结束）；④把发这条评论交给子 agent 或他人代发（转交他人顶替执行亦算未拦住）。**为什么必须拦住**：唤起一次就是新增一次执行、要重新按入口加载规范并付一次调用与等待；"再派一次"最容易被"换个节点更专注"或"上下文更干净"合理化成自动动作，而**跨轮分步要由人来决定**——一次评论就是一次派发（见下条），**发起下一次是派发者的动作，不是执行者的动作**。**正当形态（一次执行一处落点）**：想分步就**先停**、在执行者这一侧只输出一次"停下确认"（把"已做完哪一段、下一步要什么"一次性写清），由**人**在任务单下另发一条评论决定是否再来一次——**执行者不发那一条**。本条的"唤起名"由项目自身规范给出（本仓库为 `@CodeBuddy`，见上文"仅作举例"那句）。
* **唤起不等于自动开工（L3，须先判读）**：单条评论只写"@ 某人"或只有寒暄/表情时，**不构成一份可执行的派发**——被唤起者不得据此自行开工，应回问"要做什么、范围与产物形态"（同"不自行假设"，见 link:../core/execution.adoc[]「指令执行」）。

== 执行吞吐（平台侧的两处特有代价）

[quote]
依据：一次执行=一次新的唤起与一轮加载（本平台的唤起形态）；交互应可控、可预期、不阻断（ISO 9241-110）；性能是质量属性、须可度量（ISO/IEC/IEEE 25010）。**本条只在 CNB 上成立**：它讲的代价（唤起一次=一次完整加载、状态须靠平台侧查询）是**本平台的形态**带来的，不是通用要求。

* **一次唤起 = 一次完整加载 + 一轮往返（L1）**：本平台上"唤起一次"就多付一次规范加载、一次仓库检出的等待与一轮执行；故**派发侧**：同一任务不要拆成多次评论派发（要拆也由**人**决定，见上「评论唤起新实例」的自派禁令），**要求须一次写全**（做什么、边界、产物形态、验证口径，四项缺一即按"未写清"处理）。**执行侧**：本次执行内的往返须尽量合并（判据见 link:../general/context.adoc[]「执行吞吐」）——**不要为了"刷新一下某个长流程"另起一轮**。
* **长流程的状态查询要批量、要有一把梭的判据（L2）**：本平台上查看构建/流水线状态、AI 用量与请求明细、阶段耗时是**独立接口**（`build` 模块的状态/阶段/日志/AI 明细），逐个查会各付一轮。故：**先取汇总、再按需下钻**（先取构建状态与阶段耗时定位"花在哪一段"，只在需要时才取日志或请求明细），**状态与统计一次取全**（同一批把要看的几个构建/SN 一起查）；**不要**用"只发一次状态查询"这种零信息的往返来等长流程（实测：有任务在 `pending` 上推进 3038 s 而阶段耗时始终为 0，只能人工中止——这是"在跑与卡住不可分辨"的现场，见 link:../general/ci-cd.adoc[]「超时与资源」）。
* **AI 用量与请求明细是本地化的观测手段（L2）**：本平台的 **AI 用量汇总**（输入/输出 token、请求数、生成耗时）与 **AI 请求明细**（每次请求的 prompt 体积、起止时延、页码分页）是"这次执行慢在哪"的**直接证据**，属本平台特有的可观测面。做提速类任务、或在报告里判定"慢的原因"时，**以这两处的实测取值为准**，不要凭印象说"网慢/模型慢"；取值口径与量级实证见 link:../../library/throughput.adoc[]（**该库不在公共引用面内，本条不要求引用方加载它**——它是本仓库的记录落点）。

== 压缩提交（提交历史的整理）

[quote]
依据：变更与工作须受控、可追溯（ISO 10007、ISO 9001）——整理提交历史属受控变更，须可追溯；**该标准只要求"变更可追溯、可定位"，未规定"提交必须压成一个"**（同义性差异：本仓库的压缩口径是项目自身取舍，不是标准要求）。

* **压缩提交＝提交历史整理，不属禁止行为（L1）**：用户要求"压缩提交/压成一个提交"时按本条执行；它与"人工该不该合入目标分支"无关——见本节末条。判定标准（须逐条核对，缺一不可）：①**压缩对象只有本次任务产生的、尚未合入目标分支的临时中间提交**（本任务的多次试跑修正、迭代补丁、过程性提交）；②**内容零变化**——压缩前后工作区内容**逐字节相同**（以 `git diff` 无输出为准），只改变提交的分组与信息，不夹带任何新增/删除/改写；③**只作用于本次任务自己的 PR 源分支**，不动目标分支、不动他人分支（越界即按 link:../general/scope.adoc[] 拒绝）。
* **压缩须保留与目标分支的合并关系（L1）**：压缩/改写时，**不得把「已并入目标分支」这一事实一并丢掉**——若本分支此前已并过目标分支（或本就基于目标分支的最新提交），压缩后的提交**必须仍以目标分支的最新提交为祖先**（等价判据：`git merge-base <分支> <目标分支>` 等于目标分支最新提交；`git merge --no-ff <目标分支>` 时**须保留双亲**，即产物是一个**合并提交**、`git rev-list --parents -n1` 显示两个父提交）。**根因（真实失效）**：把"解决冲突"做成"照抄目标分支的文件内容后另起一个单亲提交"，工作树看起来一致、`git diff` 也看不出毛病，但**目标分支并未成为本分支的祖先**——平台侧据合并关系判定，**仍报冲突、PR 卡在 `code_conflict`**（本仓库 PR 的真实形态：`git rev-list --parents -n1` 只显示一个父提交，且 `git merge-base --is-ancestor <目标分支> <分支>` 为假）。**判定标准（任一命中即违规）**：①压缩/合并后用单亲提交承载"已含目标分支内容"；②只比工作树差异就宣称"冲突已解决、已含目标分支全部改动"；③汇报"合并关系已建立"却未给出可核对的判据（祖先关系或双亲）。**正确做法**：真做一次合并（`git merge`，冲突逐处解决）后**以合并提交落盘**；用户要求压缩时，压缩**只整理本分支自己的中间提交**、**不吞掉合并提交**（合并提交是"已并入"的凭据，不是可压掉的临时提交）。
* **禁止的压缩形态（L1）**：①把**他人（或其它任务）的提交**一并压缩（含并行任务在同一分支上产出的提交——那会顶掉别人的历史，其留证 sha 随之作废）；②压缩**已合入目标分支**的历史（改写公共历史）；③压缩后**内容出现任何差异**（哪怕只是夹带一处顺手改动）；④以"压缩提交"为由**扩大范围**（顺带整理无关文件、重排他人提交、改提交信息里的他人署名）。
* **须先确认无人在用旧对象（L1）**：压缩后要做 force push，故执行前须确认**无他人正基于该分支的旧 sha 工作**（已派发、正等待结论）；确需执行时须**明确告知受影响方**新 sha、并把旧 sha 上的结论标为过期（口径见 link:../general/collab.adoc[] 的「压缩提交/强推前确认无人在用旧对象」一条；本仓库三次评论派发的实证正属此类）。
* **压缩后须声明新旧 sha 对应关系（L1）**：执行后在 PR 说明或汇报中写明"**已压缩为一个提交，新 sha 为 X，旧 sha Y 作废**"，并如实列出被压缩掉的中间 sha；**下游按旧 sha 复核的结论视为过期**，须在新 sha 上重核，不得把过期结论计入本 PR（见下「对象钉定与可追溯」）。
* **推送口径（L1）**：压缩必然改写分支历史，故推送**需要**覆盖远端；此时用 `--force-with-lease`（带租约的强推，确认远端仍是本地已知的那次推送后才覆盖），**不得**用裸 `git push --force`（无条件覆盖，可能顶掉他人刚推上来的提交）。"AI 不做强推"的一般口径**不适用于本条的压缩提交**——用户明确要求压缩提交时，按本条执行即属授权；但**授权范围仅限本次 PR 的源分支**，不得借压缩之由动其它分支。
* **与「NPC 禁合并」互不豁免（L1）**：压缩提交**不是合并**（它只整理当前分支自己的历史、不把改动合入目标分支），故用户要求压缩提交时照做；反过来**压缩提交也不构成"可以合并"的依据**——"改动已成熟/历史已整理干净"不构成合并的例外，合入目标分支仍**只由人工完成**（见上「合并请求的合并主体（NPC 禁合并）」，其"唯一一类用户明确要求也不照做"的定性不变）。

== 对象钉定与可追溯

* **派发与复核须钉定 commit sha，不得只说分支名（L1）**：CNB 上同一分支会被多次推送（并行任务、整改追加提交、按上「压缩提交」整理后强推——那是**合规动作、不是违规改写**），**分支名不构成稳定标识**。凡把"某分支/某 PR 的改动"作为复核、比对、追溯对象时，必须**钉定具体 commit sha**（`refs/pull/<n>/head` 对应的 sha），并在派发/汇报中写明；**收到"基于某分支"的对象时，须先强刷 ref 再取 sha**（`git fetch -f` 后 `git rev-parse`）——CNB 本地缓存可能停留在旧 sha（实证：复核者按分支名取到已被压缩提交取代的旧对象，逐项比对后误判"改动不存在"，而实际改动已推送且存在；另一位参与者又取到另一个中间 sha，三方口径各错一个版本）；**合并**这一动作除本节的对象钉定外，还受上节「合并请求的合并主体（NPC 禁合并）」约束（执行主体恒为人工）。
* **压缩提交/强推会替换对象，须声明对应关系（L1）**：对分支做 `squash`/`rebase`/force push 后，**旧 commit 对象从分支历史移除**、无法再按 sha 取回。故：①执行后须在 PR 说明或汇报中写明"已压缩为一个提交、新 sha 为 X，旧 sha Y 作废"（让下游知道去哪核）；②**下游按旧 sha 复核的结论视为过期**，须在新 sha 上重核，不得把过期结论计入本 PR；③力推前须先确认**无他人正基于旧 sha 工作**（见 link:../general/collab.adoc[] 的失联感知与硬超时条的"派了就一直等"实证）。
* **CI/流水线状态须按构建号（sn）与 sha 关联（L2）**：核对流水线结果时以 **sn + sha** 组合定位当次构建，不按"分支最新一次"想当然取值（同一分支可能同时有多次构建、旧构建可能仍在 pending）。

== 协作与执行者可用性

* **派发前确认执行者实际可用（L1）**：向平台上的 NPC / 子执行者派发任务前，须确认其**产物实际存在且可取**——镜像/制品包在制品库中存在（实证：某 NPC 的制品包 `…/npc-skills` 在制品库 `not found`，流水线在 `Prepare` 阶段 `docker pull` 失败，复核从未真正开始，与被复核内容无关）；且同名 NPC 可能有多个不同来源的 slug，须用**确证可用的那个**，不得凭名称假设。
* **派发须自带超时与放弃处置（L1）**：平台协作的等待必须有可判定的时限，到点即放弃并如实标悬置，不得无限等待（口径见 link:../general/collab.adoc[] 的失联感知与硬超时、超时的处置两条）。
* **流水线不无界挂起（L1）**：平台流水线的 job/step 须设可判定的超时，不得长期停在 pending 而不失败（口径见 link:../general/ci-cd.adoc[]「超时与资源」）。
