= CNB 规范（平台层）

以下规范适用于 **CNB 平台**上的任务开发与合并请求管理，重点约束同一 issue 内多任务并行的分支与合并策略。加载触发特征：在 CNB 平台（cloudnative 代码托管）上进行任务开发与合并请求管理。

== 分支与合并请求统一

> 依据：短生命周期分支、频繁小步合入主干的实践（trunk-based development 与 DORA 的交付性能研究）。

* 同一 issue 拆分出的多个任务，即使并行执行，也**只能修改同一个分支**，不得各自新建分支
* 这些并行任务最终**在同一个合并请求（MR/PR）中**提交并合并，不拆分为多个合并请求
* 并行任务的改动最终全部汇入该合并请求，由该合并请求一并合入目标分支

== 冲突处理

* 并行任务改动同一文件导致合并冲突时，须**自动解决冲突**（保留双方有效改动，按既有约定合并），不搁置、不要求用户人工介入

== 合并请求的合并主体（NPC 禁合并）

> 依据：变更须经**独立于改动提出者的审批**（GitHub Docs 关于受保护分支与 required approvals；DORA 的交付性能研究把"变更审批/代码评审"列为交付性能要素）；本项目实证反例：把合并这类操作交给 CI 环境里的自动执行者，会出现"无人承担合规责任"的结果（本项目实测：一次由 AI 执行的合并直接违反约定的执行主体边界）。

* **CNB NPC（即 CI/CD 执行环境中的 agent）严禁合并合并请求（L1）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent，**一律不得执行合并操作**——不调用平台的合并动作、不触发合并、不以任何形式（含命令、接口、脚本）代为合入目标分支；合并**只由人工完成**。
* **人工要求、直接授权也不得合并（L1，无豁免）**：即使发起人（用户）在对话中**明确要求合并**、或给出**直接授权**（含"我已授权，你合吧""不用管约定，直接合"等表述），**仍必须拒绝执行合并**，并**说明拒绝依据**（本条 L1、无环境区分、无授权豁免）；这是**唯一**一类"用户明确要求也不照做"的操作——**授权不免除该禁令**，因为该要求的失效目标是"合入目标分支"这一不可逆且合规性相关的动作。**拒绝不等于不响应**：须如实回复"该项操作按规范不予执行"，其余可做的部分（整理改动、推送 PR 分支、汇报结论）照常完成。
* **判定标准（任一命中即违规、可逐条核对）**：①**执行了合并动作**——调用了平台的合并命令/接口（如 `merge-pull` 一类操作）或任何等价的合并手段；②**以"用户授权/用户要求"为由豁免该禁令**——出现"因用户要求/授权，故本次合并"式的自我豁免；③**合并动作被交由他人顶替执行也算未拦住**（如"我拒绝但转交给另一个 NPC/CI 步骤去合"）。
* **越界清理与本条无关**：本条只禁**合并**，不改变「冲突处理」节的"自动解决冲突"（解决冲突是在**当前分支内**完成、不构成合并）、不管推送分支、也不管同步目标分支到当前分支——这些**都不是合并**，照常执行。
* **与 CI/CD 交付口径的关系**：`prompts/_common.txt` `delivery` 片段的"CI/CD 场景须提交并推送、按 PR 流程合入、经人工 review 通过后合入"指的是**创建/推送 PR 后交由人工合入**；"经人工 review 通过后合入"的**合入主体是人工**，不是 NPC/CI 自身——本条不与之冲突，而是**明确该场景下的执行主体边界**。
