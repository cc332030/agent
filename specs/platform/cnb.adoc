= CNB 规范（平台层）

适用于 **CNB 平台**上的任务开发与合并请求管理，重点约束同一 issue 内多任务并行的分支与合并策略，以及平台流水线/协作中的可追溯性。加载触发特征：在 CNB 平台（cloudnative 代码托管）上进行任务开发与合并请求管理。

== 分支与合并请求统一

依据：短生命周期分支、频繁小步合入主干的实践（trunk-based development 与 DORA 的交付性能研究）。

* 同一 issue 拆分出的多个任务，即使并行执行，也**只能修改同一个分支**，不得各自新建分支。
* 这些并行任务最终**在同一个合并请求（MR/PR）中**提交并合并，不拆分为多个合并请求。
* 并行任务的改动最终全部汇入该合并请求，由该合并请求一并合入目标分支。

== 变更范围只限当前项目（未声明即拒绝）

**通用口径（规则本体）在 `specs/general/scope.adoc`「平台上的仓库边界（代码托管平台）」**（下文路径写作 `../general/scope.adoc` 同指该文件）——工作空间边界、未声明即拒绝、引用 ≠ 授权、判定标准、拒绝的形态、已知例外都在那里。本节只写**平台上的追加口径**，两者同向、不互相削弱：

* **平台会放大可写范围（L1）**：本平台上"可写范围"不是一棵工作目录树，而是**当前执行者账号有权访问的全部仓库**——故本条的禁令**按当前项目（仓库）表达**：**只允许修改当前项目**（当前项目＝本次任务的**入口项目**，即用户发起本次任务时所在的那个仓库）。判定标准（任一命中即越界，逐条可核）：① 改动对象**不在入口项目内**；② 以"引用过它""同一个账号下就能推""反正有权限"为由自我豁免（**权限是平台能力，授权来自用户的显式声明**）——**引用 ≠ 授权**，用户"引用了"另一个项目或任务涉及它，**不构成授权**；③ 改动**落在其他仓库上**（含转交他人顶替完成）。完整的空间边界、未声明即拒绝、引用 ≠ 授权、拒绝的形态与已知例外**只在** `specs/general/scope.adoc`「平台上的仓库边界（代码托管平台）」——本节不复制其正文。
* **本平台上的两处特有落点（这两条不在通用层，只在此处）**：① **合并恒为人工**——合并**不受**"用户声明放开可修改另一个项目"的连带影响，两条各自独立、互不豁免（见本文件「合并请求的合并主体（NPC 禁合并）」）；② **平台侧的建分支/建标签/建 PR/建 Issue/改设置**同样算"改动"，同样只对当前项目成立。
* **已知例外（唯二，须用户显式给出、不靠推断）**：① **用户显式声明**把某个其他项目纳入本次范围——仅对该次任务、该项目生效、不得泛化；② **用户声明某个位置"只读/禁止改动"**——该声明优先。逐条判据见 `specs/general/scope.adoc`「已知例外」。
* **与「范围控制」的关系（不静默推翻）**：`specs/core/execution.adoc`「范围控制」管的是"改动范围**在项目内部**不蔓延、读取按最小必要"；本条与 `specs/general/scope.adoc` 是同一维度上的**收紧**、不是替代。项目自身规范若对范围另有规定，以**项目自身规范**为准。
== 冲突处理（平台侧追加口径）

**规则本体（工具无关）在 `specs/general/version-control.adoc`「冲突处理」**（先解冲突、再压缩、最终只有一个提交，以及解冲突后须核查是否丢失内容的三档判据都在那里）；**git 侧的核对命令**见 `specs/general/git.adoc`「冲突与压缩提交（git 侧落地）」。本节只写本平台上的追加口径：

* **并行任务冲突照常自动解决（L1）**：本平台的触发面取值＝**并行任务**改动同一文件造成的合并冲突（判据与通用层同一份，见 `specs/general/version-control.adoc`「冲突处理」的『有冲突须解决，不搁置』）；本条不另立判据。
* **交付形态按本平台的合并请求表达（L1）**：通用层的"最终只有一个提交"在本平台上即——**该合并请求的源分支上只有一条提交**（`git log --oneline <目标分支>..HEAD` 只给出**只有一条**这个结果；逐条判定标准见 `specs/general/git.adoc`「冲突与压缩提交（git 侧落地）」）。
* **"只被要求压缩提交"时冲突处置不豁免（L1，本题的用户点名形态）**：本平台上的要求常只写一件事（"压缩提交/压成一个提交"），而**没提**解决冲突——**没被要求不等于可以搁置**：此时若源分支与目标分支**实际存在冲突**，须按通用层「冲突处理」**先解冲突、再压缩**（触发面见 `specs/general/version-control.adoc`「冲突处理」的『"只被要求压缩、没被要求解决冲突"也要先解冲突』一条）。**判定标准（任一命中即不合规）**：① 汇报里只报"已压缩提交"、对冲突只字未提；② 以"要求里只写了压缩"为由只压不解决、或把冲突留到压缩之后再议；③ 用"照抄目标分支的文件内容 + 单亲提交"冒充冲突已解决（工作树一致，但目标分支**并非本分支的祖先**，平台侧仍报冲突——判据 `git merge-base --is-ancestor <目标分支> <分支>`）。**与「NPC 禁合并」的关系**：解冲突是在**当前分支内**完成、**不是合并**，两条各自独立、互不豁免。
* **原文口径（不得被工具专名替代）**：本条的用户原话是"版本管理"——**不得**把它读成"只对 git 成立"或"只对 CNB 成立"；规则本体在通用层，换用 SVN/其他版本管理工具同样成立，只是核对命令随之更换。

== 合并请求的合并主体（NPC 禁合并）

依据：变更须经**独立于改动提出者的审批**（GitHub Docs 关于受保护分支与 required approvals；DORA 的交付性能研究把"变更审批/代码评审"列为交付性能要素）；本项目实证反例：把合并这类操作交给 CI 环境里的自动执行者，会出现"无人承担合规责任"的结果。

* **CNB NPC（即 CI/CD 执行环境中的 agent）严禁合并合并请求（L1）**：在 CNB 平台上由 NPC/CI 环境唤起执行的 agent，**一律不得执行合并操作**——不调用平台的合并动作、不触发合并、不以任何形式（含命令、接口、脚本）代为合入目标分支；合并**只由人工完成**。
* **按执行环境保证（L1，与"谁在跑"无关）**：执行**独立于被合并 PR 的源分支**——本条的目的不是"某个 agent 守规矩"，而是**合并动作在任何执行环境里都不会被自动执行者触发**。故：① **本节全部判据对 NPC 与人工场景一律成立**（本仓库的机械校验核的是**提交说明与分支状态**，不看提交者身份）；② **不许把"我知道这条规则"当作保证**——`CNB_TOKEN` 在 CI 环境里**能**执行平台动作、`cnb pulls merge-pull --repo … --number …` 正是可用的合并入口，故"守规矩"必须落成**可核对的判据**（`merge_commit == null`、源分支 HEAD == 并发唤起时钉定的 sha、**分支历史里没有"并进外部提交"的合并提交**——把目标分支并回来不在此列，见下条：合并提交正是"已并入"的凭据）与**提交说明的留痕**，而不是留在记忆或自述里；③ **人以外的任何自动步骤（含"拒绝后转交的另一步"）都不构成人工**。
* **人工要求、直接授权也不得合并（L1，无豁免）**：即使发起人（用户）在对话中**明确要求合并**、或给出**直接授权**（"我已授权，你合吧""不用管约定，直接合"），**仍必须拒绝执行合并**，并**说明拒绝依据**；这是**唯一**一类"用户明确要求也不照做"的操作——**授权不免除该禁令**，因为该要求的失效目标是"合入目标分支"这一不可逆且合规性相关的动作。**拒绝不等于不响应**：须如实回复"该项操作按规范不予执行"，其余可做的部分（整理改动、推送 PR 分支、汇报结论）照常完成。
* **判定标准（任一命中即违规、可逐条核对）**：① **执行了合并动作**——调用了平台的合并命令/接口（本平台的合并入口是 `cnb pulls merge-pull`，其权限面即 `repo-pr:rw`）或任何等价的合并手段；② **以"用户授权/用户要求"为由豁免该禁令**；③ **合并动作被交由他人顶替执行也算未拦住**（"我拒绝但转交给另一个 NPC/CI 步骤去合"）。
* **本仓库实证失效（L1，实际发生过一次）**：本仓库曾把"合并提交"发为用户原话后**追加执行**——原话要求的是"压缩提交"（处理 PR 最后一个需要交付的动作），执行者却把它读成"最后一个待办是合并"、直接调平台合并、在 PR 下回"已合并 ✅/squash 合并/合并提交：<sha>"，而**原话里的"压缩提交"一件都没做**、也**没有停下确认**。三处成因，逐条都在上文本条的判据里：① **凭据可用**——CI 环境里 `CNB_TOKEN` 能执行平台动作，`cnb pulls merge-pull` 直接可用；② **"合并"的字面诱惑**——"合并提交/合并关系/合并分支"与"合并 PR"共用一个词，一条不带边界说明的指令极易被读成授权；③ **没有交付终点**——执行者当时以"PR 已合并"收尾，把"交付到创建/推送 PR 分支为止"的终点丢了。**由此固定一条形态**：**"最后一个动作"的默认读法是"交付到 PR 分支为止"，不是"把 PR 合掉"**——用户要的是压缩/整理时，**先把那件事做完**，合并**一律不做**。
* **越界清理与本条无关**：本条只禁**合并**，不改变「冲突处理」节的"自动解决冲突"（解决冲突是在**当前分支内**完成、不构成合并）、不管推送分支、也不管同步目标分支到当前分支——这些**都不是合并**。
* **与 CI/CD 交付口径的关系**：`prompts/_common.txt` 的 `delivery` 片段的"CI/CD 场景须提交并推送、按 PR 流程合入"指的是**创建/推送 PR 后交由人工合入**；"经人工 review 通过后合入"的**合入主体是人工**。

== 评论唤起新实例（平台侧的派发入口）

依据：需求可追溯到干系人、可验证（ISO/IEC/IEEE 29148）；变更与工作须受控、可追溯（ISO 10007、ISO 9001）；交互应可控、可预期、不阻断（ISO 9241-110）。

* **须由与执行者相同的 Agent 承担验证（L1，本平台成立）**：**要求"验证/复核须由与执行者相同的 Agent（同一 AI 身份/产品）"的那些规则只在本平台（CNB）成立**——本平台的唤起形态（评论唤起新实例、被唤起的 NPC 与执行者是**同一个产品**）正是该前提的由来。**本平台之外不适用**：环境不提供同 Agent 的子执行者/复核者时**不得援引该条拒做或把任务停在中间**——该要求**只限定复核者的来源（不得为图省事换外部来源），不构成"没有同 Agent 就没法验证"**；此时**复核照做**、**验证与交付不因此缺失**，按 `specs/general/collab.adoc`「协作方式」的降级路径执行（**由谁承担**是**项目自身的取舍**：标准（IEEE 1028）只要求有独立、可核对的评审发生、未规定复核者须是同一产品）。
** **与「不得以评论派发唤起自己」的关系**：**复核者的来源**要求**不是复核的发起方式**——两条各自独立、不互相构成例外。故**执行者不得用**"为了满足同 Agent 复核"去 @ 自己（那是自派，不因目的是复核而放宽），也**不得据此把复核本身丢掉**（"不许自派"读不成"不必复核"）。**一个任务只由**人**决定起几次执行**：缺的复核**在本次执行内**按降级路径补（本人串行 + 标注独立性边界，或标悬置 + 写剩余风险），不得靠再发一条评论要第二个复核者。
** **"能不能拿到"须给可判定的判据、且在动手前判定**（事后补记无法核对，也不得退化成"我感觉拿不到"）：本平台上的核对方式只有两条——(a) 加载调度器明示的派发方式；(b) 环境标志实测（`printenv CNB_EVENT` 非空且触发内容含本任务的唤起名）。**两条都取不到时按"拿不到"判**、即适用降级路径——环境确实**不提供**时（同 Agent 子执行者不可得），**验证与交付不因此缺失**（不得据此拒做、停任务或等下一轮）。
** **写入面**：本条**不在公共内容**（`AGENTS_COMMON.adoc` + `specs/`，引用方按入口加载时**不会取到它**），只在本平台层——这正是它**不得被外推成平台无关前提**的原因。
** **该情形下的交付形态（L1）**：照常交付（提交、推送、建 PR 照做），结论里如实写明"可信的独立复核在当前环境不可得 + 已做的替代核对 + 剩余风险"——**"已交付 + 校验全绿 + 复核缺口如实标出"不得混写**成"已复核通过"，两者是两件事。**判定标准（任一命中即违规）**：① 用 @ 自己（或请他人 @ 自己）**换取一次新执行来做复核**；② 把"拿不到独立复核"写成"**已复核通过**"；③ 以"要等下一轮复核"为由把当前任务停在中间、不交付。依据：评审与被评审须相互独立（IEEE 1028）、变更的核验须可追溯到可核对的对象与判据（ISO 10007）。
* **评论唤起是平台侧的派发方式，不改变派发判据（L1）**：本平台上，**在 Issue 或 PR 下新增一条评论、@ 某个 NPC、并在评论里说清要求**，即新增一次执行。本条**只把"往哪派"说清楚，不放宽任何派发约束**：派给谁、用不用外部 Agent、派发须钉定对象、须自带硬超时、派发前确认执行者可执行——**一律按 `specs/general/collab.adoc` 执行**，本条不另立判据、也不构成"可以点名外部 Agent"的例外。
* **一次评论 = 一次派发，任务边界由评论正文界定（L1）**：被唤起者收到的**只有一条评论正文**。故**要求须在评论里写清**：要做**什么**、**边界**（改哪、不改哪）、**产物形态**（只分析 / 改代码 / 出报告）与**验证口径**——"写清了"由执行者按这四项逐项判定，**缺项或判据不满足时须在原评论下回复"拒绝 + 列出缺失项"或请发起人补一句，不得开工、不得拿"他没写清"当擅自扩大范围的挡箭牌**，**未写清的不得自行假定后开工**。写清的形态就是一次派发的派发指令，故同样须钉定对象、自带时限。
* **要求"用干净上下文"是派发选项、且**要求不是保证**（L1）**：默认情况下一条评论发起的执行**沿用该 Issue/PR 的既有上下文**。评论里**显式要求"使用干净的上下文/不要参考此前评论、按本次要求独立判断"**时，被唤起者须把本次任务**当作一次全新任务**执行：① **不复用**此前讨论中的结论与前提，需要先前的事实一律按**对象钉定**重新取值（钉 commit sha）；② **规范仍须按入口重新加载**（"上下文干净"只清历史对话，**不清约束**）；③ 评论里已写明的**本次边界**随之生效。**该要求属降低风险的措施、不是保证**：要求了不保证真的发生（执行侧能否新开会话属环境能力），故**须在结论里如实说明本次实际读到的上下文范围**——不得"记成"已用干净上下文。**边界两句必须一起读**：该要求**不豁免任何派发判据**；反过来**"我说了用干净上下文"也不构成"连本次对象钉定都要另取一套"**。
* **不得以评论派发唤起自己（L1，防无限派发）**：**一次评论就是一次派发**，**发起下一次是派发者的动作、不是执行者的动作**——**被评论唤起的执行者不得在本次执行中再发一条评论去点名唤起自己**（同一点名、同一实例名——不论有无"再干一件"的理由，也不论是否写明用干净上下文），**也不得转由他人/其他执行者发布这条评论**。判定标准（任一命中即违规）：① 本次执行期间**新增的点名评论指向本条评论上的唤起名**；② 以"分两步更清楚""上一轮没做完"等理由自我豁免；③ 实际发了这条评论、把任务在执行中重新发起一次（**判据是这条评论发出去没有**，不是这次执行有没有因此结束）；④ 把发这条评论交给子 agent 或他人代发（转交他人顶替执行亦算未拦住）。**为什么必须拦住**：唤起一次就是新增一次执行、要重新按入口加载规范并付一次调用与等待。**正当形态（一次执行一处落点）**：想分步就**先停**、在执行者这一侧只输出一次"停下确认"（把"已做完哪一段、下一步要什么"一次性写清），由**人**在任务单下另发一条评论决定是否再来一次——**执行者不发那一条**。本条的"唤起名"由项目自身规范给出——文中的实例名（如 `@CodeBuddy`）**仅作举例**，不得被未知项目照抄成通用要求。
* **唤起不等于自动开工（L3，须先判读）**：单条评论只写"@ 某人"或只有寒暄/表情时，**不构成一份可执行的派发**——被唤起者不得据此自行开工，应回问"要做什么、范围与产物形态"。

== 执行吞吐（平台侧的两处特有代价）

依据：一次执行=一次新的唤起与一轮加载（本平台的唤起形态）；交互应可控、可预期、不阻断（ISO 9241-110）；性能是质量属性、须可度量（ISO/IEC/IEEE 25010）。**本条只在 CNB 上成立**。

* **一次唤起 = 一次完整加载 + 一轮往返（L1）**：本平台上"唤起一次"就多付一次规范加载、一次仓库检出的等待与一轮执行；故**派发侧**：同一任务不要拆成多次评论派发（要拆也由**人**决定），**要求须一次写全**（做什么、边界、产物形态、验证口径，四项缺一即按"未写清"处理）。**执行侧**：本次执行内的往返须尽量合并（判据见 `specs/general/context.adoc`「执行吞吐」）——不要为了"刷新一下某个长流程"另起一轮。
* **长流程的状态查询要批量、要有一把梭的判据（L2）**：本平台上查看构建/流水线状态、AI 用量与请求明细、阶段耗时是**独立接口**，逐个查会各付一轮。故：**先取汇总、再按需下钻**（先取构建状态与阶段耗时定位"花在哪一段"，只在需要时才取日志或请求明细），**状态与统计一次取全**（同一批把要看的几个构建/SN 一起查）；不要用"只发一次状态查询"这种零信息的往返来等长流程。
* **AI 用量与请求明细是本地化的观测手段（L2）**：本平台的 **AI 用量汇总**（输入/输出 token、请求数、生成耗时）与 **AI 请求明细**（每次请求的 prompt 体积、起止时延、分页）是"这次执行慢在哪"的**直接证据**，属本平台特有的可观测面。做提速类任务、或在报告里判定"慢的原因"时，**以这两处的实测取值为准**，不要凭印象说"网慢/模型慢"。

== 评论不得删除（L1）

依据：交互应可控、可预期、不阻断（ISO 9241-110）；评审与被评审须相互独立、原样保留评审记录（IEEE 1028）；成文信息须原样留存、可追溯（ISO 10007、ISO 9001）。

* **任何情况下都不得删除 Issue / PR 的评论（L1，含 NPC 生成的那些）**：**删除评论是不可逆的**——它毁掉的是**派发的对象钉定与留证落点**（"这一轮收到了什么要求、回了什么、当时钉的哪个 commit sha"全靠评论串），事后既无法复核、也无法在旧 sha 上重核结论。故：**执行者不得调用平台的删除评论接口/命令**，**不得**用编辑评论把内容改写掉（**编辑等于改写留证**：原话一改，"当时到底要求了什么"就无从核对，**与删除同效**），**也不得**转交他人/其他 NPC/CI 步骤代删。**"评论发错了"的正当处置**：**再发一条更正**（写明更正了哪一条、更正了什么），或用**回复**补充——**不禁"改正"，只禁"抹掉"**；确需清理时由**人**在平台上自行处理。**判定标准（任一命中即违规）**：① 调用了删除评论的接口/命令（含批量清理、脚本化删除）；② 编辑既有评论的正文或附件使其与原话不一致（追加式补充、且不改变原意不属此列）；③ 把删除动作交给子 agent 或他人代发；④ 以"内容过时/重复/是 NPC 自己发的"为由自我豁免。**"评论不是交付"这句不得反读**：评论不计入交付物，**不等于**评论可删。
* **与"临时产物清理"的边界（L1）**：清理 `tmp/`、清理构建产物等属本地临时产物的操作照旧；本条禁的是**平台侧任务单的评论串**——它不属临时产物，是**任务本身的留证**。
* **与「人工该不该合入目标分支」的关系（L1）**：本条只禁**删除/改写评论**，与合并无关，也不构成任何合并的依据。

== 压缩提交（提交历史的整理，平台侧追加口径）

**规则本体（工具无关）在 `specs/general/version-control.adoc`「压缩提交」**——压缩＝提交历史整理、内容零变化、**默认压成一个提交**、压缩对象只有本次任务尚未合入的提交（例外两类见通用层）、压缩不等于解冲突，都在那里；本节只写**本平台的追加口径**（推送与对象钉定）。

依据：变更与工作须受控、可追溯（ISO 10007、ISO 9001）——整理提交历史属受控变更，须可追溯；**该标准只要求"变更可追溯、可定位"，未规定"提交必须压成一个"**。

* **压缩提交＝提交历史整理，不属禁止行为（L1）**：用户要求"压缩提交/压成一个提交"时按本平台执行（判据见通用层，本条只补平台侧的**作用范围**）：压缩**只作用于本次任务自己的 PR 源分支**，不动目标分支、不动他人分支；它与"人工该不该合入目标分支"无关。**平台侧交付形态**：压缩后该合并请求的源分支上**最终只有一个提交**（`git log --oneline <目标分支>..HEAD` 只给出一条）——允许留下的例外只有通用层「压缩提交」写明的两类（已合入目标分支的历史、P7 拆出的两个提交）。
* **压缩须保留与目标分支的合并关系（L1）**：压缩/改写时，**不得把「已并入目标分支」这一事实一并丢掉**——若本分支此前已并过目标分支（或本就基于目标分支的最新提交），压缩后的提交**必须仍以目标分支的最新提交为祖先**（核对命令见 `specs/general/git.adoc`「压缩后的合并关系核对」，本处不复述）。**本条在本平台的真实失效形态**：用「照抄目标分支的文件内容 + 单亲提交」冒充"已并入"——**工作树与 `git diff` 都看不出毛病，本平台却仍报冲突、PR 卡在 `code_conflict`**（平台侧的判定依据是合并关系、不是工作树；机制与判定标准见 `specs/general/git.adoc`「压缩后的合并关系核对」，本处只给平台侧能观测到的后果）。**正确做法**：真做一次合并（`git merge`，冲突逐处解决）后**以合并提交落盘**；用户要求压缩时，压缩**只整理本分支自己的中间提交**、**不吞掉合并提交**——**合并提交是"已并入"的凭据**，不是可压掉的临时提交。
* **与「NPC 禁合并」的边界（L1）**：把**目标分支**并回来（`git merge <目标分支>`、**以合并提交落盘**）与"合并 PR"是两件事——前者是**当前分支内的动作**、是「压缩须保留与目标分支的合并关系」与「返工基点的核对」要求的**修复动作**，后者才是本条禁止的。判据：合并提交的**第二个父提交侧**不得带进任何目标分支上没有的提交（`git rev-list --count <目标分支>..<合并提交>^2` 为 0）——`git merge <别人的源分支>` 那种"并进外部提交"照旧违规，**且不因为该合并提交的第二个父提交恰好落在目标分支上而得免**（两条分支共用的分叉点就在目标分支上）。
* **压缩前须先并入目标分支的最新提交（L1，本平台的用户点名形态）**：用户要求压缩时，**先确认本分支已把目标分支的当前最新提交并入过**——未并入则**先并入、再压缩**（规则本体与判定标准见 `specs/general/version-control.adoc`「压缩提交」的「压缩前须先并入目标分支的最新改动」，git 侧的取值形态见 `specs/general/git.adoc`「并入是否真实发生的核对」；本处只补平台侧能观测到的后果）。**本平台上的真实失效形态（本仓库实证一次）**：分支停在旧基点上**从未同步过目标分支**时，`git merge-base` 恰好**等于目标分支本身**——于是"目标分支是祖先"**为真**、既有的两条关系判据与机械防线**全部报绿**，而**压缩一次即把目标分支后合入的改动整批删掉**；本平台给的是**一个 PR 一条源分支、压完就合**，故这一批删除会**随 PR 合并落进目标分支**、**不可逆**。**判定标准**：交付说明里须给出"已并入目标分支当前最新提交"这一事实的**取值**（以及按它重算后的差异检出）；**只说"分支是最新的"不给取值，即不合规**。**与「压缩后的合并关系核对」的关系**：两条核的是**不同的两件事**（压缩之前发没发生过并入 / 压缩之后关系丢没丢），**互不替代**——前者为真**不构成**后者为真的依据。
* **压缩后须核查有无多余的删除（L1）**：压缩后须相对**目标分支的当前最新提交**核一遍**有没有多余的删除**（规则本体与四个核对方向见 `specs/general/version-control.adoc`「压缩提交」的「压缩后须核查有无多余的删除」，git 侧的取值形态见 `specs/general/git.adoc`「压缩后不足量删除的核对」与「被改过 / 删过的文件里的删除条目逐处核」；本处只补平台侧能观测到的后果）。**本平台上的真实失效形态**：本平台是**跨轮次接续**的（一次唤起一条评论、下次另起一条）——压缩后这一问，**既有的任何一条都没读过**（既有条核的是"冲突两侧的内容在不在"与"压缩动作自身前后差异为空"），故一条"看起来干净"的提交能一路报绿走到合并。而本平台**一个 PR 一条源分支、压完就合**，故这类多余删除**随 PR 合并落进目标分支、不可逆**。**判定标准（任一命中即不合规）**：① 交付说明里**给不出这份账**（哪些地方有删除、各属哪一侧），只说"压缩已完成"；② 只核"没有冲突 / 能编译"或只核**被整体删除的文件**；③ 以"**目标分支仍须是本分支的祖先**"顶替本条（见下条）。**与「压缩须保留与目标分支的合并关系」的关系**：两条核的是**不同的两件事**（产出形态里有没有多出删除 / 合并关系丢没丢），**互不替代**——合并关系为真**不构成**"没有多余删除"为真的依据（分叉点恰好落在目标分支自己身上时，那条为真、而删除照样整批发生）。
* **禁止的压缩形态（平台侧追加）**：① 把**他人（或其它任务）的提交**一并压缩（含并行任务在同一分支上产出的提交）；② 压缩**已合入目标分支**的历史（改写公共历史）——通用层的四种禁止形态与规则本体见 `specs/general/version-control.adoc`「压缩提交」，本条只补平台侧"同一分支上并行任务提出的提交也不得并压"。
* **压缩对象不含"改名提交 + 内容修改提交"（L1）**：按 `specs/general/git.adoc`「重命名与内容修改须分两个提交」拆出的那两个提交（**别名**："改名提交 + 内容修改提交"）**不是**临时中间提交——把它压回一个即**删掉一条可独立回溯的记录**。故：用户说"压缩提交/合并成一个提交"**而未点名重命名这一条**时，本次任务的**其余提交照默认压成一个**，那两个提交**原样保留**（判据：压缩后 `git log --diff-filter=R -M --name-status` 仍能取到那一条批量改名记录、与之紧邻的改内容提交仍在）。**与"例外"对齐**：用户**明确声明**"这次重命名与改内容合成一个提交"时，按 git 规范的「例外」执行——此时全部压成一个提交、不再保留那两个；两件事不冲突：压缩照做、边界照在。
* **须先确认无人在用旧对象（L1）**：压缩后要做 force push，故执行前须确认**无他人正基于该分支的旧 sha 工作**（已派发、正等待结论）；确需执行时须**明确告知受影响方**新 sha、并把旧 sha 上的结论标为过期。
* **压缩后须声明新旧 sha 对应关系（L1）**：执行后在 PR 说明或汇报中写明"**已压缩为一个提交，新 sha 为 X，旧 sha Y 作废**"，并如实列出被压缩掉的中间 sha；**下游按旧 sha 复核的结论视为过期**，须在新 sha 上重核。
* **推送口径（L1）**：用 `--force-with-lease`（带租约的强推），**不得**用裸 `git push --force`。**授权边界（平台侧取值）**：**"AI 不做强推"的一般口径**不适用于本条的压缩提交**——用户明确要求压缩提交时按本条执行即属授权，但**授权范围仅限本次 PR 的源分支**。命令细节与 git 侧核对见 `specs/general/git.adoc`「压缩提交」。
* **与「冲突处理」的接口（L1）**：用户提出"**压缩提交**"而分支上**还有冲突**时——**含用户只提了压缩、没提解决冲突的情形**（"没被要求"不构成不做的理由）——**不得把冲突留在原地只做压缩**——须按「冲突处理」节先解冲突、再压缩（**规则本体与三档核查判据**在 `specs/general/version-control.adoc`「冲突处理」，本平台上即**该合并请求的源分支上最终只有一个提交**）。**压缩不等于解冲突**：把冲突处的文件整体取一侧后压成一个提交，是把"丢内容"藏进了一个干净的提交里。
* **与「NPC 禁合并」互不豁免（L1）**：压缩提交**不是合并**，故用户要求压缩提交时照做；反过来**压缩提交也不构成"可以合并"的依据**——合入目标分支仍**只由人工完成**。

== 对象钉定与可追溯

* **派发与复核须钉定 commit sha，不得只说分支名（L1）**：CNB 上同一分支会被多次推送（并行任务、整改追加提交、按上「压缩提交」整理后强推——**那是"合规动作、不是违规改写"**），**分支名不构成稳定标识**。凡把"某分支/某 PR 的改动"作为复核、比对、追溯对象时，必须**钉定具体 commit sha**（`refs/pull/<n>/head` 对应的 sha），并在派发/汇报中写明；**收到"基于某分支"的对象时，须先取得该分支当前指向的 sha 再核对**（不得用本地可能过期的引用）——CNB 本地缓存可能停留在旧 sha；怎么取属执行动作，不写进规范。
* **压缩提交/强推会替换对象，须声明对应关系（L1）**：对分支做 `squash`/`rebase`/force push 后，**旧 commit 对象从分支历史移除**、无法再按 sha 取回。故：① 执行后须在 PR 说明或汇报中写明"已压缩为一个提交、新 sha 为 X，旧 sha Y 作废"；② **下游按旧 sha 复核的结论视为过期**，须在新 sha 上重核；③ 强推前须先确认**无他人正基于旧 sha 工作**。
* **CI/流水线状态须按构建号（sn）与 sha 关联（L2）**：核对流水线结果时以 **sn + sha** 组合定位当次构建，不按"分支最新一次"想当然取值（同一分支可能同时有多次构建、旧构建可能仍在 pending）。

== 协作与执行者可用性

* **派发前确认执行者实际可用（L1）**：向平台上的 NPC / 子执行者派发任务前，须确认其**产物实际存在且可取**——镜像/制品包在制品库中存在；且同名 NPC 可能有多个不同来源的 slug，须用**确证可用的那个**，不得凭名称假设。
* **派发须自带超时与放弃处置（L1）**：平台协作的等待必须有可判定的时限，到点即放弃并如实标悬置，不得无限等待。
* **命令/构建/网络等待也须有时限（L1，平台侧后果）**：本平台的执行是**跨轮次接续**的（一次唤起一条评论、下次另起一条），故**一次操作卡死不是"慢"，而是整轮执行停在那里直到人工介入**——既不会自动失败，也不会自动往下走；规则本体见 `specs/general/collab.adoc`「操作超时与超时后的处置」，本处只补平台侧能观测到的后果。

* **流水线不无界挂起（L1）**：平台流水线的 job/step 须设可判定的超时，不得长期停在 pending 而不失败（见 `specs/general/ci-cd.adoc`「超时与资源」）。

== 包源与镜像源（平台侧优先口径）

* **优先用平台内已优化的源、再逐级降级（L1）**：在 CNB 里取依赖、构件、容器镜像与系统包时，**先用平台内/云厂商内网已优化的源**，不可用再按 `specs/general/dependency.adoc`「包源（包仓库/镜像站）的选用」逐级降级；**每级启用前的取值要求＝该源已实测可取到产物**（**怎么实测属执行动作，不写进规范**），**已配置过即沿用**。**推荐不等于强制**——顺序是"优先次序"，用户/项目已声明的源优先。
* **镜像加速地址须以本平台当前实际生效的为准（L1）**：容器镜像加速/仓库镜像的地址由**平台配置**决定，**可能随环境变化**；不得把某一条地址当成跨环境的固定事实写进流水线——可用性的唯一判据＝**该地址在当前环境可取到镜像**（取值形态，不写怎么取）。不得为"用推荐源"覆盖引用方已有的镜像/仓库配置。
* **换源改动写进流水线配置（L2）**：装配步骤一次配置到位，不在每次运行时临时拼命令。
