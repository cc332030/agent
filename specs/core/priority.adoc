= 规范优先级与最高关注项（必加载层）

本文件定义**规范条目的优先级分级**、各级必须遵守的要求，以及**最高关注项**（跨重构仍不得削弱的核心约束）。它回答两个问题：**"这条规范有多重要"**（分级）与**"重构/精简时绝对不能动什么"**（最高关注项）。目前最高关注项共五项（P1-P5）：第 4 项针对"AI 读得过多、会话越长越不守规矩"，第 5 项针对"不可逆操作一旦做错无法挽回"。

**如何给一条规范定级（定级四问 + 条款类型判定表 + 归属对象 + 归类举证 + 级别变更与复盘）不写在本文件**——本文件是必加载层，每次会话都要读，而定级只在"编写/调整规范"时用到，属**写规范的方法论**，放到 link:../general/spec-lifecycle.adoc[]（通用层，涉及规范增删改时加载）。本文件只保留"读到条目后该怎么做"：**常驻层只给"怎么走"（规则 + 判定标准 + 依据名），不铺开"为什么走这条路"**——原因与取舍属"要思考、要决策"（新增/调整规范、定级、复盘）时用的依据，细则见 link:../general/spec-lifecycle.adoc[]「同一条规则有两种读法」；要执行者只需执行，无需读依据。
**维护这套规范集合的项目**，其自身维护规则（定级留痕、级别维护、去重边界、机械防线落点等）属**项目自身规范**，不在本文件内——两类内容的隔离口径见 `AGENTS_COMMON.adoc`「访问与解析」之"公共内容边界"。

== 为什么需要分级（业界依据）

条目若"看起来一样重要"，会导致两种失效：**关键约束被稀释**（"必须"与"建议"一视同仁，重构时顺手削弱最高约束）与**约束过载**（条条框框过多，AI 束手束脚、读者抓不住重点）。分级不是本文件自创，业界有成熟做法：

* **RFC 2119 / RFC 8174（IETF）**：以 `MUST`/`MUST NOT`/`SHOULD`/`MAY` 划分约束强度；RFC 8174 要求"只有全大写且本身是规范用语"才具约束力，避免歧义。
* **ISO/IEC Directives Part 2**：以 `shall`/`should`/`may` 区分**要求 / 建议 / 允许**，且"要求"必须可验证。
* **关键性分级（航空航天 DO-178C、IEC 61508 SIL、汽车 ISO 26262 ASIL 等安全关键领域的"完整性等级"）**：**级别越高、验证强度越高**，高等级需求不可降级、逐条追溯。
* **不变量（invariant）**：核心约束以"不变量"固化，改动只能**保持或加强**，不得因重构/去重/精简而降级。
* **单一事实来源（SSOT）**：同一约束只在**一处**给完整定义，其余只引用不复述（复述会漂移；"写两遍"强调属反模式，见「强调的正确做法」）。

软件测试与评审相关条目的分级依据另见 ISO/IEC/IEEE 29119（软件测试）与 IEEE 1028（软件评审）。

== 分级定义（L1 / L2 / L3）

条目按约束强度分三级；**级别决定违反后果、验证强度与"能否自行取舍"**：

* **L1 强制（必须/严禁）**：违反即视为**未完成**，不得提交/合并；任何理由（含"重构""精简""上下文不够"）都不能豁免。要求**可验证**——有明确判定标准、可核对、尽量有机械抓手。**L1 中的最高关注项还额外受"不可降级"保护**（见下节）。
* **L2 建议（应当/优先）**：默认遵守；存在**正当且可说明的理由**时可偏离，但须在代码注释/提交说明中写明取舍依据；不得无理由忽略。
* **L3 允许（可以/不强制）**：给出可选做法，不遵守不构成问题；仅在特定场景（工具支持、既有约定）下适用。

判定用语按 RFC 2119 归并：`必须/严禁/不得/禁止` = L1；`应当/优先/原则上` = L2；`可以/非强制/不要求` = L3。**未标注级别的条目按其用语判定**；`严禁/必须` 类用语天然为 L1。定级判定依据（四问、条款类型对照、归属对象）见 link:../general/spec-lifecycle.adoc[]「如何给一条规范定级」。

== 最高关注项（不可降级，重构/精简时首保）

以下是**最高关注项**：跨重构、去重、精简、迁移**必须保持，只能加强不得削弱**。每项给出**判定标准**（可执行）、**依据**（业界标准名/编号，只留一行）与"重构时如何判断它没被误改"；**失效原理与取舍论证归思考/决策侧**（见 link:../general/spec-lifecycle.adoc[]「同一条规则有两种读法」），常驻层不铺开——但**不得省掉依据**（只压缩为名称/编号）。

最高关注项**级别不是同一档**，"最高关注项"与"条款本身是 L1"是两件事——这正是"优先级混用"的典型来源，须分清（两者按 link:../general/spec-lifecycle.adoc[]「如何给一条规范定级」分别判定；依据：ISO/IEC Directives Part 2 要求与建议不得混用；RFC 2119 的 `MUST` 不因"描述的是常见失效"而变强）：

* **规范性铁律（P1/P2/P3/P5，条款本身 L1）**："该怎么做"没有裁量空间——`git mv`、校验必须真执行、内容不得减少、不可逆操作先确认且不得编造，任何理由都不得偏离；机械防线钉的是铁律本体。
* **纪律性铁律（P4，条款本身 L2）**：约束的是"读多少、在什么上下文里做"这类**行程安排**，存在正当豁免（读取范围按任务定、成本与收益可权衡），按定级四问只能到 L2；但它**极易被无声违反、违反后整条任务链的方向与准确率一起偏**，故与规范性铁律**同列最高关注项**。**列为最高关注项 ≠ 条款本身是 L1**：不可降级保护的是"不得从清单删除、不得改为'非最高关注项'、不得削弱其必加载层引用与机械防线"，而非把它的条款强度拔高。

=== P1. 文件移动/重命名必须用 `git mv`，禁止 delete+create

* **要求（L1，最高）**：不得用「新增新文件 + 删除旧文件」代替移动/重命名，否则 git 历史断裂。
* **依据**：rename 跟踪的可追溯性靠版本控制机制原语（`git mv` = 移动 + 记录重命名），delete+create 会永久断链且**事后无法恢复**——不可逆损伤（依据：配置管理对变更可追溯的要求，ISO 10007；变更须保持既有信息不丢，见 link:../general/git.adoc[]）。
* **判定标准**：`git diff --cached -M --summary` 对移动显示 `rename`；`git status`/`git diff --name-status` 不应出现"同一批改动里 `D`（删除）+ `A`（新增）且内容高度相似"（**只读状态行**，不需工作区文件内容）。完整规则与自检命令见 link:../general/git.adoc[]「文件移动与重命名」，必加载层重申见 link:execution.adoc[]「文件操作强制检查」。
* **重构防误改**：本条**不因去重而删除**。多文件/多层重复出现时，**保留一处完整定义（link:../general/git.adoc[]）**，其余位置用**一行引用**指向它（见「强调的正确做法」）；**禁止以"内容重复"为由删除任何一处对最高关注项的引用**。

=== P2. 调整规范必须保证完整性，且校验要真正执行

* **要求（L1，最高）**：调整规范不得丢失规则；**规范类改动**改完必须跑机械校验 + 干净子 agent 语义复核，不得"定义了校验却不执行"（本条是最高关注项——**其存在与不可降级对任何改动生效**；其规定的三视角动作按改动性质取值，见下「判定标准」）。**复核须一并回答三视角、都过才算完成，且由同一个干净子 agent 一次读取、结论分栏**（判据见 link:../general/verify.adoc[]「规范验证」）。
* **依据**：规范集合属受配置管理约束的资产，变更须可追溯、防止误删（ISO 10007、ISO 9001 文件信息控制）；需求变更须保持完整性并可追溯（ISO/IEC/IEEE 29148）；评审也可作为核验手段（IEEE 1028）。
* **判定标准**（**两件事分开读**）：①**本条的存在与不可降级对任何改动生效**（任何提交都不得删改本条，见下「重构防误改」）；②**本条规定的三视角动作只适用于规范类改动**——规范类改动须通过机械校验（引用/链接/节名/登记等确定性项）**加**一次隔离上下文的语义复核（**①完整性 + ②有效性与认知质量 + ③接纳面**三视角都过、各有留证），只跑机械校验不算完成；**代码类改动不走三视角**，按 link:../general/verify.adoc[]「验证的适用边界」的机械判据判过不过（**能过即过**）。**同一提交含两类改动时按更严一侧取验证范围**（口径与判据见该节），但**三视角只覆盖其中的公共内容部分**、代码部分仍按机械判据判过不过。**"验证了什么、怎么算过、依据哪个标准"须能逐项枚举**（口径、标准出处、留证三态见 link:../general/verify.adoc[]「验证总纲」「验证的效力等级」），**被未知项目加载后的影响面/成本/可控性**（link:../general/context.adoc[]「运行契约」）也在核对范围内——防"跑绿脚本就算验证过"与"加得越多次越脱离初衷"。完整口径（三视角判别式、②四维与③逐维判据、留证与合用一个子 agent 的理由）见 link:../general/verify.adoc[]「规范验证」。**结论强度按对象分档（L1，仅适用于按上款走规范类验证的改动）**：复核**只到"未发现问题"，不得写成"通过"**——有确定性判据的对象才谈"通过/不通过"；概念性对象**查不出不等于没有**，须标**悬置**并写明已复核角度，**且不得当作阻断交付的条件**（口径见 link:../general/verify.adoc[]「验证的效力等级」）。**维护规范集合的项目**须把本文件最高关注项的存在性（与定级口径的存在性）**转为机械防线**；写入与登记的完整动作见 link:../general/spec-lifecycle.adoc[]「写入与登记」。
* **重构防误改**：本条与最高关注项的存在性**必须由机械防线钉住**（存在性可确定性核对，故属该设抓手的一类；只在文档里写"不得删除"而不设检查，属 link:../general/self-check.adoc[] 意义上的"定义了却不执行"）。**抓点具名与泛化的边界（L1）**：公共内容里**不得**写某项目私有的抓手名、脚本名与仓库结构（引用方看不到），也**不得声明"已由机械防线钉住"或"存在某道防线"**——那属维护规范集合的那一方自己的事，引用方既拿不到、也无从执行；公共内容只保留"须由机械防线钉住"这类**要求**。**把具名抓手改成泛化要求而项目侧没有对应具名检查，属把"必须 + 判据"压成"原则 + 方向"的可执行性降级**。——维护规范集合的项目须把该检查落成具名抓手、落入其 CI。

=== P3. 文档/注释内容不得减少（迁移只换承载位置）

* **要求（L1，最高）**：文档内容可写在代码文档注释或独立文档，但**要求记录的内容一项不能少**；不得以"精简""去重"为名删简真实内容。
* **依据**：记录内容是事实与决策的载体，删除即失去可追溯性（ISO/IEC/IEEE 29148 的可追溯要求、ISO 9001 的文件化信息控制）。**去重针对"重复表述"，不针对"必要内容"**——这是本条与「规范组织/去重」最容易混淆的边界。
* **判定标准**：按 link:../general/doc.adoc[]「注释与文档」的「必记录项」①-⑩ 逐项核对，缺一即未完成；迁移后仍须逐项齐全。
* **重构防误改**：去重前必须先确认"删的是重复表述、不是必要内容"；对无法确定的内容**保留**（宁可冗余不可缺失）。

=== P4. 读取按最小必要，长会话简单任务须在干净上下文执行

* **要求（L2 建议，最高关注项）**：任务开始前先定出**最小必要信息集**并只读该集合内的内容；会话执行过多个任务后，切换任务时**应当**把历史上下文与新任务隔离，简单任务优先在**干净上下文**中执行。**定级理由**：本条约束"读多少、在什么上下文里做"这类行程安排，存在正当豁免（读取范围取决于任务且可权衡成本收益），且 link:../general/context.adoc[] 内的逐条规则本身即按 L1/L2 分级（读取范围边界为 L1、委派与落盘等安排为 L2）；但**存在破坏面大的典型失效**（简单任务在长会话里读一大堆无关内容、准确率与成本一起恶化），故列为最高关注项。完整规则见 link:../general/context.adoc[]，必加载层重申见 link:execution.adoc[]「范围控制」。
* **依据**：上下文越长，信息召回与长程推理越差、token 成本与时延越高（注意力预算与 `context rot`；Anthropic 工程博客《Effective context engineering for AI agents》）；只加载必要的高信号内容（Agent Skills 开放规范的 progressive disclosure）。**完整论证与量化抓手**见 link:../general/context.adoc[]「为什么控制上下文」（该处是唯一完整定义）。
* **判定标准**：①读前能说出"本次任务的最小必要信息集"，且实际读取未超出（超出须有可说明的理由）；②已定位文件的任务使用了精确定位读取、未启动全库扫描；③任务切换时不沿用旧任务的探索路径，简单任务不在长会话中"沿用旧路径再读一遍"；④读完后读到的内容全部与任务相关。
* **重构防误改**：受不可降级保护，护法与 P1-P3 一致——维护规范集合的项目须机械钉住其存在性、必加载层引用落点与『不可降级』声明；本条**不因去重而删除**，多处出现时保留一处完整定义（link:../general/context.adoc[]）、其余用一行引用。

=== P5. 不可逆操作先确认，不得编造事实与来源

* **要求（L1，最高）**：①**删除/清空/覆盖等不可逆操作**执行前须确认目标、可回滚、范围可界定，三项任一不确定即停下提问；②**不得编造事实与来源**——命令/API、依赖坐标、标准编号与名称、链接与路径、数据与结论，不知道就明说并去查证。完整规则见 link:execution.adoc[]「破坏性操作」与 link:../general/source.adoc[]。
* **依据**：两类失效**危害不可逆或会扩散**——误删/强推覆盖的数据与历史无法恢复（配置管理与变更控制：ISO 10007）；虚构来源会污染整条下游引用链且事后极难发现，故来源必须真实可溯源（link:../general/source.adoc[]；ISO/IEC IEEE 标准引用现行有效文件的要求）。**犯错成本不对称**：做对比做快重要得多，"不确定"时默认停下而非输出。
* **判定标准**：①不可逆操作前能说出"删的是什么、能否恢复、范围边界"，且实际按此执行；②本次给出的命令/路径/编号/数据，都能指出**来源或实测依据**（凭空无法指认即违规）；③无把握时输出的是"未确证"而非貌似合理的编造内容。
* **重构防误改**：本条**不因去重而删除**；完整定义分别落在 link:execution.adoc[]「破坏性操作」与 link:../general/source.adoc[]，其余位置用一行引用；存在性与关键要点**须由机械防线钉住**。

=== 最高关注项与去重的冲突处理（重点）

最高关注项与其引用**允许、且应当**在多处出现，但**一处是完整定义、其余是引用**：这样既保证"强调"（多处都指向它、不可能读不到），又不产生多份漂移（内容只有一份）。**判重时必须先判定"是不是最高关注项的引用"**：是引用 → 不判为注水、不合并；是**逐字复制的完整定义** → 收敛为一处定义 + 引用。

== 强调的正确做法（避免"写两次"的误解）

**"写两遍同样的完整内容"不等于强调**，反而是反模式：它会让 AI 把它判成"重复内容"而合并/删除（正是本仓库遇到过的问题），且两份会各自漂移。业界标准做法是**分级 + 单一定义 + 显式引用**：

* **分级**：把条目**升到 L1 / 列为最高关注项**（本文件），优先级由分级表达，不靠重复次数表达。
* **单一定义**：完整定义只写在一个**权威位置**（如在 link:../general/git.adoc[]，或在 link:execution.adoc[] 的重申），其余位置**只写一行引用**（如"见 git 规范「文件移动与重命名」"）。
* **显式标题**：权威定义所在小节用**显著标题**（如 git 规范的「文件移动与重命名」）承载强调；重要条目在 `AGENTS_COMMON.adoc`「最高优先级铁律」**登记一次**，作为"进门必读"。
* **机械钉住**：对"任何时候都不得消失"的条目，用校验脚本钉住其**存在性**（维护规范集合的项目须落到具名检查），这比人工重复书写更可靠。

结论：**同一约束只写一次完整定义、其余用引用**；需要更强强调时，用"升级别 + 加显著标题 + 机械钉住"，而不是复制正文。

== 判准维度：严格执行 / 尽力而为（何时用见通用层）

L1/L2/L3 只答"**要求有多强**"，还须答"**执行到什么程度算做到**"——**严格执行**：判据固定、二值，没做到不得声明完成；**尽力而为**：须尝试、须说明未达原因、不记通过。两者判据、判定动作与常见误用见 link:../general/verify.adoc[]「判准维度：严格执行 / 尽力而为」；**"未执行"与"执行通过"不得混写**。
