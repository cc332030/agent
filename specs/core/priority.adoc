= 规范优先级与最高关注项（必加载层）

本文件定义**规范条目的优先级分级**、各级必须遵守的要求，以及**最高关注项**（跨重构仍不得削弱的核心约束）与其原因。它回答两个问题：**"这条规范有多重要"**（分级）与**"重构/精简时绝对不能动什么"**（最高关注项）。

== 为什么需要分级（业界依据）

条目若"看起来一样重要"，会导致两种失效：**关键约束被稀释**（"必须"与"建议"一视同仁，重构时顺手削弱最高约束）与**约束过载**（条条框框过多，AI 束手束脚、读者抓不住重点）。分级不是本文件自创，业界有成熟做法：

* **RFC 2119 / RFC 8174（IETF）**：以 `MUST`/`MUST NOT`/`SHOULD`/`MAY` 划分约束强度；RFC 8174 要求"只有全大写且本身是规范用语"才具约束力，避免歧义。
* **ISO/IEC Directives Part 2**：以 `shall`/`should`/`may` 区分**要求 / 建议 / 允许**，且"要求"必须可验证。
* **关键性分级（航空航天 DO-178C、IEC 61508 SIL、汽车 ISO 26262 ASIL 等安全关键领域的"完整性等级"）**：**级别越高、验证强度越高**，高等级需求不可降级、逐条追溯（依据：IEC 61508、DO-178C 一类功能安全标准的分级思想）。
* **不变量（invariant）**：核心约束以"不变量"固化，改动只能**保持或加强**，不得因重构/去重/精简而降级。
* **单一事实来源（SSOT）**：同一约束只在**一处**给完整定义，其余只引用不复述（复述会漂移；"写两遍"强调属反模式，见「强调的正确做法」）。

本文件的 L1/L2/L3 对应上表的"要求 / 建议 / 允许"，并对最高关注项单列、加"不可降级"的机械防线。软件测试与评审相关条目的分级依据另见 ISO/IEC/IEEE 29119（软件测试）与 IEEE 1028（软件评审）。

== 分级定义（L1 / L2 / L3）

条目按约束强度分三级；**级别决定违反后果、验证强度与"能否自行取舍"**：

* **L1 强制（必须/严禁）**：违反即视为**未完成**，不得提交/合并；任何理由（含"重构""精简""上下文不够"）都不能豁免。要求**可验证**——有明确判定标准、可核对、尽量有机械抓手。**L1 中的最高关注项还额外受"不可降级"保护**（见下节）。
* **L2 建议（应当/优先）**：默认遵守；存在**正当且可说明的理由**时可偏离，但须在代码注释/提交说明中写明取舍依据；不得无理由忽略。
* **L3 允许（可以/不强制）**：给出可选做法，不遵守不构成问题；仅在特定场景（工具支持、既有约定）下适用。

判定用语按 RFC 2119 归并：`必须/严禁/不得/禁止` = L1；`应当/优先/原则上` = L2；`可以/非强制/不要求` = L3。**未标注级别的条目按其用语判定**；`严禁/必须` 类用语天然为 L1。

== 最高关注项（不可降级，重构/精简时首保）

以下是**最高关注项**：跨重构、去重、精简、迁移**必须保持，只能加强不得削弱**。每项给出**原因**与**判定标准**（可执行），并明确"重构时如何判断它没被误改"。

=== P1. 文件移动/重命名必须用 `git mv`，禁止 delete+create

* **要求（L1，最高）**：不得用「新增新文件 + 删除旧文件」代替移动/重命名，否则 git 历史断裂。
* **原因**：`git mv` 保留 rename 跟踪，是**唯一**能让"文件从哪来、改过什么"可追溯的手段；delete+create 会让 `git log --follow` / blame / 历史审查永久断链，**事后无法恢复**（属不可逆损伤）。正因为不可逆、且极易在"重构/拆分/整理"时被顺手做掉，它被列为最高关注项。
* **判定标准**：`git diff --cached -M --summary` 对移动显示 `rename`；`git status`/`git diff --name-status` 不应出现"同一批改动里 `D`（删除）+ `A`（新增）且内容高度相似"。完整规则与引用方自检命令见 link:../general/git.adoc[]「文件移动与重命名」，必加载层重申见 link:execution.adoc[]「文件操作强制检查」。
* **重构防误改**：本条**不因去重而删除**。多文件/多层重复出现时，**保留一处完整定义（link:../general/git.adoc[]）**，其余位置用**一行引用**指向它（见「强调的正确做法」）；**禁止以"内容重复"为由删除任何一处对最高关注项的引用**。

=== P2. 调整规范必须保证完整性，且校验要真正执行

* **要求（L1，最高）**：调整规范不得丢失规则；改完必须跑机械校验 + 干净子 agent 语义复核，不得"定义了校验却不执行"。
* **原因**：规范是**累积资产**，一次误删/削弱可能让某条约束永久失效且无人察觉（尤其"要删除的恰好是防误删的防线"）。规范越精简，这类"悄悄消失"的风险越大，故必须以"每次改完必校验"为硬底线。
* **判定标准**：改动后须通过机械校验（引用/链接/节名/登记等确定性项）**加**一次隔离上下文的语义复核（核对要点未丢失）；只跑机械校验不算完成。
* **重构防误改**：本条与最高关注项的存在性由本仓库 `script/check_specs.py` 的 `check_principle_guard`、`check_priority_guard` 机械钉住，删/改会被 CI 拦下（本仓库维护规则见 `AGENTS.adoc`「规范调整」）。

=== P3. 文档/注释内容不得减少（迁移只换承载位置）

* **要求（L1，最高）**：文档内容可写在代码文档注释或独立文档，但**要求记录的内容一项不能少**；不得以"精简""去重"为名删简真实内容。
* **原因**：内容是**事实与决策的载体**，删掉即无法追溯；且"减少内容"常被伪装成"优化"。**去重针对"重复表述"，不针对"必要内容"**——这是本条与「规范组织/去重」最容易混淆的边界。
* **判定标准**：按 link:../general/doc.adoc[]「注释与文档」的「必记录项」①-⑩ 逐项核对，缺一即未完成；迁移后仍须逐项齐全。
* **重构防误改**：去重前必须先确认"删的是重复表述、不是必要内容"；对无法确定的内容**保留**（宁可冗余不可缺失）。

=== 最高关注项与去重的冲突处理（重点）

最高关注项与其引用**允许、且应当**在多处出现，但**一处是完整定义、其余是引用**：这样既保证"强调"（多处都指向它、不可能读不到），又不产生多份漂移（内容只有一份）。**判重时必须先判定"是不是最高关注项的引用"**：是引用 → 不判为注水、不合并；是**逐字复制的完整定义** → 收敛为一处定义 + 引用。

== 强调的正确做法（避免"写两次"的误解）

**"写两遍同样的完整内容"不等于强调**，反而是反模式：它会让 AI 把它判成"重复内容"而合并/删除（正是本仓库遇到过的问题），且两份会各自漂移。业界标准做法是**分级 + 单一定义 + 显式引用**：

* **分级**：把条目**升到 L1 / 列为最高关注项**（本文件），优先级由分级表达，不靠重复次数表达。
* **单一定义**：完整定义只写在一个**权威位置**（如在 link:../general/git.adoc[]，或在 link:execution.adoc[] 的重申），其余位置**只写一行引用**（如"见 git 规范「文件移动与重命名」"）。
* **显式标题**：权威定义所在小节用**显著标题**（如"最高优先级铁律"）承载强调；重要条目在 `AGENTS_COMMON.adoc`「最高优先级铁律」**登记一次**，作为"进门必读"。
* **机械钉住**：对"任何时候都不得消失"的条目，用校验脚本钉住其**存在性**（`check_principle_guard` 等），这比人工重复书写更可靠。

结论：**同一约束只写一次完整定义、其余用引用**；需要更强强调时，用"升级别 + 加显著标题 + 机械钉住"，而不是复制正文。

== 各级别通用的遵守要求

* **L1**：视为不可协商。读到 L1 条目后必须按其执行；若与其它条目冲突，L1 优先（最高关注项优先级最高）；无法满足时必须**停止并说明**，不得默默降级或跳过。
* **L2**：默认遵守，偏离须有可说明的理由并留痕（注释/提交说明）；不得因"图快/省事"而无理由忽略。
* **L3**：可选，不遵守不构成问题；采用时以既有约定与工具支持为准。
* **不可降级**：任何重构/去重/精简**不得把 L1 降为 L2/L3、不得删除最高关注项的定义或引用**；调整规范时须逐条核对级别未被下调（完整性校验的一部分）。
* **条目归位**：条目按主题写入对应分组规范，**级别用本节用语标注**；同一约束只在一处给完整定义，其余引用（见上「强调的正确做法」）。

== 本文件的适用范围（公共内容）

本文件属**通用规范（公共内容）**，随 `AGENTS_COMMON.adoc` 一并被引用方项目加载（必加载层，见 `AGENTS_COMMON.adoc`「分类与懒加载」）。其中 P1/P3 直接约束引用方项目的操作；P2 约束"维护这套规范集合"的动作，在引用方项目中体现为"修改自身规范时同样要保证完整性、且校验要真执行"。
