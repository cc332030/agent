= 执行原则（必加载层）

以下规范适用于所有任务执行，为必加载层，每次工作都须遵循。涉及具体主题时再按 AGENTS_COMMON.adoc 的加载调度规则加载对应分类规范。

**条目优先级分级（L1 强制 / L2 建议 / L3 允许）与「最高关注项」（不可降级、重构首保）见 link:priority.adoc[]**——本文件中的 `严禁/必须` 类条目均为 L1，最高关注项以该文件为准。

== 优先站在前人的肩膀上看世界（先读，知其所以然）

* **优先引用业界标准，不只凭本项目规范（L1）**：规范条目的**依据**应优先来自**广泛使用、高知名度、高可靠性**的业界标准与文献——国际/国家标准（ISO、IEC、IEEE、RFC）、权威组织规范（W3C、IETF、OWASP 等）、权威工具/项目的官方规范、以及经过同行评议的论文与经典著作（如 RFC 2119、Semantic Versioning、PEP 8）。**给出出处不是可选项**：它让读者知道规则**为什么成立、来自哪里**，从而能判断边界、**举一反三**；只写"要这样做"而不给出处，属**知其然而不知其所以然**，读者只能照搬要求、无法在规范未覆盖的场景自行推导。
* **标注出处只写标准名，不写链接（L1）**：出处一律**只写标准/规范/文献的名称与编号**（如 `RFC 2119`、`ISO 8601`、`PEP 8`、`Semantic Versioning`），**不得附链接**——链接会失效、不可访问或指向非官方转载，把读者引向错处，还使规范看起来"权威"却无从核对；标准本身知名度高、名称与编号唯一，**AI 可自行检索定位**，链接既不必要、也不可靠。同时**禁止凭印象编造标准编号/名称**，无法确证时**宁可不引**。唯一例外：**个人项目、知名度很低、或仅此一处**的出处——此类无法凭名称被检索到，**须给出链接**（或等效的唯一定位信息）。给出处时须写明**用的是什么**（依据的标准名/编号，必要时点到章条或文档名），而非泛泛"依据标准"。
* **依据与规则同等重要（L1，限"可被标准佐证"的条目）**：**可被标准佐证**的条目，**须在条目处标注出处**（按上一条：只写标准名/编号，不附链接）——本条**只管"有对应标准"的条目**；**项目自身的取舍/自定约定**（如"changelog 摘要 ≤ 80 字""测试类加 `Tests` 后缀"这类无权威标准可引、或与标准无关的约定）**不适用本条，不得为凑出处硬引标准**（那正是本条与下条共同禁止的"为引用而引用"）；此类条目的依据即项目自身，按 link:../general/doc-design.adoc[]「版本与变更记录」与 link:../general/changelog.adoc[] 留痕即可。引用的出处须**真实、可溯源**（不得凭印象编造标准编号、章条或名称），无法确证时**宁可不引**。引用**不削弱原有约束**——条款本身照旧完整保留，标准只作其依据与延伸阅读（"标准怎么说"不替代"本项目要求什么"）。
* **有自己的要求时须显式覆盖并说明（L2）**：标准给出的是**通例**；当本项目对本条**已有明确取舍或更严要求**（即已理解该标准、并刻意偏离或收紧）时，**须显式写出覆盖点与理由**，让读者知道"这里与标准不同、为何不同"——未说明的偏离等同于无意疏漏。未理解该标准时，**默认遵循**，不得以"我们有更好做法"为由随意偏离。
* **完整性、同义性优先（L1，重构前提）**：以标准为参照调整规范时，须保证**完整性**（规则不丢失、边界与例外一并保留）与**同义性**（表述换了、要求不变）；**为引用而引用、引一堆用不上/不相关的标准反而有害**——引用只为佐证与延伸，不得替代、稀释或改写原规则本身（见 link:priority.adoc[]「最高关注项」P2、P3）。

== 最高优先级铁律（先读，凌驾于其他一切规则）

* **文件移动/重命名必须用 `git mv`，禁止 delete+create**：任何会让既有文件历史断裂的操作（新增新文件 + 删除旧文件代替移动/重命名）都是**最高优先级禁止项**，凌驾于任何"重构""拆分""整理"等主观理由之上——不得以"这是在重构/优化"为由用 delete+create 规避 git mv。只要最终让某个既有文件历史无法追溯，就必须 git mv。完整判断标准与兜底核对见 git 规范 link:../general/git.adoc[]「文件移动与重命名」与本文件「文件操作强制检查」。

== 指令执行

* 指令执行：严格执行用户指令——需求有歧义时先提问澄清，不自行假设后动手；用户说的每一句话、每一个字都是有效指令，不允许忽略、跳过或选择性执行任何一个字（仅明显打错字除外），执行时逐字对照用户输入，确认全部落实后方可结束；每次操作后必须验证是否达到预期（如用 diff/status 比对、运行检查等确认结果）

== 先规划后执行

* 先规划后执行：任何任务动手前必须先规划——明确目标与范围、拆解执行步骤、设计实现方案（复杂/有取舍的任务含备选方案与取舍评估），规划完成后再执行；规划文档须落到磁盘（如设计文档或临时规划文件），不得仅存于上下文（避免超出上下文限制）；规划文档是否需持久化按任务类型判断——项目代码开发等需提交的任务，规划按设计文档持久化（见 link:../general/doc-design.adoc[]），后续随代码一并提交；一般任务规划写入 `tmp/` 文件夹临时文档（见下条「临时产物」），方案在代码注释或执行说明中体现；执行中偏离规划时先调整规划再继续，不得边做边定方案

== 命令执行

* 命令执行：能用项目自身提供的构建/运行脚本（如 `mvnw.cmd`、`mvnw`、`npm`、`pnpm`、`gradlew` 等）直接运行的命令优先用其直接执行，不套用更重的 shell——避免不必要的环境差异与转义问题（如 powershell 会对参数做额外解析）；确需目标 shell 特性（如复杂对象处理、过滤管道等）时才使用对应 shell

== 文档与代码对应同步

* 文档与代码对应同步：修改源码前必须先阅读相关文档（设计文档、测试文档、规范文档等），了解现状与既有约定，避免盲目改码；动手前先把接口与契约定下来（方法签名级：参数、返回、异常、边界），再实现，设计文档正文与代码在**同一提交内**补齐——该"先行"指同一提交内的先后顺序（定契约 → 实现 → 补文档），不是跨提交的先后要求；代码与文档必须能互相对应、可互相定位关联（如功能对应设计文档、测试用例对应测试文档与编号），改代码时同步改文档、改文档时同步改代码，不得只改一处、留一处不同步；可校验的完成定义见 link:../general/doc-design.adoc[]「版本与变更记录」
* 未提交前的更改归并：文档、代码在**尚未提交（git commit）**之前，期间的所有调整（含文档/代码的反复修改）均视为**同一次更改**，一律在当前本地基础上直接修改、覆盖演进，不额外产生中间版本/历史（无需为中间过程单独提交或留痕）；直到该次改动整体完成、可提交时再统一提交，从而避免本地频繁调整产生无用的中间历史
* 人工改动未告知时的处理：当 AI 写完一段代码后，发现该段代码被人为修改过**但未被告知**（可能是有问题的改动，也可能是冗余而 AI 未发现的改动），AI 若觉得该改动有问题时——**必须先实际验证当前代码**（编译/运行检查，避免误改），不得直接动手改回：验证通过则**保持现状**（人工改动可能是对的，AI 不一定发现问题）；验证不通过则可能需要修复；**严禁不做验证就直接修复**——否则可能把人工的正确修复还原成错误/冗余的代码（误改）

== 规范变更的存量处理

* **存量随动迁移，不一次性变更（L1）**：规范新增/调整后，**不一次性变更所有存量文件**——哪怕存量**完全不满足**该规范，也不为此发动全库改造。存量按 **"随项目开发、文件变动逐一慢慢迁移"**：改到某文件（或该文件确需改动）时**顺带**使之满足规范；操作要点：① 按新规范**新增/修改**的内容**必须**满足规范（不得"存量还这样"为由放宽新内容）；② 存量文件若本次未因需求而变动，**保持原样、不专门去改**（改动需有本次任务之外的理由）；③ 存量文件本次因需求而变动时，**随动一并调整**、不另攒一次"专门改规范"的批量迁移（避免改动堆积与二次返工）；④ 存量长期不合规范不视为违规，**不得**以"存量还没迁完"为由拒绝或推迟规范生效。
  ** 唯一例外是**主动声明**：用户/项目明确声明要一次性收敛存量（如"这次全库改名""全部迁到新结构"）时，按其声明执行——声明是例外而非默认，未声明一律按"不一次性变更存量"处理
  ** 本条的实践先例（与之一致、按同一原则执行）：link:../general/doc-lifecycle.adoc[]「存量文档迁移」、link:../general/doc-design.adoc[]「存量文档收敛」（逐类文档与逐文档版本记录**碰到哪迁哪**、不做全库一次迁移），link:../general/doc.adoc[]「注释与文档」（文档内容不得因承载位置迁移而减少、迁移不要求一步到位）
  ** 依据（工程先例）：大范围一次性机械改造会**批量污染提交历史**（真实变更淹没在噪声里，难以定位与回溯）、拉大改动面而**放大回归风险**，也违背"小步快跑、持续重构"的工程实践（小步重构的行进式约束见 Martin Fowler《Refactoring》"Prepare for refactoring"、Kent Beck《Extreme Programming Explained》"small steps"）；规范条目本身见 link:priority.adoc[]「分级定义」

== 范围控制

* 改动范围：原则上不得范围蔓延，执行范围以规划的目标与范围为界——不擅自扩大改动范围（要求 A 时不额外改 B；关联改动先说明并征得同意；回退自作主张的改动时只回退、不加新内容）；执行过程中发现前期规划有问题或需补充的新内容：先记录下来（如临时文档、问题清单），不中断当前任务，待当前任务完成后再考虑修复或补充，完成后须提醒用户；默认不中断任务，除非过程中发现严重偏移目标（需大幅变更方案、明显超出原任务边界）——严重偏移目标时：当前任务完成后直接停止，无需先向用户确认，由用户人工确认后再决定是否继续或调整
* 信息读取范围：改动任务须控制信息读取范围，防止为改小需求而对整个项目做全库扫描/code review。**未经用户声明**（用户未明确要求扫描整个项目/全库 code review）时：文件名/路径已知或可由 glob 直接定位的任务，必须用 glob/grep/read 精确取文件，**禁止**启动 explore 子智能体做全库扫描；只读取与当前任务直接相关的文件，不得借机对整个项目做 code review/全量摸底；仅在"位置未知、命名未知"的开放性查找时才使用 explore，且 prompt 须限定目标，不得要求"列出所有文件/读取全部源码/读取全部文档"；**用户明确声明要扫描整个项目时，不受上述限制**

== 任务编排与上下文管理

* 任务编排与上下文管理：互不影响的任务拆分并发执行，互相影响或需共享状态的必须串行，多任务先易后难；大范围检查及多步骤任务（调研、设计、编码、写用例、用例验证、文档等）的子 agent 拆分协作细节见 agent 协作规范（specs/general/collab.adoc）；大规模检查可能上下文不足时，进度与结果写入 `tmp/` 文件夹临时文档（见下条「临时产物」）：属临时记录、只做问题记录、不写备注（备注一律写入代码注释等持久文档），问题解决后可在其中更新解决状态；整个项目级别内容按子模块拆分、分步分批处理；后续任务不依赖当前上下文即可释放（清除历史上下文或开新会话）

== 任务放弃与中断

* 任务放弃与中断：任务在执行中被中断、且用户后续未明确提及继续该任务时，该任务视为放弃——用户改变主意或另起新任务时同理；放弃的判断以用户最新指令为准，不自行推断延续；放弃后不再做任何事（含还原/撤销已实施改动），由用户人工处理；已放弃/中断的任务不再考虑，不得再次追问确认是否继续、不得重新提起或自行延续（用户主动再次发起该任务时除外）

== 按操作加载规范（懒加载）

* 按操作加载规范：执行涉及某主题的操作前，须按 AGENTS_COMMON.adoc「分类与懒加载」加载该主题对应规范文件确认规则，不得凭记忆或仅凭常驻的 AGENTS_COMMON 猜测执行——如写 Java 前先加载 java 规范、跑测试/补测试前先加载测试规范、构建/依赖调整前先加载对应构建工具规范；加载的规范以其当前内容为准，不得因「不在常驻上下文」而跳过其要求
* 兜底确认（防"定义未生效"）：凡执行受规范约束的操作，若自检发现「未实际加载对应规范文件、仅凭记忆/印象执行」，须先主动加载该规范再继续；操作完成后自检一次「本次操作所依据的关键规范是否已加载、是否按其执行」，存在遗漏须补齐。不得以"我以为不算该规范范畴"为由规避加载（判断标准：操作符合 AGENTS_COMMON.adoc 加载调度中任一触发特征即须加载）

== 文件操作强制检查（必加载，避免历史断裂）

* 文件操作强制检查（避免历史断裂，**L1 最高关注项 P1**）：凡涉及**删除现有文件、移动/重命名文件、新建替代旧文件**的任何操作（含重构、拆分、整理文件结构），应保留历史的文件移动/重命名**必须使用 `git mv`**，禁止用「新增新文件 + 删除旧文件」代替（delete+create 会使 git 历史断裂）；**本条为最高关注项，重构/去重时只能加强不得削弱**（级别与原因见 link:priority.adoc[]「最高关注项」）；判断标准、兜底核对与拆分历史继承等完整规则见 git 规范 link:../general/git.adoc[]「文件移动与重命名」

== 临时产物

* 临时产物（权威定义）：进度记录、日志文件、扫描中间结果、临时规划文件、结果报告等临时产物，统一写入项目根目录 `tmp/` 文件夹（不存在则新建），按任务/文件类型等维度在 `tmp/` 下分类建子文件夹存放，不混在一起
* 临时产物不提交；**持久文档（代码注释、设计文档、测试文档、README 等）不得引用临时产物及其中的内容**（如问题编号、问题描述等——临时产物会被清理删除，其内容无出处可追溯）
* 清理 `tmp/` 下临时产物**非强制**——默认不清理（反复修改的任务每次清理后下次还会自动生成，强制清理反而徒增干扰）；清理仅在两类情况下执行：**用户主动声明要清理**（如明确要求清理/清空 `tmp/`）；或某临时产物**能确定即便反复修改/重复验证也不会再用到**（如一次性检查的中间结果、已确定不再需要的旧日志等）——此类可自行清理，其余一律保留
* 清理通过 `script/clean_tmp.py` 执行（本仓库提供的清理脚本，以当前工作目录为项目根，内置路径穿越防护仅限 `tmp/` 下，其他删除仍按常规确认）；该脚本**无需下载到目标项目**，在目标项目根目录以本地文件或远程加载方式执行——Linux/macOS 用 `curl -s <script-url> | python3 -`（stdin 执行），Windows 用 `Invoke-WebRequest` 下载到本地再执行（详见 script/clean_tmp.py 头部用法）
* 任务报告等大范围任务结果须生成文件（如 `tmp/check-result-*.md`），内容含检查范围、问题清单（分级编号）与处理状态，按临时产物处理（不提交）
