= 执行原则（必加载层）

以下规范适用于所有任务执行，为必加载层，每次工作都须遵循。涉及具体主题时再按 AGENTS_COMMON.adoc 的加载调度规则加载对应分类规范。

**条目优先级的分级与「最高关注项」（不可降级、重构首保）见「分级与最高关注项」**——本文件的 `严禁/必须` 类条目均为 L1，最高关注项以该节为准。

== 分级与最高关注项（先读）

条目按约束强度分三级，**级别决定违反后果、能否自行取舍与验证强度**。判定用语按 RFC 2119 / RFC 8174 归并：`必须/严禁/不得/禁止` = **L1**、`应当/优先/原则上` = **L2**、`可以/非强制/不要求` = **L3**；未标注级别的条目按其用语判定。

* **L1 强制（必须/严禁，不可协商）**：违反即视为**未完成**，不得提交/合并；**任何理由（含"重构""精简""上下文不够"）都不能豁免**，且须**可验证**。
* **L2 建议（应当/优先）**：默认遵守；存在**正当且可说明的理由**时可偏离，但须在代码注释/提交说明中写明取舍依据，不得无理由忽略。
* **L3 允许（可以/不强制）**：给出可选做法，不遵守不构成问题；仅在特定场景（工具支持、既有约定）下适用。
* **冲突次序（L1）**：L1 之间冲突时，以本节「最高关注项」为准；本规范与**引用方项目自己的项目规范**冲突时，以引用方项目自身规范为准（见 `AGENTS_COMMON.adoc`「访问与解析」），但**不得因此丢失 L1 的完整性要求**。

**最高关注项（不可降级）**：以下核心约束跨重构、去重、精简、迁移**必须保持，只能加强不得削弱**——不得从清单删除、不得改为"非最高关注项"、不得削弱其必加载层引用与判定标准。**保留形态是"一处完整定义 + 其余一行引用"**：最高关注项与其引用**允许、且应当在多处出现**（多处都指向它、不可能读不到），但**不复制完整正文**——判重时**先判定"是不是最高关注项的引用"**（是引用则不判为注水、不合并；只有逐字复制的完整定义才收敛为一处定义 + 引用）。**强调的正确做法**是"升级别 + 单一定义 + 显式引用"，不是把同一段话写两遍（复述会各自漂移，还会被误判为重复而合并删除）：

* **基础三条（L1，最高）**：①**文件移动/重命名必须用 `git mv`**，禁止「新增新文件 + 删除旧文件」——判定标准见 link:../general/git.adoc[]「文件移动与重命名」，必加载层重申见本文件「文件操作强制检查」；②**规范/文档调整不得丢失内容**（改完须跑机械校验核对引用与要点、内容一项不能少，"精简/去重"不得成为删内容的理由）；③**破坏性操作（删除/清空/覆盖等不可逆操作）先确认**目标、可回滚、范围可界定，三项任一不确定即**停下提问**，且**不得编造事实与来源**（命令/API、依赖坐标、标准编号与名称、链接与路径、数据与结论，不知道就明说并去查证）——完整规则见本文件「破坏性操作」与「自检（防"加载了却没执行"）」的『不得顺口编造（L1）』条。
* **读取与上下文纪律（条款本身 L2，同列最高关注项）**：**读取按最小必要、长会话里简单任务在干净上下文执行**、**执行轮次须合并（少绕）**（见本文件「范围控制」与「任务编排与上下文管理」）。**列为最高关注项 ≠ 条款本身是 L1**：不可降级保护的是其存在性与引用，而非把条款强度拔高。

== 为什么需要分级（业界依据）

条目若"看起来一样重要"，会导致两种失效：**关键约束被稀释**（"必须"与"建议"一视同仁，重构时顺手削弱最高约束）与**约束过载**（条条框框过多，AI 束手束脚、读者抓不住重点）。分级不是本规范自创，业界有成熟做法：

* **RFC 2119 / RFC 8174（IETF）**：以 `MUST`/`MUST NOT`/`SHOULD`/`MAY` 划分约束强度；RFC 8174 要求"只有全大写且本身是规范用语"才具约束力，避免歧义。
* **ISO/IEC Directives Part 2**：以 `shall`/`should`/`may` 区分**要求 / 建议 / 允许**，且"要求"必须可验证。
* **关键性分级（航空航天 DO-178C、IEC 61508 SIL、汽车 ISO 26262 ASIL 等安全关键领域的"完整性等级"）**：**级别越高、验证强度越高**，高等级需求不可降级、逐条追溯。
* **不变量（invariant）**：核心约束以"不变量"固化，改动只能**保持或加强**，不得因重构/去重/精简而降级。
* **单一事实来源（SSOT）**：同一约束只在**一处**给完整定义，其余只引用不复述（复述会漂移；"写两遍"强调属反模式，见上「强调的正确做法」）。

软件测试与评审相关条目的分级依据另见 ISO/IEC/IEEE 29119（软件测试）与 IEEE 1028（软件评审）。

== 各级别通用的遵守要求

* **L1**：视为不可协商。读到 L1 条目后必须按其执行；若与其它条目冲突，L1 优先（最高关注项优先级最高）；无法满足时必须**停止并说明**，不得默默降级或跳过。
* **L2**：默认遵守，偏离须有可说明的理由并留痕（注释/提交说明）；不得因"图快/省事"而无理由忽略。
* **L3**：可选，不遵守不构成问题；采用时以既有约定与工具支持为准。
* **不可降级**：任何重构/去重/精简**不得把 L1 降为 L2/L3、不得删除最高关注项的定义或引用**；调整规范时须逐条核对级别未被下调。
* **条目归位**：条目按主题写入对应分组规范，**级别用本节用语标注**；同一约束只在一处给完整定义，其余引用（见上「强调的正确做法」）。

== 指令执行

* 判准先于判定：写/改含"必须/不得"的规则前，先判定它属**严格执行**还是**尽力而为**（判据：**严格执行**＝判据固定、只有「做到/没做到」二值，没做到不得声明完成；**尽力而为**＝须尝试、须说明未达原因、**不记通过**；两者都必须留证，「未执行」与「通过」不得混写。完整口径见 link:../general/verify.adoc[]「判准维度：严格执行 / 尽力而为」）
* 每个任务都当尽力、严禁糊弄（L1）：本条**不做"尽力而为"的判准豁免**——它约束的是**做事的力度**：任务一经接手即须尽最大努力，不得糊弄、敷衍、凑数交付（"看起来完成了"不算完成，见下条判准维度）。**判定标准**：以"能跑就行/先这样吧/大概是"为由交付 / 只做能被看见的那部分、把难的部分留成"已知限制" / 先声明做不到而不做任何尝试——任一命中即不合规。**与「判准维度」的分工**：本条管"有没有尽力"，做不到时**仍须如实说明未达原因**（不因此把未完成写成完成），两条各管一事、不互相削弱。
* 指令执行：严格执行用户指令——需求有歧义时先提问澄清，不自行假设后动手；用户说的每一句话、每一个字都是有效指令，不允许忽略、跳过或选择性执行任何一个字（仅明显打错字除外），执行时逐字对照用户输入，确认全部落实后方可结束；每次操作后必须验证是否达到预期（如用 diff/status 比对、运行检查等确认结果）
* 规范调整的对象判定：用户提示"调整规范"时，**调整的是引用方项目自身的规范**（项目自己编写/维护的规范，如项目根 `AGENTS.adoc`、项目特有规范）；**公共规范**（由规范仓库自身维护、引用方以 https 方式引入的那套规范集合 `AGENTS_COMMON.adoc` 及其 `specs/`）**不属引用方的调整对象**——引用方**改不了**它，也**无需把它当作"待调整对象"去读**（遵循并按加载调度加载其规则的要求不受影响，见「按操作加载规范」）
* 规范调整的范围限定（**只改规范、不动其他文件**）：用户只提及"改动/调整规范"、**未要求同步或处理代码**时，**只处理规范文件本身、不动任何其他文件**，尤其是源码/测试等代码；**即便其他文件、代码不满足新规范，也不在本任务中处理**（保持原状，待用户另行声明再处理）

== 先规划后执行

* 先规划后执行：任何任务动手前必须先规划——明确目标与范围、拆解执行步骤、设计实现方案（复杂/有取舍的任务含备选方案与取舍评估），规划完成后再执行；规划文档须落到磁盘（如设计文档或临时规划文件），不得仅存于上下文（避免超出上下文限制）；规划文档是否需持久化按任务类型判断——项目代码开发等需提交的任务，规划按设计文档持久化（见 link:../general/doc-design.adoc[]），后续随代码一并提交；一般任务规划写入 `tmp/` 文件夹临时文档（见下条「临时产物」），方案在代码注释或执行说明中体现；执行中偏离规划时先调整规划再继续，不得边做边定方案
* **动手前先摸清现状与最佳方案（L1）**：动手前先**搞清现状**（相关代码/文档/用例与既有流程现在怎么运作，含被视为过时、待废弃的部分；不得凭印象或标题推断），再**先调研最佳实践、再定方案**（列出备选方案与取舍依据，不落"能交差"的写法）——三点展开为**先查现状 → 先调研最佳方案 → 先定基线**，完整口径见 link:../general/planning.adoc[]「动手前：现状与最佳方案」。
* 不得绕开既有体系另写一套（L1）：**默认改在既有实现上**（就地承载、归并去重）；新写一套往往比改既有省事，却会把同一件事变成两套实现/配置/文档，**达不到最佳实践**（"新写一套能满足需求"不等于"做得对"）。**允许另写一套的条件只有三个**，且须在规划里写明属哪一条：①既有实现**确实无法承载**需求；②既有实现**已被用户确认废弃/计划移除**；③新方案**已证明更优且明确取代**既有实现（须同时迁移调用方、处置或删除既有实现，**不留两套并存**）。**判定标准**：另写一套却既不说明理由也不处置既有实现 / 以"先让它跑起来"为由留下两套 / 把旧那套直接丢弃不管——任一命中即不合规。**展开（条件判据、处置动作与实例）见 link:../general/planning.adoc[]「不得绕开既有体系另写一套」。**
* 大范围改动先确认（L1）：凡会**替换、废弃或改写既有流程/既有做法**（而非增量修改）的改动，**动手前须向用户确认**（说清动哪段、为什么、不动会怎样；**未确认前保持原状**）；**不得替用户判定某段既有流程"已废弃"**——是否废弃由用户认定。**判定标准**：未确认即替换/删改既有流程、或把"这段看起来没人用了"当废弃依据——命中即不合规。**展开（确认四问、老旧废弃流程的处置）见 link:../general/planning.adoc[]「大范围改动先确认」。**
* 改动前先定基线（L1）：动手前须先把**既有行为**钉成可复核的基线——扫描项目声明的全部校验手段（测试用例、构建、静态检查、规范校验脚本；**运行环境须钉定**：基线须在项目声明的版本下取得），**既有验证手段完整可用时必须先跑通**，运行命令与统计结果**落盘留证**（见 link:../general/git.adoc[]）；改动完成后须**复跑同一套校验**并与基线逐项比对（既有校验全绿 + 新增校验全绿才算完成）。**扫出的清单还要先核"够不够用"（L2）**：手段可能不全、既有用例可能不全（边界未覆盖、正反例缺一侧、无步骤），须**先按用例设计判据 review 既有用例**、并说出"查了哪些角度、哪些未覆盖、哪些未确证"；**本次改动的直接相关面**的缺口先补全再动手，**无关的存量缺口**如实记录即可、**不阻断动手**。**判定标准**：未扫描既有校验手段 / 有完整可用的用例却不跑 / 跑了但不留证——任一命中即不合规。依据：ISO 10007（配置管理与变更控制，须有可追溯的基线状态）。**展开见 link:../general/planning.adoc[]「动手前先定基线」。**


== 命令执行

* 命令执行：能用项目自身提供的构建/运行脚本直接运行的命令优先用其直接执行，不套用更重的 shell——避免环境差异与转义；确需目标 shell 特性时再用

* 运行环境：开发与验证**一律用项目声明的那一个运行环境**（如 jdk1.8、python2），换别的版本也能跑通也不得换（L1）——判据与降级路径见 link:../general/ci-cd.adoc[]「运行环境须与项目声明一致」

== 文档与代码对应同步

* 文档与代码对应同步：修改源码前必须先阅读相关文档（设计文档、测试文档、规范文档等），了解现状与既有约定，避免盲目改码；动手前先把接口与契约定下来（方法签名级：参数、返回、异常、边界），再实现，设计文档正文与代码在**同一提交内**补齐——该"先行"指同一提交内的先后顺序（定契约 → 实现 → 补文档）；代码与文档必须能互相对应、可互相定位关联，改代码时同步改文档、改文档时同步改代码，不得只改一处、留一处不同步；可校验的完成定义见 link:../general/doc-design.adoc[]「版本与变更记录」
* 未提交前的更改归并：文档、代码在**尚未提交（git commit）**之前，期间的所有调整（含文档/代码的反复修改）均视为**同一次更改**，一律在当前本地基础上直接修改、覆盖演进，不额外产生中间版本/历史（无需为中间过程单独提交或留痕），也不得反复改写行尾（LF/CRLF 的来回转换会污染 diff；行尾取值见 link:../general/encoding.adoc[]「换行符」）；直到该次改动整体完成、可提交时再统一提交，从而避免本地频繁调整产生无用的中间历史
* 人工改动未告知时的处理：当 AI 写完一段代码后，发现该段代码被人为修改过**但未被告知**（可能是有问题的改动，也可能是冗余而 AI 未发现的改动），AI 若觉得该改动有问题时——**必须先实际验证当前代码**（编译/运行检查，避免误改），不得直接动手改回：验证通过则**保持现状**（人工改动可能是对的，AI 不一定发现问题）；验证不通过则可能需要修复；**严禁不做验证就直接修复**——否则可能把人工的正确修复还原成错误/冗余的代码（误改）

== 规范变更的存量处理

* **存量随动迁移，不一次性变更（L1）**：规范新增/调整后，**不一次性变更所有存量文件**——哪怕存量**完全不满足**该规范，也不为此发动全库改造。存量按 **"随项目开发、文件变动逐一慢慢迁移"**：改到某文件（或该文件确需改动）时**顺带**使之满足规范；操作要点：① 按新规范**新增/修改**的内容**必须**满足规范（不得"存量还这样"为由放宽新内容）；② 存量文件若本次未因需求而变动，**保持原样、不专门去改**（改动需有本次任务之外的理由）；③ 存量文件本次因需求而变动时，**随动一并调整**、不另攒一次"专门改规范"的批量迁移（避免改动堆积与二次返工）；④ 存量长期不合规范不视为违规，**不得**以"存量还没迁完"为由拒绝或推迟规范生效。
  ** 唯一例外是**主动声明**：用户/项目明确声明要一次性收敛存量（如"这次全库改名""全部迁到新结构"）时，按其声明执行——声明是例外而非默认，未声明一律按"不一次性变更存量"处理
  ** 本条的实践先例（与之一致、按同一原则执行）：link:../general/doc-lifecycle.adoc[]「存量文档迁移」、link:../general/doc-design.adoc[]「存量文档收敛」（逐类文档与逐文档版本记录**碰到哪迁哪**、不做全库一次迁移），link:../general/doc.adoc[]「注释与文档」（文档内容不得因承载位置迁移而减少、迁移不要求一步到位）
  ** 依据（工程先例）：大范围一次性机械改造会**批量污染提交历史**（真实变更淹没在噪声里，难以定位与回溯）、拉大改动面而**放大回归风险**，也违背"小步快跑、持续重构"的工程实践（小步重构的行进式约束见 Martin Fowler《Refactoring》"Prepare for refactoring"、Kent Beck《Extreme Programming Explained》"small steps"）；规范条目见本文件「分级与最高关注项」

== 任务生命周期与节点自查（AI 侧，各节点该查什么）

任务从提出到收尾会经过若干**节点**：**提出 → 理解 → 方案 → 执行 → 验证 → 交付 → 复盘**。AI 侧节点任何任务都有；**复盘**只在涉及公共内容（规范、提示词、会被外部加载的工具）时才有——"为什么要按节点自查、为什么代码类任务不做全套"的口径见 link:../general/verify.adoc[]「验证的适用边界」。**节点与判据的效力标法**：除**复盘**外各节点对任何任务成立（L1）；**该表是"到点该回答什么"的索引，判据本体在被引用文件**——索引指向的落点失效即等于没有这条要求，故本表各行的引用落点须由机械防线核对仍在。各节点的核对问题（答不上即**停在原地补齐**，不得往下做）：

[cols="1,3", options="header"]
|===
| 节点 | 到点必须能回答
| **提出** | 用户表述不清时先澄清再动手；**目标、范围、产物形态不明确时不得自行假设后开工**（见「指令执行」）
| **理解** | 触发特征对应的规范**是否已实际加载**（不是"知道有"，见「按操作加载规范」）；本任务**最小必要信息集**是什么（先定出本次任务必须知道的最小信息集，见本文件「范围控制」）
| **方案** | 规划是否已落盘（见「先规划后执行」）；**基线是否已定**（含**运行环境已按项目声明钉定**，见 link:../general/planning.adoc[]「动手前先定基线」与 link:../general/ci-cd.adoc[]「运行环境须与项目声明一致」）；**去重与删减前**覆盖完整性是否已核对（见「分级与最高关注项」基础三条②）
| **执行** | 被派发/被引用时加载是否**由已加载入口驱动**（见 `AGENTS_COMMON.adoc`「访问与解析」）；环境能力是否已判定（无法确认按「不可用」走降级路径并如实记录，不得空自评）
| **验证** | **是否与基线逐项比对**（须复跑全绿、既有用例不得被改写放宽，见 link:../general/testing.adoc[]「执行与验证」）；**先判改动性质、再选验证范围**（见 link:../general/verify.adoc[]「验证的适用边界」）——**代码类改动按机械判据判过不过（能过即过）**；只有**涉及公共内容**的改动才做「规范验证」三视角、从全局核对"这条规则要解决的失效现在还在不在"，且能枚举"验了什么、怎么算过、依据哪个标准"；**结论按效力等级标**——**确定项**判**通过/不通过**（未过才阻断交付）；**概念项**只标**未发现问题/悬置**（不得当作交付前置条件）
| **交付** | 交付形态**按执行环境区分**（见 link:../general/git.adoc[]）；落盘是否与改动同步（changelog、登记）
| **复盘**（仅公共内容改动，判据见下条） | 用**三视角**评本次改动的**有效性**（见 link:../general/verify.adoc[]「验证总纲」）；核**规则自身**——初衷还在不在、有没有被写成一句"要注意"（判据被压成口号即失效）；核**该不该拆分**与拆分后是否**自洽**——**默认不拆**：三条硬条件（判据形态或加载时机不同 / 不拆就真的坏 / 拆后每一半都自足）同时成立才拆，拆完逐项核对引用可达、无自相矛盾、不失完整性、登记同步
|===

* **哪些节点不设（L1）**：**代码类改动**（改代码、修缺陷）**不设**复盘节点（见上表该行），**不做**三视角、**不做**全局核对——**能过就是能过**，不得把规范类改动的验证义务搬到代码类改动上；反之，**涉及公共内容的改动**不得只跑机械校验就收尾。**据此，"代码类改动是否也要做复盘"不再需要读者自行争辩**：先按 link:../general/verify.adoc[]「验证的适用边界」判性质，再套本节。

== 范围控制

**本节的逐条判据**（读取按任务定界、定位优先、分层渐进、重型读取委派子 agent、读前读后自检、任务切换即清洁上下文、长会话降级自保、简单任务优先另起会话、阶段结论即时落盘、超长任务分段）**完整正文**落在 link:../general/context.adoc[]（任务开始时即加载）；下方**改写范围的边界**属最高关注项，其判据见 link:../general/scope.adoc[]。

* **改动范围的边界（L1，最高关注项）**：本节的"改动范围"指**入口工作空间/入口项目内部**的蔓延控制；**改动不得越出入口工作空间（在平台上即"只改当前项目"）**——越界改动的禁令、"未声明即拒绝"、"引用 ≠ 授权"、判定标准与拒绝的形态见 link:../general/scope.adoc[]（涉及即加载）。本条与本节其余条目**同维度、互不替代**；该禁令属最高关注项、不可降级，凡本文件提到"范围控制"时均含它。
* 改动范围：原则上不得范围蔓延，执行范围以规划的目标与范围为界——不擅自扩大改动范围（要求 A 时不额外改 B；关联改动先说明并征得同意；回退自作主张的改动时只回退、不加新内容）；执行过程中发现前期规划有问题或需补充的新内容：先记录下来（如临时文档、问题清单），不中断当前任务，待当前任务完成后再考虑修复或补充，完成后须提醒用户；默认不中断任务，除非过程中发现严重偏移目标（需大幅变更方案、明显超出原任务边界）——严重偏移目标时：当前任务完成后直接停止，无需先向用户确认，由用户人工确认后再决定是否继续或调整
== 任务编排与上下文管理

* 任务编排、上下文与执行吞吐（判据的完整正文见 link:../general/context.adoc[]）：互不影响的任务拆分并发执行、互相影响或需共享状态的串行，多任务先易后难；**互相无依赖的调用/读取须一次批量发出、构建与校验的输出须一次取到、长流程不得零信息空转**（执行吞吐判据见该文件「执行吞吐」）；子 agent 拆分协作见 link:../general/collab.adoc[]；大范围检查的进度与结果写入 `tmp/`（见「临时产物」），属临时记录、只做问题记录、不写备注（备注写入持久文档，**落点按事项的适用范围判定**，见 link:../general/review.adoc[]「问题记录」）；项目级内容按子模块分步分批处理；后续任务不依赖当前上下文即可释放

== 任务放弃与中断

* 任务放弃与中断：任务被中断、且用户后续未明确提及继续时，视为放弃（用户改变主意或另起新任务时同理；以用户最新指令为准，不自行推断延续）；放弃后不再做任何事（含还原/撤销改动），由用户人工处理；已放弃的任务不得再追问、重提或自行延续（用户再次发起时除外）

== 按操作加载规范（懒加载）

* 按操作加载规范：执行涉及某主题的操作前，须按 AGENTS_COMMON.adoc「分类与懒加载」加载对应规范文件确认规则，不得凭记忆或仅凭常驻入口猜测——如写 Java 前加载 java 规范、跑测试前加载测试规范、构建/依赖调整前加载构建工具规范；以加载到的当前内容为准。
* 兜底确认（防"定义未生效"）：凡执行受规范约束的操作，若自检发现「未实际加载对应规范文件、仅凭记忆/印象执行」，须先主动加载该规范再继续；操作完成后自检一次「本次操作所依据的关键规范是否已加载、是否按其执行」，存在遗漏须补齐。不得以"我以为不算该规范范畴"为由规避加载（判断标准：操作符合 AGENTS_COMMON.adoc 加载调度中任一触发特征即须加载）

== 自检（防"加载了却没执行"）

* **执行前自检（L1，非平凡任务）**：需读完再动手的**多步骤任务**（含文档/代码/脚本）在动手前须**逐项**过一遍执行前自检清单（指令是否逐字落实、触发的规范是否已实际加载、规划是否已落盘、读取是否在最小必要信息集内、改动处是否已实际读过、完成如何验证）——任一项不通过或不确定即**不得继续**，先补齐再动手；同时执行"逐条对照本次触发特征加载对应规范"（见上条「按操作加载规范」）。**执行前自检（逐项，任一项不通过或不确定即不得继续）**：①**指令**是否已逐字理解、歧义是否已提问澄清；②**规范**是否已实际加载（只凭记忆视为未通过）；③**规划**是否已定并落盘（只存于上下文即未通过）；④**读取范围**最小必要信息集是否已确定、是否精确定位；⑤**证据**要改的地方是否已实际读过、依据的事实是否已核实；⑥**影响面**（调用方、文档、测试、changelog）是否已列出；⑦**收尾**如何验证、依据哪条命令的哪个统计结果。**过程自检**：每步完成后自检"是否达到该步预期"，未过先修再进下一步；执行中发现实际与规划不符时**先停下**、调整规划后再继续。**完成前自检**：回到用户原话**逐条**对照完成情况、逐项复检上述七项（特别确认"未擅自扩大范围、未遗漏任何一项"）；有未完成项、未核实项、无法验证项时**显式列出并说明原因**，不得掩盖或用"已完成"笼统带过。
* **不得顺口编造（L1）**：涉及命令/API、依赖坐标、标准编号与名称、链接与路径、数据与结论等事实时，**不知道就明说并去查证**，不得凭印象生成；推断与事实须分开标注（完整规则见本文件「分级与最高关注项」基础三条③，以及下方「破坏性操作」）。宁可不给，不得给错。

== 文件操作强制检查（必加载，避免历史断裂）

* 文件操作强制检查（避免历史断裂，**L1 最高关注项 P1**）：凡涉及**删除现有文件、移动/重命名文件、新建替代旧文件**的任何操作（含重构、拆分、整理文件结构），应保留历史的文件移动/重命名**必须使用 `git mv`**，禁止用「新增新文件 + 删除旧文件」代替（delete+create 会使 git 历史断裂）；**本条为最高关注项，重构/去重时只能加强不得削弱**（本条为最高关注项，重构/去重时只能加强不得削弱）；判断标准、兜底核对与拆分历史继承等完整规则见 git 规范 link:../general/git.adoc[]「文件移动与重命名」
* **重命名与内容修改须分两个提交（L1 最高关注项 P7）**：一次改动里**既重命名该文件、又修改其内容**时，一律拆成两个提交——第一个提交**只做重命名、内容逐字节不变**（先 `git mv` 并只提交改名），第二个提交**再改内容**、不再动路径；分量小、引用少都不是合并的理由，无正当理由可豁免（唯一例外：用户明确声明合并成一个提交）。**本条为最高关注项，重构/去重时只能加强不得削弱**；完整规格（判定标准、提交顺序、无损拆分、两个提交都要进本次交付、自检命令）见 git 规范 link:../general/git.adoc[]「重命名与内容修改须分两个提交（默认固定动作）」

== 破坏性操作（不可逆，先确认再动手）

* **不可逆操作先确认（L1）**：删除文件/目录、清空数据、`rm -rf`、覆盖未提交的改动、`git reset --hard`、强推覆盖远端等操作**一律先确认**——①**目标是不是要删的那个**（用精确路径/选择器，禁止通配与整目录扫删）；②**能不能取回**（未提交的改动先备份或先提交到临时分支，可回滚）；③**范围是否可界定**（只动允许动的位置，不越出项目/任务边界）。三项任一不确定即**停下提问**，不得"先删了再说"。
* **删除有前例可循的脚本化路径（L2）**：目录级清理走项目提供的清理脚本（如 link:../general/script.adoc[] 的清理约定），不手写 `rm -rf`；脚本本身须内置边界校验（防路径穿越）。
* **不覆盖他人未提交的工作（L1）**：不得用 `git checkout`/`reset`/`clean` 覆盖或丢弃**不属于本次改动**的本地修改；发现疑似的未告知改动按「人工改动未告知时的处理」验证后再定。
* **删前先留痕（L2）**：删除前确认内容已迁入合适落点（如文档迁移见 link:../general/doc-design.adoc[]「存量文档收敛」），并核对删除后"内容不减少"（最高关注项 P3）。

== 临时产物

* 临时产物（权威定义）：进度记录、日志文件、扫描中间结果、临时规划文件、结果报告等临时产物，统一写入项目根目录 `tmp/` 文件夹（不存在则新建），按任务/文件类型分类建子文件夹，不混在一起
* 临时产物不提交；**持久文档（代码注释、设计文档、测试文档、README 等）不得引用临时产物及其中的内容**（如问题编号、问题描述等——临时产物会被清理删除，其内容无出处可追溯）
* 清理 `tmp/` 下临时产物**非强制**——默认不清理（反复修改的任务每次清理后下次还会自动生成，强制清理反而徒增干扰）；清理仅在两类情况下执行：**用户主动声明要清理**（如明确要求清理/清空 `tmp/`）；或某临时产物**能确定即便反复修改/重复验证也不会再用到**（如一次性检查的中间结果、已确定不再需要的旧日志等）——此类可自行清理，其余一律保留
* 清理通过 link:../general/script.adoc[]「临时产物清理」约定的清理脚本执行（以当前工作目录为项目根，内置路径穿越防护仅限 `tmp/` 下，其他删除仍按常规确认）
* 任务报告等大范围任务结果须生成文件（如 `tmp/check-result-*.md`），内容含检查范围、问题清单（分级编号）与处理状态，按临时产物处理（不提交）
