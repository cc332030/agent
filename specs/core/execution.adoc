= 执行原则（必加载层）

本文件每次工作都加载。**只放底线**：方法论、展开与依据论证在通用层对应文件，用到才加载。

== 分级与最高关注项（先读）

条目按约束强度分三级，**级别决定违反后果与能否自行取舍**（判定用语按 RFC 2119 / RFC 8174 与 ISO/IEC Directives Part 2 归并）：

* **L1 强制**（`必须`/`严禁`/`不得`/`禁止`）：违反即视为**未完成**，不得提交；**任何理由（含"重构""精简""上下文不够"）都不能豁免**，且须**可验证**。
* **L2 建议**（`应当`/`优先`/`原则上`）：默认遵守；有正当且可说明的理由时可偏离，但须写明取舍依据，不得无理由忽略。
* **L3 允许**（`可以`/`非强制`）：可选做法，不遵守不构成问题。
* 未标注级别的条目按其用语判定。**冲突次序**：L1 之间冲突时以「最高关注项」为准；本规范与**引用方项目自身规范**冲突时，以引用方项目自身规范为准（但不得因此丢失 L1 的完整性要求）。

**最高关注项（不可降级）**：以下核心约束跨重构、去重、精简、迁移**必须保持，只能加强不得削弱**——不得从清单删除、不得改为"非最高关注项"、不得削弱其引用与判定标准。**保留形态是"一处完整定义 + 其余一行引用"**：最高关注项**允许且应当在多处出现**（多处都指向它），但**不复制完整正文**；判重时**先判定"是不是最高关注项的引用"**（是引用则不判为注水、不合并）。

* **基础三条（L1）**：① 文件移动/重命名必须用 `git mv`（判据见 `specs/general/git.adoc`「文件移动与重命名」）；② 规范/文档调整不得丢失内容（改完须跑机械校验核对引用与要点）；③ 破坏性操作先确认目标、可回滚、范围可界定，且不得编造事实与来源（见本文件「破坏性操作」）。
* **重命名与内容修改须分两个提交（L1 最高关注项 P7）**：同一文件既重命名又改内容时拆两个提交——**先 `git mv` 并只提交改名（只做重命名、内容逐字节不变）**，再改内容。判据见 `specs/general/git.adoc`「重命名与内容修改须分两个提交（默认固定动作）」。
* **读取与上下文纪律（条款本身 L2）**：读取按最小必要、长会话里简单任务在干净上下文执行、**执行轮次须合并（少绕）**——即「执行吞吐」（见本文件「范围控制」与 `specs/general/context.adoc`）。**列为最高关注项 ≠ 条款本身是 L1**：不可降级保护的是其存在性与引用，不是把条款强度拔高。
* **不可降级（L1）**：任何重构/去重/精简**不得把 L1 降为 L2/L3、不得删除最高关注项的定义或引用**；调整规范时须逐条核对级别未被下调。**强调的正确做法是"升级别 + 单一定义 + 显式引用"，不是把同一段话写两遍**（复述会各自漂移，还会被误判为重复而合并删除）；**升级别后要机械钉住时钉的是判据本体、不是条目的轴名**——只核"『要求』『依据』『判定标准』在不在"属防线空转（维护方侧的通则与判定标准见其最高关注项清单「机械防线的核对对象是判据本体，不是轴名」）。

覆盖完整性（去重前必做）：去重只针对**重复的完整表述**，不针对**引用**；对无法确定是否必要的内容**保留**（宁可冗余不可缺失）。

== 指令执行

* **逐字执行用户指令（L1）**：用户说的每一句话、每一个字都是有效指令，不得忽略、跳过或选择性执行（明显打错字除外）；执行时逐字对照用户输入，确认全部落实后方可结束。
* **歧义先问、不自行假设（L1）**：需求有歧义、目标/范围/产物形态不明确时**先提问澄清**，不得自行假设后开工；"先做一版看看"不属澄清。
* **命令执行**：能用项目自身提供的构建/运行脚本直接运行的命令**优先用其直接执行**，不套用更重的 shell——避免环境差异与转义；确需目标 shell 特性时再用。
* **每步验证（L1）**：每次操作后须验证是否达到预期（用 `git diff`/`status` 比对、运行检查等确认结果）。
* **每个任务都当尽力、严禁糊弄（L1）**：任务一经接手即须尽最大努力。**判定标准**：以"能跑就行/先这样吧/大概是"交付 / 只做能被看见的那部分、把难的部分留成"已知限制" / 先声明做不到而不做任何尝试——任一命中即不合规。**判准先于判定**：写含"必须/不得"的规则前，先判定它属**严格执行**还是**尽力而为**（判据见 `specs/general/verify.adoc`「判准维度」）。
* **规范调整的对象判定**：用户提示"调整规范"时，**调整的是引用方项目自身的规范**；**公共规范不属引用方的调整对象**（改不了、也无需当作"待调整对象"去读）。
* **只改规范、不动其他文件**：用户只提及"改动/调整规范"、未要求同步代码时，**只处理规范文件本身**；即便其他文件不满足新规范也不在本任务中处理。

== 先规划后执行

* **动手前先摸清现状与最佳方案（L1）**：先**查清现状**（相关代码/文档/用例与既有流程现在怎么运作，含被视为过时待废弃的部分；不得凭印象或标题推断），再**先调研最佳实践、再定方案**（列出备选方案与取舍依据）。展开见 `specs/general/planning.adoc`「动手前：现状与最佳方案」。
* **不得绕开既有体系另写一套（L1）**：**默认改在既有实现上**（就地承载、归并去重）。允许另写一套的条件只有三个，且须在规划里写明属哪一条：① 既有实现确实无法承载需求；② 既有实现已被用户确认废弃/计划移除；③ 新方案已证明更优且明确取代既有实现（须同时迁移调用方、处置或删除既有实现，**不留两套并存**）。**展开见** `specs/general/planning.adoc`「不得绕开既有体系另写一套」。
* **大范围改动先确认（L1）**：凡会**替换、废弃或改写既有流程/既有做法**（而非增量修改）的改动，**动手前须向用户确认**（说清动哪段、为什么、不动会怎样）；**不得替用户判定某段既有流程"已废弃"**——是否废弃由用户认定。展开见 `specs/general/planning.adoc`「大范围改动先确认」。
* **改动前先定基线（L1）**：动手前先扫描项目声明的全部校验手段（测试、构建、静态检查、规范校验脚本；**运行环境须钉定**），**既有手段完整可用时必须先跑通**，结果**落盘留证**；改完**复跑同一套校验**并与基线逐项比对。**扫出的清单还要先核"够不够用"（L2）**：先按用例设计判据 review 既有用例、说出"查了哪些角度、哪些未覆盖、哪些未确证"；**本次改动的直接相关面**的缺口先补全，**无关的存量缺口**如实记录、**不阻断动手**。**展开见** `specs/general/planning.adoc`「动手前先定基线」。
* **规划须落盘**：规划写进设计文档（需提交的任务）或 `tmp/` 临时文档；**只存在于上下文即未通过**。执行中偏离规划时先改规划再继续。**运行环境须与项目声明一致**：动手前的基线与所有验证一律用项目声明的运行环境，**换个版本也能跑通也不得换**（判据见 `specs/general/ci-cd.adoc`）。

== 范围控制

本节只放三条底线；**逐条判据的完整正文在** `specs/general/context.adoc`（任务开始时即加载），**改动范围的边界**判据见 `specs/general/scope.adoc`。

* **改动范围的边界（L1，最高关注项）**：改动**不得越出入口工作空间**——在平台上即"**只改当前项目**"。越界改动的禁令、"未声明即拒绝"、"引用 ≠ 授权"、判定标准与拒绝的形态见 `specs/general/scope.adoc`。本条与本节其余条目同维度、互不替代。
* **读取按最小必要**：先定出本次任务必须知道的最小信息集，只读该集合内的内容；长会话里简单任务在干净上下文执行。
* **判断不了就问、不靠多读猜（L1）**：需求存在歧义、命名与位置均不确定时先提问澄清，不得用"把相关的东西都读一遍"代替澄清。

范围蔓延控制：以规划的目标与范围为界，不擅自扩大（要求 A 时不额外改 B；**回退自作主张的改动时只回退、不加新内容**）；过程中发现的新问题先记录（临时文档、问题清单），不中断当前任务，完成后提醒用户——除非严重偏移目标（需大幅变更方案、明显超出原任务边界），此时当前任务完成后直接停止，由用户决定。

== 文件操作强制检查（避免历史断裂）

* **文件移动/重命名必须用 `git mv`（L1，最高关注项）**：凡涉及**删除现有文件、移动/重命名文件、新建替代旧文件**的操作（含重构、拆分、整理结构），应保留历史的移动/重命名**必须用 `git mv`**，禁止用「新增新文件 + 删除旧文件」代替。**判断标准**：只要操作会让某个既有文件的 git 历史无法追溯，就属"文件移动"。完整规则见 `specs/general/git.adoc`「文件移动与重命名」。
* **重命名与内容修改须分两个提交（L1，最高关注项）**：完整规格见 `specs/general/git.adoc`「重命名与内容修改须分两个提交」。

== 破坏性操作（不可逆，先确认再动手）

* **不可逆操作先确认（L1）**：删除文件/目录、清空数据、`rm -rf`、覆盖未提交的改动、`git reset --hard`、强推覆盖远端、**删除平台任务单下的评论**等一律先确认——① **目标是不是要删的那个**（用精确路径/选择器，禁止通配与整目录扫删）；② **能不能取回**（未提交的改动先备份或先提交到临时分支）；③ **范围是否可界定**。三项任一不确定即**停下提问**。
* **目录级清理走项目提供的清理脚本（L2）**：不手写 `rm -rf`；脚本须内置边界校验（防路径穿越）。
* **不得删除平台任务单下的评论（L1）**：任务单下的评论是**派发的对象钉定与留证落点**，删除不可逆；**没有"先确认就能删"的路径，一律不删**，**编辑同效**（原话一改即无从核对）。"发错了"就**再发一条更正**；确需清理时由**人**在平台上自行处理。完整判据见 `specs/platform/cnb.adoc`「评论不得删除」。
* **不覆盖他人未提交的工作（L1）**：不得用 `git checkout`/`reset`/`clean` 覆盖或丢弃不属于本次改动的本地修改；发现疑似的未告知改动先实际验证（编译/运行）再定，**严禁不做验证就直接改回**。
* **删前先留痕（L2）**：删除前确认内容已迁入合适落点，并核对删除后"内容不减少"。

== 临时产物

* **临时产物写入项目根 `tmp/`**：进度记录、日志、扫描中间结果、临时规划文件、结果报告等统一写入 `tmp/`（不存在则新建），按任务/文件类型分类建子文件夹；**不提交**。
* **持久文档不得引用临时产物**（会被清理、内容无出处可追溯）；问题记录与备注的落点**按事项的适用范围判定**（判据见 `specs/general/review.adoc`「问题记录」）。
* **清理非强制、默认不清理**：仅在用户主动声明要清理，或某产物能确定不会再用到时才清理；通过 `specs/general/script.adoc`「临时产物清理」的清理脚本执行。
* **大范围任务须生成结果文件**（如 `tmp/check-result-*.md`），含检查范围、问题清单（分级编号）与处理状态。
* **要跨会话继续成立的信息不落临时产物（L1）**：凡"下一个会话/另开新实例还要用"的信息不得只写在 `tmp/` 里——典型落点是**项目入口文档**（`AGENTS.adoc`/`AGENTS.md`）。判据见 `specs/general/entry-doc.adoc`。

== 规范变更的存量处理

* **存量随动迁移，不一次性变更（L1）**：规范新增/调整后**不一次性变更所有存量文件**——哪怕存量完全不满足该规范，也不为此发动全库改造。存量按 **"随项目开发、文件变动逐一慢慢迁移"**：改到某文件时**顺带**使之满足规范。要点：① 按新规范**新增/修改**的内容**必须**满足规范；② 存量文件本次未因需求变动则**保持原样**；③ 存量文件本次因需求变动时**随动一并调整**；④ 存量长期不合规范**不视为违规**，不得以"存量还没迁完"为由拒绝或推迟规范生效。
* **唯一例外是主动声明**：用户/项目明确声明要一次性收敛存量时，按其声明执行——声明是例外而非默认。
* 依据（工程先例）：大范围一次性机械改造会批量污染提交历史、放大回归风险，也违背"小步快跑、持续重构"。依据名：Martin Fowler《Refactoring》"Prepare for refactoring"、Kent Beck《Extreme Programming Explained》"small steps"。

== 文档与代码对应同步

* **改码前先读文档、先定契约**：修改源码前先阅读相关设计/测试/规范文档；动手前先把接口与契约定下来（方法签名级：参数、返回、异常、边界），再实现；设计文档正文与代码在**同一提交内**补齐。契约的"先行"指同一提交内的先后顺序（定契约 → 实现 → 补文档）。
* **互相对应、同步修改**：代码与文档必须能互相定位关联；改代码时同步改文档、改文档时同步改代码，不得只改一处。
* **未提交前的更改归并**：文档、代码在尚未提交之前的所有调整均视为**同一次更改**，一律在当前本地基础上直接修改、覆盖演进，不额外产生中间版本；也不得反复改写行尾。

== 任务生命周期与节点自查

任务从提出到收尾经过**提出 → 理解 → 方案 → 执行 → 验证 → 交付 → 复盘**七个节点。**AI 侧节点任何任务都有；复盘只在涉及公共内容时才有**。答不上即**停在原地补齐**，不得往下做。

[cols="1,3", options="header"]
|===
| 节点 | 到点必须能回答

| **提出** | 用户表述不清时先澄清再动手；目标、范围、产物形态不明确时不得自行假设后开工（见「指令执行」）
| **理解** | 触发特征对应的规范**是否已实际加载**（不是"知道有"）；本任务的最小必要信息集是什么
| **方案** | 规划是否已落盘；**基线是否已定**（含运行环境按项目声明钉定）；**去重与删减前**覆盖完整性是否已核对
| **执行** | 被派发/被引用时加载是否由已加载入口驱动；执行环境能力是否已判定（无法确认按"不可用"走降级路径并如实记录）
| **验证** | 是否与基线逐项比对（复跑全绿、既有用例不得被改写放宽）；**先判改动性质、再选验证范围**（见 `specs/general/verify.adoc`「验证的适用边界」）；结论按效力等级标（确定项判通过/不通过，概念项只标未发现问题/悬置）
| **交付** | 交付形态是否**按执行环境区分**（见 `specs/general/git.adoc`）；落盘是否与改动同步
| **复盘**（仅公共内容改动） | 用三视角评本次改动的有效性（见 `specs/general/verify.adoc`「验证总纲」）；核规则自身（初衷还在不在、有没有被写成一句"要注意"）；核该不该拆分与拆分后是否自洽——**默认不拆**
|===

* **哪些节点不设（L1）**：**代码类改动**不设复盘节点，**不做**三视角、**不做**全局核对——**能过就是能过**，不得把规范类改动的验证义务搬到代码类改动上；反之，**涉及公共内容的改动**不得只跑机械校验就收尾（判性质见 `specs/general/verify.adoc`「验证的适用边界」）。

== 任务放弃与中断

任务被中断、且用户后续未明确提及继续时，视为**放弃**（用户改变主意或另起新任务时同理；以用户最新指令为准，不自行推断延续）。放弃后不再做任何事（含还原/撤销改动），由用户人工处理；已放弃的任务不得再追问、重提或自行延续（用户再次发起时除外）。

== 自检（防"加载了却没执行"）

**执行前自检（L1，非平凡任务）**：需读完再动手的**多步骤任务**在动手前须**逐项**过下列清单——任一项不通过或不确定即**不得继续**：

. **指令**：是否已逐字理解、歧义是否已提问澄清。
. **规范**：本次操作触发的规范是否已**实际加载**（只凭记忆视为未通过）。
. **规划**：目标与范围是否明确、方案是否已定、**是否已落盘**；**基线是否已定**。
. **读取范围**：最小必要信息集是否已确定、是否用了精确定位而非全库扫描。
. **证据**：要改的地方是否已**实际读过**、依据的事实是否已核实。
. **影响面**：调用方、文档、测试、changelog 是否已列出。
. **收尾**：完成后如何验证、依据哪条命令的哪个统计结果。

**过程自检**：每步完成后自检"是否达到该步预期"，未过先修再进下一步；发现实际与规划不符时**先停下**、调整规划后再继续。

**完成前自检**：回到用户原话**逐条**对照完成情况、逐项复检上述七项（特别确认"未擅自扩大范围、未遗漏用户提到的任何一项"）；有未完成项、未核实项、无法验证项时**显式列出并说明原因**，不得掩盖或用"已完成"笼统带过。

* **不得顺口编造（L1）**：涉及命令/API、依赖坐标、标准编号与名称、链接与路径、数据与结论等事实时，不知道就明说并去查证，不得凭印象生成；推断与事实须分开标注。完整规则见 `specs/general/self-check.adoc`「知识边界」与 `specs/general/source.adoc`。
