= SQL 编写规范（通用层，跨语言）

适用于**要写/改 SQL 的项目**——任何语言、任何宿主里的 `.sql` 与迁移脚本、数据访问层里的语句。加载触发特征：出现 `.sql` 文件（新建或改动）、或要写/改 `ALTER TABLE`/`CREATE TABLE`/`INSERT`/`UPDATE` 一类语句。**数据库语法与方言差异**（某动作能不能合并、要不要 `ALGORITHM`/`LOCK`）按目标数据库官方文档执行；本文件只给**跨数据库成立的写法判据**。数据访问层的抽象形态见 `specs/general/coding.adoc`「持久化访问（数据库/缓存等）」，各技术栈的落点见 `specs/stack/` 对应文件。

== SQL 写法

* **承载（L1）**：SQL **须独立成文件**、**SQL 文本里须带库名**——**语句与取值分离**的通用判据（落点、扩展名、读取方式、加载时机）见 `specs/general/coding.adoc`「跨语言执行脚本的落点」，本文件只写 SQL 专属的两条判据与合并条，**不复制其正文**（真源一处、其余一跳引用）。

* **独立成文件（L1，用户点名）**：SQL **单独建文件**（`.sql`，放项目的资源目录，如 `src/main/resources/sql/`）——**不与宿主语言代码共处一个文件**、**不作为宿主语言字符串**（字符串常量/拼接/模板/文本块）。宿主执行时**按资源加载 `.sql` 文件**、以参数化方式绑定取值：**独立成文件**是"语句与取值分离"的承载层前提（注入防护见 `specs/general/security.adoc`），也决定 SQL 能不能被高亮与静态校验。**MyBatis 项目是已知例外**：SQL 写在 mapper 的 `*.xml` 映射文件里（该框架支持的承载形式、不再另建 `.sql`）；其 **`${}` 是字符串替换**、仅可用于不由用户输入决定的场景（如动态排序字段）并对取值做**白名单校验**，其余一律用 `#{}`（预编译参数）。**判定标准（任一命中即违规）**：① SQL 语句文本出现在宿主语言源文件里（字符串常量/拼接/模板/文本块）；② 该建的 `.sql`（或 mapper `*.xml`）没建、语句被塞进不承载 SQL 的文件里凑合——一次性的迁移与排障脚本同样单独成文件。
* **写库名（L1，用户点名；DDL 与 DML 一律强制）**：语句里的表名**须用限定名称**（`<库>.<表>`，如 `ALTER TABLE mydb.t_user ...`、`INSERT INTO mydb.t_user ...`）——**DDL 与 DML 都强制**，**不依赖连接的默认库**（`USE`、连接串里的库名、连接池默认 schema 都不算写了库名）。**为什么**：脚本会被复制到别的连接/别的环境执行（迁移、备份、排障手跑），裸表名落到默认库不同（或没有默认库）的连接上即**改错库**；库名把"改哪张表"写进语句自身。**判定标准（任一命中即违规）**：① DDL/DML 里的表名是裸表名（`t_user` 或 `` `t_user` ``）而无库名限定；② 以"连接串里已经是这个库"为由省略库名。**与参数化同向、不相互替代**：库名是**语句文本的一部分**，占位符只绑定取值、不绑定标识符。
* **同表同类操作合并为一条（DDL 强制、DML 优先；L2）**：**同类操作**＝**同一个动作、作用在同一张表**上的多个操作（`ALTER TABLE` 的**新增** `ADD COLUMN`/`ADD INDEX`、**移动** `MODIFY COLUMN`/`CHANGE`、**删除** `DROP COLUMN` 等；DML 的插入行、更新行同理）。**目标数据库支持在一条语句里并列**时（MySQL 的 `ALTER TABLE` 形如 `ALTER TABLE mydb.t ADD COLUMN a ..., ADD COLUMN b ...`；多值 `INSERT ... VALUES (...), (...)`）——**DDL 须合并进一条**、**不得每个字段写一条**；**DML 优先合并**。**确实合并不了才分开写**，并在该处**写明原因**（目标数据库不支持 / 必须串行 / 中间步骤有数据依赖）。**为什么（代价不对称）**：可合并的同类操作拆成 N 条时，**最终结构等价、代价却是一遍遍按表**——可用 INPLACE 的动作**默认仍作为一次独立操作执行**，表越大按得越久，迁移脚本还多出 N 倍冗余。
** **判定标准（任一命中即违规）**：① 同一张表同类别的 ≥2 个动作（≥2 个字段/索引的 `ADD`、`DROP` 或 `MODIFY`；同表同类 DML）**写成 ≥2 条语句**，而目标数据库支持在一条语句里并列；② 按字段/按行**批量生成**时，**生成脚本须按表合并输出**（按字段逐条生成即为违规）；③ **反向越界**——合并后跨越**不同表**或**不同动作类型**（不同表、或 `ADD` 与 `MODIFY` 混在一起）那不是"同类操作"、**属过度合并**。
** **例外面（只适用于 DML，用户原话「此条只使用于 dml，ddl 一定会锁表」）**：合并只约束**执行者本次新写的 DML**——**用户主动写的 DML 一律不动、不告警**（用户原话："不改用户的，也不告警，因为可能会造成锁表啥的"）。**为什么**：DML 的合并不是纯等价（一条多值 `INSERT`／集合式 `UPDATE` 与逐条执行在**锁的范围与持有时间**上不同），用户可能正是按业务事务粒度（逐条提交、边算边写、可重试的中间态）才那样写——改它属**越权**，且可能把用户的锁行为改坏。**DDL 不适用这个例外**：DDL 一定会锁表、合并只会**减少**锁的次数，故 DDL 侧是**强制**。**反向越界**：去改**用户主动写的** DML、或对这类存量发告警，同属违规。
* **存量边界**：本条与上一条按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**——**本次改动发现即改、不单独发动全库清理**；**历史迁移脚本（已合入/已执行）不改**（改写已执行的迁移会与已落库的结构对不上），**用户主动写的存量一律不动**。
* 依据（标准名/编号）：MySQL 官方文档（`ALTER TABLE` 语法支持一条语句并列多个 alter_option；Online DDL 一节写明可用 INPLACE 的每个动作**默认仍作为一次独立操作执行**；多值 `INSERT ... VALUES (...), (...)` 的语法形态）、ANSI SQL / ISO/IEC 9075（限定名称 `schema.table` 是 SQL 语法的一等形态，不写库名时靠当前 schema 补齐）、OWASP SQL Injection Prevention Cheat Sheet、OWASP Query Parameterization Cheat Sheet、ISO/IEC 25010（性能效率、可靠性）、ISO/IEC/IEEE 29148（要求须可验证）。**"库名（DDL/DML）强制"、"ALTER 须合并、不得每个字段一条"、"DML 优先合并且只约束执行者新写的"三条是本集合的判据化取舍（用户点名），非外部标准的规定**——官方材料给的是语法能力与代价说明。
