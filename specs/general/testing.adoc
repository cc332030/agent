= 测试规范（通用层，跨语言）

以下规范适用于**所有语言**的单元测试与性能测试。用例设计原则、测试文档、性能测试等对任何语言适用；各语言的框架、断言、目录结构、构建统计等专属细节见 `specs/stack/<语言>-testing.adoc` 对应文件（如 `java-testing.adoc`）。

== 单元测试

=== 用例设计

==== 设计方法

* 测试目标：优先覆盖"容易出错或出错后难发现"的方法，含正常路径、边界与异常路径；异常断言按对应语言的测试框架要求精确匹配异常类型（具体见 `specs/stack/<语言>-testing.adoc`）（用例设计方法依据：ISO/IEC/IEEE 29119-4 的黑盒/白盒测试技术与边界值、等价类划分；术语见 ISTQB Glossary）
* 用例设计流程：测试用例生成须依照白盒原则与黑盒原则分别生成，再以错误推测法、状态迁移测试、行为一致性检查补充，最终合并去重——
  ** 白盒原则（基于实现分析）：先理清被测方法"做什么用的、有哪些场景"，再分析方法的具体实现：分析代码可能存在的问题、支持的参数形态；对正确的参数和错误的参数分别添加测试用例，正例、反例、边界值都要覆盖；异常输入按实际使用场景决定（见下条）；复合条件分支按判定/条件覆盖分析，覆盖各条件组合，避免短路掩盖分支；循环与递归按路径覆盖分析——循环体覆盖 0 次、1 次、多次及边界次数，递归覆盖深度边界
  ** 黑盒原则（基于功能规格）：根据方法的功能添加正常和异常的用例；根据入参、出参分别分析入参与出参的取值范围，无论有效还是无效，都取代表性值添加测试用例（如典型值、边界值、越界值、非法值等）；检查入参、出参取值是否能覆盖所有情况，取值过多（无法穷举）时抽样，抽样须覆盖各取值区间与类别；多个入参条件组合决定行为时用决策表分析组合，条件多、组合爆炸时用配对抽样（如 pairwise）结合代表性值缩减组合量；检查方法有没有意料之外的输出
  ** 错误推测法（经验补充）：结合经验补充白盒、黑盒之外的易错场景——空/空集合、重复调用与幂等性、转义字符、Unicode 边界、时区/夏令时、数值溢出、浮点精度等
  ** 状态迁移测试：有状态对象/服务（如缓存、数据库等）按状态迁移设计用例，覆盖合法迁移路径与非法迁移（不允许的状态转换）路径
  ** 行为一致性：异常发生后对象内部状态/不变量不被破坏、资源正常释放；多线程并发调用（缓存、单例、lazy 初始化等共享场景）下结果一致
  ** 合并去重：白盒、黑盒及补充方法生成的用例最终合并去重，形成最终用例集；场景未测全不视为完成；场景拆解注意按输入形态变体穷举，避免只覆盖典型形态漏掉变体
  ** 记录：白盒原则、黑盒原则及补充方法的分析过程，与合并后的用例结果，须记录到测试文档（大范围或复杂测试）或测试代码注释，不留存于临时产物（见执行原则「临时产物」条目）

==== 覆盖要求

* 分支输出覆盖：被测方法存在分支（if/switch/多态分发等）时，设计用例须覆盖每种分支情况，且每种分支都须有测试用例验证其输出（结果/格式）满足要求——不得只覆盖部分分支、或仅验证分支被触达而不验证分支输出；分支多、组合爆炸时聚焦有语义意义的分支，配合全组合用例兜底整体格式
* 异常输入用例按实际情况取舍：若方法虽未注明非空、但实际使用中保证不会传空值（如内部自用、调用方契约已保证），可跳过该参数的异常输入用例，但必须在参数上标注非空约定写明，防止后续误判为可空、再次生成异常输入用例；真实场景可能传入空值或非法值时，异常输入用例必须覆盖，且异常输入用例的测试数据不限定范围与内容——应覆盖任意异常输入，不得只测少数几个看似合理的非法值
* 最真实场景优先：测试用例尽可能满足最真实的场景——测试数据、调用方式、输入/输出形态要贴近真实使用场景，不得用过于理想化或脱离实际的数据；能用完整真实流程就不绕过它简化；验证端到端行为时用真实入口；在贴近真实场景的基础上仍须保留边界与异常用例，不得因"贴近真实"而牺牲用例完整性
* 不得为测试新增专用方法/分支：测试应在被测功能真实的流程与节点上选取节点按正常流程进行，不得在真实流程之外再开发新方法、新分支节点仅为测试所用——存在仅被测试调用的方法/分支说明功能设计上有多余节点，应删除该节点并将测试改到真实流程上

=== 测试有效性

测试用例不是"写了就有效"——可能覆盖了代码但断言无效、可能通过所有测试但未真正捕获任何缺陷。本节规则用于确保测试用例**真正能测出问题**（测试充分性不能只看执行与否，还须看断言强度与缺陷检出能力：参考 Zhu、Hall、May 的 "Software unit test coverage and adequacy"（ACM Computing Surveys, 1997）与 ISTQB Glossary 中 "test oracle" / "test adequacy" 相关定义）。

==== 断言有效性（Test Oracle）

* **Test Oracle（测试断言）必须有效**：测试断言（oracle）是验证测试结果是否正确的判据，测试断言质量直接决定测试有效性（概念与依据见 ISTQB Glossary 的 "test oracle"，以及 ISO/IEC/IEEE 29119-4 测试技术标准）。要求——
  ** 测试必须断言被测方法的**实际输出/行为结果**（返回值、状态变更、异常类型与信息、副作用等），不得只调用方法而不断言（仅断言"不抛异常"对验证行为正确性无效，除非该方法无返回值且唯一目的就是不抛异常）
  ** 断言须验证**具体的值/结果**，而非泛化的非空或类型判断——用精确值断言（如 `assertEquals(3, calc())`）优先于弱断言（如 `assertNotNull(calc())`）；弱断言只用于确实无法精确预期的场景并说明原因
  ** 断言须能**捕获实现中的错误**——如果移除断言后测试仍通过，说明该断言无效（可尝试删除断言运行测试验证，能通过即断言无效）；存在"测试全部通过但代码有缺陷"的情况（如断言本身错误、断言过弱、测试数据错误），须对照正确规格核验断言

==== 变异测试（Mutation Testing）

* **变异测试（Mutation Testing）**：变异测试通过向源代码引入小的故意缺陷（变异体，如翻转比较运算符、删除一行、反转条件等），运行测试用例看是否能"杀死"（捕获）这些变异体，从而**直接度量测试用例的实际缺陷检出能力**——测试用例无法杀死的变异体说明测试对该代码区域覆盖不足或断言无效（参考：Google 在 CI 大规模部署变异测试验证测试有效性（`Practical Mutation Testing at Scale`，IEEE TSE 2022），`MuJava`、`PIT` 等为经典变异测试工具）。使用要求——
  ** 测试用例完成后，若项目支持变异测试工具（如 Java 的 PIT、PHP 的 Humbug、其他语言的对应工具），对**关键/高风险代码**运行变异测试，评估突变得分（被杀死的变异体数 / 总变异体数）
  ** 突变得分低（如 < 70% 或有重要变异体存活）的代码区域，须补充用例或修正断言；存活变异体须逐个分析——是测试漏测还是断言无效，修复后重新运行确认
  ** 存活变异体可能是"等价变异体"（变异后行为与原始代码等价），须记录原因；非等价变异体存活即测试无效，必须处理
  ** 变异测试仅在有工具可用时执行；无工具时用下述"反向验证"代替——对关键代码区域，人为在代码中引入一个已知缺陷（如翻转条件、修改返回值），运行测试确认测试**能够捕获**该缺陷，若捕获不到则说明该区域的测试无效，需补用例

==== 属性测试（Property-based Testing）

* **属性测试（Property-based Testing）**：属性测试通过**自动随机生成大量输入**并验证被测行为满足"属性"（不变量/规则），是手工用例的**补充手段**——边界值、输入组合等的系统化覆盖策略见上「用例设计」（黑盒/白盒原则），属性测试以自动化随机输入探测**手工分析难以预判的意外行为**（参考：QuickCheck、Hypothesis、jqwik 等工具）。使用要求——
  ** 存在明确的属性/不变量（如 `a + b` 与 `b + a` 结果相等、解析-序列化往返一致、排序结果总是有序等）时，优先用属性测试补充随机化用例，而非只靠手工枚举
  ** 属性测试失败时须能**最小化**失败输入（shrinking），以便定位问题
  ** 属性测试不能替代精确定义的单元用例，二者互补——属性测试负责**探测随机输入下的意外行为**，精确用例负责验证已知行为与系统化边界/组合覆盖

==== 测试代码自检

* 测试用例编写完成后，须自查——
  ** 每个测试方法是否有明确的**测试意图**（要验证什么行为/场景），测试名、注释与断言是否与意图一致
  ** 移除该测试用例后，是否会导致某个缺陷不被发现（无法回答说明该用例可能冗余或无效）
  ** 测试数据是否真实合理、断言是否足够严格、是否只测了"最安全"的路径

=== 用例编写

* 测试代码也需严格遵守全部项目规范：测试代码与主代码同等遵守本规范各文件（specs/core、specs/general、specs/stack），不得因是测试代码而放宽
* 异常场景用例不直接打印异常：预期抛异常的用例（断言捕获异常、用例通过）中，不得直接把异常/堆栈打印到控制台（如 `printStackTrace`、`console.error`、print 异常对象等）——预期异常被打印会让通过的用例看起来像失败、误导维护者与 CI 排查；断言应精确验证异常类型与信息，确需留存异常内容时用日志框架或写入测试报告，不依赖控制台输出
* 用例**必须**触发的警告须就地抑制：被测场景的代码/用例本身**就是按会触发警告的方式**编写时（警告是该场景的必然结果，且**改成其他不告警的方式，要么直接报错、要么达不到该用例的测试效果**——如用例必须调用已弃用 API 验证其兼容性、必须走会触发编译器/IDE 警告的边界路径等），不得为消除警告而改动用例；应保持代码/用例原样，在**触发点就近局部抑制**该警告（如 Java 用 `@SuppressWarnings`），并注释说明"该警告是本用例必须触发的预期行为、抑制后不得移除"——否则该警告会被扫出并被误判为遗留告警（警告处理口径见 link:../general/coding.adoc[]「警告与弃用」）；抑制范围**限于该用例/该行**，不得为图省事扩大抑制范围、掩盖真实警告，也不得借此抑制非预期的告警
* 测试文件命名用「被测文件名 + 测试后缀」式（**后缀式**，如 Python `foo.py → foo_test.py`、Java `Foo.java → FooTests.java`），**禁止 `test_` 前戳式**（如 `test_foo.py`）——后缀式使被测文件与其测试在目录排序中相邻（`foo.py` 紧邻 `foo_test.py`）、便于配对维护；前戳式会把测试文件与其他文件分离、难以一眼对应被测对象；Java 含 `Test`/`Tests` 后缀的类命名仍按 `specs/stack/<语言>-testing.adoc` 对应语言的定式
* 测试所处位置（目录/包路径）与测试类命名：测试的目录结构、包路径与命名须与**其语言/技术栈的既有定式一致**（由该技术栈的构建工具与框架约定决定、并与项目自身结构一致），不对所有语言统一规定——**Java/JUnit 的定式为测试类与源类同包路径、类名为「被测类名 + 测试类型后缀」**（默认 `Tests`；启动型 `BootTests`、性能 `PerfTests`、端到端 `IT` 及其取舍见 link:../stack/java-testing.adoc[]「测试类命名」）；其他语言按其 `specs/stack/<语言>-testing.adoc` 的定式执行，该文件未收录时遵循该语言生态的权威约定（构建工具/框架官方规范）
* 测试以正确规格为准，不迁就源代码：用例与源码冲突时，用例按正确规格书写，必要时修复源代码，不得用错误的用例迁就源码；测试不通过不代表该场景不用测，不通过更要测（先按正确用例暴露问题，再修复源码直至通过）
* Mock / Test Double 使用约束：测试中 Mock（模拟依赖）须克制使用——过度 Mock 会让测试与被测代码真实行为脱节，造成"测试全绿、线上有问题"。要求——
  ** 被测方法自身的核心逻辑**不得被 Mock**——Mock 仅用于隔离外部依赖（DB、缓存、网络、外部服务等），不得 Mock 被测方法自身的内部行为
  ** Mock 的返回值/行为须**贴近真实场景**，不得使用脱离实际的模拟数据；Mock 外部依赖时须验证**正确的调用参数与顺序**（verify 调用、参数匹配），防止"Mock 了但从未被调用"的虚假测试
  ** 尽可能使用**真实实现**而非 Mock（如内存数据库替代真实 DB、嵌入式服务替代外部依赖），Mock 作为不得已的手段
  ** Mock 不应掩盖被测代码的异常路径——测试异常场景时 Mock 的异常行为须能触发被测方法的真实异常处理
* 各语言专属的用例编写细节（语法糖展开、类型推断、资源释放等）见 `specs/stack/<语言>-testing.adoc`

=== 执行与验证

* 验证以对应构建工具的统计结果为准（surefire 等具体统计项见 specs/stack/maven.adoc 与 specs/stack/<语言>-testing.adoc）；"获取统计一步到位"等规则见 link:verify.adoc[]「编译/运行验证」
* 同一模块禁止并行构建；多 agent 协作时同一模块分阶段执行，避免构建冲突
* 测试失败判定：当测试用例失败且确认不是本次改动造成（多为人工改了代码但未同步调整测试用例时）时，以代码为准——测试用例过时，应更新测试用例使其与当前代码行为一致，不反过来改代码迁就测试
* 测试全绿不等同于无缺陷：测试全部通过仅说明测试所覆盖的场景未发现问题，不代表代码无缺陷——覆盖率与突变得分才是评估测试充分性的指标（见下「覆盖率与充分性」）

=== 覆盖率与充分性

* 覆盖率的定位：覆盖率（行/分支/条件覆盖率）是**必要但不充分**的测试充分性指标——高覆盖率不代表测试有效（断言弱的测试也能达到高覆盖率），低覆盖率则明确表示测试不充分（参考：`Software unit test coverage and adequacy`（Zhu, Hall & May, ACM Computing Surveys 1997）对覆盖率作为充分性标准的基础研究，以及 Google 实践中覆盖率高不等于质量好的发现）
* 覆盖率要求：
  ** 关键/核心代码（业务核心逻辑、安全敏感逻辑、数据转换逻辑等）的**分支覆盖率**须达标（如 ≥ 80%），行覆盖可作参考但不作为充分条件
  ** 覆盖率统计须排除自动生成的代码（lombok 生成、框架样板、getter/setter 等），只统计手写逻辑
  ** 覆盖率不达标须补充用例直至达标；覆盖率已达标但突变得分低（见「测试有效性」）的区域，仍须加强断言或补用例——两者互为补充，不可互相替代
* 回归测试：修改代码后须确保**既有用例全部通过**（不回归），新增功能须**同步新增用例**——线上缺陷转化为回归用例见下条（参考：Beizer 的"农药悖论"（Pesticide Paradox）——反复执行同样的测试不会发现新问题，须不断补充新用例覆盖新的行为变化）
* 线上问题与缺陷反哺：线上缺陷（生产事故、用户报障、review 发现的问题）须转化为**回归测试用例**——先复现缺陷场景，再补充能捕获该缺陷的测试用例，确认测试失败后修复代码使测试通过，防止问题复发

=== 环境与兼容

* 外部服务替代：依赖 redis、db 等外部服务的类、方法，若存在测试专用或嵌入式的同类实现（如嵌入式 Redis、H2/内存数据库），运行测试时优先用它替代验证，不得因本地无对应环境而跳过测试或删减用例
* 兼容性测试：覆盖易受环境影响输入的稳定性验证（如时间/日期格式、字符集、不同环境或依赖版本的差异等），验证行为在不同条件下表现一致；兼容性验证分两类——
  ** 功能完整性测试（必须）：重构/优化前后行为一致性验证（如内嵌旧语义参考实现逐字段对比），确保优化不改变既有行为；属功能完整性范畴，是每次重构/优化的必备项
  ** 源代码兼容性测试（尽力而为）：源码与编译产物的跨环境兼容，不因小优化牺牲兼容性。场景包括：运行时版本升级后可用性、跨操作系统差异、开发环境特殊依赖（如开发时使用的特殊环境变量在真实运行时可能不存在）；能测则测，无法执行的场景须记录用例设计、考量与限制，不得因环境受限而删减记录

=== 测试文档

* 测试代码比工作代码更重要——测试是行为规格的载体，须认真维护并同等对待；测试相关内容一律要有持久落点，**按内容范围分别写入测试文档或测试代码的文档注释**（落点判定见下条），**不强制要求存在独立测试文档文件**；与注释用途不同（注释面向 API 使用方说明语义，测试文档面向测试维护者）；大范围或复杂测试须在用例设计时同步落位其测试设计——跨类/模块级进测试文档、类/方法级进测试代码文档注释；测试文档同样适用文档质量要求（准确/完整/可执行/有价值/简洁/可验证，见 link:../general/doc.adoc[]「注释与文档」），**内容不减少**（见下条）
* 测试文档内容按"范围"分离、**内容一项不能丢**：测试相关内容一律要有持久落点，按内容范围决定写在哪——**跨类/模块/功能级**的测试总结与规划（测试架构与组织、测试手法与参考实现、为什么这样测、覆盖场景规划、已知限制与未覆盖场景、兼容性考量等）写入**独立测试文档**；**类/方法级**的内容（测试意图、用例编号、该用例的设计思路与依据、边界与断言取舍、测试数据选择理由等）**写入测试代码的文档注释中**（类上放用例目录、方法上放细节），**不要求每个测试类都另配一份文档**、更不要求"一文档 + 一测试文档"式的逐类配对；源文件、测试、性能测试等各类测试之间在代码文档注释中互相引用（javadoc / docstring 等，按语言实际机制；见 link:../general/doc-design.adoc[]「信息归属」「类间关系与双向引用」）
* 用例设计思路等须完整进代码、放对位置（**不得丢弃、不得降格**）：原测试文档中属**类/方法级**的内容（用例设计思路与依据、为什么这样测、覆盖的场景与取舍、边界与断言取舍、测试数据选择理由等）在文档向代码迁移时**也必须进代码**——按内容归属放到**适当位置**：类级（测试类 javadoc/docstring）放用例目录、覆盖场景清单、该测试的整体设计思路与**覆盖取舍**；方法级（各测试方法的文档注释）放该用例的测试意图、设计思路与依据、边界与断言取舍、**测试数据选择理由**。**这些内容不得因"进代码放不下"而省略或简化**（内容不减少，见 link:../general/doc.adoc[]「注释与文档」）；载体优先用文档注释，语言不支持时用多行块注释（见 link:../general/coding.adoc[]「注释」）
* 测试用例编号须可定位（测试方法的注释承载用例编号）：测试用例的**分类 + 编号**（如 1.2.5）**默认写在测试类的类级 javadoc 中**（用例目录/编号索引），**以测试代码内的文档注释为落点、不再为此另建独立文档**；仅当确有**跨类/功能级的测试策略**（多模块/多功能的整体测试组织、跨类测试手法）时才保留独立测试设计文档（与设计文档同放，落点与命名遵循 link:../general/doc-design.adoc[]，禁止放 `tmp/`）；分类编号有层级、按功能/行为维度组织，便于从代码了解测试范围、检查遗漏；**测试类在类上的注释声明是哪个功能哪个类的测试用例**；**测试方法的注释中标识对应分类编号**（如"对应测试用例 1.2.5"），使代码与用例清单互相定位——编号的汇总标识统一写在测试方法注释中，不写在方法体注释或别处；新增/调整用例时同步更新编号，保证文档与代码一致；**设计文档不需要写测试内容**（测试内容只在测试文档/测试类注释）

== 性能测试

* 独立性：性能测试独立于单元测试（不随常规测试执行），仅在明确命令执行性能测试时才执行（具体语言的承载与命名见 `specs/stack/<语言>-testing.adoc`，如 Java 用 `<被测类名>PerfTests`）
* 对比测试：性能测试须为对比测试，对比常用的同类实现方式与工具，实现方式类别至少 3 类（不足 3 类时按实际可用数量对比）
* 排除初始化干扰：性能测试需测试两次，第二次须在全部实现方式均初始化完成后再进行（首次结果含初始化/加载开销，不计入最终结论）
* 结果分析：测试完成后须分析性能差异由哪些原因引起（如实现原理、初始化/缓存开销、反射/序列化开销等），并给出对应的解决方案

== 验证与运行契约

本节是编译/运行验证、分步验证与**规范验证**的公共口径。编译耗时较长，**不滥运行**——仅当确需验证（用户明确要求，或存在仅能靠运行确认的行为）时才执行；多个待验证项能合并时合并为一次执行，不逐项独立验证；运行命令时优先把完整输出重定向到文件（如 `mvn ... > build.log 2>&1`、`npm run build > build.log 2>&1`），避免终端输出截断或命令中断后无法恢复而需重试；日志等临时产物按执行原则「临时产物」处理。

* **以真实结果为准（L1）**：不得仅凭命令 exit code 判断成败，须依据对应工具的实际统计结果（如测试的 run/failures/errors/skipped 统计、构建的成功日志）判断；统计须**一步直接到位**（在同一命令内从重定向的日志中过滤统计行），禁止"先运行、再提示后单独读取报告"的两段式流程。
* **分步验证（L1）**：设计、开发、写用例等多步骤任务，每个步骤执行完须对涉及的部分做一次隔离上下文的复核，确保每步正确——前面方向错了，后面做再多也是无用功。
* **外部资源必须实测可用（L1）**：引入外部资源（CDN/脚本/CSS/图片 URL、第三方依赖、远程文件等）时须**实际验证其可用**（发起真实请求确认返回预期状态码，如 200），不得只凭版本号/文档推测路径存在；注意 `latest`、`@latest` 等浮动版本可能解析到无对应产物的新版，须固定到经实际验证的具体版本。
* **外部资源禁止本地下载引用（L1）**：**未经用户声明**（明确允许/要求下载），严禁将外部资源、依赖（CDN 脚本/CSS、第三方库、JAR/二进制等）**下载到本地以本地文件方式引用**——含工作目录及任何本地位置；应使用**链接**（URL 直接引用）或其他引用方式（如构建工具的依赖声明）。确需下载到本地时须先获得用户声明同意。

=== 判准维度：严格执行 / 尽力而为

L1/L2/L3 只答"**要求有多强**"，还须答"**执行到什么程度算做到**"——同一级别的条款有"判据固定、可逐次核对"与"判据开放、做不到不算违规"两种形态，混在一起就会出现两头落空：把"尽力而为"的条款当硬指标承诺，或把"严格"的条款当尽力而为（跑不了就跳过、不说明）。

* **严格执行（须逐次达成并给出证据）**：判据固定、结果只有「做到/没做到」二值，没做到即**不得声明完成**——如 `git mv`、引用须指向真实文件、破坏性操作先确认、最高关注项的存在性。**判定**：能否给出"本次是否达成"的核对动作（命令/取值/清单）。
* **尽力而为（须尝试、须说明、不记通过）**：判据依赖环境或第三方，**做不到本身不构成违规，但"不尝试"与"做不到却记成做到"都违规**——如兼容性测试中环境受限的场景、`IT` 依赖的外部环境不可用、依赖上游修复的问题。**判定**：本次是否**实际尝试**了、是否如实写明"未执行/未达成 + 原因 + 替代做法"。
* **两者都必须留证（L1）**："未执行"与"执行通过"是两个不同结论，**不得混写**；对判准类型有疑问时按"严格执行"处理并补判据，不得借"尽力而为"降低既有约束的强度。
* **何时用（L1）**：本判准维度答"**执行到什么程度算做到**"，与 L1/L2/L3（"要求有多强"）**是两个轴**——凡新写一条含"必须/不得"的规则、或判断某条是否被遵守时，都要先判它属严格执行还是尽力而为。它与「验证的效力等级」的确定项/概念项**也是两个轴**（后者说"判据形态"，本条说"执行到什么程度算做到"）：**常见但非必然**的对应是确定项多按严格执行、概念项多按尽力而为，**不得据此压在一条轴上**——确定项也可以被项目规定为尽力而为，此时须写明其留证形态。
* **同一约束只能有一个判准（L1）**：同一件事不得在不同文件里出现两种判准（如一处按严格执行、另一处当作可跳过）。
* **常见误用（L1）**：把"环境不支持"直接当作结论而不尝试（应属尽力而为、须先试）；把"尽力而为"写成硬承诺（会在环境正常差异下频繁"看起来未完成"）；同一件事在不同文件里出现两种判准。

=== 验证的适用边界（先判改动性质，再决定验证到什么程度）

验证机制本身也是会被加载、被执行的规则——**用错对象就是把不可控的验证义务强加给不需要它的任务**。故先给判据：**按改动性质取值，先判性质、再选范围**。

[cols="1,2,2", options="header"]
|===
| 改动性质 | 验证到什么程度 | 判据与依据
| **A. 代码类改动**（改代码、修缺陷、调参数；不触碰会被未知项目加载的公共内容） | **机械判据判过不过**——编译/构建通过、测试按实际统计通过即可交付；**不做**三视角、**不做**全局核对、**不设**复盘节点 | 依据：本文件「以真实结果为准」（有确定性判据的事，用判据说话；ISO/IEC Directives Part 2 要求可验证——已有可验证判据时不叠加无判据的流程）
| **B. 规范类改动**（改动公共内容：规范条目、任务提示词、随规范分发的工具；或改动会被未知项目加载的任何产物） | **三视角深度验证**（①完整性 + ②有效性与认知质量 + ③接纳面，同一干净子 agent 一次读取、分栏列），**而且因为判据多是概念性、笼统、不可控的**，必须**从全局核对**：这条规则要解决的失效现在还在不在、依据是否仍支持该条 | 依据：概念性判据没有"跑一遍就知道"的确定性判据，只能靠语义复核 + 全局追溯（IEEE 1028 软件评审；ISO/IEC/IEEE 29148 可追溯；ISO 10007 变更控制）
|===

* **判据只有一个问句（L1）**：**"这次改动会不会被未知项目加载、会不会改变别人的行为？"**——会（或不确定）→ 按 B 走；明确不会（项目内部实现）→ 按 A 走。**不得因为"改动小"就降级**：改一条规范里的一个词也可能改变别人行为，性质判据不看改动量。
* **不得互串（L1）**：A 类任务不得自行升级为三视角 + 全局复核（属过度验证：把可控的验证做成不可控的多步流程）；B 类任务不得只跑机械校验就收尾（属跳过验证：机械校验覆盖不到判据是否被压成口号、机制是否真在运行环境发生）。**同一任务含两类改动时取**更严的一侧**（B）**，但**只需对公共内容那一部分**做三视角与全局核对，代码部分仍按 A 的机械判据核对——**取更严的一侧**，但别把代码部分也拖进概念性流程。
* **不得另立一套验证体系（L1）**：验证范围是**下限与口径**，不是"项目必须另建的验证阶段/产物"——项目已有的 CI、构建、测试、评审直接沿用，本节只规定"到什么程度算过"（口径与留证要求不得省）。

=== 验证的效力等级（按对象定手段与结论强度）

验证会被用来推翻或认可别人的结论，**验证自己说错话的代价最大**。故给判据：**对象有确定性判据 → 机械校验，结论可判对错；对象只有概念性判据 → 只能启发式复核，结论只到"未发现问题"**。

[cols="1,2,2,2", options="header"]
|===
| 验证对象 | 判据形态 | 可用手段与结论 | 失效模式与去向
| **确定项**（有确定性判据：存在性、双向登记、引用可解析、格式与取值、构建与测试的实际统计） | 二值、可机械核对 | **判据本体验证**：机械校验按**判据本身**核对（如"引用指向真实文件"用**文件存在性**核对），**不按引用形式近似**；结论为**通过 / 不通过** | 近似式校验（按引用形式而不是判据本身核对）会**漏报**（判据坏了仍绿）；漏掉的判定点须逐个列出
| **概念项**（无确定性判据：判据是否笼统、内容是否完整、机制在真实环境会不会发生、被未知项目加载后是否可控） | 开放、须语义判断 | **只能启发式复核**（三视角复核、换机器、换角度、换样本） | **换一个角度就可能查出问题，也可能永远查不出**——故其结论只到**"未发现问题"，不能推出"没有问题"**；**也不得当作可二值化的通过条件去阻断交付**（**不得当作阻断交付的条件**）；"已换过若干角度、仍是未发现"即可**如实交付并悬置**
|===

* **结论强度（L1）**：汇报与留证须按对象区分写法，**"未发现问题"与"验证通过"不得混写**——确定项写**通过/不通过**（可举判据）；概念项写**"已复核、未发现问题"**并列出**已复核角度与样本**。**把"复核过、没看出问题"写成"这条规范没问题"，属以启发式结论冒充已验证**。
* **交付是否可阻断（L1）**：**只有确定项的判据不满足才阻断交付**（机械校验报错、构建/测试未通过、引用悬空等）；概念项**不设阻断条件**——它筛得出问题就修，筛不出就如实交付，**不得把"找不到问题"变成交付的隐性前置条件**。
* **悬置（L1）**：概念项未发现问题**不等于已确证**——凡**还没有确定性证据**支撑的部分，一律标记为**悬置**并写明理由与剩余风险。悬置**可与改动一并交付**（不阻断），但须**逐项可枚举**、可被后续证据收口；**不得把悬置项在汇总里写成通过项**。
* **手段的效力不对称（L1，须如实声明）**：机械校验**只能核对确定性判据**——它覆盖不到判据是否被压成口号、机制在真实环境发不发生、内容是否完整；概念项复核**发现的是"问题案例"、不是"没有问题"**（查到一处即确证有问题，查不到不构成证明）。**降低漏报的办法是增加独立的核对角度与样本（换视角、换机器、换反例），而不是把复核结论当成确定性判据**。
* **留证形态：三态台账（L1）**：留证**不得写成散文结论**，须逐项成行、每条带**三态标签之一**——**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附未确证的原因与剩余风险），**三态各占一栏、不得合并**。**"查不出问题"与"没有做复核"须能分辨**。

=== 验证总纲（回答"验证什么、怎么算过"）

规范类改动（B 类）的验收只有一句"跑一遍检查"是不够的：**验证什么、每项怎么算过、标准出自哪里**若不写死，验证就会退化成"把现有脚本跑绿"，规则会在一次次维护中**慢慢脱离初衷**。故把验收拆成**三个视角**，每个视角给出**判定标准**与**标准出处**（出处只写标准名/编号、不附链接）：

[cols="1,2,1,1", options="header"]
|===
| 视角 | 判定问题 | 不合格的典型症状 | 标准出处
| **① 完整性** | **对照面：改动前后**——被改对象在改动前后是否**等价** | 误删条目、把"必须+判据"降级成"要注意"、内容被搬到加载不到的位置 | ISO 10007（配置管理与变更控制）、ISO/IEC/IEEE 29148（可追溯）
| **② 有效性与认知质量** | **对照面：规范本体**——规则是否**说得对、说得清、跑得动、判得了、效力标得准** | 判据不可判定（无判定标准）、机制在真实环境不会发生、依据被删到无从追溯、写错受众（执行侧夹带解释 / 决策侧缺依据）、"验证通过"其实只是"跑完脚本"、**把启发式复核冒充确定性验证** | ISO/IEC Directives Part 2（要求须可验证）、ISO/IEC/IEEE 29148（单一/无歧义/可验证）、ISO/IEC/IEEE 25010（质量特性含性能效率）、RFC 2119 / RFC 8174（用语强度）
| **③ 接纳面（未知项目加载可控）** | **对照面：引用方项目**——被未知项目加载后会造成什么**可预见**的影响（概念项：逐项只看"是否发现"，查不出不等于没有） | 与引用方自身规范冲突时无优先级规则、默认替引用方改文件/格式化/提交、新增依赖或强制工具链、夹带项目私有约定、加载体积不可控 | ISO/IEC Directives Part 2（规范性文件引用现行文件、不作隐含要求）、ISO/IEC/IEEE 29148（干系人需求）、ISO 9241-110（交互原则：可控、可预期、不阻断）
|===

* **验证按对象与改动性质取值（L1）**：三个视角是**口径**，实际验证动作按上表取值——①、②适用于**每次规范改动**；③适用于**任何会被未知项目加载的公共内容**，且其**影响面/成本/可控性**三维见下「运行契约」。
* **验证对象不止规范文件、也须能枚举“如何验证”（L1）**：被加载后**会被执行**的产物同样是验证对象——**任务提示词**（会被项目复制成指令执行）与**随规范分发的工具脚本**都须按①完整性 + ②有效性与认知质量 + ③接纳面三项一并核对；**不得只验证规范文本、把会被执行的产物漏掉**。
* **"验证了什么"必须能枚举（L1）**：每次改动的汇报须**逐项**给出三个视角的结论（①逐条对照表、②按判据分类的问题清单、③按影响面/成本/可控性分类的清单），并**逐项标注效力等级与依据**（确定项＝判据名与取值；概念项＝已复核的角度与样本）——**没有按对象标注效力等级、或把启发式复核冒充确定性验证，不算验证**；**"未核对""未确证""核对通过"三态不得混写**。**只跑机械校验、说不出验了什么**不算验证。
* **防"慢慢脱离初衷"（L1）**：验证须回答"这条规则**当初要解决的失效**现在还在不在"（**这是概念项**：能查出一处"初衷已不成立"即确证有问题；查不出只说明**未发现问题**，不足以宣布"仍有效"）。**凡只保住文本、保不住初衷的改动，视为验证未通过**。
* **本节自身的效力等级（L1）**：本节与「验证的效力等级」「验证的适用边界」的判据都是"机制在真实环境会不会发生、被加载后是否可控"这类开放判断，故其结论**只能标"未发现问题"、不得宣称"已验证有效"**；本节自身也须被复盘（判据还在 ≠ 判据还成立）。

=== 规范验证（改完规范后的三视角复核）

规范的**语义有效性不能由确定性校验覆盖**——判据是否被压成口号、机制在真实环境是否会发生、被未知项目加载后是否可控，**属语义判断**，故须另起**干净子 agent**（隔离上下文，不带改动方立场；**优先用与执行者同源的子 Agent**，见 link:collab.adoc[]「agent 协作规范」）复核（依据：IEEE 1028 软件评审；ISO 10007 配置管理的变更控制）。

* **三视角各一问（L1）**：**①完整性**问「**对象**在改动前后是否**等价**——谁少了一条要求？误删、降级、放错层都属不等价」；**②有效性与认知质量**问「它**可被合规地执行**吗——判据可判定吗？依据还在吗、是否**说对了**？机制在**当前执行环境**真会发生吗？放对层、加载代价在预算内吗？从属者加载得到吗？**代价说得清吗**？」；**③接纳面**按下「运行契约」的影响面/成本/可控性三维逐维过。**同一个干净子 agent 一次做完（L1）**——同一份 diff、同一批受影响文件，重复起子 agent 是重复读取与重复计费；**一次读取、结论分栏列**，不得因合并而混答（三者对照面不同：改动前后 / 规范本体 / 引用方项目）。**每次验证都换一个干净上下文（L1）**：复核者须与发起改动者隔离，且**不得复用上一次验证用过的上下文**（带着上一轮结论再看一遍，会只找"是否已改"而放过新问题，等于自己复核自己）。只有①无任何语义可判（纯错字/格式/引用目标存在性）时才可只跑机械校验、不起子 agent。
* **②的判据（L1）**：①**判据可执行**（每条 L1 有判定标准）；②**依据**（标准名/编号）仍在、且**说对了**——不得只验证"依据行还在"，还须核对引用的标准**确实支持该条**；③**机制真会发生**（依赖环境能力的机制须有缺失时的降级路径）；④**读的形态**（执行侧只给"怎么走"——规则 + 判定标准 + 依据名；原因与取舍归思考/决策侧）；⑤**放对层与体积**（加载面只放底线）与**从属者可达**（被派发任务的加载由入口驱动）；⑥**性能**（代价说得清——加载后的时延/token 开销、机制本身的成本须有可核对说法，不得以"反正不贵"含糊带过；ISO/IEC/IEEE 25010 性能效率）。**典型可查项**：判据被压成"要注意"（不可判定）、"必须做到"却没有抓手也无降级路径、引用了一个并不支持该条的标准、把解释塞回执行侧条目、方法论/依据论证涨回常驻层、新条目未登记调度器或未定级。
* **③接纳面的判据（L1）**：逐项核对"未知项目加载后会怎样"——①**冲突与优先级**：与引用方自身规范冲突时优先级是否写明（以引用方项目自身规范为准）、新条目是否可能**静默推翻**引用方既有约定；②**对引用方工作区的默认动作**：是否默认改动/格式化引用方文件、是否默认代为提交或清理临时产物；③**新增依赖与工具要求**：是否引入新依赖、新工具链或版本要求（若引入须有降级路径），且**不得**出现引用方看不到的私有脚本名/仓库结构；④**私有约定与假定**：是否夹带只在某些项目成立的假定（特定目录、特定语言、特定平台）；⑤**成本与体积**：加载后的体积与加载路径是否可控。**典型可查项**：新增 L1 却未给冲突次序、默认替引用方改工作区、条目隐含"必须有某工具"却没有不可用时的做法、把本项目的取舍当通用要求。
* **三视角都须留证（L1）**：①留"逐条对照表"（原文 vs 改动后，缺项/降级项/移层项写明去向）；②留"问题清单"（每条带 判据/依据/机制/形态/层级体积/性能 中的哪一项 + 判定依据）；③留"接纳面清单"（每条带 冲突/默认动作/依赖/假定/成本 中的哪一维 + 影响与处置）。**"未复核"与"复核通过"不得混写**；三视角都过才可提交，不通过须先修再复核。
* **派发须自带硬超时（L1）**：语义复核派给子 agent 或外部复核者时**必须设可判定的时限**，到点即视为失联并"**放弃 + 如实标悬置**"，**不得无限等待**；**复核职责不绑定特定执行者**——外部复核者不可用时，由发起方按同一判据组织等价复核，并如实标注独立性边界（与改动方同模型的复核，独立性弱于第三方）。派发时优先选**一次性、边界明确、可超时**的形式。
* **执行者选择：强制同 Agent（L1）**：三视角复核**一律由与执行者相同的 Agent（同 Agent 身份、同入口、同调度器）承担**；**不得点名外部 Agent / 外部 NPC**、也不得以"换个 Agent 更独立"为由换来源（**判定标准**：派发目标是外部服务或外部 Agent 的标识、交换面超出本执行者可直接调用的派发、结论回传面本执行者读不到——任一命中即违规）。**同 Agent 的子执行者不可用时按 link:collab.adoc[]「协作方式」的降级路径执行**——由发起方在同一会话内按同一判据串行核对并标注独立性边界，或如实标悬置；**不得跳过复核，也不得用外部 Agent 顶替**（理由与判据见 link:collab.adoc[]）。
* **标准从哪来（L1）**：凡是**已有业界标准/权威约定的判定项，先引标准、不另造一套说法**——本文件用到的对应关系是：判据可验证性 → ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148；用语强度 → RFC 2119 / RFC 8174；变更控制与可追溯 → ISO 10007 与 ISO 9001；软件评审 → IEEE 1028；性能效率 → ISO/IEC/IEEE 25010；可用性与可控性 → ISO 9241-110。**只列与本条判据确有对应关系的标准，不得为"看起来有依据"堆砌**；**没有可援引标准时，才自定判据并写明理由**。

=== 运行契约（公共内容被未知项目加载时的可控性）

公共内容（本入口 + `specs/` + `prompts/` + 会被引用方加载的工具）**不随某个项目的上下文生效，而是被未知项目加载**——看不到它的项目结构、已经存在的项目规范、依赖与工具链。故"加一条规则"不止要问"这条对不对"，还要问"**它落到一个未知项目里会发生什么**"。

判定按**三维**逐维过（依据：ISO/IEC Directives Part 2 要求规范性文件引用现行文件、不作隐含要求；ISO/IEC/IEEE 29148 的需求须可追溯到干系人；ISO 9241-110 的交互原则——可控、可预期、不阻断）：

* **① 影响面（L1）**：这条规则会改变引用方的哪些既有行为？**与引用方自身规范的冲突次序**是否写明（以引用方项目自身规范为准）；**不得出现"静默推翻引用方既有约定"的条目**——凡收紧/推翻既有做法者须显式授权（用户声明或引用方自身规范声明），并给出"不采用时怎么办"。
* **② 成本（L1）**：加载与遵守的代价是否说得清——**加载面体积**（每次会话都加载的部分应设可机械核对的上限，只写"要注意体积"不构成上限）、加载后的时延/token 开销、引入的依赖或工具链要求（含版本要求，且须给出不可用时的降级路径）；**不得以"不贵"含糊带过**（ISO/IEC/IEEE 25010 性能效率）。
* **③ 可控性（L1）**：引用方是否**能预期、能关闭、能自行执行**——①**不得依环境自动动作**：不默认改动/格式化引用方文件、不默认代为提交、不默认清理其临时产物（须由其显式触发或用户声明）；②**不得让引用方依赖本仓库私有物**：条目不得引用引用方看不到的私有脚本名、仓库结构或私有约定；③**不得阻断**：规则不得让引用方在正常路径上无法完成工作（无降级路径的硬性前置一律不合规）。
* **接纳面须留证（L1）**：新增/调整公共内容时，须在改动说明（提交说明或汇报）中逐维写明"影响面 / 成本 / 可控性"的核对结论；**未核对不得计入验证通过**。
