= git 规范（通用层）

适用于 git 操作。任务临时产物管理见 `specs/core/execution.adoc`「临时产物」。

== 文件移动与重命名

本节是 `git mv` 铁律的**权威完整定义**（最高关注项 P1，L1 强制，不可降级）；其他位置（`specs/core/execution.adoc`「文件操作强制检查」、`AGENTS_COMMON.adoc`「最高优先级铁律」）均为**引用/重申**，不得被判为重复而合并删除。

* **文件移动/重命名必须使用 `git mv`（L1）**：git 按内容相似度识别 rename、保留跟踪历史（依据：git 官方文档 `git-mv` 与 `git-diff` 的 `-M/--find-renames`）；禁止用「新增新文件 + 删除旧文件」代替——delete+create 会使 git 历史断裂。**判断标准**：只要操作会让某个既有文件的 git 历史无法追溯，就属"文件移动"，**必须保留跟踪历史**，不得因主观认为"这是在重构而非移动文件"而规避。移动/重命名前须先确认源文件已纳入版本控制跟踪。
* **强制核对（兜底）**：凡本次改动涉及文件的新增/删除/移动，操作完成后必须核对——应保留历史的文件**须仍被识别为移动**（**取值**：差异检出里**不出现同一批改动的"删除 + 新增一对"**）；未识别即误用了 delete+create，须同步修复工作区：恢复旧文件后以保留历史的方式重新移动，再应用内容修改。怎么核属执行动作，不写进规范。
* **一份变多份的历史归属（一拆多 / 移动 + 复制）**：移动是文件级一对一动作——**同一源文件只能让其中一份继承移动历史**，其余作为新文件创建；不得对同一源文件重复移动。**继承哪一份、按三级判据取**：① **内容相似度高的那一份继承**（相似度高者与旧文件的"同一条记录"最贴切，历史接得上）；② **相似度相同时，集中到一个模块**——同一次改动里同一批"移动 + 复制"丢历史的文件，历史归属须**整体落在同一个模块内**，不得跨模块各分几个（**取值**：本批继承历史的文件全部落在同一个模块）；③ **模块的选择取能继承数量最多者**——即该模块内**确实满足相似度门槛、会被识别为移动**的文件数最多（不是文件总数最多的模块）；数量仍相同时任选一个模块，**一经选定即固定**，不得本批摇摆。**判定标准（逐条可核对，任一命中即不合规）**：① 同一批移动/重命名 + 复制的文件里，继承历史的文件**落在两个及以上模块**；② 某模块内只有一部分文件继承历史、同批另一份落在别处（"每一边丢几个"的形态）；③ 为凑"整体落在一个模块"而把不相干的模块或文件算进本批；④ 同一源文件被移动多次（多份同时继承）。**例外（L2）**：用户明确声明某一份（或某个模块）继承历史时按其声明——声明仅对该次任务、该处生效，不得泛化。拆分出的文件不得添加指向旧文件的历史来源注记。
* **避免移动失效的识别**：移动是否被识别受**内容相似度**影响；大幅改动内容后再移动可能识别失败，故**先移动并保留历史、再应用内容修改**。
* **移动未被识别的两类非操作类根因（L1，须先查根因再动手）**：差异检出显示为**删除 + 新增一对**（未识别为移动）时，除"误用 delete+create"外还可能是**结构性的**，此时调整命令无法解决：
** **合并/基点错位**：分支上的移动是相对**它自己的基点**做的，而 PR/比对以**目标分支为基点**算——若目标分支在此期间也动过同一批文件，两边路径对不上，版本管理工具就无法把新旧路径配成一对。**处置**：以目标分支为**线性基底**重放移动，而非反复重跑同一个移动动作。
** **一拆二/内容再分配**：把一个文件拆成两个、或把内容大部分并入**已存在**的另一文件时，移动记录是**文件级一对一**、记录不下"拆分/再分配"这个动作。**处置**：如实说明"属内容再分配、非 1:1 移动"，**以"内容一条未丢"（逐条对照）作为完整性判据**，不以移动形态作为交付前置条件；不得为"凑出移动形态"而堆留无用内容。
* **提交历史须按目标分支基线组织（L2）**：PR 的 diff 以目标分支为基线，故整理提交历史时以**目标分支当前 sha 为线性基底**重放改动（避免夹在中间的合并提交使 rename 识别与 diff 比对失真）。
* **可执行抓手（引用方项目自检）**：核对到的是**取值状态**——本次改动里**不出现"同一批改动里删除 + 新增一对、且两者内容高度相似"**（命中即为误用 delete+create，应以保留历史的方式重做该处改动），且应保留历史的文件**被识别为移动**。怎么核属执行动作，不写进规范。

== 重命名与内容修改须分两个提交（默认固定动作）

本节是"重命名 + 内容修改必须拆成两个提交"的**权威完整定义**（最高关注项 P7，L1 强制，不可降级）；其他位置均为**引用/重申**，不得被判为重复而合并删除。

**一句话规则**：一次改动里同时存在**文件重命名**与**内容修改**时，**一律拆成两个提交**——第一个提交**只做重命名、内容逐字节不变**（**本次涉及重命名的文件全在这一个提交里**），第二个提交**只改内容、不再动路径**。

* **适用对象与判定标准（L1）**：适用对象是"一次改动中既重命名该文件、又修改其内容"的**每一个**文件（含"顺手重命名"），**不按文件个数分摊**：合格提交序列是**一次改名（内容不变）+ 一次（或多次）内容修改**，**不是**"一个文件一个改名提交"。**判定标准（逐条可核对）**：① 该文件在**同一个提交**里同时出现**改名与内容行改动**；② 首个提交里该文件内容**不是逐字节不变**；③ "只重命名"的提交缺失——任一命中即不合规。依据：ISO 10007（一次变更只承载一个可追溯的目的）；把一批改名收进同一个提交，是让"这次移动"成为**一条可独立回溯的记录**。**与 `git mv` 铁律的关系**：`git mv` 保证"版本管理工具认得这是一次移动"，本条保证"这次移动是一条可独立回溯的记录"——同一目的的两道防线，顺序不可颠倒（先重命名、后改内容）。
* **分量大小不是理由（L1）**：不得以"改动很小/影响面可控"为由合并提交——"小"没有任何可判定的阈值，一旦允许，判定标准立刻退化成执行者的**主观判断**。"用户要求压缩提交"不是本条的理由条目。
* **提交顺序（L1）**：**先重命名、后改内容**，不得颠倒。依据：rename 识别按内容相似度（默认阈值 50%）；先把内容大改、再改名，或把两者放进同一个提交，可能同时丢掉 rename 识别。
* **无损拆分（L1，判定标准）**：按新路径移动并把改动提交为**只重命名**那一个后，必须提交仍能取到**内容逐字节不变**的版本；随后在**同一新路径**上应用内容修改、提交为第二个提交。**判定标准**：首个提交里该文件**只有改名、内容 0 增 0 删**（怎么取属执行动作，不写进规范）。**一批文件同时改名时逐文件核对**：每个改名文件都须满足上述判据，不得只核其中一个——只要有一个文件把内容改动留在了改名提交里，那份**中间版本从未存在过**（首个提交的内容会变成"新路径 + 已改内容"），历史取回的是一份**不存在的版本**。依据：ISO 10007（基线须是真实存在且可追溯的状态）。
* **两个提交都要进本次交付（L1）**：两个提交须**一并推送**、**落在同一个 PR**；**同一 PR 内改动分批交付时，这条序列不重排**（**分批交付**不得压、拆或重排已交付的两个提交）——后一次改动不得把前一次已交付的改名提交与内容提交压、拆或重排。**本条不构成合并的例外**：压缩提交按 `specs/platform/cnb.adoc`「压缩提交」执行（本次任务尚未合入的提交**默认压成一个**、内容不变），而本条的"两个提交"**不是临时中间提交**——它是本条要求交付的可追溯记录，**不得以"压缩提交"为由把两者压回一个**。
* **「压缩提交」的请求不覆盖本条（L1）**：用户提出**压缩提交/压成一个提交**时，其中**属于改名的部分仍按本条拆两个提交**——用户**未点名本条**时，压缩要求作用于本次任务尚未合入目标分支的**其余提交**（**默认压成一个提交**，见 `specs/general/version-control.adoc`「压缩提交」），本条的两个提交**原样保留**、是压缩后允许留下的唯一一组多提交。**判定标准（逐条可核对，任一命中即不合规）**：① 以"用户要求合并成一个提交"为由把改名与内容修改放进同一个提交，而本次会话里用户从未点名本条——共用一个词不等于声明；② 先按本条拆了两个提交、又以压缩为由把它们合回一个，且无明确声明；③ 把这两个提交当"临时中间提交"处理。**为什么算两件事**：用户要压缩的是"**没内容的中间历史**"（多次试跑的修正、迭代补丁），本条那两个提交是**已交付内容里**的一个只改变路径、不改变内容的提交，并进内容提交之后再也无法分别取回。
* **例外（只有一条，L1）**：用户**明确声明**"这次重命名与改内容合成一个提交"时按其声明执行——声明须**点名重命名与内容修改这两件事**、须**预先声明**（在整理这两个提交之前说）、须在**交付说明**里写明。"合并成一个提交""压缩提交""压成一个"这类**没点名本条**的说法**不算**声明（它只解除"临时中间提交"要压成一个的那一侧）。
* **可执行抓手（引用方项目自检）**：提交前核对到的**取值状态**是——① 该路径的历史里能看到"**先改名（内容 0 增删）、后改内容**"两条记录；② 首个提交里该文件增删数为 0/0；③ **断链核对**：存在那一条**批量改名**记录，且紧接其后的提交里不得再出现同类文件的移动；④ **压缩后核对**：以压缩为由整理过历史后仍须能取回这两条记录。怎么取属执行动作，不写进规范。

== 分阶段交付（大任务）

本节是"大任务的阶段成果何时必须落到已提交的载体"的权威定义（L1）；其他位置只作引用。**与交付链的其余两半的分工**：本节的**交付时机**只管"任务中途"（阶段成果），任务**收尾**的交付按 `prompts/_common.txt` 的 `delivery` 片段（那是提示词侧、会被未知项目复制执行）；**提交序列**（改名与改内容不得压进同一个提交）按本文件「重命名与内容修改须分两个提交」——三者同属一条交付链，互不替代。

* **大任务先分阶段、再执行（L1）**：任务量预估下来**不是一次就能做完**时（跨多轮操作、跨多个模块、需先设计再实现再验证一类），**动手前先把它拆成阶段**，并把阶段划分落到规划里（`specs/core/execution.adoc`「先规划后执行」的规划落盘）；**"先规范再执行"**——每个阶段**先定下本阶段的判断依据（规则、口径、判据与验收方式），再进入该阶段的执行**，不得边做边定规矩、也不得**整个任务一口气做完再一次性交付**。**判定标准**：说不出"分了哪几个阶段、各自的判断依据是什么"即不合规。
* **每个阶段完成即交付（L1）**：**判据（取值）＝该阶段产出的全部成果都在已提交并已推送的载体里**，工作区与暂存区**不留本阶段尚未交付的成果**；**阶段成果不得只存在于临时产物、会话上下文或本地未提交的工作区**。**为什么以"已提交的工作"为载体**：它是本集合里唯一**同时**满足"可恢复（中断后可从中继续）"与"可评审（合入须经独立评审）"的载体，且不新增任何产物形态——不新增暂存文件、不新增临时目录约定、不新增脚本。
* **判据按执行环境取值（L1）**：**自动化场景**（CI/CD、平台唤起的一次性工作空间）——**提交并推送**（只改不提交的成果随临时环境销毁而丢失）；**本地人工场景**——落在本地工作空间由人工处理（不提交、不推送），此时**不得把成果留在会被清理的载体里**（临时产物、会话上下文）。**两端同源**：本条与 `prompts/_common.txt` 的 `delivery` 片段同口径，差别只在**时机**（中途 / 收尾）。
* **"任务还没做完"不是不交付的理由（L1）**：阶段本身就是交付单位——**不得攒到收尾一次性交付**；阶段成果的交付**不等于**任务已收尾，收尾仍按各任务类型的交付口径执行（缺一即不合规）。
* **临时产物一律不提交（L1，与 `specs/core/execution.adoc`「临时产物」同口径）**：阶段交付的对象是**该阶段实际改动的对象**；规划、进度记录、扫描中间结果、结果报告等临时产物**不进入阶段提交**（交付前须核对暂存内容）。
* **中断与恢复（L1）**：任务**被中断**、且用户后续未明确提及继续时，按 `specs/core/execution.adoc`「任务放弃与中断」**视为放弃**——不自行延续、不擅自还原；**恢复时从最后一个已交付的阶段继续**，已交付的阶段**不重做**，且**先按已交付的载体取回现状**（`specs/general/context.adoc`「任务切换即清洁上下文」：不得拿上下文里的记忆当现状）。
* **边界：只到"提交 + 推送 + 建 PR"（L1）**：分阶段交付**不含合并**（合并一律不做，判据见 `specs/platform/cnb.adoc`「合并请求的合并主体（NPC 禁合并）」）；**同一 PR 内分批交付时，已交付的「重命名 / 内容修改」两个提交不得被压、拆或重排**（判据见本文件「重命名与内容修改须分两个提交」）。
* **依据（标准名/编号）**：DORA（交付性能研究：小批量、短生命周期分支、频繁小步合入主干）；ISO 10007（变更须基于受控、可追溯的状态——未提交的成果不构成受控状态）。**本集合如实标注**："阶段与提交一一对应""阶段成果不得只留在临时载体"是**本集合自己的判据化取舍**，外部材料只给方向与下限（小步、可控、可追溯），**未**规定"执行者必须为每个阶段建立提交"。

== 行尾与检出归一

行尾**取值**的权威判据（LF 基准、`.bat`/`.cmd` 必须 CRLF）见 `specs/general/encoding.adoc`「换行符」；本节只定 git 侧的落盘与提交口径。

* **`.gitattributes` 固定行尾策略，不靠人工手动调整（L1）**：仓库根**须有** `.gitattributes`，并按文件类型显式声明 `text eol=lf`（默认文本）与 `text eol=crlf`（`.bat`/`.cmd`/`.ps1`），二进制声明 `binary`。
* **`core.autocrlf` 交给仓库配置（L2）**：仓库已用 `.gitattributes` 显式声明时，本机 `core.autocrlf` 应设为 `false`，避免本机设置与仓库规则二次改写。
* **不提交行尾噪声（L1）**：提交前核对暂存内容，若某文件的差异**只因行尾（LF↔CRLF）变化**而变化，须先还原该文件的纯行尾改动、再只提交真实内容改动。
* **行尾取值可核对（L2）**：核对的是**取值状态**——受检文件的**工作区行尾与索引/属性声明一致、且无混用**；"某命令能查出什么"属执行动作，不写进规范。

== 暂存与提交检查

* **新生成且需保留的文件默认加入暂存区**；提交前须检查暂存内容，确认无临时文件（`tmp/` 临时产物、扫描中间产物、构建产物）被误提交。
* **若发现临时文件已被提交（异常场景）**：直接执行 `git rm` 删除，该场景下不得执行 `git commit`、交由用户确认后再提交，不得因此中断任务。

== 提交信息

本节只定**提交信息怎么写**；变更日志的条目怎么写是另一件事（见 `specs/general/changelog.adoc`）。两者是同一条链的两端：**提交信息是上游**（一次提交改了什么），**变更日志是下游**（一版发出去后使用者要跟进什么）——上游没有类型时，下游"组内按类型分组"只能靠人工归类。

* **首行写类型前缀（L2）**：提交信息首行按 `<type>[(scope)]: <subject>` 书写——`type` 取**固定闭集**（与 `specs/general/changelog.adoc`「组织形态」中组内类型分组的类型同源：`feat`/`fix`/`perf`/`refactor`/`docs`/`style`/`test`/`build`/`ci`/`chore`，同一项目内用词一致、不混用同义词），`scope` 可省、写**受影响的对象**（模块/组件/文档落点），`subject` 用一句话说明改了什么、不加句末标点。**判定标准**：首行不以 `<type>:` 或 `<type>(scope):` 起头即不合规。
* **破坏性变更须显式标注（L2）**：会改变既有行为、契约、数据格式或使用方式时，在 `type`/`scope` 后加 `!`（`feat(api)!: …`）**并**在页脚写 `BREAKING CHANGE: <说明与迁移方式>`——**不得把某个类型默认为破坏性的**（破坏性变更可与任何类型组合），也不得只在正文里含糊提一句。**判定标准**：存在破坏性变更而首行无 `!`、页脚无 `BREAKING CHANGE:`，即不合规。
* **变更编号只出现在提交信息里（L1）**：**Issue / 合并请求的编号（下称「变更编号」，与内部工单号是同一概念）只允许出现在提交信息中，不得出现在项目内容里**（唯一的例外是变更日志——它按 `specs/general/changelog.adoc` 的「可核对」条承载条目与需求的对应关系）。**项目内容**指随项目交付、会被他人读到或被执行的一切文本：规范、文档与说明、代码与注释、脚本与规则数据、配置、站点与模板。**理由**：这些编号是**平台侧的临时坐标**——换一个托管平台、换一次迁移、或仓库改名即失效，而项目内容的读者与执行者拿不到它们、据此也找不到任何东西；追溯的落点是 git 历史（提交信息），不是交付物本身。**判定标准（任一命中即不合规）**：① 正文/注释里写「Issue #N」「PR #N」一类编号；② 以「某项目的 #N」形态引用外部仓库的编号；③ 用编号代替"哪一次改动、什么原因"的表述——要说明来由就写事实（谁提出、什么场景、失效形态），编号留给提交信息。**边界**：本条只禁「变更编号」这一样；**规范自身的编号、标准名里的编号**（如 `PKCS #5`、防线清单的序号）是内容本身的载体，不受本条约束。**存量随动迁移**（改到哪改到哪），用户显式声明一次性收敛时按其范围全库收。**本条是本集合自己的判据化取舍**——外部材料只规定提交信息怎么写（见 `specs/general/git.adoc` 的依据行），**未**规定变更编号能出现在哪些文本里；取这个方向的理由是「交付物只承载读者拿得到、可据以定位的东西」（同向的既有条：`specs/general/encoding.adoc`「不在产物里泄漏内部代号」）。
* **正文写"为什么"与边界（L2）**：需要解释时在空行后写正文，说明**为什么这样改**与**影响边界**；不重复 diff 已能看出的"改了什么"、不写调试过程。
* **依据（标准名/编号）**：Conventional Commits 1.0.0——**业界约定、非标准**（其自述为 "a lightweight convention on top of commit messages"），故本条只作约定、不写成"依据某标准要求"；类型与语义化版本的对应关系（`feat`↔MINOR、`fix`↔PATCH、`BREAKING CHANGE`↔MAJOR）同出该约定。

== 冲突与压缩提交（git 侧落地）

**规则本体**（工具无关：先解冲突、再压缩、最终只有一个提交、解冲突后核查是否丢内容）见 `specs/general/version-control.adoc`；本节只写**在 git 上取哪个值来判**（只给取值形态，命令属执行动作）。

* **冲突解决后的核对（L1）**：核对到的是**取值状态**——本次改动与两侧各自的改动清单**逐条对得上**：差异检出里**不出现同一批改动的"删除 + 新增一对"**、应保留历史的文件**被识别为 rename**、文本内容**两侧的改动都在**（与「文件移动与重命名」同一条强制核对）。**不得整体取一侧收尾**（取哪一侧、用什么开关属执行动作，不写进规范）。
* **"最终只有一个提交"的核对（L1）**：核对到的是**取值状态**——目标分支到本分支之间**只有一个提交**（P7 的两个提交因「例外」被用户点名保留时，以那两个提交为终点核对，不再另有多余提交）；且压缩后仍**能取到**本规范「重命名与内容修改须分两个提交」拆出的那两条记录（未点名该条时压缩对象不含它们）。怎么取属执行动作，不写进规范。
* **返工基点的核对（L1）**：核对到的是**取值状态**——**返工前钉定的基点仍是当前分支的祖先**（在 git 上即 `git merge-base --is-ancestor <基点> <本分支>` 为真）。取不到基点时（平台未给、或该 sha 不在本仓库）**不得猜**——按『无判据可用』如实说明，不写成『已核对为真』。**根因**：把返工做成『在一个更早的分叉点上重做』时，基点之后合入的改动**不会出现在本次差异里**——`git diff <基点..本分支>` 看着干净，`git diff <目标分支> <本分支>` 却把那批改动显示成**反向删除**，而后者在一次『解冲突』的语境里最容易被读成『我要删的就是它』。**怎么取属执行动作，不写进规范。**
* **返工后不得让『差异为空』成为唯一判据（L1）**：『工作区与目标分支差异为空』**不等于**『没有回退目标分支的改动』——重建在更早分叉点上的分支，其差异检出恰恰**看起来更干净**（要回退的东西已被切除）。故返工的核对**须以基点关系为主判据**，差异为空只作辅助。
* **压缩后的合并关系核对（L1）**：核对到的是**取值状态**——**目标分支仍须是本分支的祖先**（合并关系不得因压缩而丢失）。**根因**：把"解决冲突"做成"照抄目标分支的文件内容后另起一个单亲提交"，工作树看起来一致、差异检出也看不出毛病，但**目标分支并未成为本分支的祖先**——平台侧据合并关系判定，**仍报冲突**。怎么取属执行动作，不写进规范。
* **并入是否真实发生的核对（L1）**：核对到的是**取值状态**——**目标分支的当前最新提交是本分支的祖先**，且本分支的差异检出是按"**已并入该最新提交**"重算过的。**这一条与「压缩后的合并关系核对」的分工**：那条核的是『压缩之后不要把它弄丢』，本条核的是『**压缩之前它到底发生过没有**』——**`git merge-base` 的取值恰好等于目标分支本身**（分叉点在目标分支自己身上）时，前者为真，**却不是"已并入最新"**（本分支的内容快照仍是旧基点那套）；故**不得以这条关系为真顶掉本条**。**怎么取属执行动作，不写进规范。**
* **相对基线的核对（L1）**：核对到的是**取值状态**——**两个方向都核**：目标分支在基线之后新增的内容一条不少、本分支在基线之后新增的内容一条不少；核对的账是"**合并后的差异检出**与**仅按目标分支当前最新提交、同一基点算出的那一份逐条一致（且为空）**"。**不得整体取一侧收尾**（见上文「冲突解决后的核对」同一条）。怎么取属执行动作，不写进规范。
* **压缩后不足量删除的核对（L1）**：核对到的是**取值状态**——相对**目标分支当前最新提交**的差异检出里，**本分支在基线之后新增的条目不得出现为删除**；核的账须与"**仅按目标分支当前最新提交、同一基点重算**"的那一份**逐条一致**，且**那一份为空**。**这一条与「相对基线的核对」的分工**：那条在**并入时**核（把账算平再压缩）、核的是"内容在不在"；本条在**压缩之后**核、核的是"**有没有多出删除**"。**根因**：压缩的产出是"相对目标分支的差异"，分支停在旧基点上时，那个差异**看起来更干净**（该在的东西被记成了删除），故"工作区自洽 / 无冲突标记"在这条上**不构成任何依据**。怎么取属执行动作，不写进规范。
* **被改过 / 删过的文件里的删除条目逐处核（L1）**：核对到的是**取值状态**——**两个方向的删除各自都是空**：① **本分支侧**——本次改过、删过的**每个文件**里，本分支在基线之后**新增**的行**不得出现在删除条目里**（**不得只核被整体删除的文件**：改过的文件里混着反向删除，文件级根本看不出来）；② **目标分支侧**——目标分支在基线之后新增的条目**一条不得出现在删除条目里**；③ **两侧的删除须对得上**——**一侧单方删除的，不得被另一侧的删除抵消**（甲处目标分支删、乙处本分支删，总量看着对得上，仍属**多余删除**）。**为什么这一条单列**：文件被整体删除只是删除的一种形态，而"改过 / 删过的文件里混进反向删除"**不改变文件个数**、也不显示为删除 + 新增一对，故它漏得掉任何按"文件"维度的核对。**不得整体取一侧收尾**（与上文「冲突解决后的核对」同一句）。怎么取属执行动作，不写进规范。
* **推送口径（L1）**：压缩必然改写分支历史，故推送**需要**覆盖远端；此时**只允许带租约地覆盖远端**（凭远端当前指向的 sha 承认这次覆盖），**不得**无条件覆盖。**"AI 不做强推"的一般口径不适用于用户明确要求的压缩提交**；强推前须先确认**无他人正基于旧 sha 工作**，并在汇报里声明新旧 sha 的对应关系（两条的平台侧落地见 `specs/platform/cnb.adoc`「对象钉定与可追溯」）。
