= git 规范（通用层）

以下规范适用于 git 操作。任务临时产物管理见执行原则（specs/core/execution.adoc）「临时产物」条目。

== 文件移动与重命名

* 文件移动/重命名必须使用 git mv（git 按内容相似度识别 rename、保留跟踪历史），禁止用「新增新文件 + 删除旧文件」代替——delete+create 会使 git 历史断裂（旧文件历史丢失）；移动/重命名前须先确认源文件已纳入 git 跟踪（未跟踪的新文件先 git add，再从暂存区/工作区 git mv），保证 git 能识别为 renamed
* **强制核对（兜底）**：凡本次改动涉及文件的新增/删除/移动，操作完成后必须执行 `git status`/`git diff --name-status` 核对——应保留历史的文件若显示为 `deleted` + `new file`（未识别为 rename），说明误用了 delete+create，须同步修复工作区：恢复旧文件后 git mv 正式重命名，再应用内容修改，确保 git 识别为 renamed；该强制核对规则提升于必加载层（specs/core/execution.adoc「文件操作强制检查」）
* **一拆多场景**：git mv 为文件级一对一操作。将一个文件拆分为多个时，只能让其中一个继承 rename 历史——以内容主体/最核心的文件继承历史（git mv），其余拆分出的文件作为新文件创建（继承历史），不得对同一源文件重复 git mv。拆分出的文件不得添加指向旧文件的历史来源注记（旧文件可能已无法追溯，且会让引用悬空），如需交叉引用一律直接指向当前有效的文件地址（见规范管理 specs/core/management.adoc「规范引用文件必须真实存在」）
* **避免重命名失效的识别**：重命名是否被 git 识别受内容相似度影响（默认 50%）；大幅改动内容后再 git mv 可能识别失败，故先 `git mv` 保留历史、再应用内容修改，而非先改内容再移动

== 暂存与提交检查

* 新生成且需保留的文件，默认执行 git add 加入暂存区；git add/commit 前须检查暂存内容，确认无临时文件（`tmp/` 文件夹临时产物、扫描中间产物、构建产物等）被误提交；若发现临时文件已被提交，直接执行 git rm 删除，不得执行 git commit，由用户最终自行提交确认，不得因此中断任务
