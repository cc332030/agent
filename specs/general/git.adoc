= git 规范（通用层）

以下规范适用于 git 操作。任务临时产物管理见执行原则 link:../core/execution.adoc[]「临时产物」。

== 文件移动与重命名

> 本节是 `git mv` 铁律的**权威完整定义**（最高关注项 P1，L1 强制）；其他位置（link:../core/execution.adoc[]「文件操作强制检查」、`AGENTS_COMMON.adoc`「最高优先级铁律」）均为**引用/重申**，不得被判为重复而合并删除（见 link:../core/execution.adoc[]「分级与最高关注项」）。

* 文件移动/重命名必须使用 git mv（git 按内容相似度识别 rename、保留跟踪历史；依据：git 官方文档 `git-mv` 与 `git-diff` 的 `-M/--find-renames` rename 检测），禁止用「新增新文件 + 删除旧文件」代替——delete+create 会使 git 历史断裂（旧文件历史丢失）；**判断标准**：只要操作会让某个既有文件的 git 历史无法追溯，就属"文件移动"，必须 git mv，不得因主观认为"这是在重构而非移动文件"而规避；移动/重命名前须先确认源文件已纳入 git 跟踪（未跟踪的新文件先 git add，再从暂存区/工作区 git mv），保证 git 能识别为 renamed
* **强制核对（兜底）**：凡本次改动涉及文件的新增/删除/移动，操作完成后必须执行 `git status`/`git diff --name-status` 核对——应保留历史的文件若显示为 `deleted` + `new file`（未识别为 rename），说明误用了 delete+create，须同步修复工作区：恢复旧文件后 git mv 正式重命名，再应用内容修改，确保 git 识别为 renamed；该强制核对规则提升于必加载层（specs/core/execution.adoc「文件操作强制检查」）
* **一拆多场景**：git mv 为文件级一对一操作。将一个文件拆分为多个时，只能让其中一个继承 rename 历史——以内容主体/最核心的文件继承历史（git mv），其余拆分出的文件作为新文件创建（继承历史），不得对同一源文件重复 git mv。拆分出的文件不得添加指向旧文件的历史来源注记（旧文件可能已无法追溯，且会让引用悬空），如需交叉引用一律直接指向当前有效的文件地址
* **避免重命名失效的识别**：重命名是否被 git 识别受内容相似度影响（默认 50%，见 git 官方文档 `git-diff` 的 `-M<n>`/`--find-renames[=<n>]`）；大幅改动内容后再 git mv 可能识别失败，故先 `git mv` 保留历史、再应用内容修改，而非先改内容再移动
* **rename 未被识别的两类非操作类根因（L1，须先查根因再动手）**：`git diff --name-status` 显示 `D`+`A`（未识别为 `rename`）时，除"误用 delete+create"外，还可能是**结构性的**，此时调整命令无法解决，须先判根因：
  ** **合并/基点错位**：分支的 `git mv` 是相对**它自己的基点**做的，而 PR/比对以**目标分支（main）为基点**算——若目标分支在此期间也动过同一批文件，两边路径对不上，git 就无法把新旧路径配成一对（实证：某次重构在分支内已 `git mv`，但因 main 也改了同一批文件，PR diff 仍显示删除+新增）。**处置**：以目标分支为**线性基底**重放移动（去掉中间合并提交、在该基底上重做），而非反复重跑 `git mv`。
  ** **一拆二/内容再分配**：把一个文件拆成两个、或把内容大部分并入**已存在**的另一文件时，git 的 rename 是**文件级一对一**、记录不下"拆分/再分配"这个动作——无论怎么调提交都识别不出（实证：同一文件公共部分并入既有 `testing.adoc`、私有小节留在别处，留存内容不足原 10%，任一阈值下都非 rename）。**处置**：如实说明"属内容再分配、非 1:1 移动"，**以"内容一条未丢"（逐条对照）作为完整性判据**，不以 rename 形态作为交付前置条件；不得为"凑出 rename"而堆留无用内容。
* **提交历史须按目标分支基线组织（L2）**：PR 的 diff 以目标分支为基线，故整理提交历史时以**目标分支当前 sha 为线性基底**重放改动（避免夹在中间的合并提交使 rename 识别与 diff 比对失真）；目的不是"让 git 好看"，而是让追溯与复核取到正确对象。

* **可执行抓手（引用方项目自检）**：引用方项目须在自查中核对本次改动——`git status` / `git diff --name-status` 出现同一批改动的 `D`（删除）+ `A`（新增）且内容高度相似时，即为 delete+create 误用，应改用 `git mv` 后重做该处改动；`git diff --cached -M --summary` 应显示 `rename` 记录。规范集合本身**不做也无法做**这项拦截（它看不到引用方的工作区），故给出可执行的自检命令，让"必须 git mv"不止是口号

== 行尾与检出归一

> 行尾**取值**的权威判据（LF 基准、`.bat`/`.cmd` 必须 CRLF）见 link:../general/encoding.adoc[]「换行符」「跨平台检出」；本节只定 git 侧的落盘与提交口径。

* **`.gitattributes` 固定行尾策略，不靠人工手动调整（L1）**：仓库根 `.gitattributes` 按文件类型显式声明 `text eol=lf`（默认文本）与 `text eol=crlf`（`.bat`/`.cmd`/`.ps1`），二进制声明 `binary`；`.gitattributes` 随仓库入库，检出时由 git 按规则写入工作区（见 link:../general/encoding.adoc[]「跨平台检出」）。
* **`core.autocrlf` 交给仓库配置（L2）**：仓库已用 `.gitattributes` 显式声明时，本机 `core.autocrlf` 应设为 `false`，避免本机设置与仓库规则二次改写、出现"同一文件在不同机器上不同的行尾"（依据：git 官方文档 `gitattributes` 与 `core.autocrlf` 的优先级说明）。
* **不提交行尾噪声（L1）**：`git add`/`commit` 前核对暂存内容，若某文件的 diff **只因行尾（LF↔CRLF）变化**而变化，须先还原该文件的纯行尾改动、再只提交真实内容改动——"整文件全红"的行尾噪声会淹没真实变更、让 blame 与 review 失效（依据：git 官方文档 `git-diff --ignore-space-at-eol` 对行尾差异的说明）。行尾改错的修复方式见 link:../general/encoding.adoc[]「换行符（行尾）」。
* **核对命令（L2）**：`git ls-files --eol` 检查工作区行尾（`w/crlf`、`w/mixed` 为异常）；`git check-attr -a <文件>` 确认属性生效；`git diff --ignore-space-at-eol` 可只在忽略行尾差异时看真实改动。

== 暂存与提交检查

* 新生成且需保留的文件，默认执行 git add 加入暂存区；git add/commit 前须检查暂存内容，确认无临时文件（`tmp/` 临时产物、扫描中间产物、构建产物等）被误提交；**若发现临时文件已被提交（该异常场景下）**，直接执行 git rm 删除，该场景下不得执行 git commit、交由用户确认后再提交，不得因此中断任务（此限定仅针对"临时文件已被提交"这一异常场景，不构成对任务提交策略的限制）
