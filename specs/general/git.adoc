= git 规范（通用层）

适用于 git 操作。任务临时产物管理见 `specs/core/execution.adoc`「临时产物」。

== 文件移动与重命名

本节是 `git mv` 铁律的**权威完整定义**（最高关注项 P1，L1 强制，不可降级）；其他位置（`specs/core/execution.adoc`「文件操作强制检查」、`AGENTS_COMMON.adoc`「最高优先级铁律」）均为**引用/重申**，不得被判为重复而合并删除。

* **文件移动/重命名必须使用 `git mv`（L1）**：git 按内容相似度识别 rename、保留跟踪历史（依据：git 官方文档 `git-mv` 与 `git-diff` 的 `-M/--find-renames`）；禁止用「新增新文件 + 删除旧文件」代替——delete+create 会使 git 历史断裂。**判断标准**：只要操作会让某个既有文件的 git 历史无法追溯，就属"文件移动"，必须 `git mv`，不得因主观认为"这是在重构而非移动文件"而规避。移动/重命名前须先确认源文件已纳入 git 跟踪。
* **强制核对（兜底）**：凡本次改动涉及文件的新增/删除/移动，操作完成后必须执行 `git status`/`git diff --name-status` 核对——应保留历史的文件若显示为 `deleted` + `new file`（未识别为 rename），即误用了 delete+create，须同步修复工作区：恢复旧文件后 `git mv` 正式重命名，再应用内容修改。
* **一拆多场景**：`git mv` 为文件级一对一操作。将一个文件拆分为多个时，只能让其中一个继承 rename 历史——以内容主体/最核心的文件继承历史（`git mv`），其余拆分出的文件作为新文件创建；不得对同一源文件重复 `git mv`。拆分出的文件不得添加指向旧文件的历史来源注记。
* **避免重命名失效的识别**：重命名是否被 git 识别受内容相似度影响（默认 50%）；大幅改动内容后再 `git mv` 可能识别失败，故**先 `git mv` 保留历史、再应用内容修改**。
* **rename 未被识别的两类非操作类根因（L1，须先查根因再动手）**：`git diff --name-status` 显示 `D`+`A`（未识别为 `rename`）时，除"误用 delete+create"外还可能是**结构性的**，此时调整命令无法解决：
** **合并/基点错位**：分支的 `git mv` 是相对**它自己的基点**做的，而 PR/比对以**目标分支为基点**算——若目标分支在此期间也动过同一批文件，两边路径对不上，git 就无法把新旧路径配成一对。**处置**：以目标分支为**线性基底**重放移动，而非反复重跑 `git mv`。
** **一拆二/内容再分配**：把一个文件拆成两个、或把内容大部分并入**已存在**的另一文件时，git 的 rename 是**文件级一对一**、记录不下"拆分/再分配"这个动作。**处置**：如实说明"属内容再分配、非 1:1 移动"，**以"内容一条未丢"（逐条对照）作为完整性判据**，不以 rename 形态作为交付前置条件；不得为"凑出 rename"而堆留无用内容。
* **提交历史须按目标分支基线组织（L2）**：PR 的 diff 以目标分支为基线，故整理提交历史时以**目标分支当前 sha 为线性基底**重放改动（避免夹在中间的合并提交使 rename 识别与 diff 比对失真）。
* **可执行抓手（引用方项目自检）**：核对本次改动——`git status`/`git diff --name-status` 出现同一批改动的 `D`+`A` 且内容高度相似时即为误用，应改用 `git mv` 后重做该处改动；`git diff --cached -M --summary` 应显示 `rename` 记录。

== 重命名与内容修改须分两个提交（默认固定动作）

本节是"重命名 + 内容修改必须拆成两个提交"的**权威完整定义**（最高关注项 P7，L1 强制，不可降级）；其他位置均为**引用/重申**，不得被判为重复而合并删除。

**一句话规则**：一次改动里同时存在**文件重命名**与**内容修改**时，**一律拆成两个提交**——第一个提交**只做重命名、内容逐字节不变**（**本次涉及重命名的文件全在这一个提交里**），第二个提交**只改内容、不再动路径**。

* **适用对象与判定标准（L1）**：适用对象是"一次改动中既重命名该文件、又修改其内容"的**每一个**文件（含"顺手重命名"），**不按文件个数分摊**：合格提交序列是**一次改名（内容不变）+ 一次（或多次）内容修改**，**不是**"一个文件一个改名提交"。**判定标准（适用对象与判定标准（L1），逐条可核对）**：① 该文件在**同一个提交**里同时出现 `rename` 与内容行改动；② 首个提交里该文件内容**不是逐字节不变**；③ "只重命名"的提交缺失——任一命中即不合规。依据：ISO 10007（一次变更只承载一个可追溯的目的）；把一批改名收进同一个提交，是让"这次移动"成为**一条可独立回溯的记录**。**与 `git mv` 铁律的关系**：`git mv` 保证"git 认得这是一次移动"，本条保证"这次移动是一条可独立回溯的记录"——同一目的的两道防线，顺序不可颠倒（先重命名、后改内容）。
* **分量大小不是理由（L1）**：不得以"改动很小/影响面可控"为由合并提交——"小"没有任何可判定的阈值，一旦允许，判定标准立刻退化成执行者的**主观判断**。"用户要求压缩提交"不是本条的理由条目。
* **提交顺序（L1）**：**先重命名、后改内容**，不得颠倒。依据：rename 识别按内容相似度（默认阈值 50%）；先把内容大改、再改名，或把两者放进同一个提交，可能同时丢掉 rename 识别。
* **无损拆分（L1，判定标准）**：按新路径 `git mv` 并把改动提交为**只重命名**那一个后，必须提交仍能取到**内容逐字节不变**的版本；随后在**同一新路径**上应用内容修改、提交为第二个提交。**判定标准**：`git diff <改名提交>^ <改名提交> -M --stat` 显示该文件只有改名、内容 0 增 0 删。**一批文件同时改名时逐文件核对**：每个改名文件都须满足上述判据，不得只核其中一个——只要有一个文件把内容改动留在了改名提交里，那份**中间版本从未存在过**（首个提交的内容会变成"新路径 + 已改内容"），历史取回的是一份**不存在的版本**。依据：ISO 10007（基线须是真实存在且可追溯的状态）。
* **两个提交都要进本次交付（L1）**：两个提交须**一并推送**、**落在同一个 PR**；**同一 PR 内改动分批交付时，这条序列不重排**（**分批交付**不得压、拆或重排已交付的两个提交）——后一次改动不得把前一次已交付的改名提交与内容提交压、拆或重排。**本条不构成合并的例外**：压缩提交按 `specs/platform/cnb.adoc`「压缩提交」执行（只压本次任务尚未合入的临时中间提交、内容不变），而本条的"两个提交"**不是临时中间提交**——它是本条要求交付的可追溯记录，**不得以"压缩提交"为由把两者压回一个**。
* **「压缩提交」的请求不覆盖本条（L1）**：用户提出**压缩提交/压成一个提交**时，其中**属于改名的部分仍按本条拆两个提交**——用户**未点名本条**时，压缩要求**只作用于本次任务尚未合入目标分支的临时中间提交**，本条的两个提交**原样保留**。**判定标准（逐条可核对，任一命中即不合规）**：① 以"用户要求合并成一个提交"为由把改名与内容修改放进同一个提交，而本次会话里用户从未点名本条——共用一个词不等于声明；② 先按本条拆了两个提交、又以压缩为由把它们合回一个，且无明确声明；③ 把这两个提交当"临时中间提交"处理。**为什么算两件事**：用户要压缩的是"**没内容的中间历史**"（多次试跑的修正、迭代补丁），本条那两个提交是**已交付内容里**的一个只改变路径、不改变内容的提交，并进内容提交之后再也无法分别取回。
* **例外（只有一条，L1）**：用户**明确声明**"这次重命名与改内容合成一个提交"时按其声明执行——声明须**点名重命名与内容修改这两件事**、须**预先声明**（在整理这两个提交之前说）、须在**交付说明**里写明。"合并成一个提交""压缩提交""压成一个"这类**没点名本条**的说法**不算**声明（它只解除"临时中间提交"要压成一个的那一侧）。
* **可执行抓手（引用方项目自检）**：提交前核对——① `git log --follow --name-status <新路径>` 应能看到"先 `R`（仅改名、内容 0 增删）、后 `M`（改内容）"两条记录；② `git diff <改名提交>^ <改名提交> -M --stat -- <新路径>` 的增删数应为 0/0；③ **断链核对**：`git log --diff-filter=R -M --name-status` 应能看到那一条**批量改名**记录，且紧接其后的提交里不得再出现同类文件的重命名；④ **压缩后核对**：以压缩为由整理过历史后仍须能按 ①②③ 取回这两条记录。

== 行尾与检出归一

行尾**取值**的权威判据（LF 基准、`.bat`/`.cmd` 必须 CRLF）见 `specs/general/encoding.adoc`「换行符」；本节只定 git 侧的落盘与提交口径。

* **`.gitattributes` 固定行尾策略，不靠人工手动调整（L1）**：仓库根**须有** `.gitattributes`，并按文件类型显式声明 `text eol=lf`（默认文本）与 `text eol=crlf`（`.bat`/`.cmd`/`.ps1`），二进制声明 `binary`。
* **`core.autocrlf` 交给仓库配置（L2）**：仓库已用 `.gitattributes` 显式声明时，本机 `core.autocrlf` 应设为 `false`，避免本机设置与仓库规则二次改写。
* **不提交行尾噪声（L1）**：`git add`/`commit` 前核对暂存内容，若某文件的 diff **只因行尾（LF↔CRLF）变化**而变化，须先还原该文件的纯行尾改动、再只提交真实内容改动。
* **核对命令（L2）**：`git ls-files --eol` 检查工作区行尾（`w/crlf`、`w/mixed` 为异常）；`git check-attr -a <文件>` 确认属性生效；`git diff --ignore-space-at-eol` 可只在忽略行尾差异时看真实改动。

== 暂存与提交检查

* **新生成且需保留的文件默认 `git add` 加入暂存区**；`git add`/`commit` 前须检查暂存内容，确认无临时文件（`tmp/` 临时产物、扫描中间产物、构建产物）被误提交。
* **若发现临时文件已被提交（异常场景）**：直接执行 `git rm` 删除，该场景下不得执行 `git commit`、交由用户确认后再提交，不得因此中断任务。

== 提交信息

本节只定**提交信息怎么写**；变更日志的条目怎么写是另一件事（见 `specs/general/changelog.adoc`）。两者是同一条链的两端：**提交信息是上游**（一次提交改了什么），**变更日志是下游**（一版发出去后使用者要跟进什么）——上游没有类型时，下游"组内按类型分组"只能靠人工归类。

* **首行写类型前缀（L2）**：提交信息首行按 `<type>[(scope)]: <subject>` 书写——`type` 取**固定闭集**（与 `specs/general/changelog.adoc`「组织形态」中组内类型分组的类型同源：`feat`/`fix`/`perf`/`refactor`/`docs`/`style`/`test`/`build`/`ci`/`chore`，同一项目内用词一致、不混用同义词），`scope` 可省、写**受影响的对象**（模块/组件/文档落点），`subject` 用一句话说明改了什么、不加句末标点。**判定标准**：首行不以 `<type>:` 或 `<type>(scope):` 起头即不合规。
* **破坏性变更须显式标注（L2）**：会改变既有行为、契约、数据格式或使用方式时，在 `type`/`scope` 后加 `!`（`feat(api)!: …`）**并**在页脚写 `BREAKING CHANGE: <说明与迁移方式>`——**不得把某个类型默认为破坏性的**（破坏性变更可与任何类型组合），也不得只在正文里含糊提一句。**判定标准**：存在破坏性变更而首行无 `!`、页脚无 `BREAKING CHANGE:`，即不合规。
* **正文写"为什么"与边界（L2）**：需要解释时在空行后写正文，说明**为什么这样改**与**影响边界**；不重复 diff 已能看出的"改了什么"、不写调试过程。
* **依据（标准名/编号）**：Conventional Commits 1.0.0——**业界约定、非标准**（其自述为 "a lightweight convention on top of commit messages"），故本条只作约定、不写成"依据某标准要求"；类型与语义化版本的对应关系（`feat`↔MINOR、`fix`↔PATCH、`BREAKING CHANGE`↔MAJOR）同出该约定。
