= 上下文与读取范围规范（通用层，任务开始时即加载）

本文件回答三个问题：**"这件事该读多少"**（读取范围）、**"会话变长了怎么办"**（长会话治理）与**"怎么用更少的轮次拿到结论"**（执行吞吐、生成效率、token 纪律）。`specs/core/execution.adoc`「范围控制」只放三条底线，逐条判据的完整正文在本文件。

== 读取范围（逐条判据）

* **读取按任务定界（L1）**：开始读任何东西前先按用户要求定出本次任务**必须知道的最小信息集**（要改什么、要什么证据），只读该集合内的内容——不因"顺手、反正便宜、了解下没坏处"而多读；读完后自检"读的这些是否都用到了"，未用到即属越界读取。
* **定位优先，避免全库扫描（L1）**：文件名/路径已知、或可由 glob/grep 直接定位的文件，必须用**精确定位**读取，禁止启动 explore 类子 agent 做全库扫描；禁止借修改小需求之机对整个项目做 code review/全量摸底。只在"位置未知、命名未知"的开放性查找时才用 explore，且派发指令须限定目标。
* **分层渐进、按需深入（L1）**：按"元数据 → 入口/目录 → 目标文件 → 必要片段"的层次递进读取，每层读完再决定是否深入；命中检索结果时**先核对是否命中、命中位置是否真的是目标**，只读命中片段附近必要内容。
* **先查导航与索引，再读正文（L2）**：优先读项目的索引/总览（README、AGENTS 入口、`doc/` 索引页、规范调度器）来定位，再读对应正文；有代码索引/符号跳转时优先用索引能力。
* **委派重型读取给子 agent（L2）**：跑测试、读长日志、拉外部文档、大范围调研等**输出量大**的读取优先委派子 agent（或先只留关键行再进本上下文），让冗长内容留在子 agent 上下文里，只把结论/摘要带回。
* **读取结果落盘、不靠记忆（L2）**：大范围检查与多步骤任务的进度、结论写入 `tmp/` 下临时文档，供后续步骤/后续会话读取。
* **判断不了就问，不靠多读猜（L1）**：需求存在歧义、命名与位置均不确定时先按 `specs/core/execution.adoc`「指令执行」提问澄清，不得用"把相关的东西都读一遍"来代替澄清。
* **任务切换即清洁上下文（L1）**：一次会话内切换**互不相关**的任务时，先把通用规范入口与项目自身规范**重新读取/重新确认**，再开始新任务；不得依赖"上文已经读过规范"而带着旧任务上下文直接干新活；已放弃/已中断的任务上下文不得再作为判断依据。
* **长会话降级自保（L1）**：发现当前会话已执行多个任务、上下文明显变长时，**主动降低读取范围**——简单任务按最小必要读取，不沿用上一任务的探索路径、不重复上一任务读过的文件；若一次简单任务仍需要读大量文件，先停下来说明"需要更多上下文的原因"，而不是直接开读。
* **结论交给持久文档与规范（L2）**：任务产生的持久结论写入代码注释/设计文档/规范/`tmp/` 记录，使其可被后续会话重新读取；不要把"结论要靠本次会话的上下文记住"当作机制。
* **简单任务优先另起会话（L1）**：执行环境支持新开会话/清空上下文、且任务与当前会话历史无依赖时，简单任务**优先另起会话或清空上下文后再执行**。执行环境不支持时，按上两条在会话内降级处理，并**在结果中说明"建议下次在干净会话中执行此任务"**。
* **阶段结论即时落盘（L1，长会话底线）**：每完成一个阶段/里程碑，**立刻**把结论写入持久位置，不等上下文逼近上限才整理。
* **超长任务的分段（L2）**：单任务确实跨越多轮、上下文逼近窗口上限时，先压缩（保留决策、未决问题、接口约定，丢弃冗余工具输出）或把阶段结论落盘，再继续；需要并行探索的调研类任务改用子 agent 隔离。**压缩或清空前必须先把关键约定与结论落到持久位置**。
* **读前自检（L1）**：① 本次任务的目标与范围是否已明确（未明确先澄清）；② 这批读取是否落在最小必要信息集内（不在则说明理由或缩小范围）。
* **读后自检（L1）**：① 读到的内容是否都与任务相关（有无关内容即停止继续读）；② 是否已具备完成任务的充分信息（不足时再判断"该补哪一层"，而非扩大为全量扫描）。

== 执行吞吐（逐条判据）

读取范围管"少读"，本节管"少绕"——同一个任务，**多花一轮往返就多付一次全上下文的输入、多等一次模型往返**：执行轮次是上下文体积的**乘数**。

* **独立调用必须合并，禁止试探式往返（L1）**：执行环境中**同一次调用（同一批）内互相无依赖**的命令/查询/读取须**一次批量发出**（一条脚本/一次调用里完成）；**不得**为了"先看一步再决定下一步"把可并行、可预判的步骤拆成多轮。**判定标准**：一次调用只做一件事、且下一件事在动手前就已可判定，即违规。**反例**（实测高频形态）：把四个互相无依赖的读取动作拆成四轮发出——四轮各付一次全上下文输入；正确形态是**一次调用内做完、只输出需要的那几行**。
* **构建与校验的输出须一次取到（L1）**：跑构建、跑测试、跑校验命令时，**同一次调用内**完成"执行 + 取统计 + 取失败明细"（怎么取到属执行动作，不写进规范），不得先跑一遍拿状态、再跑一遍捞日志、再跑第三遍复现；不得在多轮里反复重启同一个构建去"看看这次是什么错"。
* **读到的内容一次沉淀、不重复读（L1）**：同一份文件/同一组证据在一次任务里**只读一次**，读到的结论当即写入规划或 `tmp/` 记录；不得在后续轮次里"再确认一次""再看一遍"。**判定标准（可核对）**：同一路径在一次任务里被读第二次，而两次之间**没有新的事实、也没有新结论产生**——命中即违规。**例外（三种，须写明理由）**：① 文件在本任务内被本次改动改过（须重读改动后的内容）；② 第一次读到的只是片段（节选/命中行附近），这次要的是另一段；③ 需要按**对象钉定**重新取值（换 commit sha 复查）。
* **往返成本也要算（L2）**：任务规划时把"预计要几轮往返、每轮要多久"一并估出来；**长任务优先"一次批量提交 + 一次汇总验证"**，不把需要逐步确认但实际无分支的步骤排成串行。
* **执行环境凭据须固化为可复用形态（L2）**：会用多次的访问凭据**在任务开始时**按平台机制**固化一次**，后续取数直接复用；不得每次需要时再"问一遍、拼一遍、重登一遍"。
* **本地缓存与镜像就近取用（L2）**：构建产物与依赖**先按已有本地缓存/工作区取用**、再考虑远端；下载量大的依赖/镜像按项目所在地选就近的镜像站（见 `specs/stack/maven.adoc`「仓库与镜像」、`specs/general/dependency.adoc`「包源」）——**换源应一次配置到位、不在每轮里重试**；**已配置过即沿用、不覆盖、不重配**。
* **长流程不留零信息等待（L1）**：为长流程设置**可判定的进展与超时**，使"在跑"与"卡住"可分辨（见 `specs/general/ci-cd.adoc`「超时与资源」）；**等待期间不得空转**——不得连续发出只问"好了没有"的调用去探状态。**非流水线类的每一次操作（命令/构建/读取/网络等待）同样适用**——超时取值与超时后的处置见 `specs/general/collab.adoc`「操作超时与超时后的处置」；**失效形态**是把"零信息等待"只理解成流水线的 job——命令卡住时既没有时限、也就无从分辨"在跑"与"卡死"，任务停在同一处直到人工介入。

== 生成效率（同等质量下最少往返）

上一节管"少绕"的**调用形态**；本节管**做事的安排**。**前提是先守住质量与效果**：本节任何一条都**不得**以牺牲正确性、完整性、验证为代价。

* **先定完成判据，再动手（L1）**：动手前把"什么算做完"写成可核对的判据（要产出什么、要过哪些校验、怎么验收）——**判据不清就动手是最大的返工来源**。判据落在规划文档，执行中只做"按判据收敛"，不做"边做边猜要什么"。
* **一次做对一次做完（L1）**：能一轮做完的事不得拆成多轮试探；**同一改动一次改到位**（要改的文件一次全改、要补的用例一次全补、要同步的引用与文档一次同步），不得留"先改一处、跑一下、再改下一处"式的碎片推进。**判据：本轮交付之后是否需要再改同一批文件才能满足同一条要求——需要即说明本轮没做完。**
* **延后验证、一次到位（L1）**：把互相无依赖的验证动作**攒到一处**——先完成整批改动，再跑一次完整校验；不得每改一个小点就重启一次构建/测试。**例外**：单步改动之间**存在真实依赖**（上一步的产出决定下一步的方向，且无法预判）时才逐步验证——"先看一步再决定"若在动手前就已可判定，即不属例外。（"完整校验"指该项目声明的**全部**校验手段，清单与取值见 `specs/general/verify.adoc`「验证的适用边界」与 `specs/general/ci-cd.adoc`「校验链完整」）
* **失败一次就查根因，不靠重试撞对（L1）**：命令/构建/测试失败时，**先把失败原因查清**（读完整报错与最小复现），再改**并一次把同类问题一起改掉**；不得反复"改一处跑一次、撞到过为止"。**判断标准**：出现同一命令在同一问题上被执行第二遍、且两遍之间没有对根因的新认识——命中即违规。
* **按需读取、不全量预处理（L1）**：不要"先把可能有用的资料**全量预读**一遍再开工"；不确定要不要读时先按精确定位看目录/索引/命中片段，再决定是否展开——**全量预读既费输入、又把低信号内容灌进上下文**。
* **批量化同类操作（L2）**：同一类操作（多文件同类改动、多份资料同类取值、多个接口同类查询）**批量一次做完**，不逐条串成多轮；同类操作**能一次化即不逐条往返**（是否可脚本化、怎么脚本化属执行动作，不写进规范）。
* **按需加载按文件切分、单文件别太大（L2）**：规范/文档类内容是**整份按需加载**的——**单个文件**越大，"按需"就越退化成"整份读完"。故组织时按**归属分层切分**，并给**单个文件一个可机械核对的体量提醒线**——超线只是**触发"该评估归属与层级了"的提醒**、不是硬上限、不强制拆分；且**不得为压体积删内容**。**模板类内容（要用就得整份取用、平时不必常备）另按"要么不读、要么读全部"单独归类**：不与"每次会话要遵守的规则"混放、各自独立成篇（判据与例外属维护方自查层，本处不重复）。
* **任务边界一次说清（L2）**：任务涉及多个产出物时，一次把边界与产物形态说清；需求不清时先澄清，不要用"先做一版看看"来试需求。
* **依据名代替复述（L2）**：产出与汇报里引用规则、标准、既有结论时**写依据名/编号与落点**，不复述其正文——复述既占篇幅又制造第二真源。
* **不重做已做完的事（L2）**：本次任务里已经确认过的结论、已经跑过的校验、已经取到的取值**直接复用**（落盘于 `tmp/` 或规划文档），不得在后续轮次里"再确认一次""再跑一遍看看"。
* **收尾一次收敛（L2）**：汇报与留证**一次写完**（改动清单 + 验证取值 + 三态台账 + 未决项），不分多轮零散补齐。
* **效率不得越过质量（L1，本节的边界）**：本节任何一条都**不得用于减少**必要的工作——必要的校验、必要的用例、必要的三视角复核、必要的留证一条都不能省；**效率是"同样质量下更少的轮次"，不是"**更少的质量**"**。判定标准：以"省一轮"为由跳过校验/复核/留证、或把"没跑"写成"通过"——命中即违规。
* 依据（标准名/编号）：ISO/IEC/IEEE 25010（性能效率）、Anthropic 工程博客《Effective context engineering for AI agents》、Agent Skills 开放规范（progressive disclosure）、Martin Fowler《Refactoring》（"small steps" 的前提是每步都有明确完成判据）。**"把轮次当成本来管"是本集合按现场用量判据化的取舍**。

== token 纪律（提高利用率与节省开销）

**先把两个概念分开**：**不是一回事**，但**手段大幅重叠**。

* **提高 token 利用率 = 提高"每一份输入产生的有效产出"**。利用率低的表现是输入很大而有效产出很小——读了一堆没用上的资料、复述了一遍已知的规则、把同一条结论说三遍、把原始日志灌进汇报。
* **节省 token = 减少"总 token 消耗"**，一般手段是少读、少说、少贴、少重读。
* **两者的关系**：提高利用率通常同时节省总量；但**"单纯省钱"的省法可能砸掉效果**——少读到缺信息、少说到讲不清楚、少贴到无法核对，都会让产出变差、返工，反而多花。故本条的取向是：**在功能完整性、代码质量、验证完整三件事都不降的前提下，先提高利用率，再谈节省总量**。
* **利用率判据：输入须"**用到了**"（L1）**：**每一份被读进上下文的内容，都要能说出它用在了哪里**（支撑了哪个判断、哪条判据、哪处改动）；读后自检时答不出用途的即属无效输入。**判定标准**：出现"顺手读的、预读备用的、反正便宜"的读取，或读完后汇报里没有任何结论由它支撑——命中即违规。
* **约束放在外部、不进上下文（L1）**：规则、清单、模板、验收判据、长参数——**能落成文件/脚本/命令的就不要靠对话反复复述**（写在**对话里每次请求都要重发**一遍）。**边界（L1）**：落成外部文件的前提是**不降低可执行性与可追溯性**。
* **少复述、多引用（L1）**：不要让模型复述已知内容——规范条文、既有结论、已确认的事实、标准原文一律按依据名/编号与落点引用、不复述。**判定标准**：汇报/产出中出现对已知规则的整段复述、或把依据原文抄进来充当论证——命中即违规。
* **不重复读、不重复贴（L1）**：同一份文件/同一组证据在一次任务里只读一次、只贴一次（结论落盘后引用落点即可）；判据与三种例外以上方「执行吞吐」节的「读到的内容一次沉淀、不重复读」条为唯一落点，本处不重列。**留痕**：读到即沉淀——结论写入规划或 `tmp/` 记录，后续按落点引用而不重读。
* **只记结论与取值、不带原始日志（L1）**：留证与汇报写**结论 + 取值 + 来源 + 条件**，不夹带原始日志、完整终端输出、逐行调试过程（需要时给命令与文件落点让读者自行复现）。
* **三件事不得为省 token 让步（L1，本条的边界）**：**功能完整性**、**代码质量**、**验证完整**——三者任一受影响时，节省 token 一律放弃。
* **成本须可说明、不得以"不贵"带过（L2）**：涉及大量输入输出的设计须能说出"这份输入换来什么判断"；说不出来即应砍掉。
* **存量与适用面（L1）**：适用于**任何一次任务执行**；**不设"必须量化 token"的要求**（量化不是目的，判据是"输入有没有被用上"）。
* 依据（标准名/编号）：ISO/IEC/IEEE 25010（性能效率）、Anthropic 工程博客《Effective context engineering for AI agents》、Agent Skills 开放规范、ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148（引用现行文件而不复述内容）。**"利用率 / 节省两者的区别与取舍"是本集合自己的判据化表达**。

== 运行契约（公共内容被未知项目加载时的可控性）

本节的**完整正文与判据在** `specs/general/verify.adoc`「运行契约」——公共内容不是在某一个项目的上下文里生效，而是**被未知项目加载**，故"加一条规则"还要问"它落到一个未知项目里会发生什么"。

本节只留三维的**索引**（**只给维名，逐维的取值、判定标准与依据名一律以 `specs/general/verify.adoc` 为准，本处不重述**）：**① 影响面**、**② 成本**、**③ 可控性**。
