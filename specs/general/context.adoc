= 上下文与读取范围规范（通用层）

以下规范适用于**所有语言、所有项目**的 agent 执行过程。它解决两个问题：**"这件事该读多少"**（读取范围）与**"会话变长了怎么办"**（长会话治理）。必加载层的执行原则（先规划后执行、范围控制）见 link:../core/execution.adoc[]，多 agent 拆分协作见 link:../general/collab.adoc[]。

== 为什么控制上下文（业界依据）

上下文不是"免费"的，也不是"越多越好"——业界已有一致共识，规范据此立条：

* **注意力预算衰减（context rot）**：上下文越长，模型对其中信息的准确召回与长程推理越差；Transformer 每 token 两两注意、n 个 token 有 n² 对关系，上下文变长时这种关系被摊薄。故上下文是**有限资源、边际收益递减**（依据：Anthropic 工程博客《Effective context engineering for AI agents》提出的 "attention budget" 与 "context rot"）。
* **最小必要上下文集**：上下文工程的目标是"**找到能最大化目标达成概率的最小高信号 token 集合**"，而非把所有可能相关的材料都塞进去（依据：同上）。
* **按需渐进披露（progressive disclosure）**：编排层（启动期）只加载极少量元数据（如 skill 的 `name`/`description`，约 100 token），任务命中时才把完整指令读入（建议 < 5000 token），更细的参考材料**用到才读**；分层与预算是给出"读到哪停"的量化抓手（依据：Agent Skills 开放规范；Claude Code、Cursor 的 Skills/Rules 均按该机制实现）。
* **规则文件要短**：常驻加载的规则文件应只保留**任何会话都需要的事实**（构建命令、约定、布局、"永远做 X"），多步流程与只对局部代码成立的内容另置并按需加载；否则既占用每次请求的上下文、又降低遵守率（依据：Claude Code 官方文档给出的 CLAUDE.md 控制在 200 行以内的实践建议；Cursor 官方文档 "Keep rules under 500 lines" 与 "What to avoid in rules"——不要复制整份风格指南、不要罗列 agent 已知的常用命令、不要为罕见边界写指令、不要重复代码库里已有的内容）。
* **长任务的三种手段**：压缩（compaction）、结构化笔记（structured note-taking）、多 agent 架构，是业界应对"任务长度超出上下文窗口"的标准做法（依据：同 Anthropic 工程博客）。
* **污染来源可枚举**：会话里除"任务需要的内容"外，还混有系统提示/输出风格、各层规则文件、工具定义、历史工具结果与文件内容、子 agent 的返回——**这些都占同一份注意力预算**，且多数与当前任务无关（依据：Claude Code 官方文档《Explore the context window》给出的"每类内容各占多少"的会话分解）。
* **上下文是成本**：上下文长度直接决定 token 开销与响应时延——长会话里一个一行的简单问题，仍会按整段历史计费（含缓存命中），故"读多了"既伤质量也伤成本（依据：Claude Code 官方成本文档 "Why usage climbs in a long session"）。

== 读取范围（最小必要）

* **读取按任务定界（L1）**：开始读任何东西前，先按用户要求定出本次任务**必须知道的最小信息集**（要改什么、要什么证据），只读该集合内的内容——不因"顺手、反正便宜、了解下没坏处"而多读；读完后自检"读的这些是否都用到了"，未用到即属越界读取。
* **定位优先，避免全库扫描（L1）**：文件名/路径已知、或可由 glob/grep 直接定位的文件，必须用**精确定位**（glob/grep/read 精确取文件）读取，禁止启动 explore 类子 agent 做全库扫描；禁止借修改小需求之机对整个项目做 code review/全量摸底。只在"位置未知、命名未知"的开放性查找时才用 explore，且派发指令须限定目标、不得要求"列出所有文件/读取全部源码/读取全部文档"（与必加载层"信息读取范围"一致，见 link:../core/execution.adoc[]「范围控制」）。
* **分层渐进、按需深入（L1）**：按"元数据 → 入口/目录 → 目标文件 → 必要片段"的层次递进读取，每层读完再决定是否深入，不一次读到底。命中检索结果时**先核对是否命中、命中位置是否真的是目标**，只读命中片段附近必要内容，不把整文件/整目录读入。
* **先查导航与索引，再读正文（L2）**：优先读项目的索引/总览（README、AGENTS 入口、`doc/` 索引页、规范调度器）来定位，再读对应正文；避免靠"逐个文件试读"摸索结构（有代码索引/符号跳转时优先用索引能力，其一跳定义胜过"grep + 读多份候选文件"）。
* **委派重型读取给子 agent（L2）**：跑测试（含按类别的测试执行，见 link:../stack/java-testing.adoc[]「测试分类与执行边界」）、读长日志、拉外部文档、大范围调研等**输出量大**的读取，优先委派子 agent（或先用 grep/head 等预处理只留关键行），让冗长内容留在子 agent 上下文里，只把结论/摘要带回——子 agent 自身可大量读取，返回的浓缩摘要通常仅千余 token（委派边界与调用量控制见 link:../general/collab.adoc[]）。
* **读取结果落盘、不靠记忆（L2）**：大范围检查与多步骤任务的进度、结论写入 `tmp/` 下临时文档（见 link:../core/execution.adoc[]「临时产物」），供后续步骤/后续会话读取；不要求把大段原文常驻上下文，也不靠"记得住"。
* **判断不了就问，不靠多读猜（L1）**：需求存在歧义、命名与位置均不确定时，先按"指令执行"提问澄清（见 link:../core/execution.adoc[]「指令执行」），不得用"把相关的东西都读一遍"来代替澄清；此时对照"用户明确声明要扫描整个项目"的解禁条件判断是否已被授权扩大读取范围。

== 长会话治理（上下文变长后的自保）

会话执行过多个任务后，历史上下文会污染后续简单任务：读入的历史文件、已放弃的方案、上一任务的结论都会挤占注意力预算，使简单任务被"过度解读"。处理原则是**不让上一个任务的上下文成为下一个任务的输入**：

* **任务切换即清洁上下文（L1）**：一次会话内切换**互不相关**的任务时，先把通用规范入口与项目自身规范**重新读取/重新确认**（规范是常驻前提，不是历史噪音），再开始新任务；不得依赖"上文已经读过规范""记得住约束"而带着旧任务上下文直接干新活；已放弃/已中断的任务上下文不得再作为判断依据（见 link:../core/execution.adoc[]「任务放弃与中断」）。
* **长会话降级自保（L1）**：发现当前会话已执行多个任务、上下文明显变长时，**主动降低读取范围**——简单任务按最小必要读取，不沿用上一任务的探索路径、不重复上一任务读过的文件；若一次简单任务仍需要读大量文件，先停下来说明"需要更多上下文的原因"，而不是直接开读。
* **结论交给持久文档与规范（L2）**：任务产生的**持久结论**写入代码注释/设计文档/规范/`tmp/` 记录（见 link:../general/doc-design.adoc[]），使其可被后续会话**重新读取**；不要把"结论要靠本次会话的上下文记住"当作机制——会话上下文是易失的、且越大越不可靠。
* **简单任务优先另起会话（L1）**：执行环境支持新开会话/清空上下文、且任务与当前会话历史无依赖时，简单任务**优先另起会话或清空上下文后再执行**，收益是确定的（简单任务在干净上下文下更准确、更快、更省）；判断依据是"本次任务是否需要历史的细节"——需要的是**规范与持久文档**（可重新读取），不是历史对话本身。执行环境不支持时，按上两条在会话内降级处理，并**在结果中说明"建议下次在干净会话中执行此任务"**。
* **阶段结论即时落盘（L1，长会话底线）**：每完成一个阶段/里程碑，**立刻**把结论写入持久位置（`tmp/` 记录、设计文档、代码注释），不等上下文逼近上限才整理——届时可能已无空间写清；这是"会话可随时被清空/压缩"的前提（见 link:../core/execution.adoc[]「临时产物」）。
* **超长任务的分段（L2）**：单任务确实跨越多轮、上下文逼近窗口上限时，按业界手段分段：先压缩（保留决策、未决问题、接口约定，丢弃冗余工具输出）或把阶段结论落盘，再继续；需要并行探索的调研类任务改用子 agent 隔离（见 link:../general/collab.adoc[]）。**压缩或清空前必须先把关键约定与结论落到持久位置**，避免"压缩完就丢"。

== 执行前自检（防越界）

* **读前自检（L1）**：动手读之前确认两点——①本次任务的目标与范围是否已明确（未明确先澄清）；②这批读取是否落在最小必要信息集内（不在则说明理由或缩小范围）。
* **读后自检（L1）**：读完后确认两点——①读到的内容是否都与任务相关（有无关内容即停止继续读）；②是否已具备完成任务的充分信息（不足时再按上节判断"该补哪一层"，而非扩大为全量扫描）。
