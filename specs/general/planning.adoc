= 任务规划规范（通用层，动手前加载）

本文件是**动手前**那一步的完整口径：**先查现状 → 先调研最佳方案 → 先定基线**，以及**大范围改动先确认**与**不得绕开既有体系另写一套**。必加载层（`specs/core/execution.adoc`）只放这三件事的底线，本文件承载展开。

== 动手前：现状与最佳方案

* **先查现状（L1）**：动手前先查清**现状**，不得凭印象或标题推断：
** **相关代码/文档/用例**在哪里、现在怎么运作——读你要改的那部分，不靠文件名与目录结构猜。
** **既有约定与既有流程**（含被视为过时、待废弃的部分）——现状结论须落到规划文档，并列出**核实方式**（读了哪些文件、跑了什么命令）；未核实项如实标"未确证"。
** **判定标准**：说不出"现状是什么、依据哪次读取/运行"就动手 / 把"看起来是这么回事"当现状 / 拿旧结论当现状——任一命中即不合规。
* **先调研最佳方案（L1）**：方案须先**调研最佳实践**再定，并列出**备选方案与取舍依据**（受益与代价：可维护性/可读性/性能/兼容性/改动面）；**已有业界标准/权威约定可循时优先引用**（不另造一套说法）。**不得**只给一个"能交差"的写法就动手。
* **需求先找参照物（L1）**："调整内容"一类需求（**新增与调整同属一类**，包括改规范条目、改文档、改设计、改实现）在定方案前**先找现成可参照的既有标准与更优设计**——按序检索：① **业界标准/权威约定**（ISO/IEC/IEEE、RFC、W3C、OWASP、POSIX 等，出处只写标准名/编号）；② **既有通行设计范式**；③ **本项目既有条目与先例**（见 `specs/general/coding.adoc`「既有实现与先例优先」）。**三条都要查、查到更优的设计就用更优的**（仍照原口述收须写明理由）：查到什么、据此取的是哪一条、为什么更优，**都要写进规划**，**不得只留结论、不留取舍**。**查不到**也要在规划里写明**查了哪几个方向、用什么方式查的**，并按 `specs/general/source.adoc`「无法确证时的正确做法」如实标"未确证"（**查不到 ≠ 可以不查**）。
** **判定标准（任一命中即不合规）**：① 方案里说不出参照物与检索动作（只写"已调研最佳实践"而无查了哪个方向、取的是哪一条）；② 有标准可循却自造一套说法；③ 查到有更优设计却仍按原口述照收、且未写明理由。**收的是哪一条**（现成标准、通行范式、本项目先例，还是与既有条目归并）同样须写进规划。
** **依据**：ISO/IEC/IEEE 12207（软件生命周期过程：先调查可用的既有方案再实现）、ISO 10007（配置管理与变更控制）。
** **判定标准**：只按"能跑"直接落地方案、无方案比对 / 方案不写取舍依据 / 对既有做法视而不见——任一命中即不合规。
* **规划落盘后才动手（L1）**：把现状、选定方案（含被否方案与否决理由）、执行步骤、验证方式与**基线**一并落到磁盘（设计文档或 `tmp/` 临时文档）；执行中偏离规划先改规划再继续。

=== 要改的那一处是否已实际读过（改动面按处读）

* **改动面按处读（L1）**：**动手改文件时，先读该文件里要改的那一处**——本条的核对对象是**要改的那一处现状**（全文读到够用即可、与本次改动无关的部分不必读；"读到多少算够"是执行动作，不进本条）。**判定标准（任一命中即不合规）**：① 未读取目标处即按其**记忆中的内容**写入（本仓库实证：该处已被改过，按记忆写入把本地内容覆盖掉）；② 以"可能已经改过了"为由跳过读取；③ 读取的范围与本次要改的位置对不上（读的是同一文件里与本次改动无关的段落）。**边界**：本条只管**要改的那一处**——读取范围的最小必要仍按 `specs/core/execution.adoc`「范围控制」判定，**不得**被本条读成"每个文件都要通读"；本条在**必加载层**与**自检清单**各有一处落点（`specs/core/execution.adoc`、`specs/general/self-check.adoc`）。

== 不得绕开既有体系另写一套

* **默认改在既有实现上（L1）**：能就地承载就改既有（归并去重、就地扩展），**不得**因为"新写更快"而另起一套——同一件事变成两套实现/两套配置/两套文档后，字段增删只改一处、行为与校验规则各自漂移，且后来者不知道该以哪套为准。
* **允许另写一套的三个条件**（须在规划里写明属哪一条，缺一即不合规）：
** ① 既有实现**确实无法承载**需求——须写明**无法承载的判据**（是缺能力、还是只是你没找到用法）。
** ② 既有实现**已被用户确认废弃/计划移除**——是否废弃**由用户认定**（见下「大范围改动先确认」）；"这段看起来没人用了"不构成理由。
** ③ 新方案**已被证明优于**既有实现且**明确取代**它——须同时处置既有实现：迁移全部调用方、删除既有实现（或按其项目规范的废弃口径标注并约定移除时机），**不留两套并存**。
* **处置既有实现是这套动作的一部分**：按上条①③另写时，旧实现**不得直接丢弃不管**；移动/重命名按 `specs/general/git.adoc`「文件移动与重命名」执行（`git mv`）。
* **判定标准**：另写一套却既不说明理由、也不处置既有实现 / 以"先让它跑起来"为由留下两套 / 把旧那套直接丢弃（含未识别为 rename 的 delete+create）——任一命中即不合规。

== 大范围改动先确认

* **大动之前先确认（L1）**：凡会**替换、废弃或改写既有流程/既有做法**（而非在既有实现上做增量修改）的改动，**动手前须向用户确认**。确认须一次性说清四问：
** **动哪段**：要替换/改写的既有流程或做法，及其影响面（谁在用它、有哪些调用方与文档/用例依赖它）。
** **为什么必须这样动**：现状与依据（用户要求、缺陷证据、标准/规范要求）。
** **不动会怎样**：保留现状的代价与风险。
** **确认后的动作**：确认即可继续、并按上节处置既有实现；**用户未确认前保持原状，不得先做一半**。
* **老旧废弃流程的兼容（L1）**：涉及**老旧/废弃流程**时——① **是否废弃只能由用户认定**，不得自行判断"已经没人用"；② 与旧流程的兼容要求按用户确认的结论执行（保留兼容 / 按版本化退场 / 直接移除）；③ **兼容性无法同时满足**时先停下确认（口径见 `specs/general/testing.adoc`「执行与验证」）。
* **判定标准**：未确认即替换、废弃或删改既有流程 / 把"这段看起来没人用了"当废弃依据 / 用户未确认就先把改动做了一半——任一命中即不合规。

== 动手前先定基线

**基线**＝动手前**既有行为**的可复核快照。没有基线，改完只能说"我觉得没破坏"，而不是"我核对过、没破坏"（ISO 10007：变更须基于可追溯的基线状态）。

* **基线的适用边界（L1）**：**先判改动性质、再决定这条要不要做**——性质判定与各档取值（含例外、**判不准时按更严的一侧**）**以 `specs/general/verify.adoc`「验证的适用边界」为唯一真源，本条不重列第二套定义**。**本节的其余各条只在该做的档位下适用**（不做基线的档位改后按该改动自身的机械判据核对，**不做基线 ≠ 不做验证**）。

* **扫描既有验证手段（L1）**：先列出该项目**声明的全部校验手段**——测试用例（单元/集成/专项/性能）、构建与编译、静态检查、规范/完整性校验脚本，并记录各自的**运行命令**与**当前统计结果**（用例数、通过/失败/跳过情况）。**运行环境也要一并钉定**——先取定项目声明的运行时/构建工具版本，基线**必须在声明环境下取得**（即「**运行环境须与项目声明一致**」，判据见 `specs/general/ci-cd.adoc`）。**判定口径**："存在测试"≠"测试被执行"，须能说出"跑了哪几套、各自统计是什么"。**怎么发现它们**：以**项目自身的声明**为准——项目规范（入口文件）/README 写明的命令、构建文件与 CI 配置里实际跑的任务、既有检查脚本、包的脚本段与实际目录结构；**不凭技术栈惯例假定**。
* **基线的完整性：手段与用例够不够用（L2，仅在该做基线时适用）**：扫描出的**清单本身可能不完整**——项目**声明的**手段不等于**够用的**手段，既有测试用例也**可能不全**（边界未覆盖、正反例缺一侧、步骤/前置条件缺失）。故**先按这些判据 review 既有用例**（`specs/general/testing.adoc`「用例设计」「测试有效性」），不是拿到命令就直接跑；本条的产物是**基线可信度声明**：能说出"复核了哪些角度与样本、哪些未覆盖、哪些未确证"。**怎么查（逐条可核对）**：① **手段缺不缺**——对照项目技术栈与该类改动的常规校验面逐项对；② **用例缺不缺**——按「用例设计」的生成原则核对覆盖：正常路径 / 边界（等价类与边界值、循环 0 次与 1 次与多次、空与空集合）/ 异常路径 / 正反例成对；③ **用例够不够强**——断言是否真的断在输出与行为上，编号与用例清单一不一致；④ **步骤与前置齐不齐**。**阈值与门槛**：**本次改动的直接相关面**须先补全再动手；**无关的存量缺口**如实记录、不阻断。**何时做**：在"先列清单"之后、"跑通留证"之前。
* **能跑通即跑通、并落盘留证（L1）**：既有验证手段完整可用时必须先跑通——**不能只跑最像验证的那一条命令**；结果须在动手前落到持久位置（设计文档、`tmp/` 规划文档、CI 日志），**不得只留在会话上下文里**——**留证不等于"必须提交"**，也不新增第二种交付口径（本地人工场景不提交、自动化场景随改动提交）。
* **不完整或本来就红时怎么办（L1，防把基线变成硬性前置）**：这三类都**不阻断动手**，但必须**如实记录并留证**，不得当作"没跑也通过"：
** **没有任何校验手段**：记录"本项目暂无既有校验手段"即可开工；**新功能/修复必须补上对应校验**，且不得据本条要求项目"先建一套 CI"。
** **手段不完整或环境不可用**：记录**缺什么、为什么**，能替代的用替代方式，**不把"没跑"写成"通过"**。
** **既有用例本来就是红的**：记录**红的用例清单与原因**作为基线（"红的还是红的、绿的不变红"）；本次任务本就是修红时按其目标推进，**不得**要求"先把所有红测试修绿才能动手"。
* **代价按项目规模说清（L2）**：跑之前先说明"要跑哪几套、预计多重"，**只跑本次改动相关的最小集也可接受，但须写明理由与未跑项**。
* **基线用于改完复跑（L1）**：改动完成后**复跑同一套校验**并与基线逐项比对：**基线里是绿的仍须绿、基线里红的不得变多**（新增校验须全绿）。**既有用例不得为迁就改动而改判**。
* **与"测试失败判定"的边界**：既有用例**本就过时**（人工改了代码但未同步用例）时以代码为准、更新用例——那是"修复过时用例"，不是本条的例外；本条禁的是**改动方为让自己的改动通过而单方面改判既有用例**。
* **判定标准**：**先判该不该做基线**（见本节「基线的适用边界」）——该做而不做（B 类未做基线、A 类命中大规模重构或大部分内容却未做）即不合规；**判为不做时**以"性质判定 + 依据"落盘为凭，不得只写"没做基线"。**该做的情形下**：未扫描既有校验手段 / 有完整可用的用例却不跑 / 跑了但不落盘留证 / 改动后不与基线比对——任一命中即不合规。**基线完整性一条（L2）另判**：本次改动的直接相关面的用例缺口未补全即动手 / 复核后说不出"查了哪些角度、哪些未覆盖、哪些未确证"→ 命中即不合规；无关的存量缺口如实记录即合规。

== 依据（标准名/编号）

* **ISO 10007**（配置管理：变更须有可追溯的基线状态）——基线条。
* **ISO/IEC/IEEE 29148**（需求须单一、无歧义、可验证、可追溯）与 **ISO/IEC Directives Part 2**（要求须可验证）——"现状与方案须落成可核对的判据"。
* **ISO/IEC/IEEE 29119-4**（测试技术）与 **IEEE 1028**（软件评审）——基线扫描与既有用例复跑的做法。
* **Semantic Versioning 2.0.0** 与 Martin Fowler《Refactoring》——"行为不变才叫重构/兼容"的定义。
* **ISO/IEC/IEEE 42010**（架构描述）与 **The Twelve-Factor App**（Dependencies）——"不得绕开既有体系另写一套"的架构面依据。
