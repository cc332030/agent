= 任务规划规范（通用层，动手前加载）

本文件是**动手前**那一步的完整口径：**先查现状 → 先调研最佳方案 → 先定基线**，以及**大范围改动先确认**与**不得绕开既有体系另写一套**。

必加载层（每次会话无条件加载）只放这三件事的**底线**（规则 + 判定标准 + 依据名）与其引用落点，本文件承载**展开**：条件判据、处置动作、留证落点与典型反例——按 link:../core/execution.adoc[]「分级与最高关注项」的分工，方法论与依据论证不进常驻层。

== 动手前：现状与最佳方案

本节与下两节同属**动手前**那一步：先查现状 → 先调研最佳方案 → 先定基线（顺序不可颠倒，必加载层见 link:../core/execution.adoc[]「先规划后执行」）。

* **先查现状（L1）**：动手前先查清**现状**，不得凭印象或标题推断：
** 相关代码/文档/用例**在哪里、现在怎么运作**——读你要改的那部分（读法见 link:../core/execution.adoc[]「范围控制」），不靠文件名与目录结构猜。
** **既有约定与既有流程**（含被视为过时、待废弃的部分）——现状结论须落到规划文档，并列出**核实方式**（读了哪些文件、跑了什么命令）；未核实项如实标"未确证"（见 link:self-check.adoc[]「知识边界」）。
** **判定标准**：说不出"现状是什么、依据哪次读取/运行"就动手 / 把"看起来是这么回事"当现状 / 拿旧结论当现状（改动可能已被推翻）。
* **先调研最佳方案（L1）**：方案须先**调研最佳实践**再定，并列出**备选方案与取舍依据**（受益与代价：可维护性/可读性/性能/兼容性/改动面）；**已有业界标准/权威约定可循时优先引用**（不另造一套说法，见 link:source.adoc[]「外部引用」）。**不得**只给一个"能交差"的写法就动手——"新写一套能满足需求"不等于"做得对"（见下「不得绕开既有体系另写一套」）。
** **判定标准**：只按"能跑"直接落地方案、无方案比对 / 方案不写取舍依据 / 对既有做法视而不见——任一命中即不合规。
* **规划落盘后才动手（L1）**：把现状、选定方案（含被否方案与否决理由）、执行步骤、验证方式与**基线**一并落到磁盘（设计文档或 `tmp/` 临时文档，见 link:../core/execution.adoc[]「先规划后执行」）；执行中偏离规划先改规划再继续。

== 不得绕开既有体系另写一套

* **默认改在既有实现上（L1）**：能就地承载就改既有（归并去重、就地扩展），**不得**因为"新写更快"而另起一套——同一件事变成两套实现/两套配置/两套文档后，字段增删只改一处、行为与校验规则各自漂移，且后来者不知道该以哪套为准。
* **允许另写一套的三个条件**（须在规划里写明属哪一条，缺一即不合规）：
** ① 既有实现**确实无法承载**需求——须写明**无法承载的判据**（是缺能力、还是只是你没找到用法）。
** ② 既有实现**已被用户确认废弃/计划移除**——是否废弃**由用户认定**（见下「大范围改动先确认」）；"这段看起来没人用了"不构成理由。
** ③ 新方案**已被证明优于**既有实现且**明确取代**它——须同时处置既有实现：迁移全部调用方、删除既有实现（或按其项目规范的废弃口径标注并约定移除时机），**不留两套并存**。
* **处置既有实现是这套动作的一部分**：按上条①③另写时，旧实现**不得直接丢弃不管**（历史与调用方一并受损）；移动/重命名按 link:git.adoc[]「文件移动与重命名」执行（`git mv`）。
* **判定标准**：另写一套却既不说明理由、也不处置既有实现 / 以"先让它跑起来"为由留下两套 / 把旧那套直接丢弃（含未识别为 rename 的 delete+create）——任一命中即不合规。

== 大范围改动先确认

* **大动之前先确认（L1）**：凡会**替换、废弃或改写既有流程/既有做法**（而非在既有实现上做增量修改）的改动，**动手前须向用户确认**。确认须一次性说清（四问，与 link:../general/verify.adoc[]「规范验证」的三视角共用同一份判断习惯）：
** **动哪段**：要替换/改写的既有流程或做法，及其影响面（谁在用它、有哪些调用方与文档/用例依赖它）。
** **为什么必须这样动**：现状与依据（用户要求、缺陷证据、标准/规范要求）。
** **不动会怎样**：保留现状的代价与风险。
** **确认后的动作**：确认即可继续、并按第 3 条处置既有实现；**用户未确认前保持原状，不得先做一半**（"先做一半再看"会把工作区留在新旧混用状态，比不做更糟）。
* **老旧废弃流程的兼容（L1）**：涉及**老旧/废弃流程**时——①**是否废弃只能由用户认定**，不得自行判断"已经没人用"；②与旧流程的兼容要求按用户确认的结论执行（保留兼容 / 按版本化退场 / 直接移除）；③**兼容性无法同时满足**时先停下确认（口径见 link:testing.adoc[]「执行与验证」）。
* **判定标准**：未确认即替换、废弃或删改既有流程 / 把"这段看起来没人用了"当废弃依据 / 用户未确认就先把改动做了一半——任一命中即不合规。

== 动手前先定基线

**基线**＝动手前**既有行为**的可复核快照。没有基线，改完只能说"我觉得没破坏"，而不是"我核对过、没破坏"（ISO 10007 配置管理与变更控制：变更须基于可追溯的基线状态）。

* **扫描既有验证手段（L1）**：先列出该项目**声明的全部校验手段**——测试用例（单元/集成/专项/性能）、构建与编译、静态检查、规范/完整性校验脚本等，并记录各自的**运行命令**与**当前统计结果**（用例数、通过/失败/跳过情况）。**判定口径**："存在测试"≠"测试被执行"，须能说出"跑了哪几套、各自统计是什么"（见 link:verify.adoc[]「编译/运行验证」）。**怎么发现它们**：以**项目自身的声明**为准——项目规范（入口文件）/README 写明的命令、构建文件与 CI 配置里实际跑的任务、既有检查脚本、包的脚本段（如 `package.json`）与实际目录结构；**不凭技术栈惯例假定**（"某语言通常有测试目录"不构成"本项目有测试"）。
* **能跑通即跑通、并落盘留证（L1）**：既有验证手段**完整可用时必须先跑通**——**不能只跑最像验证的那一条命令**；**结果须在动手前落到持久位置**（设计文档、`tmp/` 规划文档、CI 日志等，按项目自身的临时产物与交付约定处理：本地人工场景不提交、自动化场景随改动提交推送，见 link:git.adoc[]）；**不得只留在会话上下文里**（会话可能被清空、压缩，届时"基线"无从核对）。
**留证的形态按项目自身的交付约定**：本地人工场景（不提交不推送）就把结果写成文件留在工作空间交人工看、自动化场景随改动提交推送——**留证不等于"必须提交"，也不新增第二种交付口径**（交付口径唯一落点见 link:git.adoc[] 与模板提示词的 `delivery` 片段）。
* **不完整或本来就红时怎么办（L1，防把基线变成硬性前置）**：这三类都**不阻断动手**，但必须**如实记录并留证**，不得当作"没跑也通过"：
** **没有任何校验手段**（无测试、无 CI、无静态检查）：记录"本项目暂无既有校验手段"即可开工；**新功能/修复必须补上对应校验**（测试缺口的补齐见 link:testing.adoc[]），且不得据本条要求项目"先建一套 CI"。
** **手段不完整或环境不可用**（缺依赖、跑不起来）：记录**缺什么、为什么**（命令与报错），能替代的用替代方式（如只跑可运行的那部分），**不把"没跑"写成"通过"**（判准见 link:verify.adoc[]「判准维度：严格执行 / 尽力而为」）。
** **既有用例本来就是红的**：记录**红的用例清单与原因**作为基线（"红的还是红的、绿的不变红"）；**本次任务本就是修红**时按其目标推进，**不得**要求"先把所有红测试修绿才能动手"。
* **代价按项目规模说清（L2）**：基线跑通与改动后复跑都要花时间，大项目的全量可能很贵——跑之前先说明"要跑哪几套、预计多重"，**只跑本次改动相关的最小集也可接受，但须写明理由与未跑项**（口径与 link:verify.adoc[]「编译/运行验证」的"不滥运行"一致）。
* **基线用于改完复跑（L1）**：改动完成后**复跑同一套校验**（与基线同一范围、同一命令）并与基线逐项比对：**基线里是绿的仍须绿、基线里红的不得变多**（新增校验须全绿）。**既有用例不得为迁就改动而改判**（除相关功能被显式移除，口径见 link:testing.adoc[]「执行与验证」）。
* **与"测试失败判定"的边界**：既有用例**本就过时**（人工改了代码但未同步用例）时以代码为准、更新用例——那是"修复过时用例"，**不是本条的例外**；本条禁的是**改动方为让自己的改动通过而单方面改判既有用例**（先改断言再让测试变绿）。
* **判定标准**：未扫描既有校验手段 / 有完整可用的用例却不跑 / 跑了但不落盘留证（只凭记忆说"通过"）/ 改动后不与基线比对——任一命中即不合规。

=== 依据（标准名/编号）

* **ISO 10007**（配置管理：变更须有可追溯的基线状态）——基线条。
* **ISO/IEC/IEEE 29148**（需求须单一、无歧义、可验证、可追溯）与 **ISO/IEC Directives Part 2**（要求须可验证）——"现状与方案须落成可核对的判据"。
* **ISO/IEC/IEEE 29119-4**（测试技术）与 **IEEE 1028**（软件评审）——基线扫描与既有用例复跑的做法。
* **Semantic Versioning 2.0.0** 与 Martin Fowler《Refactoring》——"行为不变才叫重构/兼容"的定义。
* **ISO/IEC/IEEE 42010**（架构描述）与 **The Twelve-Factor App**（Dependencies：显式声明、不重复）——"不得绕开既有体系另写一套"的架构面依据。
