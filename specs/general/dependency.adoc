= 依赖管理规范（通用层，跨语言）

适用于**所有语言、所有项目**的依赖（第三方库、框架、构件、工具、镜像）引入与升级。构建工具专属写法见 `specs/stack/` 对应文件（Maven 见 `specs/stack/maven.adoc`）；CI 中的版本固定见 `specs/general/ci-cd.adoc`；安全评估见 `specs/general/security.adoc`。

依据：Semantic Versioning 2.0.0、npm 的 `package-lock`/`npm ci`、Maven 的 `<dependencyManagement>`、Python 的 lock 文件与 PEP 508；The Twelve-Factor App 对显式声明依赖的要求。

== 引入依赖

* **先查再用，不重复造也不重复引（L1）**：引入前先确认项目**是否已有等价能力**（自有工具类、已引入的库），已有则复用；**不得为一个小功能引入大依赖**，也不得同一用途并存多个库（两个 JSON 库、两个日志框架）。
* **来源可信、版本固定（L1）**：依赖只来自官方/可信仓库，声明**明确的版本号或受控范围**，禁止 `latest`/快照/浮动标签。
* **传递依赖不直接使用（L2）**：不得直接使用仅由其他依赖传递带入的库（未在依赖清单中声明）；确需使用时须显式声明并说明理由。**多模块项目的模块间依赖不在本条范围**——模块已被（直接或间接）依赖时不得重复声明同一依赖，判定前先读模块间依赖的唯一视图（见 `specs/general/doc-design.adoc`「依赖关系文档（模块间依赖的唯一视图）」）。
* **版本范围从严（L2）**：版本范围越窄越好；生产依赖优先精确版本或最小兼容范围，不用大范围通配（`*`、空范围）。
* **依赖数量与体积克制（L2）**：评估引入收益与代价（体积、启动开销、攻击面、维护成本），不为省几行代码引入重依赖。

== 依赖冲突与统一

* **同一依赖全局唯一版本（L1）**：应用中同一依赖（含传递依赖）须解析到**唯一版本**；冲突时在项目层显式声明统一版本（Maven `<dependencyManagement>`、Gradle constraints、npm overrides、Python constraints），不得放任多版本共存导致运行期行为不一致。
* **依赖清单集中管理（L2）**：版本集中声明（BOM/父 POM/锁文件/依赖清单），不在各处散落硬编码版本；升级只改一处。
* **锁文件须提交并保持一致（L1）**：支持锁文件的生态须**提交锁文件**，构建时用**锁定模式**（`npm ci` 而非 `npm install`）保证可重现；锁文件与清单不一致时不得提交。

== 升级与废弃

* **升级前看变更说明（L1）**：升级依赖须先读其变更日志/发布说明，识别**破坏性变更**与行为差异，再评估影响面（调用方、配置、序列化兼容）——不得直接改版本号就提交。
* **升级小步进行（L2）**：跨大版本时按中间版本逐步升级，避免一次性跨越多个大版本造成问题难以定位。
* **废弃替代及时跟进（L2）**：依赖被废弃或长期不维护时，须评估替代方案并记录（状态标记）；项目自研的废弃 API 被内部调用时不强制迁移。
* **升级须验证（L1）**：依赖升级后须跑全量编译与全量测试；仅升级未验证的提交视为未完成。
* **版本变更的记录口径**：影响使用方的依赖/运行时/平台版本变化属 `specs/general/changelog.adoc`「应当记录」的一类；记什么、怎么写以该文件为准。

== 可重现与离线

* **构建可重现（L1）**：同一清单与锁文件在任意环境应得到同样的依赖树与产物；不得依赖本地已装好的全局包或私有缓存才能构建。
* **私有依赖走受控仓库（L2）**：内部/私有构件须通过受控仓库分发并声明坐标，不得用本地路径依赖（`systemPath`、`file:`）或手工拷贝。

== 包源（包仓库/镜像站）的选用

**适用面**：本节的"包源"指**下载依赖、构件、语言运行时或系统包**所经的仓库（包管理器配置的 registry / mirror / index）。**拉取这类内容的项目**——无论语言与工具——都按本节选源；**各语言/工具的具体推荐源地址在** `specs/stack/` 对应文件（如 `specs/stack/maven.adoc`「仓库与镜像」），本节只给**选源次序与判定标准**。依据（标准名/编号）：ISO/IEC/IEEE 25010（性能效率）、ISO 9241-110（可控、可预期）、The Twelve-Factor App（Dependencies）。**"先把源排成次序、再逐级降级"是本集合的判据化取舍**。

* **按次序选源、逐级降级，不得跳级（L1）**：选源次序（从先到后）：① **就近/平台内已优化的源**（云厂商内网源、任务所在平台已配置的流量优化源）；② **项目/使用者所在国家地区的主流公共源**；③ **地理上邻近的其他境外源**；④ **更远的境外源站**（先选有全球边缘加速的、再选跨洋直连源站）。**只有当上一级**在**当前环境实测取不到内容**（连不上、代理不到、报错、超时，且已按下面的判定核对过配置正确）才降级到下一级。**判定标准（任一命中即违规）**：未配置过任何源时**直接跳**到第③④级 / 上一级未实测不可用就换源 / 因"感觉慢"或"以前在别处失败过"就换源（**慢不是不可用**）。
* **先实测可用再启用、一次配置到位（L1）**：**动手构建/安装前**先对候选源做一次**真实请求**（取一个确定存在的包/索引并看返回是否成功；配置后再跑一次真实取用确认），不得只凭地址形态或文档描述就假定可用，也不得"边构建边撞"。**换源要一次配置到位**（写进项目/用户/构建工具的配置或 CI 的装配步骤），**不得**在每一轮里反复重试同一个源。**判定标准**：出现"每轮都重试/每次都临时传源参数"或"未实测就把源当作可用"——命中即违规。
* **不得覆盖引用方既有配置（L1）**：项目或环境**已配置过**包源时**一律沿用**，不得为"用推荐源"而覆盖、重配、追加互相冲突的配置；**只有在"未配置过任何源"时才动手配置**（逐项看过构建工具配置文件、包管理器配置、环境变量、CI 装配步骤，确认都没有才算）。**推荐源不是强制源**——用户/项目声明的源永远优先。
* **判可用性要取确定存在的产物（L1）**：镜像站上常见"目录根返回 404、按包名取却 200"的形态（如某些镜像的 npm 目录）——判可用性须取**一个确定存在的包/构件**，不得只请求站点根或目录根；**单次采样不构成结论**（见 `specs/general/testing.adoc`「性能测试」）。
* **实测取值与条件须可复核（L2）**：实测的取值与条件（哪个源、什么环境、实际结果）须如实记录——**结果须可复核**，使后人能自行重取判断"这条推荐今天还成不成立"。
