= 依赖管理规范（通用层，跨语言）

以下规范适用于**所有语言、所有项目**的依赖（第三方库、框架、构件、工具、镜像）引入与升级。构建工具专属写法见 `specs/stack/` 对应文件（如 Maven 见 link:../stack/maven.adoc[]）；CI 中的版本固定见 link:../general/ci-cd.adoc[]；安全评估见 link:../general/security.adoc[]「依赖与供应链」。

依据：语义化版本与锁定（Semantic Versioning 2.0.0、npm 的 package-lock/`npm ci`、Maven 的 `<dependencyManagement>`、Python 的 lock 文件与 PEP 508 依赖声明）；十二要素应用对显式声明依赖的要求。

== 引入依赖

* **先查再用，不重复造也不重复引（L1）**：引入前先确认项目**是否已有等价能力**（自有工具类、已引入的库），已有则复用；**不得为一个小功能引入大依赖**，也不得同一用途并存多个库（如两个 JSON 库、两个日志框架）。
* **来源可信、版本固定（L1）**：依赖只来自官方/可信仓库，声明**明确的版本号或受控范围**，禁止 `latest`/快照/浮动标签（依据见 link:../general/security.adoc[]「依赖与供应链」）。
* **传递依赖不直接使用（L2）**：不得直接使用仅由其他依赖传递带入的库（未在依赖清单中声明）；确需使用时须显式声明并说明理由，避免上游升级后被动失效。
* **版本范围从严（L2）**：版本范围越窄越好；生产依赖优先精确版本或最小兼容范围，不用大范围通配（`*`、空范围），避免不可控升级。
* **依赖数量与体积克制（L2）**：评估引入收益与代价（体积、启动开销、攻击面、维护成本），不为省几行代码引入重依赖。

== 依赖冲突与统一

* **同一依赖全局唯一版本（L1）**：应用中同一依赖（含传递依赖）须解析到**唯一版本**；冲突时在项目层显式声明统一版本（Maven `<dependencyManagement>`、Gradle constraints、npm overrides、Python constraints），不得放任多版本共存导致运行期行为不一致。
* **依赖清单集中管理（L2）**：版本集中声明（BOM/父 POM/锁文件/依赖清单），不在各处散落硬编码版本；升级只改一处。
* **锁文件须提交并保持一致（L1）**：支持锁文件的生态（npm/pip/poetry 等）须**提交锁文件**，构建时用**锁定模式**（如 `npm ci` 而非 `npm install`）保证可重现；锁文件与清单不一致时不得提交。

== 升级与废弃

* **升级前看变更说明（L1）**：升级依赖须先读其变更日志/发布说明，识别**破坏性变更**与行为差异，再评估影响面（调用方、配置、序列化兼容）——不得直接改版本号就提交。
* **升级小步进行（L2）**：跨大版本时按中间版本逐步升级，避免一次性跨越多个大版本造成问题难以定位。
* **废弃替代及时跟进（L2）**：依赖被废弃或长期不维护时，须评估替代方案并记录（状态标记）；项目自研的废弃 API 被内部调用时不强制迁移（见 link:../general/coding.adoc[]「警告与弃用」）。
* **升级须验证（L1）**：依赖升级后须跑全量编译与全量测试；仅升级未验证的提交视为未完成。
* **版本变更记入 changelog（L1）**：影响使用方的依赖/运行时/平台版本变化须记入统一 changelog（含兼容性取舍），撰写口径见 link:../general/changelog.adoc[]「应当记录」。

== 可重现与离线

* **构建可重现（L1）**：同一清单与锁文件在任意环境应得到同样的依赖树与产物；不得依赖本地已装好的全局包或私有缓存才能构建。
* **私有依赖走受控仓库（L2）**：内部/私有构件须通过受控仓库分发并声明坐标，不得用本地路径依赖（`systemPath`、`file:`）或手工拷贝（依据见 link:../general/verify.adoc[]「编译/运行验证」中「外部资源禁止本地下载引用」条）。
