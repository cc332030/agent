= 规格规范（通用层，定需求与写文档时加载）

适用于**任何语言、任何项目**：把"这次要做成什么样"从口头需求落成一份**可判定的规格**，并划清它与设计、用例、入口文档的边界。设计文档与信息归属见 `specs/general/doc-design.adoc`；文档承载与写法见 `specs/general/doc.adoc`；用例设计见 `specs/general/testing.adoc`；动手前的现状、方案与基线见 `specs/general/planning.adoc`。

依据（标准名/编号）：ISO/IEC/IEEE 29148（需求须单一、无歧义、可验证、可追溯）、ISO/IEC/IEEE 12207（先定需求与验收、再实现与验证）、ISO/IEC/IEEE 42010（方案与取舍须留记录）；验收条件的书写形态参照 Gherkin（Cucumber 的 Given/When/Then，**业界约定、非标准**）。**"规格只到行为面、按规模分档、默认只服务本次任务"是本集合的判据化取舍**——上述材料只给"需求须可验证、可追溯"的下限，**未**规定规格写到哪一步，也**未**规定小改动要不要写规格。

== 本文件的字典（本文件使用的名称，定义写在本文开头）

[[term-spec]]
**规格**：用自然语言写的、以**行为**为对象的产物（或其一组），说明**要什么、为什么**，并给出**可判定的验收条件**；不含实现方案。

[[term-acceptance]]
**验收标准**：针对规格里某一条要求**可判定**的条件——前置状态、动作、预期结果三样能写清，照着执行能得出"满足"或"不满足"。

[[term-spec-depth]]
**规格深度**：这份规格**留多久**——只服务本次任务（first）、任务结束后继续作为该功能的维护依据（anchored）、或作为唯一手改产物而代码由它生成（as-source）。

== 规格写到什么程度（内容与判据）

* **一条要求一项验收标准（L1）**：规格里**每一条要求**都要有对应的验收标准。写不出可观察结果的表述（"体验更好""尽量快"）不得作为要求进入规格，须改成能看见的事实（出现什么、多久内、失败时看到什么）。**判定标准**：抽掉验收标准后这条要求仍能被判"满足/不满足"——若不能，即这一条只是愿望、不是要求。
* **要求只写到行为面（L1）**：规格写**外部可观察的行为**——谁能做什么、输入给出什么、错误长什么样、边界怎么处理；不写实现方案：类与模块划分、表结构与索引、算法与依赖选型、内部接口签名。**判定标准**：规格正文里出现代码、内部类名、表名或库名，即越界——那些内容属设计（见下节）。
* **每条要求可定位、可被引用（L1）**：规格条目有**稳定标识**（编号或名称），任务清单、用例与提交说明按该标识引用它，使"这条要求实现到哪、由哪条用例验"可追溯。标识在**本规格内唯一**、不随重排变化。
* **不复制既有内容（L1）**：规格不复制项目里已有的定义、外部标准原文与既有文档正文，只引名称与落点（判据见 `specs/general/terminology.adoc`「数据字典」与 `specs/general/doc.adoc`「信息密度」）。规格是最容易被写"厚"的产物：一旦它重复代码与既有文档，同一件事就有两处来源，改一处必漏另一处，读者也不再知道该以哪一份为准。
* **一条要求一句说完（L1）**：规格按**条**写、不按**篇**写——每条要求用一句能一口气读完的话写完（前置、动作、预期落在同一句里），条目之间不互相复述。写不下时它已不是一条：要么其实是多条要求（拆开），要么夹带了方案与论证（移走，那些属设计文档与依据）。**取值**：单条要求以**一句**为形态、**不许跨段落**；完整规格档的完成度按**要求条数 × 每条一句**计，**不按页数与字数计**。**判定标准**：同一条要求跨了两段以上、或一篇规格的篇幅随改动的搜索与试错过程一起长起来（读者要靠跳读才点得出"要求是什么"），即属写厚。**处置方向是移动不是删**：按「规格的处置与去向」把方案与论证并入设计文档、把结论并进入口文档，要求本身一条不减少。

== 什么时候写规格（按规模取，别拿大锤敲钉子）

* **先按改动性质分档（L1）**：三档取值——**免规格**：一处行为改动，需求本身已把输入、预期结果与影响面说清；**轻规格**：跨文件或跨模块、行为有歧义、存在多方取舍——写一份短规格并附验收标准，落点可以就是任务单正文（不新开文件）；**完整规格**：新功能或新模块、要交给别人或另一个执行者做、产出被多个下游消费（用例、接口、界面）。**判定标准（任一命中即不合规）**：① 免规格档却新开了规格文件；② 完整规格档却只有一句需求，缺口由执行者自行推断补上；③ 把"文档先行"读成"每件事都要新开一份规格文档"；④ **写成一本说明书**——要求条数没变，篇幅却翻了几倍（同一条要求跨多段、方案与论证搬进规格）。四个方向的边界都是"要求"这一层，不是"文档"这一层。
* **档位由行为影响面判、不由改动体量判（L1）**：判据是"要不要改对外可观察的行为、这处行为有几个下游要跟着变"，不是"改了几个文件、多少行"。改十个文件而对外行为不变，仍在免规格档；改一处而对多端可见，按完整规格办。
* **落点先看既有载体（L1）**：先看项目有没有现成的规格载体（任务单正文、需求阶段文档、既有设计文档里"适用范围"一节）；能就地承载就写在那里，不另起一套（判据见 `specs/general/planning.adoc`「不得绕开既有体系另写一套」）。文件形态与命名按项目自身的文档规范取。

== 规格的维护深度（默认只服务本次任务）

* **默认取 first（L1）**：规格只服务本次任务——写完据此实现与验证，任务结束时按下节处置它的去向，不默认留下一份长期维护的规格。**理由**：长期留存却不承担"行为变了就同步改它"的义务，留下的是过期的第二份说明书——读者按它读会与代码背离，比没有更坏。
* **anchored 须项目主动声明（L2）**：要把规格作为某功能的**长期维护依据**（行为变了就改规格、人与执行者都按它读）时，由项目在其自身规范里声明；声明后规格与实现**同一提交内更新**，与代码不一致的规格按缺陷处理。
* **as-source 默认不做（L1）**：不得把规格当作唯一手改产物、代码一律由它生成。它的前提是规格完备到能唯一确定代码，而这个前提在没有**能验证"生成结果与规格一致"的手段**时不成立——先落地只会得到两份真源：规格与手改补丁各说一套。要取这一档须项目显式声明，并按声明的范围执行。

== 规格的处置与去向（不留过期的第二份）

* **收尾时必须有去向（L1）**：任务完成时规格须显式处置——**并入**（跨类/模块级内容进设计文档、行为约束进用例、跨会话约定进入口文档）或**丢弃**（一次性、结论已由上述落点承载）。**判定标准**：交付里说得清"这份规格现在在哪、谁在维护它"，或说得清"它是临时的、结论已并入哪几处"；两份并存、各改各的即违规。
* **规格与用例一体（L1）**：验收标准就是用例的来源——写规格时同步定"哪条验收标准由哪条用例验"，规格改了用例随改；两者冲突时以正确规格为准、修代码或修规格并说明（口径见 `specs/general/testing.adoc`「测试以正确规格为准，不迁就源代码」）。
* **与设计双向可定位（L2）**：规格指向承载方案与取舍的设计文档，设计文档回指它服务的规格条目（取向同 `specs/general/doc-design.adoc`「类间关系与双向引用」）。

== 边界（不属本文件的范围）

* **不替代任务单与计划**：规格回答"要做成什么样"；执行步骤、基线与验证范围按 `specs/general/planning.adoc`。
* **不替代入口文档**：要跨会话继续成立的约定写进项目入口文档（`specs/general/entry-doc.adoc`），规格不承担这一职责。
* **不规定流程节点**：是否"先评审规格再开工"属项目自身流程，本文件不置评。
