= 入口文档的持久化规范（通用层）

适用于**任何项目**：入口文档（项目根目录的 `AGENTS.adoc` / `AGENTS.md`，下称"入口文档"）是**唯一会被后续会话与另开的新实例读到**的落点。它解决一个问题：**什么信息必须写进入口文档才不会随会话消失**。

本文件是这一判据的**唯一真源**——其他文件（公共入口的安装与取回口径、维护方落点、技术栈落点）只引用它、不复述其条文。反过来，"入口文档里具体要写哪几条路径、落点长什么样"属**安装流程的操作细节**，其唯一真源是公共入口的「安装与更新」「取规范到本地副本」两节（安装口径已并入入口），本文件不抄那几条路径的字面值。**这份文件说"该不该写"，入口的安装与取回口径说"写成什么样"**。

== 最小集（必须写进入口文档）

* **规范入口的读取方式（L1）**：写明规范入口地址（或本地落点）与"开工前必须先读取再执行"。后续会话据此重新加载规范，不依赖上一次会话读过。
* **安装与取回口径的落点路径、取规范脚本路径（L1）**：入口文档只放"这是什么、在哪"，**详述交给路径指向的文档**——除规范入口外，须给出**承载安装与取回口径的那个入口的路径**（要重装、要更新、要看完整的取法与退路时直接读它）与**取规范脚本的路径**（下一次怎么下载规范、怎么再取一次）。**判据**：另起一个新实例只拿到这个项目时，它按入口文档给出的这几条路径就能走到"装/更新/再取一次"的权威说明，不必回头问用户、也不必把安装须知整套抄进入口文档。
* **规范副本的检索路径（L1）**：本地副本落在**项目内**时写明它的路径（如项目内临时目录）；落在项目外（用户家目录下）时写明那一个路径。**那一处的具体取值以公共入口的取回口径为唯一真源**（本文件不抄路径字面值——两处都写即两处各自漂移）。**判据**：新实例按入口文档给出的路径**能直接定位到副本**，不必回头读安装过程、也不必按平台自己推。
* **取回与更新方式（L2）**：写明"怎么再取一次/怎么更新"（运行哪个工具、是否以远程为准、落点可否改）。缺这句时后续会话只能靠猜。
* **接替时的读取入口（L1）**：写明"上次做到哪、下一步做什么"的**唯一入口**是什么（`tmp/` 根那份索引、进度文件，或任务单评论），并写明它在什么情况下不存在、此时以什么为准。**判据**：另起一个实例只拿到这个项目时，按入口文档就能回答"上一轮停在哪、下一步做什么"，不必逐个目录翻 `PLAN.md`。**缺它时**，接替者手里只有"该写什么"、没有"从哪读起"——机制齐备而入口不明，退回逐个目录翻，多 agent 接替的时间与成本就白花。
* **跨会话须保留的本项目信息（L1）**：其余**不属于项目自身规范、但要跨会话/跨实例继续成立**的内容，一并写进入口文档（规范副本落点、本机与项目共用的约定、安装时使用的来源地址）。**判定标准**：出现"只有本次会话知道、下次得重问一遍"的信息，且它确实影响后续执行——即命中。

== 最小集与边界（写什么、不写什么）

* **项目自身规范优先（L1）**：项目自己写的规则写进**入口文档的项目自身内容**（或项目自己的规范文件），**优先于**通用规范、且**不因重新执行安装被改写或删除**。入口文档同时承载两类内容（入口占位 + 项目自身规则）时，重写入口占位**不得**动项目自身规则。
* **临时产物不放入口文档（L1）**：进度记录、运行日志、扫描中间结果、一次性结论属**临时产物**，按 `tmp/` 约定存放，**不写进入口文档**——否则入口文档会被易失内容灌满，真正的持久约定反而被淹没。**判据**：这份内容下次还要用吗？要＝持久；不要＝临时。
* **同一信息只写一处（L1）**：入口文档里的持久信息与项目其他文档、代码注释之间不得各写一遍；入口文档**写不下的详述交由它所指向的文档承载**，只留"这是什么、在哪"。
* **每次安装只动入口（L2）**：重复执行安装时，入口文档的**项目自身内容原样保留**；安装只更新它自己写入的那部分（入口占位与持久信息节），不替项目改写别的文件。

== 与"会话结束就丢"的分界（可核对的问句）

判断一条信息该不该落进入口文档，只问一句：**"另起一个新实例、只给它这个项目，它还缺什么才接得上？"**

* 缺规范入口、安装与取回口径的落点路径、取规范脚本路径与副本位置 → 进入口文档（上「最小集」前四条）；
* 缺某条本项目约定（如"本机的副本落点在哪、来源取哪个地址"） → 进入口文档的持久信息节；
* 只缺"上次做到哪一步、当时怎么查的" → 属临时产物，按 `tmp/` 约定处理，不进入口文档。
* 缺"上一轮做出的、而下一轮不该重做一遍的**结论**" → **不属临时产物**，须写进它的持久落点（代码注释、设计文档、规范、任务单评论），判据见「交接：什么必须扛过中断」。

== `tmp/` 索引的形态与并行取值（承接 `specs/core/execution.adoc`「tmp/ 的布局与命名」）

**判据本体在必加载层，本节只给形态取值**——`tmp/` 根那份索引长什么样、多任务并行时怎么取行。

* **索引一行一任务（L1）**：行的取值是"任务目录名 / 停在哪一步 / 下一步做什么 / 钉定的任务单"四项，**不写过程、不写结论**（结论按「交接：什么必须扛过中断」一节进持久落点）。判据是**不打开任何文件**就能回答"做完了没有、要不要接着做"。
* **并行按任务分，不按任务单合并、不按执行拆行（L1）**：一次任务一个目录，目录名带任务单标识，使索引行与目录**按名对得上**；同一任务单拆出的多个任务**各占一行**；同一任务的多轮执行**改自己那一行**，不新增行。判定标准（任一命中即不合规）：① 多个任务合写成一行（分不出哪一个做完了）；② 每一轮执行各加一行（索引退化成流水账）；③ 索引行与目录名对不上。
* **并行时不动别人的行（L1）**：只增、只改自己那一行，位置不承载含义。合并策略只合并两侧**各自新增的整行**，就地插一行等于两侧改到同一行。
* **同一任务单拆出的多任务仍共用一个分支与一个合并请求（L1）**：平台层取值见 `specs/platform/cnb.adoc`「分支与合并请求统一」，本节不另立。
* **索引要不要合并策略，由"索引是否进版本库"唯一决定（L1）**：本集合的 `tmp/` **不提交**（见 `specs/core/execution.adoc`「临时产物」），故索引**不存在版本库合并面**，**不配** `merge=union`——给一份不进版本库的文件配合并策略，属「配了但不是那些落点」。项目若另行决定把进度与索引**提交进版本库**，则须使索引满足 `specs/general/version-control.adoc`「冲突处理」的「只增不改的落点」那一档并在仓库配置里按路径声明——**那一条属并发档**（项目取常规档时按「有冲突须解决，不搁置」办，不要求声明合并策略）。**判据**：索引在版本库里＝要合并策略；不在＝不配。
* **接替时的读取次序（L1）**：索引在 → 先读索引，再看提交历史与任务单评论；索引不在（被清理过、换了机器或工作空间）→ 以**任务单评论**里钉定的对象与结论为准。**两者不一致时以任务单评论为准**——它是持久落点，索引只是同一台机器上的加速件。

依据（标准名/编号）：ISO/IEC/IEEE 29148（要求须可追溯、可验证）、ISO 10007（配置项须可辨识、变更受控）；跨多个上下文窗口的进度落盘与"会话开始时先读进度记录与提交历史"的业界做法见 Anthropic《Effective harnesses for long-running agents》与 Cline Memory Bank 官方文档（业界材料，非标准）；"可并行的任务＝改动不同文件、彼此无依赖"见 GitHub Spec Kit 的任务模板（业界约定）。**"索引不提交故不配合并策略""以任务单评论为唯一持久落点"是本集合的判据化取舍**。

== 交接：什么必须扛过中断

中断（会话被清空、工作区被重建、由一个 agent 换成另一个）之后，下一位接得上的前提是**"上一位已经确定下来的事"还在**——不是"上一位写到哪一步"，而是**"哪些问题已经不必再查、哪些路已经试过并否掉了"**。**判据问句：这件事**重做一遍**会不会得到不同结论？不会 → 它是结论，必须进持久落点**——否则下一位要重做一遍才知道同样的答案，代价就是"浪费时间与成本"。

* **接管"派发对象"的钉定信息必须持久（L1）**：本次任务钉的是**哪个 Issue/PR、哪个 commit sha、哪个分支**——这类信息决定后面所有结论能否复核。落点是**平台任务单的评论**（随任务单存活），**不得只写在 `tmp/`**。
* **不可重建的取舍必须持久（L1）**：被否掉的方案与否决理由、已试过并失败的手段（连同失败方式）、必须遵守的临时约定。**下一位看不到就会原样再试一遍**——这是接替里最贵的一类重复。
* **已核实的事实连同核实方式一并持久（L1）**：写"是什么"要带"怎么查到的"（读了哪个文件、跑了什么命令、哪个 sha）。只写结论时下一位无法判断它还成不成立，只能重查——**等于没省**。
* **边界**：本节只判**"该不该进持久落点"**；进哪个持久落点按内容归属定（代码约定进代码注释、跨会话的项目约定进入口文档、任务过程结论进任务单评论），**不把过程流水、逐条日志、进度百分比往持久落点搬**——那是 `tmp/` 的活。

依据（标准名/编号）：ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148（信息须落在可追溯的落点、要求须可复核，不得只存在于过程叙述里）、ISO 10007（配置管理与变更控制：配置项的持久化位置须明确）；"以入口文档为唯一持久落点、按最小集判定"是本集合的现场判据化表达。
