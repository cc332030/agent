= 执行前自检规范（通用层）

以下规范适用于**所有语言、所有项目**的 agent 执行过程。它解决一个最易被跳过的问题：**动手之前的自检**——"我读到的规则是不是真的读到并照做了"（与「规范是否被实际遵守」对应）。必加载层的执行原则（先规划后执行、范围控制、文档与代码同步）见 link:../core/execution.adoc[]，读取范围与长会话治理见 link:../general/context.adoc[]。

背景：本规范集合按"分类 + 懒加载"设计，**加载是规则生效的前提**——文件里写了某条"必须"，不等于本次执行已经加载并遵守了它。规范采用"必加载层 + 涉及即加载 + 兜底自检"的防线，本文件即为**自检关口**的完整定义，把"自检"从一句无判定标准的自觉要求，变成可核对的动作。

== 知识边界（先读）

* **不得顺口编造（L1）**：涉及具体事实——命令/参数/API 签名与版本、依赖与构件坐标、标准与文献的编号与名称、文件与路径、配置项与默认值、平台行为等——时，**不知道就明说"不知道"，并去查证**（读项目文件、运行 `--help`、查官方文档），不得凭印象生成看似合理的内容；宁可反馈"未确证"也不得输出假信息。
* **事实与推断分开（L1）**：输出中凡属**推断、猜测、未核实**的结论，须显式标注（如"据现有代码推断，未验证"），不得与已核实的结论混在一起当成事实陈述；据此动手前先核实。

== 环境能力自评（防"无机制还按有机制自评"）

本规范多处依赖**执行环境自身的能力**（能否开新会话/清空上下文、能否派发子 agent、能否保留历史上下文、能否读盘落盘、能否执行命令）。这些能力**不是每个环境都提供**（不同平台、不同版本、不同接入方式差异很大），而自检与"长会话治理"都以"按实际情况处理"为口径——**若不先判定能力，就会出现"无机制却按有机制自评通过"的自欺**（如环境不支持清空上下文，却照抄"已清洁上下文"；不支持子 agent，却记为"已委派"）。

* **先判定能力、再选择做法（L1）**：执行前先用**可核对的动作**确认相关机制的可用性，不得靠假设——能否新开会话/清空上下文、能否派发子 agent、能否持久化落盘、能否执行命令，各按其环境提供的入口实测或查看环境说明；**无法确认的能力一律按"不可用"处理**（宁可少依赖，不可空自评）。
* **能力缺失时按其降级路径执行、不记作已执行（L1）**：机制不可用时不得留空自评，须走规范给出的**降级路径**并**如实记录"能力不可用 + 实际做法"**——如长会话治理在无清空能力时按 link:../general/context.adoc[]「长会话治理」在会话内降级，并**在结果中说明"建议下次在干净会话中执行"**；子 agent 不可用时由主 agent 串行执行（见 link:../general/collab.adoc[]）。**不得把"做不到的机制"写成"已完成"**（属"不得编造事实"范围）。
* **机制可用的判据只有实测/环境声明（L2）**：不确定时按"不可用 + 降级"处理，并在完成汇报中写明未使用该机制的原因——留痕比空自评可信。

== 执行前自检清单（动手前逐项过）

以下清单**适用范围是"非平凡任务"**（**非平凡** = 需读完再动手的**多步骤任务**，包含文档、代码、脚本等任何产物——判定标准：能否不经阅读/规划直接一次做对；只有**单步、无需读取上下文即可确定**的改动才属平凡任务）。命中范围时**逐项检查**；任一项不通过（含不确定）就**不得继续往后做**，须先补齐：

* **① 指令（L1）**：是否已**逐字**理解用户要求，歧义是否已提问澄清？有无自我加戏、选择性执行或跳过某个字？
* **② 规范（L1）**：本次操作触发的规范是否**已实际加载**（不只是"知道有这条"）？加载判断依据见 `AGENTS_COMMON.adoc`「分类与懒加载」；只凭记忆、仅凭常驻入口文件行事即视为未通过。
* **③ 规划（L1）**：目标与范围是否明确、步骤是否已拆解、方案是否已定？**是否已落盘**（设计文档或 `tmp/` 临时文档）？规划只存在于上下文即未通过（见 link:../core/execution.adoc[]「先规划后执行」）。
* **④ 读取范围（L1）**：本次任务的**最小必要信息集**是否已确定？计划读取的内容是否都在集合内？是否用了精确定位（glob/grep/read）而非全库扫描？规则见 link:../general/context.adoc[]「读取范围（最小必要）」。
* **⑤ 证据（L1）**：要改的地方是否**已实际读过**（而非仅凭文件名、目录结构或印象推断）？本次要依据的事实是否已核实（对照「知识边界」）？
* **⑥ 影响面（L2）**：本次改动会波及谁（调用方、文档、测试、changelog、其他模块）？是否已列出、并纳入改动范围？
* **⑦ 收尾（L1）**：完成后如何验证？依据哪条命令的哪个统计结果？与用户要求一一对照的核对表是否已备好？

== 过程自检（边做边核）

* **每步自检（L1）**：每个步骤完成后自检"是否达到了该步的预期"，不通过则先修再进下一步，不得"先做完后面再补"。
* **落盘（L1）**：计划、进度与阶段结论**即时写入持久位置**（`tmp/` 临时文档、设计文档、代码注释），不得只留在上下文里靠记忆——会话可能被压缩或清空（见 link:../core/execution.adoc[]「临时产物」、link:../general/context.adoc[]「长会话治理」）。
* **漂移处理（L1）**：执行中发现实际与规划不符时**先停下**，调整规划后再继续，不得边做边改方案（见 link:../core/execution.adoc[]「先规划后执行」）。

== 完成前自检（交付前逐项核）

* **对照原始要求逐条核（L1）**：回到用户原话**逐条**对照完成情况，不得凭"我记得做完了"；有条件时用核对表逐项勾选。
* **核对表逐项过（L1）**：按「执行前自检清单」的七项逐项复检，特别确认"未擅自扩大范围、未遗漏用户提到的任何一项"。
* **验证结果以真实统计为准（L1）**：不得用"应该没问题""看起来正常"代替实际运行结果（见 link:../general/verify.adoc[]「编译/运行验证」）。
* **未完成即如实说明（L1）**：存在未完成项、未核实项或无法验证项时，**显式列出**并说明原因，不得掩盖、不得用"已完成"笼统带过。

== 自检的记录与留痕

* 自检的**结果**（尤其"发现的问题"与"未核实项"）须在完成汇报中体现；属临时过程的记录写入 `tmp/`（见 link:../core/execution.adoc[]「临时产物」），**不得写入规范文件或持久文档**（自检过程不是规范内容）。
