= 验证规范（通用层，验证时加载）

== 验证与运行契约的落点

本文件即「验证与运行契约」的落点（含「运行契约」一节）：编译/运行验证、判准维度、验证的适用边界、效力等级、验证总纲、规范验证与运行契约均在本文件内。

本文件是**编译/运行验证、分步验证与规范验证**的单一落点。阅读顺序：先用「验证的适用边界」判定改动性质，再按「编译/运行验证」的「按需验证、不滥验证」定**验不验、验多少、哪些不必重验**，按「验证的效力等级」定手段与结论强度，按「验证总纲」「规范验证」执行，判"做到什么程度"用「判准维度」。

== 编译/运行验证

* **按需验证、不滥验证（L1）**：验证**只在必须有验证的地方做**——验证耗时（编译/构建/测试尤甚），把验证撒在每一步上只会拖长交付而换不来新判据。判定标准（逐项可核对）：
** **该不该验**：仅当**用户明确要求**、或**存在仅能靠运行/编译确认的行为**（如行为正确性、实时结果）时才执行；能从改动本身与其静态判据（编译期检查、类型、引用可解析）直接判定的，**不做运行验证**。
** **没做完就不验**：任务**尚未做完时不做阶段性验证**——半成品上的结果不构成交付判据；验证**收在本次改动的收尾**（最后一次须做），中间**只在有必要时**加（如方向性风险高、不可逆操作前、仅能靠运行确认行为），且须说得清"为什么这一步非验不可"。
** **能合就合**：多个待验证项**合并为一次执行**（一次构建/一次测试跑覆盖多项），**不得为每项单跑一遍**。
** **能简化就简化、能部分就部分**：验证范围**只覆盖本次改动的直接相关面**，**不做与其无关的全量验证**（全量只在改动确实波及全量时才做）；能用更轻的手段（只跑受影响的模块/用例、只做部分验证）就不上全量。
** **先信已验过的、不重复验**：前面**已经实际验过、且其后无改动**的部分**直接采信已有结果、不再重跑**——同一改动范围内的验证动作**每个只做一次**；须**重验**的只有三类：① 该部分**自身之后又被改动**、② 上一次验的**不是这份内容**（对象不同，如 sha 变了而采信对象与当前内容对不上）、或 ③ 上一次的**结论本就不成立**（未确证 / 不通过 / 只跑了一部分）。**单纯"又提交了一个 commit"不构成重验理由**——只看**该部分自身有没有变**。**判据**：能说出"哪一项采信了哪一次验证的结果、为什么仍然有效"；**说不出凭什么仍有效，即不属可采信**。采信**只接已有结果、不放过该做的验证**——收尾那次该做的仍须做（本条与下条「验证须覆盖项目的全部既定校验手段」同读）。
** **一次到位**：验证**攒到一处、一次做完**——"不得每改一个小点就重启构建/测试"与"何时才允许逐步验证"的完整口径见 `specs/general/context.adoc`「延后验证、一次到位」，本条不重列。
**运行输出须完整可读、不被截断**（怎么取到属执行动作，不写进规范）。
* **验证手法取"能出判据的最轻路径"（L1）**：本条的判据对象是**手法**（上与「能合就合」「能简化就简化」同向，那两条管**次数与范围**、本条管**每项怎么验**）——**它只改每一步的执行手法、不改覆盖范围**（「本步该不该做、做到哪一步为止」仍按上文与下条「验证须覆盖项目的全部既定校验手段」取值），也**不构成"先轻跑一遍、不通过再加码"的许可**（那是「一次到位」的违反，须一次就选对最轻且充分的路径）：**能承载该判据的更轻手段优先，不默认上重流程**——**能启动就够的不打包、能单点触发的不跑全链路、能取统计的不产出完整产物、能查接口/日志的不手点 UI、能跑单个用例的不跑全量**。判定标准（逐条可核，任一命中即不合规）：① **把手工作为唯一手段，而同一判据本可由更轻的自动/半自动手段取到**（该手段须**实际存在且本次可执行**，不得以"理论上能"充数）；② **用比基线更重的手段验同一件事**（基线已是更轻那一种、却改用更重的重跑一遍）；③ **为一项判据顺带跑完整链路**（打包、部署、发布、端到端回归等），而该判据并不依赖链路更下游的那一步。**判据本身没写明时**（如探索性验证），以**该功能对外可观察行为的最小集合**为判据，再按上述取值——不得以"判据没定"为由随手停在哪一步。**该走完整流程的两类例外**（此时重流程正是必要流程、不得被本条缩掉）：**① 被判据的正是那一道重流程本身**（打包流程、可执行产物、安装包、发布链路）——判据在哪一步，就走到哪一步为止（不必为验它再往链路下游走）；**② 更轻手段取不到该判据**——轻手段在这台机器、这个版本、这个形态上**实际不成立**（须先实际试过、并写明"试了哪个、卡在哪"，不得凭印象判"取不到"）。**依据**：测试层级由被测对象决定（ISTQB Glossary 的 test level / component 与 system 测试之分——同一判据不必在每一层各验一遍）；质量模型把时间行为与资源利用作为可度量质量属性（ISO/IEC/IEEE 25010 性能效率）；"最轻路径"与"判据在哪一步就走到哪一步为止"两条取值属**本集合按上述方向的判据化取舍**，外部材料未给"轻到什么程度"的明文规定。
* **需要看显示效果时，取那一个目标自身的画面、不接管用户的桌面（L1）**：判据是**"看着对不对"**（界面渲染、布局、文案、状态）时，**用户实际在使用这台机器**——任何"操作电脑"的动作（把窗口切到前台、移动鼠标、敲键盘、逐个点按）都会**抢走用户的输入焦点、打断他手上的事**；整屏截图则把用户的桌面（别的窗口、消息、私人内容）一并拍下来，既干扰又外泄，还很难看出"到底该看哪一块"。
** **取值**（逐条可核，按代价从轻到重取最轻的一条）：① **能不开界面就不开**——同一个判据能从接口、页面对象、DOM/日志、程序化断言取到时，走这条路（`{最轻路径}` 的"能查接口/日志的不手点 UI"即本级）；② **要开界面时，界面别落在用户眼前**——无头（headless）渲染、虚拟显示（如 Xvfb）、或应用自身的离屏/隐藏启动形态，**不抢占前台、不动用户输入**；③ **取那个目标自己的画面，不取整屏**——按窗口/进程/控件截图（合成器与系统 API 能取到**不在最上层、被别的窗口盖住**的那个窗口画面），或由浏览器抓**该页面/元素**的截图：**截的是目标，不是整个桌面**；④ **渲染单元测试/快照**作为可 diff 的判据形态（视觉回归）——取这条时按 `specs/general/doc-design.adoc`「图的文本源」同向处理：**判据是逐行可 diff 的文本源**，不把二进制截图当唯一判据。
** **判定标准（任一命中即不合规）**：① 为看显示效果而**把应用窗口切到前台、抢焦点、动鼠标键盘**，或逐个点按走查——判据本可由无头/离屏/程序化手段取到；② 交付里给的是**整屏截图**，而判据只需要其中一个目标窗口/页面；③ 同一判据**先手工看一眼、再跑自动手段**两遍（比基线更重，同 `{最轻路径}` 的判定标准②）；④ 把截图当**唯一**判据并用"我看着没问题"下结论（视觉判据须能复核：可 diff 的快照，或**取法可重放**——同一目标、同一尺寸/缩放、同一取画面路径执行第二次能拿到等价画面）。
** **该走完整流程（含真人交互）的两类例外**：① **被判据的就是『用户手动操作』这条路径本身**（快捷键、拖拽、系统级集成、真机/真实窗口管理器的行为）；② 无头/离屏/按窗口取画面在**这台机器、这个版本、这个形态上实际试过取不到**（写明试了哪个、卡在哪——如该应用无法离屏启动、系统不提供按窗口取画面的能力）。此时**才**接管桌面，且先说明为什么非这样不可。
** **边界（L1）**：本条**只管『判据怎么取』**、**不放宽"该不该验"**（同 `{最轻路径}`：覆盖范围不变，也不是『先手工看一眼、不通过再上自动』的许可）；**调试工具与自动化手段能代替的优先代替**——浏览器先走 DevTools 协议（无头、可按元素截图、可读 DOM/网络/控制台），桌面应用先走其自身的离屏/隐藏启动与按窗口取画面，『操作电脑』是**最后**一条路。
// 依据：ISO 9241-110（对话的可控与不干扰：系统不得打断用户当前工作）；ISO/IEC/IEEE 25010（可用性/性能效率——"看一次效果"的时间开销与资源占用须可度量）；ISO/IEC/IEEE 29119-4（视觉回归以可复核的判据为准）。"不接管桌面、只取目标窗口画面"这一取值属**本集合按上述方向的判据化取舍**。
* **要复用的验证场景归入测试源码，不得落成一次性脚本（L1）**：本条判的是**验证场景的归属**（它写在哪、下次还找不找得到），与 `{最轻路径}` 的分工是：那条管**每项怎么验**（手法轻重）、「按需验证」管**次数与范围**，本条只管**验法本身是留还是扔**。判据是一个问句：**这个场景以后还要不要再验一次？**
** **会重复出现的场景，写成测试用例**：凡是「改动后再验一次」「换个分支/换台机器再验一次」「下次回归还要再过一遍」的场景，一律写进**该项目的测试源码**——按分类、编号、文档注释与断言落在测试类里（形态见 `specs/general/testing.adoc`「用例设计」「测试文档」，各语言落点见 `specs/stack/<语言>-testing.adoc`），纳入项目声明的校验手段（见「验证须覆盖项目的全部既定校验手段」）。**不得**留在 `tmp/`、`/tmp`、命令行历史里的临时脚本、随手写的 `verify.sh`/`demo.py` 一类**一次性文件**里——它们跑完即散：下次验证要么找不到、要么照着印象**重新设计重写一遍**，同一场景于是每验一次就重写一次、越写越与代码脱节，也从不进入回归（**本条的立项理由即此**：用户指出"每次验证都重新设计重写"这件事本身就是失效形态）。
** **只有"一次性"才可留在临时产物里**：确属一次性的（复现一个不会再出现的现象、只对本机这一次环境有效的核对）按 `specs/core/execution.adoc`「临时产物」写入项目 `tmp/`，用完按清理口径处理；**判不准时按"会重复"处理**——写成用例的代价只是多一个测试方法，扔掉的代价是下次重写。
** **写进测试源码就进自动执行集合**：既有该被自动验证、又"只自己跑"这两件事不能并存——真的不该进任何自动阶段时，按该语言栈的「永不自动执行」那一类命名与配置落点（Java 为 `Playground`）表达，**不得**为此把它留在 `tmp/`。**既有的临时验证脚本按"随动迁移"处理**（碰到哪个改哪个、不发动全库改造，见 `specs/core/execution.adoc`「规范变更的存量处理」）。
** **判定标准（任一命中即不合规）**：① 同类场景**第二次**仍以临时脚本/命令行的形态重做了一遍，而项目已有一套它能落进去的测试校验；② 交付里出现**未纳入校验手段**的验证脚本，且该脚本验的就是本次改动的行为；③ 同一场景在测试源码与 `tmp/` 各有一份、此后**各改各的**（两处真源）。
** **边界（L1）**：本条**不要求**为一次性探索也写用例、也**不扩张**任何一处该不该验（该不该验仍按「按需验证、不滥验证」判）；它只要求**验过的东西有持久落点**。
// 依据：ISTQB Glossary 的 "regression testing" / "test case"（可重复执行的用例才是回归的载体）；ISO/IEC/IEEE 29119-4（用例须是可复用、可追溯的产物）；Beizer 的"农药悖论"（同一套用例必须持续可用、不断增补——散落的临时脚本连"同一套"都不成立）。
* **以真实结果为准（L1）**：不得仅凭命令 exit code 判断成败，须依据对应工具的实际统计结果（测试的 run/failures/errors/skipped 统计、构建的成功日志）判断；统计须**一步直接取到**——一次执行内同时得到统计结果，禁止"先运行、再单独读取报告"的两段式。
* **验证须覆盖项目的全部既定校验手段（L1，仅限收尾那一次）**：把项目**声明的全部校验手段**都跑到——编译/构建、配套测试（单元与各专项）、规范/完整性机械校验、静态检查；**与「按需验证、不滥验证」同读**：本条约束的是**收尾那次验证的覆盖面**（该跑的都跑到），**不是**要求每步都跑全套——中间阶段按「不滥验证」只做必要项、可部分可合并。**只跑主校验脚本、或只跑"最像验证"的那一条命令，都属验证不完整**。判定口径：**"存在测试"≠"测试被执行"**——须能指出"本次跑了哪几套、各自统计结果是什么"；**"被跑的那一套够不够用"是另一问**——手段与被跑用例**本身可能不完整**，**先按 link:testing.adoc[]「用例设计」review**、说明"查了哪些角度、哪些未覆盖、哪些未确证"，**本次改动的直接相关面**先补全。新增校验手段后须同步接进验证链（见 `specs/general/ci-cd.adoc`「校验链完整」）。
* **验证对象须钉定 commit sha（L1）**：分支名不是稳定标识。验证/复核前须**先取定具体 commit sha**并写明，在该 sha 上核对；**发现对象是"某分支的最新"时须先取得该分支当前指向的 sha 再核对**（不得用本地可能过期的引用；怎么取属执行动作，不写进规范）。
* **分步复核按需触发、不逐步骤复（L1）**：分步复核只在**方向性风险高**（一处判错会使后续全白做）、**不可逆操作前**、或**本步结果仅能靠复核确认**时才做；**不是"每步都要做一次复核"**——逐步骤跑隔离上下文复核会把验证成本乘上步数，且多数步骤在收尾验证里本就会一并覆盖。触发时**只复核本步涉及的部分**（不做全量），并与收尾那次**合并**（能由收尾验证覆盖的不单开）。判据：能说出本次有几步做了复核、为什么这几步非做不可；说不出的步骤即不该做。
* **运行环境须与项目声明一致（L1）**：一律用项目**声明的**运行环境（jdk1.8、python2 等），"换个版本也能跑通"不构成理由；声明环境不可得时如实说明并把结论标未确证，**不得记为通过**。判据见 `specs/general/ci-cd.adoc`「运行环境须与项目声明一致」。
* **外部资源必须实测可用（L1）**：引入外部资源（CDN/脚本/CSS/图片 URL、第三方依赖、远程文件）时须**实际验证其可用**（取值＝"已收到预期状态码"这一状态；怎么实测属执行动作，不写进规范），不得只凭版本号/文档推测路径存在；`latest`、`@latest` 等浮动版本可能解析到无对应产物的新版，须固定到经实际验证的具体版本。
* **外部资源禁止本地下载引用（L1）**：**未经用户声明**，严禁将外部资源、依赖下载到本地以本地文件方式引用；应使用链接或其他引用方式（如构建工具的依赖声明）。

== 判准维度：严格执行 / 尽力而为

L1/L2/L3 只答"**要求有多强**"，还须答"**执行到什么程度算做到**"——两者是两个轴。

* **严格执行（须逐次达成并给出证据）**：判据固定、结果只有「做到/没做到」二值，没做到即**不得声明完成**——如 `git mv`、引用须指向真实文件、破坏性操作先确认、最高关注项的存在性。**判定**：能否给出"本次是否达成"的核对动作（命令/取值/清单）。
* **尽力而为（须尝试、须说明、不记通过）**：判据依赖环境或第三方，做不到本身不构成违规，但**"不尝试"与"做不到却记成做到"都违规**——如兼容性测试中环境受限的场景、`IT` 依赖的外部环境不可用。**判定**：本次是否实际尝试了、是否如实写明"未执行/未达成 + 原因 + 替代做法"。
* **两者都必须留证（L1）**："未执行"与"执行通过"是两个不同结论，**不得混写**；对判准类型有疑问时按"严格执行"处理并补判据。
* **何时用（L1）**：凡新写一条含"必须/不得"的规则、或判断某条是否被遵守时，都要先判它属严格执行还是尽力而为。它与「验证的效力等级」的确定项/概念项**也是两个轴**（后者说"判据形态"，本条说"执行到什么程度算做到"）。
* **同一约束只能有一个判准（L1）**：同一件事不得在不同文件里出现两种判准。
* **常见误用（L1）**：把"环境不支持"直接当作结论而不尝试（应属尽力而为、须先试）；把"尽力而为"写成硬承诺；同一件事在不同文件里出现两种判准。

== 验证的适用边界（先判改动性质，再决定验证到什么程度）

判据只有一个问句（L1）：**"这次改动会不会被未知项目加载、会不会改变别人的行为？"**——会（或不确定）→ 按 B 走；明确不会 → 按 A 走。**不得因为"改动小"就降级**。

[cols="1,2,2", options="header"]
|===
| 改动性质 | 验证到什么程度 | 判据与依据
| **A. 代码类改动**（改代码、修缺陷、调参数；不触碰会被未知项目加载的公共内容） | **机械判据判过不过**——编译/构建通过、测试按实际统计通过即可交付；**不做**三视角、**不做**全局核对、**不设**复盘节点。**动手前**：**不做基线测试**，**例外**＝大规模重构、或本次会改动**大部分内容**（**移动/重命名不算**） | ISO/IEC Directives Part 2（有可验证判据时用判据说话，不叠加无判据的流程）
| **B. 规范类改动**（改动公共内容：规范条目、任务提示词、随规范分发的工具；或改动会被未知项目加载的任何产物） | **三视角深度验证**（①完整性 + ②有效性与认知质量 + ③接纳面，同一干净子 agent 一次读取、分栏列），且须**从全局核对**：这条规则要解决的失效现在还在不在、依据是否仍支持该条。**动手前**：**必须取得基线**，一条都不豁免 | IEEE 1028（软件评审）、ISO/IEC/IEEE 29148（可追溯）、ISO 10007（变更控制）
| **C. 不改内容的操作**（只改提交/历史的组织或文件路径、不改变工作区内容：压缩提交、只做重命名的提交） | **不做基线测试**；**用该操作自身的确定性判据核对，不重跑全量编译与测试**（判据＝该操作**确未改变工作区内容**这一取值；**怎么核属执行动作，不写进规范**） | 内容既然逐字节相同，重跑不会得到任何新判据（ISO/IEC/IEEE 25010 性能效率）
|===

* **先判"有没有改内容"、再进 A/B（C 优先）**：改动前后工作区内容**确未改变**时属 **C**，不重跑全量编译与测试——该判定**只认核心版本管理的差异检出结果**（怎么取属执行动作，不写进规范）。
* **"内容没变"不是"少核对"的借口（L1）**：C 省的是**重跑全量校验**，不是**核对**——该操作自身的判据一条都不能少、须逐条给出取值；**判据不满足即阻断交付**。差异检出结果一旦非空、或出现夹带改动，即不再属 C，须回到 A/B 按改动性质重判。
* **不得互串（L1）**：A 类任务不得自行升级为三视角 + 全局复核（过度验证）；B 类任务不得只跑机械校验就收尾（跳过验证）。**同一任务含两类改动时取**更严的一侧**（B）**，但只需对公共内容那一部分做三视角与全局核对，代码部分仍按 A 的机械判据核对。
* **边界同时管"动手前做不做基线"（L1）**：本节判出的性质**一并决定基线测试的做与不做**——上表每行的"动手前"一栏即该档的取值，**不另立第二套判据**；基线**怎么做**（扫描手段、跑通留证、复跑比对）见 `specs/general/planning.adoc`「动手前先定基线」。
* **不得另立一套验证体系（L1）**：项目已有的 CI、构建、测试、评审直接沿用，本节只规定"到什么程度算过"。
* **汇报须与可核对的事实一致，不得狡辩（L1）**：汇报里的每一项结论都须与**实际取值**一致——既不得用"核对项全绿""验证通过"一类笼统结论**顶替**对用户所问那件事的直接回答，也不得让汇报中的数字、清单与实际统计**对不上**。**判定标准（任一命中即不合规）**：① 汇报里的**数字与清单**（提交数、文件数、用例统计、改动清单等）与**实际统计**不一致——数字类结论须与实际取值同源，**写进汇报前须重取一次**，不得凭过程中任一时刻的印象填写；② 用"各核对项都通过"自证用户质疑的那件事**没发生**——核对项全绿只说明**被核对的那几项**成立，**不得推出"用户指出的不符不存在"**；用户给出与汇报相悖的观察时，**先复取值再回答**：重跑取值、指出分歧出在哪一处，**不得拿既有结论当辩词**；③ 用户指出的不符**成立**时，先更正汇报、再处理余下的事，不得先论证"自己没错"。**依据**：成文信息须可核验、报告与实际须一致（ISO 9001）；"核过的项全绿"与"被质疑的事没发生"是两个不同的命题（ISO/IEC/IEEE 29148——判定须可验证）。

== 验证的效力等级（按对象定手段与结论强度）

[cols="1,2,2,2", options="header"]
|===
| 验证对象 | 判据形态 | 可用手段与结论 | 失效模式与去向
| **确定项**（存在性、双向登记、引用可解析、格式与取值、构建与测试的实际统计） | 二值、可机械核对 | **判据本体验证**：机械校验按判据本身核对，不按引用形式近似；结论为**通过 / 不通过** | 近似式校验会漏报（判据坏了仍绿）；漏掉的判定点须逐个列出
| **概念项**（判据是否笼统、内容是否完整、机制在真实环境会不会发生、被未知项目加载后是否可控） | 开放、须语义判断 | **只能启发式复核**（三视角复核、换机器、换角度、换样本） | 换一个角度就可能查出问题，也可能永远查不出——故结论只到**"未发现问题"**，不能推出"没有问题"，**也不得当作阻断交付的条件**
|===

* **结论强度（L1）**：汇报与留证须按对象区分写法，**"未发现问题"与"验证通过"不得混写**——确定项写**通过/不通过**（可举判据）；概念项写**"已复核、未发现问题"**并列出已复核角度与样本。**把"复核过、没看出问题"写成"这条规范没问题"，属以启发式结论冒充已验证**。
* **交付是否可阻断（L1）**：**只有确定项的判据不满足才阻断交付**；概念项**不设阻断条件**——筛得出问题就修，筛不出就如实交付。
* **悬置（L1）**：概念项未发现问题不等于已确证——凡还没有确定性证据支撑的部分一律标记为**悬置**并写明理由与剩余风险。悬置**可与改动一并交付**（不阻断），但须逐项可枚举、可被后续证据收口；**不得把悬置项在汇总里写成通过项**。
* **手段的效力不对称（L1）**：机械校验只能核对确定性判据——它覆盖不到判据是否被压成口号、机制在真实环境发不发生、内容是否完整；概念项复核**发现的是"问题案例"、不是"没有问题"**。**降低漏报的办法是增加独立的核对角度与样本，而不是把复核结论当成确定性判据**。
* **留证形态：三态台账（L1）**：留证不得写成散文结论，须逐项成行、每条带**三态标签之一**——**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附未确证的原因与剩余风险），**三态各占一栏、不得合并**。**"查不出问题"与"没有做复核"须能分辨**。

== 验证总纲（回答"验证什么、怎么算过"）

规范类改动的验收只有一句"跑一遍检查"是不够的：**验证什么、每项怎么算过、标准出自哪里**若不写死，验证就会退化成"把现有脚本跑绿"，规则会在一次次维护中**慢慢脱离初衷**。三视角与其标准出处（只写标准名/编号）：

[cols="1,2,1", options="header"]
|===
| 视角 | 判定问题 | 标准出处
| **① 完整性** | **对照面：改动前后**——被改对象在改动前后是否**等价**（误删条目、把"必须+判据"降级成"要注意"、内容被搬到加载不到的位置） | ISO 10007（配置管理与变更控制）、ISO/IEC/IEEE 29148（可追溯）
| **② 有效性与认知质量** | **对照面：规范本体**——规则是否**说得对、说得清、跑得动、判得了、效力标得准**（判据不可判定、机制在真实环境不会发生、依据被删到无从追溯、写错受众、"验证通过"其实只是"跑完脚本"、把启发式复核冒充确定性验证） | ISO/IEC Directives Part 2、ISO/IEC/IEEE 29148、ISO/IEC/IEEE 25010、RFC 2119 / RFC 8174
| **③ 接纳面（未知项目加载可控）** | **对照面：引用方项目**——被未知项目加载后会造成什么可预见的影响（逐项只看"是否发现"，查不出不等于没有） | ISO/IEC Directives Part 2、ISO/IEC/IEEE 29148、ISO 9241-110
|===

* **验证按对象与改动性质取值（L1）**：①、② 适用于**每次规范改动**；③ 适用于**任何会被未知项目加载的公共内容**，其影响面/成本/可控性三维见下「运行契约」。
* **如何验证、验证对象不止规范文件（L1）**：会被执行的产物同样是验证对象——**任务提示词**（会被项目复制成指令执行）与**随规范分发的工具脚本**都须按三项一并核对。
* **"验证了什么"必须能枚举（L1）**：每次改动的汇报须**逐项**给出三个视角的结论（①逐条对照表、②按判据分类的问题清单、③按影响面/成本/可控性分类的清单），并**逐项标注效力等级与依据**。**只跑机械校验、说不出验了什么**不算验证。
* **防"慢慢脱离初衷"（L1）**：验证须回答"这条规则**当初要解决的失效**现在还在不在"（概念项：能查出一处"初衷已不成立"即确证有问题；查不出只说明未发现问题）。**凡只保住文本、保不住初衷的改动，视为验证未通过**。

== 规范验证（改完规范后的三视角复核）

* **三视角各一问（L1）**：**①完整性**问「对象在改动前后是否等价——谁少了一条要求？误删、降级、放错层都属不等价」；**②有效性与认知质量**问「它可被合规地执行吗——判据可判定吗？依据还在吗、是否说对了？机制在当前执行环境真会发生吗？放对层、加载代价在预算内吗？从属者加载得到吗？代价说得清吗？」；**③接纳面**按下「运行契约」三维逐维过。**同一个干净子 agent 一次做完（L1）**——同一份 diff、同一批受影响文件，一次读取、结论分栏列，不得因合并而混答。**每次验证都换一个干净上下文（L1）**：复核者须与发起改动者隔离，且不得复用上一次验证用过的上下文——**这一半只说"要换"**，"换"的通道判据、派发形式与降级路径的另一半在 `specs/general/review.adoc`「review 时的干净子 agent 复核（强制）」（两处互不替代）。只有 ① 无任何语义可判（纯错字/格式/引用目标存在性）时才可只跑机械校验、不起子 agent。
* **②的判据（L1）**：① **判据可执行**（每条 L1 有判定标准）；② **依据**仍在、且**说对了**（不得只验证"依据行还在"，还须核对引用的标准确实支持该条）；③ **机制真会发生**（依赖环境能力的机制须有缺失时的降级路径）；④ **读的形态**（执行侧只给"怎么走"——规则 + 判定标准 + 依据名；原因与取舍归思考/决策侧）；⑤ **放对层与体积**与**从属者可达**；⑥ **性能**（代价说得清——加载后的时延/token 开销、机制本身的成本须有可核对说法）。**典型可查项**：判据被压成"要注意"、"必须做到"却没有抓手也无降级路径、引用了一个并不支持该条的标准、把解释塞回执行侧条目、新条目未登记调度器或未定级。
* **③接纳面的判据（L1）**：逐项核对"未知项目加载后会怎样"——① **冲突与优先级**（是否写明以引用方项目自身规范为准、是否可能静默推翻其既有约定）；② **对引用方工作区的默认动作**（是否默认改动/格式化其文件、默认代为提交或清理临时产物）；③ **新增依赖与工具要求**（若有须有降级路径，且不得出现引用方看不到的私有脚本名/仓库结构）；④ **私有约定与假定**（是否夹带只在某些项目成立的假定）；⑤ **成本与体积**。
* **三视角都须留证（L1）**：① 留"逐条对照表"；② 留"问题清单"（每条带判据/依据/机制/形态/层级体积/性能中的哪一项 + 判定依据）；③ 留"接纳面清单"（每条带冲突/默认动作/依赖/假定/成本中的哪一维 + 影响与处置）。三视角都过才可提交，不通过须先修再复核。
* **派发须自带硬超时（L1）**：语义复核派给子 agent 时**必须设可判定的时限**，到点即视为失联并"**放弃 + 如实标悬置**"，不得无限等待；派发时优先选**一次性、边界明确、可超时**的形式。
* **执行者选择：强制同 Agent（L1，其适用面由平台层限定）**：三视角复核一律由与执行者**相同的 Agent**（同 Agent 身份、同入口、同调度器）承担；不得点名外部 Agent / 外部 NPC、也不得以"换个 Agent 更独立"为由换来源。**"由与执行者相同的 Agent 承担"不是平台无关的强制前提**。**适用面（L1）**：该强制**只在承载该任务的平台层写明该前提成立时**按强制判（CNB 落点见 `specs/platform/cnb.adoc`「评论唤起新实例」）；**平台不提供同 Agent 的子执行者时**，不得援引本条跳过复核、更不得把任务停在中间——按 `specs/general/collab.adoc`「协作方式」降级为发起方本人串行核对并标注独立性边界，或如实标悬置，**复核与交付不因此缺失**。
* **标准从哪来（L1）**：凡已有业界标准/权威约定的判定项，先引标准、不另造一套说法。本文件用到的对应关系：判据可验证性 → ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148；用语强度 → RFC 2119 / RFC 8174；变更控制与可追溯 → ISO 10007 与 ISO 9001；软件评审 → IEEE 1028；性能效率 → ISO/IEC/IEEE 25010；可用性与可控性 → ISO 9241-110。**只列与本条判据确有对应关系的标准，不得为"看起来有依据"堆砌**；没有可援引标准时才自定判据并写明理由。

== 运行契约

公共内容**不随某个项目的上下文生效，而是被未知项目加载**——看不到它的项目结构、既有项目规范、依赖与工具链。故"加一条规则"不止要问"这条对不对"，还要问"**它落到一个未知项目里会发生什么**"。三维逐维过：

* **① 影响面（L1）**：这条规则会改变引用方的哪些既有行为？**与引用方自身规范的冲突次序**是否写明（以引用方项目自身规范为准）；**不得出现"静默推翻引用方既有约定"的条目**——凡收紧/推翻既有做法者须显式授权（用户声明或引用方自身规范声明），并给出"不采用时怎么办"。
* **② 成本（L1）**：加载与遵守的代价是否说得清——**加载面体积**（每次会话都加载的部分应设可机械核对的上限，只写"要注意体积"不构成上限）、加载后的时延/token 开销、引入的依赖或工具链要求（含版本要求，且须给出不可用时的降级路径）；**不得以"不贵"含糊带过**（ISO/IEC/IEEE 25010）。
* **③ 可控性（L1）**：引用方是否能**预期、能关闭、能自行执行**——① **不得依环境自动动作**：不默认改动/格式化引用方文件、不默认代为提交、不默认清理其临时产物；② **不得让引用方依赖本仓库私有物**：条目不得引用引用方看不到的私有脚本名、仓库结构或私有约定；③ **不得阻断**：规则不得让引用方在正常路径上无法完成工作（无降级路径的硬性前置一律不合规）。
* **接纳面须留证（L1）**：新增/调整公共内容时，须在改动说明（提交说明或汇报）中逐维写明核对结论；**未核对不得计入验证通过**。
* 依据（标准名/编号）：ISO/IEC Directives Part 2（规范性文件引用现行文件、不作隐含要求）、ISO/IEC/IEEE 29148（需求须可追溯到干系人）、ISO 9241-110（交互原则：可控、可预期、不阻断）。

== 改完规范必做的五件事（机械手段必跑，干净子 agent 复核不可漏）

判据本体在上文各节，本节只给**执行顺序与不可省略项**。**每次改完规范，本节五件事一件都不能少**；"改动小""只是改了个词""用户没要求"都不构成跳过理由。

. **① 机械手段必须先跑、且跑全（L1）**：一律先跑项目声明的全部既定校验脚本与其配套测试，**全量扫描、不按"只查变更文件"取巧**；**报红就地修复、不得留红**（"不在本次范围"不构成理由）。**判定标准**：说不出"跑了哪几套、各自统计结果是什么"即未通过。**没有机械手段的项目**：如实记录并按本条的**要求**为新增内容补上可机械核对的部分，不得据此跳过。
. **② 干净子 agent 的语义复核不可漏（L1）**：机械手段只覆盖确定性判据，判据是否被压成口号、机制在真实环境会不会发生、被未知项目加载后是否可控**属语义判断**，故必须另起**干净上下文**的子 agent 复核（每次换干净上下文）。**"有了就忽略"**：项目规范里已写明该要求时按其执行、不重复写第二份；**"没有就加"**：**须补在项目自身规范里**，不在公共内容里（公共内容不写引用方看不到的落点）。
. **③ 三视角一并回答、一次读取分栏列（L1）**：复核按**①完整性 + ②有效性与认知质量 + ③接纳面**三视角**一并回答**、一次读取、结论**分栏列**（见上「验证总纲」「规范验证」）。
. **④ 复核要走"三态台账"、不得写成散文（L1）**：留证逐项成行、每条带三态之一——**通过**／**未发现问题**／**悬置**，**三态各占一栏、不得合并**（见上「验证的效力等级」）。台账随交付一并发布（提交说明或 PR 结论），发布前的完成前自检须把它填实——"要求写了、台账没填"与"没复核"同判。
. **⑤ 子 agent 不可用时的降级与留证（L1）**：不得跳过复核、不得换外部来源顶替——由执行者在本次执行内按同一判据串行核对，并如实标注独立性边界；仍不可行时如实标悬置、写明未覆盖的角度与剩余风险。**降级后交付照常**。

* **本节的边界（L1）**：**只对规范类改动（B 类）**成立——代码类改动不做三视角、不设复盘节点；同一提交含两类改动时取更严的一侧（B），但只对公共内容那一部分做三视角与全局核对。本节也**不新增验证阶段或产物**。
