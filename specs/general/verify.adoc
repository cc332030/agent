= 验证规范（通用层）

以下规范适用于编译/运行验证、多步骤任务的分步验证与**规范验证**。某技术栈的编译/测试验证细节见 `specs/stack/` 对应文件（如 Maven 的 surefire 统计见 link:../stack/maven.adoc[]）。

== 编译/运行验证

* 验证执行：编译/运行验证耗时较长，不滥运行——仅当确需验证（用户明确要求，或存在仅能靠运行确认的行为）时才执行；多个待验证项能合并时合并为一次执行，不逐项独立验证；运行命令时优先将完整输出重定向到文件（如 `mvn ... > build.log 2>&1`、`npm run build > build.log 2>&1`，`2>&1` 为 cmd/bash 语法，PowerShell 下请用 `*>&1` 或按 link:../core/execution.adoc[]「命令执行」约定选择对应 shell），避免终端/IDE 输出截断或命令中断后无法恢复而需重试；日志文件等临时产物按执行原则「临时产物」条目处理
* 以真实结果为准：不得仅凭命令 exit code 判断成败，须依据对应工具的实际统计结果（如测试的 run/failures/errors 统计、构建的成功日志等）判断；获取统计须一步直接到位——从重定向的日志文件中过滤统计行（同一命令内串联完成），一次拿到结果，禁止两段式"先运行、再提示后单独读取报告"的流程，也不得反复附提示性说明
* 外部资源可用性验证：引入外部资源（CDN/脚本/CSS/图片 URL、第三方依赖、远程文件等）时必须**实际验证其可用**——发起真实 HTTP 请求确认返回预期状态码（如 200），不得只凭版本号/文档推测路径存在。注意 `@latest`、`latest` 等浮动版本可能解析到无对应产物的新版（如改为 ESM 后不再提供 browser 产物），应固定到经实际验证的具体版本
* 外部资源禁止本地下载引用：**未经用户声明**（明确允许/要求下载），严禁将外部资源、依赖（CDN 脚本/CSS、第三方库、JAR/二进制等）**下载到本地以本地文件方式引用**——含工作目录及任何本地位置；应使用**链接**（URL 直接引用）或其他引用方式（如 Maven/npm 等构建工具的依赖声明）。确需下载到本地时须先获得用户声明同意

== 分步验证

* 分步验证：设计、开发、写用例测试等多步骤任务，每个步骤执行完须对涉及的部分做一次隔离上下文的 code review，确保每步正确——前面方向错了，后面做再多也是无用功

== 判准维度：严格执行 / 尽力而为（防"判准含混"）

上述 L1/L2/L3 回答"**要求有多强**"，但不回答"**执行到什么程度算做到**"——同一级别的条款有"判据固定、可逐次核对"与"判据开放、做不到不算违规"两种形态，混在一起就会出现两头落空：**把"尽力而为"的条款当硬指标承诺**（如"外部环境不可用时不得记为通过"被误读为"必须跑通所有 IT"），或**把"严格"的条款当尽力而为**（跑不了就跳过、不说明）。故补判准维度（依据：ISO/IEC Directives Part 2 对"要求须可验证、等级越高验证越严"的区分；ISO/IEC/IEEE 29148 对需求可验证性的要求）：

* **严格执行（须逐次达成并给出证据）**：判据固定、结果只有"做到/没做到"二值，没做到即**不得声明完成**——如 `git mv`、引用须指向真实文件、破坏性操作先确认、最高关注项的存在性。**判定**：能否给出"本次是否达成"的核对动作（命令/取值/清单）。
* **尽力而为（须尝试、须说明、不记通过）**：判据依赖环境或第三方，**做不到本身不构成违规，但"不尝试"与"做不到却记成做到"都违规**——如兼容性测试中环境受限的场景、`IT` 依赖的外部环境不可用、依赖上游修复的问题。**判定**：本次是否**实际尝试**了、是否如实写明"未执行/未达成 + 原因 + 替代做法"。
* **两者都必须留证（L1）**：严格执行给"达成证据"；尽力而为给"尝试记录与未达原因"。**"未执行"与"执行通过"是两个不同结论，不得混写**；对判准类型有疑问时按"严格执行"处理并补判据，不得借"尽力而为"降低既有约束的强度（本条不改变任何条款既有的级别与判定标准）。
* **常见误用**：把"环境不支持"直接当作结论而不尝试（应属尽力而为，须先试）；把"尽力而为"写成硬承诺（会在环境正常差异下频繁"看起来未完成"）；同一件事在不同文件里出现两种判准（同一约束只能有一个判准，见 link:../general/spec-lifecycle.adoc[]「级别变更与复盘」）。

* **何时用（L1）**：本节的判准维度答案"**执行到什么程度算做到**"，与 L1/L2/L3（"要求有多强"）是两个轴——**凡新写一条含"必须/不得"的规则、或判断某条是否被遵守时，都要先判它属严格执行还是尽力而为**（与「验证的效力等级」的确定项/概念项**是两个轴**：后者说"判据形态"，本条说"执行到什么程度算做到"，**常见但非必然**的对应是确定项多按严格执行、概念项多按尽力而为——**不得据此压在一条轴上**：确定项也可以被项目规定为尽力而为，此时须写明其留证形态）。**必加载层只留一句话与本节落点**：常驻层只放底线，见 link:spec-lifecycle.adoc[]「规范集合的自身重构」），完整判据在此处用到才加载。

== 验证的适用边界（先判改动性质，再决定验证到什么程度）

**为什么要有这一节**：验证机制本身也是会被加载、被执行的规则——**用错对象就是把不可控的验证义务强加给不需要它的任务**。规范里的验证要求分两类对象，此前没有一条边界把二者分开，于是出现两头落空：改一行代码被要求"三视角 + 全局复核"（把可控的事做成了不可控的流程），改一条规范却只跑了机械校验（把不可控的事当成了可控的）。故先给判据：**按改动性质取值，先判性质、再选范围**。

[cols="1,2,2", options="header"]
|===
| 改动性质 | 验证到什么程度 | 判据与依据
| **A. 代码类改动**（改代码、修缺陷、调参数；不触碰会被未知项目加载的公共内容） | **机械判据判过不过**——编译/构建通过、测试按实际统计通过即可交付；**不做**三视角、**不做**全局复核、**不设**复盘节点 | 依据：本文件「编译/运行验证」的"以真实结果为准"（有确定性判据的事，用判据说话；ISO/IEC Directives Part 2 要求可验证——已有可验证判据时不叠加无判据的流程）
| **B. 规范类改动**（改动公共内容：规范条目、任务提示词、随规范分发的工具；或改动会被未知项目加载的任何产物） | **三视角深度验证**（①完整性 + ②有效性与认知质量 + ③接纳面，同一干净子 agent 一次读取、分栏列；**效力等级与结论强度见下「验证的效力等级」**），**而且因为判据多是概念性、笼统、不可控的**，必须**从全局核对**：这条规则要解决的失效现在还在不在、依据是否仍支持该条（口径与依据见本文件「验证总纲」「规范验证」，留证与判准见 link:../core/priority.adoc[]） | 依据：概念性判据没有"跑一遍就知道"的确定性判据，只能靠语义复核 + 全局追溯（IEEE 1028 软件评审；ISO/IEC/IEEE 29148 可追溯；ISO 10007 变更控制）
|===

* **判据只有一个问句（L1）**：**"这次改动会不会被未知项目加载、会不会改变别人的行为？"**——会（或不确定）→ 按 B 走；明确不会（本仓库/本项目内部实现）→ 按 A 走。**不得因为"改动小"就降级**：改一条规范里的一个词也可能改变引用方行为，性质判据不看改动量。
* **不得互串（L1）**：A 类任务**不得**自行升级为三视角 + 全局复核（属过度验证：把可控的验证做成不可控的多步流程、增加无判据的环节）；B 类任务**不得**只跑机械校验就收尾（属跳过验证：机械校验覆盖不到判据是否被压成口号、机制在真实环境是否发生）。
* **同一任务含两类改动时按 B 走（L1）**：一次提交里既有代码改动又有公共内容改动时，验证范围取**更严的一侧**（B），但**只需对公共内容那一部分**做三视角与全局核对，代码部分仍按 A 的机械判据核对——**别把代码部分也拖进概念性流程**。

**验证与项目自身流程的关系（L1）**：验证范围是本规范给出的**下限与口径**，不是"项目必须另建的验证体系"——**不得**把本节的验证要求另立为项目的一个独立阶段/独立产物（那会多出一个没人维护的东西）；项目已有的 CI、构建、测试、评审直接沿用，本节只规定"到什么程度算过"（标准可从简，但**口径与留证要求不得省**）。

== 验证的效力等级（先判改动性质，再定验证手段与可信度）

**为什么要有这一节**：验证机制会被加载、被执行，**验证自己说错话的代价最大**——它会被用来推翻或认可别人的结论。此前"概念性判据没有确定性判据、只能靠语义复核"这个事实**只在论证里出现过，没有变成判据**：于是一方面把"复核过了我没看出问题"当成"这条规范没问题"（把复核的结论当依据，实际上只是没找到），另一方面又把它当成交付前置条件（**阻断**：找不到问题就交付不了；而找不到问题**本身没有判据**，交付于是卡在一件不可控的事上）。两类失效同源：**验证手段的效力没被定级**。故本节给判据：**对象有确定性判据（判据本体验证）→ 机械校验，结论可判对错；对象只有概念性判据 → 只能启发式复核，结论只到"未发现问题"**。范围取值见上「验证的适用边界」，本节只定**手段与结论的可信度**。

[cols="1,2,2,2", options="header"]
|===
| 验证对象 | 判据形态 | 可用手段与结论 | 失效模式与去向
| **确定项**（有确定性判据：存在性、双向登记、引用可解析、格式与取值、构建与测试的实际统计） | 二值、可机械核对 | **判据本体验证**：机械校验按**判据本身**核对（如"引用指向真实文件"用**文件存在性**核对），**不按引用形式近似**；结论为**通过 / 不通过** | 近似式校验（按引用形式而不是判据本身核对）会**漏报**（判据坏了仍绿）；漏掉的判定点须**逐个列出并归入常驻层体积预算**，不得以"能跑绿"代替
| **概念项**（无确定性判据：判据是否笼统、内容是否完整、机制在真实环境会不会发生、被未知项目加载后是否可控） | 开放、须语义判断 | **只能启发式复核**（三视角复核、换机器、换角度、换样本） | **换一个角度就可能查出问题，也可能永远查不出**——故其结论只到**"未发现问题"，不能推出"没有问题"**；**也不得当作可二值化的通过条件去阻断交付**；"已换过若干角度、仍是未发现"即可**如实交付并悬置**（见下"悬置"）
|===

* **结论强度（L1）**：汇报与留证须按对象区分写法，**"未发现问题"与"验证通过"不得混写**（判准见 link:../general/verify.adoc[]「判准维度：严格执行 / 尽力而为」）——确定项写**通过/不通过**（可举判据）；概念项写**"已复核、未发现问题"**并列出**已复核角度与样本**（换过哪些对照面、查过哪些位置）。**把"复核过、没看出问题"写成"这条规范没问题"，属以启发式结论冒充已验证**。
* **交付是否可阻断（L1）**：**只有确定项的判据不满足才阻断交付**（机械校验报错、构建/测试未通过、引用悬空等）；概念项**不设阻断条件**——它筛得出问题就修，筛不出就如实交付，**不得把"找不到问题"变成交付的隐性前置条件**（否则交付被钉死在一件没有判据的事上，只能靠反复复核假装推进）。**收尾时不必等到"互相认可"**：本规范只要求下面的"悬置"如实写明，不要求验证者与改动者就"有没有问题"取得一致（对外承诺是否可发、发不发由项目按自身风险口径决定，不在本规范的判据内）。
* **悬置与对外承诺（L1）**：概念项未发现问题**不等于已确证**——凡**还没有确定性证据**支撑的部分，一律标记为**悬置**并写明理由与剩余风险（如"机制依赖执行环境提供某能力，本环境已验证有降级路径；其余环境未验，悬置"）。**悬置可与改动一并交付**（不阻断，见上条），但须**逐项可枚举**、可被后续证据收口；**不得把悬置项在汇总里写成通过项**（"未核对""未确证"与"通过"三态不得混写）。
* **手段的效力不对称（这是验证自身的最大威胁），须如实声明（L1）**：机械校验**只能核对确定性判据**——它覆盖不到判据是否被压成口号、机制在真实环境发不发生、内容是否完整；概念项的复核**发现的是"问题案例"、不是"没有问题"**（查到一处即确证有问题，查不到不构成证明）。**降低漏报的办法是增加独立的核对角度与样本（换视角、换机器、换反例），而不是把复核结论当成确定性判据**；"换一个角度看就对不上"恰是概念项的常态，须按其效力如实标注，不得据此宣布"已验证无误"。
* **效力等级的标注与留证（L1）**：每条验证结论须标注它属哪一等级、依据什么判据（确定项 → 判据名与取值；概念项 → 已复核的角度与样本）。**没有按对象标注效力等级、或把启发式复核冒充确定性验证**，不算验证（口径见上「验证总纲」，留证形态见 link:../core/priority.adoc[] P2）。
* **留证形态：三态台账（L1）**：留证**不得写成散文结论**，须逐项成行、每条带**三态标签之一**——**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附未确证的原因与剩余风险），**三态各占一栏、不得合并**（"未核对""未确证""通过"三态不得混写的判据见上两条，本条只规定**留证产物形态**）。**"查不出问题"与"没有做复核"须在台账里能分辨**——这是把"靠自觉的留证"变成可核对产物的唯一办法；**产物形态可核对的项（行数、三态标签齐全、悬置必带原因）由维护规范集合的项目设机械防线**（公共内容里不写引用方看不到的私有抓手名）。

== 验证总纲（回答"验证什么、怎么算过"）

规范调整的验收只有一句"跑一遍检查"是不够的：**验证什么、每项怎么算过、标准出自哪里**若不写死，验证就会退化成"把现有脚本跑绿"，规则会在一次次维护中**慢慢脱离初衷**（最初为什么立这条没人再核对）。故本节把验收拆成**三个视角**，每个视角给出**判定标准**与**标准出处**（"有没有现成标准"的答案在此；出处只写标准名/编号、不附链接，见 link:../general/source.adoc[]）：

[cols="1,2,1,1", options="header"]
|===
| 视角 | 判定问题 | 不合格的典型症状 | 标准出处
| **① 完整性** | **对照面：改动前后**——被改对象在改动前后是否**等价** | 误删条目、把"必须+判据"降级成"要注意"、内容被搬到加载不到的位置 | ISO 10007（配置管理与变更控制）、ISO/IEC/IEEE 29148（可追溯）
| **② 有效性与认知质量** | **对照面：规范本体**——规则是否**说得对、说得清、跑得动、判得了、效力标得准** | 判据不可判定（无判定标准）、机制在真实环境不会发生、依据被删到无从追溯、写错受众（执行侧夹带解释 / 决策侧缺依据）、"验证通过"其实只是"跑完脚本"、**把启发式复核冒充确定性验证**（"我没看出问题"写成"没有问题"，见下「验证的效力等级」） | ISO/IEC Directives Part 2（要求须可验证）、ISO/IEC/IEEE 29148（单一/无歧义/可验证）、ISO/IEC/IEEE 25010（质量特性含性能效率）、RFC 2119 / RFC 8174（用语强度）
| **③ 接纳面（未知项目加载可控）** | **对照面：引用方项目**——被未知项目加载后会造成什么**可预见**的影响（概念项：逐项只看"是否发现"，查不出不等于没有，见下「验证的效力等级」） | 与引用方自身规范冲突时无优先级规则、默认替引用方改文件/格式化/提交、新增依赖或强制工具链、夹带项目私有约定、常驻体积不可控 | ISO/IEC Directives Part 2（规范性文件引用现行文件、不作隐含要求）、ISO/IEC/IEEE 29148（干系人需求）、ISO 9241-110（交互原则：可控、可预期、不阻断）
|===

* **验证按对象与改动性质取值（L1）**：三个视角是**口径**，实际验证动作按上表取值——①、②适用于**每次规范改动**（口径见「规范验证」）；③适用于**任何会被未知项目加载的公共内容**，且其**影响面/成本/可控性**三维由 link:context.adoc[]「运行契约」定式化核对。
* **验证对象按改动性质取值（L1）**：验证到什么程度须**先判改动性质**——代码类改动按「编译/运行验证」的机械判据判过不过，只有**涉及公共内容**（规范、提示词、随规范分发的工具）的改动才做三视角深度验证；判据与“不得互串”的边界见上方「验证的适用边界」（防过度验证与跳过验证两头失效）；**结论强度与可否阻断交付**见上「验证的效力等级」。
* **验证对象不止规范文件（L1）**：被加载后**会被执行**的产物同样是验证对象——**任务提示词**（会被项目复制成指令执行）与**随规范分发的工具脚本**（如临时产物清理脚本，会被项目远程执行）都须按①完整性 + ②有效性与认知质量 + ③接纳面三项一并核对；**不得只验证规范文本、把会被执行的产物漏掉**（它们出错同样直接伤到引用方）。
* **"验证了什么"必须能枚举（L1）**：每次改动的汇报须**逐项**给出三个视角的结论（①逐条对照表、②按判据分类的问题清单、③按影响面/成本/可控性分类的清单），并**逐项标注效力等级**（确定项＝判据与取值；概念项＝已复核的角度与样本），**"未核对""未确证""核对通过"三态不得混写**（判准见 link:../general/verify.adoc[]「判准维度：严格执行 / 尽力而为」）。**只跑机械校验、说不出验了什么**不算验证。
* **按对象判效力、不搞一锅端（L1）**：验证手段与结论强度按**对象有没有确定性判据**取值——有确定判据的（存在性、登记、引用可解析、构建与测试统计）用机械校验**按判据本身**核对、结论可判对错；只有概念判据的（判据是否笼统、内容是否完整、机制真不真、未知项目可控否）**只能启发式复核**、结论**只到"未发现问题"**，**不得把它标成"验证通过"、更不得当作阻断交付的条件**（判据、悬置与承诺口径见下「验证的效力等级」）。
* **防"慢慢脱离初衷"（L1）**：验证须回答"这条规则**当初要解决的失效**现在还在不在"（**这是概念项**：能查出一处"初衷已不成立"即确证有问题；查不出只说明**未发现问题**，不足以宣布"仍有效"）——新条目的初衷按「规范验证」留证、既有条目的初衷按 link:../general/spec-lifecycle.adoc[]「级别变更与复盘」定期复盘（含"规范验证"自身反复盘，见该节）。**凡只保住文本、保不住初衷的改动，视为验证未通过**。

== 规范验证（改完规范后的三视角复核）

> 口径：规范的**语义有效性不能由确定性校验覆盖**——`specs/` 是常驻上下文中的规则，判据是否被压成口号、机制在真实环境是否会发生、被未知项目加载后是否可控，**属语义判断**，故须另起**干净子 agent**（隔离上下文，不带改动方立场）复核（依据：IEEE 1028 软件评审；ISO 10007 配置管理的变更控制）。


**本节的效力等级（先声明，防"验证规范自身未被验证"）**：本节与「验证总纲」「验证的效力等级」「验证的适用边界」同为**概念项**——它们的判据是"机制在真实环境会不会发生、未知项目是否可控"这类开放判断，故**只能标"未发现问题"、不得宣称"已验证有效"**；本节自身的清理与失效由 link:../general/spec-lifecycle.adoc[]「级别变更与复盘」的定期复盘承担（含"规范验证自身也须复盘"）。

**结论强度（先记住，防把复核当依据）**：本节的三视角复核**属启发式**——它查得出问题（查出一处即确证），查不出**只得到"未发现问题"**；故它是**发现手段，不是判定依据**，**不得**当作"这条规范没有问题"的证据去替代确定性验证、**也不得**当作阻断交付的条件。逐维判据是"SOP 与查错清单"，不是"效力的提高"（口径与悬置写法见上「验证的效力等级」）。

**标准从哪来（先答"有没有现成标准"）**：凡是**已有业界标准/权威约定的判定项，先引标准、不另造一套说法**——本文件用到的对应关系是：判据可验证性 → ISO/IEC Directives Part 2（要求须可验证）与 ISO/IEC/IEEE 29148（单一/无歧义/可验证/可追溯）；用语强度 → RFC 2119 / RFC 8174；变更控制与可追溯 → ISO 10007 与 ISO 9001；软件评审 → IEEE 1028；性能效率 → ISO/IEC/IEEE 25010；可用性与可控性 → ISO 9241-110（出处写法见 link:../general/source.adoc[]）。**只列与本条判据确有对应关系的标准，不得为"看起来有依据"堆砌**（见 link:../general/source.adoc[]「外部引用（标准/文献/规范）」之"不得编造编号/名称/章条"）；**没有可援引标准时，才按本规范自定判据并写明理由**。这一"先查标准"的动作本身是提案校验第 3 步的判据（见 link:../general/spec-lifecycle.adoc[]「新增规范的提案校验」），不得跳过。

* **三视角各一问（L1）**：**①完整性视觉**（核对我方改动）问「**对象**在改动前后是否**等价**——谁少了一条要求？误删、降级、放错层都属不等价」；**②有效性与认知质量视觉**（核对规范本体）问「它**可被合规地执行**吗——判据可判定吗（①判据）？依据还在吗、是否**说对了**（②依据）？机制在**当前执行环境**真会发生吗？放对层且常驻代价在预算内吗？从属者加载得到吗？（③形态）？**代价说得清吗**——上下文/时延开销是否可控（④性能）？」；**③接纳面查**（核对被未知项目加载后的影响）按 link:context.adoc[]「运行契约」的影响面/成本/可控性三维逐维过（口径见该节）。**同一个干净子 agent 一次做完（L1）**——同一份 diff、同一批受影响文件，重复起子 agent 是重复读取与重复计费；**一次读取、结论分栏列**，不得因合并而混答（三者的对照面不同：改动前后 / 规范本体 / 引用方项目）。**每次验证都换一个干净上下文（L1）**：复核者须与发起改动者隔离，且**不得复用上一次验证用过的上下文**——带着上一轮的结论再看一遍，会只找“是否已改”而放过新问题，等于自己复核自己；跨轮次复用的结论**不得计为通过**。只有①无任何语义可判（纯错字/格式/引用目标存在性）时才可只跑机械校验、不起子 agent。
* **②的判据按"规范该怎么被写与执行"（L1）**：①判据可执行（每条 L1 有判定标准，见 link:../core/priority.adoc[]「分级定义」）；②依据（标准名/编号）仍在、且**说对了**——不得只验证"依据行还在"，还须核对引用的标准**确实支持该条**（link:../general/source.adoc[]）；③机制真会发生（依赖环境能力的机制须有缺失时的降级路径，见 link:../general/self-check.adoc[]「环境能力自评」）；④读的形态（执行侧只给"怎么走"——规则 + 判定标准 + 依据名；原因与取舍归思考/决策侧，见 link:../general/spec-lifecycle.adoc[]「同一条规则有两种读法」）；⑤放对层与体积（常驻层只放底线，见 link:../general/spec-lifecycle.adoc[]「规范集合的自身重构」）与**从属者可达**（子 agent/被派发任务的加载由入口驱动，见 `AGENTS_COMMON.adoc`「访问与解析」；**且复核对执行环境的能力有降级路径**——环境不支持派发子 agent / 外部复核者卡住或超时时，由主 agent（或一次性可超时的等价调用）承担同一复核职责并如实标注独立性边界，见 link:../general/collab.adoc[]「资源限制与感知」之硬超时与超时处置）；⑥性能（代价说得清）——常驻体积、加载后的时延/token 开销、机制本身的成本（如机械校验是否纳入只做确定性检查的 CI、是否毫秒级）须有可核对说法，不得以"反正不贵"含糊带过（ISO/IEC/IEEE 25010 性能效率）。**典型可查项**：判据被压成"要注意"（不可判定）、"必须做到"却没有机械抓手也无降级路径、引用了一个并不支持该条的标准、把解释塞回执行侧条目（读的形态走样）、方法论/依据论证涨回常驻层、新条目未登记调度器或未定级。
* **③接纳面的判据（会被未知项目加载的内容，L1）**：逐项核对"未知项目加载后会怎样"——①**冲突与优先级**：与引用方自身规范冲突时，优先级是否写明（公共规范与项目规范冲突以项目自身规范为准，见 `AGENTS_COMMON.adoc`「访问与解析」）、新条目是否可能**静默推翻**引用方既有约定；②**对引用方工作区的默认动作**：是否默认改动/格式化了引用方文件、是否默认代为提交或清理临时产物（须由其显式触发或用户声明）；③**新增依赖与工具要求**：是否引入新依赖、新工具链或版本要求（若引入须有降级路径，见 link:../general/self-check.adoc[]），且**不得**出现引用方看不到的本仓库脚本名/仓库结构（link:../general/spec-lifecycle.adoc[]「规范集合的自身重构」"删"）；④**私有约定与假定**：是否夹带只在某些项目成立的假定（如特定目录、特定语言、特定平台）；⑤**成本与体积**：引用方加载后的常驻体积与加载路径是否可控——**凡设"常驻层体积/条数上限"的项目，须把上限写成可机械核对的值**（只写"要注意体积"不构成上限）；上限的具名抓手与取值属项目自身规范，不在公共内容内。**典型可查项**：新增 L1 却未给冲突次序、默认替引用方改工作区、条目隐含"必须有某工具"却没有不可用时的做法、把本项目自身的取舍当通用要求。
* **三问都须留证（L1）**：①留"逐条对照表"（原文 vs 改动后，缺项/降级项/移层项写明去向）；②留"问题清单"（每条带 判据/依据/机制/形态/层级体积/性能 中的哪一项 + 判定依据）；③留"接纳面清单"（每条带 冲突/默认动作/依赖/假定/成本 中的哪一维 + 影响与处置）。**"未复核"与"复核通过"不得混写**；三问都通过才可提交，不通过须先修再复核。**维护规范集合的项目**应把本节要求转成机械抓手（钉住三视角、标准出处与③的落点仍在），使其不靠自觉。
