= 验证规范（公共内容，验证时加载）

== 验证与运行契约的落点

本节是**编译/运行验证、分步验证与规范验证**的公共落点，也是 `testing.adoc`「验证与运行契约」指向的**完整正文**：跑测试/补测试时加载 link:testing.adoc[]，其同名节只留一跳入口（验证口径只写一处，两处不得各自漂移）。

阅读顺序：先用「验证的适用边界」判定改动性质，再按「验证的效力等级」定手段与结论强度，按「验证总纲」「规范验证」执行，判"做到什么程度"用「判准维度：严格执行 / 尽力而为」，被未知项目加载的内容另过「运行契约」。

=== 编译/运行验证

本节是**编译/运行验证、分步验证与规范验证**的公共口径。

本节是编译/运行验证、分步验证与**规范验证**的公共口径。编译耗时较长，**不滥运行**——仅当确需验证（用户明确要求，或存在仅能靠运行确认的行为）时才执行；多个待验证项能合并时合并为一次执行，不逐项独立验证；运行命令时优先把完整输出重定向到文件（如 `mvn ... > build.log 2>&1`、`npm run build > build.log 2>&1`），避免终端输出截断或命令中断后无法恢复而需重试；日志等临时产物按执行原则「临时产物」处理。

* **以真实结果为准（L1）**：不得仅凭命令 exit code 判断成败，须依据对应工具的实际统计结果（如测试的 run/failures/errors/skipped 统计、构建的成功日志）判断；统计须**一步直接到位**（在同一命令内从重定向的日志中过滤统计行），禁止"先运行、再提示后单独读取报告"的两段式流程。
* **分步验证（L1）**：设计、开发、写用例等多步骤任务，每个步骤执行完须对涉及的部分做一次隔离上下文的复核，确保每步正确——前面方向错了，后面做再多也是无用功。
* **外部资源必须实测可用（L1）**：引入外部资源（CDN/脚本/CSS/图片 URL、第三方依赖、远程文件等）时须**实际验证其可用**（发起真实请求确认返回预期状态码，如 200），不得只凭版本号/文档推测路径存在；注意 `latest`、`@latest` 等浮动版本可能解析到无对应产物的新版，须固定到经实际验证的具体版本。
* **外部资源禁止本地下载引用（L1）**：**未经用户声明**（明确允许/要求下载），严禁将外部资源、依赖（CDN 脚本/CSS、第三方库、JAR/二进制等）**下载到本地以本地文件方式引用**——含工作目录及任何本地位置；应使用**链接**（URL 直接引用）或其他引用方式（如构建工具的依赖声明）。确需下载到本地时须先获得用户声明同意。


=== 判准维度：严格执行 / 尽力而为

L1/L2/L3 只答"**要求有多强**"，还须答"**执行到什么程度算做到**"——同一级别的条款有"判据固定、可逐次核对"与"判据开放、做不到不算违规"两种形态，混在一起就会出现两头落空：把"尽力而为"的条款当硬指标承诺，或把"严格"的条款当尽力而为（跑不了就跳过、不说明）。

* **严格执行（须逐次达成并给出证据）**：判据固定、结果只有「做到/没做到」二值，没做到即**不得声明完成**——如 `git mv`、引用须指向真实文件、破坏性操作先确认、最高关注项的存在性。**判定**：能否给出"本次是否达成"的核对动作（命令/取值/清单）。
* **尽力而为（须尝试、须说明、不记通过）**：判据依赖环境或第三方，**做不到本身不构成违规，但"不尝试"与"做不到却记成做到"都违规**——如兼容性测试中环境受限的场景、`IT` 依赖的外部环境不可用、依赖上游修复的问题。**判定**：本次是否**实际尝试**了、是否如实写明"未执行/未达成 + 原因 + 替代做法"。
* **两者都必须留证（L1）**："未执行"与"执行通过"是两个不同结论，**不得混写**；对判准类型有疑问时按"严格执行"处理并补判据，不得借"尽力而为"降低既有约束的强度。
* **何时用（L1）**：本判准维度答"**执行到什么程度算做到**"，与 L1/L2/L3（"要求有多强"）**是两个轴**——凡新写一条含"必须/不得"的规则、或判断某条是否被遵守时，都要先判它属严格执行还是尽力而为。它与「验证的效力等级」的确定项/概念项**也是两个轴**（后者说"判据形态"，本条说"执行到什么程度算做到"）：**常见但非必然**的对应是确定项多按严格执行、概念项多按尽力而为，**不得据此压在一条轴上**——确定项也可以被项目规定为尽力而为，此时须写明其留证形态。
* **同一约束只能有一个判准（L1）**：同一件事不得在不同文件里出现两种判准（如一处按严格执行、另一处当作可跳过）。
* **常见误用（L1）**：把"环境不支持"直接当作结论而不尝试（应属尽力而为、须先试）；把"尽力而为"写成硬承诺（会在环境正常差异下频繁"看起来未完成"）；同一件事在不同文件里出现两种判准。

=== 验证的适用边界（先判改动性质，再决定验证到什么程度）

验证机制本身也是会被加载、被执行的规则——**用错对象就是把不可控的验证义务强加给不需要它的任务**。故先给判据：**按改动性质取值，先判性质、再选范围**。

[cols="1,2,2", options="header"]
|===
| 改动性质 | 验证到什么程度 | 判据与依据
| **A. 代码类改动**（改代码、修缺陷、调参数；不触碰会被未知项目加载的公共内容） | **机械判据判过不过**——编译/构建通过、测试按实际统计通过即可交付；**不做**三视角、**不做**全局核对、**不设**复盘节点 | 依据：本文件「以真实结果为准」（有确定性判据的事，用判据说话；ISO/IEC Directives Part 2 要求可验证——已有可验证判据时不叠加无判据的流程）
| **B. 规范类改动**（改动公共内容：规范条目、任务提示词、随规范分发的工具；或改动会被未知项目加载的任何产物） | **三视角深度验证**（①完整性 + ②有效性与认知质量 + ③接纳面，同一干净子 agent 一次读取、分栏列），**而且因为判据多是概念性、笼统、不可控的**，必须**从全局核对**：这条规则要解决的失效现在还在不在、依据是否仍支持该条 | 依据：概念性判据没有"跑一遍就知道"的确定性判据，只能靠语义复核 + 全局追溯（IEEE 1028 软件评审；ISO/IEC/IEEE 29148 可追溯；ISO 10007 变更控制）
|===

* **判据只有一个问句（L1）**：**"这次改动会不会被未知项目加载、会不会改变别人的行为？"**——会（或不确定）→ 按 B 走；明确不会（项目内部实现）→ 按 A 走。**不得因为"改动小"就降级**：改一条规范里的一个词也可能改变别人行为，性质判据不看改动量。
* **不得互串（L1）**：A 类任务不得自行升级为三视角 + 全局复核（属过度验证：把可控的验证做成不可控的多步流程）；B 类任务不得只跑机械校验就收尾（属跳过验证：机械校验覆盖不到判据是否被压成口号、机制是否真在运行环境发生）。**同一任务含两类改动时取**更严的一侧**（B）**，但**只需对公共内容那一部分**做三视角与全局核对，代码部分仍按 A 的机械判据核对——**取更严的一侧**，但别把代码部分也拖进概念性流程。
* **不得另立一套验证体系（L1）**：验证范围是**下限与口径**，不是"项目必须另建的验证阶段/产物"——项目已有的 CI、构建、测试、评审直接沿用，本节只规定"到什么程度算过"（口径与留证要求不得省）。

=== 验证的效力等级（按对象定手段与结论强度）

验证会被用来推翻或认可别人的结论，**验证自己说错话的代价最大**。故给判据：**对象有确定性判据 → 机械校验，结论可判对错；对象只有概念性判据 → 只能启发式复核，结论只到"未发现问题"**。

[cols="1,2,2,2", options="header"]
|===
| 验证对象 | 判据形态 | 可用手段与结论 | 失效模式与去向
| **确定项**（有确定性判据：存在性、双向登记、引用可解析、格式与取值、构建与测试的实际统计） | 二值、可机械核对 | **判据本体验证**：机械校验按**判据本身**核对（如"引用指向真实文件"用**文件存在性**核对），**不按引用形式近似**；结论为**通过 / 不通过** | 近似式校验（按引用形式而不是判据本身核对）会**漏报**（判据坏了仍绿）；漏掉的判定点须逐个列出
| **概念项**（无确定性判据：判据是否笼统、内容是否完整、机制在真实环境会不会发生、被未知项目加载后是否可控） | 开放、须语义判断 | **只能启发式复核**（三视角复核、换机器、换角度、换样本） | **换一个角度就可能查出问题，也可能永远查不出**——故其结论只到**"未发现问题"，不能推出"没有问题"**；**也不得当作可二值化的通过条件去阻断交付**（**不得当作阻断交付的条件**）；"已换过若干角度、仍是未发现"即可**如实交付并悬置**
|===

* **结论强度（L1）**：汇报与留证须按对象区分写法，**"未发现问题"与"验证通过"不得混写**——确定项写**通过/不通过**（可举判据）；概念项写**"已复核、未发现问题"**并列出**已复核角度与样本**。**把"复核过、没看出问题"写成"这条规范没问题"，属以启发式结论冒充已验证**。
* **交付是否可阻断（L1）**：**只有确定项的判据不满足才阻断交付**（机械校验报错、构建/测试未通过、引用悬空等）；概念项**不设阻断条件**——它筛得出问题就修，筛不出就如实交付，**不得把"找不到问题"变成交付的隐性前置条件**。
* **悬置（L1）**：概念项未发现问题**不等于已确证**——凡**还没有确定性证据**支撑的部分，一律标记为**悬置**并写明理由与剩余风险。悬置**可与改动一并交付**（不阻断），但须**逐项可枚举**、可被后续证据收口；**不得把悬置项在汇总里写成通过项**。
* **手段的效力不对称（L1，须如实声明）**：机械校验**只能核对确定性判据**——它覆盖不到判据是否被压成口号、机制在真实环境发不发生、内容是否完整；概念项复核**发现的是"问题案例"、不是"没有问题"**（查到一处即确证有问题，查不到不构成证明）。**降低漏报的办法是增加独立的核对角度与样本（换视角、换机器、换反例），而不是把复核结论当成确定性判据**。
* **留证形态：三态台账（L1）**：留证**不得写成散文结论**，须逐项成行、每条带**三态标签之一**——**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附未确证的原因与剩余风险），**三态各占一栏、不得合并**。**"查不出问题"与"没有做复核"须能分辨**。

=== 验证总纲（回答"验证什么、怎么算过"）

规范类改动（B 类）的验收只有一句"跑一遍检查"是不够的：**验证什么、每项怎么算过、标准出自哪里**若不写死，验证就会退化成"把现有脚本跑绿"，规则会在一次次维护中**慢慢脱离初衷**。故把验收拆成**三个视角**，每个视角给出**判定标准**与**标准出处**（出处只写标准名/编号、不附链接）：

[cols="1,2,1,1", options="header"]
|===
| 视角 | 判定问题 | 不合格的典型症状 | 标准出处
| **① 完整性** | **对照面：改动前后**——被改对象在改动前后是否**等价** | 误删条目、把"必须+判据"降级成"要注意"、内容被搬到加载不到的位置 | ISO 10007（配置管理与变更控制）、ISO/IEC/IEEE 29148（可追溯）
| **② 有效性与认知质量** | **对照面：规范本体**——规则是否**说得对、说得清、跑得动、判得了、效力标得准** | 判据不可判定（无判定标准）、机制在真实环境不会发生、依据被删到无从追溯、写错受众（执行侧夹带解释 / 决策侧缺依据）、"验证通过"其实只是"跑完脚本"、**把启发式复核冒充确定性验证** | ISO/IEC Directives Part 2（要求须可验证）、ISO/IEC/IEEE 29148（单一/无歧义/可验证）、ISO/IEC/IEEE 25010（质量特性含性能效率）、RFC 2119 / RFC 8174（用语强度）
| **③ 接纳面（未知项目加载可控）** | **对照面：引用方项目**——被未知项目加载后会造成什么**可预见**的影响（概念项：逐项只看"是否发现"，查不出不等于没有） | 与引用方自身规范冲突时无优先级规则、默认替引用方改文件/格式化/提交、新增依赖或强制工具链、夹带项目私有约定、加载体积不可控 | ISO/IEC Directives Part 2（规范性文件引用现行文件、不作隐含要求）、ISO/IEC/IEEE 29148（干系人需求）、ISO 9241-110（交互原则：可控、可预期、不阻断）
|===

* **验证按对象与改动性质取值（L1）**：三个视角是**口径**，实际验证动作按上表取值——①、②适用于**每次规范改动**；③适用于**任何会被未知项目加载的公共内容**，且其**影响面/成本/可控性**三维见下「运行契约」。
* **验证对象不止规范文件、也须能枚举“如何验证”（L1）**：被加载后**会被执行**的产物同样是验证对象——**任务提示词**（会被项目复制成指令执行）与**随规范分发的工具脚本**都须按①完整性 + ②有效性与认知质量 + ③接纳面三项一并核对；**不得只验证规范文本、把会被执行的产物漏掉**。
* **"验证了什么"必须能枚举（L1）**：每次改动的汇报须**逐项**给出三个视角的结论（①逐条对照表、②按判据分类的问题清单、③按影响面/成本/可控性分类的清单），并**逐项标注效力等级与依据**（确定项＝判据名与取值；概念项＝已复核的角度与样本）——**没有按对象标注效力等级、或把启发式复核冒充确定性验证，不算验证**；**"未核对""未确证""核对通过"三态不得混写**。**只跑机械校验、说不出验了什么**不算验证。
* **防"慢慢脱离初衷"（L1）**：验证须回答"这条规则**当初要解决的失效**现在还在不在"（**这是概念项**：能查出一处"初衷已不成立"即确证有问题；查不出只说明**未发现问题**，不足以宣布"仍有效"）。**凡只保住文本、保不住初衷的改动，视为验证未通过**。
* **本节自身的效力等级（L1）**：本节与「验证的效力等级」「验证的适用边界」的判据都是"机制在真实环境会不会发生、被加载后是否可控"这类开放判断，故其结论**只能标"未发现问题"、不得宣称"已验证有效"**；本节自身也须被复盘（判据还在 ≠ 判据还成立）。

=== 规范验证（改完规范后的三视角复核）

规范的**语义有效性不能由确定性校验覆盖**——判据是否被压成口号、机制在真实环境是否会发生、被未知项目加载后是否可控，**属语义判断**，故须另起**干净子 agent**（隔离上下文，不带改动方立场）复核（依据：IEEE 1028 软件评审；ISO 10007 配置管理的变更控制）。

* **三视角各一问（L1）**：**①完整性**问「**对象**在改动前后是否**等价**——谁少了一条要求？误删、降级、放错层都属不等价」；**②有效性与认知质量**问「它**可被合规地执行**吗——判据可判定吗？依据还在吗、是否**说对了**？机制在**当前执行环境**真会发生吗？放对层、加载代价在预算内吗？从属者加载得到吗？**代价说得清吗**？」；**③接纳面**按下「运行契约」的影响面/成本/可控性三维逐维过。**同一个干净子 agent 一次做完（L1）**——同一份 diff、同一批受影响文件，重复起子 agent 是重复读取与重复计费；**一次读取、结论分栏列**，不得因合并而混答（三者对照面不同：改动前后 / 规范本体 / 引用方项目）。**每次验证都换一个干净上下文（L1）**：复核者须与发起改动者隔离，且**不得复用上一次验证用过的上下文**（带着上一轮结论再看一遍，会只找"是否已改"而放过新问题，等于自己复核自己）。只有①无任何语义可判（纯错字/格式/引用目标存在性）时才可只跑机械校验、不起子 agent。
* **②的判据（L1）**：①**判据可执行**（每条 L1 有判定标准）；②**依据**（标准名/编号）仍在、且**说对了**——不得只验证"依据行还在"，还须核对引用的标准**确实支持该条**；③**机制真会发生**（依赖环境能力的机制须有缺失时的降级路径）；④**读的形态**（执行侧只给"怎么走"——规则 + 判定标准 + 依据名；原因与取舍归思考/决策侧）；⑤**放对层与体积**（加载面只放底线）与**从属者可达**（被派发任务的加载由入口驱动）；⑥**性能**（代价说得清——加载后的时延/token 开销、机制本身的成本须有可核对说法，不得以"反正不贵"含糊带过；ISO/IEC/IEEE 25010 性能效率）。**典型可查项**：判据被压成"要注意"（不可判定）、"必须做到"却没有抓手也无降级路径、引用了一个并不支持该条的标准、把解释塞回执行侧条目、方法论/依据论证涨回常驻层、新条目未登记调度器或未定级。
* **③接纳面的判据（L1）**：逐项核对"未知项目加载后会怎样"——①**冲突与优先级**：与引用方自身规范冲突时优先级是否写明（以引用方项目自身规范为准）、新条目是否可能**静默推翻**引用方既有约定；②**对引用方工作区的默认动作**：是否默认改动/格式化引用方文件、是否默认代为提交或清理临时产物；③**新增依赖与工具要求**：是否引入新依赖、新工具链或版本要求（若引入须有降级路径），且**不得**出现引用方看不到的私有脚本名/仓库结构；④**私有约定与假定**：是否夹带只在某些项目成立的假定（特定目录、特定语言、特定平台）；⑤**成本与体积**：加载后的体积与加载路径是否可控。**典型可查项**：新增 L1 却未给冲突次序、默认替引用方改工作区、条目隐含"必须有某工具"却没有不可用时的做法、把本项目的取舍当通用要求。
* **三视角都须留证（L1）**：①留"逐条对照表"（原文 vs 改动后，缺项/降级项/移层项写明去向）；②留"问题清单"（每条带 判据/依据/机制/形态/层级体积/性能 中的哪一项 + 判定依据）；③留"接纳面清单"（每条带 冲突/默认动作/依赖/假定/成本 中的哪一维 + 影响与处置）。**"未复核"与"复核通过"不得混写**；三视角都过才可提交，不通过须先修再复核。
* **派发须自带硬超时（L1）**：语义复核派给子 agent 或外部复核者时**必须设可判定的时限**，到点即视为失联并"**放弃 + 如实标悬置**"，**不得无限等待**；**复核职责不绑定特定执行者**——外部复核者不可用时，由发起方按同一判据组织等价复核，并如实标注独立性边界（与改动方同模型的复核，独立性弱于第三方）。派发时优先选**一次性、边界明确、可超时**的形式。
* **标准从哪来（L1）**：凡是**已有业界标准/权威约定的判定项，先引标准、不另造一套说法**——本文件用到的对应关系是：判据可验证性 → ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148；用语强度 → RFC 2119 / RFC 8174；变更控制与可追溯 → ISO 10007 与 ISO 9001；软件评审 → IEEE 1028；性能效率 → ISO/IEC/IEEE 25010；可用性与可控性 → ISO 9241-110。**只列与本条判据确有对应关系的标准，不得为"看起来有依据"堆砌**；**没有可援引标准时，才自定判据并写明理由**。

=== 运行契约（公共内容被未知项目加载时的可控性）

公共内容（本入口 + `specs/` + `prompts/` + 会被引用方加载的工具）**不随某个项目的上下文生效，而是被未知项目加载**——看不到它的项目结构、已经存在的项目规范、依赖与工具链。故"加一条规则"不止要问"这条对不对"，还要问"**它落到一个未知项目里会发生什么**"。

判定按**三维**逐维过（依据：ISO/IEC Directives Part 2 要求规范性文件引用现行文件、不作隐含要求；ISO/IEC/IEEE 29148 的需求须可追溯到干系人；ISO 9241-110 的交互原则——可控、可预期、不阻断）：

* **① 影响面（L1）**：这条规则会改变引用方的哪些既有行为？**与引用方自身规范的冲突次序**是否写明（以引用方项目自身规范为准）；**不得出现"静默推翻引用方既有约定"的条目**——凡收紧/推翻既有做法者须显式授权（用户声明或引用方自身规范声明），并给出"不采用时怎么办"。
* **② 成本（L1）**：加载与遵守的代价是否说得清——**加载面体积**（每次会话都加载的部分应设可机械核对的上限，只写"要注意体积"不构成上限）、加载后的时延/token 开销、引入的依赖或工具链要求（含版本要求，且须给出不可用时的降级路径）；**不得以"不贵"含糊带过**（ISO/IEC/IEEE 25010 性能效率）。
* **③ 可控性（L1）**：引用方是否**能预期、能关闭、能自行执行**——①**不得依环境自动动作**：不默认改动/格式化引用方文件、不默认代为提交、不默认清理其临时产物（须由其显式触发或用户声明）；②**不得让引用方依赖本仓库私有物**：条目不得引用引用方看不到的私有脚本名、仓库结构或私有约定；③**不得阻断**：规则不得让引用方在正常路径上无法完成工作（无降级路径的硬性前置一律不合规）。
* **接纳面须留证（L1）**：新增/调整公共内容时，须在改动说明（提交说明或汇报）中逐维写明"影响面 / 成本 / 可控性"的核对结论；**未核对不得计入验证通过**。
