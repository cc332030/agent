= 验证规范（通用层，验证时加载）

== 验证与运行契约的落点

本文件即「验证与运行契约」的落点（含「运行契约」一节）：编译/运行验证、判准维度、验证的适用边界、效力等级、验证总纲、规范验证与运行契约均在本文件内。

本文件是**编译/运行验证、分步验证与规范验证**的单一落点。阅读顺序：先用「验证的适用边界」判定改动性质，再按「验证的效力等级」定手段与结论强度，按「验证总纲」「规范验证」执行，判"做到什么程度"用「判准维度」。

== 编译/运行验证

* **不滥运行**：编译耗时较长，仅当确需验证（用户明确要求，或存在仅能靠运行确认的行为）时才执行；多个待验证项能合并时合并为一次执行；运行命令时优先把完整输出重定向到文件（`mvn ... > build.log 2>&1`），避免终端截断。
* **以真实结果为准（L1）**：不得仅凭命令 exit code 判断成败，须依据对应工具的实际统计结果（测试的 run/failures/errors/skipped 统计、构建的成功日志）判断；统计须**一步直接到位**（在同一命令内从重定向的日志中过滤统计行），禁止"先运行、再单独读取报告"的两段式。
* **验证须覆盖项目的全部既定校验手段（L1）**：把项目**声明的全部校验手段**都跑到——编译/构建、配套测试（单元与各专项）、规范/完整性机械校验、静态检查。**只跑主校验脚本、或只跑"最像验证"的那一条命令，都属验证不完整**。判定口径：**"存在测试"≠"测试被执行"**——须能指出"本次跑了哪几套、各自统计结果是什么"；**"被跑的那一套够不够用"是另一问**——手段与被跑用例**本身可能不完整**，**先按 link:testing.adoc[]「用例设计」review**、说明"查了哪些角度、哪些未覆盖、哪些未确证"，**本次改动的直接相关面**先补全。新增校验手段后须同步接进验证链（见 `specs/general/ci-cd.adoc`「校验链完整」）。
* **验证对象须钉定 commit sha（L1）**：分支名不是稳定标识。验证/复核前须**先取定具体 commit sha**并写明，在该 sha 上核对；**发现对象是"某分支的最新"时须先强刷 ref 再取 sha**（`git fetch -f` + `git rev-parse`）。
* **分步验证（L1）**：多步骤任务每步执行完须对涉及部分做一次隔离上下文的复核——前面方向错了，后面做再多也是无用功。
* **运行环境须与项目声明一致（L1）**：一律用项目**声明的**运行环境（jdk1.8、python2 等），"换个版本也能跑通"不构成理由；声明环境不可得时如实说明并把结论标未确证，**不得记为通过**。判据见 `specs/general/ci-cd.adoc`「运行环境须与项目声明一致」。
* **外部资源必须实测可用（L1）**：引入外部资源（CDN/脚本/CSS/图片 URL、第三方依赖、远程文件）时须**实际验证其可用**（发起真实请求确认返回预期状态码），不得只凭版本号/文档推测路径存在；`latest`、`@latest` 等浮动版本可能解析到无对应产物的新版，须固定到经实际验证的具体版本。
* **外部资源禁止本地下载引用（L1）**：**未经用户声明**，严禁将外部资源、依赖下载到本地以本地文件方式引用；应使用链接或其他引用方式（如构建工具的依赖声明）。

== 判准维度：严格执行 / 尽力而为

L1/L2/L3 只答"**要求有多强**"，还须答"**执行到什么程度算做到**"——两者是两个轴。

* **严格执行（须逐次达成并给出证据）**：判据固定、结果只有「做到/没做到」二值，没做到即**不得声明完成**——如 `git mv`、引用须指向真实文件、破坏性操作先确认、最高关注项的存在性。**判定**：能否给出"本次是否达成"的核对动作（命令/取值/清单）。
* **尽力而为（须尝试、须说明、不记通过）**：判据依赖环境或第三方，做不到本身不构成违规，但**"不尝试"与"做不到却记成做到"都违规**——如兼容性测试中环境受限的场景、`IT` 依赖的外部环境不可用。**判定**：本次是否实际尝试了、是否如实写明"未执行/未达成 + 原因 + 替代做法"。
* **两者都必须留证（L1）**："未执行"与"执行通过"是两个不同结论，**不得混写**；对判准类型有疑问时按"严格执行"处理并补判据。
* **何时用（L1）**：凡新写一条含"必须/不得"的规则、或判断某条是否被遵守时，都要先判它属严格执行还是尽力而为。它与「验证的效力等级」的确定项/概念项**也是两个轴**（后者说"判据形态"，本条说"执行到什么程度算做到"）。
* **同一约束只能有一个判准（L1）**：同一件事不得在不同文件里出现两种判准。
* **常见误用（L1）**：把"环境不支持"直接当作结论而不尝试（应属尽力而为、须先试）；把"尽力而为"写成硬承诺；同一件事在不同文件里出现两种判准。

== 验证的适用边界（先判改动性质，再决定验证到什么程度）

判据只有一个问句（L1）：**"这次改动会不会被未知项目加载、会不会改变别人的行为？"**——会（或不确定）→ 按 B 走；明确不会 → 按 A 走。**不得因为"改动小"就降级**。

[cols="1,2,2", options="header"]
|===
| 改动性质 | 验证到什么程度 | 判据与依据
| **A. 代码类改动**（改代码、修缺陷、调参数；不触碰会被未知项目加载的公共内容） | **机械判据判过不过**——编译/构建通过、测试按实际统计通过即可交付；**不做**三视角、**不做**全局核对、**不设**复盘节点 | ISO/IEC Directives Part 2（有可验证判据时用判据说话，不叠加无判据的流程）
| **B. 规范类改动**（改动公共内容：规范条目、任务提示词、随规范分发的工具；或改动会被未知项目加载的任何产物） | **三视角深度验证**（①完整性 + ②有效性与认知质量 + ③接纳面，同一干净子 agent 一次读取、分栏列），且须**从全局核对**：这条规则要解决的失效现在还在不在、依据是否仍支持该条 | IEEE 1028（软件评审）、ISO/IEC/IEEE 29148（可追溯）、ISO 10007（变更控制）
| **C. 不改内容的操作**（只改提交/历史的组织或文件路径、不改变工作区内容：压缩提交、只做重命名的提交） | **用该操作自身的确定性判据核对，不重跑全量编译与测试**（`git diff <旧> <新>` 无输出、根 tree 相同、`git diff -M --stat` 0 增 0 删、`merge-base` 关系、`git log --follow` 的 `R`/`M` 可分） | 内容既然逐字节相同，重跑不会得到任何新判据（ISO/IEC/IEEE 25010 性能效率）
|===

* **先判"有没有改内容"、再进 A/B（C 优先）**：改动前后工作区内容逐字节相同（以 `git diff` 无输出为准）时属 **C**，不重跑全量编译与测试。
* **"内容没变"不是"少核对"的借口（L1）**：C 省的是**重跑全量校验**，不是**核对**——该操作自身的判据一条都不能少、须逐条给出取值；**判据不满足即阻断交付**。`git diff` 一旦有输出或出现夹带改动，即不再属 C，须回到 A/B 按改动性质重判。
* **不得互串（L1）**：A 类任务不得自行升级为三视角 + 全局复核（过度验证）；B 类任务不得只跑机械校验就收尾（跳过验证）。**同一任务含两类改动时取**更严的一侧**（B）**，但只需对公共内容那一部分做三视角与全局核对，代码部分仍按 A 的机械判据核对。
* **不得另立一套验证体系（L1）**：项目已有的 CI、构建、测试、评审直接沿用，本节只规定"到什么程度算过"。

== 验证的效力等级（按对象定手段与结论强度）

[cols="1,2,2,2", options="header"]
|===
| 验证对象 | 判据形态 | 可用手段与结论 | 失效模式与去向
| **确定项**（存在性、双向登记、引用可解析、格式与取值、构建与测试的实际统计） | 二值、可机械核对 | **判据本体验证**：机械校验按判据本身核对，不按引用形式近似；结论为**通过 / 不通过** | 近似式校验会漏报（判据坏了仍绿）；漏掉的判定点须逐个列出
| **概念项**（判据是否笼统、内容是否完整、机制在真实环境会不会发生、被未知项目加载后是否可控） | 开放、须语义判断 | **只能启发式复核**（三视角复核、换机器、换角度、换样本） | 换一个角度就可能查出问题，也可能永远查不出——故结论只到**"未发现问题"**，不能推出"没有问题"，**也不得当作阻断交付的条件**
|===

* **结论强度（L1）**：汇报与留证须按对象区分写法，**"未发现问题"与"验证通过"不得混写**——确定项写**通过/不通过**（可举判据）；概念项写**"已复核、未发现问题"**并列出已复核角度与样本。**把"复核过、没看出问题"写成"这条规范没问题"，属以启发式结论冒充已验证**。
* **交付是否可阻断（L1）**：**只有确定项的判据不满足才阻断交付**；概念项**不设阻断条件**——筛得出问题就修，筛不出就如实交付。
* **悬置（L1）**：概念项未发现问题不等于已确证——凡还没有确定性证据支撑的部分一律标记为**悬置**并写明理由与剩余风险。悬置**可与改动一并交付**（不阻断），但须逐项可枚举、可被后续证据收口；**不得把悬置项在汇总里写成通过项**。
* **手段的效力不对称（L1）**：机械校验只能核对确定性判据——它覆盖不到判据是否被压成口号、机制在真实环境发不发生、内容是否完整；概念项复核**发现的是"问题案例"、不是"没有问题"**。**降低漏报的办法是增加独立的核对角度与样本，而不是把复核结论当成确定性判据**。
* **留证形态：三态台账（L1）**：留证不得写成散文结论，须逐项成行、每条带**三态标签之一**——**通过**（附判据与取值）／**未发现问题**（附已复核角度与样本）／**悬置**（附未确证的原因与剩余风险），**三态各占一栏、不得合并**。**"查不出问题"与"没有做复核"须能分辨**。

== 验证总纲（回答"验证什么、怎么算过"）

规范类改动的验收只有一句"跑一遍检查"是不够的：**验证什么、每项怎么算过、标准出自哪里**若不写死，验证就会退化成"把现有脚本跑绿"，规则会在一次次维护中**慢慢脱离初衷**。三视角与其标准出处（只写标准名/编号）：

[cols="1,2,1", options="header"]
|===
| 视角 | 判定问题 | 标准出处
| **① 完整性** | **对照面：改动前后**——被改对象在改动前后是否**等价**（误删条目、把"必须+判据"降级成"要注意"、内容被搬到加载不到的位置） | ISO 10007（配置管理与变更控制）、ISO/IEC/IEEE 29148（可追溯）
| **② 有效性与认知质量** | **对照面：规范本体**——规则是否**说得对、说得清、跑得动、判得了、效力标得准**（判据不可判定、机制在真实环境不会发生、依据被删到无从追溯、写错受众、"验证通过"其实只是"跑完脚本"、把启发式复核冒充确定性验证） | ISO/IEC Directives Part 2、ISO/IEC/IEEE 29148、ISO/IEC/IEEE 25010、RFC 2119 / RFC 8174
| **③ 接纳面（未知项目加载可控）** | **对照面：引用方项目**——被未知项目加载后会造成什么可预见的影响（逐项只看"是否发现"，查不出不等于没有） | ISO/IEC Directives Part 2、ISO/IEC/IEEE 29148、ISO 9241-110
|===

* **验证按对象与改动性质取值（L1）**：①、② 适用于**每次规范改动**；③ 适用于**任何会被未知项目加载的公共内容**，其影响面/成本/可控性三维见下「运行契约」。
* **如何验证、验证对象不止规范文件（L1）**：会被执行的产物同样是验证对象——**任务提示词**（会被项目复制成指令执行）与**随规范分发的工具脚本**都须按三项一并核对。
* **"验证了什么"必须能枚举（L1）**：每次改动的汇报须**逐项**给出三个视角的结论（①逐条对照表、②按判据分类的问题清单、③按影响面/成本/可控性分类的清单），并**逐项标注效力等级与依据**。**只跑机械校验、说不出验了什么**不算验证。
* **防"慢慢脱离初衷"（L1）**：验证须回答"这条规则**当初要解决的失效**现在还在不在"（概念项：能查出一处"初衷已不成立"即确证有问题；查不出只说明未发现问题）。**凡只保住文本、保不住初衷的改动，视为验证未通过**。

== 规范验证（改完规范后的三视角复核）

* **三视角各一问（L1）**：**①完整性**问「对象在改动前后是否等价——谁少了一条要求？误删、降级、放错层都属不等价」；**②有效性与认知质量**问「它可被合规地执行吗——判据可判定吗？依据还在吗、是否说对了？机制在当前执行环境真会发生吗？放对层、加载代价在预算内吗？从属者加载得到吗？代价说得清吗？」；**③接纳面**按下「运行契约」三维逐维过。**同一个干净子 agent 一次做完（L1）**——同一份 diff、同一批受影响文件，一次读取、结论分栏列，不得因合并而混答。**每次验证都换一个干净上下文（L1）**：复核者须与发起改动者隔离，且不得复用上一次验证用过的上下文。只有 ① 无任何语义可判（纯错字/格式/引用目标存在性）时才可只跑机械校验、不起子 agent。
* **②的判据（L1）**：① **判据可执行**（每条 L1 有判定标准）；② **依据**仍在、且**说对了**（不得只验证"依据行还在"，还须核对引用的标准确实支持该条）；③ **机制真会发生**（依赖环境能力的机制须有缺失时的降级路径）；④ **读的形态**（执行侧只给"怎么走"——规则 + 判定标准 + 依据名；原因与取舍归思考/决策侧）；⑤ **放对层与体积**与**从属者可达**；⑥ **性能**（代价说得清——加载后的时延/token 开销、机制本身的成本须有可核对说法）。**典型可查项**：判据被压成"要注意"、"必须做到"却没有抓手也无降级路径、引用了一个并不支持该条的标准、把解释塞回执行侧条目、新条目未登记调度器或未定级。
* **③接纳面的判据（L1）**：逐项核对"未知项目加载后会怎样"——① **冲突与优先级**（是否写明以引用方项目自身规范为准、是否可能静默推翻其既有约定）；② **对引用方工作区的默认动作**（是否默认改动/格式化其文件、默认代为提交或清理临时产物）；③ **新增依赖与工具要求**（若有须有降级路径，且不得出现引用方看不到的私有脚本名/仓库结构）；④ **私有约定与假定**（是否夹带只在某些项目成立的假定）；⑤ **成本与体积**。
* **三视角都须留证（L1）**：① 留"逐条对照表"；② 留"问题清单"（每条带判据/依据/机制/形态/层级体积/性能中的哪一项 + 判定依据）；③ 留"接纳面清单"（每条带冲突/默认动作/依赖/假定/成本中的哪一维 + 影响与处置）。三视角都过才可提交，不通过须先修再复核。
* **派发须自带硬超时（L1）**：语义复核派给子 agent 时**必须设可判定的时限**，到点即视为失联并"**放弃 + 如实标悬置**"，不得无限等待；派发时优先选**一次性、边界明确、可超时**的形式。
* **执行者选择：强制同 Agent（L1，其适用面由平台层限定）**：三视角复核一律由与执行者**相同的 Agent**（同 Agent 身份、同入口、同调度器）承担；不得点名外部 Agent / 外部 NPC、也不得以"换个 Agent 更独立"为由换来源。**"由与执行者相同的 Agent 承担"不是平台无关的强制前提**。**适用面（L1）**：该强制**只在承载该任务的平台层写明该前提成立时**按强制判（CNB 落点见 `specs/platform/cnb.adoc`「评论唤起新实例」）；**平台不提供同 Agent 的子执行者时**，不得援引本条跳过复核、更不得把任务停在中间——按 `specs/general/collab.adoc`「协作方式」降级为发起方本人串行核对并标注独立性边界，或如实标悬置，**复核与交付不因此缺失**。
* **标准从哪来（L1）**：凡已有业界标准/权威约定的判定项，先引标准、不另造一套说法。本文件用到的对应关系：判据可验证性 → ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148；用语强度 → RFC 2119 / RFC 8174；变更控制与可追溯 → ISO 10007 与 ISO 9001；软件评审 → IEEE 1028；性能效率 → ISO/IEC/IEEE 25010；可用性与可控性 → ISO 9241-110。**只列与本条判据确有对应关系的标准，不得为"看起来有依据"堆砌**；没有可援引标准时才自定判据并写明理由。

== 运行契约（公共内容被未知项目加载时的可控性）

公共内容**不随某个项目的上下文生效，而是被未知项目加载**——看不到它的项目结构、既有项目规范、依赖与工具链。故"加一条规则"不止要问"这条对不对"，还要问"**它落到一个未知项目里会发生什么**"。三维逐维过：

* **① 影响面（L1）**：这条规则会改变引用方的哪些既有行为？**与引用方自身规范的冲突次序**是否写明（以引用方项目自身规范为准）；**不得出现"静默推翻引用方既有约定"的条目**——凡收紧/推翻既有做法者须显式授权（用户声明或引用方自身规范声明），并给出"不采用时怎么办"。
* **② 成本（L1）**：加载与遵守的代价是否说得清——**加载面体积**（每次会话都加载的部分应设可机械核对的上限，只写"要注意体积"不构成上限）、加载后的时延/token 开销、引入的依赖或工具链要求（含版本要求，且须给出不可用时的降级路径）；**不得以"不贵"含糊带过**（ISO/IEC/IEEE 25010）。
* **③ 可控性（L1）**：引用方是否能**预期、能关闭、能自行执行**——① **不得依环境自动动作**：不默认改动/格式化引用方文件、不默认代为提交、不默认清理其临时产物；② **不得让引用方依赖本仓库私有物**：条目不得引用引用方看不到的私有脚本名、仓库结构或私有约定；③ **不得阻断**：规则不得让引用方在正常路径上无法完成工作（无降级路径的硬性前置一律不合规）。
* **接纳面须留证（L1）**：新增/调整公共内容时，须在改动说明（提交说明或汇报）中逐维写明核对结论；**未核对不得计入验证通过**。
* 依据（标准名/编号）：ISO/IEC Directives Part 2（规范性文件引用现行文件、不作隐含要求）、ISO/IEC/IEEE 29148（需求须可追溯到干系人）、ISO 9241-110（交互原则：可控、可预期、不阻断）。

== 改完规范必做的五件事（机械手段必跑，干净子 agent 复核不可漏）

判据本体在上文各节，本节只给**执行顺序与不可省略项**。**每次改完规范，本节五件事一件都不能少**；"改动小""只是改了个词""用户没要求"都不构成跳过理由。

. **① 机械手段必须先跑、且跑全（L1）**：一律先跑项目声明的全部既定校验脚本与其配套测试，**全量扫描、不按"只查变更文件"取巧**；**报红就地修复、不得留红**（"不在本次范围"不构成理由）。**判定标准**：说不出"跑了哪几套、各自统计结果是什么"即未通过。**没有机械手段的项目**：如实记录并按本条的**要求**为新增内容补上可机械核对的部分，不得据此跳过。
. **② 干净子 agent 的语义复核不可漏（L1）**：机械手段只覆盖确定性判据，判据是否被压成口号、机制在真实环境会不会发生、被未知项目加载后是否可控**属语义判断**，故必须另起**干净上下文**的子 agent 复核（每次换干净上下文）。**"有了就忽略"**：项目规范里已写明该要求时按其执行、不重复写第二份；**"没有就加"**：**须补在项目自身规范里**，不在公共内容里（公共内容不写引用方看不到的落点）。
. **③ 三视角一并回答、一次读取分栏列（L1）**：复核按**①完整性 + ②有效性与认知质量 + ③接纳面**三视角**一并回答**、一次读取、结论**分栏列**（见上「验证总纲」「规范验证」）。
. **④ 复核要走"三态台账"、不得写成散文（L1）**：留证逐项成行、每条带三态之一——**通过**／**未发现问题**／**悬置**，**三态各占一栏、不得合并**（见上「验证的效力等级」）。台账随交付一并发布（提交说明或 PR 结论），发布前的完成前自检须把它填实——"要求写了、台账没填"与"没复核"同判。
. **⑤ 子 agent 不可用时的降级与留证（L1）**：不得跳过复核、不得换外部来源顶替——由执行者在本次执行内按同一判据串行核对，并如实标注独立性边界；仍不可行时如实标悬置、写明未覆盖的角度与剩余风险。**降级后交付照常**。

* **本节的边界（L1）**：**只对规范类改动（B 类）**成立——代码类改动不做三视角、不设复盘节点；同一提交含两类改动时取更严的一侧（B），但只对公共内容那一部分做三视角与全局核对。本节也**不新增验证阶段或产物**。
