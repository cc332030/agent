= 通用编码规范·数据与对象（通用层，跨语言）

本文件是通用编码规范的一族之一（**按主题拆分**，其余见同目录 `coding.adoc`、`coding-shape.adoc`、`coding-ui.adoc`、`coding-runtime.adoc`、`coding-source.adoc`、`coding-file-role.adoc`）：对象怎么建、契约用什么承载、怎么访问持久化。

== 对象初始化（手动创建对象时的写法）

**任何语言**都适用：**手动**创建/初始化一个对象时（`new`、构造调用、字面量构造、工厂调用等由本次代码直接写出的创建动作）**一律走链式初始化**——链式初始化指**一次把所属关系串起来的写法**，覆盖**链式 setter**（一类返回对象自身的 setter，`new X().setA(1).setB(2)`）与 **builder**（`X.builder().a(1).b(2).build()`），**具名参数**在语言支持时同属这一档。判据只看**形态**、不看语言。

* **对象初始化：链式初始化优先、无链式才用 `set`、严禁有参构造初始化（L1）**：**手动创建对象一律用链式初始化**（链式初始化 > 逐条 `set`；同一项目内不得一处链式、一处逐条 `set`）；**没有链式形态**（builder 与链式 setter 都不可得）才退回**逐条 `set`**，且仍按「链式赋值顺序随字段顺序」排赋值次序；**严禁**以"参数带着字段一起传"的**有参构造方法**（含全参构造、位置参数构造、`new X(a, b, c)` 形态）**手动创建对象**，**唯一例外**是**对象内的构造方法调用构造方法**（构造链式转发、`this(...)`/`super(...)` 一类同类或父类构造之间的调用）。

**Java 内部再分档：builder 优先于链式 setter（L1）**：Java 侧**优先用 builder 链**（lombok 的 `@SuperBuilder`，`X.builder().a(1).b(2).build()`），**没有 builder 时才退回链式 setter**。**分档理由**：builder 把"正在拼装"的对象与"可用的对象"分开（`build()` 之前拿不到半成品），链式 setter 返回的**就是那个半成品对象本身**、任何一句之后都能被继续引用，即中间态问题在链式 setter 这一档**只减不消**；载体与分档的 Java 侧落点见 `specs/stack/java.adoc`「编码」。

**理由**：① 逐条 `set` 把同一个对象的创建**打散成多行多条语句**，中间态（只设了部分字段）随时可被下一条语句读到，读的人要跨行拼出"这个对象最终长什么样"；② 链式写法把**创建与赋值收在一处**，字段清单只有一个落点（与「链式赋值顺序随字段顺序」同源），构造完即完整对象；③ 有参构造把**参数位置的语义**交给调用点——同一个 `new X(true, false)` 在两个月后没有人能读出这两个布尔各是什么，且**字段增删或重排时调用点无一报错**（同名同类型的参数照样编译通过），属**静默失效**；④ 具名环节（builder 的 `.a(...)`、链式 setter 的 `.setA(...)`）把"哪个值给哪个字段"写在**名字**上，是同一失效面唯一的消除手段。

**例外清单与理由（L2，须逐条写明理由，不得以"这个类用惯了"为由扩大）**：

** **对象内构造方法调用构造方法**：属**类内部**的构造转发，调用点就在类里、参数语义由本类自己的签名保证，不存在"外部调用点凭位置猜字段"的失效面。**误用形态**：把它读成"凡在类里写构造都合规"——在类内**手动创建另一个业务对象**（不是同类/父类构造之间的转发）仍按本条的禁止面处理。
** **框架按声明创建对象**（注入、反序列化、映射/ORM/反射）：创建**不是**本次代码写出来的调用点，其"参数"来自框架声明的契约（构造注入的依赖、全参构造、反序列化的无参构造），不属本条所指的**手动初始化**；这类构造的书写仍按各自规则（Java 侧见「无参 / 必参 / 全参构造优先用 lombok、不手写」）。
** **语言或框架根本没有链式形态**（builder 与链式 setter 都不可得）：退回逐条 `set`。
** **目标对象是第三方类型、不可改**（无 builder、setter 也不返回自身）：只能逐条 `set`；**不得**为凑出链式而包一层自有壳类（那是另一处抽象）。
** **语言惯用的具名构造即该语言的链式形态**（该语言以具名参数/字典字面量表达"哪个值给哪个字段"）：按具名参数形态写，视为满足本条。

**判定标准（任一命中即违规）**：① 本次手动创建的对象里，出现**两处及以上**逐条 `set`（而该类型的语言/技术栈有链式形态可用）；② Java 侧该类型**已有 builder**（标了 `@SuperBuilder`/`@Builder`）却改用链式 setter 或逐条 `set`；③ 手动创建对象时出现**有参构造调用**（`new X(a, b, …)`），而该创建不属上述例外清单；④ 以「这个对象字段少」「这样更直观」「有参构造就一行」为由自我豁免。

**边界（防反用）**：本条**只管"手动创建这个对象时怎么写"**——不管**对象内部**（构造器、静态工厂、builder 自定义方法里的组装）、不管**框架驱动的创建**（注入/反序列化/映射/ORM/反射），也不要求为满足本条去给第三方类型补 builder；**已经写好的链式 setter 与 builder 该怎么排序**不归本条管（那是「链式赋值顺序随字段顺序」）。

**存量边界（L1）**：本条**只管新增与改到的创建点**，**不发动全库改写**既有创建语句（不改既有 `new X(...)`、不批量补 builder）（随动迁移，见 `specs/core/execution.adoc`）。

依据（标准名/编号）：ISO/IEC 25010（可维护性、可分析性——赋值语义须在调用点可见）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Effective Java「考虑使用构建器」（条目 2：**位置参数一多，调用点就读不出哪个值是什么**、字段增删时调用点静默错位；"builder 把对象拼装与可用分开"），以及《重构》（Long Parameter List 属典型坏味道，取向是引入参数对象或具名环节）。**「优先链式初始化（Java 内 builder > 链式 setter）、没有链式才用 `set`、严禁有参构造初始化」是本集合的判据化取舍**——通行材料给的方向是"参数多时用 builder"，**未**规定"手动创建对象一律不得用有参构造、且链式内部再按 builder > 链式 setter 分档"。**与「无参 / 必参 / 全参构造优先用 lombok、不手写」同源**：那条管"Java 类上怎么写构造"、本条管"创建对象时用哪种写法"，两条并存（`@AllArgsConstructor` 供框架用、业务创建走 builder）。

== 数据契约的载体（数据库实体类不进对外契约）

**任何语言**都适用：以数据库表/集合结构为载体的数据对象（下称**数据库实体类**——各语言栈里由对象-关系映射框架或映射注解定义的模型类/结构体）**不得**充当**对外数据契约的载体**——即外部可观测的请求参数、响应返回值。

**识别判据（先判对象，再判规则）**：类/结构体**以表结构为来源**（与表/集合逐字段对应、由映射注解或迁移脚本定义）即属本条所指的数据库实体类。**不看类名**——叫 `UserDTO` 但逐字段对应表结构、被当实体用的同样在禁止面内；反之叫 `UserEntity` 却与表无关的按普通数据结构类判。

* **不得作为对外契约的请求参数与响应值（L1）**：对外暴露的接口（HTTP 控制器方法、声明式 HTTP 客户端接口、RPC 服务契约、消息 DTO 等）**不得**以数据库实体类作为入参或返回类型，也**不得**在入参/返回值里**嵌套**它（集合元素、对象字段、分页包装体内均不得出现）。**理由**：① 对外契约与库表结构本是两份数据，用实体类承载即**同一份数据出现两个来源**（接的字段由表结构定，改一处必漏另一处）；② 外部因此能观测到**不应外露的内部字段**（审计列、软删除标记、内部关联）；③ 字段增删随迁移脚本漂移、**静默破坏既有调用方**。
* **载体取该接口自己的请求/响应类（L1）**：对外接口须使用**为该接口定义的请求类/响应类**（沿用项目既有命名的 DTO/VO/Request/Response 一类，**命名按项目先例、本条不另定命名法**）。**层间转换**按其技术栈的转换规则执行（本集合优先声明式映射，见「对象转换」节）；**转换后不复用实体类本身**。
* **已被调用方依赖的既有接口（L2，须走变更流程）**：理论上该改但会被**显式契约变更**（可能破坏既有调用方）的情形**不是自动的例外**：须先按「跨服务/对外调用的请求响应类优先移动复用」的判定与「破坏性操作」流程处置（对既有调用方构成破坏性变更的，先向用户确认），并在同一轮内补上"该轮改动触达的那部分"的响应类与测试——**是否保留旧形态由用户决定**。
* **判定标准（任一命中即违规）**：① 对外接口的入参类型或返回类型是数据库实体类；② 入参/返回值的字段或集合元素里嵌套数据库实体类；③ 为"省一次转换"而让实体类实现/继承接口契约类型（同一形态的另一种写法）；④ 以"类名不叫 Entity""只多一个字段""内部调用不算对外"为由自我豁免。
* **例外与边界（L2）**：① **纯内部调用**（不经任何跨进程/跨网络边界的同进程函数调用）不在本条范围内；② **持久化自身的出口**（仓库/DAO/Mapper 的返回）不受本条约束——本条只管**对外契约**；③ 项目自身规范**可加严或收窄**本条（如明确"内部 RPC 也适用"），冲突时以项目自身规范为准。
* **存量边界（L1，用户点名"已经用了不管"）**：改到哪个接口才顺带调整；**不得**据此发动全库改造（批量换参数类型、批量补 DTO）（随动迁移，见 `specs/core/execution.adoc`）。
* **例外之例外（口头声明即生效）**：**除非用户主动声明**允许某处（或某接口）以数据库实体类作为请求/响应参数，否则一律适用本条。声明**仅对该次任务、该处生效、不得泛化**（与「改动范围边界」的例外同口径）。
* **不得以键值容器承载方法参数（L1）**：方法参数与返回值的载体是**具名类型**（该操作自己的请求/参数/传输对象）——以**键值容器**（`Map`、字典、哈希一类只有键名、没有成员声明的类型）承载数据时，**字段名、字段类型与必填性都没有落点**：调用方按字面键写入、实现按字面键读取，键名改一处即**静默失效**，两端的键集合也**无法在编译期核对**。**判定标准（任一命中即违规）**：① 本项目对同类参数**已有具名类型或具名先例**，本次仍以键值容器承载；② 该组参数在本次改动里**已有一个等价的具名类型**（同一份数据出现第二个载体）；③ 返回值以键值容器承载本该具名的数据结构；④ 以「这个参数会变」「字段太多」「只是个内部方法」为由自我豁免。

**例外与边界（L2）**：① **键值集合本身就是要表达的数据**（配置项映射、字典表、按动态键查值）不受本条约束；② **框架/第三方契约要求键值容器**的场合（反射入口、动态属性、序列化容器）按其要求走；③ 调用方主动声明允许的**仅对该处、该次生效、不得泛化**（同本节上条口径）。

**存量边界**：改到哪处才顺带调整（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性、安全性的信息暴露面）、ISO/IEC/IEEE 29148（契约须单一、无歧义、可验证）、OWASP API Security Top 10（**API3:2023 Broken Object Property Level Authorization**——"批量赋值/过度暴露"即把内部数据面直接当契约面）。**"对外契约不得以库表结构为载体"是本集合的判据化取舍**；层间转换的优先路径另见本文件「对象转换（多层嵌套对象的转换）」。「参数不得以键值容器承载」一条的坏味道依据为 Martin Fowler《Refactoring》的「数据泥团」（总是成组出现的字段反复成组传递，取向是引入参数对象）；**「参数不得以键值容器承载」是本集合自己的判据化取舍**。

== 对象转换（多层嵌套对象的转换）

不同层/不同模型之间**多层嵌套对象**的转换（对象含对象、集合含对象、逐层都要转），**首选声明式映射**；**无嵌套（单层）的转换不在本条范围内**。具体技术可用的转换库见 `specs/stack/` 对应文件。

* **首选声明式映射（L2）**：转换**优先**由**转换库的映射声明**（映射接口/转换方法 + 字段映射注解等）完成——其价值在"转换只写在一处、映射关系由声明表达"，能在编译期或首次运行前暴露字段对不上。**优先路径不是唯一解**：深拷贝/结构复制工具、序列化中转、手工构建器等等价路径同样合规，按下条判据判。
* **达标判据（判的是结果，不是手段）**：同一份转换**只有一处来源**（改模型只改一处）；该结构增删字段、改字段时，转换处**不会静默漏字段**（能报错/提示，或由声明自动随动）。**手写逐字段搬运**（一层层 `new` + 逐个字段 `set`/`get`、手动递归/循环展开嵌套对象树）**在多层嵌套下达不到该判据**。
* **除主动声明外优先声明式映射；确需手写时须备注原因（L2）**：人来主动声明（代码注释 / PR 描述 / Issue 要求）允许手写的，按声明写；否则优先走声明式映射，确需手写时在代码注释写明原因。**本条不设强制面**。
* **声明的检查强度须真的落到构建期（L2，选了声明式映射时）**：选声明式映射的理由是「字段对不上时**能报错**」——这一半落在**工具配置**上：映射库对「目标字段没被赋到」的处置有**报错 / 只警告 / 忽略**几档，配成后两档时构建照旧成功、缺陷留到运行期表现为「某个字段一直是空」，**等于没有声明式映射**。故取用的映射方案须让这类不匹配**在构建期失败**；确有正当理由不映射的字段**逐处显式忽略**，不得为此把整体策略退回只警告。**判据同「达标判据」**：结构变化时转换处不会静默漏字段——本处说的是「让这条判据有承载」，不是新增一条强制面。
* **映射声明的落点**：映射声明与转换方法**独立成文件、不塞进纯数据结构类**；落点跟随项目既有约定。
* **取用走该技术给定的装配方式（L2）**：映射实现由**依赖注入容器托管**时，**一律经依赖注入取用**——不在调用点以工厂方法、静态实例常量或 `new` 实现类自取实例：容器外自取的那份**装不进它依赖的协作映射**，也与注入的那份成了同一转换的两处来源。**判定标准**：容器托管的映射实现在调用点被自取即违规。**范围**：本条约束的是**取用方式**、与转换是否多层嵌套无关——单层转换的映射实现同样经注入取用。**边界**：项目没有依赖注入容器时本条不适用。
* **例外与边界（L2）**：① 映射声明表达不了的语义（字段名与来源不对应需自定义规则、需外部查值/远程取值、需条件分支决定取值、多来源合成一个字段）不适用，可在映射声明内以自定义方法承接，也可按主动声明手写；② **无嵌套（单层）不在本条范围内**（与字段数量无关）。
* **存量边界**：随动迁移，见 `specs/core/execution.adoc`。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）。**"优先声明式映射、不支持手写转换代码"是本集合的建议取向，非外部标准规定**。

== 持久化访问（数据库/缓存等）

访问数据库、缓存等持久化存储时，**一律走所属技术已提供的类型安全/声明式查询构造 API 与其统一入口（网关）**，不得各自手写原始语句或自建构造器。**具体技术的入口与禁止清单见** `specs/stack/` 对应文件（如 `specs/stack/java.adoc`「持久化访问」）。

* **统一入口（L1）**：持久化操作须经**该技术约定的统一访问入口**调用（数据访问接口、仓储、服务基类、模板/客户端等），业务代码不得自建"临时构造器"绕过该入口。识别特征：调用点出现**技术自带构造器/包装器类的直接 `new`**（或把这类对象当局部变量来回传递）。
* **优先用类型安全/声明式查询构造 API（L1）**：入口提供**类型安全（编译期可校验）**的查询构造 API 时，**优先且一律使用**它——如以**方法引用/属性名引用**表达列名、以**声明式方法名**表达查询（`findByXxx`）、以类型化 Criteria 表达条件。**禁止**用**字符串书写列名/表名**去表达本可由类型安全 API 表达的条件（字符串写列名编译期查不出、改名即静默失效）。
* **替代优先（L1）**：技术自带"替代写法"（同一 API 的类型安全/声明式形态）时**强制使用替代写法**；只在该替代形态**表达不了所需语义**时才退回通用构造器，且须在代码注释写明"为何替代形态表达不了"。
* **判定标准（任一命中即违规）**：① 出现技术自带构造器/包装器的直接 `new`，且该条件可由类型安全/声明式 API 表达；② 列名/字段名以**字符串**写在查询构造中（非注解声明、非框架支持的映射文件）；③ 绕过技术给定的统一入口自建查询构造。
* **例外与边界（L2）**：本条**不**禁止同一技术的正当通用形态——**跨语言语句的承载**（如以映射文件承载 SQL，见 `specs/general/coding-runtime.adoc`「跨语言执行脚本的落点」）不在禁止面内；类型安全 API 表达不了的语义（框架未封装的自定义语句片段、条件化 JOIN、数据库特有函数与提示）允许退回通用构造器或映射文件，但**调用入口不变**。
* **存量边界**：见上条（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）、OWASP Query Parameterization Cheat Sheet（本条在其上**加严**为"构造须走类型安全 API"，属本集合取舍）。
* **访问前先判空、不发起无效查询（L1，跨语言）**：调用持久化接口前，**凡参数取值使该次访问必然查不到任何数据**（主键/唯一键为 `null` 或空、集合/数组为空、必填查询条件缺失）时，须**就地返回**（单条查不到返回"没有"值、批量返回空集合），**不得把这类参数交给数据库**。**理由**：访问本身是外部 IO——判空是本地零成本动作，不判则每次白付一次连接、网络往返与查询解析，可观测为慢查询与被放大的 QPS；这在批量循环里是乘法而非加法（ISO/IEC 25010 性能效率）。
* **返回集合的接口一律返回空集合、不返回 `null`（L1，跨语言）**：查集合类接口在无结果、参数被短路时返回**空集合**；调用方因此无需逐点判 `null`，也避免隐式 NPE。**单条查询**按契约返回"没有"值（`null` 或 `Optional` 一类，跟随项目先例），**不得**为"统一"而把单条查询也改成返回集合。
* **判定标准（任一命中即违规）**：① 主键/唯一键取值未判空即调用按主键查询（典型：`getById(id)`、`findById(id)` 未先判 `id == null`）；② 集合入参为空时仍逐个或整批发起查询（典型：`listByIds(emptyList)`、循环体里未判空即查）；③ 集合类接口在无结果路径上 `return null`；④ 以"调用方会传对"为由不判（本条的失效目标正是调用方传错时的无效 IO，不是"参数不合法"这一层）。
* **边界（L2，防反用）**：本条**只**管"参数使查询必然无结果"这一类**无效访问**与"集合返回 null"这一种**契约缺陷**；**不**要求为**合法但可能查不到**的取值（不存在的 id、不匹配的条件）加任何前置判断——那属于正常业务路径，**不得据此把正常的"查不到"包成提前返回**（会掩盖数据缺失、也会让调用方以为数据不存在）。**须真的去查**的语义（存在性校验、幂等写入前的探测）不受本条约束，不受影响。
* **存量边界**：改到哪个调用点才顺带调整（随动迁移，见 `specs/core/execution.adoc`）。

=== 方法名与逻辑删除的对应（查询方法名即删隐面）

**删除标志**＝数据行上的**逻辑删除标记**（各技术的载体名可能不同：布尔列、时间戳列、状态列、由 ORM 注解声明的删除字段等）。**删隐面**＝本次查询在删除标志上的取向：**不过滤删除标志**（含已删数据）／**只取未删**／**只取已删**。**"默认"＝不带任何删隐面特征的方法名所表达的那一面**。

* **方法名即删隐面（L1，适用所有语言与持久化技术）**：查询方法名**只准表达"默认"这一面**——**默认面取该技术是否自动附加删除标志条件**：① 持久化技术**不自动附加**删除标志条件时（未启用逻辑删除，或自行实现而调用点须显式写条件），**默认＝不过滤删除标志**；② **自动附加**时（框架的逻辑删除默认生效），**默认＝只取未删**。**须查**非默认面的数据时（该技术不自动附加时的"只看未删/只看已删"、自动附加时的"含已删/只看已删"），**方法名须带该面的特征词**（各技术栈的取值落点见 `specs/stack/` 对应文件）。

**理由**：同一个不带特征的名字在两种技术下一次是"含已删"、一次是"只取未删"，**删隐面只能从技术配置反推、读代码的人与评审者都无从预期**；"默认"也因此不再是"约定俗成的那一面"，而是"这一行的技术恰好怎么配"。**判定标准（任一命中即违规）**：① 不带删隐面特征词的方法名查询了**非默认面**的数据；② 带特征词的方法名与它查询的删隐面不一致；③ 同一实体上同一删隐面并存两个名字（含特征与不带特征各一个）；④ 以"项目里没启逻辑删除""反正能查出数据""配置里写着"为由自我豁免。
* **默认面的判定只在一种情形下另有出处（L2）**：项目自身规范或该项目既有先例已明确"这个项目里不带特征的名字查哪一面"时按其执行，**在同一项目内只保留一种默认口径**；项目没写、也没有先例时，按上一条取值（技术是否自动附加）。**不得**以"框架文档这么定的"直接当项目的默认——同一项目里各实体可各自配置（实体注解 = 声明该实体启用逻辑删除，**只决定该实体的默认面、不决定整个项目的方法名默认面**）。
* **例外与边界（L2）**：① 本条**只**约束**按实体/表做查询的方法名**——非查询方法、局部变量与参数名、非实体的数据结构名不适用；② `includeDeleted`/`withDeleted` 一类**显式表达该面的参数或调用形态**与特征词等同，不构成第二套口径；③ 同一技术的**框架自带**方法名不受本条改写范围约束（如框架自带的按主键查询按其自身语义生效）——它们是框架契约的一部分。
* **存量边界（L1）**：改到哪个方法才顺带定名；**且不得据本条做全库改名**（改名会同时破坏调用方与下游契约）（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性：同一名字在不同技术配置下含义漂移、删隐面不可从名字预期）、ISO/IEC/IEEE 29148（判定须可验证）、《阿里巴巴 Java 开发手册》（方法名须望文生义、避免歧义）。**"默认面随技术是否自动附加删除标志条件而变、非默认面须带特征词"是本集合的判据化取舍**——外部材料只给"命名须表意、避免歧义"这一下限；本集合的取舍与实证见依据图书馆『规范准入与自身取舍』主题。
* 依据（标准名/编号）：ISO/IEC 25010（性能效率、可靠性）、ISO/IEC/IEEE 29148（判定须可验证）。**本集合的取舍**：主流框架与通行写法并不强制这一层判空（把参数校验交给调用方或数据库），本条把它提为 L1，理由是"无效访问是外部 IO 成本 + 集合返回 null 是契约缺陷"两者都不可接受；技术栈侧的落点与用法见 `specs/stack/` 对应文件（Java 见 `specs/stack/java.adoc`「健壮性」）。
