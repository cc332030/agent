= 规范分类与准入规范（通用层）

本文件回答四个问题：**一条规则该不该收、收进哪一层**（分类与准入）、**一条规范该定哪一级**（定级口径）、**提出新增规范时如何校验与升级要求**（提案校验）、**规范集合自身如何重构与瘦身**（自身重构）。仅当工作涉及"新增/调整/归位/重构规范条目"时加载。

依据：规范集合本身是**受配置管理约束的资产**，其增删改须有准入与变更控制，不得随讨论零散追加——变更控制与配置项管理见 ISO 10007（配置管理指南）、ISO 9001 之文件信息控制；需求须可验证、可追溯到干系人需求见 ISO/IEC/IEEE 29148（需求工程）；要求须简明、无歧义、能被独立理解见 ISO/IEC Directives Part 2（草拟与表述规则）；软件生命周期过程另参考 ISO/IEC/IEEE 12207；术语定义另参考 ISO/IEC/IEEE 24765（系统与软件工程词汇）。

== 公共规范还是项目规范（归属判定，先判定再动手）

判定**一条规则该进公共内容还是项目自身规范**，只看一条标准：**对谁成立**。

* **对任意项目/任意语言成立**（如 `git mv`、文档不得注水、测试失败以代码为准）→ **公共内容**（`AGENTS_COMMON.adoc` + `specs/`），随规范分发给引用方项目。
* **只对某个项目成立**（项目模块划分、业务模块名、包名、私有库与私有约定、按某公司要求收紧的规则）→ **该项目自身规范**（引用方项目根目录 `AGENTS.adoc`），不进公共内容。

判定要点（有歧义时逐条套用）：

* **替换主语测试**：把主语换成"另一个不想看到这条规则的项目"——规则若因此变成错误要求，则它是**项目规范**；规则仍然成立才是公共规范。
* **不得凭"谁在用"归类**：某规则**当前只有本项目需要**≠它只对本项目成立。可推而广之者仍属公共规范（按使用频次归类会把公共规则错标成项目私有，是常见误判）。
* **项目收紧不算公共规则**：项目可以在自身规范里对公共规则**加严**（公共规范与项目规范冲突时以项目自身规范为准，见 `AGENTS_COMMON.adoc`「访问与解析」）；**加严要求本身不进公共内容**，公共内容只保留下限要求。

== 公共规范的类型与分层（同一条公共规则的正交三问）

一条公共规则须同时回答三个**相互正交**的问题，答案缺一即"不知道该写进哪里、何时加载"：

. **适用层级（放进哪一层）**：必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层——分层定义、存储位置与加载规则见 `AGENTS_COMMON.adoc`「分类与懒加载」，本文件不重复表述。
. **适用语言/技术栈**：跨语言 → 只写进通用层文件、**不得**在各栈文件中重复收录；某栈专属 → 写进 `specs/stack/<栈>.adoc`，并按 `AGENTS_COMMON.adoc`「技术栈扩展约定」在调度器登记**检测特征**（存在哪些文件/依赖/注解即触发加载）。
. **适用项目类型/平台**：仅对特定项目类型生效 → 写 `specs/general/` 下，并在调度器"项目类型层"登记，由**项目主动声明**触发（不靠特征自动检测）；仅对某平台生效 → 写 `specs/platform/<平台>.adoc`。

粒度上另有一条硬线：**收录"可推而广之的规则"，不收录"局部决策"**——项目自己的选型、取舍、约定属局部决策，写进对应代码注释或项目自身规范，不进公共内容。

=== 同一条规则有两种读法（读的形态要跟着场景变）

同一条规则有两个受众、两种场景，**写法必须跟着场景变**（否则要么啰嗦、要么丢依据）：**执行**时它是命令——AI 只需要"怎么走"，多出来的"为什么走这条路"是**占注意力的噪音**；**思考与决策**（新增/调整/定级/重构规范、出现取舍或争议、复盘）时它是依据——没有"为什么"，依据无从追溯、取舍无从判断。

判定口径（三条，均可核对）：

* **按场景分形态**：执行场景**只给规则 + 判定标准 + 依据名**（"做什么、怎么判断做到没做到、依据哪个标准"）；思考与决策场景**在同一处补原因与取舍**（依据讲清、备选方案与不选原因写明，ISO/IEC Directives Part 2 要求说明性内容不混入要求、ISO/IEC/IEEE 29148 要求可追溯）。
* **两形态同源、不复制两份**：同一处只保留**一份完整定义**（含依据），其余位置**一行引用**（做法见 link:../core/priority.adoc[]「强调的正确做法」）；**禁止**把"解释"另抄一份、也**禁止**为让执行侧干净而把依据直接删掉（那是内容减少，见该文件 P3）。
* **执行侧只读必要项**：常态不做解释，仅当(1)**要执行者思考或决策**、(2)存在**争议或取舍**、(3)**用户要求解释**时给出（"为什么"的详略按此裁剪，属行程安排的取舍——link:../core/execution.adoc[]「范围控制」）。

> 边界：本口径约束"规范、提示词、给 AI 的任务说明"的**写法**，不改变各条规则的级别与判定标准；也不得借"精简给执行者的信息"删掉任何规则或判据（完整性是底线，见 link:../core/priority.adoc[] P2、P3）。发布形态与"可执行产物由源码构建"类似：**发布给执行者的是压缩后的可执行形态（规则+判据+依据名），完整依据与论证留在同一处的定义里**，不随执行链分发、也不消失。

== 准入判定（该不该收进规范集合）

新增条目**须先过准入判定**（八问，逐项可答"是"才收；任一为"否"即改为不新增，或改写为项目规范/代码注释）：

. **通用性**：对任意项目/语言成立？只对某个项目成立 → 进项目自身规范（见上「公共规范还是项目规范」）。
. **可执行**：有明确判定标准（能核对、能指向具体文件或取值），不靠"尽量""注意"这类无抓手表述？**要求须可验证**（ISO/IEC Directives Part 2；ISO/IEC/IEEE 29148）。
. **非重复**：与现有条目不重复、可归并；能归入既有条目即**改既有条目**、不新增（去重边界见 link:../core/priority.adoc[]「最高关注项与去重的冲突处理」与「强调的正确做法」）。
. **有依据**：**条目可被标准佐证**时须标注出处（只写标准名/编号、不附链接，做法见 link:../general/source.adoc[]「外部引用（标准/文献/规范）」）；**项目自身的取舍/自定约定不适用**，**不得为凑出处硬引标准**（判断两条的边界同上）。
. **有承载价值**：承载可核对的**事实/决策/边界/取值**（或缺失会重复踩坑的**教训**）——空话套话、复述既有结论、为对称凑数者一律不收（link:../general/doc.adoc[]「注释与文档」的文档质量与"不得注水"）。
. **能定级**：该条属 L1 强制 / L2 建议 / L3 允许，可依四问（违反后果、豁免性、可验证性、代价与误伤）判定并可举证？**级别不定即不得收录**——含两个强度或「很重要但说不清能不能例外」的条目，须先拆条再定级（口径见下「如何给一条规范定级」）。
. **有落点**：能**明确**归入某一层与某一文件，且有**触发加载的特征/声明**（否则写了也不会被加载，规则实际失效，见 `AGENTS_COMMON.adoc`「规范文件登记完整性」）。落点不可判定时先补分层与触发条件再立项。
. **成本可接受**：规则的加载体积与约束强度可接受、**不高频误伤**——规范会被加载进 AI 上下文，篇幅越大越易挤爆上下文、限制过严会挤掉合理裁量（见下「规范集合的自身重构」之"常驻层只放底线"）；要约束"必须统一"的点，不约束无必要统一的点。

== 如何给一条规范定级（定级口径四问）

条目在写入规范前须用以下四问定级（**依据**：RFC 2119 / RFC 8174 以 `MUST`/`SHOULD`/`MAY` 划分**违反后果**，RFC 8174 要求只用规范用语表达强度、避免歧义；ISO/IEC Directives Part 2 要求"要求（shall）"须**可验证**、等级越高**验证越严**、"要求"与"建议"不得混用；ISO/IEC/IEEE 29148 要求需求**单一、无歧义、可验证、可追溯**）：

* **Q1 违反后果**：违反它会**破坏不可恢复的事实**（提交历史、内容、追溯链）、产出**错误或有害的结果**（行为错误、契约破坏、数据/安全受损），还是只降低了**质量与效率**？前者为 L1，后者降一级。
* **Q2 豁免性**：有正当理由（更贴合场景、成本不可接受）时**能不能豁免**？不能豁免即 L1——如"不误改用户数据""不丢规则"属无论何种场景都不成立的底线，故不设例外。
* **Q3 可验证性**：有**明确判定标准**（可指向文件/取值/命令核对）吗？有则最多可定 L1；**没有则只能为 L2/L3**（无法验证的"必须"形同强制，在争议中无法判断是否被遵守——这是 L2 与 L1 的分水岭）。
* **Q4 代价与误伤**：遵守它的成本（改动量、上下文体积、约束强度）与**高频误伤风险**是否可接受？代价或误伤过高者应降级或收窄适用范围（准入判定"成本可接受"的落地判定）。

依赖关系按 **"不满足 Q1-Q3 之一者不得为 L1"** 执行：**L1 = 有可验证判定标准（Q3）+ 不可豁免（Q2）+ 违反后果严重（Q1）**；只"重要"但可豁免、或无法验证的条目，写为 L2。**定级只看这四问，不看条目被写在哪、写了多长、反复提了几次**——等级不由位置、篇幅或重复次数决定（见 link:../core/priority.adoc[]「强调的正确做法」）。

=== 与条款类型一一对应（L1 / L2 / L3 判定表）

Q3 "可验证"的具体判据是**条款类型**：合规性条款（shall，可逐条核对）为**要求**，说明性/建议性条款（should/may）为**建议/允许**（依据：ISO/IEC Directives Part 2）。

[cols="1,3,1,1"]
|===
| 类型 | 形态（例） | 定级 | 依据 |
| 合规性约束（shall） | 必须、严禁、不得、禁止（可核对为"是/否"） | **L1** | ISO/IEC Directives Part 2 的"要求"分类；RFC 2119 `MUST`/`MUST NOT` |
| 可核对的结构性约束 | 登记双向一致、引用可解析、模板逐字保留（可由脚本核对） | **L1** | 同上（要求须可验证） |
| 带豁免条件的规则（shall，附条件可豁） | 原则上……、除……外不得……、默认……（豁免须说明理由） | **L2** | ISO/IEC Directives Part 2（要求/建议不混用）；RFC 2119 `SHOULD` |
| 优先级/顺序类指引 | 优先 X、先 Y 后 Z、宜…… | **L2** | 同上（属可偏离的行程安排，非正确性底线） |
| 风格/偏好类 | 建议、尽量、倾向于 | **L2** | 同上 |
| 容错类（出错后才生效） | 兜底、遇到……时重试/降级、不确定时先确认 | **L2** | 同上（正常路径不受约束、失败时才有强制动作） |
| 可选做法 | 可以、非强制 | **L3** | RFC 2119 `MAY` / ISO "may"=允许 |
| 说明性内容 | 为什么这么做（原因、依据、背景） | **不参与分级** | ISO/IEC Directives Part 2（说明不构成要求） |
| 判定依据 | 判定标准、核对清单、检查命令 | **不参与分级**（随其所解释的条款同级） | 同上 |
| 示例/中性说明 | 举例、比较、常见写法 | **不参与分级** | 同上 |
|===

表用口径（**防"定级只看关键词"的误判**）：

* **条款类型优先于关键词**：等级由**条款类型**决定，关键词只作归并用语（见上「定级口径四问」）——同样是"优先"，出现在行程安排里是 L2，出现在安全/正确性底线里才是 L1。
* **标题、章节说明、依据出处不参与分级**：文档节标题、节的引言、引用的标准名称与编号本身不构成要求，不得只因含"必须/禁止"字样就被当作 L1 条目。
* **标注落在条款本身**：级别须标在**具体的强制点**上（"此类问题直接修复（L1）"），不标在整节或整条开头；一条并列要求含两个强度时**拆成两条分别定级**（L1 与 L2 混写是歧义之源）。

=== 归属谁（对象 × 强度两维判定）

等级之外，条目还须判定**"对谁强制"**——等级与对象是相互正交的两维，缺对象则"强制"落到不该落的地方（依据：ISO/IEC/IEEE 29148 需求须**单一、可追溯到干系人**）：

* **两维独立**：先按「定级口径四问」定强度（L1/L2/L3），再判定对象（对**AI 执行**强制、对**引用方项目**强制、还是约束**维护规范集合**的动作）；**同一等级可作用于不同对象**，等级不等于对象。
* **L1 须落在可控对象上**：L1 条目必须由执行者**能够核对或控制**——规范集合看不到引用方项目的代码与操作，故"面向引用方项目工作区"的条目（如 `git mv`）以**规范文本写清判定标准**为落点，且**不得声称由规范集合自带的脚本强制**（声明与实际不符即"定义未执行"）。
* **对象须写明**：条目须能回答"谁必须做到、凭什么判定"，无法回答即为对象不明，须先澄清再收录。
* **冲突次序**：L1 之间冲突以 link:../core/priority.adoc[]「最高关注项」为准；公共规范与引用方项目自身规范冲突以项目自身规范为准（见 `AGENTS_COMMON.adoc`「访问与解析」），此时仍**不得丢失 L1 的完整性要求**。

=== 归类举证（写入规范时同步登记）

定级结论须**可追溯**：新增/调整条目时，在提交说明中写明该条的**对象**（对 AI 执行 / 引用方项目 / 维护规范集合）、**依据**（标准名/编号，标准可得性判据见 link:../general/source.adoc[]）、**条款类型**（合规性约束 / 优先级指引 / 风格偏好 / 容错 / 可选 / 说明）与**定级结论**（L1/L2/L3 或"不参与分级"）——四者齐备才可定级（ISO/IEC/IEEE 29148 的可追溯要求）。规范集合**不设**级别清单表（会与条目本体双份维护、必然漂移），改由机械校验核对**现存级别未被静默改动**（见下「级别变更与复盘」）。

=== 级别变更与复盘（防降级、防级别混乱）

* **级别变更须说明理由**：调整某条的级别须写明依据与影响，不得静默改级（RFC 2119 的用语一致性、ISO/IEC Directives Part 2 的变更控制）。
* **改动时机械核对**：批量调整/去重后须核对待改范围的级别标注（`（L1）`/`（L2）` 一类）**未被误改**，并按「写入与登记」走登记与自检（依据：ISO 10007 配置管理的变更控制——变更须可追溯、不得顺手改动）。
* **定期复盘级别混乱（六查）**：条目级别会随时间累积漂移，须定期核对六类症状并归位——① 同一事项在不同文件里级别不一致（同一约束只能有一个级别）；② 带豁免条件的规则被写成"必须"（应为 L2）；③ 顺序/风格偏好被写成 L1（关键词绑架条款类型）；④ 必加载层（`specs/core/`）出现与"底线"无关的 L2/L3 条目（见「规范集合的自身重构」常驻层判据）；⑤ 无判定标准的"必须"（无法验证，应降级或补判定标准）；⑥ 只在文档里无机械抓手的 L1（须补抓手，见下「新增规范的提案校验」）。

== 新增规范的提案校验（先校验、再登记、后写入）

用户提出"新增/调整某条规范"时，**先按以下顺序校验其要求，不得直接照写落盘**：

. **理解与澄清（不臆测）**：先复述其要解决的问题与期望边界；需求有歧义时**先提问澄清**，不自行假设后动手（见 link:../core/execution.adoc[]「指令执行」）。
. **校验要求的合理性（可执行性）**：判定标准是否明确、能否被核对（对应准入判定"可执行"）。**模糊要求一律先具体化**再收录——把"要规范点""要注意安全"这类表述，改写成带判定标准的条目（如"指定列时 s 值与列数不得相同，否则该列全列为空"）。
. **检查是否已有标准（别自己造）**：该主题是否已有业界标准/权威约定（ISO/IEC/IEEE、RFC、W3C、OWASP、POSIX、SemVer、PEP 等）。**已有标准则优先引用标准**，不另造一套说法——出处只写标准名/编号、不附链接（依据：ISO/IEC Directives Part 2 要求术语与表述规范，且规范性文件引用现行文件优先于重述）。
. **检查是否已有本项目条目（不重复收）**：在 `specs/` 与项目自身规范中检索同主题条目：**已覆盖 → 不新增**（至多补一句引用）；**部分覆盖 → 归并进既有条目**，不另起一条。
   **全局性默认取更全的方案**：同一约束的多个候选写法/方案中，**默认取覆盖更全、更少例外的那一个**（更全即同时覆盖原需求与同类场景），**例外与降级须有明确理由**；不得因"写起来省事"取覆盖更窄的方案。
   **升级与举一反三（L1）**：把用户的具体要求**抽象到同类问题**，一次把它连带覆盖——①从单例升到规则（"这次这个字段别写死"→"不得写死常量数值"）；②从特例升到同类（"这一个类的注释要完整"→"每个公共成员的注释须齐全"）；③从现象升到成因（"这次忘了写 changelog"→"提交完成定义须含 changelog 条目"）；④检查同一主题的既有条目是否应一并升级、并把新条目登记到对应分组与层级。**升级不得超出用户要求的范围**：**用户明确限定了范围**（只这一个类/只有本次/只改这一处）时，**按其范围执行**，升级只能作为建议提出、不得擅自扩大（见 link:../core/execution.adoc[]「范围控制」）。
. **可机械校验的机械钉住（防"定义未执行"）**：条目若能被确定性校验（存在性、双向登记、关键词、格式），须**同时补机械抓手**（校验脚本 + 测试）——只写进文档、没有任何检查的"必须"条款，等于默认它会被无声违反。

== 规范集合的自身重构（瘦身与归位）

规范集合会被反复调整，**"规范自身的重构"必须有自己的判据**——否则"越写越多"与"越删越散"两种失效都会出现（前者捆住执行者、后者丢规则）。重构按以下固定顺序做，**顺序不可颠倒**（前一步没做完就做后一步，会把"放错位置的内容"直接删掉）：

. **先判归属（公共 / 项目自身）**：按「公共规范还是项目规范」的替换主语测试逐条过；公共内容里出现的"某个项目自己的维护动作、脚本名、仓库结构"即属放错位置，移回项目自身规范或删除。
. **再判层级（放对层）**：把只对特定场景/特定维护动作成立的内容从常驻层移出。**常驻层（`specs/core/`）只放**：①"该怎么做"没有裁量空间的底线（L1 铁律）；②被列为最高关注项、必须每次会话都看到的纪律；③必加载层的引用落点。**放不进去的不是删，而是移到通用层**（用到才加载）——如"如何写规范的元规范"（准入、定级、重构）只对"写规范时"成立，属通用层。
. **再判重复（去重）**：同一约束只保留**一处完整定义**、其余改为一行引用（见 link:../core/priority.adoc[]「强调的正确做法」「最高关注项与去重的冲突处理」）；**最高关注项的引用不属重复、不得合并删除**。
. **最后压缩表述**（压缩不得削弱有效性，验收见下）：只留"规则 + 判定标准 + 依据（标准名/编号）"，删掉论证过程、重复重申与"为什么重要"的长篇铺陈——**不删规则本身**（完整性与内容不减少仍是底线，见 link:../core/priority.adoc[] P2、P3）。

重构后须核对规范有效性（除"不丢内容"外，还须核对**有效性未被改坏**）（把"读起来顺"当成"重构成功"是常见失效：判据被压成口号、依据被删到无从追溯、条目被挪到加载不到的位置——内容看似还在、规则已经不生效）：

* **两形态分离（读者一致性）**：按「同一条规则有两种读法」执行——执行侧只留"规则 + 判定标准 + 依据名"，原因与取舍归思考/决策侧；**依据只允许压缩为"标准名/编号"，不允许整段删除**（标准只作依据、不替代规则本身，见 link:../general/source.adoc[]「外部引用」）。
* **可执行性不降级**：压缩后每条 L1 仍须**可判定**（有判定标准、尽量有机械抓手，见 link:../core/priority.adoc[]「分级定义」）；**不得把"必须 + 判定标准"压成"要注意"**（约束强度随表述漂移即级别失效，见「级别变更与复盘」第 ⑤ 条）。逐条核对：**"必须/不得"仍在、判据仍在、依据（名称/编号）仍在、级别未降**。
* **可见性不丢**：常驻层与各加载入口对最高关注项的**一行引用不得因去重删除**（link:../core/priority.adoc[]「最高关注项与去重的冲突处理」）；被移动的内容在其**新位置可被正常加载**（按调度器的触发特征加载，见 `AGENTS_COMMON.adoc`「规范文件登记完整性」）——**移错层与删规则同属失效**。

重构后必须核验：**体量**（常驻层是否仍膨胀）、**层级**（是否有内容放错层）、**级别**（是否有级别被顺手改动）、**有效性**（判据是否仍在、依据是否仍在、可见性是否仍在，见下）、**引用**（是否留下悬空引用或历史来源注记）——前两项靠人/子 agent 复核，后三项由本仓库的机械校验兜底（见根目录 `AGENTS.adoc`「Agent 项目自身工具声明」）。

判定速查（内容"完全没用"与"放错位置"的区分）：

* **删**：与现有条目重复且无可引用价值；空话套话、无判定标准；只把临时讨论/过程落盘；已被其他文件完整承载且无引用必要；**判据被压成口号（"要注意"）、或依据被整段删掉**（依据可压成标准名/编号，但不能消失）——以及**本仓库工具名、脚本名、仓库结构写进公共内容**（引用方看不到，属声明与实际不符，应删或改为通用表述）。
* **移**：内容有价值但只对特定对象成立——"写规范"的元规范移到通用层；"维护规范集合"的动作移到项目自身规范；某技术栈专属内容移到 `specs/stack/`；只对特定项目类型成立的内容移到"项目类型层"并由项目声明触发。
* **留**：L1 底线与最高关注项（含其在多处的一行引用）、每次会话都需要的判定标准与取值。

== 写入与登记（落地动作）

过审后一次做完四件事，缺一即视为未完成：

* **写入**：按主题归位到对应分组文件（不新增文件即可承载时**不新建文件**，见 link:../general/doc.adoc[]「注释与文档」之"多余文档直接去除"），并按上「如何给一条规范定级」标注级别。
* **登记**：在 `AGENTS_COMMON.adoc` 加载调度器登记（唯一登记处，写文件与登记是**同一个动作**；口径见该文件「规范文件登记完整性」）。
* **同步**：本仓库维护时按根目录 `AGENTS.adoc`「规范调整」同步项目自身规范相关落点。
* **自检**：按 link:../core/priority.adoc[] P2 做完整性校验（机械校验 + 语义复核），并按 link:../general/changelog.adoc[] 记录对外影响。
