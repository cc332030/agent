= agent 协作规范（通用层）

以下规范适用于所有拆分 agent（含主 agent）协作的场景。

**同 Agent 的适用面（L1，先定条件再谈强制）**：本条要求的是**"不得把外部来源当合法复核者"**，它**不是无条件成立的规则**——**"须由与执行者相同的 Agent 承担"只在执行环境里确实找得到同 Agent 的执行者时才有意义**，其前提（同一 Agent 身份、同入口、同一份规范加载方式）由**承载该任务的平台**给出。**故它的成立与判定一律以平台层写明为前提**（CNB 上的落点见 link:../platform/cnb.adoc[]「评论唤起新实例（平台侧的派发入口）」的同名 L1 条）：**平台层写明该前提成立**（如 CNB 的唤起形态——被唤起的 NPC 与执行者本就是同一个产品）→ 按本条强制、不得换外部来源；**平台层未写明**（其他平台、本地人工环境、产品间协作）→ **不得援引本条拒做**，环境不提供同 Agent 的子执行者时**照做该职责**：按本节「协作方式」的『子 Agent 不可用时的降级路径』条由执行者本人串行承担并标注独立性边界，或如实标悬置，**验证与交付不因此缺失**。**为什么不能外推**：把"必须同一产品"当成通用要求，会让**没有同 Agent 子执行者**的环境把"我做不到同 Agent"读成"所以我不能验证/不能交付"——而标准（IEEE 1028 软件评审）只要求**有独立、可核对的评审发生**，**未规定复核者须是同一产品**；"由谁承担"是项目自身的取舍。**判定标准**：①`@提及`/派发目标是不是外部服务或外部 Agent 的标识（该禁令**不因平台而放宽**）；②环境是否**确实提供**同 Agent 的子执行者（未提供时走降级路径，**不以此为由跳过**）。
**子任务必须由与执行者相同的 Agent 承担（L1，强制同 Agent）**：需要子 Agent（子任务执行者、复核者、并行分片）时，**一律由本次任务的执行者已经在用的那套 Agent 承担**——同一 Agent 身份、同入口、同调度器、加载同一份 `AGENTS_COMMON.adoc`。判据（两者同时成立）：①**同 Agent**：派出的执行者与执行者是**同一个 Agent**（同一 AI 身份/产品，如都是本会话所运行的 Agent）；②**同规范**：其入口与规范加载方式与本执行者一致，须加载同一份 `AGENTS_COMMON.adoc` 并按其调度器自行加载。**"用另一个 AI 来复核更独立"不是选择理由**：换成另一个来源（另一个平台的 Agent、外部 NPC）承担同一职责**不属本规范许可的手段**——跨来源的执行者**看不到本执行者已加载的规范**（加载驱动权在入口侧，见 `AGENTS_COMMON.adoc`「从属者适配」），既不能保证同一判据，也无法核对它是否真按判据做；**"换个 Agent" 常被当成解决复核不独立的第一手段，结果引入的是不可控与不可核对**。理由：规范给的是**可核对**（能查它按哪份判据、按什么时限返回、结论落在哪），不是形式上的独立性。

**不得点名外部 Agent / 外部 NPC（L1）**：**不得用点名"另一个 Agent、NPC、某某 AI、某个外部产品"的形式把子任务派出去**——派发对象只能是本执行者这类（同 Agent、同入口）执行者，或按本文件「协作方式」的『子 Agent 不可用时的降级路径』条在本地承担/如实标悬置；**也不得在派发说明里点名某个外部 NPC 作为该项职责的执行者**（如"这一步交给某某 NPC"）。判定标准（任一命中即违规、可逐条核对）：①**派发目标**是外部服务/外部 Agent 的标识（`@提及`、第三方 slug、外部产品名）；②**交换面**超出"本执行者可直接调用的调用/派发"——出现外部平台的会话/接口、外部 Agent 的账号或频道、由人工转交的跨产品协作；③**结论回传面**落在本执行者读不到的地方（外部平台的会话、外部 Agent 自己的记录、人工转述）。**推荐写法**：只写职责与判据（"按三视角复核本次 diff"），由执行者按本规范自行选择同 Agent 的承担方式；**不要出现外部执行者的名字**。理由（本项目实证）：派给外部评审 NPC 的两次分别卡在**派发即失败（镜像不存在）**与**1 小时以上未回传**，复核结论无从采信——点名外部 NPC 的代价是**任务挂起 + 结论不可核对**。

== 资源限制与感知

* 调用次数限制：agent（含主 agent）调用 AI 次数有限（约百次量级），超限后自动停止并要求人工接入；主 agent 自身也要控制调用量，避免超限后需人工接入
* 拆分原则：拆分 agent 不能只按模块拆分（模块大小不均会导致任务量失衡），应按任务量分批拆分子 agent，使每个 agent 的调用次数低于限制
* 失联感知与**硬超时（L1）**：子 agent 超限停止或长时间无响应时主 agent **无感知**，任务会永久挂起（实证：把语义复核派给外部评审 NPC，多轮停在同一节点 1 小时以上、结论未回传，发起方只能人工中止）。故派发时**必须自带超时**：给**每一次**子 agent 调用设**可判定的时限**（数值由项目按任务规模定），到点即视为失联，并按"**放弃该子 agent + 如实记悬置**"处置，**不得无限等待**；探活/重建只是可选手段，**超时是必备手段**。**时限取值须有判据、不得"看着办"（L1）**：按"复核应在**单次任务可承受的量级**内返回"取值——**取"分钟级"档**（如同类任务正常返回耗时的 2~3 倍；实证：一次性模型调用返回 30 秒至 1 分钟量级），并优先选**一次性、边界明确、可超时**的派发形式（把复核做成一次不可追问的调用，比交一个有自主探查权的执行者更可控）；**实测显著超出的形式即应放弃**，不留"它也许会回来"的模糊状态。
* **超时的处置（L1）**：超时（含**没有可用超时机制**时的等价判断：无响应超过约定量级）后**不得**：①把没回传的复核写成"已通过"；②反复重派同一个会卡住的执行者（重复计费、重复卡）；③因此不交付。正确做法是**三条一起**：**换更可控的手段承担同一复核职责**（如把复核拆成一次性可超时的调用）、**把未覆盖的部分逐项标悬置**（写明已覆盖的角度与未由谁覆盖）、**按效力等级如实报告**（见 link:verify.adoc[]「验证的效力等级」）。**"复核者不可用"属概念项、不阻断交付**，但**其覆盖缺口必须写在留证里**。**优先一次性调用（L1）**：子任务（尤其复核）优先选**一次性、边界明确、可超时**的调用形式（给定输入即返回结论、不可追问、不必自行探查），而不是交一个**有自主探查权的执行者**——后者的耗时与边界都不可预估，"超时"在它身上实际上无法判定。
* **复核职责不绑定特定执行者（L1）**：规范要求的是"**有独立、干净上下文的语义复核发生**"，不是"必须由某个 NPC/某个产品来复核"。规范对执行者的约束是**同 Agent、同判据、可核对**（见上文「子任务必须由与执行者相同的 Agent 承担」「不得点名外部 Agent / 外部 NPC」）；**另一个来源的 Agent 即使可用，也不因其"更独立"而成为许可的复核者**。

== 派发入口（往哪派、派什么）

* **评论唤起是"评论即派发入口"的一种形态（L1）**：**在 Issue / PR（或等价的任务单、讨论串）下新增一条评论、在评论里点名叫起某个 NPC/Agent 并说清要求**，即在该任务单下新增一次执行（平台侧口径见 link:../platform/cnb.adoc[]「评论唤起新实例」，但"评论即入口"本身是平台无关的通用机制）。**该入口不豁免本文件的任何派发判据**——派给谁、有没有点名外部 Agent、派发对象是否钉定、是否自带硬超时、派发前是否确认执行者可执行，**一律照判**；入口只是"往哪派"的通道，不是"放宽"的理由。
* **一次评论 = 一次派发，任务边界由评论正文界定（L1）**：被唤起者读到的任务就是**那一条评论**——要求须在评论里**写清目标、边界（改哪、不改哪）、产物形态（只分析 / 改代码 / 出报告）与验证口径**；**未写清的不得自行假定后开工**（"目标、范围、产物形态不明确时不得自行假设"，见 link:../core/execution.adoc[]「指令执行」）。**"@ 一下"本身不是派发**：只有点名、没有要求时不得自行开工，应回问范围与产物形态。
* **"一次评论 = 一次派发"的计数口径（L2）**：**一条评论 = 一次派发**；同一任务单下**另起一条评论**即另一次派发（**不合并计算**——每次都重新提出要求、重新计调用量）；**一条评论里点名多个对象时，按被点到的对象个数计 N 次派发**（这一形态本身受上条"点名外部 Agent"约束）。故评论里**不必**重复描述同一任务的全部背景——**派发入口只负责"这一次要做什么"，上下文不继承**（见下条）。
* **可要求"用干净上下文"，但这是要求不是保证（L1）**：评论里可显式要求被唤起者**使用干净上下文**（不沿用此前评论里的结论与前提、按本次要求独立判断）。收到该要求时须**当作全新任务**：**"干净"只指"不继承此前对话里的结论与前提"**——**不豁免本文件任何派发判据**（同 Agent、钉定对象、硬超时、派发前确认执行者可执行**一律照判**，见下「派发对象须钉定与可执行」），也**不意味着"连本次自己的对象钉定都要另取一套"**（钉的是本次要处理的那个对象，同一目标同一 sha 即可）；需要先前事实时**按对象钉定重新取值**（钉 commit sha），**规范仍须按入口重新加载**（"上下文干净"只清历史对话、**不清约束**，"上级已读过"不构成免责）。**能否真的新开/清空上下文属执行环境能力**，故须先自评、不确定按不可用处理（见 link:../general/self-check.adoc[]「环境能力自评」），并**在结论里如实说明本次实际读到的上下文范围**——不得把"要求过"写成"已经发生"。
* **评论是"派发者"的入口，不是"执行者"的手段（L1）**：该入口由**派发者**（人工，或按用户明确授权代为派发的执行者）在任务单下发起；**执行者不得自行发一条评论去唤起另一个 Agent/NPC 来接手自己的活**（那是把子任务点名派给外部执行者，属上条「不得点名外部 Agent / 外部 NPC」的禁止形态，且会让任务在等待中挂起）。区分判据：**人工在任务单下发起**＝派发入口；**执行者在任务进行中自行 @ 另一个 Agent/NPC 去干活**＝点名外部 Agent（违规）。**该入口不扩权**：不会因为"评论里 @ 一下就能起执行"而使本文件其他条失效。
* **执行者不得自行发评论唤起自己（L1，防无限派发）**：**执行者不得在本次执行中自行发一条评论点名唤起自己**（也不得转由他人/其他执行者代发）——**发起下一次是"派发者"的动作**，故这条与上条同源：评论入口由派发者（人工，或按用户明确授权代为派发的执行者）发起，**执行者"想分步"不是派发的依据**。**想分步的唯一正当形态**：**先停**、只输出一次"停下确认"（把"已做完哪段、下一步要什么"一次性写清），由**人**另发一条评论决定要不要再来一次；**跨轮分步由人决定、不由执行者自动续跑**（判据：本次执行期间是否新增了一条指向本次唤起名的点名评论——发了即违规；"分两步更清楚""上一轮没做完"都不是理由）。平台侧的同口径条与判定标准见 link:../platform/cnb.adoc[]「评论唤起新实例（平台侧的派发入口）」。
* **"复核者的来源"与"复核的发起"是两件事（L1，不自派 ≠ 不许复核）**：需要复核时**不得**把"满足同 Agent"读成"必须再发一条评论叫一个 Agent 来"——**一个任务只由人决定起几次执行**；本平台上执行者**不能**用 @ 自己换取一次带干净上下文的新执行来做自己的复核（自派，见上条与 link:../platform/cnb.adoc[]「评论唤起新实例（平台侧的派发入口）」），**也不得**因为拿不到额外的复核者就跳过复核、把任务停在中间或以"等下一次"为由不交付。此时的判据是两条：①**拿不到同 Agent 子执行者时按本节「协作方式」的『子 Agent 不可用时的降级路径』条在本次执行内补**（本人串行 + 标独立性边界，或标悬置并写剩余风险）；②**交付照常**，结论里**如实写明缺口**（'可信的独立复核不可得 + 已做的替代核对 + 剩余风险'），**"已交付 + 校验全绿 + 缺口如实标出"不得混写成"已复核通过"**。
* **要求未写清或判据不满足时的形态（L1）**：**要求须在评论里写清**——至少写清**做什么、边界（改哪/不改哪）、产物形态（只分析/改代码/出报告）、验证口径**；"写清了"的判定主体是**执行者**，但其判定**须可核对**（按上述四项逐项对，缺哪项列哪项）。判据不满足（如派发对象钉不定、超出权限）或要求缺项时，**执行者须在原评论下回复：拒绝并列出缺失项，或明确请发起人补一句**——**不得开工、不得拿"他没写清"当擅自扩大范围的挡箭牌，也不得只回一句"不能做"**（拒绝不等于不响应）。**留证落点即该条评论下的回复**：须写明本次**读到了什么**（对象钉定、实际上下文范围）、**做了什么/拒了什么**，使事后可核对——这是"事后能否审计"的唯一落点。
* **评论不得删除（L1，平台无关）**：**任务单（Issue / PR / 讨论串）下的评论一律不得删除**——含 NPC/执行者生成的评论、含“看起来只是过程性叙述”的那条。理由：**评论是派发的对象钉定与留证落点**（这一轮收到什么要求、回了什么、当时钉的哪个 commit sha 全靠它），**删除不可逆**，删掉即事后无法复核；**编辑掉原话与删除同效**（原话一改，“当时要求了什么”无从核对）。**“发错了”的正当处置是再发一条更正或回复补充**（写明更正了哪一条），**不是抹掉**；确需清理时由**人**在平台上自行处理。**判定标准**：调用删除评论的接口/命令、编辑既有评论使其与原话不一致、转交他人/其他 NPC/CI 步骤代删——任一命中即违规。**边界**：清理本地 `tmp/` 与构建产物照旧（见 link:../core/execution.adoc[]「临时产物」）；“评论不是交付”讲的是**评论不计入交付物**，**不得反读成“评论可删”**。平台侧的同口径条与判定标准见 link:../platform/cnb.adoc[]「评论不得删除」。
* **本入口与"文件操作强制检查"的边界（L1，"评论不是交付"）**：**发一条评论不等于完成下一件事，也不等于可以改文件**——通过入口派发的工作，其改动一律按本条任务自己的范围与规范执行（改文件仍按 link:../core/execution.adoc[]「文件操作强制检查」与 link:scope.adoc[]判，"评论里说了"不构成越界改动或合并的授权）。

== 派发对象须钉定与可执行

* **派发对象须钉定 commit sha（L1）**：把"某分支/某 PR 的改动"作为复核、比对、追溯对象时，派发指令里必须写明**具体 commit sha**（见 link:../platform/cnb.adoc[]「对象钉定与可追溯」）——分支名会被后续推送改变，收到方若按分支名自行取值，极易取到过期对象、产出与被复核内容不符的结论（实证：复核者取到已被压缩提交取代的旧 sha，逐项比对后误判"改动不存在"；另一参与者又用了另一个中间 sha）。**收到"基于某分支"的派发时，须先强刷 ref 再取 sha**（`git fetch -f` + `git rev-parse`），并在结论中写明所核 sha。
* **派发前确认执行者可执行（L1）**：派发前须确认执行者的**运行前提实际成立**——所需镜像/制品包存在且可取（实证：某执行者的制品包在制品库 `not found`，流水线在 `Prepare` 阶段 `docker pull` 失败，任务从未真正开始，看似"在跑"实则早已失败）；同名执行者可能来自不同来源，须用**确证可用的那个**。执行者的**可用性**属环境前提，派发者负核对责任，不得假设"派了就是能跑"。
* **压缩提交/强推前确认无人在用旧对象（L1）**：对分支做 `squash`/`rebase`/force push 前，须确认**无他人正基于旧 sha 工作**（已派发、正等待结论）；确需执行时，须**明确告知**受影响方新 sha、并把旧 sha 上的结论标为过期（见 link:../platform/cnb.adoc[]「对象钉定与可追溯」）。

== 协作方式

* 大任务优先使用子 agent：项目级检查（测试检查、code review、全量修改等）优先拆分给子 agent 执行，主 agent 只做任务编排、结果汇总与最终验证；子 agent 的执行边界须在派发指令中写明（如禁止并发构建、只写文件不验证等），避免多 agent 相互冲突；子 agent 不执行构建验证时，由主 agent 统一串行验证
* **子 Agent 不可用时的降级路径（L1）**：同 Agent 子执行者不可用（环境不提供子 Agent 能力、派发失败、超时）时，**不跳过该职责，也不换任何外部来源的 Agent 顶替**，按序降级：①**由执行者本人（主 agent）串行承担**同一职责（如三视角复核由主 agent 在同一会话内按同一判据逐项过），并在留证中标注**独立性边界**（复核者与改动方同一上下文，独立性弱于第三方）；②仍不可行时**如实标悬置**、写明未覆盖的角度与剩余风险。降级后**明确交付**，不因机制缺失把任务停在中间；"以机制不可用为由跳过"与"假装已委派"都属违规（见 link:../general/self-check.adoc[]「环境能力自评」）。**"本环境没有同 Agent 的子执行者可用"不是改用外部 Agent 的理由**——它只把路径指向本条降级。
* 步骤隔离：多步骤任务（调研、设计、编码、写用例、用例验证、文档等）步骤间无依赖时，优先各自用干净的子 agent 独立完成——子 agent 上下文隔离，避免前序步骤的上下文影响后续步骤；主 agent 负责编排与汇总
* 同一对象只起一个子 agent（L1）：同一批文件、同一份 diff 的核对**合并为一次派发**、一次读取、结论分栏列，不"一个视觉一个子 agent"地重复起——重复起子 agent 是重复读取与重复计费，且两次派发拿到的证据面本就相同；多个视角的合并方式见 link:verify.adoc[]「规范验证」
