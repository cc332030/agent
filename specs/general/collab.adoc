= agent 协作规范（通用层）

以下规范适用于所有拆分 agent（含主 agent）协作的场景。

**子任务必须由与执行者相同的 Agent 承担（L1，强制同 Agent）**：需要子 Agent（子任务执行者、复核者、并行分片）时，**一律由本次任务的执行者已经在用的那套 Agent 承担**——同一 Agent 身份、同入口、同调度器、加载同一份 `AGENTS_COMMON.adoc`。判据（两者同时成立）：①**同 Agent**：派出的执行者与执行者是**同一个 Agent**（同一 AI 身份/产品，如都是本会话所运行的 Agent）；②**同规范**：其入口与规范加载方式与本执行者一致，须加载同一份 `AGENTS_COMMON.adoc` 并按其调度器自行加载。**"用另一个 AI 来复核更独立"不是选择理由**：换成另一个来源（另一个平台的 Agent、外部 NPC）承担同一职责**不属本规范许可的手段**——跨来源的执行者**看不到本执行者已加载的规范**（加载驱动权在入口侧，见 `AGENTS_COMMON.adoc`「从属者适配」），既不能保证同一判据，也无法核对它是否真按判据做；**"换个 Agent" 常被当成解决复核不独立的第一手段，结果引入的是不可控与不可核对**。理由：规范给的是**可核对**（能查它按哪份判据、按什么时限返回、结论落在哪），不是形式上的独立性。

**不得点名外部 Agent / 外部 NPC（L1）**：**不得用点名"另一个 Agent、NPC、某某 AI、某个外部产品"的形式把子任务派出去**——派发对象只能是本执行者这类（同 Agent、同入口）执行者，或按本文件「子 Agent 不可用时的降级路径」在本地承担/如实标悬置；**也不得在派发说明里点名某个外部 NPC 作为该项职责的执行者**（如"这一步交给某某 NPC"）。判定标准（任一命中即违规、可逐条核对）：①**派发目标**是外部服务/外部 Agent 的标识（`@提及`、第三方 slug、外部产品名）；②**交换面**超出"本执行者可直接调用的调用/派发"——出现外部平台的会话/接口、外部 Agent 的账号或频道、由人工转交的跨产品协作；③**结论回传面**落在本执行者读不到的地方（外部平台的会话、外部 Agent 自己的记录、人工转述）。**推荐写法**：只写职责与判据（"按三视角复核本次 diff"），由执行者按本规范自行选择同 Agent 的承担方式；**不要出现外部执行者的名字**。理由（本项目实证）：派给外部评审 NPC 的两次分别卡在**派发即失败（镜像不存在）**与**1 小时以上未回传**，复核结论无从采信——点名外部 NPC 的代价是**任务挂起 + 结论不可核对**。

== 资源限制与感知

* 调用次数限制：agent（含主 agent）调用 AI 次数有限（约百次量级），超限后自动停止并要求人工接入；主 agent 自身也要控制调用量，避免超限后需人工接入
* 拆分原则：拆分 agent 不能只按模块拆分（模块大小不均会导致任务量失衡），应按任务量分批拆分子 agent，使每个 agent 的调用次数低于限制
* 失联感知与**硬超时（L1）**：子 agent 超限停止或长时间无响应时主 agent **无感知**，任务会永久挂起（实证：把语义复核派给外部评审 NPC，多轮停在同一节点 1 小时以上、结论未回传，发起方只能人工中止）。故派发时**必须自带超时**：给**每一次**子 agent 调用设**可判定的时限**（数值由项目按任务规模定），到点即视为失联，并按"**放弃该子 agent + 如实记悬置**"处置，**不得无限等待**；探活/重建只是可选手段，**超时是必备手段**。**时限取值须有判据、不得"看着办"（L1）**：按"复核应在**单次任务可承受的量级**内返回"取值——**取"分钟级"档**（如同类任务正常返回耗时的 2~3 倍；实证：一次性模型调用返回 30 秒至 1 分钟量级），并优先选**一次性、边界明确、可超时**的派发形式（把复核做成一次不可追问的调用，比交一个有自主探查权的执行者更可控）；**实测显著超出的形式即应放弃**，不留"它也许会回来"的模糊状态。
* **超时的处置（L1）**：超时（含**没有可用超时机制**时的等价判断：无响应超过约定量级）后**不得**：①把没回传的复核写成"已通过"；②反复重派同一个会卡住的执行者（重复计费、重复卡）；③因此不交付。正确做法是**三条一起**：**换更可控的手段承担同一复核职责**（如把复核拆成一次性可超时的调用）、**把未覆盖的部分逐项标悬置**（写明已覆盖的角度与未由谁覆盖）、**按效力等级如实报告**（见 link:verify.adoc[]「验证的效力等级」）。**"复核者不可用"属概念项、不阻断交付**，但**其覆盖缺口必须写在留证里**。**优先一次性调用（L1）**：子任务（尤其复核）优先选**一次性、边界明确、可超时**的调用形式（给定输入即返回结论、不可追问、不必自行探查），而不是交一个**有自主探查权的执行者**——后者的耗时与边界都不可预估，"超时"在它身上实际上无法判定。
* **复核职责不绑定特定执行者（L1）**：规范要求的是"**有独立、干净上下文的语义复核发生**"，不是"必须由某个 NPC/某个产品来复核"。规范对执行者的约束是**同 Agent、同判据、可核对**（见上文「子任务必须由与执行者相同的 Agent 承担」「不得点名外部 Agent / 外部 NPC」）；**另一个来源的 Agent 即使可用，也不因其"更独立"而成为许可的复核者**。

== 派发对象须钉定与可执行

* **派发对象须钉定 commit sha（L1）**：把"某分支/某 PR 的改动"作为复核、比对、追溯对象时，派发指令里必须写明**具体 commit sha**（见 link:../platform/cnb.adoc[]「对象钉定与可追溯」）——分支名会被后续推送改变，收到方若按分支名自行取值，极易取到过期对象、产出与被复核内容不符的结论（实证：复核者取到已被压缩提交取代的旧 sha，逐项比对后误判"改动不存在"；另一参与者又用了另一个中间 sha）。**收到"基于某分支"的派发时，须先强刷 ref 再取 sha**（`git fetch -f` + `git rev-parse`），并在结论中写明所核 sha。
* **派发前确认执行者可执行（L1）**：派发前须确认执行者的**运行前提实际成立**——所需镜像/制品包存在且可取（实证：某执行者的制品包在制品库 `not found`，流水线在 `Prepare` 阶段 `docker pull` 失败，任务从未真正开始，看似"在跑"实则早已失败）；同名执行者可能来自不同来源，须用**确证可用的那个**。执行者的**可用性**属环境前提，派发者负核对责任，不得假设"派了就是能跑"。
* **压缩提交/强推前确认无人在用旧对象（L1）**：对分支做 `squash`/`rebase`/force push 前，须确认**无他人正基于旧 sha 工作**（已派发、正等待结论）；确需执行时，须**明确告知**受影响方新 sha、并把旧 sha 上的结论标为过期（见 link:../platform/cnb.adoc[]「对象钉定与可追溯」）。

== 协作方式

* 大任务优先使用子 agent：项目级检查（测试检查、code review、全量修改等）优先拆分给子 agent 执行，主 agent 只做任务编排、结果汇总与最终验证；子 agent 的执行边界须在派发指令中写明（如禁止并发构建、只写文件不验证等），避免多 agent 相互冲突；子 agent 不执行构建验证时，由主 agent 统一串行验证
* **子 Agent 不可用时的降级路径（L1）**：同 Agent 子执行者不可用（环境不提供子 Agent 能力、派发失败、超时）时，**不跳过该职责，也不换任何外部来源的 Agent 顶替**，按序降级：①**由执行者本人（主 agent）串行承担**同一职责（如三视角复核由主 agent 在同一会话内按同一判据逐项过），并在留证中标注**独立性边界**（复核者与改动方同一上下文，独立性弱于第三方）；②仍不可行时**如实标悬置**、写明未覆盖的角度与剩余风险。降级后**明确交付**，不因机制缺失把任务停在中间；"以机制不可用为由跳过"与"假装已委派"都属违规（见 link:../general/self-check.adoc[]「环境能力自评」）。**"本环境没有同 Agent 的子执行者可用"不是改用外部 Agent 的理由**——它只把路径指向本条降级。
* 步骤隔离：多步骤任务（调研、设计、编码、写用例、用例验证、文档等）步骤间无依赖时，优先各自用干净的子 agent 独立完成——子 agent 上下文隔离，避免前序步骤的上下文影响后续步骤；主 agent 负责编排与汇总
* 同一对象只起一个子 agent（L1）：同一批文件、同一份 diff 的核对**合并为一次派发**、一次读取、结论分栏列，不"一个视觉一个子 agent"地重复起——重复起子 agent 是重复读取与重复计费，且两次派发拿到的证据面本就相同；多个视角的合并方式见 link:verify.adoc[]「规范验证」
