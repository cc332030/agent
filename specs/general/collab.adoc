= agent 协作规范（通用层）

以下规范适用于所有拆分 agent（含主 agent）协作的场景。

== 资源限制与感知

* 调用次数限制：agent（含主 agent）调用 AI 次数有限（约百次量级），超限后自动停止并要求人工接入；主 agent 自身也要控制调用量，避免超限后需人工接入
* 拆分原则：拆分 agent 不能只按模块拆分（模块大小不均会导致任务量失衡），应按任务量分批拆分子 agent，使每个 agent 的调用次数低于限制
* 失联感知与**硬超时（L1）**：子 agent 超限停止或长时间无响应时主 agent **无感知**，任务会永久挂起（实证：把语义复核派给外部评审 NPC，多轮停在同一节点 1 小时以上、结论未回传，发起方只能人工中止）。故派发时**必须自带超时**：给**每一次**子 agent 调用设**可判定的时限**（数值由项目按任务规模定），到点即视为失联，并按"**放弃该子 agent + 如实记悬置**"处置，**不得无限等待**；探活/重建只是可选手段，**超时是必备手段**。**时限取值须有判据、不得"看着办"（L1）**：按"复核应在**单次任务可承受的量级**内返回"取值——**取"分钟级"档**（如同类任务正常返回耗时的 2~3 倍；实证：一次性模型调用返回 30 秒至 1 分钟量级），并优先选**一次性、边界明确、可超时**的派发形式（把复核做成一次不可追问的调用，比交一个有自主探查权的执行者更可控）；**实测显著超出的形式即应放弃**，不留"它也许会回来"的模糊状态。
* **超时的处置（L1）**：超时（含**没有可用超时机制**时的等价判断：无响应超过约定量级）后**不得**：①把没回传的复核写成"已通过"；②反复重派同一个会卡住的执行者（重复计费、重复卡）；③因此不交付。正确做法是**三条一起**：**换更可控的手段承担同一复核职责**（如把复核拆成一次性可超时的调用）、**把未覆盖的部分逐项标悬置**（写明已覆盖的角度与未由谁覆盖）、**按效力等级如实报告**（见 link:verify.adoc[]「验证的效力等级」）。**"复核者不可用"属概念项、不阻断交付**，但**其覆盖缺口必须写在留证里**。
* **复核职责不绑定特定执行者（L1）**：规范要求的是"**有独立、干净上下文的语义复核发生**"，不是"必须由某个 NPC/某个产品来复核"。外部复核者不可用（卡住、超时、能力不匹配）时，由发起方按同一判据**自行组织等价复核**并如实标注其**独立性边界**（如"复核者与改动方同一模型，独立性弱于第三方"）——**不得因为外部复核者不可用就跳过复核，也不得因此伪造复核结论**。

== 协作方式

* 大任务优先使用子 agent：项目级检查（测试检查、code review、全量修改等）优先拆分给子 agent 执行，主 agent 只做任务编排、结果汇总与最终验证；子 agent 的执行边界须在派发指令中写明（如禁止并发构建、只写文件不验证等），避免多 agent 相互冲突；子 agent 不执行构建验证时，由主 agent 统一串行验证
* 步骤隔离：多步骤任务（调研、设计、编码、写用例、用例验证、文档等）步骤间无依赖时，优先各自用干净的子 agent 独立完成——子 agent 上下文隔离，避免前序步骤的上下文影响后续步骤；主 agent 负责编排与汇总
* 同一对象只起一个子 agent（L1）：同一批文件、同一份 diff 的核对**合并为一次派发**、一次读取、结论分栏列，不"一个视觉一个子 agent"地重复起——重复起子 agent 是重复读取与重复计费，且两次派发拿到的证据面本就相同；多个视角的合并方式见 link:verify.adoc[]「规范验证」
