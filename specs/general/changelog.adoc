= 变更日志编写规范（通用层）

以下规范适用于**所有语言、所有项目**的变更日志（changelog）。变更日志的文件位置、命名、版本号来源、**排序方向与分组口径（版本分组 / 时间流水）与只追加机制**见 link:../general/doc-design.adoc[]「版本与变更记录」（业务系统各阶段文档的变更一并纳入项目统一 changelog，见 link:../general/doc-lifecycle.adoc[]）；本文件定两头：**写哪些条目、每条怎么组织**（「组织形态」「条目书写」）与**不写什么**（「不应当记录」）——取舍口径与形态在各项目之间必须一致，否则同一份日志换个项目就读不懂。

== 组织形态（按版本分组；版本内按类型分组）

* **以发布版本为一级分组（默认，L1）**：每个**发布版本**一个分组，组内再按变更类型分组；**不按提交日期流水堆积**——日志的读者是"要升级到某个版本的使用者"，他们要的是"这一版里有什么、我要做什么"，不是"哪天改了什么"。**版本号即发布标识**（tag / 制品坐标 / 项目自己的发布号），不是仓库里随手递增的内部计数
* **按时间流水（次级形态，L2）**：**仅在项目没有"发布版本"概念时**（持续交付的工具链、单文件脚本集合）才不用版本分组，改为**按日期流水的单层倒序**（最新在上、追加时插到顶部）；**排序方向不变（仍为时间倒序）**，只是少了版本这一级分组。**有发布版本却用流水式**即退回"一条条堆积"的失效形态（用户报告：一个版本改了很多东西时不可检索）
* **排序方向恒为时间倒序（最新在上），与分组口径无关（L1）**：条目与版本组**一律最新在上**。「按版本分组（默认）」与「按时间流水」只是**分组口径**之别：版本是**单调递增**的（版本号即发布标识），故**版本倒序天然就是时间倒序**——**版本倒序与时间倒序是同一件事，不是两种排序**，**不存在"正序"形态**，也**没有**需要二选一的两种排序。**判据**：把 `- 3.30` 读在 `- 3.31` 之前、把更早的版本组放在更新版本组之上，即方向错。按版本分组的项目**不得**在版本组内插入日期流水排序；流水式项目**不得**在条目之间插入版本分组
* **组内按类型分组**：组内再按变更类型分组（**排序方向仍是时间倒序**）；类型取**固定的闭集**，同一项目内用词一致、不混用同义词；**没有条目的分组不写**（空分组占篇幅、还会让人以为"这一版没改这些"是漏记）；**两种分组口径不并存**——一个项目同一种日志只能用一种分组口径
* **与发布标识对齐**：条目所属的版本组、版本号与发布日期须能对上项目的发布事实（tag/制品元数据/发布记录）；对不上即二者之一有错，须先核对再写
* **不维护「未发布」区段（本集合的取舍，L2）**：常见做法是在文件顶部维护 `Unreleased` 一节、发布时整段改名为版本号。本集合**不采用**——变更是"做完了才落笔"（见「不应当记录」的"未提交前的反复修改合并为一条最终结果"），提前维护一个待发布区段会让未完成的工作被当成对外承诺；**发布后一次性补记本版本组即可**

== 编写原则

* **面向变更的读者，不是作者**：changelog 的读者是领导、用户、升级/排障者等——他们关心"这次变更带来什么影响"，不关心"是怎么做的"。**读者不会问改了几行代码，除非这几行让公司赚/亏一个亿**：只有真正改变价值、风险或使用者感知的改动才值得写进 changelog
* **说影响，不说实现过程**：每条写"改成了什么、对外表现/影响有何变化"，不写"怎么改的"（不写逐步骤的实现过程/调试过程/重试过程）
* **一条一个变更点**：一个变更点写一条，不把多个不相关的变更塞进一条；同一变更点分散在多处文件的改动合并为一条
* **详略按影响**：破坏性变更、新增能力、安全与数据/资金相关改动写清"影响面与应对方式"；普通修复一句话说清"修了什么、对谁有影响"
* **可核对**：条目中的功能名/模块名/接口名/编号须真实存在（可被读者据此定位到代码或需求），不写模糊指代

== 应当记录（有价值）

* **对外可见的行为/接口/契约变更**：新增/调整/移除的功能与命令、API、配置项、参数与默认值
* **破坏性变更（Breaking Change，最高关注）**：会改变既有行为、契约、数据格式或使用方式，使用者必须跟进——须**单独标注**（如条目开头标 `破坏性变更` 或在条目前加 `!`）并写明影响范围与迁移/应对方式
* **缺陷修复**：修掉的问题及影响面（谁在什么场景下受影响、修复后的表现）
* **安全与数据相关**：漏洞修复、权限与鉴权调整、数据迁移/兼容性处理、资金/计费相关改动
* **性能与资源**：可感知的性能提升或劣化（如接口响应、内存/存储占用、启动时间），并给出量级（如"约 3 倍"）；只在无实测数据支撑时避免写具体数字
* **依赖与兼容性**：依赖升级/更换、运行时或平台版本要求变化、兼容性取舍
* **已知缺陷的状态变更**：新发现的已知缺陷、已关闭的缺陷（含此前在文档中标记 `待修复` 的项）
* **运维与部署影响**：影响部署/升级/回滚的改动、需要的运维动作

**要素齐备底线（L1）**：无论采用哪种组织形态与条目形态（流水式 / 表格式），每条变更记录都须齐备**四项要素**——**①类型②变更点（受影响的对外标识）③影响（读者要做什么、能感知到什么）④标记（破坏性变更等）**。「写一句话摘要」与「填一行表格」只是形态差别，**不得因为换成表格就漏掉"影响"、也不得因为写流水句就漏掉"类型"**；缺「影响」的条目等于只说了"改了什么"、读者仍要自己猜要不要跟进——**这是本条最常被形态掩盖的失效**。

== 表格形态的判据（采用表格式时）

**前提**：判据只在项目**选择了表格式**时适用；选流水式的项目不受影响。表格式的**理由**是"一个版本内变更点很多"——纯单行流水读者无法按模块或版本检索，且"变更点"与"影响"两类信息挤在一句话里，读者要自己拆。

* **列义：表格承载的字段**（列名各项目自定，**语义与齐备性**如下）：
  ** **分组列 = 受影响的对象**（模块 / 组件 / 平台范围；无模块划分的项目写组件名，单组件项目可省此列）——**分组列是"与版本对齐"之外的分组，服务于检索**，不得因"一个版本一个组"就省掉
  ** **类型列 = 变更类型**（新增 / 变更 / 修复 / 移除 / 安全，见「条目书写」的类型闭集）——空类型分组不写
  ** **变更点 = 受影响的对外标识**（类 / 函数 / 命令 / 接口 / 配置键 / 文档落点）——取**读者能据以定位的真实标识**，不写"优化了一些逻辑"
  ** **影响 = 读者要做什么、能感知到什么**（含约束、边界与默认值；破坏性变更在此写明迁移方式）
* **判据依赖关系（L1，最容易松掉的一条）**：**"变更点"与"影响"分列，不等于两列都要写满，更不等于可以从类型列反推**——类型只是分类，**不得用类型分级代替破坏性变更标注**（把某个类型默认为"破坏性的"），**不得把影响写成"变更点"的同义重复**（"新增了 X：现在有 X 了"）——**影响列写不出读者要做的动作时，说明这条其实不该记**（见「不应当记录」）
* **破坏性变更在表格中的标注**：**逐行标注**（行内徽标或独立列），**不得只放在版本组的引文/说明句里**——说明句读者会跳过；**破坏性变更不得因转为表格形态而消失**（流水式用 `!` 或 `破坏性变更` 前缀，表格式用行内标注，两者是同一要求的两形态）
* **条目下限（L1）**：**表格里一条 = 一个变更点**，与流水式同口径——转表格式、加分组与列，**都不是拆条目或并条目的理由**；不得把不相关变更塞进一行"顺带记一下"
* **容量边界**：表格行数超过读者能扫读的量（经验值**单版本超过约 50 行**）时，先按**分组列**拆分（按模块/组件），仍不足时按**类型**再拆（二级小标题），**不得**改用更粗的粒度合并条目
* **不因形态而改动事实**：链接引用、路径与类名一律按**当时真实存在**的落点写；历史条目中的路径是"当时的位置"，**不在旧条目里改写**（见 link:../general/doc-design.adoc[]「版本与变更记录」）

== 不应当记录（细枝末节）

* **纯内部实现细节**：内部方法/类命名调整、代码搬动、局部重构、注释与格式整理——对外表现无变化
* **过程与工作量**：改了多少文件/多少行、花了多久、调试与试错过程、内部评审与讨论过程
* **无用户可见影响的琐碎修复**：日志文案微调、无功能影响的告警消除、仅内部依赖的小版本升级、无实测支撑的"性能优化"
* **可从代码或提交历史直接看出的信息**：函数签名、局部变量、单个提交的 diff 内容
* **临时产物与未提交内容**：临时排查结论、本地实验、已移除且从未提交过的功能（见 link:../general/doc.adoc[]「注释与文档」）；未提交前的反复修改合并为一条最终结果，不逐次留痕（见 link:../core/execution.adoc[]「文档与代码对应同步」）

== 条目书写

* **两种条目形态（择一，不得混用）**：**流水式**与**表格式**。同一项目内**只能有一种**；两形态的区别只是**一条条目承载几个字段**，**不得因此少记任何一项**（见「应当记录」的**要素齐备底线**）：
  ** **流水式（默认，条目少、项目小）**：单行条目 `版本号 | 日期 | 变更摘要`（最新在上，总体机制见 link:../general/doc-design.adoc[]「版本与变更记录」），条目内**不换行、不写成多段**——续写成多行会与下一条粘连、渲染成一整段
  ** **表格式（一个版本内变更多、或项目有模块划分时）**：**版本组标题 + 类型分组小标题 + 表格**，表格逐列承载判据，使读者能整列扫读、按模块检索；列义与判据依赖关系见下「表格形态的判据」
* **一条一个变更点（两形态通用）**：一个变更点一条；同一变更点分散在多处文件的改动**合并为一条**（表格形态同理：一条改动只占一行，不因跨文件而拆行）
* **一条一行、编号/标签前缀**：需要分组或标类型时用行内标签而非多行小节——如 `破坏性变更`、`新增`、`修复`、`安全`；多条可加序号便于指针引用（如 `- [3]`），格式各项目自定、同一项目内保持一致
* **一句话**：摘要用一句话、**≤ 80 字**说清"改了什么 + 给谁带来什么影响"，超出即说明混入了细节，应拆分或删减
* **不逐文件列举**：功能名/模块名写一次即可，不逐文件逐类罗列改动清单
* **日期**：用 `YYYY-MM-DD`（依据：ISO 8601 日期格式，RFC 3339 亦沿用同一基线）；同一天多个版本各自成行、不合并
* **表述一致**：同一功能/模块在 changelog 中始终用同一名称（与代码、需求中的命名一致），便于检索与追溯
