= 模块级文档规范（通用层）

以下规范适用于**多模块项目（multi-module）中，模块内部文档的组织与归属**。全局文档（跨模块、规划性、阶段级）与根 `doc/` 目录的组织见 link:../general/doc-lifecycle.adoc[] 与 link:../general/doc.adoc[]；模块内设计文档/测试设计文档的编写格式规范见 link:../general/doc-design.adoc[]。

**本规范是总体大纲，只限定必要规则，不限制项目自主性**——模块名、模块 doc 内部按功能模块分类的目录组织、文件命名由各模块按其实际代码结构自行确定，项目可调整，不被本规范写死。

== 全局文档与模块文档的分界

* 全局文档（放根 `doc/`）：跨模块、规划性、阶段级、长期稳定描述系统的内容——系统架构与技术选型、模块划分、部署架构、数据库、接口、需求、生命周期各阶段产物等（见 link:../general/doc-lifecycle.adoc[]）。全局文档**不应**描述某个具体类/文件/函数粒度的实现细节
* 模块文档（放 `<各模块>/doc/`）：**该模块的**具体细节与规划性内容——模块职责与边界、模块内核心类/组件/功能的设计与实现细节、模块内专属约定、模块内复用的注意点等。模块文档**不应**描述跨模块、系统全局的规划性内容
* 归属判定：内容描述的范围属于"某个具体模块内部"（类/文件/函数粒度、模块内功能），记入该模块的 `doc/`；描述范围跨越多个模块或描述系统整体，记入根 `doc/`。无法确定归属时可参考"能否定位到单一模块"——能则入模块 doc，否则入根 doc

== 模块文档目录结构（大纲）

模块文档根目录为 `<各模块>/doc/`，**位于模块目录内、与源码同层**，保证离开代码就近可查。要求满足以下规则：

* 模块 doc 目录与模块源码结构**对应/可定位**：以模块内功能模块/组件建立目录，能由文档定位到对应功能/代码、由功能/代码定位到对应文档
* 目录结构具体多深、如何按功能模块分类，由各模块按自身代码规模自行确定，不写死（趋近规模小可平铺，规模大再按功能模块分类）
* 模块 `doc/` 下可放 `README.adoc` 作模块文档索引，总览模块职责与关键文档索引

示例结构（仅示意，非强制）——正常项目按**功能模块**分类组织文档，而非镜像包路径：

```
<module>/
├── src/.../<包路径>/<组件>.java     # 代码
└── doc/
    ├── README.adoc                 # 模块级索引（总览模块职责、关键文档）
    └── <功能模块>/                 # 按功能模块分类
        └── <功能>.adoc …           # 模块内功能/组件文档
```

== 模块内引用与代码↔文档互引

* 模块 doc 内的链接：与其他文档一致，用**相对当前文件所在目录的相对路径**（link:../general/doc.adoc[]「引用路径」），保证浏览器/站点与各工具的 ide 相对语义一致
* 模块 doc 引用根 `doc/` 的全局内容：从模块 doc 向上（`../` 到模块根，再 `../` 到仓库根）后进入根 `doc/`；以"相对当前文件"统一推导即可，不引入独立的"模块根相对"基准
* 代码↔文档双向可定位：遵循 link:../general/doc-design.adoc[]「代码与文档互相引用」——文档写明对应模块与类/方法，代码注释（含 `specs/stack/` 对应语言的注释规范，如 javadoc `@see`）显式引用对应文档的相对路径
