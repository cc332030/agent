= 改动范围边界规范（通用层）

以下规范适用于**所有语言、所有项目**：约束"本次改动**允许落在哪些文件/项目上**"。它与 link:../core/execution.adoc[]「范围控制」同维度、是**同一维度的收紧**（不替代、不静默推翻）：那条管"改动在项目内部不蔓延、读取按最小必要"，本条管"**改动不得越出被授权改动的那一份工作区**"。

识别特征（涉及即加载）：**要在已有工作空间里增删改文件、在代码托管平台上动手（建仓库/分支/提交/PR），或本次任务引用了当前工作空间以外的文件、项目、仓库（链接、路径、PR/Issue、代码片段、要求与之比对）**——只要"改动会落到哪一份工作区上"需要判定，即命中本条。

== 工作空间边界（不依赖任何平台）

* **只改当前工作空间（L1）**：执行者**只允许修改本次任务的工作空间**——即用户发起本次任务时所处的那个工作副本（用户自己的电脑、服务器或容器上的那棵工作目录树；下称"**入口工作空间**"）。**越出该工作空间的任何改动一律不得执行**：写入、创建、删除、移动、重命名、格式化、生成到工作空间之外的路径、对工作空间以外的位置做 `git` 操作等，都属越界。
* **未声明即拒绝（L1）**：**除非用户主动声明**把工作空间以外的某个位置纳入本次范围，否则**不得改动任何工作空间以外的文件**——**即使它在技术上可写**（同一个盘符/主机/容器上的其他目录、同一台服务器上的其他项目、任何可达的路径）。命中时须**明确拒绝该项并说明依据**，把改动留在入口工作空间内；其余**在入口工作空间内可做的部分照常完成**——不得默默照做，也不得只回一句"不能做"就停摆（同下「拒绝的形态」）。
* **引用 ≠ 授权（L1）**：任务里**引用了**工作空间以外的文件（贴了绝对路径/链接、把它的内容拷进对话、要求以它为依据或与之比对）只构成**读取/对照**的许可——**只读不在禁止之列，但读取不构成改动授权**；把改动顺手落到被引用的文件上（如"顺手把它也格式化了""顺手改掉那里的笔误"）即越界。要改它，须用户**显式声明**。
* **只读与对照照常做（L1，防"拒绝即停摆"的另一面）**：读取被引用的外部文件、用它比对、把它作为依据/证据**不在禁止之列**；本规范的失效目标是**改动**，不是读取。故"这个不能改"不构成"这个不能用"——须把它**当只读材料用足**，再在入口工作空间内完成能做的部分。
* **与破坏性操作的接口（L1）**：删除/清空/覆盖一类不可逆操作另受 link:../core/execution.adoc[]「破坏性操作」约束（先确认目标、可回滚、范围可界定）——**两条同时成立、互不豁免**：越界改动不得执行，"确认过"也不例外；反过来"不涉及不可逆操作"也不构成越界改动的理由。
* **与版本控制的接口（L1）**：本工作空间的 `git` 操作不受本条限制（暂存、提交、推送是项目内行为，其环境相关的取舍见 link:../general/git.adoc[]）；本条禁的是**把改动做到另一份工作空间/另一个仓库上**——例如进另一个工作目录改文件、把别的仓库当工作区、把不属于本次任务的改动纳入本次提交。

== 已知例外（唯二的解禁情形，靠用户显式给出、不靠推断）

* **①用户显式声明**：用户明确说出"这次连 X 一起改"（含写明路径/项目名的同类表述）时，**仅对该次任务、该位置生效**——**不得泛化**（一次声明不等于长期授权、不等于"以后这个位置也能改"、不扩到第三处）；本次任务结束即失效。
* **②用户声明某位置"只读/禁止改动"**：该声明**优先**，相应位置一律不得改动（即使本次其他条件看起来已解禁）。
* **不放行清单（L3 提示，非穷尽）**："看起来顺路""反正就差一处""我刚读它时顺手改了下""用户应该不会介意""同一台机器上就能看到"——**一律不放行**：放行的判据只有上两条，由用户的显式语句给出。

== 判定标准（任一命中即越界，可逐条核对）

* **①改动对象**不在入口工作空间内——出现对入口工作空间以外位置的写入、创建、删除、移动、重命名、格式化或 `git` 操作。
* **②以"引用过它""任务里提到了它""它就在旁边""同一个主机/服务器上"为由**把改动做到工作空间以外（**自我豁免**）。
* **③把越界改动转交他人/其他执行者顶替完成**（如派一个工作目录在别处的执行者去改，见 link:../general/collab.adoc[] 的"不得点名外部 Agent / 外部 NPC"条）。

== 拒绝的形态（L1）

* 拒绝须**如实、可核对**：写明"该项按规范不予执行 + 依据 + 需要补什么声明"（如"要改它请声明『本次允许修改 X』"），并在汇报里**显式列出**被拒的项与已完成的项；不得默默照做、不得只回一句"不能做"就停摆、也不得把越界项悄悄跳过不提。
* **拒绝不等于任务失败**：入口工作空间内可做的部分须照常完成并汇报——"有一项被拒"与"任务没做完"是两件事，不得用前者当后者（也不得用后者掩盖前者）。

== 平台上的仓库边界（代码托管平台）

* **平台会放大可写范围（L1）**：在代码托管平台（如 CNB）上工作时，**可写范围不是"一棵工作目录树"，而是"当前执行者账号有权访问的全部仓库"**——平台侧的建仓库/建分支/建标签/建 PR、改文件、改仓库设置、提交、推送等，在技术上都不受本地工作目录限制。故本节的禁令**按当前项目（仓库）表达**：**只改当前项目**。
* **只改当前项目（L1）**：**当前项目**＝本次任务的**入口项目**——用户唤起本次任务时所处的那一个项目/仓库（会话入口所在的工作空间所属的仓库）。**越出该项目的改动一律不得执行**：不向其他仓库写入/创建/删除/移动/格式化/提交/推送，不在其他仓库建分支、建标签、建 PR/Issue、改设置。
* **未声明即拒绝 + 引用 ≠ 授权（L1）**：**除非用户主动声明**把某个其他项目纳入本次范围，否则不得改动其他任何仓库——**任务里引用了另一个项目（贴了它的链接、路径、PR/Issue、代码片段，或要求与之比对）只构成读取/对照的许可，不构成改动它的授权**。命中时按上节「拒绝的形态」处理：明确拒绝并说明依据、只把改动留在当前项目内、其余照常完成。
* **判定标准**：除上节三条外，再加一条——**④改动落在其他仓库上**（含以"引用过它""同一个账号下就能推""反正有权限"为由的自我豁免、含转交他人顶替）。**"我有权限"不构成授权**：权限是平台能力，授权来自用户的显式声明。
* **合并仍恒为人工（L1，与本条各自独立、互不豁免）**：用户声明放开"可修改另一个项目"**不**意味着允许合并，本条也不放开任何合并动作——合并只由人工完成，见 link:../platform/cnb.adoc[]「合并请求的合并主体（NPC 禁合并）」。
* **跨项目的只读协作照常（L1）**：读其他仓库、按 sha 取对象比对、引用其内容作依据，都不受本条限制（读取与对象钉定见 link:../general/collab.adoc[]）。
* **平台层另有补充时**：某平台若对仓库边界另有更细的口径（平台对象钉定、派发与执行者边界等），按该平台规范文件（如 link:../platform/cnb.adoc[]）一并遵守；两者同向，不互相削弱。

== 与既有规范的衔接（不静默推翻）

* **与「范围控制」的关系**（link:../core/execution.adoc[]）：同维度的**收紧**——那条管项目**内部**不蔓延与读取最小必要，本条管**跨出**入口工作空间/入口项目；本条的判定不替代那条，反之亦然。
* **与项目自身规范的冲突次序**：按 `AGENTS_COMMON.adoc`「访问与解析」的既有口径——**引用方项目自身规范优先**（例如该项目自己声明了"本项目包含工作空间之外的生成目录、也属本次可改范围"，则按其规范执行）；本条的 L1 是**底线**，不得被"精简/顺手/上下文不足"降级，但项目显式声明的范围口径属用户侧的授权表达。
* **与产物落点的关系**：临时产物、报告等仍按 link:../core/execution.adoc[]「临时产物」写入**入口工作空间内**的项目 `tmp/`，**不得**因为"那里更顺手/更持久"而写到入口工作空间之外。
