= 编码与语言无关规范（通用层）

以下规范适用于**所有语言、所有项目**的产物编写。它回答一个"以谁为读者"的问题：产物是给**使用方**读的，不绑定实现语言、不泄露与读者无关的实现框架细节。注释与文档的内容要求（必记录项、质量六条）见 link:../general/doc.adoc[]，命名与代码质量见 link:../general/coding.adoc[]，脚本格式见 link:../general/script.adoc[]。

== 读写编码

* **一律 UTF-8（L1）**：所有源文件、脚本、文档、配置文件一律使用 UTF-8 编码（依据：RFC 3629 定义的 UTF-8），除非该格式明确不是（二进制格式、规范指定其他编码者除外）；**不得使用 GBK/GB2312/UTF-16 等本地或平台默认编码**——它们一旦离开原环境即乱码，且在跨平台工具链与 CI 中行为不一致。
* **编码一致性校验（L2）**：涉及中文等多字节内容时，改完随机抽检（能正常显示、未出现乱码），不得"看起来写了中文"就当成功。

== 换行符（行尾）

基准是 LF；CRLF **只允许**出现在"操作系统/解释器强制要求 CRLF"的少量例外上，且必须落盘为 CRLF（不靠检出转换）。判定顺序是"先判例外、再用基准"——先按下面的例外清单逐类对照，命中即用该例外要求的行尾；未命中才用基准 LF。

* **仓库内容以 LF 为基准（L1）**：同一文件内不得混用 LF 与 CRLF；仓库内**默认一律 LF**（依据：git 官方文档 `core.autocrlf`、`core.eol` 对行尾归一化的说明）。
* **能自主识别两种行尾的解释器用 LF（L1）**：**bash/sh 等 shell 脚本、Python 脚本一律 LF**（含扩展名 `.sh`/`.py` 与"无扩展名的脚本、`scripts/` 下的脚本"）——`/bin/sh`、`bash`（含 Windows 上 Git Bash/Cygwin/WSL 提供的 `/bin/bash`）、Python 等对 LF 与 CRLF 都能正常解析，**不得为其落盘 CRLF**（`\r` 会被当成命令/参数的一部分而报错，如 `bash: $'\r': command not found`）。
* **Windows 批处理必须 CRLF（L1）**：`.bat`、`.cmd` 文件**一律落盘 CRLF**，不得存成 LF。原因：Windows 命令解释器按字节读行尾、不做行尾归一化，LF-only 的批处理会**直接执行失败**（`goto`/标签匹配、`if`/`for` 等复合语句、行尾注释与续行都可能失效；依据：Microsoft Learn 的 Windows 命令参考），这是 Windows 上最常见的一类"脚本莫名其妙不工作"。
  ** 与基准的关系（例外而非冲突）：本类文件的"CRLF"要求**覆盖**上条"仓库内容以 LF 为基准"的基准——因这类文件**必须按 CRLF 落盘**（只能二选一，故按解释器要求选择），属本规范**显式规定的例外**，不属"混用行尾"；反过来，**不得**把"仓库以 LF 为基准"套用到 `.bat`/`.cmd` 上而存成 LF。
  ** 在 Unix/Linux/macOS 上编辑这类文件时（常见成因）：编辑器与 git 提示的"换行符不一致"多数是**在 Unix 上编辑 Windows 批处理**造成的——须按本条规定**存为 CRLF**，不"随大流改成 LF"。
* **易被 CRLF 破坏的文本类格式（L2）**：`.ps1`（见 link:../stack/powershell.adoc[]「编码与行尾」）、`.cmd` 之外，含 shebang 的文本、`Makefile`、`.gitattributes`/`.gitignore`、Dockerfile、`.env` 等以行/字节严格解析或会被工具按行读取的文本文件，默认按 LF 落盘（依据：POSIX 对文本行以 `\n` 分隔的定义；GNU Make 的 `make` 手册对行尾的要求）。
* **行尾一致性校验（L2）**：行尾问题不靠肉眼判断——改完按下面命令核对，结果须为"零违规、零混用"：
  ** 批量核对：`git ls-files --eol` 中 `w/crlf`、`w/mixed` 即工作区为 CRLF 或混用，对照"哪些文件应当 CRLF"（`.bat`/`.cmd`/`.ps1`）判断是否违规；
  ** 定点核对单个文件：`file <文件>`、`grep -c $'\r' <文件>`（`0` 即 LF-only，用于确认 `.sh`/`.py` 未被写成 CRLF）。

== 跨平台检出（不靠人工手动调整）

"文件该用什么行尾"必须**由仓库配置固定、工具自动执行**，不靠人工逐个文件手动转换（人工调整必然遗漏、且每次提交都会重新引入），也不靠每个开发者各自设置本机 git 配置（依据：git 官方文档 `gitattributes` 的 `text`/`eol` 属性与 `core.autocrlf`/`core.eol`）。

* **仓库根 `.gitattributes` 是权威落盘口（L1）**：行尾策略须写在仓库根的 `.gitattributes` 中，**显式声明、不按平台自动推断**——LF 规则的文本写 `text eol=lf`，必须 CRLF 的批处理与 `.ps1` 写 `text eol=crlf`，二进制写 `binary`（`text=auto` 依赖开发者本机的 `core.autocrlf` 设置、不同机器结果不同，故本规范不用它）。示例（路径按项目实际调整）：
  [listing]
  ----
  * text eol=lf
  *.bat text eol=crlf
  *.cmd text eol=crlf
  *.ps1 text eol=crlf
  *.png binary
  ----
* **新接入项目先配好再提交（L1）**：首次提交前就要有 `.gitattributes`，避免先按本机默认提交、再回头统一行尾（历史里会留下大量"只因换行符"的假变更）。
* **配套设置（L2）**：`.gitattributes` 已显式声明时，开发者本机的 `core.autocrlf` 应设为 `false`（由仓库配置决定行尾，不再让本机设置二次改写）；`eol=crlf` 的文件其 CRLF 由 git 按规则生成、**不写进仓库内容**（仓库内仍按 LF 存储）。
* **存量项目补齐（L2）**：尚未配置的存量项目按 link:../core/execution.adoc[]「规范变更的存量处理」随项目开发逐步补上，不为此发动全库一次性转换。
* **自检（L1，引用方项目执行）**：本规范集合看不到引用方的工作区，故该条由**引用方项目自查**承担——`git check-attr -a <文件>` 须给出与上表一致的 `eol` 取值；`git ls-files --eol` 无违规（见上节「行尾一致性校验」）。

== 语言无关性

* **注释、文档、日志面向使用方描述（L1）**：**不得描述只有当前实现框架/语言才需要的私事**，也不得把实现语言/框架/内部技术栈的名称写进面向使用方的描述——除非该项本身是使用方必须知道的约束（如"仅支持 Java 8+"、版本要求、平台限制）。判定口径：**读者是不是使用方**——内部实现细节、语言语法糖、框架注解、内部数据结构属"实现私事"，写进代码内注释只说清"这段代码在做什么、边界在哪"，不自夸实现套路、不描述可选实现细节。
* **不假设语言特性（L2）**：规范、文档、示例**不得假设读者使用的语言**——例子与措辞应可用任意语言对应表达；给出某语言示例时须写明语言，不得把某语言专属写法（如类型系统特性、特定标准库 API）当作通用做法。
* **术语统一（L2）**：同一概念在全部文档、注释、日志中使用**同一个名称**（与代码中的命名一致），便于检索与追溯，不因换一种说法而同一个东西三个名字。
* **不在产物里泄漏内部代号（L2）**：内部工单号、临时分支名、内部模块代号、人员昵称等**不应出现在面向使用方的文档或 changelog** 中（可回溯的内部编号按项目约定处理），读者无法据此定位，只会造成噪音。
