= 编码与语言无关规范（通用层）

适用于**所有语言、所有项目**的产物编写。注释与文档的内容要求见 `specs/general/doc.adoc`，命名与代码质量见 `specs/general/coding.adoc`，脚本格式见 `specs/general/script.adoc`。

== 读写编码

* **一律 UTF-8（L1）**：所有源文件、脚本、文档、配置文件一律使用 UTF-8 编码（依据：RFC 3629 定义的 UTF-8），除非该格式明确不是（二进制格式、规范指定其他编码者除外）；**不得使用 GBK/GB2312/UTF-16 等本地或平台默认编码**——它们一旦离开原环境即乱码，且在跨平台工具链与 CI 中行为不一致。
* **Windows 批处理的编码是显式例外（L1）**：批处理指令**一律用纯 ASCII 写**（`cmd.exe` 按系统 ANSI 代码页解析，非 ASCII 会被解析成乱码；与"一律 UTF-8"不冲突——属本条显式规定的例外）。**取值做法、不写 BOM 与首行口径的唯一落点＝** `specs/stack/batch.adoc`「编码与行尾」，本处不重复其取值。
* **编码一致性校验（L2）**：涉及中文等多字节内容时，改完随机抽检（能正常显示、未出现乱码），不得"看起来写了中文"就当成功。

== 换行符（行尾）

基准是 LF；CRLF **只允许**出现在"操作系统/解释器强制要求 CRLF"的少量例外上，且必须落盘为 CRLF。判定顺序是"先判例外、再用基准"。

* **仓库内容以 LF 为基准（L1）**：同一文件内不得混用 LF 与 CRLF；仓库内**默认一律 LF**（依据：git 官方文档 `core.autocrlf`、`core.eol`）。
* **能自主识别两种行尾的解释器用 LF（L1）**：**bash/sh 等 shell 脚本、Python 脚本一律 LF**（含 `.sh`/`.py` 与无扩展名的脚本、`scripts/` 下的脚本）——`/bin/sh`、`bash`、Python 等对 LF 与 CRLF 都能正常解析，**不得为其落盘 CRLF**（`\r` 会被当成命令/参数的一部分而报错，如 `bash: $'\r': command not found`）。
* **Windows 批处理必须 CRLF（L1）**：`.bat`、`.cmd` 文件**一律落盘 CRLF**，不得存成 LF。原因：Windows 命令解释器按字节读行尾、不做归一化，LF-only 的批处理会**直接执行失败**（`goto`/标签匹配、`if`/`for` 等复合语句、行尾注释与续行都可能失效；依据：Microsoft Learn 的 Windows 命令参考）。
** **与基准的关系（例外而非冲突）**：本类文件的"CRLF"要求**覆盖**上条"仓库内容以 LF 为基准"的基准——属本规范**显式规定的例外**，不属"混用行尾"；反过来，**不得**把"仓库以 LF 为基准"套用到 `.bat`/`.cmd` 上而存成 LF。
** **在 Unix/Linux/macOS 上编辑这类文件时（常见成因）**：编辑器与 git 提示的"换行符不一致"多数是**在 Unix 上编辑 Windows 批处理**造成的——须按本条规定**存为 CRLF**，不"随大流改成 LF"。
* **`powershell` 的 `.ps1` 用 CRLF（L1）**：见 `specs/stack/powershell.adoc`「编码与行尾」。
* **易被 CRLF 破坏的文本类格式（L2）**：`.cmd` 之外，含 shebang 的文本、`Makefile`、`.gitattributes`/`.gitignore`/`.editorconfig`、Dockerfile、`.env` 等以行/字节严格解析或会被工具按行读取的文本文件，默认按 LF 落盘（依据：POSIX 对文本行以 `\n` 分隔的定义；GNU Make 手册）。
* **行尾取值可核对（L2）**：行尾不靠肉眼判断——改动后须核对到"零违规、零混用"这一**取值状态**：逐个受检文件的行尾形态与该文件应有的形态**一致**（应当 CRLF 的仍是 CRLF、应当 LF 的仍是 LF，不得出现混用）。**怎么核对属执行动作，不写进规范**。

== 跨平台检出（不靠人工手动调整）

"文件该用什么行尾、用什么编码"必须**由仓库配置固定、工具自动执行**，不靠人工逐个文件手动转换，也不靠每个开发者各自设置本机 git 配置（依据：git 官方文档 `gitattributes` 的 `text`/`eol` 属性与 `core.autocrlf`/`core.eol`）。

* **仓库根须有 `.gitattributes` 与 `.editorconfig`，缺失即按本节补齐（L1）**：两者是同一件事的两端——`.gitattributes` 定 git 检出/提交侧的行尾与二进制判定，`.editorconfig` 定编辑器侧的编码、行尾、缩进与末尾换行；**项目里缺任一个就按本节要求新建**，已有的就地核对、只改与本规范不一致的项（缩进等取值随项目），不"先按本机默认用着、出问题再补"。
* **仓库根 `.gitattributes` 是权威落盘口（L1）**：行尾策略须写在仓库根的 `.gitattributes` 中，**显式声明、不按平台自动推断**——LF 规则的文本写 `text eol=lf`，必须 CRLF 的批处理与 `.ps1` 写 `text eol=crlf`，二进制写 `binary`（`text=auto` 依赖开发者本机的 `core.autocrlf` 设置、不同机器结果不同，故本规范不用它）。示例（路径按项目实际调整）：

[listing]
----
* text eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf
*.png binary
----

* **`.editorconfig` 的取值（L1）**：声明编辑器侧的编码、行尾、缩进与末尾换行，取值须与本规范一致——`[*]` 段 `charset = utf-8`、`end_of_line = lf`、`insert_final_newline = true`，缩进按项目实际统一；行尾按文件类型分段（`.bat`/`.cmd`/`.ps1` 用 `crlf`）；`.ps1` 的 BOM 取舍见 `specs/stack/powershell.adoc`（要求 BOM 时该段写 `charset = utf-8-bom`）；**`charset = utf-8` 只覆盖按本规范按 UTF-8 存储的文件**——某类文件若按格式规范或外部工具要求须存为非 UTF-8 编码，须为该类文件单列一段写 `charset = unset`（该取值用于移除该键的既有效果）。示例（路径按项目实际调整）：

[listing]
----
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.{bat,cmd}]
end_of_line = crlf

[*.ps1]
end_of_line = crlf
----

* **新接入项目先配好再提交（L1）**：首次提交前就要有这两个文件，避免先按本机默认提交、再回头统一行尾与编码（历史里会留下大量"只因换行符"的假变更）。
* **配套设置（L2）**：`.gitattributes` 已显式声明时，开发者本机的 `core.autocrlf` 应设为 `false`。
* **存量项目补齐（L2）**：尚未配置的存量项目随项目开发逐步补上，不为此发动全库一次性转换。
* **自检（L1，引用方项目执行）**：本规范集合看不到引用方的工作区，故该条由**引用方项目自查**承担——仓库根 `.gitattributes`、`.editorconfig` 均存在（缺失即按本节补齐）；`git check-attr -a <文件>` 须给出与上表一致的 `eol` 取值；`git ls-files --eol` 无违规；`.editorconfig` 与 `.gitattributes` 对同一类文件的行尾取值一致。

== 语言无关性

* **注释、文档、日志面向使用方描述（L1）**：**不得描述只有当前实现框架/语言才需要的私事**，也不得把实现语言/框架/内部技术栈的名称写进面向使用方的描述——除非该项本身是使用方必须知道的约束（"仅支持 Java 8+"、版本要求、平台限制）。判定口径：**读者是不是使用方**——内部实现细节、语言语法糖、框架注解、内部数据结构属"实现私事"。
* **不假设语言特性（L2）**：规范、文档、示例不得假设读者使用的语言——例子与措辞应可用任意语言对应表达；给出某语言示例时须写明语言。
* **术语统一（L2）**：同一概念在全部文档、注释、日志中使用**同一个名称**（与代码中的命名一致），便于检索与追溯。
* **名称的定义归档与引用方式（L2）**：本条只定"叫法统一"；**定义写在哪、怎么引**（按作用域归档、只引名称不引定义）见 `specs/general/terminology.adoc`「数据字典」。
* **不在产物里泄漏内部代号（L2）**：临时分支名、内部模块代号、人员昵称等不应出现在面向使用方的文档或 changelog 中。本条的**唯一例外是 changelog 里的变更编号**——它按 `specs/general/changelog.adoc`「可核对」条承载条目与需求的对应关系；**变更编号在别处能否出现不由本条定**，一律以 `specs/general/git.adoc`「提交信息」为准（该处只许它落在提交信息里，范围严于本条）。本条原「可回溯的内部编号按项目约定处理」的松口**已随之收回**——项目约定不得放宽到「按约定可写进项目内容」。

== 配置文件的字符串取值须加引号（防被转义）

适用于**写配置文件时**——以 YAML 为载体、或任何**存在隐式类型推断**的配置格式（YAML、`.cnb.yml`、GitHub Actions 工作流等）。**不含本就无隐式推断的格式**（JSON 的字符串必须自带引号、TOML 的值类型由语法决定）——本条不向它们扩用。依据：YAML 1.1/1.2 的隐式类型解析把裸标量按 `int`/`float`/`bool`/`null`/日期等推断（YAML 规范「Tag Resolution」），版本间解析规则还不一致（YAML 1.2 不再把 `yes`/`no`/`on`/`off` 当布尔）；The Twelve-Factor App（配置外置且须原样、可预期）。**口径对齐**：用户说的"避免被转义"，机制上指的就是这类**隐式类型推断与取值规范化**——裸标量被读成非字符串类型后，原文本即丢失（`1.10` 变成浮点 1.1、`yes` 变成布尔真），与"字符串被改写成别的类型"同效。

* **明确是字符串的值一律加双引号（L1，用户口径）**：一个值的**语义是字符串**时——哪怕它由数字、英文、特殊符号组成——**必须用双引号包裹**（`version: "1.10"` 而非 `version: 1.10`、`name: "yes"` 而非 `name: yes`、`phone: "10086"` 而非 `phone: 10086`）。**取值＝该标量被双引号包着**这一状态；**不依赖解析器如何推断**——推断出的类型随解析器与 YAML 版本而变，写引号才是把"这是字符串"钉定在文本里。**判定标准（任一命中即违规）**：① 语义为字符串的标量以裸值书写（无引号）；② 靠"我这边解析出来正好是想要的类型"为裸值开脱；③ 为规避转义而改写成别的等价裸形态（如把 `1.10` 写成 `1.1`）——那改的是取值、不是格式。
* **须加引号的取值形态（可逐条核对）**：**任何以数字开头的字符串**（版本号 `"1.10"`、电话号码、编号、`"3.10.0"` 一类）；**恰为布尔/空值字样的字符串**（`"yes"`/`"no"`/`"on"`/`"off"`/`"true"`/`"false"`、以及 `"null"`/`"~"`/`"NULL"` 一类——YAML 1.1 会把前一组吃成布尔、把空值字样吃成 `null`/空）；**以特殊符号起头的字符串**（`"*"`、`"&"`、`"#"`、`"!"`、`"|"`、`">"`、`"%"`、`"{"`、`"["`、`"@"`、`` ` `` 一类 YAML 有语法含义的指示符）；**含 YAML 有特殊含义字符的字符串**（含 `:` 后接空格、`#` 前有空格、引号、换行、行首缩进、前后空格——不写引号时该值会被截断或被解析成新的键/注释）；**会被推断成日期/时间等非字符串类型的字符串**（`"2024-01-01"`——YAML 1.1 的解析器会把它读成时间戳；YAML 1.2 core schema 取消了该隐式解析，故同一份文本在不同解析器下得到的类型不同）。**判定标准**：取值命中上述任一类而未加双引号——即违规。
* **含需转义的字符时用双引号，不用单引号（L1）**：值里含 `\`、`"`、换行、制表符等需要**转义序列**表达的内容时，**只能**用双引号（`"...\n..."`）；**单引号内唯一被解释的转义是 `''`**（两个单引号表示一个字面单引号），`\n`/`\t`/`\"` 一类序列在单引号里都是**字面字符**，表达不了换行与制表符。故**本条统一取双引号、不混用两种引号**——混用时"这里为什么用单引号"没有稳定读法，且同一份文件出现两套引号规则。
* **加引号不改值、只为钉定类型（L1）**：加引号**只改变该标量被解析时走的路径**（走字符串、而非落到某个非字符串的隐式推断上），**不得借加引号之机改动值的文本**（不得顺手去空格、改大小写、补零、走样日期）；值本身要改属另一件事。
* **与「不信任外部输入」的分工**：本条管的是**配置文本里字符串的书写形态**；把配置值读进程序后如何使用（校验、转义、不拼命令）见 `specs/general/script.adoc`「安全」与 `specs/general/security.adoc`「输出编码/转义」——两条各自独立、互不替代。
