= 文档规范（通用层）

以下规范适用于文档、注释、设计文档的编写。某语言/技术栈的注释细节（如 Java 的 javadoc 规范）见 `specs/stack/` 对应文件。

== 注释与文档

* 注释与文档：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（如初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界），不追求完整设计叙述——完整设计（功能怎么设计、用例考虑、兜底、适用范围等）统一写入设计文档（见下条「设计文档」），避免注释东一块西一块不完整；常规小改动不强制备注；总纲：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释、README、规范文件等），不遗漏、不依赖记忆，临时产物除外（见执行原则「临时产物」条目）

== 设计文档

* 设计文档：核心功能的新增、重构（含行为变更、方案选型、有取舍的设计）必须编写或更新设计文档，记录当时考虑到的所有东西：功能设计（方案是什么、为什么这样做、备选方案及不选原因）、测试设计（测试行为本身的设计：测试架构与组织、测试手法与参考实现、覆盖哪些场景、为什么这样测、测试边界与取舍）、兜底（有哪些兜底、兜底触发条件与边界）、适用范围（适用场景、不适用场景、已知限制与取舍）；功能设计与测试设计放在同一设计文档内（测试是功能的验证规格，二者一体，避免文档分散）；文档按模块建立子目录存放：根目录 `doc/design/<模块>/`，模块名取核心功能/组件所属模块（如 core/web/feign/log，以各项目实际模块划分为准），功能与测试文档成对放在同一模块子目录下（`Xxx.adoc` 设计、`XxxTests.adoc` 测试）；AsciiDoc 格式；文档随代码演进同步更新，新增、重构时必须处理
* 代码与文档互相引用：代码与设计文档必须**双向可定位**——文档须写明所对应功能的模块与类/方法（从文档能找到代码），代码（类/方法的注释）也须显式引用对应的设计文档相对路径（从代码能找到文档），二者任一处都能顺利跳转到另一处；注释写法见 `specs/stack/` 对应语言文件的注释规范；新增/重构代码时同步补齐双向引用，缺失引用的旧代码发现后直接补，不遗漏
* 设计文档须记录已知缺陷与不足：设计文档除记录设计本身，还须**显式记录当前工具类、方法、字段的已知缺陷、不足与注意事项**——包括但不限于：
  ** 易误用点：调用方可能踩坑的入参/出参假设、线程安全、可变状态被共享修改等
  ** 边界与异常：异常未处理/吞掉、空值/超长/超大输入等
  ** 默认值：字段/参数的默认值及其语义（如"0 表示未测量 / null 表示未采集"等易混淆约定），默认值可能引发的行为差异与误判
  ** 可能引发的问题：如拼接日志时异常静默导致主流程中断、字段不同步、序列化兼容等
  ** 性能瓶颈：大对象/循环内分配、正则/反射/序列化开销、阻塞 IO、复杂度隐患等
  ** 可能影响的功能：当前缺陷/不足/默认值变更会波及的其它功能、调用方或下游逻辑，须列出受影响范围以便评估改动
  ；记录粒度到"类→方法/字段"层级，按类/方法/字段分段标注，能定位到具体代码；缺陷内容随代码演进同步更新（修复后标注已解决或删除），不遗漏、不依赖记忆
* 文档版本与变更日志（**适用范围：仅设计文档、测试文档；规范文件不适用，见下**）：**设计文档、测试文档**（.adoc）头部必须包含 `Version` 与 `LastModified` 字段（置于标题之后，如 `Version: 1.0`、`LastModified: 2026-08-21`）；文档须维护**变更日志**小节（`== 变更日志`），按时间倒序记录每次变更：版本号、日期、变更摘要（改了什么、关联代码/需求）；初始落地版本从 `1.0` 起，代码有行为/接口/默认值/已知缺陷等任何变更时，Version 递增（如 `1.0`→`1.1`，重大重构可 `1.x`→`2.0`）、LastModified 更新为当前日期、并在变更日志追加一条
  ** **适用范围界定**：本机制**仅适用于设计文档、测试文档**（业务文档，随代码演进记录版本）。**规范文件（`specs/` 下各 .adoc）不适用、不要求维护 Version/LastModified/变更日志字段**——规范变更由其 git 历史承载，并须按规范管理（specs/core/management.adoc「规范调整」）执行"调整后子 agent 验证"。二者不得混淆。
  ** **变更日志位置（文末，时间倒序）**：放在**文档最末尾**，作为独立小节 `== 变更日志`，按**时间倒序**记录（最新变更在最上方、最旧在最下方，即追加时总是插到小节顶部）；头部 `Version`/`LastModified` 字段仍固定在标题之后，不随变更日志移动
  ** AI 强制约束（仅对设计/测试文档）：修改代码前，必须先更新此文档的 Version 与 LastModified 字段、并在变更日志追加对应条目，**否则禁止提交代码**；缺失头部字段的旧设计/测试文档发现后直接补，不遗漏
  ** 头部字段与变更日志位置参考（设计/测试文档通用）：
    ```
    = Xxx 设计文档

    Version: 1.1
    LastModified: 2026-08-21
    ...

    == 1. 功能设计
    ...

    == 变更日志

    - 1.1 | 2026-08-21 | 本次变更摘要（最新在上）
    - 1.0 | 2026-08-16 | 初始落地
    ```

* README 须登记项目级支撑目录：根 README 须登记项目下非源码模块的项目级目录（如 `specs/`、`doc/`、`script/` 等支撑目录），说明其用途与关键内容，使读者一眼知道"哪里有什么"、避免遗漏；`tmp/` 为临时产物目录（不提交），不登记；根级零散文档也应在 README 注明用途；新增项目级目录或脚本时同步更新 README；README 作为项目总览文档，其变更也按"文档版本与变更日志"精神维护

== 文件格式与编码

* 文件格式与编码：除入口 AGENTS 文件外，其他文档优先使用 AsciiDoc（.adoc）格式；所有文件一律 UTF-8 编码，除非明确不是 UTF-8（如特定二进制格式、明确指定其他编码的文件）
* 文档代码块：md/adoc 文档中代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法（避免 IDE 语法检查报红）；无法保证语法正确时标识为无格式类型（如 `text`），优先使用带格式的准确语言标识；伪代码/结构描述等非语法内容不得标注具体语言
* 文档问题：注释、README 等纯文档性缺陷，发现后直接修复，无需问询
