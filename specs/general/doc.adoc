= 文档规范（通用层）

以下规范适用于**所有语言、所有项目类型**（业务项目、工具库、脚本等，按实际情况适用）的文档与注释通用编写原则，以及文档格式与编码。设计文档与测试设计文档的编写规范见 link:../general/doc-design.adoc[]；业务系统（从立项到上线的完整项目）的全生命周期文档组织见 link:../general/doc-lifecycle.adoc[]；**多模块项目**下模块内部文档的组织与归属见 link:../general/doc-module.adoc[]（全局/规划性文档放根 `doc/`，模块内总结/规划文档放各模块 `doc/`）。某语言/技术栈的注释细节（如 Java 的 javadoc 规范）见 `specs/stack/` 对应文件。

== 注释与文档

* 注释与文档：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（如初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界）；**设计内容按范围落地、不是"一律进设计文档"**——跨类/模块/功能级的设计（方案与取舍、兜底、适用范围等）写入设计文档，类/方法级细节（参数契约、用例考虑、边界与默认值等）写入代码文档注释（判定见 link:../general/doc-design.adoc[]「信息归属」），避免注释东一块西一块不完整；常规小改动不强制备注；总纲：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释、README、规范文件等），不遗漏、不依赖记忆，临时产物除外（见执行原则「临时产物」条目）
* 文档内容不得因承载位置迁移而减少（**适用于所有语言、所有项目类型，含脚本**）：文档内容可写在**代码内的文档注释**（javadoc / docstring / JSDoc / 文件头注释等，按语言实际机制）或**独立文档**（`doc/` 下）中，二者只是**承载位置**不同——**要求记录的内容一项都不能少**（定位、能力目录、API 契约细节、边界、默认值、易误用点、设计取舍、兜底、适用范围、已知缺陷、变更记录等），**不得以减少、省略、"对付"式补写来降低文档要求**；总体要求比以往**更严格**：描述须写到代码可及的文档注释中，并随代码同步更新。**迁移不要求一步到位**——**不要一蹴而就，随代码变更逐步迁移**（改到哪迁到哪、随代码变更慢慢迁），不为此做一次性大迁移、也不得因"还没迁完"而不记录（新写/改动处一律按上述要求执行）
* 文档不得描述未提交且已移除的功能：本地开发/迭代过程中临时开发、后续被删除且从未提交（git commit）过的功能（含其模式、路径、方案等），一律不得写入任何持久文档（设计文档、测试文档、README、代码注释等）——它从未进入提交历史、无 git 记录可追溯，写入文档会产生「文档描述了代码中不存在的功能」的假象；**已提交**的移除/变更属于真实变更，须正常记录进文档（如按「版本与变更记录」记入统一 changelog），即「提交过的可以保留，属于变更，需要进文档」

== 文档组织与导航

* 文档目录只放总结性、规划性文档（类级描述进代码文档注释）：文档目录承载**总结性、规划性**内容（模块/功能总览、方案与规划、关键约定、跨模块内容等）；**类级与方法级描述写在代码内的文档注释中**（javadoc / docstring / JSDoc 等，按语言实际机制；类上放总结与目录、方法/字段上放细节，见 link:../general/doc-design.adoc[]「信息归属」）
* 文档与代码就近存放（内容要求不因承载位置降低，见上条）：文档确需成篇时与代码**同模块就近存放**（多模块项目放该模块 `doc/`，见 link:../general/doc-module.adoc[]），不得把模块内的文档统一堆到根 `doc/`——文档与代码离得越远越易出现"改了一半、文档与代码冲突"；根 `doc/` 只放跨模块/全局的总结性与规划性内容（架构、模块划分、需求、阶段产物等），**多模块项目的根 `doc/` 下不得出现类级文档**（不与任一源码文件同名而成的逐类文档）
* 文档目录即站点导航：文档目录树须能直接映射为在线文档站点的导航结构——每级目录须有**索引页**（命名统一，不混用 `README.adoc`/`index.adoc`/`README.md` 等多种形式）列出本级内容与下级入口，形成"总览 → 模块 → 功能"的层级（类与方法级细节由代码内的文档注释承载、随代码生成），保证有文档目录与结构可循（文档的价值在于可导航，不只在于存在）
* 文档间引用可解析、类间关系在代码中互引：文档中提到另一个类/方法时，须给出指向其**可点击链接**（非纯文本类名）；**类与类之间的关系（源文件、测试、性能测试及其相互依赖）由代码内的文档注释互相引用承载**（见 link:../general/doc-design.adoc[]「类间关系与双向引用」），使结构可被工具遍历，不靠文档里人工维护的索引；链接目标必须真实存在（可达性纳入 review/verify 检查项，见 link:../general/verify.adoc[]、link:../general/review.adoc[]）

== 文件格式与编码

* 文件格式与编码：除入口 AGENTS 文件外，其他文档优先使用 AsciiDoc（.adoc）格式；所有文件一律 UTF-8 编码，除非明确不是 UTF-8（如特定二进制格式、明确指定其他编码的文件）
* 文档代码块：md/adoc 文档中代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法（避免 IDE 语法检查报红）；无法保证语法正确时标识为无格式类型（如 `text`），优先使用带格式的准确语言标识；伪代码/结构描述等非语法内容不得标注具体语言
* 文档问题：注释、README 等纯文档性缺陷，发现后直接修复，无需问询
* 引用路径（一切引用）：任何需要指向本仓库/项目内其他文件的地方——文档正文、注释、说明文字、代码中的 doc 引用等——都必须用**可点击链接**而非纯文本路径，且链接须在**浏览器/站点与 IDE、编辑工具、开发工具、文本编辑器等各类工具中都能正常跳转**
* 链接写法：链接目标一律写**相对当前文件所在目录的相对路径**，使文件系统与站点按同一相对语义解析、各工具一致跳转——同目录直接写文件名（如 `link:doc-design.adoc[]`），跨目录按需用 `../` 上行到目标（如位于 `specs/core/` 下引用通用层写作 `link:../general/doc-design.adoc[]`）
* 禁止根绝对路径：**禁止使用以 `/` 开头的根绝对路径**（即链接目标写死成 `/specs/...` 这种以 `/` 开头的地址）：它在站点里按仓库根解析看似正确，但 IDE / 文本编辑器会把它当作文件系统盘符根解析，导致无法跳转；相对路径配正确的 `../` 才能让文件系统与站点同时跳转正确。指向目录、占位符或尚不存在的文件（如 `specs/stack/`、`specs/stack/<语言>-testing.adoc`）不属于引用，不受此约束
* 引用规则的适用范围：此条不适用于**代码运行时自身的逻辑实现**——如按相对位置读取配置文件、加载资源等——那属于代码逻辑设计，由对应技术栈/代码规范约束，不在本引用规范范围内；代码注释中依赖目标语言/IDE 识别机制的引用（如 Java 的 javadoc `@see`，其书写规则以技术栈规范为准——link:../stack/java.adoc[]「javadoc」规定文档路径**以模块根为基准**、须用英文双引号包裹，避免被 javadoc 当作类/成员引用解析报错；非 AsciiDoc `link:`）不受本条 `link:` 形式约束，但同样须能在 IDE 中跳转且指向真实存在、可追溯的文件
