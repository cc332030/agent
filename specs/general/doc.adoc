= 文档规范（通用层）

以下规范适用于**所有语言、所有项目类型**（业务项目、工具库、脚本等，按实际情况适用）的文档与注释通用编写原则，以及文档格式与编码。设计文档与测试设计文档的编写规范见 link:../general/doc-design.adoc[]；业务系统（从立项到上线的完整项目）的全生命周期文档组织见 link:../general/doc-lifecycle.adoc[]；**多模块项目**下模块内部文档的组织与归属见 link:../general/doc-module.adoc[]（全局/规划性文档放根 `doc/`，模块内总结/规划文档放各模块 `doc/`）。某语言/技术栈的注释细节（如 Java 的 javadoc 规范）见 `specs/stack/` 对应文件。

== 注释与文档

* **javadoc 即文档（其他语言同理）**：代码内的文档注释（Java 的 javadoc、Python 的 docstring、JS/TS 的 JSDoc 等，按语言实际机制）**本身就是文档**，与独立文档（`doc/` 下）地位等同——"文档先行"原则不变，但**先行的落点包含代码文档注释**，不是"必须先写独立 .adoc 文档"；先写代码文档注释（定契约：参数、返回、异常、边界）即已满足"文档先行"，独立设计文档与代码在**同一提交内**补齐即可（见 link:../core/execution.adoc[]「文档与代码对应同步」）
* 注释与文档：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（如初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界）；**设计内容按范围落地、不是"一律进设计文档"**——跨类/模块/功能级的设计（方案与取舍、兜底、适用范围等）写入设计文档，类/方法级细节（参数契约、用例考虑、边界与默认值等）写入代码文档注释（判定见 link:../general/doc-design.adoc[]「信息归属」），避免注释东一块西一块不完整；常规小改动不强制备注；总纲：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释、README、规范文件等），不遗漏、不依赖记忆，临时产物除外（见执行原则「临时产物」条目）
* 文档内容不得因承载位置迁移而减少：文档可写在**代码内的文档注释**（javadoc / docstring / JSDoc / 文件头注释等，按语言实际机制）或**独立文档**（`doc/` 下），二者只是**承载位置**不同——**要求记录的内容一项都不能少**，不得以减少、省略、"对付"式补写来降低文档要求（写法与篇幅要求见下「文档质量」）。**迁移不要求一步到位**——随代码变更逐步迁移（改到哪迁到哪），不为此做一次性大迁移、也不得因"还没迁完"而不记录；**记什么**按下「必记录项」核对，**搬到哪**见 link:../general/doc-design.adoc[]「存量文档收敛」的迁移对照清单
  ** 必记录项（逐项核对清单，缺一即未完成；不是"举例参考"而是**核对表**）：① 定位/一句话说明；② 能力目录/总览；③ **每个公共成员的职责与 API 契约**（参数、返回值、异常——**逐个公共成员都要有，不得只写类级**）；④ 边界与空值语义；⑤ 默认值及其语义；⑥ 易误用点；⑦ 设计取舍与为什么这样设计；⑧ 兜底与适用范围；⑨ 已知缺陷/限制（含状态标记）；⑩ 版本与变更记录。**十项都必须有落点、一项不落**；**承载位置按内容范围分配**：①② 类级描述与 ③-⑥ 类/方法级细节进代码文档注释，⑦-⑨ 跨类/模块/功能级内容进独立文档，⑩ 版本号进代码文档注释、变更摘要归项目统一 changelog（落点判定见 link:../general/doc-design.adoc[]「信息归属」「版本与变更记录」）
* 文档质量（**给人和 AI 读，六条缺一即未达高质量；不得以"写了文档"代替"写好文档"**）：① **准确**：与代码/事实一致，无过时描述；② **完整**：按上条「必记录项」核对，该有的落点一项不少；③ **可执行**：给出判定标准、边界与取值，读者能据此判断"做没做到"，不停留在口号式表态；④ **有价值**：只记录读者据此可判断/可动手的内容，不写空话套话、不复述代码自明的内容；⑤ **简洁**：篇幅与内容量匹配、**禁止长篇大论**，说清核心即可；⑥ **可验证**：涉及"必须/不得"的条目须可核对（指向具体文件、取值或检查方式），不留下无法验证的表述
* 文档不得注水（**内容质量硬线**）：严禁无意义、划水、凑字数——不写空话套话、不复述代码自明的内容、不为"看起来完整/体量够大"堆砌同义反复或没有实质内容的章节。本条只提高内容质量、**不放宽任何内容要求**：上两条一项不减，**简不等于缺、全不等于水**，判定标准是"是否承载可追溯的事实/决策/取值"（机械兜底见本仓库 `script/check_specs.py` 的 check_filler_docs）
* 去重不得误删最高关注项的引用（**与最高关注项的边界**）：去重只针对**重复的完整表述**，不针对**最高关注项/铁律的引用**——同一最高关注项（如 link:../general/git.adoc[]「文件移动与重命名」的 `git mv`）在多处出现是**刻意的强调与可发现性**，正确形态是"**一处完整定义 + 其余一行引用**"（见 link:../core/priority.adoc[]「强调的正确做法」）；条目上的**级别与最高关注项标注**同样是刻意信息，不得在判重时顺手删改（级别按 link:../general/spec-lifecycle.adoc[]「如何给一条规范定级」定级，标定后不得静默改级）；把这类引用判成重复而删除，即违反最高关注项 P2（完整性），风险高于"少量冗余"本身
* 多余文档直接去除：**要求有文档不等于要产出文档**——**未经用户明确要求，不得为"补文档"新建独立文档文件**（落点依「信息归属」与 link:../general/doc-design.adoc[]「设计文档」判定）；**已存在的无实质内容文档、重复文档、过时文档发现即删或合并**（是文档、是规范、是模板一律照此办理），不保留"为完整而存在"的空壳；删除/合并前须逐项核对内容已迁入合适落点（见 link:../general/doc-design.adoc[]「存量文档收敛」），删后仍须满足"内容不减少"
* 文档不得描述未提交且已移除的功能：本地开发/迭代过程中临时开发、后续被删除且从未提交（git commit）过的功能（含其模式、路径、方案等），一律不得写入任何持久文档（设计文档、测试文档、README、代码注释等）——它从未进入提交历史、无 git 记录可追溯，写入文档会产生「文档描述了代码中不存在的功能」的假象；**已提交**的移除/变更属于真实变更，须正常记录进文档（如按「版本与变更记录」记入统一 changelog），即「提交过的可以保留，属于变更，需要进文档」

== 文档组织与导航

* 文档目录只放总结性、规划性文档（类级描述进代码文档注释）：文档目录承载**总结性、规划性**内容（模块/功能总览、方案与规划、关键约定、跨模块内容等）；**类级与方法级描述写在代码内的文档注释中**（javadoc / docstring / JSDoc 等，按语言实际机制；类上放总结与目录、方法/字段上放细节，见 link:../general/doc-design.adoc[]「信息归属」）
* 文档与代码就近存放（内容要求不因承载位置降低，见上条）：文档确需成篇时与代码**同模块就近存放**（多模块项目放该模块 `doc/`，见 link:../general/doc-module.adoc[]），不得把模块内的文档统一堆到根 `doc/`——文档与代码离得越远越易出现"改了一半、文档与代码冲突"；根 `doc/` 只放跨模块/全局的总结性与规划性内容（架构、模块划分、需求、阶段产物等），**多模块项目的根 `doc/` 下不得出现类级文档**（不与任一源码文件同名而成的逐类文档）
* 文档目录即站点导航：文档目录树须能直接映射为在线文档站点的导航结构——每级目录须有**索引页**（命名统一，不混用 `README.adoc`/`index.adoc`/`README.md` 等多种形式）列出本级内容与下级入口，形成"总览 → 模块 → 功能"的层级（类与方法级细节由代码内的文档注释承载、随代码生成），保证有文档目录与结构可循（文档的价值在于可导航，不只在于存在）
* 文档间引用可解析、类间关系在代码中互引：文档中提到另一个类/方法时，须给出指向其**可点击链接**（非纯文本类名）；**类与类之间的关系（源文件、测试、性能测试及其相互依赖）由代码内的文档注释互相引用承载**（见 link:../general/doc-design.adoc[]「类间关系与双向引用」），使结构可被工具遍历，不靠文档里人工维护的索引；链接目标必须真实存在（可达性纳入 review/verify 检查项，见 link:../general/verify.adoc[]、link:../general/review.adoc[]）

== 文件格式与编码

* 文件格式与编码：除入口 AGENTS 文件外，其他文档优先使用 AsciiDoc（.adoc）格式；所有文件一律 UTF-8 编码（依据：RFC 3629 定义的 UTF-8），除非明确不是 UTF-8（如特定二进制格式、明确指定其他编码的文件）
* 文档代码块：md/adoc 文档中代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法（避免 IDE 语法检查报红）；无法保证语法正确时标识为无格式类型（如 `text`），优先使用带格式的准确语言标识；伪代码/结构描述等非语法内容不得标注具体语言
* 文档问题：注释、README 等纯文档性缺陷，发现后直接修复，无需问询
* 引用路径（一切引用）：任何需要指向本仓库/项目内其他文件的地方——文档正文、注释、说明文字、代码中的 doc 引用等——都必须用**可点击链接**而非纯文本路径，且须在**浏览器/站点与各类 IDE、编辑器、开发工具中都能正常跳转**；**路径基准只有两套、按引用所在位置区分、不得混用**——
  ** 文档/说明文字中的 link 引用 → **相对当前文件所在目录**：同目录直接写文件名（如 `link:doc-design.adoc[]`），跨目录用 `../` 上行（如位于 `specs/core/` 下引用通用层写作 `link:../general/doc-design.adoc[]`）；**禁止以 `/` 开头的根绝对路径**（如 `/specs/...`——站点按仓库根解析看似正确，但 IDE 会当作文件系统盘符根解析而无法跳转）。指向目录、占位符或尚不存在的文件（如 `specs/stack/`、`specs/stack/<语言>-testing.adoc`）不属于引用，不受此约束
  ** 代码注释中由 IDE/javadoc/docstring 工具解析的引用（如 Java 的 javadoc `@see`） → **相对模块根**（不受源文件包层级影响、不写 `../`；写法见 specs/stack/ 对应语言文件的注释规范，如 link:../stack/java.adoc[]「javadoc」）
* 引用规则的收尾与例外：上述两套基准下的引用都须指向真实存在、可追溯的文件；此条不适用于**代码运行时自身的逻辑实现**（如按相对位置读取配置文件、加载资源等——那属代码逻辑设计，由对应技术栈/代码规范约束）
