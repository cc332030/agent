= 文档规范（通用层）

以下规范适用于文档、注释的通用编写原则，以及文档格式与编码。设计文档与测试设计文档的编写规范见 link:../general/doc-design.adoc[]；业务系统（从立项到上线的完整项目）的全生命周期文档组织见 link:../general/doc-lifecycle.adoc[]。某语言/技术栈的注释细节（如 Java 的 javadoc 规范）见 `specs/stack/` 对应文件。

== 注释与文档

* 注释与文档：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（如初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界），不追求完整设计叙述——完整设计（功能怎么设计、用例考虑、兜底、适用范围等）统一写入设计文档（见 link:../general/doc-design.adoc[]），避免注释东一块西一块不完整；常规小改动不强制备注；总纲：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释、README、规范文件等），不遗漏、不依赖记忆，临时产物除外（见执行原则「临时产物」条目）

== 文件格式与编码

* 文件格式与编码：除入口 AGENTS 文件外，其他文档优先使用 AsciiDoc（.adoc）格式；所有文件一律 UTF-8 编码，除非明确不是 UTF-8（如特定二进制格式、明确指定其他编码的文件）
* 文档代码块：md/adoc 文档中代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法（避免 IDE 语法检查报红）；无法保证语法正确时标识为无格式类型（如 `text`），优先使用带格式的准确语言标识；伪代码/结构描述等非语法内容不得标注具体语言
* 文档问题：注释、README 等纯文档性缺陷，发现后直接修复，无需问询
* 引用路径（一切引用）：任何需要指向本仓库/项目内其他文件的地方——文档正文、注释、说明文字、代码中的 doc 引用等——都必须用**可点击链接**而非纯文本路径，且链接须在**浏览器/站点与 IDE、编辑工具、开发工具、文本编辑器等各类工具中都能正常跳转**。链接目标一律写**相对当前文件所在目录的相对路径**，使文件系统与站点按同一相对语义解析、各工具一致跳转：同目录直接写文件名（如 `link:doc-design.adoc[]`），跨目录按需用 `../` 上行到目标（如位于 `specs/core/` 下引用通用层写作 `link:../general/doc-design.adoc[]`）。**禁止使用以 `/` 开头的根绝对路径**（即链接目标写死成 `/specs/...` 这种以 `/` 开头的地址）：它在站点里按仓库根解析看似正确，但 IDE / 文本编辑器会把它当作文件系统盘符根解析，导致无法跳转；相对路径配正确的 `../` 才能让文件系统与站点同时跳转正确。指向目录、占位符或尚不存在的文件（如 `specs/stack/`、`specs/stack/<语言>-testing.adoc`）不属于引用，不受此约束。此条不适用于**代码运行时自身的逻辑实现**——如按相对位置读取配置文件、加载资源等——那属于代码逻辑设计，由对应技术栈/代码规范约束，不在本引用规范范围内。代码注释中依赖目标语言/IDE 识别机制的引用（如 Java 的 javadoc `@see`，其书写规则以技术栈规范为准——link:../stack/java.adoc[]「javadoc」规定文档路径须用英文双引号包裹，避免被 javadoc 当作类/成员引用解析报错；非 AsciiDoc `link:`）不受本条 `link:` 形式约束，但同样须能在 IDE 中跳转且指向真实存在、可追溯的文件
