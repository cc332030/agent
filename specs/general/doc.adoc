= 文档规范（通用层）

适用于**所有语言、所有项目类型**的文档与注释通用编写原则与文档格式编码。设计文档与测试设计文档见 `specs/general/doc-design.adoc`；业务系统全生命周期文档组织见 `specs/general/doc-lifecycle.adoc`；多模块项目下模块文档归属见 `specs/general/doc-module.adoc`。某语言的注释细节（如 Java 的 javadoc）见 `specs/stack/` 对应文件。

== 注释与文档

* **文档注释即文档（其他语言同理）**：代码内的文档注释（Java 的 javadoc、Python 的 docstring、JS/TS 的 JSDoc）**本身就是文档**，与独立文档（`doc/` 下）地位等同——"文档先行"原则不变，但**先行的落点包含代码文档注释**，不是"必须先写独立 .adoc 文档"；先写代码文档注释（定契约：参数、返回、异常、边界）即已满足"文档先行"，独立设计文档与代码在**同一提交内**补齐即可（见 `specs/core/execution.adoc`「文档与代码对应同步」）。
* **注释与文档的内容**：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界）。**设计内容按范围落地、不是"一律进设计文档"**——跨类/模块/功能级的设计（方案与取舍、兜底、适用范围）写入设计文档，类/方法级细节（参数契约、用例考虑、边界与默认值）写入代码文档注释（判定见 `specs/general/doc-design.adoc`「信息归属」），避免注释东一块西一块不完整；常规小改动不强制备注。**总纲**：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释、README、规范文件），不遗漏、不依赖记忆，临时产物除外。
* **文档内容不得因承载位置迁移而减少**：文档可写在**代码内的文档注释**或**独立文档**，二者只是**承载位置**不同——**要求记录的内容一项都不能少**，不得以减少、省略、"对付"式补写来降低文档要求。**迁移不要求一步到位**——随代码变更逐步迁移（改到哪迁到哪），不为此做一次性大迁移、也不得因"还没迁完"而不记录。
* **必记录项（逐项核对清单，缺一即未完成）**：① 定位/一句话说明；② 能力目录/总览；③ **每个公共成员的职责与 API 契约**（参数、返回值、异常——**逐个公共成员都要有，不得只写类级**）；④ 边界与空值语义；⑤ 默认值及其语义；⑥ 易误用点；⑦ 设计取舍与为什么这样设计；⑧ 兜底与适用范围；⑨ 已知缺陷/限制（含状态标记）；⑩ 版本与变更记录。**十项都必须有落点、一项不落**；**承载位置按内容范围分配**：①② 类级描述与 ③-⑥ 类/方法级细节进代码文档注释，⑦-⑨ 跨类/模块/功能级内容进独立文档，⑩ 版本号进代码文档注释、变更摘要归项目统一 changelog（落点判定见 `specs/general/doc-design.adoc`「信息归属」「版本与变更记录」）。
* **文档质量（六条缺一即未达高质量；不得以"写了文档"代替"写好文档"）**：① **准确**——与代码/事实一致，无过时描述；② **完整**——按「必记录项」核对，该有的落点一项不少；③ **可执行**——给出判定标准、边界与取值，读者能据此判断"做没做到"，不停留在口号式表态；④ **有价值**——只记录读者据此可判断/可动手的内容，不写空话套话、不复述代码自明的内容；⑤ **简洁**——篇幅与内容量匹配、**禁止长篇大论**，说清核心即可；⑥ **可验证**——涉及"必须/不得"的条目须可核对（指向具体文件、取值或检查方式）。
* **文档不得注水（内容质量硬线）**：严禁无意义、划水、凑字数——不写空话套话、不复述代码自明的内容、不为"看起来完整/体量够大"堆砌同义反复或没有实质内容的章节。本条只提高内容质量、**不放宽任何内容要求**：上两条一项不减，**简不等于缺、全不等于水**，判定标准是"是否承载可追溯的事实/决策/取值"。
* **去重不得误删最高关注项的引用**：去重只针对**重复的完整表述**，不针对**最高关注项/铁律的引用**——同一最高关注项在多处出现是刻意的强调与可发现性，正确形态是"**一处完整定义 + 其余一行引用**"；条目上的**级别与最高关注项标注**同样是刻意信息，不得在判重时顺手删改。
* **多余文档直接去除**：**要求有文档不等于要产出文档**——**未经用户明确要求，不得为"补文档"新建独立文档文件**（例外是规范化要求的固定落点，如多模块项目的依赖关系文档 `doc/dependency.adoc`）；**已存在的无实质内容文档、重复文档、过时文档发现即删或合并**，不保留"为完整而存在"的空壳；删除/合并前须逐项核对内容已迁入合适落点，删后仍须满足"内容不减少"。
* **文档不得描述未提交且已移除的功能**：本地开发/迭代过程中临时开发、后续被删除且从未提交过的功能一律不得写入任何持久文档——它从未进入提交历史、无 git 记录可追溯；**已提交**的移除/变更属真实变更，须正常记录进文档。

== 文档组织与导航

* **文档目录只放总结性、规划性文档**：文档目录承载**总结性、规划性**内容（模块/功能总览、方案与规划、关键约定、跨模块内容）；**类级与方法级描述写在代码内的文档注释中**。
* **文档与代码就近存放**：文档确需成篇时与代码**同模块就近存放**（多模块项目放该模块 `doc/`），不得把模块内的文档统一堆到根 `doc/`；根 `doc/` 只放跨模块/全局的总结性与规划性内容，**多模块项目的根 `doc/` 下不得出现类级文档**。
* **文档目录即站点导航**：文档目录树须能直接映射为在线文档站点的导航结构——**已承载文档的目录**须有**索引页**（命名统一，不混用多种形式）列出本级内容与下级入口，形成"总览 → 模块 → 功能"的层级。
* **索引页的触发判据（"该不该建索引页"）**：索引页是**"有下级内容"时才需要**——
** 目录下**已承载实质文档**（本级或更深的 `.adoc`/`.md`，非空壳）→ 建索引页；**空目录/仅有索引页"自己"的目录一律不建**——不得为"补索引"先建 `doc/` 目录再放一个 `README.adoc`；
** 索引页**只做导航**：指向下级/同级真实文档，**不得把上一级文档的内容换个壳复制一份**；索引页指向的目标全是别处同一份内容、不含本级自身信息时属空壳，发现即删；
** **模块级导航由模块 `README` 承担**：模块总入口本就是其 `README`，模块内若无独立功能文档，**不必**再在 `doc/` 下另设一层索引。
* **文档中提及类型优先写类名 + import，不写类全名（L2）**：文档（含代码内的文档注释）提到某个类型时，**一律先直接写它的类名**（`CUnauthorizedException`），需要解析时在**就近的代码示例**里写一条该类型的 `import`——**不得**用**类全名**（FQN）充当标识。**理由**：类全名把包路径整条塞进句子，一句话里出现两三个即不可读；而包路径是"去哪找"的信息、只该出现一次，读者据此 import 一次即可在通篇按短名阅读。**"如果有必要"的判据（命中任一才算必要）**：① **同名类冲突**（两个待指代的类型短名相同，限定到能区分的粒度）；② **无代码示例可承载 import**（纯文档通篇没有代码块）；③ **该类型不在本仓库的 classpath 内**（读者无法据短名解析、也给不出可解析的 `import`）。**三个例外的边界（不得被读成本条的禁止对象）**：① **路径与坐标**（文档里的链接与 `@see` 标签所引的文件路径）不是类型名；② **字符串与配置**里必须全限定的场合（`@ConditionalOnClass` 类名、`main-class`、反射按名加载、`import` 语句本身）属逻辑实现；③ **文档自身的文本引用**仍按引用写法。**判定标准（任一命中即违规）**：① 文档正文/文档注释里出现"包名 + 类名"形态的指代且不属三种必要情形；② 同一段里既写短名又写类全名指代同一个类型；③ 以"写全名更准确"为由通篇写类全名。**语言无关**：Java 的 import、Python 的 `import`、TS 的 `import` 同理——此处 `classpath` 取"**本仓库的依赖/可解析范围**"，各语言按等价依赖树理解。**为 L2、不做存量一次性替换**（随动调整）。Java 落点见 `specs/stack/java.adoc`「javadoc」。
* **名称的定义按作用域归档、引用只写名称**：文档里出现某个**名称**（概念/代号/缩写）时，**只写名称、不复述定义**；定义按其作用域写进唯一落点（**当前文档的名称定义写在本文开头**，其余各档见 `specs/general/terminology.adoc`「数据字典」的作用域分档表）。本条与「信息归属」同向：那条管"一段内容该写在哪一层"，本条管"一个名称的定义该归在哪一档"。
* **文档间引用可解析、类间关系在代码中互引**：文档中提到另一个类/方法时须给出指向其**可点击链接**（非纯文本类名）；**类与类之间的关系（源文件、测试、性能测试及其相互依赖）由代码内的文档注释互相引用承载**（见 `specs/general/doc-design.adoc`「类间关系与双向引用」），使结构可被工具遍历；链接目标必须真实存在。

== 文件格式与编码

* **格式与编码**：除入口 AGENTS 文件外，其他文档优先使用 AsciiDoc（`.adoc`）格式；所有文件一律 UTF-8 编码（依据：RFC 3629 定义的 UTF-8），除非明确不是 UTF-8。
* **文档代码块**：代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法；无法保证语法正确时标识为无格式类型（`text`），优先使用带格式的准确语言标识；伪代码/结构描述等非语法内容不得标注具体语言。
* **文档问题**：注释、README 等纯文档性缺陷，发现后直接修复，无需问询。

=== 引用路径（一切引用）

任何需要指向本仓库/项目内其他文件的地方——文档正文、注释、说明文字、代码中的 doc 引用——都必须用**可点击链接**而非纯文本路径，且须在**浏览器/站点与各类 IDE、编辑器、开发工具中都能正常跳转**。**路径基准只有两套、按引用所在位置区分、不得混用**：

* **文档/说明文字中的 link 引用 → 相对当前文件所在目录**：同目录直接写文件名（`link:doc-design.adoc[]`），跨目录用 `../` 上行（`link:../general/doc-design.adoc[]`）；**禁止以 `/` 开头的根绝对路径**（站点按仓库根解析看似正确，但 IDE 会当作文件系统盘符根解析而无法跳转）。指向目录、占位符或尚不存在的文件不属于引用，不受此约束。
* **代码注释中由 IDE/javadoc 工具解析的引用（如 Java 的 javadoc `@see`）→ 相对模块根**（不受源文件包层级影响、不写 `../`；写法见 `specs/stack/` 对应语言文件）。
* **反引号式路径引用（`` `specs/...` ``）：基准随加载入口、两态同源**——规范/文档正文中以反引号给出的仓库内路径**必须按"相对其加载入口（`AGENTS_COMMON.adoc` / 项目根 `AGENTS.adoc`）所在目录"解析**，不得改写成相对当前文件的 `../` 形式（否则同一个文件从不同入口加载会得到不同目标）。**两态同源**：① **有 base 的渲染态**（AsciiDoc 站点、带仓库根 base 的文档站）——反引号路径按仓库根解析、可直接定位，故**必须写成仓库根起算的完整路径**；② **无 base 的渲染态/纯文本态**（IDE 预览、AI 文本读取）——路径不会被解析为链接，须按"加载入口所在目录"人工解析（这是规范文件内**刻意使用反引号而非 `link:`** 的原因：同一份文件既要在仓库内被引用、又要作为远程规范被消费方加载，两态须同源可解析）。**两种读法指向同一文件**即合规；同一引用出现两种不同基准、或在能作为链接处用纯路径，均属违规。
* **引用方式选型的覆盖面判据（L1）**：选"可点击链接"还是"反引号路径"，按**目标读者的工具链覆盖面**判定——
** **需同时覆盖站点与各类 IDE/编辑器** → 用 `link:` 相对当前文件；
** **需同时覆盖"仓库内阅读"与"作为远程规范被加载"** → 用反引号 + 相对加载入口；
** **覆盖面判据同样适用于文档站**：站点解析依赖构建时的 base，故选型时按"读者的工具链里哪种解析方式占比更高、缺哪一种会失效"决定，并在同一仓库内保持一致（不得同一仓库两种基准混用）。
* **引用规则的收尾与例外**：上述两套基准下的引用都须指向真实存在、可追溯的文件；此条不适用于**代码运行时自身的逻辑实现**（按相对位置读取配置文件、加载资源等，那属代码逻辑设计）。
