= code review 规范（通用层）

以下规范适用于 code review 活动（依据：IEEE 1028 软件评审与审查标准；安全视角参考 OWASP Code Review Guide）。

== 问题记录

* code review 问题记录：分级用 P 前缀，P0 最高、数字越小级别越高；序号以 Q 开头跨分级连续编号（如 P0 编 Q1~Q3 则 P1 从 Q4 开始），级别仅作分类不影响编号；**文档已备注为已知问题、暂不修改的问题，用独立标记 `KNOWN` 单独归类（等级最低，不占 P 分级与 Q 序号）**，仅记录留痕、不需后续处理，避免混入待处理高优先级干扰注意力；每个问题浓缩一句话标题；问题需有明确状态（待处理/已修复/已备注/待评估等），已备注问题写明处理方案，便于人工更新（适用于所有有状态、需人工确认的问题记录）；废弃方法、字段及待完成占位代码（TODO、空实现、未引用方法等）不作问题提示；过于细节、无实际影响的问题不作提示（矫情原则）；上述不作问题提示的规则同样适用于测试类
* **备注落点按事项的适用范围判定（L1）**：人工要求给某个扫描出的问题/事项"备注"时，**先判它属哪一类、再决定写到哪**。判定标准（可逐条核对）：①**把具体类名/模块名去掉后该结论是否仍成立**？仍成立＝**全局性**；②**是否只有某一处能触发或违反**？是＝**范围性**；③两条都答不上来时按**全局性**处理（宁可落到全局落点，也不让某一类问题只在一处可见）。
  ** **全局性**（跨类/跨模块/项目级的约定与系统性风险、与具体实现位置无关的规则）→ 备注到**全局落点**（根 `doc/` 的全局文档、项目规范、README、统一 changelog 等；全局文档与模块文档的分界见 link:../general/doc-module.adoc[]「全局文档与模块文档的分界」），**不得**写进范围性落点——典型反例：把"全项目都要注意 X"写进某个类的 javadoc（只有读该类的人看得见，换个入口就找不到，也会与"同一信息只写一处"冲突）；**优先用既有的全局落点，不为此新建文档**（见 link:../general/doc.adoc[]「注释与文档」的"多余文档直接去除"）；**全局备注里也不出现范围性内容**——写进全局落点的内容同样须是全局表述（去掉具体类名/模块名后仍成立），某个类的具体位置与实现细节、只在某个模块成立的取值或取舍都属范围性内容，须留在范围内落点、全局备注只用**链接**指向它。反例：全局落点里写"`Foo` 类的 `bar()` 要判空"——应写成"入参可能为空，调用方须判空"这类通用约定，并链接到该类/方法。
  ** **范围性**（该类的契约/边界/易误用点、该模块内的实现取舍）→ 备注到**范围内落点**（该类的文档注释、模块级文档），不上升为全局规范。

== 问题修复

* 修复 review 问题：只做最小目标改动，修复前后自查，不得引入新的行为变更或缺陷；修复前先声明该功能的"不可违反的约束"（不变量），候选方案必须全部满足；候选方案做正常路径与异常路径双检查（正常路径行为不得改变、异常路径资源须释放）；修复后反向自查：本次修复会让哪个原本正常的场景失效？答不上来视为未自查；修复完补充测试用例且验证通过
