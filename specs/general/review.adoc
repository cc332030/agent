== 问题记录

* **分级与编号**：问题记录用 P 前缀分级，P0 最高、数字越小级别越高；序号以 Q 开头跨分级连续编号（P0 编 Q1~Q3 则 P1 从 Q4 开始），级别仅作分类不影响编号；**文档已备注为已知问题、暂不修改的问题用独立标记 `KNOWN` 单独归类**（等级最低，不占 P 分级与 Q 序号），仅记录留痕、不需后续处理；每个问题浓缩一句话标题；问题需有明确状态（待处理/已修复/已备注/待评估），已备注问题写明处理方案，便于人工更新。
* **不作提示的对象**：废弃方法、字段及待完成占位代码（TODO、空实现、未引用方法）；过于细节、无实际影响的问题（矫情原则）；上述规则同样适用于测试类。
* **备注落点按事项的适用范围判定（L1）**：人工要求给某个扫描出的问题/事项"备注"时，**先判它属哪一类、再决定写到哪**。判定标准（可逐条核对）：① **去掉具体类名/模块名**后该结论是否仍成立？仍成立＝**全局性**；② **是否只有某一处能触发或违反**？是＝**范围性**；③ 两条都答不上来时按**全局性**处理（宁可落到全局落点，也不让某一类问题只在一处可见）。
** **全局性**（跨类/跨模块、项目级的约定与系统性风险、与具体实现位置无关的规则）→ 备注到**全局落点**（根 `doc/` 的全局文档、项目规范、README、统一 changelog），**不得**写进范围性落点——典型反例：把"全项目都要注意 X"写进某个类的 javadoc（只有读该类的人看得见，换个入口就找不到，也会与"同一信息只写一处"冲突）；**优先用既有的全局落点，不为此新建文档**；**全局备注里也不出现范围性内容**——某个类的具体位置与实现细节、只在某个模块成立的取值或取舍都属范围性内容，须留在范围内落点、全局备注只用**链接**指向它。
** **范围性**（该类的契约/边界/易误用点、该模块内的实现取舍）→ 备注到**范围内落点**（该类的文档注释、模块级文档），不上升为全局规范。

== review 的默认检查面（只查问题，不动存量）

review（含 code review、改动后的 review、检查修复类任务）**默认只查问题**：**代码问题、文档问题、用例问题**三类。规范里的其余取向性要求（如优先用 `@ConfigurationProperties`、优先声明式映射一类"更优写法"的引导）**默认不在 review 中查出来、不据此提出问题**——它们对**新增/修改**的内容生效，review 不是它们的第三个生效面。

* **默认检查面（L1）**：review 只提出**三类问题**——① **代码问题**（缺陷、错误、安全隐患、资源与并发问题等会造成实际失效的）；② **文档问题**（内容与代码不符、描述缺失/过时等）；③ **用例问题**（用例缺失、断言无效等）。其余规范条目**只约束"本次新增/修改的内容"**，对**存量**（既有代码、既有文档、既有用例中不符合那些取向性要求的部分）**默认不查、不报、不要求整改**。
* **存量不动、随动迁移（L1）**：存量不合某条取向性规范**不构成问题**，改到哪个文件才顺带调整（随动迁移，见 `specs/core/execution.adoc`），review 不得据此提出问题（含以"与规范不一致""建议补齐""顺手规范一下"等形态提出的意见）。
* **唯一例外是主动声明（L1）**：用户明确声明要求 review 某类内容（如"这次 review 一下配置项绑定"）时，按其声明范围查——**声明是例外而非默认**，且仅对当次生效、不得泛化为默认检查面。
* **降级式表述属必查的问题形态（L1，用户提出）**：`prompts/review.adoc` 与 `prompts/spec-refine.adoc` **共用这一条**——两份命令的第 2、3 步所列的检查面都要查它，不得只在其中一份里写一份自己的版本。**要治的形态**："把没做成的事写成了做过的"——措辞完整、语气也不含糊，**结论与事实对不上**才是它的特征。判定标准（任一命中即报）：① 本可自行取到证据的事被"这条已记录 / 已说明 / 建议人工确认"一类说法结束（判据本体见 `specs/general/planning.adoc`「卡住时先自证」的『降级式表述与本节同罪』）；② 把"我这边没有"写成"项目不支持 / 环境不可用"；③ 一档要求被悄悄压成更窄的一档（范围收窄、"要有"降成"暂不支持"、L1 降成建议）。**判据取结论与可核对事实的差**，不取措辞像不像在汇报；**本条是真源**，两份命令与别的提示词只回指本条、不复述。
* **一个功能的实现跨模块属代码问题（L1，必查）**：**同一件事（同一行为、同一份取值、同一条流程）的实现分散在两处及以上、且这两处不在同一个模块**（构建单元/包边界/独立发布的库）时，**算代码问题、须查出来并报**——它不是"写法偏好"，而是**同一功能的多个来源**：改一处必漏另一处、两处各自漂移，且没有单一位置掌握它的触发条件与副作用。**判定标准（任一命中即报）**：① 完成一件事的代码被拆在两个及以上模块里，**调用方要按顺序各调一遍**才成立（本可一次调用的事变成跨模块的编排）；② 同一份取值/契约/规则在两个模块里**各有一份完整定义**，靠"两处要一起改"维持一致；③ 一个模块的实现**依赖另一个模块的内部细节**才能成立（跨模块直接读写对方的表、类型、内部状态，或绕经公共层之外的旁路）；④ 拆开的理由只是**代码量/文件已存在的位置**，而拆出的部分**没有人单独取用**（判据同 `specs/general/coding.adoc`「源码文件的规模」的"拆要按职责切、不按体量切"）。**与「存量不动」的边界（L1）**：本条与「存量不动、随动迁移」**不冲突**——它查的是**一个功能的实现跨了模块**这一事实本身（属①代码问题），不是"某处写法不符合某条取向性要求"；故**存量里已经跨模块的功能同样要报**，按随动迁移处理到本次改动触达为止，不得以"存量"为由放过。**与「一个 issue 一个 PR / 范围控制」的边界（L1）**：报出不等于在本轮把它全量重排——**报出与处置分开**：报出须给位置与证据（见本文件「结论的记账形态」），处置按 `specs/general/scope.adoc` 与改动面定（能本轮收敛的本轮收敛、不能的如实标待处理，不得静默放过、也不得擅自发动全库改造）。**重构须处理这一形态（L1）**：判定为重构的任务里，本条命中处**必须进重构清单并落地**（收敛到单一模块/单一来源、或补成显式的公共层让调用方只调一次），**不得只记为"已发现"就收尾**。**这一条不因"这两处看起来各管一摊"放过**：判据问句是"**要把这件事做成，是不是得跨过模块边界**"——答"是"即命中。
* 依据（标准名/编号）：IEEE 1028（评审目的是发现异常/问题，不是重新执行符合性审计）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）。

== 结论的记账形态（固定六列，一句事实，不复述判据）

依据：成文信息须可核验、可追溯（ISO 9001、ISO 10007）；判定须单一、无歧义、可验证（ISO/IEC/IEEE 29148）。**"固定六列、一句事实、不复述判据原文"是本集合的判据化取舍**——通行材料只要求"评审结论须可追溯"，没有规定列、也没有规定"不得复述规则原文"。

* **一条结论一行、六列固定（L1）**：每一条结论须落成一行，逐列写出——**① 问题**（一句话标题，见本文件「问题记录」的分级与编号）｜**② P 级**（P0–P3；`KNOWN` 按本文件「问题记录」不占 P 分级，单独标）｜**③ 位置**（文件 + 能被检索到的定位：节名、函数名或行号）｜**④ 一句事实**（**一句话**说清"哪里、什么、与哪条不符"）｜**⑤ 证据**（**可核对的取值**：命令与输出片段、文件与行、对比两处的位置；"已确认""已核对"不算证据）｜**⑥ 判断**（这一条的处置：**已修复 / 待处理 / 已备注**；须与④⑤对得上）。**列名与次序不得改、不得少列**——缺哪一列，读者就得回去翻原始材料才能判这条结论成不成立。
* **不复述判据原文（L1）**：④⑤只写**这一条事实与它的证据**，**不把规则正文抄一遍**、也不写"按规范某节应如何如何"式的引述——规则是可检索的、位置可点开，抄一遍只是把读过的原文再付一次成本。要指规则时**只写引用坐标**。
* **总账按三态分栏、与逐行不重复（L1）**：总账（这次验到哪一步）按 `specs/general/verify.adoc`「验证的效力等级」的**三态台账**分栏，**三态各占一栏、不得合并**（逐态取值以那里为准，本处不重列）；**逐行六列管"这一条是什么"，三态分栏管"整体验到哪一步"**——两处各写一件事，**逐行里不再重复整体结论**。**两处不是同一套取值、也不互相映射**：⑥ 是**单条问题的处置**（已修复/待处理/已备注），三态是**验证本身**的结论——"本次未发现问题"属后者，不占 ⑥。
* **汇报口径（L1）**：review 类任务的对外汇报＝**逐行结论 + 三态分栏总账**，不写成散文式过程叙述；**"本次未发现问题"同样是完整结论**（本文件「review 的默认检查面」已定：review 的目的是发现异常，不是凑产出）。汇报里出现数字与清单的，须与逐行台账**对得上**（判据见 `specs/general/verify.adoc`「汇报须与可核对的事实一致」）。
* **存量（L1，不回改历史行）**：本条**只约束生效之后**产出的结论与台账；**既有台账按原形态保留、不回改、不追认违规**——改到哪一份才按新形态写（随动迁移，见 `specs/core/execution.adoc`「规范变更的存量处理」）。
* **边界（L1）**：本条管**结论怎么写下来**，不管"查什么"（`specs/general/review.adoc`「review 的默认检查面」）、也不管"验证做到哪一步"（`specs/general/verify.adoc`「验证力度分档」）——三处各管一件事，互不替代。

== 增量复核（同一个对象只审一次，只审它上次之后的那一段）

依据：评审目的与审查重核的依据同上（IEEE 1028）；变更控制要求"同一配置项的状态可辨识、可追溯"（ISO 10007）；内容未变即结果不变、重做得不到新判据（ISO/IEC/IEEE 25010 性能效率）。**增量复核、以 sha 记账**是本集合按上述方向的判据化取舍——通行材料与本平台都没有这个机制。

* **同一个对象、同一个 sha 不重审（L1）**：复核**以 commit sha 为对象**、不以分支名或"这个 PR"为对象（分支会被追加提交、被强推，见 `specs/platform/cnb.adoc`「对象钉定与可追溯」）。**开始时先核打头要审的那个 sha 在既有复核留证里有没有**：该 sha 已记在留证里、且其后该对象**没有新增提交**时，**不重审**——直接写明"本次对象＝上一轮的 X 已在第 N 轮审过、其后无新增"，把上一轮的结论按原样带着（不得重打一遍结论、也不得换个措辞再结论一次）。
* **适用面（L1）**：复核对象**本身就是一次提交（commit sha）**时按本条取值；对象不是提交（设计稿、对话、文档版本）时，按承载它的平台或项目自身规范给"上次复核到哪"的取值——**不得**因此把本条读成"只对 git 成立"，本条管的是**检查面**这件事。
* **只审"上次复核 sha 之后"的那一段（L1）**：对象已经推进到 Y、而上次复核停在 X 时，**本次的检查面＝`X..Y` 的改动**，不是整份对象、也不是 `目标分支..Y` 的全部改动。**两处不可省（否则增量等于没审）**：① **接缝处要回到 Y 的完整内容上判**——**"完整内容"取改动所在的那一份单位**（被改的那个节、函数、文件），不是整份对象、也不是只剩 diff 那几行：一段新增文本、一处改动，只看 diff 里那几行判不出对错（它可能把上文的意思改掉了、"必须"被改成了"应当"）；② **判据一件不少地照取**——"查什么"按本文件「review 的默认检查面」，"验证做哪几件"按 `specs/general/verify.adoc`「验证力度分档」——增量省的是**重复读已审过的那一段**，不是省**判据**。
* **上一次的结论在四种情形下不作数、须重审（L1）**：① 被否；② 未确证（含悬置、只跑了一部分、跑的不是这一份）；③ **审的不是这一份**——上一次钉的 sha **已不在该分支历史里**（强推、压缩、rebase 之后旧 sha 被替换，平台侧的后果与处置见 `specs/platform/cnb.adoc`「对象钉定与可追溯」），按旧 sha 得出的"这些行没问题"不能转嫁给新 sha（对应 `specs/general/verify.adoc`「按需验证、不滥验证」的重验三类）；④ 对象**换了承载位置**（另一个 PR／另一个分支）。**判据是一个问句**：上一轮那条结论**凭的当时那个 sha、与眼前这个 sha 是不是同一份内容**（怎么判属执行动作；判不出来即按不成立）——说不出凭什么仍有效，即按"没审过"处理。
* **记账落在对象上、不在人身上（L1）**：续接复核靠的是**复核留证里的"上次复核 sha + 结论"**，不靠记忆、也不靠"我记得看过"。故① 每轮复核的留证须写清**核的对象是哪个 sha**（`specs/general/verify.adoc`「验证对象须钉定 commit sha」）；② **留证长什么样不另立形态**——它就在这一轮的结论里（形态见本文件「结论的记账形态」，`specs/general/verify.adoc`「验证的效力等级」的三态台账也是同一处留证）；③ 取不到留证时按**首次复核**做，不假定"前面有人审过"；④ **不为此另造一份状态位**（标签、配置文件一类）——同一事实的第二处来源；留证落在哪里、怎么取，由承载这次复核的平台或项目给出，**本文件不指定实现**（CNB 的落点见 `specs/platform/cnb.adoc`「对象钉定与可追溯」）。
* **与"改完即审"的分工（L1）**：本条管**这一轮该读哪一段**（检查面）；**该做什么动作**仍按改动性质取值（见本文件「改动后的 review（每次改完都得复核一次）」与 `specs/general/verify.adoc`「验证力度分档」）——增量不是降档的理由，改一个错字的 A 档与新增一道防线的 C 档，**该做的件数一件不少**，少的只是已判过的那段输入。
* **存量（L1）**：本条**只对生效之后**的复核成立——既有的复核记录不追认、不要求回补，也不回改历史行（与 `specs/core/execution.adoc` 的存量随动迁移同向）。

== review 时的干净子 agent 复核（强制）

依据：评审与被评审须相互独立、且须能独立重核（IEEE 1028 软件评审与审查标准；ISO 10007 变更控制与可追溯、ISO/IEC/IEEE 29148 可追溯）。本条与 `specs/general/verify.adoc`「规范验证」写的是**同一件事的两半，两处各占一半**：那一半给"复核的视角、效力等级与留证形态"（触发面＝**按改动性质**，规范类改动才做三视角），本条给"复核怎么落成一个干净上下文"（触发面＝**review 活动自身**，不依赖改动的性质）；**两处互不替代**，各处的触发面只在各自处声明，不在另一处复述。

* **强制开干净子 agent（L1）**：review 须由**与执行者相同的 Agent**承担——"相同"按**该环境自己的粒度**判（判据与不确定时的处置见 `specs/general/self-check.adoc`「环境能力自评」的「同 Agent 的判定粒度」，本处不复述）。这一条不因改动小、任务标题不是 "review"、或"只是顺手改的"而豁免。
* **"干净"指上下文、且不得由改动方自任（L1）**：复核者的**上下文干净**——不得复用前序对话里的结论与判断前提；改动方**不得以自己那次执行的上下文充当复核的上下文**（自己那次执行就是被复核的对象所在的那次）。能证明"干净"的是**该次调用自己的输入面**（只带本次钉定的对象与判据），不是"我觉得已经隔离了"。
* **通道须先实测、后派发（L1）**：动手前须用**可核对的动作**确认本次执行里"能拿到干净子 agent"是否成立——只有确实取到的通道才算成立，**取不到按不成立处理**（不得"记成"已派发）。通道按平台/环境提供者，**本条不指定实现**；判定标准（两条都须实际做出）：① 确认调用方式**可执行**（该入口的调用实际返回结果，而非仅知道它存在）；② 确认该次调用**不承载本次会话的上下文**（新会话、或只带本次钉定的对象与其判据）。取到的通道、用到的模型/实例与对象钉定须写进本次留证。
* **派发形式（L1）**：优先**一次性、边界明确、可超时**的调用——给定对象（改动清单与钉定的 commit sha）即返回结论、不可追问、**不带工具**（不让复核者自行探查仓库）；每次复核**换一次干净上下文**，不复用上一次复核用过的那个。
* **硬超时（L1）**：每次派发须设**可判定的时限**（按同类任务的量级取，见 `specs/general/collab.adoc`「资源限制与感知」）；到点即视为失联，按"**放弃 + 如实标悬置**"处置，不得无限等待。
* **复核者不得换外部来源（L1）**：通道取不到时**不换任何外部来源的 Agent/NPC 顶替**（跨来源者看不到本执行者已加载的规范、判据无从核对）；也不得把复核派给一个会自行探查仓库的执行者——那与"一次读取、结论分栏"的一次性形态相抵。
* **降级路径（L1）**：通道确实不可用时**不跳过复核、不阻断交付**——在本次执行内按同一判据**由执行者本人串行承担**，并**如实标注独立性边界**（与改动方同一上下文/同一模型，独立性弱于第三方）；仍不可行时**如实标悬置**、写明未覆盖的角度与剩余风险。**"已交付 + 机械校验全绿 + 复核缺口如实标出"不得混写成"已复核通过"**。
* **复核结论按三态留证**：通过／未发现问题／悬置，三态各占一栏、不得合并，且须写出**实际读到的上下文范围**（判据与逐态取值见 `specs/general/verify.adoc`「验证的效力等级」，本条不复述）。
* **对引用方的口径（L1）**：本条**不指定实现、不要求某个特定产品**——引用方用自己平台已有的「另起一次干净上下文」即算满足；**引用方项目自身规范与本条冲突时以其自身规范为准**。**生效面**：只约束**本条生效之后**的 review，既有的 review 记录不追认为违规、也不要求回补。
* **依据落点**：干净子 agent 的能力可用性、同 Agent 的范围、硬超时与超时处置在 `specs/general/collab.adoc`；语义复核的视角、效力等级与留证形态在 `specs/general/verify.adoc`「规范验证」；"这个能力在本次环境里到底有没有"属执行环境自评，判据在 `specs/general/self-check.adoc`「环境能力自评」。

== 问题修复

* **最小目标改动**：只做最小目标改动，修复前后自查，不得引入新的行为变更或缺陷。
* **先声明不变量**：修复前先声明该功能的"不可违反的约束"（不变量），候选方案必须全部满足。
* **双检查**：候选方案做正常路径与异常路径双检查（正常路径行为不得改变、异常路径资源须释放）。
* **反向自查**：修复后反向自查——本次修复会让哪个原本正常的场景失效？答不上来视为未自查。
* **补用例**：修复完补充测试用例且验证通过。

== 精炼性（同一描述只写一处）

精炼性不是「写得短」，而是**同一描述只有一个真源**：同一件事在多处各写一遍，改一处必漏另一处，读者也不知道该以哪处为准。故**每次 review 与每次重构都须把「重复面」当成必查项**（不是可选项、不因「这次只改别的」跳过）。

* **重复面是必查项（L1）**：review 与重构开始时，须把**本次改动涉及面 + 同一事实的既有落点**扫一遍，逐一判「这条描述在本仓库还有没有第二处」，并把重复面记入清单——**这是「没发现重复」与「没查过重复」的分界**：说不出「查了哪些角度」即视为未查。
* **判定标准（任一命中即为重复描述）**：① 同一事实（取值、路径、命令、机制、清单）在两处以上**以完整表述出现**，而非「引用 + 指向」；② 同一事实的两处**措辞已经不同**（各自漂移已经开始）；③ 一处改了而另一处必须跟着改——**「改一处要记得改 N 处」本身即重复的证据**。
* **收敛形态（L1）**：**一处完整定义，其余位置只留「这是什么 + 在哪」的一行引用**。真源落点按事实的适用范围定：通用规则与其判据的落点是 `specs/` 内该主题的文件；安装与取法的操作细节的落点是其操作文档；代码的取值与契约的落点是代码本身（文档引用它，不抄它的字面值）。**同一件事的两半各有唯一落点**时，两边都须声明「我只说这一半、另一半去别处读」。
* **收敛时不得以去重换缺失（L1，与「内容不减少」的边界）**：**删掉的必须是重复表述本身，被删处须留下可达的引用**；删后须逐项核对内容未减少（判据见 `specs/general/doc.adoc`「注释与文档」与最高关注项 P3）。**对无法确定是否重复的内容一律保留**（宁可冗余不可缺失）。
* **两类形态不得被当成重复收敛**：① **最高关注项与其引用**——多处出现是刻意的强调与可发现性，收敛对象只有「逐字复制的完整定义」；② **各自的承接**——同一规则在通用层给判据、在技术栈层给该技术的落点，属分工不属重复；判「是不是重复」先看两处讲的是不是**同一件事**。
* **「篇幅大」与「重复」是两件事**：长的条目只要承载可核对的事实/决策/取值就不算多；短的条目逐字重复也不算精炼。**判据是「同一描述有几处」，不是字多字少**。
* **与「信息密度」的分工（两把尺子，都要过）**：本条判**"同一描述有几处"**（跨处的重复面）；**单处里"有多少句没有承载"**是另一把尺子——**只有一处、完全不重复的一段文字仍可能通篇是废话**。该判据（每一句须承载、判定标准、与 P3 的边界）在 `specs/general/doc.adoc`「信息密度（每句须承载）」，本条不复制其正文。
* 依据（标准名/编号）：ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148（同一要求须有唯一、可追溯的表述落点）；ISO 10007（配置管理与变更控制：同一配置项不得有多个真源）；DRY（Don't Repeat Yourself）与 Martin Fowler《Refactoring》「重复代码」。

== 改动后的 review（每次改完都得复核一次）

审查**不止发生在"专门做 code review 任务"时**——**每次动手改完东西（代码、文档、规范、测试、脚本、配置），都要在同一轮里对自己这份改动做一次 review**（"改完即审"），不得把它推到"下一轮再看""交给别人 review"。**"小改动不用审""顺手改的不用审"都不构成理由**（复核成本远低于漏改的返工成本）。

* **每次改动后的常规 review（L1）**：范围＝**本次改动的全部产物**（含顺手同步的引用、文档、用例、配置、登记），动作＝**按改动性质取值**——**代码类改动**按机械判据逐项核对（能编译/构建、测试按实际统计通过、无新增告警），**不做**三视角、**不做**全局核对（见 `specs/general/verify.adoc`「验证的适用边界」）；**规范类改动**先按 `specs/general/verify.adoc`「验证力度分档」判档（A 表述与登记 / B 单条判据 / C 新增与语义或加载面），再按该档做「改完规范必做的五件事」里对应那几件——**机械手段任何档都跑全，三视角只对 C 档强制**。
* **"改完即审"的固定动作（L1）**：① **跑**机械手段（该项目的全部既定校验）；② **比**基线（**该做基线时**与动手前取得的基线逐项比对——该不该做按改动性质判，见 `specs/general/verify.adoc`「验证的适用边界」；原有绿的仍绿、红的不得变多）；③ **核**改动清单与用户原话是否一一对应（有无漏项、有无越界，见 `specs/core/execution.adoc`「完成前自检」）——**"漏下的没说" 与 "没做" 同判**，本项须逐条回读发起人的问句、核对**输出有没有答到它**（判据见 `specs/core/execution.adoc`「输出的对齐与唯一落点」与 `specs/general/self-check.adoc`「已完成项的复读」），**并按「精炼性」核对一遍重复面**——本次改动涉及的那件事在本仓库还有没有第二处完整表述；有则按「精炼性」收敛（**不得只记不收敛就收尾**，唯一例外是超出本次任务范围、须交用户定）；④ **留**证（结果落盘，与改动一并交付）。
* **规范类改动不得只跑机械手段（L1）**：机械手段只覆盖确定项；"跑绿了"不等于"判据没被压成口号、机制在真实环境还会发生"——故 **B/C 两档都必须跟上语义复核**，C 档还须三视角与干净子 agent。**不得以"机械手段全绿"为由跳过该档要求的语义复核**；**A 档免做的依据只能是「验证力度分档」的判据命中**，不得是"改动小"。
* **复核者不可用时（L1）**：环境不提供子 agent / 派发失败或超时——**不跳过复核**、复核职责不丢：在本次执行内按同一判据串行核对并**如实标注独立性边界**，或**如实标悬置**；不得跳过复核把结论写成"已复核"。
* **复核的执行形态另有一处强制要求（L1）**：干净子 agent 的通道判据、派发形式与降级路径在本文件「review 时的干净子 agent 复核（强制）」——本条只说「要做哪种复核」（按改动性质取值），**那一条说「复核怎么落成一个干净上下文」**；两者的触发面不同（改完即审按改动性质触发，那一条是 review 活动自身的强制要求），互不替代。
* **"改完即审"与"专项 review 任务"的分工**：本条管**每次改动**这一层（不论任务标题是不是"review"）；专门的检查修复任务另见 `prompts/review.adoc`（会被复制到未知项目执行的公共提示词），两者**判据同源、不重复定义**（本条给判据，提示词给执行步骤）。
* 依据（标准名/编号）：IEEE 1028（软件评审与审查：评审是常规工程活动、不必等到专项评审阶段）、ISO 10007（配置管理与变更控制：每次变更都须核验）、ISO/IEC/IEEE 12207（软件生命周期过程：实现过程含验证）。
