= code review 规范（通用层）

适用于 code review 活动（依据：IEEE 1028 软件评审与审查标准；安全视角参考 OWASP Code Review Guide）。

== 问题记录

* **分级与编号**：问题记录用 P 前缀分级，P0 最高、数字越小级别越高；序号以 Q 开头跨分级连续编号（P0 编 Q1~Q3 则 P1 从 Q4 开始），级别仅作分类不影响编号；**文档已备注为已知问题、暂不修改的问题用独立标记 `KNOWN` 单独归类**（等级最低，不占 P 分级与 Q 序号），仅记录留痕、不需后续处理；每个问题浓缩一句话标题；问题需有明确状态（待处理/已修复/已备注/待评估），已备注问题写明处理方案，便于人工更新。
* **不作提示的对象**：废弃方法、字段及待完成占位代码（TODO、空实现、未引用方法）；过于细节、无实际影响的问题（矫情原则）；上述规则同样适用于测试类。
* **备注落点按事项的适用范围判定（L1）**：人工要求给某个扫描出的问题/事项"备注"时，**先判它属哪一类、再决定写到哪**。判定标准（可逐条核对）：① **去掉具体类名/模块名**后该结论是否仍成立？仍成立＝**全局性**；② **是否只有某一处能触发或违反**？是＝**范围性**；③ 两条都答不上来时按**全局性**处理（宁可落到全局落点，也不让某一类问题只在一处可见）。
** **全局性**（跨类/跨模块、项目级的约定与系统性风险、与具体实现位置无关的规则）→ 备注到**全局落点**（根 `doc/` 的全局文档、项目规范、README、统一 changelog），**不得**写进范围性落点——典型反例：把"全项目都要注意 X"写进某个类的 javadoc（只有读该类的人看得见，换个入口就找不到，也会与"同一信息只写一处"冲突）；**优先用既有的全局落点，不为此新建文档**；**全局备注里也不出现范围性内容**——某个类的具体位置与实现细节、只在某个模块成立的取值或取舍都属范围性内容，须留在范围内落点、全局备注只用**链接**指向它。
** **范围性**（该类的契约/边界/易误用点、该模块内的实现取舍）→ 备注到**范围内落点**（该类的文档注释、模块级文档），不上升为全局规范。

== 问题修复

* **最小目标改动**：只做最小目标改动，修复前后自查，不得引入新的行为变更或缺陷。
* **先声明不变量**：修复前先声明该功能的"不可违反的约束"（不变量），候选方案必须全部满足。
* **双检查**：候选方案做正常路径与异常路径双检查（正常路径行为不得改变、异常路径资源须释放）。
* **反向自查**：修复后反向自查——本次修复会让哪个原本正常的场景失效？答不上来视为未自查。
* **补用例**：修复完补充测试用例且验证通过。

== 精炼性（同一描述只写一处）

精炼性不是「写得短」，而是**同一描述只有一个真源**：同一件事在多处各写一遍，改一处必漏另一处，读者也不知道该以哪处为准。故**每次 review 与每次重构都须把「重复面」当成必查项**（不是可选项、不因「这次只改别的」跳过）。

* **重复面是必查项（L1）**：review 与重构开始时，须把**本次改动涉及面 + 同一事实的既有落点**扫一遍，逐一判「这条描述在本仓库还有没有第二处」，并把重复面记入清单——**这是「没发现重复」与「没查过重复」的分界**：说不出「查了哪些角度」即视为未查。
* **判定标准（任一命中即为重复描述）**：① 同一事实（取值、路径、命令、机制、清单）在两处以上**以完整表述出现**，而非「引用 + 指向」；② 同一事实的两处**措辞已经不同**（各自漂移已经开始）；③ 一处改了而另一处必须跟着改——**「改一处要记得改 N 处」本身即重复的证据**。
* **收敛形态（L1）**：**一处完整定义，其余位置只留「这是什么 + 在哪」的一行引用**。真源落点按事实的适用范围定：通用规则与其判据的落点是 `specs/` 内该主题的文件；安装与取法的操作细节的落点是其操作文档；代码的取值与契约的落点是代码本身（文档引用它，不抄它的字面值）。**同一件事的两半各有唯一落点**时，两边都须声明「我只说这一半、另一半去别处读」。
* **收敛时不得以去重换缺失（L1，与「内容不减少」的边界）**：**删掉的必须是重复表述本身，被删处须留下可达的引用**；删后须逐项核对内容未减少（判据见 `specs/general/doc.adoc`「注释与文档」与最高关注项 P3）。**对无法确定是否重复的内容一律保留**（宁可冗余不可缺失）。
* **两类形态不得被当成重复收敛**：① **最高关注项与其引用**——多处出现是刻意的强调与可发现性，收敛对象只有「逐字复制的完整定义」；② **各自的承接**——同一规则在通用层给判据、在技术栈层给该技术的落点，属分工不属重复；判「是不是重复」先看两处讲的是不是**同一件事**。
* **「篇幅大」与「重复」是两件事**：长的条目只要承载可核对的事实/决策/取值就不算多；短的条目逐字重复也不算精炼。**判据是「同一描述有几处」，不是字多字少**。
* **与「信息密度」的分工（两把尺子，都要过）**：本条判**"同一描述有几处"**（跨处的重复面）；**单处里"有多少句没有承载"**是另一把尺子——**只有一处、完全不重复的一段文字仍可能通篇是废话**。该判据（每一句须承载、判定标准、与 P3 的边界）在 `specs/general/doc.adoc`「信息密度（每句须承载）」，本条不复制其正文。
* 依据（标准名/编号）：ISO/IEC Directives Part 2 与 ISO/IEC/IEEE 29148（同一要求须有唯一、可追溯的表述落点）；ISO 10007（配置管理与变更控制：同一配置项不得有多个真源）；DRY（Don't Repeat Yourself）与 Martin Fowler《Refactoring》「重复代码」。

== 改动后的 review（每次改完都得复核一次）

审查**不止发生在"专门做 code review 任务"时**——**每次动手改完东西（代码、文档、规范、测试、脚本、配置），都要在同一轮里对自己这份改动做一次 review**（"改完即审"），不得把它推到"下一轮再看""交给别人 review"。**"小改动不用审""顺手改的不用审"都不构成理由**（复核成本远低于漏改的返工成本）。

* **每次改动后的常规 review（L1）**：范围＝**本次改动的全部产物**（含顺手同步的引用、文档、用例、配置、登记），动作＝**按改动性质取值**——**代码类改动**按机械判据逐项核对（能编译/构建、测试按实际统计通过、无新增告警），**不做**三视角、**不做**全局核对（见 `specs/general/verify.adoc`「验证的适用边界」）；**规范类改动**按 `specs/general/verify.adoc`「改完规范必做的五件事」逐条执行（**机械手段必跑 + 干净子 agent 三视角复核 + 三态台账**，一件都不能少）。
* **"改完即审"的固定动作（L1）**：① **跑**机械手段（该项目的全部既定校验）；② **比**基线（与动手前取得的基线逐项比对：原有绿的仍绿、红的不得变多；判据见 `specs/general/planning.adoc`「动手前先定基线」）；③ **核**改动清单与用户原话是否一一对应（有无漏项、有无越界，见 `specs/core/execution.adoc`「完成前自检」），**并按「精炼性」核对一遍重复面**——本次改动涉及的那件事在本仓库还有没有第二处完整表述；有则按「精炼性」收敛（**不得只记不收敛就收尾**，唯一例外是超出本次任务范围、须交用户定）；④ **留**证（结果落盘，与改动一并交付）。
* **规范类改动不得只跑机械手段（L1）**：机械手段只覆盖确定项；"跑绿了"不等于"判据没被压成口号、机制在真实环境还会发生"——故**必须**跟上干净子 agent 的语义复核与三态台账。**不得以"机械手段全绿"为由跳过语义复核**。
* **复核者不可用时（L1）**：环境不提供子 agent / 派发失败或超时——**不跳过复核**、复核职责不丢：在本次执行内按同一判据串行核对并**如实标注独立性边界**，或**如实标悬置**；不得跳过复核把结论写成"已复核"。
* **"改完即审"与"专项 review 任务"的分工**：本条管**每次改动**这一层（不论任务标题是不是"review"）；专门的检查修复任务另见 `prompts/review.adoc`（会被复制到未知项目执行的公共提示词），两者**判据同源、不重复定义**（本条给判据，提示词给执行步骤）。
* 依据（标准名/编号）：IEEE 1028（软件评审与审查：评审是常规工程活动、不必等到专项评审阶段）、ISO 10007（配置管理与变更控制：每次变更都须核验）、ISO/IEC/IEEE 12207（软件生命周期过程：实现过程含验证）。
