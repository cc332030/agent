= 通用编码规范（通用层，跨语言）

以下规范适用于**所有编程语言**的编码活动。某语言/技术栈专属的编码规则见 `specs/stack/` 对应文件。

== 抽象与接入成本

对外提供能力（公共库、框架、组件、SDK、可复用模块）时，**接入成本是设计指标**：功能可用不等于产品可用，使用方要写多少、要不要重复声明同一件事，直接决定它能不能被用起来。判定标准：**同一个可替换点（实现类型、配置项、装配动作）在接入方出现的次数不随使用点数量增加**——若使用方要按使用点各写一遍（如三个 service 各实现一遍同一个接口、各传一遍同一实现类型），即为抽象漏做，按「代码复用」处理（归并到唯一装配点）。

* 唯一装配点（L1）：对外能力的可替换点须有**唯一的一处声明/装配落点**（应用入口装配，即 Composition Root：一处理解与组装、其余各处取用），**不得要求多个使用点各自提供同一实现或同一配置**。判定特征：同一实现类型/配置项在接入方出现次数 > 1，或"新增一个使用点就要照着再传一遍"——出现即判重复（同一事实多个来源，改一处必漏其余），须上提到唯一装配点
* 可替换点须有可用默认（L1）：每个对外暴露的可替换点**须有可用的默认实现/默认值**；确实给不出默认时，须在文档显式声明"必须提供，否则启动失败"这类失败面，**禁止既无默认又不声明**（表现是"文档看着能用、跑起来才发现缺东西"）。判定标准：要么有默认（不提供也能跑），要么有显式必填声明（不提供就明确失败），二者必居其一
* 能自动装配就不要求接入方手写（L2）：可通过**约定/自动装配**（如 SPI 自动装配：`ServiceLoader`、自动配置注册文件；`@ConfigurationProperties` 的默认值）默认生效的，不要求接入方逐点书写——接入方手写行数越多，越难被用起来
* 存量边界：本条适用于**新写的对外能力**（新增抽象、新增可替换点）与**改到的既有抽象**（按「规范变更的存量处理」随动迁移：改到哪个接入点就归并该点，不发动全库改造）
* 多实现用限定符、不逐层传参（L2）：同一类型有多个实现时，用限定符/命名 Bean 等**声明式区分**、由装配侧决定用哪个；**禁止逐层传参传递依赖**（参数穿透）与让使用方自行创建或自行提供实现类型；跨层级共享的对象（会话、上下文等）用**作用域/上下文对象**承载，而非层层透传
* 依据（标准名/编号）：ISO/IEC 25010（易用性与可维护性属**产品质量特性**，与功能适用性同级）、ISO 9241-110（可控、符合预期）、ISO/IEC/IEEE 29148（需求单一、无歧义、可验证）、The Twelve-Factor App（Config 外置、Dependencies 显式声明）、Convention over Configuration 与依赖注入（Spring Boot 官方文档 Externalized Configuration / Auto-configuration；SOLID 的 DIP 与好莱坞法则）

== 代码复用

* **既有实现与先例优先（L1，动手前先查）**：写任何代码前，必须先确认"项目里这件事**已经怎么做**"——①查当前项目/模块**是否已有等价能力**（自有工具类、公共方法、既有封装）与**同类场景的先例**；②查**已引入的依赖/框架**是否已提供等价能力；③有先例或有等价能力时**必须复用**，新代码的写法须与既有先例**保持一致**，不得另起一套。识别特征：要写的功能在项目中已有类似调用点、已引入的库有现成 API、项目自有工具类已覆盖该操作。
* **不得以语言内置写法绕过既有能力（L1）**：当项目自有工具类、已引入的库/框架已覆盖某操作时，**禁止**改用语言/标准库的原生写法重写同一件事——典型反例：已有 `IdUtil.fastUUID()`/`CIdUtils.UUID()` 仍手写 `UUID.randomUUID().toString()`、已有 `CollUtil.isNotEmpty` 类工具仍手写 `x != null && !x.isEmpty()`、已有集合/字符串/空值工具类仍手写原生判空与拼装。工具类选择优先级与各栈的现成 API 见 `specs/stack/` 对应文件；依赖是否已引入按 link:../general/dependency.adoc[]「引入依赖」核实（未引入则不得为此强行引入，按当前可得能力选择）。
* **先例一致优于个人写法偏好（L2）**：同一项目内同类操作必须走同一入口、写法一致；发现既有先例与规范冲突时，按项目自身约定与「存量处理」处置（改到该文件时随动迁移），不得在同一项目里并存两种写法。
* 避免重复写相同代码：相同的代码逻辑抽离为公共方法，或移动到下游公共流程统一处理，不复制粘贴
* 一个对象需要初始化多个值且多处频繁调用时，优先抽离出公共方法（工厂方法/初始化方法）统一创建，避免重复初始化代码
* 工具类如需实例化（如实例工厂），用静态方法构建（静态工厂方法）而非构造方法，便于封装创建逻辑、命名语义与后续扩展；此时构造方法设为私有（private），禁止外部直接 new 构造
* 缓存前先判断对象生命周期（避免内存泄露）：为提升性能而缓存对象或中间对象时，须先搞清它是**一次性使用**还是**多次复用**——**只缓存会被多次使用的对象**；**禁止缓存一次性对象**（用完即弃的对象被缓存后不会释放，持续占用内存，长期运行导致内存泄露）。判断依据：该对象/结果是否会在后续被重复访问（跨调用、多请求命中）；无复用价值的不要缓存，需要时重新创建即可

== 警告与弃用

* 警告处理：除非显式声明（如代码注释说明该警告已知且接受），否则严禁遗留任何警告（编译警告、IDE 警告等）——警告虽不影响编译甚至运行，但特定场景下与报错无异，必须像解决报错一样解决；新代码不得引入警告，存量警告须修复或声明
* 兼容老代码无法避免的警告（如弃用 API 因低版本依赖无法替换）：须在代码注释说明原因并抑制，避免反复提醒；为兼容低版本而保留的旧 API 告警是正常且必要的，不属于需修复的警告
* 内部弃用 API 的调用不迁移、不修复：项目自研的废弃 API 被项目内部调用时，调用处保持原样，产生的弃用警告已知且接受（内部废弃 API 随时会被移除，迁移收益低且可能引入回归）；仅第三方库弃用 API 须升级到新签名

== 表达式与调用写法

* 实参不内联复杂逻辑与对象：方法调用实参只传简单值或已算好的局部变量，不内联复杂逻辑（如三元表达式、方法调用嵌套、多级 `.xxx()` 串联），也禁止内联对象初始化后直接作为入参——复杂计算与对象必须先创建为局部变量再传入；无参构造除外。识别特征：单行内嵌套多层方法调用/构造、同一表达式内连续换行的 `.method(...)` 链、以 builder/configure 等命名或以返回自身为特征的构造器方法
* 三元表达式（三段式）为**最低优先级**：只要存在其他可替代写法（工具方法、if-else、辅助函数、`||`/`or` 兜底等），就**绝不用三段式**；仅当既无现成工具方法、又无更清晰的替代写法时才允许用，且只限简单判断（如单个 null 兜底），复杂逻辑（嵌套三元、多分支、含长方法调用）一律改用 if-else，可读性优先于行数
* 判空/默认值兜底优先用工具方法：对"空则取默认值"这类兜底（如 `x != null ? x : default`、`x || default` 等），**有现成工具方法（如 `defaultIfEmpty`/`defaultIfNull`/`emptyToDefault` 之类）时强制使用**，不手写三段式；无现成工具方法时优先用 `||`/`or` 等语言内置兜底或 if-else，也可自行抽离一个通用辅助函数（如 JS 可自写 `defaultIfEmpty`），有就统一复用、不散落手写；以上均不可用时才退回三段式

== 类设计

* 纯数据结构类中不写逻辑：仅保留字段与简单的字段读写，不做计算、组装、格式转换、对外部对象的访问；需要时下沉到工具类或独立服务。识别特征：以 bean/model/pojo/dto/vo/entity 等命名的类，其方法中出现非字段读写的计算/转换/组装逻辑
* 配置类不写逻辑（各类承载配置的类，如 Spring `@ConfigurationProperties`、`@Configuration` 等）：除声明配置项与按配置装配对象外，**不得包含任何逻辑**——任何情况都不允许，无例外；配置类只保持纯数据对象（POJO）的基本功能（字段及其访问器；`@Configuration` 另可按需声明 `@Bean` 装配方法），需计算/转换/组装时下沉到工具类或服务中。判定标准：①配置类中不得出现条件分支（`if`/`switch`/三元等）与循环；②不得做格式转换、数据加工、对外部对象或远程资源的访问；③`@Bean` 方法须是「构造/装配」形态——构造依赖由容器注入、不得自行查找（如 `getBean`），装配只允许配置项到构造参数的传递（取值时按「判空/默认值兜底优先用工具方法」用工具方法或语言内置写法，不写分支、不做计算）。识别特征：以 Config/Properties/Options/Settings 等命名的类（已有存量按「规范变更的存量处理」随动迁移，不发动全库改造）
* 有开关（enable/switch 等布尔配置项）控制的逻辑：先判断开关，开关关闭时直接跳过，不在开关外做耗时操作（如取时间戳、拼字符串、访问外部资源），开关关闭即零成本。识别特征：布尔配置项之后接的代码块，整段逻辑应包在开关判断内或开关判断前置 return，开关判断置于最前
* 原则上不允许使用内部类（inner class，含嵌套类），除非无法代替（如回调/监听器、临时组合数据、实现局部接口等确需内部类承载的场景）；能抽为独立顶层类的应抽出去，避免类过度嵌套、职责不清

== 命名与代码质量

* NPE 原则：NPE 问题原则上必须修复（存在取舍时，在代码注释中说明取舍依据与边界）
* 兼容性与平衡：不因局部小优化牺牲兼容性（语言/运行时版本、操作系统、环境依赖等）；优化与健壮性、可维护性、实用性之间保持平衡，目标始终是更好维护、代码更健壮、实用性更好
* 接口/类/注解成员排序（大小 + 时间 + 复杂度，可同处一个类）：工具类的字段/方法顺序存在可排序维度时，按下述规则排列，多个维度可同时应用于同一类——
  ** 按大小：字段/方法按基本类型重载/分组时，按可存储数据大小/位宽顺序排列——整数类型按位宽递增、随后浮点按位宽递增、再 boolean（特殊仅两值）、最后 Object（引用类型）
  ** 按时间：字段/方法存在逻辑时序（如流程步骤、数据加工阶段）时，按流程走过的先后顺序、数据加工在流程中的处理顺序排列——先发生的在前、后发生的在后，与业务执行次序一致
  ** 按复杂度：字段/方法按实现/使用复杂度排列时，简单的在前、复杂的在后（如基础能力在前、组合/高级用法在后）
  ** 不按使用频率、字母序或历史追加顺序随意摆放
* 注解/装饰器（annotation/decorator，各语言均适用）属性排序：属性顺序须满足①与数据存储字段顺序保持一致（主键/必填在前）；②常用/必传属性在前，其中省略属性名时默认赋值的属性排最前，便于使用；其余属性按使用频率或逻辑顺序排列
* 接口/抽象类的实现类命名：实现类应有**标识性名字**（体现其具体实现方式/策略/用途，如按实现技术、场景、算法等命名），接口/基类使用简单名字；除非实现类是继承链中的一环（非末端），否则各实现类严禁同名

== 日志

* 禁止控制台打印：不允许直接输出到控制台（如 `System.out.println`、`console.log` 等）；需要输出日志时统一使用日志框架；控制台打印仅限明确需要控制台展示的独立场景（如性能测试，且应同时写入文件报告，不依赖控制台留存）
* 日志分级记录（便于调试排查、增强可维护性）：代码既要保证质量，也要方便排查问题——各环节**关键节点**（方法入口/出口、流程步骤、分支去向、中间结果等）应打日志记录运行轨迹。分级原则：
  ** 辅助排查的**细节**（关键输入/输出、中间状态、分支取舍等）用 **debug** 级别——**默认不打印**，仅在排查问题时开启 debug 查看，避免刷屏；
  ** **需注意的事项**（异常、边界兜底、非预期但可处理的场景、重要状态变更等）用 **info 及以上**（info/warn/error），确保默认日志能覆盖到值得关注的点；
  ** 权衡：不得因"代码重要就省略日志"导致难排查，也不得为省事全打 info 刷屏——**细节用 debug、值得注意才 info+**，按级别分层。具体日志框架写法（如 Java 的 slf4j）见 `specs/stack/` 对应技术栈文件
* 不打无意义日志：日志打在**关键节点**即可，非关键处不打——**空方法/空实现不打**（无轨迹价值）；**有开关启用的逻辑，开关不启用时一般不打**（开关关闭直接跳过、不打"开关未启用"类日志），除非确实有必要（如排查开关为何未生效）；不打无助于定位问题的噪音日志，**为打而打不如不打**
* 日志属性打印格式：打印属性（key/value）**不包双引号**，格式为 `key: value`——常规用**半角冒号 `:` + 空格**（如 `userId: 123`）；当 key 或 value 为**纯中文**时，用**全角冒号 `：` 且不加空格**（如 `用户ID：登录成功`）

== 注释

* 注释定位（结构 vs 逻辑）：面向结构的说明（类/模块、字段、方法/函数签名等的用途、契约、约束、默认值等）一律用该语言的**文档注释**机制书写（如 Java 的 javadoc、JS/TS 的 JSDoc、Python 的 docstring），供文档工具与 API 使用方识别；**详细设计（参数、返回值、异常、边界、默认值、空值语义、易误用点、已知缺陷、性能、线程安全等）一律写在源码的文档注释里、不另建独立文档**（独立文档只承载跨类/模块/功能级内容，判定见 link:../general/doc-design.adoc[]「信息归属」）；普通（非文档）注释原则上**仅限方法/函数体内部**，用于说明具体逻辑实现（为什么这样写、局部决策、边界取舍），不得用于方法体外的结构说明
* 内容进代码时须用文档注释，无文档注释机制才退回多行注释：原独立文档中的内容迁入代码后，**须以该语言的文档注释形式存在**（Java 的 javadoc `/** */`、JS/TS 的 JSDoc、Python 的 docstring 等），不得改用普通注释承载；判定"是否支持"看**该语言/文件类型是否有专门的文档注释语法**（有则必须用，如 Java/JS/Python；无则退回多行注释，如 Bash、PowerShell、配置/模板文件）；退回时使用**多行块注释**（见 link:../general/script.adoc[]「脚本头部注释」），置于结构定义之前、保持与文档注释同等的完整度与可读性，不得降格为行尾零散注释——**这是上条"普通注释仅限方法体内"的唯一例外：仅限"该语言无文档注释机制"时，才用多行块注释承载方法体外的结构说明**；即便在此例外下，**方法/函数体外的普通注释仍须收敛、只保留必要说明**，不因缺少文档注释机制而放任注释散落
* 注释内容本身遵守文档规范（link:../general/doc.adoc[]「注释与文档」）：仅记录局部决策与要点，不追求完整设计叙述
