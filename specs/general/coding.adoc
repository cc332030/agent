= 通用编码规范·代码组织与质量（通用层，跨语言）

本文件是通用编码规范的一族之一（**按主题拆分**，各份见下）：只放这一族主题的判据，不复制别族的条文。


== 本族怎么加载（按主题取，不整族读完）

本族按**主题**分成几份，**一份对应一类改动**：动手时只加载命中的那几份，不把整族读一遍。

[cols="2,3", options="header"]
|===
| 份 | 命中就加载

| `specs/general/coding.adoc`（本份） | 代码组织与质量：抽不抽公共件、既有能力有没有先例、源码文件该不该拆、质量下限、日志
| `specs/general/coding-shape.adoc` | 写法与结构：表达式与调用、类设计、命名与成员次序、注释的形式与承载
| `specs/general/coding-objects.adoc` | 数据与对象：手动建对象、对外契约的载体、多层转换、在哪调持久化 API
| `specs/general/coding-ui.adoc` | 界面：形状/尺度/颜色/交互/文案，以及两处是不是同一件事的第二份来源
| `specs/general/coding-runtime.adoc` | 运行期约定：一处取值落哪、缓存读写、接口方法与状态码、跨语言脚本落点、警告与弃用
| `specs/general/coding-source.adoc` | 源码管理与分发：常规档还是并发档、产物体积与按需加载
| `specs/general/coding-file-role.adoc` | 这个落点会不会被并行改动（只在项目取并发档时适用）
|===


* **按需取、不预读（L1）**：只加载**本次改动命中**的那几份；判不准时先取最贴近的一两份，确需再取——**不因"读了更保险"而整族读完**（读取范围见 `specs/general/context.adoc`「读取范围」）。
* **族内互指用全路径（L1）**：指到另一份的节时写**目标全路径**，不写"上一节""见下节"——族内节序会变，靠相对位置指路在拆分后必然指错。
* **本份是族的入口（L1）**：新增主题先判它属哪一份；新增一份须在本表登记并写明触发面——未登记的份永不加载、规则实际失效。

== 抽象与接入成本

对外提供能力（公共库、框架、组件、SDK、可复用模块）时——**含项目自己为补现成方案的缺口而写的组件**（见 `specs/general/coding-ui.adoc`「界面与样式」的「从零写的唯一正当情形」）——**接入成本是设计指标**：功能可用不等于产品可用。判定标准：**同一个可替换点（实现类型、配置项、装配动作）在接入方出现的次数不随使用点数量增加**——若使用方要按使用点各写一遍（三个 service 各实现一遍同一接口、各传一遍同一实现类型），即为抽象漏做，按「代码复用」处理。

* **唯一装配点（L1）**：对外能力的可替换点须有**唯一的一处声明/装配落点**（应用入口装配），**不得要求多个使用点各自提供同一实现或同一配置**。判定特征：同一实现类型/配置项在接入方出现次数 > 1，或"新增一个使用点就要照着再传一遍"——出现即判重复（同一事实多个来源，改一处必漏其余）。
* **自建也须按通用件来写，不按本次用量的形态写（L1）**：**因现成方案缺口而自建的组件**（尤其界面基础件）**同样是通用件**——它的**对外形态**只由「这类东西本该长成什么样」决定，**不由本次页面的用量决定**：外观与行为的差异一律开成**受控的变体**（与既有组件同形的一档属性或变体取值），**不得**把本次页面的尺寸、间距、状态、文案写成该组件的固定值；**新增一个使用点不改组件本身**——要改才能用时，缺的是变体，补在**组件那一处**、其余使用点随之可用。**判定标准（任一命中即违规）**：① 自建组件里出现只为某一个使用点存在的固定外观/文案/状态，而其后第一个使用点就得复制或改它；② 同一自建组件的第二个使用点靠"复制一份再调样式"满足，而非取用变体；③ 以「这是专为这块页面写的」「先满足这一处」为由，把它写成只服务该处的私有件。
* **共用一旦看得出来，本轮就合并，不等用户提（L1）**：项目初期代码量不够时，**判不出哪些该抽成通用件是正常的**——判据不要求那时就猜到；但代码量上来后，**哪些本来是一件事会自己显形**（第二处开始复制、同一改法在两处出现、同形控件长出第三份）。**一旦看得出**（就本次改动所见，能指出两处以上同源实现），**须在本次改动内主动发起合并**：收敛到唯一一处（组件/公共方法/公共流程），把各使用点改成取用它、差异开成变体或参数，并在同一轮内同步更新全部引用（不留副本）、补上能发现"又长出第二份"的手段（见 `specs/general/coding-ui.adoc`「同一件事只有一个来源」的判据与自证）。**不得放任不管**、**不得**只在旁边记一笔或留 TODO、**不得等用户提醒才动**。**与存量边界的分工**：看得出就要合并，是**判据本身**；合并的**规模**受存量边界约束（随动迁移，见 `specs/core/execution.adoc`）——与本次改动同源的那两处顺便并掉，其余未触达的存量不发动全库改造。**判定标准（任一命中即违规）**：① 本次改动已看得出两处以上同源实现（或同一个改动要在多处各改一遍），却只使用新写法、把旧的那份留着，也未把合并记进同一轮的改动；② 以「初期猜不到该抽什么」「先这样，以后再说」为由推迟——初期猜不到不构成推迟的理由，**看得出之后仍不动**才违规；③ 等用户点名要合并才合并。
* **可替换点须有可用默认（L1）**：每个对外暴露的可替换点**须有可用的默认实现/默认值**；确实给不出默认时，须在文档显式声明"必须提供，否则启动失败"这类失败面——**要么有默认、要么有显式必填声明，二者必居其一**。**禁止既无默认又不声明**。
* **能自动装配就不要求接入方手写（L2）**：可通过约定/自动装配（如 SPI 自动装配的 `ServiceLoader`、自动配置注册文件、配置项默认值）默认生效的，不要求接入方逐点书写。
* **多实现用限定符、不逐层传参（L2）**：同一类型有多个实现时用限定符/命名 Bean 等**声明式区分**、由装配侧决定用哪个；**禁止逐层传参（参数穿透）**与让使用方自行创建或提供实现类型；跨层级共享的对象用**作用域/上下文对象**承载。
* **存量边界**：适用于**新写的对外能力**与**改到的既有抽象**（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（易用性与可维护性属产品质量特性）、ISO 9241-110（可控、符合预期）、ISO/IEC/IEEE 29148（需求单一、无歧义、可验证）、The Twelve-Factor App（Config 外置、Dependencies 显式声明）、Spring Boot 官方文档（Externalized Configuration / Auto-configuration）、SOLID 的依赖倒置原则（开闭：扩展走变体，不改使用点）。**「自建组件的对外形态由这类东西的通用形态决定、差异开成受控变体」「共用看得出就在本轮合并、不等用户提」是本集合的判据化取舍**——组件库文档只给变体与扩展点的**机制**，**未**规定自建件也须按通用件写，也**未**把"本次用量"与"通用形态"的优先级写明；Fowler《Refactoring》明文的前提是"**第一次出现重复时才收敛、不预先抽取**"，**未**规定重复已经看得见之后该由谁在什么时候动手，也**未**把"等用户提"列为可接受的状态。

== 代码复用

* **既有实现与先例优先（L1，动手前先查）**：写任何代码前先确认"项目里这件事**已经怎么做**"——① 查当前项目/模块是否已有等价能力（自有工具类、公共方法、既有封装）与同类场景的**先例**；② 查已引入的依赖/框架是否已提供等价能力；③ 有先例或有等价能力时**必须复用**，新代码写法须与先例保持一致。
* **不得以语言内置写法绕过既有能力（L1）**：当项目自有工具类、已引入的库/框架已覆盖某操作时，**禁止**改用语言/标准库的原生写法重写同一件事——典型反例：已有 `IdUtil.fastUUID()`/`CIdUtils.UUID()` 仍手写 `UUID.randomUUID().toString()`、已有 `CollUtil.isNotEmpty` 类工具仍手写 `x != null && !x.isEmpty()`。工具类选择优先级与各栈的现成 API 见 `specs/stack/` 对应文件（Java 见 `specs/stack/java-syntax.adoc`「工具类使用优先级」）。
* **先例一致优于个人写法偏好（L2）**：同一项目内同类操作必须走同一入口、写法一致，不得并存两种写法。
* **避免重复写相同代码**：相同逻辑抽离为公共方法，或移动到下游公共流程统一处理，不复制粘贴。
* **多处频繁初始化同一对象时抽公共创建方法（工厂/初始化方法）**；工具类如需实例化，用**静态工厂方法**而非构造方法，构造方法设为私有。
* **跨服务/对外调用的请求响应类优先移动复用，不新建（L1）**：给**已有接口**增加**新的内部调用接口**（如 Feign 等声明式 HTTP 客户端）时，**优先把该接口所需的请求/响应类移动**到新接口所属位置并沿用，**不得**另写一套同名同构的类——同一份数据契约出现两个类后即**分叉**（改一处必漏另一处，序列化字段与校验规则各自漂移）。**移动而非复制**：移动后同步更新全部引用，不得一处移动、一处留副本。**两种例外**：① **数据库实体类**——除用户明确声明允许外一律不移动；② **引用了第三方类型**的类。**边界：本项目自身的依赖不算三方依赖**——由本项目其他模块提供的类型仍属可一起移动，不得以"它依赖别的模块"为由另建一套。**落地口径**：请求/响应类放哪按项目自身规范或既有先例，没有先例才按新接口所属模块就近安置。**判定标准（任一命中即违规）**：① 新增接口旁出现新建的等价类，而项目内已有逐字段等价的同类可复用；② 新类与既有类同名或仅差包名、字段一一对应；③ 只复制既有类而不改原引用；④ 以"它依赖本项目其他模块"为由拒绝移动；⑤ 移动了数据库实体类而无用户声明。依据：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（需求单一、无歧义、可验证）。
* **存量边界（本条适用面）**：改到哪个接入点就归并该点（随动迁移，见 `specs/core/execution.adoc`）。
* **长方法的反复调用点：在本类（或本处已依赖的落点）加透传、不把调用点散到各处（L1，任何语言）**：被调方法**本身就很长**（多个参数、或多层嵌套取值）时，**同一处（同一个类/模块）多次调用它**一律在**本处**加一层**透传**（本类自己的方法，方法体只是一句委托、把参数原样交给被调方法），调用点改成调本处的透传；**不得**把这段很长的调用原样抄在每个调用点。透传的**数量**由本处调用点决定，不由被调方法的长度决定。
+
**多处都要加同一份透传时的三条去向（按序判，取最先成立的一条）**：① **改被调方法自身的形态**——参数过多用**参数对象**、多层嵌套用**提级取值**（先把值取成局部变量再传），让调用点**本来就短**；② **该操作已有等价入口**（被调方法所在类型自己就该提供这一操作、或项目里已有更短的同义入口）时**改用那个入口**（按「既有实现与先例优先」）；③ 以上都不成立——即**同一份透传在多个互不相干的类里各写一遍**，而**跨类透传又改不动被调方法**（它是外部代码、或已是被多处依赖的既有签名）——才在**公共落点**（该方法的所属类型、或项目约定的公共工具类）加**一处**透传（或**只加一次**的**公共创建/取值方法**），各处调用改用公共落点。**判定标准（任一命中即违规）**：① 同一句长调用在同一处出现**两处及以上**而未加透传；② 透传只包住**这一次**调用，而**其余同类调用点**仍照抄长调用；③ **一边加透传、一边保留**原样的长调用（同一处两种写法并存）；④ 以「以后可能要用」「这样更短」「有参构造就一行」为由自我豁免；⑤ 把**短**调用也加上只做转发的透传——**本条只针对本身就长的调用**。
+
**例外与边界（L2）**：① **调用点本来就短**（单层调用、参数就是少数几个简单值）不加透传，加了反而是多处一跳；② 被调方法**属外部公共 API、且其签名已构成对外契约**时，去向上条②或③（不擅自改它的签名）；③ **语言或框架没有"显式透传方法"这一层**时，按其**等价形态**落（语言自带的转发机制、别名、函数引用），**不为凑形态而包一层空壳**；④ **本条管的是"调用点怎么写"，不是"把长方法拆开"**——被调方法自身的过长、参数过多按既有判据另行处理（「代码质量」节的**职责单一、结构清晰**、**新代码不得引入坏味道**、**过长参数列表**、「抽象与接入成本」），本条不替代它们。
+
**存量边界（L1）**：本条**只管新增与本次改到的调用点**——**不预先把同类透传给全项目补齐**，改到哪处才顺带收敛该处（随动迁移，见 `specs/core/execution.adoc`）。

* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Martin Fowler《Refactoring》（Long Parameter List 与 Inline Class 一类手法的取向是"把取值与组装收敛到一处"，其明确前提是**第一次出现重复时才收敛、不预先抽取**）。**「同一处的长调用须在本处加透传、跨类重复才上公共落点，且加透传不替代缩短参数本身」是本集合的判据化取舍**——通行材料只要求"参数多时收成参数对象、重复代码抽成公共方法"，**未**规定"透传落点按调用点数量分档、且加透传不替代缩短参数"这一层。

* **缓存前先判断对象生命周期（避免内存泄露）**：为提升性能而缓存对象或中间对象时，先搞清它是一次性使用还是多次复用——**只缓存会被多次使用的对象**；**禁止缓存一次性对象**（用完即弃的对象被缓存后不会释放，长期运行导致内存泄露）。

== 源码文件的规模（单个文件不得长成"什么都往里写"）

**任何语言**都适用：源文件是**取用与检索的单位**——一个文件就是别人"要读就得整份读、要用就得整份引"的一份东西。文件一大，最先坏掉的不是可读性，而是**可复用性**：能复用的部分被埋在一处私有实现里，别处要用只能再写一份。

**识别判据**：由人编写、按源码形态维护与检索的文件即本条所指的源码文件，**不限语言**（界面样式、SQL、模板、配置同样在内）；**边界**：生成的产物与随分发的第三方副本不属本条。

* **一个文件只做一件事（L1）**：单个文件**只承载一件能被一句话说清的事**（一类职责、一个主题、一组同源能力）——同一文件里出现**两组以上互不相干的职责**即为"写到一起"。**判定标准（任一命中即违规）**：① 文件里出现本可独立成篇的第二件事（第二套职责、第二组无调用关系的类与函数、只服务某一处的一段实现）；② 一件事要靠"文件内的分段注释/分节标题"才读得清（那是**几个文件被装进了一个文件**）；③ 以「反正只有一个使用点」为由把通用实现写在调用点的文件里。
* **公共部分放别人取得到的位置（L1）**：本次或将来**会第二次用到**的能力，其来源须落在**可被取用的文件**里（公共模块、工具文件、组件文件），使用点只组装与取用——**不得**先就近写死，等第二个使用点出现再挪一遍。判定标准：① 明知会有第二个使用点，仍把它写成某个业务文件里的私有函数；② 第二个使用点只能靠复制解决（同一件事长出第二份来源，按 `specs/general/coding-ui.adoc`「同一件事只有一个来源」判）。
* **单文件体量的提醒线（L2，超线即须给出判据化定论）**：单个源码文件超过**约 500 行**或**约 30 KB**（两者以先到者为准；各语言栈可另设更严取值）即视为**需要评估拆分**——**只提醒、不报错、不阻断**，但**超线必须给出定论，不得沉默放过**：按下面的"拆不拆怎么判"逐条核，**或拆、或写明为什么不拆**。**常驻/入口类文件（应用入口、依赖清单、路由表、构建脚本）体量由"只做装配"约束，不按本条另设阈值**——它们的膨胀按"入口只做装配、具体实现下沉"处置。
* **拆不拆怎么判（L1，按职责判定，不按行数判定）**：行数只是**提醒信号**，拆分动作由**职责边界**决定。**须拆（任一命中即拆）**：① 文件里存在**两组以上互不相干的职责**；② 文件里存在**一处可被别的文件取用的公共部分**而当前只能在文件内使用；③ 文件里**已有多种"取用粒度"混在一起**（少数几个入口 + 大量内部实现细节），读者要读全才能用其一。**不拆的正当形态（须写明理由）**：① 拆开后各部分**判据形态相同、加载时机相同、无人会单独取用**（拆只会多出跳转，不减少读取）；② 内容是**同一份数据的完整定义**（一份契约、一份清单、一张映射表），切断即不完整；③ 拆出去会成为**无人维护、判据空转的空壳**。**不得**以「看起来更整齐」「行数还不到线」为理由拆或留。
* **拆要按职责切、不按体量切（L1）**：拆分须**沿职责与取用边界切**，切出的每份都**自足**（有自己的名字、说明与可被取用的入口）；**不得**按"前 300 行一份、后 300 行一份"这类体量切法拆分，也不得以拆分为由删内容、把实现改成副本。
* **拆完的收口（L1）**：拆分后原位置**只留取用与装配**、不留在文件内又改一遍的副本；全部引用同步更新（按 `specs/general/coding-ui.adoc`「同一件事只有一个来源」的"一次收敛，不逐处漂移"办），并补上能发现"又长回来的"手段（下一处该抽的公共部分出现时能被发现、超线能被机械核对）。
* **判定标准（任一命中即违规）**：① 单个文件承载两组以上互不相干的职责；② 文件里已有可被别处取用的公共部分，却只能在文件内用；③ 超过提醒线而未给出定论（既没拆、也没写不拆的理由）；④ 以「现在还能读」为由把新增内容继续往同一个大文件里追加，而新增部分与文件既有职责不同源；⑤ 拆分按体量切、切出的部分不自足，或拆分时删了内容、留了副本。
* **存量边界（L1）**：本条**只管新增文件与本次改到的文件**——**新写的代码让它一开始就落对位置**；已超线但本次不触达的存量不发动全库拆分（随动迁移，见 `specs/core/execution.adoc`）。**反向要求**：**不得**因为"文件太大了"就在一次无关改动里顺手大改既有文件结构（同「不得借重构之机顺手改动与目标无关的代码」）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性：模块化与可复用性、可分析性）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Robert C. Martin《Clean Code》（单一职责与"源文件应当小到易于理解"的取向）、Martin Fowler《Refactoring》（按职责抽取、重复出现才收敛）。**「500 行 / 30 KB 只作提醒线、拆分动作由职责边界判定」「超过提醒线须给出判据化定论、不得沉默」是本集合的判据化取舍**——通行风格指南与静态检查工具给的是行数阈值（常按 500 行一类经验值），**未**规定"超线之后必须给出定论"，也**未**把"可被别处取用的公共部分留在文件内"单列为违规形态。

== 代码质量（新产出即高质）

功能写出来了不等于做完了——**同一件事，功能一致、质量可以差一个量级**。本节约束**新写的与本次改到的代码**（存量随动迁移），给出可逐条核对的**质量下限**：达不到即视为**未完成**。

* **适用面（先读）**：**写任何新代码、改任何既有代码**时适用；**代码评审**时按本节逐条核对。存量不在强制面内（改到哪迁到哪），但**新增的那一部分永远按本节判**。
* **新代码不得引入坏味道（L1）**：不得把已知坏味道写进新代码——重复代码、过长函数（一屏读不完）、过长参数列表、发散式变化（改一个需求要同时改多处）、霰弹式修改（一处改动散落几十个文件）、依恋情结（频繁访问他类内部数据）、数据泥团（总是一起出现的字段反复成组传递）、基本类型偏执（用裸字符串/裸数字承载领域概念）、被拒绝的遗赠（继承但用不上父类大部分能力）、注释代替澄清。**判定标准（任一命中即违规）**：① 同一段逻辑在本次改动里出现两次及以上而未抽离；② 一个函数需要靠注释分段才能读懂；③ 新增分支靠继续加 `if/else` 而不是抽出策略/多态；④ 新增字段只是为了让某处 `if` 多一个条件。依据：Martin Fowler《Refactoring》、Robert C. Martin《Clean Code》。
* **职责单一、结构清晰（L1）**：一个函数/方法/类只做一件事（"能不能用一句话说清它做什么"是判据）；函数体优先**线性可读**；嵌套层级控制在**三层以内**（`if`/循环/`try` 叠加计层），超过即先抽方法或提前返回；**不得**写超长 god method。**判定标准**：一句话说不清职责 / 嵌套数超过三层 / 需要通过 goto 式跳转才能读完——任一命中即违规。
* **命名表意、不用缩写（L1）**：命名须**表意**、**全文一致**（同一概念在项目中只有一个叫法）；**禁止**无共同认知的缩写、单字母（循环下标等惯用短名除外）、拼音、数字后缀（`data1`/`newService2`）、以及"能看出类型看不出用途"的名字（`map`、`list`、`temp`）。**判定标准**：出现需靠读实现才知道含义的名字 / 同一概念两种叫法 / 用缩写牺牲可读性——任一命中即违规。
* **可读性优先（L1）**：优先**直白**写法，不为"短"牺牲可读——不写多重嵌套三元、不在实参位置内联复杂表达式与对象构造、不用无意义的魔法值；**同一表达式不重复求值、同一判断不重复书写**。判据与既有条款见 `specs/general/coding-shape.adoc`「表达式与调用写法」。
* **显式处理失败与边界（L1）**：**不得吞异常**（`catch` 后空实现、只打日志不处理、`except: pass`）；异常须处理或按契约向上抛；**边界条件必须显式处理**（空集合、`null`/`nil`、0 与负数、超长与超大、并发与重入），不以"调用方会传对"为前提；对外输入一律校验（见 `specs/general/security.adoc`「输入与输出」）。**条件例外（L2，把"查不到 → 取默认值"这类纯取值转换写成空 `catch`）**：只在该 API 的**异常只有一种原因**（**查找内容不存在**，不含任何失败）且调用方**以该查找的默认值为业务语义**时成立。**三条同时成立才算命中、缺一即回到 L1**：① **异常语义单一**——该 API 的异常只可能表示"查找内容不存在"，参数非法、状态非法、IO/资源/权限失败等一切真失败**另有出口**（返回"没有"值、单独异常，或调用前显式校验）；② **取不到即无值**——返回值就是"没有"的表示，无需另补兜底动作；③ **默认值取自同一 API 的返回值**——使顶层调用处"仍须处理失败"这一契约不受影响；**且该处须写明"异常只有这一种原因"的依据**。**判定标准（任一命中即不合规）**：① 该 API 的异常**不止"查找内容不存在"一种原因**（含查找过程中的执行失败），却按本例外空 `catch`；② 调用方**要求失败可见**（超时、不可用须报错或重试、状态变更须乐观锁失败即报错），却仍按"查不到"取默认值；③ 借本例外绕过**可探测的非法输入**（未预先校验就空 `catch`，见 `specs/general/security.adoc`「输入与输出」）；④ 空 `catch` 处**没有写明"异常只有这一种原因"的依据**；⑤ 把本例外扩大到**任何异常的 `catch`**。

**边界（防反用）**：本条**不改变**"不得吞异常"与"对外输入一律校验"的其余部分——命中的调用点**仍是空 `catch`**；该写法是**对例外的显式标注**，不属「注释代替澄清」。各语言的具体落点由技术栈层给出（Java 见 `specs/stack/java.adoc`「健壮性」）。
* **无资源泄漏（L1）**：文件、连接、流、锁、线程池、订阅与监听须成对释放，一律用语言提供的确定性释放机制（`try-with-resources`、`using`、`with`、`defer`、`finally`），禁止依赖 GC 或人工记忆释放。
* **无并发隐患（L1）**：共享可变状态须有明确的同步策略（锁范围与顺序写清，或改用并发安全结构/不可变对象/消息传递）；不得出现可见性缺失、锁顺序不一致（可致死锁）、双重检查未加锁、共享可变对象直接暴露。**判定标准**：共享可变状态无同步策略、或同步策略在代码里看不出边界——命中即违规。
* **性能不写退化写法（L2）**：避开可预见的性能退化——循环内 IO/查询/远程调用、循环内字符串拼接、可预知的 N+1 查询、在热点路径重复创建昂贵对象或重复读取不变资源。**何时需要实测数据**按 `specs/general/testing.adoc`「性能测试」判定。
* **测试与文档跟得上（L1）**：新功能**必须**配测试；本次改动相关面的既有用例不得为迁就改动而改判；结构说明、契约与边界写进该语言的**文档注释**。**判定标准**：新功能无对应用例 / 有行为改动而未同步文档——任一命中即违规。
* **交付前质量自检（L1）**：交付前对新代码逐条自查本节十项（坏味道 / 职责与嵌套 / 命名 / 可读性 / 失败与边界 / 资源 / 并发 / 性能 / 测试与文档），答不上"逐项怎么过的"即视为未过；**能过机械判据是下限、不等于质量过关**。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性、可靠性、性能效率）、ISO/IEC/IEEE 12207（实现过程）、Martin Fowler《Refactoring》、Robert C. Martin《Clean Code》、SEI CERT Coding Standards、ISO/IEC/IEEE 29148。「十项逐条判」是本集合的判据化取舍。

== 日志

* **禁止控制台打印**：不允许直接输出到控制台（`System.out.println`、`console.log` 等）；需要输出日志时统一使用日志框架。控制台打印仅限明确需要控制台展示的独立场景（如性能测试，且应同时写入文件报告）。
* **日志分级记录**（便于调试排查）：各环节**关键节点**（方法入口/出口、流程步骤、分支去向、中间结果）应打日志记录运行轨迹。**辅助排查的细节**（关键输入/输出、中间状态、分支取舍）用 **debug**——默认不打印；**需注意的事项**（异常、边界兜底、非预期但可处理的场景、重要状态变更）用 **info 及以上**。**不得因"代码重要就省略日志"导致难排查，也不得为省事全打 info 刷屏**。
* **不打无意义日志**：日志打在**关键节点**即可——空方法/空实现不打；有开关启用的逻辑、开关不启用时一般不打；为打而打不如不打。
* **日志属性打印格式**：属性（key/value）**不包双引号**，格式 `key: value`；常规用**半角冒号 + 空格**（`userId: 123`），key 或 value 为**纯中文**时用**全角冒号且不加空格**（`用户ID：登录成功`）。异常日志须把 throwable 作为最后一个参数传入（`log.error("msg: {}", arg, e)`），不得拼 `e.getMessage()`。
