= 通用编码规范（通用层，跨语言）

适用于**所有编程语言**的编码活动。某语言/技术栈专属规则见 `specs/stack/` 对应文件。

== 抽象与接入成本

对外提供能力（公共库、框架、组件、SDK、可复用模块）时，**接入成本是设计指标**：功能可用不等于产品可用。判定标准：**同一个可替换点（实现类型、配置项、装配动作）在接入方出现的次数不随使用点数量增加**——若使用方要按使用点各写一遍（三个 service 各实现一遍同一接口、各传一遍同一实现类型），即为抽象漏做，按「代码复用」处理。

* **唯一装配点（L1）**：对外能力的可替换点须有**唯一的一处声明/装配落点**（应用入口装配），**不得要求多个使用点各自提供同一实现或同一配置**。判定特征：同一实现类型/配置项在接入方出现次数 > 1，或"新增一个使用点就要照着再传一遍"——出现即判重复（同一事实多个来源，改一处必漏其余）。
* **可替换点须有可用默认（L1）**：每个对外暴露的可替换点**须有可用的默认实现/默认值**；确实给不出默认时，须在文档显式声明"必须提供，否则启动失败"这类失败面——**要么有默认、要么有显式必填声明，二者必居其一**。**禁止既无默认又不声明**。
* **能自动装配就不要求接入方手写（L2）**：可通过约定/自动装配（如 SPI 自动装配的 `ServiceLoader`、自动配置注册文件、配置项默认值）默认生效的，不要求接入方逐点书写。
* **多实现用限定符、不逐层传参（L2）**：同一类型有多个实现时用限定符/命名 Bean 等**声明式区分**、由装配侧决定用哪个；**禁止逐层传参（参数穿透）**与让使用方自行创建或提供实现类型；跨层级共享的对象用**作用域/上下文对象**承载。
* **存量边界**：适用于**新写的对外能力**与**改到的既有抽象**（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（易用性与可维护性属产品质量特性）、ISO 9241-110（可控、符合预期）、ISO/IEC/IEEE 29148（需求单一、无歧义、可验证）、The Twelve-Factor App（Config 外置、Dependencies 显式声明）、Spring Boot 官方文档（Externalized Configuration / Auto-configuration）、SOLID 的依赖倒置原则。

== 代码复用

* **既有实现与先例优先（L1，动手前先查）**：写任何代码前先确认"项目里这件事**已经怎么做**"——① 查当前项目/模块是否已有等价能力（自有工具类、公共方法、既有封装）与同类场景的**先例**；② 查已引入的依赖/框架是否已提供等价能力；③ 有先例或有等价能力时**必须复用**，新代码写法须与先例保持一致。
* **不得以语言内置写法绕过既有能力（L1）**：当项目自有工具类、已引入的库/框架已覆盖某操作时，**禁止**改用语言/标准库的原生写法重写同一件事——典型反例：已有 `IdUtil.fastUUID()`/`CIdUtils.UUID()` 仍手写 `UUID.randomUUID().toString()`、已有 `CollUtil.isNotEmpty` 类工具仍手写 `x != null && !x.isEmpty()`。工具类选择优先级与各栈的现成 API 见 `specs/stack/` 对应文件（Java 见 `specs/stack/java-syntax.adoc`「工具类使用优先级」）。
* **先例一致优于个人写法偏好（L2）**：同一项目内同类操作必须走同一入口、写法一致，不得并存两种写法。
* **避免重复写相同代码**：相同逻辑抽离为公共方法，或移动到下游公共流程统一处理，不复制粘贴。
* **多处频繁初始化同一对象时抽公共创建方法（工厂/初始化方法）**；工具类如需实例化，用**静态工厂方法**而非构造方法，构造方法设为私有。
* **跨服务/对外调用的请求响应类优先移动复用，不新建（L1）**：给**已有接口**增加**新的内部调用接口**（如 Feign 等声明式 HTTP 客户端）时，**优先把该接口所需的请求/响应类移动**到新接口所属位置并沿用，**不得**另写一套同名同构的类——同一份数据契约出现两个类后即**分叉**（改一处必漏另一处，序列化字段与校验规则各自漂移）。**移动而非复制**：移动后同步更新全部引用，不得一处移动、一处留副本。**两种例外**：① **数据库实体类**——除用户明确声明允许外一律不移动；② **引用了第三方类型**的类。**边界：本项目自身的依赖不算三方依赖**——由本项目其他模块提供的类型仍属可一起移动，不得以"它依赖别的模块"为由另建一套。**落地口径**：请求/响应类放哪按项目自身规范或既有先例，没有先例才按新接口所属模块就近安置。**判定标准（任一命中即违规）**：① 新增接口旁出现新建的等价类，而项目内已有逐字段等价的同类可复用；② 新类与既有类同名或仅差包名、字段一一对应；③ 只复制既有类而不改原引用；④ 以"它依赖本项目其他模块"为由拒绝移动；⑤ 移动了数据库实体类而无用户声明。依据：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（需求单一、无歧义、可验证）。
* **存量边界（本条适用面）**：改到哪个接入点就归并该点（随动迁移，见 `specs/core/execution.adoc`）。
* **长方法的反复调用点：在本类（或本处已依赖的落点）加透传、不把调用点散到各处（L1，任何语言）**：被调方法**本身就很长**（多个参数、或多层嵌套取值）时，**同一处（同一个类/模块）多次调用它**一律在**本处**加一层**透传**（本类自己的方法，方法体只是一句委托、把参数原样交给被调方法），调用点改成调本处的透传；**不得**把这段很长的调用原样抄在每个调用点。透传的**数量**由本处调用点决定，不由被调方法的长度决定。
+
**多处都要加同一份透传时的三条去向（按序判，取最先成立的一条）**：① **改被调方法自身的形态**——参数过多用**参数对象**、多层嵌套用**提级取值**（先把值取成局部变量再传），让调用点**本来就短**；② **该操作已有等价入口**（被调方法所在类型自己就该提供这一操作、或项目里已有更短的同义入口）时**改用那个入口**（按「既有实现与先例优先」）；③ 以上都不成立——即**同一份透传在多个互不相干的类里各写一遍**，而**跨类透传又改不动被调方法**（它是外部代码、或已是被多处依赖的既有签名）——才在**公共落点**（该方法的所属类型、或项目约定的公共工具类）加**一处**透传（或**只加一次**的**公共创建/取值方法**），各处调用改用公共落点。**判定标准（任一命中即违规）**：① 同一句长调用在同一处出现**两处及以上**而未加透传；② 透传只包住**这一次**调用，而**其余同类调用点**仍照抄长调用；③ **一边加透传、一边保留**原样的长调用（同一处两种写法并存）；④ 以「以后可能要用」「这样更短」「有参构造就一行」为由自我豁免；⑤ 把**短**调用也加上只做转发的透传——**本条只针对本身就长的调用**。
+
**例外与边界（L2）**：① **调用点本来就短**（单层调用、参数就是少数几个简单值）不加透传，加了反而是多处一跳；② 被调方法**属外部公共 API、且其签名已构成对外契约**时，去向上条②或③（不擅自改它的签名）；③ **语言或框架没有"显式透传方法"这一层**时，按其**等价形态**落（语言自带的转发机制、别名、函数引用），**不为凑形态而包一层空壳**；④ **本条管的是"调用点怎么写"，不是"把长方法拆开"**——被调方法自身的过长、参数过多按既有判据另行处理（「代码质量」节的**职责单一、结构清晰**、**新代码不得引入坏味道**、**过长参数列表**、「抽象与接入成本」），本条不替代它们。
+
**存量边界（L1）**：本条**只管新增与本次改到的调用点**——**不预先把同类透传给全项目补齐**，改到哪处才顺带收敛该处（随动迁移，见 `specs/core/execution.adoc`）。

* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Martin Fowler《Refactoring》（Long Parameter List 与 Inline Class 一类手法的取向是"把取值与组装收敛到一处"，其明确前提是**第一次出现重复时才收敛、不预先抽取**）。**「同一处的长调用须在本处加透传、跨类重复才上公共落点，且加透传不替代缩短参数本身」是本集合的判据化取舍**——通行材料只要求"参数多时收成参数对象、重复代码抽成公共方法"，**未**规定"透传落点按调用点数量分档、且加透传不替代缩短参数"这一层。

* **缓存前先判断对象生命周期（避免内存泄露）**：为提升性能而缓存对象或中间对象时，先搞清它是一次性使用还是多次复用——**只缓存会被多次使用的对象**；**禁止缓存一次性对象**（用完即弃的对象被缓存后不会释放，长期运行导致内存泄露）。

== 对象初始化（手动创建对象时的写法）

**任何语言**都适用：**手动**创建/初始化一个对象时（`new`、构造调用、字面量构造、工厂调用等由本次代码直接写出的创建动作）**一律走链式初始化**——链式初始化指**一次把所属关系串起来的写法**，覆盖**链式 setter**（一类返回对象自身的 setter，`new X().setA(1).setB(2)`）与 **builder**（`X.builder().a(1).b(2).build()`），**具名参数**在语言支持时同属这一档。判据只看**形态**、不看语言。

* **对象初始化：链式初始化优先、无链式才用 `set`、严禁有参构造初始化（L1）**：**手动创建对象一律用链式初始化**（链式初始化 > 逐条 `set`；同一项目内不得一处链式、一处逐条 `set`）；**没有链式形态**（builder 与链式 setter 都不可得）才退回**逐条 `set`**，且仍按「链式赋值顺序随字段顺序」排赋值次序；**严禁**以"参数带着字段一起传"的**有参构造方法**（含全参构造、位置参数构造、`new X(a, b, c)` 形态）**手动创建对象**，**唯一例外**是**对象内的构造方法调用构造方法**（构造链式转发、`this(...)`/`super(...)` 一类同类或父类构造之间的调用）。

**Java 内部再分档：builder 优先于链式 setter（L1）**：Java 侧**优先用 builder 链**（lombok 的 `@SuperBuilder`，`X.builder().a(1).b(2).build()`），**没有 builder 时才退回链式 setter**。**分档理由**：builder 把"正在拼装"的对象与"可用的对象"分开（`build()` 之前拿不到半成品），链式 setter 返回的**就是那个半成品对象本身**、任何一句之后都能被继续引用，即中间态问题在链式 setter 这一档**只减不消**；载体与分档的 Java 侧落点见 `specs/stack/java.adoc`「编码」。

**理由**：① 逐条 `set` 把同一个对象的创建**打散成多行多条语句**，中间态（只设了部分字段）随时可被下一条语句读到，读的人要跨行拼出"这个对象最终长什么样"；② 链式写法把**创建与赋值收在一处**，字段清单只有一个落点（与「链式赋值顺序随字段顺序」同源），构造完即完整对象；③ 有参构造把**参数位置的语义**交给调用点——同一个 `new X(true, false)` 在两个月后没有人能读出这两个布尔各是什么，且**字段增删或重排时调用点无一报错**（同名同类型的参数照样编译通过），属**静默失效**；④ 具名环节（builder 的 `.a(...)`、链式 setter 的 `.setA(...)`）把"哪个值给哪个字段"写在**名字**上，是同一失效面唯一的消除手段。

**例外清单与理由（L2，须逐条写明理由，不得以"这个类用惯了"为由扩大）**：

** **对象内构造方法调用构造方法**：属**类内部**的构造转发，调用点就在类里、参数语义由本类自己的签名保证，不存在"外部调用点凭位置猜字段"的失效面。**误用形态**：把它读成"凡在类里写构造都合规"——在类内**手动创建另一个业务对象**（不是同类/父类构造之间的转发）仍按本条的禁止面处理。
** **框架按声明创建对象**（注入、反序列化、映射/ORM/反射）：创建**不是**本次代码写出来的调用点，其"参数"来自框架声明的契约（构造注入的依赖、全参构造、反序列化的无参构造），不属本条所指的**手动初始化**；这类构造的书写仍按各自规则（Java 侧见「无参 / 必参 / 全参构造优先用 lombok、不手写」）。
** **语言或框架根本没有链式形态**（builder 与链式 setter 都不可得）：退回逐条 `set`。
** **目标对象是第三方类型、不可改**（无 builder、setter 也不返回自身）：只能逐条 `set`；**不得**为凑出链式而包一层自有壳类（那是另一处抽象）。
** **语言惯用的具名构造即该语言的链式形态**（该语言以具名参数/字典字面量表达"哪个值给哪个字段"）：按具名参数形态写，视为满足本条。

**判定标准（任一命中即违规）**：① 本次手动创建的对象里，出现**两处及以上**逐条 `set`（而该类型的语言/技术栈有链式形态可用）；② Java 侧该类型**已有 builder**（标了 `@SuperBuilder`/`@Builder`）却改用链式 setter 或逐条 `set`；③ 手动创建对象时出现**有参构造调用**（`new X(a, b, …)`），而该创建不属上述例外清单；④ 以「这个对象字段少」「这样更直观」「有参构造就一行」为由自我豁免。

**边界（防反用）**：本条**只管"手动创建这个对象时怎么写"**——不管**对象内部**（构造器、静态工厂、builder 自定义方法里的组装）、不管**框架驱动的创建**（注入/反序列化/映射/ORM/反射），也不要求为满足本条去给第三方类型补 builder；**已经写好的链式 setter 与 builder 该怎么排序**不归本条管（那是「链式赋值顺序随字段顺序」）。

**存量边界（L1）**：本条**只管新增与改到的创建点**，**不发动全库改写**既有创建语句（不改既有 `new X(...)`、不批量补 builder）（随动迁移，见 `specs/core/execution.adoc`）。

依据（标准名/编号）：ISO/IEC 25010（可维护性、可分析性——赋值语义须在调用点可见）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Effective Java「考虑使用构建器」（条目 2：**位置参数一多，调用点就读不出哪个值是什么**、字段增删时调用点静默错位；"builder 把对象拼装与可用分开"），以及《重构》（Long Parameter List 属典型坏味道，取向是引入参数对象或具名环节）。**「优先链式初始化（Java 内 builder > 链式 setter）、没有链式才用 `set`、严禁有参构造初始化」是本集合的判据化取舍**——通行材料给的方向是"参数多时用 builder"，**未**规定"手动创建对象一律不得用有参构造、且链式内部再按 builder > 链式 setter 分档"。**与「无参 / 必参 / 全参构造优先用 lombok、不手写」同源**：那条管"Java 类上怎么写构造"、本条管"创建对象时用哪种写法"，两条并存（`@AllArgsConstructor` 供框架用、业务创建走 builder）。

== 数据契约的载体（数据库实体类不进对外契约）

**任何语言**都适用：以数据库表/集合结构为载体的数据对象（下称**数据库实体类**——各语言栈里由对象-关系映射框架或映射注解定义的模型类/结构体）**不得**充当**对外数据契约的载体**——即外部可观测的请求参数、响应返回值。

**识别判据（先判对象，再判规则）**：类/结构体**以表结构为来源**（与表/集合逐字段对应、由映射注解或迁移脚本定义）即属本条所指的数据库实体类。**不看类名**——叫 `UserDTO` 但逐字段对应表结构、被当实体用的同样在禁止面内；反之叫 `UserEntity` 却与表无关的按普通数据结构类判。

* **不得作为对外契约的请求参数与响应值（L1）**：对外暴露的接口（HTTP 控制器方法、声明式 HTTP 客户端接口、RPC 服务契约、消息 DTO 等）**不得**以数据库实体类作为入参或返回类型，也**不得**在入参/返回值里**嵌套**它（集合元素、对象字段、分页包装体内均不得出现）。**理由**：① 对外契约与库表结构本是两份数据，用实体类承载即**同一份数据出现两个来源**（接的字段由表结构定，改一处必漏另一处）；② 外部因此能观测到**不应外露的内部字段**（审计列、软删除标记、内部关联）；③ 字段增删随迁移脚本漂移、**静默破坏既有调用方**。
* **载体取该接口自己的请求/响应类（L1）**：对外接口须使用**为该接口定义的请求类/响应类**（沿用项目既有命名的 DTO/VO/Request/Response 一类，**命名按项目先例、本条不另定命名法**）。**层间转换**按其技术栈的转换规则执行（本集合优先声明式映射，见「对象转换」节）；**转换后不复用实体类本身**。
* **已被调用方依赖的既有接口（L2，须走变更流程）**：理论上该改但会被**显式契约变更**（可能破坏既有调用方）的情形**不是自动的例外**：须先按「跨服务/对外调用的请求响应类优先移动复用」的判定与「破坏性操作」流程处置（对既有调用方构成破坏性变更的，先向用户确认），并在同一轮内补上"该轮改动触达的那部分"的响应类与测试——**是否保留旧形态由用户决定**。
* **判定标准（任一命中即违规）**：① 对外接口的入参类型或返回类型是数据库实体类；② 入参/返回值的字段或集合元素里嵌套数据库实体类；③ 为"省一次转换"而让实体类实现/继承接口契约类型（同一形态的另一种写法）；④ 以"类名不叫 Entity""只多一个字段""内部调用不算对外"为由自我豁免。
* **例外与边界（L2）**：① **纯内部调用**（不经任何跨进程/跨网络边界的同进程函数调用）不在本条范围内；② **持久化自身的出口**（仓库/DAO/Mapper 的返回）不受本条约束——本条只管**对外契约**；③ 项目自身规范**可加严或收窄**本条（如明确"内部 RPC 也适用"），冲突时以项目自身规范为准。
* **存量边界（L1，用户点名"已经用了不管"）**：改到哪个接口才顺带调整；**不得**据此发动全库改造（批量换参数类型、批量补 DTO）（随动迁移，见 `specs/core/execution.adoc`）。
* **例外之例外（口头声明即生效）**：**除非用户主动声明**允许某处（或某接口）以数据库实体类作为请求/响应参数，否则一律适用本条。声明**仅对该次任务、该处生效、不得泛化**（与「改动范围边界」的例外同口径）。
* **不得以键值容器承载方法参数（L1）**：方法参数与返回值的载体是**具名类型**（该操作自己的请求/参数/传输对象）——以**键值容器**（`Map`、字典、哈希一类只有键名、没有成员声明的类型）承载数据时，**字段名、字段类型与必填性都没有落点**：调用方按字面键写入、实现按字面键读取，键名改一处即**静默失效**，两端的键集合也**无法在编译期核对**。**判定标准（任一命中即违规）**：① 本项目对同类参数**已有具名类型或具名先例**，本次仍以键值容器承载；② 该组参数在本次改动里**已有一个等价的具名类型**（同一份数据出现第二个载体）；③ 返回值以键值容器承载本该具名的数据结构；④ 以「这个参数会变」「字段太多」「只是个内部方法」为由自我豁免。

**例外与边界（L2）**：① **键值集合本身就是要表达的数据**（配置项映射、字典表、按动态键查值）不受本条约束；② **框架/第三方契约要求键值容器**的场合（反射入口、动态属性、序列化容器）按其要求走；③ 调用方主动声明允许的**仅对该处、该次生效、不得泛化**（同本节上条口径）。

**存量边界**：改到哪处才顺带调整（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性、安全性的信息暴露面）、ISO/IEC/IEEE 29148（契约须单一、无歧义、可验证）、OWASP API Security Top 10（**API3:2023 Broken Object Property Level Authorization**——"批量赋值/过度暴露"即把内部数据面直接当契约面）。**"对外契约不得以库表结构为载体"是本集合的判据化取舍**；层间转换的优先路径另见本文件「对象转换（多层嵌套对象的转换）」。「参数不得以键值容器承载」一条的坏味道依据为 Martin Fowler《Refactoring》的「数据泥团」（总是成组出现的字段反复成组传递，取向是引入参数对象）；**「参数不得以键值容器承载」是本集合自己的判据化取舍**。

== 持久化访问（数据库/缓存等）

访问数据库、缓存等持久化存储时，**一律走所属技术已提供的类型安全/声明式查询构造 API 与其统一入口（网关）**，不得各自手写原始语句或自建构造器。**具体技术的入口与禁止清单见** `specs/stack/` 对应文件（如 `specs/stack/java.adoc`「持久化访问」）。

* **统一入口（L1）**：持久化操作须经**该技术约定的统一访问入口**调用（数据访问接口、仓储、服务基类、模板/客户端等），业务代码不得自建"临时构造器"绕过该入口。识别特征：调用点出现**技术自带构造器/包装器类的直接 `new`**（或把这类对象当局部变量来回传递）。
* **优先用类型安全/声明式查询构造 API（L1）**：入口提供**类型安全（编译期可校验）**的查询构造 API 时，**优先且一律使用**它——如以**方法引用/属性名引用**表达列名、以**声明式方法名**表达查询（`findByXxx`）、以类型化 Criteria 表达条件。**禁止**用**字符串书写列名/表名**去表达本可由类型安全 API 表达的条件（字符串写列名编译期查不出、改名即静默失效）。
* **替代优先（L1）**：技术自带"替代写法"（同一 API 的类型安全/声明式形态）时**强制使用替代写法**；只在该替代形态**表达不了所需语义**时才退回通用构造器，且须在代码注释写明"为何替代形态表达不了"。
* **判定标准（任一命中即违规）**：① 出现技术自带构造器/包装器的直接 `new`，且该条件可由类型安全/声明式 API 表达；② 列名/字段名以**字符串**写在查询构造中（非注解声明、非框架支持的映射文件）；③ 绕过技术给定的统一入口自建查询构造。
* **例外与边界（L2）**：本条**不**禁止同一技术的正当通用形态——**跨语言语句的承载**（如以映射文件承载 SQL，见下「跨语言执行脚本的落点」）不在禁止面内；类型安全 API 表达不了的语义（框架未封装的自定义语句片段、条件化 JOIN、数据库特有函数与提示）允许退回通用构造器或映射文件，但**调用入口不变**。
* **存量边界**：见上条（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）、OWASP Query Parameterization Cheat Sheet（本条在其上**加严**为"构造须走类型安全 API"，属本集合取舍）。
* **访问前先判空、不发起无效查询（L1，跨语言）**：调用持久化接口前，**凡参数取值使该次访问必然查不到任何数据**（主键/唯一键为 `null` 或空、集合/数组为空、必填查询条件缺失）时，须**就地返回**（单条查不到返回"没有"值、批量返回空集合），**不得把这类参数交给数据库**。**理由**：访问本身是外部 IO——判空是本地零成本动作，不判则每次白付一次连接、网络往返与查询解析，可观测为慢查询与被放大的 QPS；这在批量循环里是乘法而非加法（ISO/IEC 25010 性能效率）。
* **返回集合的接口一律返回空集合、不返回 `null`（L1，跨语言）**：查集合类接口在无结果、参数被短路时返回**空集合**；调用方因此无需逐点判 `null`，也避免隐式 NPE。**单条查询**按契约返回"没有"值（`null` 或 `Optional` 一类，跟随项目先例），**不得**为"统一"而把单条查询也改成返回集合。
* **判定标准（任一命中即违规）**：① 主键/唯一键取值未判空即调用按主键查询（典型：`getById(id)`、`findById(id)` 未先判 `id == null`）；② 集合入参为空时仍逐个或整批发起查询（典型：`listByIds(emptyList)`、循环体里未判空即查）；③ 集合类接口在无结果路径上 `return null`；④ 以"调用方会传对"为由不判（本条的失效目标正是调用方传错时的无效 IO，不是"参数不合法"这一层）。
* **边界（L2，防反用）**：本条**只**管"参数使查询必然无结果"这一类**无效访问**与"集合返回 null"这一种**契约缺陷**；**不**要求为**合法但可能查不到**的取值（不存在的 id、不匹配的条件）加任何前置判断——那属于正常业务路径，**不得据此把正常的"查不到"包成提前返回**（会掩盖数据缺失、也会让调用方以为数据不存在）。**须真的去查**的语义（存在性校验、幂等写入前的探测）不受本条约束，不受影响。
* **存量边界**：改到哪个调用点才顺带调整（随动迁移，见 `specs/core/execution.adoc`）。

=== 方法名与逻辑删除的对应（查询方法名即删隐面）

**删除标志**＝数据行上的**逻辑删除标记**（各技术的载体名可能不同：布尔列、时间戳列、状态列、由 ORM 注解声明的删除字段等）。**删隐面**＝本次查询在删除标志上的取向：**不过滤删除标志**（含已删数据）／**只取未删**／**只取已删**。**"默认"＝不带任何删隐面特征的方法名所表达的那一面**。

* **方法名即删隐面（L1，适用所有语言与持久化技术）**：查询方法名**只准表达"默认"这一面**——**默认面取该技术是否自动附加删除标志条件**：① 持久化技术**不自动附加**删除标志条件时（未启用逻辑删除，或自行实现而调用点须显式写条件），**默认＝不过滤删除标志**；② **自动附加**时（框架的逻辑删除默认生效），**默认＝只取未删**。**须查**非默认面的数据时（该技术不自动附加时的"只看未删/只看已删"、自动附加时的"含已删/只看已删"），**方法名须带该面的特征词**（各技术栈的取值落点见 `specs/stack/` 对应文件）。

**理由**：同一个不带特征的名字在两种技术下一次是"含已删"、一次是"只取未删"，**删隐面只能从技术配置反推、读代码的人与评审者都无从预期**；"默认"也因此不再是"约定俗成的那一面"，而是"这一行的技术恰好怎么配"。**判定标准（任一命中即违规）**：① 不带删隐面特征词的方法名查询了**非默认面**的数据；② 带特征词的方法名与它查询的删隐面不一致；③ 同一实体上同一删隐面并存两个名字（含特征与不带特征各一个）；④ 以"项目里没启逻辑删除""反正能查出数据""配置里写着"为由自我豁免。
* **默认面的判定只在一种情形下另有出处（L2）**：项目自身规范或该项目既有先例已明确"这个项目里不带特征的名字查哪一面"时按其执行，**在同一项目内只保留一种默认口径**；项目没写、也没有先例时，按上一条取值（技术是否自动附加）。**不得**以"框架文档这么定的"直接当项目的默认——同一项目里各实体可各自配置（实体注解 = 声明该实体启用逻辑删除，**只决定该实体的默认面、不决定整个项目的方法名默认面**）。
* **例外与边界（L2）**：① 本条**只**约束**按实体/表做查询的方法名**——非查询方法、局部变量与参数名、非实体的数据结构名不适用；② `includeDeleted`/`withDeleted` 一类**显式表达该面的参数或调用形态**与特征词等同，不构成第二套口径；③ 同一技术的**框架自带**方法名不受本条改写范围约束（如框架自带的按主键查询按其自身语义生效）——它们是框架契约的一部分。
* **存量边界（L1）**：改到哪个方法才顺带定名；**且不得据本条做全库改名**（改名会同时破坏调用方与下游契约）（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性：同一名字在不同技术配置下含义漂移、删隐面不可从名字预期）、ISO/IEC/IEEE 29148（判定须可验证）、《阿里巴巴 Java 开发手册》（方法名须望文生义、避免歧义）。**"默认面随技术是否自动附加删除标志条件而变、非默认面须带特征词"是本集合的判据化取舍**——外部材料只给"命名须表意、避免歧义"这一下限；本集合的取舍与实证见依据图书馆『规范准入与自身取舍』主题。
* 依据（标准名/编号）：ISO/IEC 25010（性能效率、可靠性）、ISO/IEC/IEEE 29148（判定须可验证）。**本集合的取舍**：主流框架与通行写法并不强制这一层判空（把参数校验交给调用方或数据库），本条把它提为 L1，理由是"无效访问是外部 IO 成本 + 集合返回 null 是契约缺陷"两者都不可接受；技术栈侧的落点与用法见 `specs/stack/` 对应文件（Java 见 `specs/stack/java.adoc`「健壮性」）。

== 对象转换（多层嵌套对象的转换）

不同层/不同模型之间**多层嵌套对象**的转换（对象含对象、集合含对象、逐层都要转），**首选声明式映射**；**无嵌套（单层）的转换不在本条范围内**。具体技术可用的转换库见 `specs/stack/` 对应文件。

* **首选声明式映射（L2）**：转换**优先**由**转换库的映射声明**（映射接口/转换方法 + 字段映射注解等）完成——其价值在"转换只写在一处、映射关系由声明表达"，能在编译期或首次运行前暴露字段对不上。**优先路径不是唯一解**：深拷贝/结构复制工具、序列化中转、手工构建器等等价路径同样合规，按下条判据判。
* **达标判据（判的是结果，不是手段）**：同一份转换**只有一处来源**（改模型只改一处）；该结构增删字段、改字段时，转换处**不会静默漏字段**（能报错/提示，或由声明自动随动）。**手写逐字段搬运**（一层层 `new` + 逐个字段 `set`/`get`、手动递归/循环展开嵌套对象树）**在多层嵌套下达不到该判据**。
* **除主动声明外优先声明式映射；确需手写时须备注原因（L2）**：人来主动声明（代码注释 / PR 描述 / Issue 要求）允许手写的，按声明写；否则优先走声明式映射，确需手写时在代码注释写明原因。**本条不设强制面**。
* **映射声明的落点**：映射声明与转换方法**独立成文件、不塞进纯数据结构类**；落点跟随项目既有约定。
* **例外与边界（L2）**：① 映射声明表达不了的语义（字段名与来源不对应需自定义规则、需外部查值/远程取值、需条件分支决定取值、多来源合成一个字段）不适用，可在映射声明内以自定义方法承接，也可按主动声明手写；② **无嵌套（单层）不在本条范围内**（与字段数量无关）。
* **存量边界**：随动迁移，见 `specs/core/execution.adoc`。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）。**"优先声明式映射、不支持手写转换代码"是本集合的建议取向，非外部标准规定**。

== 跨语言执行脚本的落点（资源文件夹，不写字符串拼接/模板）

调用**其他语言**来解释/执行的脚本（SQL、Lua、JavaScript、shell 片段等），**不得以字符串拼接、字符串模板或字符串常量内联在宿主语言代码里**，一律**独立成文件放在资源文件夹**，**文件扩展名取被调语言自身的扩展名**（`.sql`、`.lua`、`.js`、`.sh` 等）；无通用扩展名时取该技术明确支持的文件形式（如 MyBatis 的 `*.xml` 承载 SQL）。取用时**按资源读取**。

* **落点（L1）**：跨语言脚本须**独立成文件**，放在项目的资源文件夹/资源目录（Java 的 `src/main/resources/`、Node 的 `resources/`），**不得**内联在宿主语言代码里。
* **扩展名（L1）**：文件扩展名取被调语言自身的扩展名；无通用扩展名或所属框架有既定文件形式时，取该技术明确支持的文件形式。**不得**用宿主语言的扩展名或 `.txt` 一类无语义扩展名承载。
* **读取方式（L1）**：脚本**从资源读取后执行**——按资源加载并交给对应执行器；**不得**把脚本内容拼进字符串再执行，也**不得**为"好拼接"而把脚本拆成片段。
* **加载时机（L1）**：读取须**按性能敏感度定性**——**性能敏感路径**（高频调用、争分夺秒的调用，如 Redis 操作、循环内、请求热路径）**不得每次使用时都去读资源**：资源进了 classpath 后发布即成常量，须在**第一次使用**时读取一次并缓存，后续复用；**不敏感路径**（启动装配、一次性任务、低频操作）每次读取无妨；**需求要求内容会变**的（每次渲染前可编辑的 HTML 模板、需热更新的脚本）**不适用缓存**，按"是否需重读"决定。
* **判定标准（任一命中即违规）**：① 宿主语言代码里出现被调语言的语句文本（`SELECT`/`INSERT`/`UPDATE`/`DELETE`、Redis 命令、`return redis.call` 等）；② 以字符串拼接、格式化、插值、模板字面量组装该脚本；③ 该语言/技术有约定的文件承载形式却未采用；④ 性能敏感路径上"每次使用都重新读取一次资源"（`open`/`read`/`getResourceAsStream`/`load` 出现在调用路径内且无缓存）；⑤ 反向误用——把需求要求可变的模板/脚本按静态常量一次性读死。
* **例外与边界（L2）**：本条只管跨语言脚本的**承载与取用**，不要求为已由框架以文件形式承载的脚本另建文件（MyBatis 的 mapper `*.xml` 就是这种承载）；也不禁止**同一技术**自身的语句构造机制（ORM 的查询构造器、动态 SQL 标签）。
* **反例（L2）**：Java 里 `"SELECT * FROM t WHERE id = " + id` 拼 SQL、把一段 Lua 写成 Java 多行字符串再 `eval`、把 shell 片段写进 Python 字符串再 `subprocess`。
* 依据（标准名/编号）：OWASP SQL Injection Prevention Cheat Sheet、OWASP Query Parameterization Cheat Sheet（本条**加严**为"语句须独立成文件"，加严理由是"无高亮、无错误校验的文本易错"，属本集合取舍）、ISO/IEC 25010（可维护性、性能效率）、ISO/IEC/IEEE 29148（判定须可验证）。

== 警告与弃用

* **警告处理（L1）**：除非显式声明（代码注释说明该警告已知且接受），否则严禁遗留任何警告（编译警告、IDE 警告等）；新代码不得引入警告，存量警告须修复或声明。
* **兼容老代码无法避免的警告**：须在代码注释说明原因并抑制，避免反复提醒；为兼容低版本而保留的旧 API 告警属正常且必要，不属需修复的警告。
* **不得调高阈值或关掉规则来消灭告警（L1，任何语言）**：工具链或构建工具报出的**质量哨兵**（构建告警、体积/复杂度阈值、静态检查与类型检查的规则、测试与覆盖率门槛）**一律不得**以"把门槛挪开"的方式消除——**判定标准（任一命中即违规）**：① 改动只是**放宽哨兵自身的取值**（调高告警上限、关闭/降级规则、加豁免清单），而触发告警的那一处代码**未变**；② 以「告警太多」「阈值不合适」「先跑通」为由调高阈值，而未落到例外。

**去路（L1）**：哨兵响了就**消掉成因**——改结构、拆粒度、把该懒加载的拆出去、把该删的删掉；**只有一种情形可以调**：哨兵**取值定错**（它报的不是本项目的质量问题），此时**改取值须有可核对的依据**（如实测的包体积构成、该规则在本项目不适用的具体理由），并在配置处写明。**判据是"成因变没变"**：调完阈值后**触发告警的那一处代码一个字都没改**，就属本条禁止的形态。

**边界（防反用）**：本条**不管**"把门槛调到更严"、也不管工具升级带来的等价迁移；**例外（L2，须写明理由）**：尚无可行手段消掉成因时（第三方产物不可改、平台不支持该拆分方式），可显式抑制**该处**（局部豁免、附原因），或按上条"取值定错"处置，**不得**整类关闭。
* **不得使用被弃用的类/API，改用替代者（L1）**：被标记弃用（`@Deprecated`、`deprecated`、文档标注废弃等）的**类、方法、接口、字段**一律**不得在新代码里使用**，须改用其**替代者**；替代者**优先取升级后的新类、或同名新类**（同一能力的更高版本形态、`XxxV2`/新包下的同名类型一类），其余替代形态（迁到别的类/方法）次之。**判定标准（任一命中即违规）**：① 新写的代码里出现被弃用类型/成员的直接使用（调用、继承、作为字段类型/参数类型/返回值类型）；② 以「旧写法也能跑」「新写法不熟」为由继续用被弃用者，而未落到例外；③ 把「替代者」选成同类弃用者的别名（换了个弃用者不算替代）。

**例外（L2，须写清理由）**：弃用者的替代者**在本项目声明的依赖面内不存在**（框架未提供新形态、或被弃用者就是唯一可用入口）时，可在代码注释写明「替代者为何取不到」，此时保持原状、不构成违规。
* **取兼容性更好的那一个（L1，跨语言）**：同一能力存在**两个及以上等价入口**（类、方法、注解、API、库、以及任何其他可互换的形态）时，**取兼容性更好的那一个**；只在**效果相同**时适用——效果确有差异时按差异本身取舍，本条不介入。**"完整能力面"是取用前提**：候选者**取不到你想要的那个能力**时不得选它（少一个开关、少一层控制、少一个重载即为取不到），仍按效果差异取，避免把"换一个更兼容的写法"做成功能缩水。

**"兼容性更好"的取值（三条，从先到后，取最先成立的那一条）**：① **迁移风险更小**——**它的既有用法将来不需要按技术栈现行取向整体改名或换包**（典型：同版本区间内已换过包名/命名空间的 API，其**旧名形态**即属风险更大的一方，选其**新名形态**或未换过的那一方）；② **它同时被两代以上技术栈版本支持**（新旧版本并存期无需二选一、无需按版本配置）；③ **它的技术支持方是标准组织**（TS 是标准组织，而 TS 仅针对该组织的平台给出、不得据以判定跨上下文（字段级联、跨语言）的约束）。以上均不能判定时，**按其既有依赖面的先例取**——先例优先，不另立一套（见 `specs/general/coding.adoc`「既有实现与先例优先」）。**判据形态是"同一组条件下两个候选各自成立"**（同等功能、同等约束强度），**不是"谁写起来更短"**——写法长短、包名长短、是否熟悉都不构成理由。

**判定标准（任一命中即违规）**：① 同一能力在同一处代码里并存两种等价形态（一半用它、一半用另一个）；② 以「旧写法也能跑」「新写法不熟」「记不清是哪一代的名字」「这样写更短」为由取兼容性更差的一方，而未落到例外；③ 把"取兼容性更好的"读成"**凡是新的就取**"——**新不等于兼容**（新形态若尚未被当前依赖面支持，取了即引编译/运行问题，属取错）；④ 把本条读成"可以拿更兼容的形态去**替掉效果不同的那个**"（效果有差异时本条不适用，须按差异本身取舍）。

**例外（L2，须写清理由并说明用了哪一条）**：① 效果确有差异（含"你要的能力只有一方提供"）；② 兼容性更好的一方**在当前依赖面内取不到**；③ **符合标准的既有形态**与另一候选等价时，**既有形态优先**——它是同一层级的正当候选、不是"兼容性更差的一方"，本条不据此要求更换（如约束注解的 **`jakarta`/新命名空间形态**与框架自有入口并存时，前者取标准与新命名空间两个方向、可径取；而"标准已是上一代命名空间"的形态才落到本条第①档）。**这一档只保「在当前技术栈版本下仍被兼容」的既有形态**——"当前版本已不兼容的那个"不在本档内；**「未被标记弃用」也不构成**把它留在候选面的理由（`@Deprecated` 只是弃用的一种载体，**不再兼容＝事实上已废弃**）。**边界**：只规定取哪一个，**不规定怎么改**；不得以本条为由顺手调依赖、改版本或做全库替换。**依据（标准名/编号）**：ISO/IEC 25010（可维护性与兼容性：同一能力只留一个入口、迁移成本须在选型时收敛）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Semantic Versioning 2.0.0（包名/命名空间变更属破坏性变更、不在同版本内兼容）。**「同一能力取兼容性更好的一个」是本集合的判据化取舍**——通行材料只给"注意兼容性"这一方向，未把它落成候选之间的取值口径。
* **默认不为此调整依赖、也不动依赖版本（L1）**：改用替代者**不得**顺带改依赖清单或依赖版本——本条只要求**改代码里的调用点**，替代者应取**项目当前依赖面内已有**的形态；确需升级依赖才能拿到替代者时，按 `specs/general/dependency.adoc`「升级与废弃」另行处理，**不得**以「换掉弃用类」为由顺手改版本号。
* **内部弃用 API 的调用不迁移、不修复（L2，存量边界）**：项目自研的废弃 API 被项目内部调用时调用处保持原样（内部废弃 API 随时会被移除，迁移收益低且可能引入回归）；仅第三方库弃用 API 须升级到新签名。**本条**只管既有调用点——**新写的代码仍按上面「不得使用被弃用的类/API」执行**（新代码不得引入对弃用者的新调用），本条**不构成**对新代码的豁免。
* 依据（标准名/编号）：Java 官方 API 文档与各语言/框架的弃用机制说明（`@Deprecated` 与文档标注废弃给出替代者）、ISO/IEC 25010（可维护性：同一能力并存旧新两条路径即两条真源）、ISO/IEC/IEEE 29148（判定须可验证）。**「不得使用被弃用者、替代者优先取升级类/同名新类，且默认不动依赖与版本」是本集合的判据化取舍**——官方材料只给出「某成员已弃用、有替代者」，**未**规定必须迁移、也**未**规定迁移的范围不得波及依赖面。

== 分发产物的体积与按需加载

**任何语言**都适用：只要做过**分发产物**（可执行文件与归档包、容器镜像、安装包、前端打包产物、库的发布件等），**体积上限就是一条质量哨兵**——构建工具报"某产物超过体积上限"时，处理方式与任何告警相同（见「警告与弃用」）。

**识别判据（先认产物，再判体积）**：可分发并被加载方取用的一次交付物即本条所指的**分发产物**。**边界**：只在本机运行的中间件、测试夹具、调试产物不属本条；本集合不列各生态的工具名与产物文件名。

* **体积哨兵响了就消成因，不得调高上限（L1）**：构建工具报出某产物超过体积上限时，**须消除成因**，**不得**把上限调高、也不得关掉该告警。**成因只有三类，按序判**：① **该产物整份被"首屏/首次使用"打包**（用到一点、加载全部）；② **产物里含本次执行路径用不到的实现或依赖**；③ **产物里的代码本身过多、过大**。**判定标准（任一命中即违规）**：① 上限被调高或告警被关闭，而产物内容与引用方式未变；② 以「阈值不合理」「拆包太麻烦」为由放过该告警。
* **按需加载（L1）**：分发产物的**入口**只装"首次执行就要用的那一部分"，其余（其余路由/页面、其余命令、其余平台分支、其余可选能力）按**实际用到时才取**的方式组织——取值形态是"**引用点可被静态识别为按需**"（动态引用的形态在各语言/框架里不同，本集合不列写法）。**判定标准（任一命中即违规）**：① 入口处一次性引入了本次执行用不到的实现；② 为"少写一层包装"把全部能力挂在入口可达的同一引用路径上。
* **可达的依赖须可被静态消除（L1）**：产物里不得留下**按语言/构建工具的静态分析手段无法消除**的依赖——判定标准是"**引用点可被静态识别、且依赖自身没有全局副作用声明**"，不看依赖是否"看起来用不到"。**判据取形态、不取体积**：某依赖是否真被消除，须以产物的实际构成核对（`体积数字` 是结果，不是依据）。**判定标准（任一命中即违规）**：① 为"少配一处"把带全局副作用的导入放在入口处；② 依赖库里只用到其中一小部分，却按其整体宽度引入。
* **公共部分只留一处（L2）**：多个产物共用的实现须由构建工具**共享**（同一份块/同一份胶水代码），不得为"每个产物各拷一份"而把公共实现复制进每个产物——重复的公共部分同时抬高总体积与"改一处漏一处"的风险。
* **存量边界（L1）**：本条**只管新增的产物组织与本次改到的引用点**，**不发动全库重构**（不批量改既有引用形态、不批量拆包）（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（性能效率、可维护性）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、web.dev 的 Core Web Vitals 与 Lighthouse 对打包体积的性能预算取向（业界约定、非标准）、各构建工具官方文档对按需加载与静态消除的机制说明。**「体积上限是质量哨兵、消成因不调上限」以及「判据取可达性形态而非体积数字」是本集合的判据化取舍**——构建工具只给「超限告警」这一条信号，**未**规定"响铃后该改代码还是该改阈值"。

=== 前端打包产物（适用于任何打包器）

* **路由/页面级按需加载（L1）**：前端应用的路由（页面）与**首屏用不到的重区块**（图表库、编辑器、富文本、地图、PDF/Office 预览、国际化文案包等）须**按需加载**，不得在入口处静态引入全部页面与全部重依赖。**判定标准（任一命中即违规）**：① 入口（应用根、路由表）处静态引入的模块集合里含有**首屏渲染用不到**的页面或重区块；② 已有多条路由的应用把**页面**集中在一处静态引入（判定依据是"首屏是否需要它"，不是"代码在哪个目录"）。
* **依赖库的静态消除不得失效（L1）**：引用第三方库须让打包器能判定"用到哪些、哪些可丢"——**按名引入具体成员**，不整体引入命名空间再取属性；库清单里须声明**无全局副作用**（该库确实无副作用时才声明），使未用到的部分可被剔除。**判定标准（任一命中即违规）**：① 入口处整体引入一个只用到少量成员的库（`import * as X` 后只用一两个成员、或整包默认导入后取属性）；② 为"配置一次省事"，把带全局副作用的导入（样式、polyfill、注册类副作用脚本）放在入口，而该副作用只服务于某条按需加载的路径。
* **第三方依赖的落点（L1）**：体积大的第三方能力**优先取"用到时再取"的形态**（按需注册的组件/插件、按需加载的模块），不在入口处注册全部。
* **独立产物须有实测的拆分依据（L2）**：把依赖拆成独立的产物块时，**取该拆分确有收益的依据**（实测算出的依赖构成），不为"看起来更快"手工堆拆分表。**判据取收益、不取配置量**。
* **不得用上限值掩掉告警（L1）**：构建工具的产物体积上限**不得**调高以消除告警（见本节的「体积哨兵响了就消成因」）——这类告警正是本条要处理的问题。
* 依据（标准名/编号）：ISO/IEC 25010（性能效率）、ISO/IEC/IEEE 29148（判定须单一、可验证）、各打包器官方文档对按需加载（动态引用）、依赖树静态消除与副作用声明的机制说明、web.dev 对首屏体积的性能预算取向（业界约定、非标准）。**「路由与重区块按需加载」「副作用只许就近落」是本集合的判据化取舍**——打包器只给机制（动态引用、副作用声明），**未**规定"哪些模块必须按需加载"。

== 界面与样式（任何语言、任何端）

**任何语言**都适用：只要产出**给人看的界面**（网页与前端应用、桌面窗口、移动端页面、服务端渲染的模板、终端 UI 等），无论用什么语言与 UI 技术写。本集合不列框架名与库名（各生态可选者众、会随时间换代），只给判据与判定标准。

**识别判据（先认是不是界面）**：由**布局与外观**承载信息、需要人**看得懂、点得动**的产出即本节所指的界面。**边界**：只输出数据的接口、日志与命令行的一段输出不属本节；纯样式文件（主题、设计令牌）属界面的一部分。

**为什么界面排在最前**：本节这一档是**唯一没有可执行判据**的一类——外观与观感没有测试，同一形态各写一套后跑什么都不报错，只有人看出来；故它先按本节与下节「同一件事只有一个来源」处置，其余各档见下节。

* **优先取现成 UI 框架与开源样式方案，不从零写一套（L1）**：**新写**界面时，先取**项目已引入**的 UI 组件库/样式方案，其次取**该生态通用**的开源方案（组件库、设计系统、无障碍与主题方案）；**不得**在没有先例、也没有取舍理由时，从零手写一套组件与样式。**判定标准（任一命中即违规）**：① 新增界面里出现与现成框架成员**同形**的基础件（按钮、输入框、弹窗、表单、表格、分页、提示条等），而项目或该生态已有现成方案；② 以「自己写更可控」「AI 写得快」「样式更贴合」为由从零手写，而未落到下面「从零写的唯一正当情形」。
* **同一形态只许一个样式来源（L1）**：**视觉形态相同**的元素——业务上本就是**同一套东西**（同一种按钮、同一种卡片、同一种表单控件）——在项目内**只许有唯一一处样式与结构来源**（框架组件、公共组件、公共样式类之一），其余位置取用它、不得各写一份。**判定标准（任一命中即违规）**：① 同一形态在两个及以上位置各写一套样式或结构（复制样式、就地重写同名组件）；② 同一形态在项目内并存两种外观（大小、圆角、间距、颜色、交互态不一致），而形态本身相同；③ 以「这块页面特殊」为由就地改框架外观，而未把差异收回一处。
* **框架默认外观与主题只在一处改（L2）**：对框架的默认外观做**全局**调整（主题变量、设计令牌、框架样式的覆盖层）须落在**唯一一处**；**不得**在每个使用点逐个改框架内部结构或重复覆盖同一属性。**判定标准**：同一视觉属性在两个及以上使用点各自覆盖，而无统一落点。
* **`!important` 是最后一步，不是常规手段（L1）**：它是**优先级**的手段，本身不表达任何来源关系——用它压下的不是某一条样式，而是**这处选择器与其余所有选择器的关系**（谁先谁后不再有意义），于是同一项目里只能靠**逐处再加更强的 `!important`** 去覆盖，改一处必漏一处，直到没人说得清哪种写法会生效。故取用的**次序是**：① **提高选择器本身的优先级**（层次与形态已由结构表达时，改在唯一落点的选择器上）；② **收进来源那一处**（公共组件/公共样式类/主题变量，见本节上两条）；③ **第三方库或内联样式这类取不到来源时**，**收在一处覆盖层**（框架样式覆盖层或全局样式落点，只此一处）并**写明理由**；任何一处都走不通、且不写就达不到目标时，`!important` **只落在那一处**、**须写明理由**。**判定标准（任一命中即违规）**：① 同一处（同一样式落点、同一段样式内的相邻规则）出现**两处及以上** `!important`，或为覆盖一处 `!important` 又写了一个——**以 `!important` 覆盖 `!important` 即违规**，无论分几处写作；② **判定只在写它的那处算、不看调用点有多少**——同一个 `!important` 被二十个页面取用**不算频繁**（它是唯一来源），而在二十处各自写一个、或同一段里连写多个，即使各自都"只写了一次"也算；③ 新写的样式里出现 `!important`，却没有上文第 ③ 步那条**收在一处的覆盖层与理由**——以「临时压一下」「框架改不动」为由就地加，即便只加一处也不算。**边界**：`!important` 落在项目自己写的覆盖层里属①的正确形态，本条的靶心是它**散在使用点、或在同一处层层加码**；存量按存量边界随动迁移，不发动全库清理。
* **无障碍与语义属性取框架所给（L2）**：现成方案的**语义结构、键盘可达、焦点与读屏属性**按其所给使用，**不得**为局部外观把它剥掉（如把按钮换成可点的容器、去掉标签与焦点样式）；需要的差异走框架提供的扩展点。
* **从零写的唯一正当情形：与既有界面对齐（L1）**：**可以**从零写，但**只在**下列情形之一成立时：① 项目与该生态都取不到满足需求的现成方案（判据取「**本机、目标版本、目标形态上实际试过取不到**」，不凭印象，并写明试了什么、卡在哪）；② **被测对象就是既有的那份界面**——**逆向/复刻**（还原既有页面或产品）或按固定设计稿实现，外观须与参照一致，此时**以对齐参照为准**（按设计令牌与结构对齐，不引入与参照冲突的框架外观）；③ 项目自身规范明确要求。**判定标准（任一命中即违规）**：① 以上三种情形都不成立，仍从零手写；② 以「逆向/复刻」为由把**同一项目的其余页面**也一并手写（该情形**只覆盖需要对齐的那个范围**）；③ 把「取不到」说成结论而未实际试过。
* **从零写也须收在一处、只此一份（L1）**：**无论**用框架还是从零写，**同一形态的实现只许存在一处**——基础件走公共组件/公共样式的唯一落点，页面只组装、不各写一套；**跨端**（同一产品的网页与桌面/移动端）复用同一份设计令牌与形态定义，不以「端不同」为由各造一套。**判定标准（任一命中即违规）**：① 从零手写的同一形态在第二个位置被复制或重写；② 以「这次先就地写」为由留下第二套基础件。
* **存量边界（L1）**：本条**只管新增界面与本次改到的部分**，**不发动全库改造**（不批量替换既有组件、不为统一外观重写既有页面）（随动迁移，见 `specs/core/execution.adoc`）。
* **内容多的页面按分组组织，不把各分组隔成互不相关的块（L1）**：同一个页面里的内容多到需要**分组**时（设置页、配置页一类），各分组**同处一页**、由**分组标题与分组内的顺序**组织，**不得**把分组拆成互相隔离的块（并排的独立卡片/面板、各分组自带边框与背景、分组之间空出整块间隔、二级标签页各藏一部分）——分组之间本可对比与跳读的关系，被这些边界切断后读的人只能逐块翻过去、也读不出整页有哪些设置。分组的内聚与顺序取**使用流程**（被依赖的在前、同一件事的归一组），不取字母序或改动追加序。**判定标准（任一命中即违规）**：① 新增或改到的页面里，分组以上述任一隔离形态呈现，而非分组标题下的顺序内容；② 页面出现二级标签页/折叠区，仅为把分组彼此隔开；③ 分组与其下条目的关系只由间距与边框表达，没有分组的标题（或读屏可读的分组名）。
* **分组须能被检索到（L1）**：页面做过分组、或单页条目到**扫读不现实**的量（判据取形态：要逐条读一遍才能找到目标，而非一眼扫过即可）时，须提供**页面内检索**——**检索面向的是页面上起名可见的各项（分组名与条目名），命中即可一步定位到该项**（所在分组随之可见），**不按关键词猜内容**。**判定标准（任一命中即违规）**：① 页面已分组或条目量已到上述量级，而没有页面内检索入口；② 检索要用户先逐组展开或逐组切过去才能看到结果——检索没有落到全页那一层，等于让用户先自己分组再找。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性与一致性：同一形态两份来源即改一处漏一处）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、ISO 9241-110（符合预期与可控：同一形态外观一致，用户才不必重新辨认）、W3C WCAG（语义结构与键盘可达属无障碍的基线取向）、ISO 9241-112（信息呈现：按使用者的任务与预期组织信息、呈现须自洽且可预期）、ISO 9241-143（表单：分组须有序且各组有可辨的标题）、WCAG 2.2 SC 3.2.3/3.2.6（同一产品内的导航与帮助位置保持一致）、Nielsen Norman Group 关于设置页分组与页内检索（业界实践、非标准）；**「框架优先、同一形态只留一处样式来源、从零写的唯一正当情形＝对齐既有界面 / 实际取不到、`!important` 只作最后一步且须收在一处、内容多的页面同处一页按分组组织而不隔离各分组、分组与超量条目须提供页面内检索」是本集合的判据化取舍**——各组件库与设计系统的官方文档只给**机制**（主题变量、扩展点、设计令牌），**未**规定「该不该从零写」「哪些形态必须来自框架」，也**未**把 `!important` 列为禁忌（浏览器各家规范只定**机制**：它抬高声明的优先级、并让一条声明压过其余所有选择器）。

=== 界面的规模与性能（任何语言、任何端）

**识别判据**：由**布局与外观**承载信息、需要人**看得懂、点得动**的产出即本节的界面，**不限语言与端**（Java、Python 一类写的桌面/内嵌界面同样在内）——识别判据与上一节同一份、不另定。

**为什么单独成条**：界面**能用**（打开就看到、点得动）与**好用**（数据长起来之后打开还快、滚动与筛选不卡）是两件事，而**开发期看不出来**——刚开始数据不多时界面并不卡，与后端接口一样，只有数据量大了，才知道哪一处卡。故判据不取「看着快不快」，只取下面四条可核对的形态。

* **列表与表格按需取数，不把整份集合一次画出来（L1）**：可增长的集合（表格、列表、树、下拉、时间线）在**打开与切换时**只取与只渲染当前需要的量——取数侧走分页/按需加载/游标，渲染侧走虚拟滚动、分页、折叠之一；**不得**把整份集合一次取回、一次渲染成 DOM/控件/行。**判定标准（任一命中即违规）**：① 界面里出现「把集合整个取回来再交给表格/列表」的取数形态；② 渲染侧一次性生成与数据量同阶的节点或控件；③ 以「现在数据没那么多」为由不设取数边界——**判据取形态，不取当前数据量**。
* **同一次展示里不逐项各取一次（L1）**：界面里逐行/逐项拼装内容时，**不得每项各发起一次取数或计算**（选中项、名称、状态、格式化结果这类**同一次展示用得上**的东西，一次性取回或在一次渲染内批量取得）；**判定标准（任一命中即违规）**：① 循环/渲染回调里出现取数调用；② 同一份输入在渲染路径上被反复重算而未共享结果。
* **只在会用到时才画、才取（L1）**：重区块（图表、编辑器、地图、预览器）与首屏用不到的区块**按需加载**（用户走到那里才加载代码与数据）；**判定标准**：入口或共享布局的静态引用图里能走到该重区块即违规（前端的具体载体见 `specs/stack/web.adoc`「分包与按需加载」）。
* **只加载可视区时，全量类操作要说清对哪一份生效（L1）**：按需取数与虚拟滚动只解决**画**与**取**，**全量聚合类操作**（总数统计、跨页全选、导出、全局搜索、批量操作）仍要有落点——① 对**全量**生效的（总数、导出、全局搜索、跨页选中）走**服务端/数据源侧**的聚合与筛选接口，**不得**在前端逐页拉取扫全表；② 只对**已加载范围**生效的，须在**界面上显式标示该范围**（「已选已加载的 N 条／全选全部 M 条」这类可点选的区分），**不得**让用户以为已作用于全量。**数据不在前端不等于不存在**——数据在数据源侧（服务端、库、磁盘）就有，差的只是**由谁来聚合**：前端只加载可视区，聚合交给有全量数据的那一侧。**判定标准（任一命中即违规）**：① 全量类操作以「循环调用分页接口直到最后一页」的方式在前端凑出全量；② 全选、计数、导出的结果**只覆盖已加载范围**而界面未标示该范围；③ 以「用了虚拟列表所以不卡了」为由，不给全量类操作留落点。
* **什么时候要做性能结论（引用）**：本条只定**形态**；要不要为某处界面做带取样与离散度的性能结论，按 `specs/general/testing.adoc`「性能测试」的触发特征判（界面的数据量可增长、重区块、重计算三类已列入该处特征），本处不复述其判据。
* **存量边界（L1）**：本条**只管新增界面与本次改到的部分**，不发动全库改造（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC/IEEE 25010（性能效率是产品质量特性之一，须**可度量**且与**使用条件**绑定；容量与资源利用须在数据规模增长的情形下成立）、ISO 9241-110（对话的符合预期与可控：响应及时、用户不必等待重操作）、ISO/IEC/IEEE 29119-4（判据须可复现、可核对）。**「判据取形态、不取当前数据量」「四处形态分别是取数边界、逐项各取一次、重区块按需加载、全量类操作的生效范围」是本集合的判据化取舍**——通行前端与桌面框架文档只给机制（分页、虚拟滚动、懒加载），**未**规定"界面性能该不该默认测""哪几处形态必须成立"。

=== 同一件事只有一个来源（不限界面，任何语言）

**界面只是这套判据的一层皮**：底层失效是**同一件事在项目里长出多份实现**，而后果按这件事有没有判据分出两档。

**两档后果（这就是"为什么先提界面"）**：① **没有判据的那一档＝只能靠人眼**——外观、观感、交互手感这类产出**没有可执行的测试**，同一形态各写一套后，改一处漏一处、页面之间长得不一样，**跑什么都没有声音**，只有人看出来；② **有判据的那一档＝不一致会自己冒出来**——功能、工具类、数据契约、配置这类产出一旦多份，**分支与参数只要有一点不同，结果就不同**：走错分支即报错、行为悄悄变、断言与快照对不上、编译或类型检查直接红，**能查出来**。故执行顺序是**先治没有判据的那一档（界面与样式，见上一节）**，再把同一套判据铺到有判据的那一档——**能查出来不等于会收敛**：没人替它做决定，底层仍按各自为政的方式各长一套。

**识别判据（先判这是不是"一件事"）**：**业务上同义**（做同一件事、产出同一份结果、回答同一个问题）的产出一律算同一件事——**同义取业务语义，不取代码相似度**：两处写法长得像但不是同一件事不算，写得完全不同但业务上同义（两个名字各叫一套、两处各判一遍同一个状态）仍算。**边界**：本条管**新写与本次改到的部分**；纯数据对象的多份副本按「数据契约的载体」判，依赖与版本的唯一来源按 `specs/general/dependency.adoc` 判，名称本身（同一个东西叫法不一、定义被复述多份）按 `specs/general/terminology.adoc`「数据字典」判——那是本条里"同一个名称只有一处定义"那一支，两者同源：**一处定义、其余取用**；本条不重复要求。

* **同一件事只许一个来源（L1）**：业务上同义的能力**只许有唯一一处来源**——一个函数、一个工具方法、一个组件、一个数据契约、一处配置、一处校验规则——其余位置**取用它**，不得各写一份。**判定标准（任一命中即违规）**：① 同一件事在第二个位置被复制或就地重写（复制一段函数体、各写一个同名同构的工具方法、各判一遍同一套校验、同一份配置抄两处）；② 同一件事并存两种写法或两份来源（一半用它、一半用另一份），而后来的读者无从知道该以哪份为准；③ 以「这块场景特殊」「这次先就地写」为由留下第二份。
* **第一处就该是能被取用的那一处（L1）**：**写第一次时就把来源放在别人取得到的位置**——同一件事在第二个位置用得上，它的来源须是**公共落点**（公共模块、工具类、公共组件、公共配置），页面/调用方只组装与取用；**不得**先就近写死、等第二个位置出现再挪一遍。**判定标准（任一命中即违规）**：① 明知会有第二个使用点，仍把它写成某处的私有实现，第二个位置只能复制或重写；② 以「还没人用到」「先跑通」为由把它留在使用点里。
* **实现已存在时不得另写一套（L1）**：项目或已引入的依赖**已有等价能力/先例**时**一律复用它**，不得另写一套（判据与动手前先查的口径见 `specs/general/coding.adoc`「既有实现与先例优先」与「不得以语言内置写法绕过既有能力」；本处**只把「另写一套」单列为违规形态，不另定查法**）。
* **定下唯一来源时一次收敛，不逐处漂移（L1）**：确定某件事有了唯一来源后，**改写其余位置去取用它**（改调用点、删副本），**不得**只加新的、把旧的留下——两套并存正是本条要治的形态。
* **判据与自证：重复要有办法自己冒出来（L1）**：同一件事的两份来源，**须有能自动发现它的手段**——按该产出所属的那一档取：有判据的一档（功能、工具类、契约、配置）用**测试/类型检查/静态检查**发现（两份走不同分支、参数不同、结果不一致时须报红）；没有判据的一档（外观与观感）用**可 diff 的快照或清单**兜住（同一形态的样式与结构只在一处，第二处出现即报红或由复核点出）。**判定标准（任一命中即违规）**：① 新增的同一件事没有任何能发现第二份的手段（既无测试也无校验），只靠"记得改两处"；② 以「人眼看得见」为由不给没有判据的那一档留可 diff 的落点。
* **例外（L2，须写清理由并说明用了哪一条）**：① **两侧分属无法共享的运行边界**（前后端、跨进程、客户端与服务端各一份）：**判据是契约不是代码**——两侧各实现可以，但**契约（字段、常量、校验规则）只有一处来源**，另一侧由它生成或对照核验，不得各写一份再靠人同步；② **被测对象就是参照物本身**（逆向/复刻、按固定设计稿实现，见上一节「从零写的唯一正当情形」）；③ **项目自身规范明确要求**（如某些分层约定要求两层各有一组对象）。
* **语言只定载体、不定判据，也不给某门语言开例外（L1）**：上面的识别判据与判定标准对**任何语言**一律成立（函数式、脚本、面向对象、前端、SQL 与模板语言同样在内）。**语言与生态只决定"这个唯一来源落在哪种载体上"**——静态方法、模块级函数、公共组件、共享常量与类型声明、项目自有的配置与校验定义之一，**判据不因语言变**。**判定标准（任一命中即违规）**：① 以"这门语言没有工具类""它不是面向对象的""动态语言就这样"为由，放过同一件事的第二个来源；② 把某门语言里"有两个现成入口"当成例外——那是取值口径，替代关系只在一处定；③ 只给一门语言写落点，就当成"本条只对那门语言成立"（栈层只**举例式**给载体，不是判据的适用面）。
* **存量边界（L1）**：本条**只管新写的与本次改到的部分**，**不发动全库改造**（不批量抽公共方法、不批量合并重复实现）（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性与一致性：同一件事两份来源即改一处漏一处）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、ISO 10007（配置项与变更须有单一、受控的来源）、The Twelve-Factor App（同一份构建产物跨环境复用，不在各处分叉）、Martin Fowler《Refactoring》（重复代码的收敛前提是"第一次出现重复时才收敛、不预先抽取"）；**「先治没有判据的一档（界面），再把同一判据铺到有判据的一档（功能与工具类），并要求重复须有能自动发现它的手段」是本集合的判据化取舍**——通行材料只给"不要重复、抽取公共实现"的方向，**未**规定按"有没有可执行的判据"分档处置，也**未**把"能发现第二份的手段"列为规则。

== 缓存（统一管理、先缓存后在线）

**任何语言、任何端**都适用：**缓存**＝把一份数据的副本留在取数较慢的一侧（内存、本地存储、浏览器会话存储），让界面或调用点先取到它，再与数据源核对。加载触发特征：要缓存数据或中间结果、要写/改读缓存与刷新缓存的代码、要做"打开页面先显示、再更新"的取数流程。**对象生命周期**的判据（只缓存会多次复用的对象）见本文件「代码复用」。

**先分清两处缓存（L1）**：同一份数据可能同时存在**后端接口缓存**（服务端的数据副本：进程内缓存、分布式缓存、HTTP 缓存头）与**界面缓存**（客户端侧的副本：内存状态、本地存储、会话存储）。两处**各自成立、各自判定**，不得拿一处的结论去免掉另一处：后端缓存没做不等于界面可以不先给缓存，界面先给缓存也不等于接口可以返回不确定的那一份。

* **一份数据只有一处缓存入口（L1）**：同一份数据的缓存**只许有一个**——一处缓存读写入口、一把缓存键取值规则，其余位置**取用它**；**不得**页面各自存一份、可缓存与本地存储各留一份、同一份数据在会话内被反复塞进不同容器。**这一条在两处缓存上各判一次、不合并**：后端缓存与界面缓存是两个不同的存储侧，各自的入口唯一；**不得**以「后端已经有缓存了」为由省掉界面侧的入口，也**不得**以「界面自己会先给缓存」为由让服务端再开第二个入口。**判定标准（任一命中即违规）**：① 同一份数据在**同一侧**的两处各建一份缓存（各自的变量、键前缀、存储区、失效逻辑）；② 另有位置绕过该入口直接读缓存或直接打数据源再自行保存；③ 以「这页特殊」「先开个局部缓存」为由留下第二个入口；④ 键的取值规则在两处各写一遍（改一处必漏另一处）。
* **后端接口：返回哪一份是确定的（L1）**：后端接口要返回的是**确定的那一份**——要么按缓存策略返回（命中即以缓存的那一份为结果），要么直取数据源；**不得**把「先给一份、随后再换另一份」搬到接口上：一个响应就是一个结果，也不在响应已发出后再推送同一请求的第二个版本（推送更新走显式通道而非同一响应）。**一侧响应出来即该次取数的终值**——调用方拿到的这一份就是要用的那一份，不需要、也不该等它被替换。**判定标准（任一命中即违规）**：① 接口先返回缓存副本、又在同一响应或其后续异步动作里替换同一请求的结果；② 界面上"先给缓存再换在线"被照搬到接口，以致调用方拿到两份互相矛盾的结果却无从判断该用哪一份。
* **界面：有实时查看需求时先给缓存、再换在线（L1）**：**这一条只管界面（给人看的取数）**——同一份数据既要"打开就能看到"又要"看到最新"时，取数次序恒为「先取缓存并立即呈现，再异步取在线数据」；**不得**让界面先空着等在线数据回来再画（首屏空白与加载后重绘的闪动即违规），也**不得**因为手里有在线数据就丢掉缓存入口。**判据按使用方分**：**给人看的取数**适用本条；**给程序用的取数（后端接口的返回值、服务间调用、供别的代码判定的数据）不适用**——程序要的是一份确定的结果，不认"先给旧的后给新的"。**判定标准（任一命中即违规）**：① 首屏等待在线数据返回后才渲染，界面先白屏或先显示占位再整块替换；② 缓存已在手，仍先发在线请求再决定画什么；③ 以「网络很快」「反正一下子就回来了」为由不留缓存路径；④ 把本条套到接口上（判据同上一条，一处违规即两处都不得成立）。
* **只在有变动时才更新（L1）**：在线数据回来后，与**已呈现的那一份**比对，**有变动才更新界面并回写缓存**；无变动即**不重绘**、不刷新缓存时间戳。**这一条只在界面成立**——接口没有"已呈现的那一份"，它的更新是随下一次取数发生的。**判定标准（任一命中即违规）**：① 每次在线返回都无条件重设状态、重画列表（内容完全相同也重绘，滚动位置与选中态被打断）；② 以「回来就用新的覆盖」为由不做比对；③ 把比对做成整份序列化字符串比较这类与数据规模同阶的重计算，却仍放在渲染路径上（比对本身的落点见本文件「界面的规模与性能」的"同一次展示里不逐项各取一次"）。
* **数据来源与时间要能看出来（L2）**：界面上显示的若是缓存数据或非当次取回的数据，须**能看出它是哪一份、有多旧**——标出**来源**（缓存／在线）与**时间**（缓存写入于多久前、在线数据刷新于何时）。标不标、标在哪按界面的信息密度定；**判据是不让人以为自己看到的是刚取的**。**判定标准（任一命中即违规）**：① 显示的是缓存或过期数据而界面无任何区别（用户无从知道手上这份有多旧）；② 以「数据基本不变」为由省掉标识，而该数据存在在线刷新的路径。
* **缓存的边界（L2）**：缓存的是**数据**，不是"用它算出来的结论"的第二个来源（同一件事只有一个来源见上一节）；**权限、身份、一次性凭据、随时间必然失效的令牌不按"先缓存后在线"处理**——那类取值的正确性优先于速度（见 `specs/general/security.adoc`），接口侧同理（凭据类读数不得返回陈旧副本）；需求要求内容**可变**的（可编辑的模板、热更新脚本）不缓存（判据同本文件「跨语言执行脚本的落点」的"加载时机"）。
* **存量边界（L1）**：本条**只管新增的缓存与本次改到的部分**，**不发动全库改造**（不批量迁缓存入口、不批量改取数次序）（随动迁移，见 `specs/core/execution.adoc`）。
* 依据（标准名/编号）：ISO/IEC 25010（性能效率与易用性：响应须及时、状态须对用户可见）、ISO 9241-110（对话的符合预期与自解释：系统状态须可感知）、ISO/IEC/IEEE 29148（判定须单一、可验证）、RFC 9111（HTTP 缓存语义）、RFC 9110（`GET` 一类安全方法取回的是表示、同一响应不承载先后两份）。**「一处缓存入口 + 后端只给确定的份 + 界面先缓存后在线 + 有变动才更新 + 来源与时间可辨识」是本集合的判据化取舍**——通行材料给的是缓存机制与失效策略（新鲜度、校验、逐出），**未**规定取数次序，也**未**把"先给缓存后换在线"与"接口返回确定结果"这两件事的适用面分开说；把适用面按使用方分（界面适用、接口不适用）同为本集合的取舍。

== 表达式与调用写法

* **实参不内联复杂逻辑与对象（L1）**：方法调用实参只传简单值或已算好的局部变量，不内联复杂逻辑（三元表达式、方法调用嵌套、多级 `.xxx()` 串联），也禁止内联对象初始化后直接作为入参；复杂计算与对象必须先创建为局部变量再传入。无参构造除外。
* **三元表达式为最低优先级**：只要存在其他可替代写法（工具方法、if-else、辅助函数、`||`/`or` 兜底），就**绝不用三段式**；仅当既无现成工具方法、又无更清晰的替代写法时才允许用，且只限简单判断；复杂逻辑（嵌套三元、多分支、含长方法调用）一律改用 if-else，可读性优先于行数。
* **不得新增只做条件取值的方法（L1）**：**新增方法时，不得让方法体只剩一处条件取值**——即方法的存在只为在一个表达式里挑一个值（本次改动的取值来自多个来源、按空值或取值有无二选一，典型是「传进来一个对象就取它的、为空就取外层/默认的」）。

**理由**：这类方法**没有自己的语义**（名字只是把那次挑选复述一遍）、只把同一个取值逻辑从调用点搬了个位置，**每次取值都要多跳一次**；而「空则取默认值」在标准库、项目自有工具类与已引入工具库（`defaultIfNull`/`defaultIfEmpty`/`emptyToDefault` 一类）里**已有现成入口**，缺的只是**加一个通用工具方法**（一处定义、全项目复用），不是就地为这一次调用造一个专用方法。**判定标准（任一命中即违规）**：① 新增的方法体只有一处条件表达式（三元、`if/else` 后 `return`、`??`/`or` 兜底之一）且其中一支只是「取另一个来源的同一个值」；② 以「调用点会更短」「复述一下意图」「这个方法以后可能有用」为由抽取该方法。**不得反向放大**：**有自身语义的取值方法（做计算、转换、多来源合成、按业务规则决定取值）不受本条约束**。

**例外与边界（L2）**：① **该处已有先例**（同类专用方法在本项目里已成惯例）时跟随先例；② 该语言/框架**没有现成的兜底入口、也无通用工具方法可用**时，**先加通用工具方法**（一处、可复用），仍不成立才允许就地抽取；③ **响应式/流式管线**（在链式操作符里取值）等写不进通用工具的场合不受本条约束。

**存量边界（L1）**：**既有此类方法**保持原样，改到哪处才顺带调整；**不得**据此发动全库改造（批量内联、批量删方法）（随动迁移，见 `specs/core/execution.adoc`）。
* **链式调用一律换行（L1）**：调用链（同一表达式里连续的方法/属性调用，如 `a.b().c().d()`、`o.getX().getY()`、流式 `stream()...collect(...)`、builder 链、可选链 `?.`）**每个环节各占一行、`.` 起头**；**长度不是判据**——再短的链也换行，**不得**因为「这行放得下」而写成一行。**判定标准（任一命中即违规）**：① 同一行里出现**两处及以上**的调用链环节；② 以「很短」「一屏放得下」「拆开反而更占行数」为由保持单行。

**例外（L2）**：该链是**单个不可再分的原子表达式**的一部分（如仅一层调用 `a.b()`、链本身就是语言内置的惯用写法如 `String.valueOf` 一类纯取值、注解或常量声明里受语法限制的场合），以及**测试断言**里单层的 `assertXxx(x.y())`。

**边界（防反用）**：本条**只规定换行形态、不改变求值语义与调用顺序**，不得借换行把一条链拆成多个中间变量而丢失链式语义时仍声称「已换行」；也不得据此要求把链改写成分步 `return`（那是另一件事）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性、可分析性：一屏内的结构信息量与最小惊讶原则）、ISO/IEC/IEEE 29148（判定须可验证）、Google Java Style Guide 与《阿里巴巴 Java 开发手册》（链式调用换行属通行风格要求）。**「哪怕很短也要换行」是本集合的判据化取值**——通行风格指南通常按**行宽**决定是否换行，本条取更严的单一形态，免去「多短算短」的裁量。
* **判空/默认值兜底优先用工具方法**：对"空则取默认值"这类兜底，有现成工具方法（`defaultIfNull`/`defaultIfEmpty`/`emptyToDefault` 之类）时**强制使用**；**没有现成工具方法时，取值的去向是「加一个通用工具方法」，而不是就地写三段式或就地为这一次调用抽一个专用方法**（通用工具方法一处定义、全项目复用；上条「不得新增只做条件取值的方法」同此去向）；该语言无通用工具可加时，才退回语言内置兜底（`||`/`or`）或 if-else；以上均不可用时才退回三段式。**判定标准（任一命中即违规）**：① 已有等价工具方法（标准库、项目自有、已引入工具库）仍手写三段式；② 多次需要同一兜底时逐处内联或逐处抽专用方法，而未收敛到一个通用工具方法。

**例外与边界（L2）**：**该处已有先例**（项目里同类兜底已统一走某个方法）时跟随先例，不再另立一个通用方法。

**存量边界**：见上条（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：Martin Fowler《Refactoring》（重复代码与「数据泥团」的取向是收敛到一处）、ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）。**「没有现成工具方法就加一个通用方法、不就地抽专用方法」是本集合自己的判据化取舍**——通行做法只要求「不必重复手写」，**未**规定去向是通用工具方法而非专用方法。

== 类设计

* **纯数据结构类中不写逻辑**：仅保留字段与简单的字段读写，不做计算、组装、格式转换、对外部对象的访问；需要时下沉到工具类或独立服务。识别特征：以 bean/model/pojo/dto/vo/entity 等命名的类，其方法中出现非字段读写的计算/转换/组装逻辑。
* **配置类不写逻辑（L1）**：各类承载配置的类（如 Spring `@ConfigurationProperties`、`@Configuration`）除声明配置项与按配置装配对象外，**不得包含任何逻辑**——任何情况都不允许，无例外；配置类只保持纯数据对象（POJO）的基本功能（字段及其访问器；`@Configuration` 另可按需声明 `@Bean` 装配方法），需计算/转换/组装时下沉到工具类或服务中。**判定标准**：① 不得出现条件分支（`if`/`switch`/三元等）与循环；② 不得做格式转换、数据加工、对外部对象或远程资源的访问；③ `@Bean` 方法须是「构造/装配」形态——构造依赖由容器注入、不得自行查找（如 `getBean`），装配只允许配置项到构造参数的传递（取值时按「表达式与调用写法」用工具方法或语言内置写法，不写分支、不做计算）。识别特征：以 Config/Properties/Options/Settings 等命名的类。

**存量处理**：本条严于框架常规用法（随动迁移，见 `specs/core/execution.adoc`）。
* **有开关控制的逻辑**：先判断开关，开关关闭时直接跳过，不在开关外做耗时操作（取时间戳、拼字符串、访问外部资源）；开关关闭即零成本。识别特征：布尔配置项之后接的代码块，整段逻辑应包在开关判断内，或开关判断前置 `return`。
* **工具类不继承另一个工具类（L1，任何语言）**：承载**通用静态工具方法**的类（下称工具类，各语言里以 `Utils`/`Util`/`Helper` 一类命名、只放静态方法的类）**不得继承另一个工具类**——不得以 `extends`/`:` 继承、也不得让一个工具类派生自另一个工具类；**继承链里不得出现两个工具类相邻**。

**理由**：工具类的能力面应当是**平铺、可按名直接找到**的一组静态入口——一个抽象基类把「哪些方法从哪来」藏进继承链后，调用点读到的方法不属于它自己的类、搜索与跳转都落不到定义处，同一个方法还会随继承关系出现多个可达路径；而工具类本就**无状态、无多态**（不需要被按父类型使用），继承能给的只是「少写一次签名」，换来的是一层**隐藏的、只增不减的**耦合（改基类即改全部子类）。**工具类的公共部分用两个入口收敛**：① **组合**——把公共逻辑放进**被调用的那个工具类**，由另一处工具方法直接调用它；② **静态导入**——同语言支持时按名直接引用。**判定标准（任一命中即违规）**：① 被继承者与继承者都是工具类（不论继承者是否另加了方法、是否为 `abstract`）；② 以「公共方法抽到基类里」为由建工具类基类；③ 以前缀、导入清单或「方法都还调得到」为由不处理。

**边界（L2，防反用）**：本条**只管工具类之间的继承**——非工具类的正常继承（模板方法、抽象基类、框架基类）、以及工具类**实现接口**（如 `Comparable`、框架要求的回调接口）不受本条约束；工具类里对一个**第三方工具库同名类**的扩展/对应类（如 JDK 静态类的补齐类）按项目既有约定处理，不据此改名或改建。

**存量边界（L1）**：**既有这类继承**保持原样，改到哪处才顺带调整；**不得**据此发动全库改造（批量拆基类、批量挪方法）（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性、可分析性——能力面须可直接定位）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Effective Java「组合优于继承」（继承是「实现复用」的捷径，但把复用写进类型层级后即锁死演进）。**「工具类不得继承工具类」是本集合自己的判据化取舍**——通行材料只给「组合优于继承」的方向，未把工具类单列。
* **没有多态时不得为 service 类加同方法父接口（L1，任何语言）**：一个 **service 类**（承载业务逻辑的服务实现类，控制器调用的那一层）**只有它一个实现**、且没有人按父类型使用它时，**不得**为它另建一个**声明了同样的方法**的父接口——即不为「接口 + 唯一实现」这种两件套而建接口：类上写 `implements XxxService`（或各语言的等价形态）、接口里逐条重复该类的公开方法签名，属本条禁止面。**「没有多态」的判据**：本次改动里**只有一个实现类**实现该接口，**且没有任何注入点、参数、返回值或集合以该接口类型声明**（注入/声明全用实现类本身即命中）。

**理由**：接口的全部价值是**让调用方只依赖契约、由多态决定跑哪一份实现**——没有第二个实现、也没有调用方按父类型依赖时，接口**不承担任何替换与解耦**，能给的只剩「多一个文件、多一份方法清单」；而这份清单还会与类**逐条重复**，改方法即改两处（漏一处则编译不过、看着像"有保障"，实际只是把同一次改动抄两遍），读的人却要在两个文件之间来回对照才能知道这个方法到底是干什么的。**没有多态时的去向是「直接用该类」**——需要区分能力面时用该类的**自己的一组成员方法**表达，不为凑形态而拆接口。

**例外（L2，须写清理由并说明用了哪一条）**：① **存在（或本次一并引入）第二个实现**，或接口是**实现方按契约提供、由调用方按父类型取用**的场合（如 Spring Data 仓储接口这类**框架由接口生成实现**的契约、声明式 HTTP 客户端契约、RPC 服务契约）——这些接口的**实现不写在本次代码里、父类型本来就成立**，不受本条约束；② **接口上挂了框架能力**（事务/校验/代理/切面等注解或框架按接口生成代理的能力）；③ **该处已有先例**（本项目同类 service 一律「接口 + 实现」成对出现）时跟随先例，**不为此把已发布的接口删掉**。

**判定标准（任一命中即违规）**：① 新增（或本次重构新抽出）的 service 接口**只有一个实现类**，且**没有任何注入点/参数/返回值/集合以该接口类型声明**，接口成员与该实现类的公开方法**一一对应**；② 以「面向接口编程」「以后可能换实现」「团队规范这么写」为由自我豁免，而未落到例外；③ 把本条读成「所有接口都不能有唯一实现」而删掉上面例外清单里的契约（**反向误用**：框架由接口生成实现、或接口上挂了框架能力的，不属本条禁止面）。

**边界（防反用）**：本条**只管 service 类的父接口**——工具类、数据对象、枚举、异常类不受本条约束；也**不规定**已有接口必须删除（见下条存量边界）。**「父接口」指被实现的那个接口**，service 类实现框架要求的回调/标记接口（如 `Serializable`）不在本条核对面内。

**存量边界（L1）**：**既有这类接口**保持原样，改到哪处才顺带处置（该处正好重构到、且确无多态时，可并入实现类）；**不得**据此发动全库改造——**批量删接口、批量把注入类型改成实现类**都属此列（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：同一份方法清单只有一个来源）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Robert C. Martin《Clean Code》与 Martin Fowler《Refactoring》（抽象应当由**实际存在的多个实现或替换需求**驱动，而不是为形态而建）、SOLID 的接口隔离原则（契约的价值在调用方只依赖所需能力，无调用方依赖时契约为空转）。**「没有多态时不为 service 类加同方法父接口」是本集合自己的判据化取舍**——通行材料只给「面向接口编程」的方向，**未**规定唯一实现且无人按父类型依赖时该不该留接口。
* **原则上不允许使用内部类**，除非无法代替（回调/监听器、临时组合数据、实现局部接口等确需承载的场景）；能抽为独立顶层类的应抽出去。

== 命名与代码质量

* **NPE 原则**：NPE 问题原则上必须修复（存在取舍时在代码注释中说明取舍依据与边界）。
* **兼容性与平衡**：不因局部小优化牺牲兼容性（语言/运行时版本、操作系统、环境依赖等）；优化与健壮性、可维护性、实用性之间保持平衡。
* **接口/类/注解成员排序**（大小 + 时间 + 复杂度，可同处一个类）：① **按大小**——字段/方法按可存储数据大小/位宽顺序排列（整数按位宽递增、浮点按位宽递增、再 boolean、最后 Object）；② **按时间**——存在逻辑时序时按流程先后、数据加工顺序排列；③ **按复杂度**——简单的在前、复杂/组合/高级用法在后。**不按使用频率、字母序或历史追加顺序随意摆放**。
* **成员与方法次序（L1，任何语言）**：**新增**成员/方法/函数时，其**位置**按「**流程次序**」定——**调用方在前、被调用方在后**（**先初始化的在前**、**先被用到的在前**、**被依赖者在前**：后面的依赖前面的，如 `RestTemplate` 依赖 `ObjectMapper` 时 `ObjectMapper` 排在前）；允许把新增的方法加在**已有成员的前面（含最前面）或中间**，**不得**为「不动已有顺序」而一律追加到类/文件末尾。**重载成员**（同名不同参数）**一律紧邻已有同名成员**（与它相邻），**重载之间的次序同样按流程次序**。**例外（L2）**：① **数据转换方法**（把数据库实体与返回模型互转的那一类）**默认写在查询它的那个接口/方法之后**——**先把查询写出来、再写转换**，不按「被调用者在前」把它提到查询方法**之前**；② 成员次序**决定语义时**（初始化顺序、字段依赖、语言/框架规定的执行顺序）以语义正确为准，本条不适用。

**理由**：位置本身表达「谁先谁后」，读者按读序就能建立流程与依赖链；按「改动追加在末尾」摆放时，同一个类里会出现**多套互相无关的次序**（历史追加序、字母序、随手序），且**新增的位置不报错**、只是次序无声漂移。**判定标准（任一命中即违规）**：① 新增成员被一律追加到类/文件**末尾**，而按其流程次序本可在其他成员**之前或之间**；② 新增成员的调用方排在它**后面**、或它依赖的成员排在它**后面**（如把 `RestTemplate` 写在其依赖的 `ObjectMapper` 之前）；③ 新增**重载**成员与已有同名成员**不相邻**（被别的成员隔开）；④ 数据转换方法排在其**查询接口之前**；⑤ 以「不改动已有顺序」为由自我豁免、把位置选择推给读者。

**边界（防反用）**：本条**只管新增成员的落点位置**——**不要求**为满足本条而**重排**既有成员（那是「存量边界」）；也**不**据此评判既有代码的次序。

**存量边界（L1）**：本条**只对新增成员生效**，**不改动**既有成员的位置，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）；review 时对既有成员的位置不提出问题（全局口径见 `specs/general/review.adoc`「review 的默认检查面」，本条不复述）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：位置即次序信息，同一处不产生第二个次序来源）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Google Java Style Guide 3.4.2（成员次序须是**逻辑次序**、维护者能解释，且**禁止**「新方法习惯性追加到末尾」这类「按加入日期」的次序）。**「按流程次序、可插前面或中间 + 重载相邻 + 转换跟随查询」是本集合的判据化取值**——Google 只禁止「追加在末尾」这一形态、未规定具体落点次序。
* **静态字段排在类最前（L1）**：类中的**静态字段一律排在类体最前面**——在所有实例字段与方法之前，作为整类共享的常量/状态集中可见。**例外（L2，仅此一条）**：某静态字段被**某个方法**直接使用时，允许把它放在**该方法的紧前面**（相当于插在方法之间），使"定义与唯一使用点"相邻；**放与不放都合规**——未这样放**不构成问题**，不得据此判违规（开发者自主决定）。**边界**：例外只放宽**位置**，不放宽"静态字段优先于实例字段"的次序本身；一处静态字段只能有一个位置，不得为迁就多个使用点而复制或反复挪动。**存量边界**：改到某类时才顺带调整其成员/注解次序，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）；某语言**没有静态成员概念**（如纯函数式语言）时本条自然不适用
* **实体类字段按数据库顺序（L1，任何语言）**：映射数据库表的**实体类**（以该语言的持久化映射方式标注——如注解、装饰器、映射声明/映射文件，或项目约定以 entity/model 命名并对应数据表的类）的**字段顺序跟随其映射表的列顺序**（以建表语句/迁移脚本/映射声明中的列序为准），不套用上面的通用次序——便于与表结构、DDL、查询结果逐列对照。**本条覆盖**通用成员排序中"字段次序"的部分；实体类的**注解次序**、**方法的排序**仍按通用规则。若映射表列序无法确定（如由 ORM 自动建表且无显式列序），退回通用次序。
* **链式赋值顺序随字段顺序（L1，任何语言）**：**链式调用**（含 builder 链）里的**赋值环节**（代码里给字段赋值的那些环节，如 lombok 链式 setter、builder 的 `.xxx(...)`），**书写顺序须与字段顺序一致**；**字段顺序**取该条已定义者——**实体类**按「实体类字段按数据库顺序」取映射表的列序，**其他类**按「接口/类/注解成员排序」取该类的成员次序。

**理由**：字段次序是这类对象上唯一已经定下的次序，赋值再排一个序就是同一份字段清单的第二个来源——按字段顺序走，读的人不必回看类定义即可与字段、表结构逐项对照；否则同一次构建里会出现两种次序，且只改了字段、忘了赋值处时**不报错**、只是次序无声漂移。**判定标准（任一命中即违规）**：① 同一处构建的赋值环节次序与字段顺序不一致（含按字母序、按使用频率、按改动追加的次序）；② 以「这样读起来更顺」「顺手先设这两个」为由自行排列；③ 把「字段顺序」读成「本条的专用顺序」而不回指上两条（那等于本条自成第二个来源）。

**例外（L2）**：① 赋值环节的**执行次序决定语义**时（后一次赋值覆盖前一次、后设的值依赖前设的值）以语义正确为准，本条不适用；② 只赋值其中一部分字段、或同一字段赋值多次时，**按所选字段在字段顺序里的相对先后**核对，不要求把它们排成连续的一段。

**边界（防反用）**：本条**只规定赋值环节的书写次序、不改变求值语义**，也不要求为满足本条的次序而多写一次赋值或拆成多个中间变量。

**存量边界**：改到哪处才顺带调整该处的次序，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：同一份字段清单只有一个次序来源）、ISO/IEC/IEEE 29148（判定须可验证）、Google Java Style Guide 3.4.2（成员次序须是**逻辑次序**、维护者能解释）、《阿里巴巴 Java 开发手册》（按表结构逐列对照属通行做法）。**「赋值顺序随字段顺序」是本集合的判据化取值**——通行风格指南未规定赋值次序须跟随字段次序。
* **注解/装饰器排序（L2）**：同一目标（类、字段、方法、参数等）上叠加**多个注解**时，**先比重要性、重要的排在下面**——重要性按以下次序判定（上者更重要）：① 影响**数据存储/持久化映射**的（`@Id`、`@Column`、`@TableName`）——**数据库/持久化注解一律排在最下面**（本条最重要的约束：与库表结构相关的注解除外，其余注解都在其上方）；② 影响**对外契约/序列化**的（`@JsonProperty`、`@ApiModelProperty`）；③ 影响**校验/约束**的（`@NotNull`、`@Valid`）；④ **框架注入/装配**的（`@Autowired`、`@Bean`）；⑤ 余下的**生成/工具类**注解（lombok 的 `@Data`、`@Builder`）。**重要性相同时再比名长**——**名字短的在上面、长的在下面**；**长度只算注解名本身**（如 `@Data` 算 `Data` 四个字符），**不含其后的属性/参数列表**。**次序完全确定**：先比重要性（重要在下），重要性相同时再比名长（短在上）——两步即可唯一定序，无歧义。**同档次内不得按名长跨档插队**：同档注解之间才比名长——`@NotNull`（档③，名长 7）属校验档，仍排在建档②的 `@JsonProperty`（名长 13）**下面**，不得因为名字更短而越过档位。**数据库优先于名长**：`@Id`（名长 2）虽短，仍因属①档而排在 `@Data`（名长 4）**下面**；不得以「名字更短」为由把数据库注解提到上面。**本条的运行前提**：注解次序不影响语义——若某语言/框架**对注解次序敏感**（有先后依赖、后者覆盖前者），**以语义正确为准**，本条不适用。
* **注解/装饰器属性排序**：① 与数据存储字段顺序保持一致（主键/必填在前）；② 常用/必传属性在前，省略属性名时默认赋值的属性排最前；③ 其余按使用频率或逻辑顺序排列。
* **Feign 接口命名带所属域/项目前缀（L1）**：**Feign 声明式 HTTP 客户端接口**（本次**只此一类**，REST Controller、RPC 服务契约等**其他对外接口**不适用、不据本条改名，也不得据此扩张判定面）命名须为「**前缀 + 接口业务名 + `Api`**」，前缀由**接口所属的域/项目**决定——**先取该域已存在的固定前缀（先例优先）**，没有先例才按项目名取词首字母组合（`user-center` → `Uc`、`open-user-center` → `Ouc`，即 `UcUserApi`、`OucUserApi`）。**判定（任一命中即违规）**：① 所属域已有固定前缀却另取一套；② 同类接口有的带前缀有的不带；③ 把业务名或所属服务全名当前缀（如 `UserCenterUserApi` 一类**拼全名**的写法）。

**存量边界**：不发动全库改名（存量口径见 `specs/core/execution.adoc`）。Java 落点见 `specs/stack/java.adoc`「命名」。
* **接口/抽象类的实现类命名**：实现类应有**标识性名字**（体现具体实现方式/策略/用途），接口/基类使用简单名字；除非实现类是继承链中的一环，否则各实现类严禁同名。
* 依据（标准名/编号）：**成员与注解排序**一条为**本集合自身的判据化取舍**——Google Java Style Guide 3.4.2（Ordering of class contents）明确指出成员次序"**没有唯一正确的配方**"，只要求"每类使用某种**逻辑次序**、维护者能解释即可"，并禁止"按追加时间堆在末尾"；阿里巴巴 Java 开发手册亦无"静态字段必须在最前"或"注解按名长排"的明文。故"静态字段在类最前""实体类按数据库列序""链式赋值顺序随字段顺序""注解先按重要性（数据库映射注解在最下）、同重要性再按名长升序"四条是**本集合在上述"须为逻辑次序"的下限之上自定的更严取值**（理由是"整类共享状态集中可见""与表结构逐列对照""同一份字段清单只有一个次序来源""数据库关注点收尾扫读"），**不得**读成某标准的规定。**须注意的语义差异**：Google 只要求"逻辑次序"，未规定具体次序（**也未**规定赋值环节的书写次序须跟随字段次序）；本集合给出具体次序，属**加严**，且已按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**（不发动全库重排）。

== 日志

* **禁止控制台打印**：不允许直接输出到控制台（`System.out.println`、`console.log` 等）；需要输出日志时统一使用日志框架。控制台打印仅限明确需要控制台展示的独立场景（如性能测试，且应同时写入文件报告）。
* **日志分级记录**（便于调试排查）：各环节**关键节点**（方法入口/出口、流程步骤、分支去向、中间结果）应打日志记录运行轨迹。**辅助排查的细节**（关键输入/输出、中间状态、分支取舍）用 **debug**——默认不打印；**需注意的事项**（异常、边界兜底、非预期但可处理的场景、重要状态变更）用 **info 及以上**。**不得因"代码重要就省略日志"导致难排查，也不得为省事全打 info 刷屏**。
* **不打无意义日志**：日志打在**关键节点**即可——空方法/空实现不打；有开关启用的逻辑、开关不启用时一般不打；为打而打不如不打。
* **日志属性打印格式**：打印属性（key/value）**不包双引号**，格式为 `key: value`；常规用**半角冒号 `:` + 空格**（`userId: 123`），当 key 或 value 为**纯中文**时用**全角冒号 `：` 且不加空格**（`用户ID：登录成功`）。异常日志须将 throwable 作为最后一个参数传入（`log.error("msg: {}", arg, e)`），不得拼 `e.getMessage()`。

== 注释

* **注释的形式与承载位置**：面向结构的说明用什么机制写、详细设计写在哪一层、没有文档注释机制时退回什么形态、脚本的例外，**判据的唯一落点在本节**（`specs/general/doc.adoc`「注释与文档」管**内容与承载层**：哪些内容必须记录、写在文档注释还是独立文档；**形式**规则不在那边另写一份——两处各写一遍时，改一处必漏另一处）。
* **代码注释的内容下限（放错层会同一件事写两遍）**：**结构说明用文档注释、普通注释只写方法体内的局部实现**（为什么这样写、局部决策、边界取舍）；**详细设计（参数、返回值、异常、边界、默认值、空值语义、易误用点、已知缺陷、性能、线程安全）写进源码的文档注释、不另建独立文档**（落层判定见 `specs/general/doc-design.adoc`「信息归属」）。
* **脚本的落点与粒度（脚本例外）**：脚本默认**脚本单打独斗**、文档随脚本落盘、不逐脚本另建独立文档（**不允许一个脚本对应一个文档**），承载方式按**多行文档注释 → 多行普通/块注释 → 普通注释**的优先级取值（判据见 `specs/general/script.adoc`「脚本文档的承载位置与协作粒度（默认写进脚本自身）」）——**这是"普通注释仅限方法体内"的唯一例外**。

== HTTP 接口语义（对外提供或调用 HTTP 接口的项目）

**适用范围**：项目**对外提供或调用 HTTP 接口**时适用（无 HTTP 接口的项目不适用）。与语言、框架无关的**协议语义下限**；框架专名与路由写法见 `specs/stack/` 对应文件。

* **安全方法不得产生状态变更（L1）**：`GET`、`HEAD`、`OPTIONS`、`TRACE` 是**安全方法**（语义为只读）——**不得**用它们承载写、删、状态流转等有副作用的动作（如 `GET /order/delete?id=1`）。**判定标准（任一命中即违规）**：① 路由以安全方法映射到会改动服务端状态的处理逻辑；② 把有副作用的动作放进查询参数、由 `GET` 触发。**理由**：自动化抓取（爬虫/链接检查）与预取会自行遍历链接，被 `GET` 触发的副作用会在无人操作时发生（依据：RFC 9110「Safe Methods」）。
* **幂等语义与重试须对齐（L2）**：`PUT`、`DELETE` 与安全方法是**幂等方法**，`POST` **不幂等**。判定标准：① 把非幂等请求配成自动重试；② 按"哪个方便"选方法（用 `POST` 做纯读取、用 `GET` 做写入）（依据：RFC 9110「Idempotent Methods」）。
* **状态码按语义使用（L2）**：用状态码表达结果类别——成功 `2xx`（新建 `201`、无内容 `204`）、重定向 `3xx`、客户端错误 `4xx`（`400`/`401`/`403`/`404`/`409`）、服务端错误 `5xx`。**不得**把错误一律包成 `200` 再在响应体里写失败标记（那样重试、缓存、监控与网关策略全部失效）。**判定标准**：出现"HTTP `200` + 响应体 `success:false`"这类本可用 `4xx`/`5xx` 表达的错误即违规（依据：RFC 9110「Status Codes」）。
* **对外错误响应统一结构（L3，可选）**：对外 HTTP API 的错误体**可以**统一为 Problem Details 结构（成员 `type`/`title`/`status`/`detail`/`instance`，媒体类型 `application/problem+json`）；**结构里不得放入堆栈、SQL、内部路径等内部细节**（见 `specs/general/security.adoc`「敏感信息」；依据：RFC 9457）。
* 依据（标准名/编号）：RFC 9110（HTTP 语义，STD 97）、RFC 9457（Problem Details for HTTP APIs，已取代 RFC 7807）。

== 代码质量（新产出即高质）

功能写出来了不等于做完了——**同一件事，功能一致、质量可以差一个量级**。本节约束**新写的与本次改到的代码**（存量随动迁移），给出可逐条核对的**质量下限**：达不到即视为**未完成**。

* **适用面（先读）**：**写任何新代码、改任何既有代码**时适用；**代码评审**时按本节逐条核对。存量不在强制面内（改到哪迁到哪），但**新增的那一部分永远按本节判**。
* **新代码不得引入坏味道（L1）**：不得把已知坏味道写进新代码——重复代码、过长函数（一屏读不完）、过长参数列表、发散式变化（改一个需求要同时改多处）、霰弹式修改（一处改动散落几十个文件）、依恋情结（频繁访问他类内部数据）、数据泥团（总是一起出现的字段反复成组传递）、基本类型偏执（用裸字符串/裸数字承载领域概念）、被拒绝的遗赠（继承但用不上父类大部分能力）、注释代替澄清。**判定标准（任一命中即违规）**：① 同一段逻辑在本次改动里出现两次及以上而未抽离；② 一个函数需要靠注释分段才能读懂；③ 新增分支靠继续加 `if/else` 而不是抽出策略/多态；④ 新增字段只是为了让某处 `if` 多一个条件。依据：Martin Fowler《Refactoring》、Robert C. Martin《Clean Code》。
* **职责单一、结构清晰（L1）**：一个函数/方法/类只做一件事（"能不能用一句话说清它做什么"是判据）；函数体优先**线性可读**；嵌套层级控制在**三层以内**（`if`/循环/`try` 叠加计层），超过即先抽方法或提前返回；**不得**写超长 god method。**判定标准**：一句话说不清职责 / 嵌套数超过三层 / 需要通过 goto 式跳转才能读完——任一命中即违规。
* **命名表意、不用缩写（L1）**：命名须**表意**、**全文一致**（同一概念在项目中只有一个叫法）；**禁止**无共同认知的缩写、单字母（循环下标等惯用短名除外）、拼音、数字后缀（`data1`/`newService2`）、以及"能看出类型看不出用途"的名字（`map`、`list`、`temp`）。**判定标准**：出现需靠读实现才知道含义的名字 / 同一概念两种叫法 / 用缩写牺牲可读性——任一命中即违规。
* **可读性优先（L1）**：优先**直白**写法，不为"短"牺牲可读——不写多重嵌套三元、不在实参位置内联复杂表达式与对象构造、不用无意义的魔法值；**同一表达式不重复求值、同一判断不重复书写**。判据与既有条款见上「表达式与调用写法」。
* **显式处理失败与边界（L1）**：**不得吞异常**（`catch` 后空实现、只打日志不处理、`except: pass`）；异常须处理或按契约向上抛；**边界条件必须显式处理**（空集合、`null`/`nil`、0 与负数、超长与超大、并发与重入），不以"调用方会传对"为前提；对外输入一律校验（见 `specs/general/security.adoc`「输入与输出」）。**条件例外（L2，把"查不到 → 取默认值"这类纯取值转换写成空 `catch`）**：只在该 API 的**异常只有一种原因**（**查找内容不存在**，不含任何失败）且调用方**以该查找的默认值为业务语义**时成立。**三条同时成立才算命中、缺一即回到 L1**：① **异常语义单一**——该 API 的异常只可能表示"查找内容不存在"，参数非法、状态非法、IO/资源/权限失败等一切真失败**另有出口**（返回"没有"值、单独异常，或调用前显式校验）；② **取不到即无值**——返回值就是"没有"的表示，无需另补兜底动作；③ **默认值取自同一 API 的返回值**——使顶层调用处"仍须处理失败"这一契约不受影响；**且该处须写明"异常只有这一种原因"的依据**。**判定标准（任一命中即不合规）**：① 该 API 的异常**不止"查找内容不存在"一种原因**（含查找过程中的执行失败），却按本例外空 `catch`；② 调用方**要求失败可见**（超时、不可用须报错或重试、状态变更须乐观锁失败即报错），却仍按"查不到"取默认值；③ 借本例外绕过**可探测的非法输入**（未预先校验就空 `catch`，见 `specs/general/security.adoc`「输入与输出」）；④ 空 `catch` 处**没有写明"异常只有这一种原因"的依据**；⑤ 把本例外扩大到**任何异常的 `catch`**。

**边界（防反用）**：本条**不改变**"不得吞异常"与"对外输入一律校验"的其余部分——命中的调用点**仍是空 `catch`**；该写法是**对例外的显式标注**，不属「注释代替澄清」。各语言的具体落点由技术栈层给出（Java 见 `specs/stack/java.adoc`「健壮性」）。
* **无资源泄漏（L1）**：文件、连接、流、锁、线程池、订阅与监听须成对释放，一律用语言提供的确定性释放机制（`try-with-resources`、`using`、`with`、`defer`、`finally`），禁止依赖 GC 或人工记忆释放。
* **无并发隐患（L1）**：共享可变状态须有明确的同步策略（锁范围与顺序写清，或改用并发安全结构/不可变对象/消息传递）；不得出现可见性缺失、锁顺序不一致（可致死锁）、双重检查未加锁、共享可变对象直接暴露。**判定标准**：共享可变状态无同步策略、或同步策略在代码里看不出边界——命中即违规。
* **性能不写退化写法（L2）**：避开可预见的性能退化——循环内 IO/查询/远程调用、循环内字符串拼接、可预知的 N+1 查询、在热点路径重复创建昂贵对象或重复读取不变资源。**何时需要实测数据**按 `specs/general/testing.adoc`「性能测试」判定。
* **测试与文档跟得上（L1）**：新功能**必须**配测试；本次改动相关面的既有用例不得为迁就改动而改判；结构说明、契约与边界写进该语言的**文档注释**。**判定标准**：新功能无对应用例 / 有行为改动而未同步文档——任一命中即违规。
* **交付前质量自检（L1）**：交付前对新代码逐条自查本节十项（坏味道 / 职责与嵌套 / 命名 / 可读性 / 失败与边界 / 资源 / 并发 / 性能 / 测试与文档），答不上"逐项怎么过的"即视为未过；**能过机械判据是下限、不等于质量过关**。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性、可靠性、性能效率）、ISO/IEC/IEEE 12207（实现过程）、Martin Fowler《Refactoring》、Robert C. Martin《Clean Code》、SEI CERT Coding Standards、ISO/IEC/IEEE 29148。「十项逐条判」是本集合的判据化取舍。
