= 反馈与提示规范（通用层，跨端判据本体）

适用于**任何语言、任何端**的产品：人要能知道"刚才那件事成了没有、为什么没成、现在能做什么"。加载特征：要定**错误提示、信息提示**的文案与形态；要设计**通知与消息**（站内消息、通知中心、角标、订阅）；要定**进度、忙碌、结果回执**；要定**空态与引导**；要设计**接口错误响应**；要判定"这个提示该出现在哪一端、哪一层、以什么形态出现"。

本文件把"信息提示、错误提示"扩成**一个完整的反馈面**：**成功、错误、警示、提示、进度**是同一件事的五种取值，判据必须成套给，否则只做了最容易的那一种（成功），最要命的那几种（错误、危险、超时）各端各写一套。

**取值清单（提示通道选择表、错误码与文案模板、打扰预算取值）不写在这里**：它们是模板文件，见 `specs/general/ui-feedback.adoc`。**文案的用词与语气**在 `specs/general/ui-voice.adoc`，**视觉取值**（颜色、对比度、字号、命中区）在 `specs/general/ui.adoc` 与 `specs/general/ui-tokens.adoc`，**接口的错误体与状态码语义**在 `specs/general/coding.adoc`「HTTP 接口语义」——本文件只补**它们之间那一层**：反馈怎么分类、由哪一层产生、跨端怎么一致、什么算打扰、什么地方必须留痕。

== 本文件的字典（本文件使用的名称，定义写在本文开头）

[[term-feedback]]
**反馈**：系统对"人做了一件事、或系统里发生了一件事"给出的**可见回应**。它有三个必需成分——**发生了什么**（对象与结果）、**现在能做什么**（下一步或结束）、**去哪看更多**（详情、台账、日志入口）。缺任何一个成分的"提示"仍可显示，但不算反馈完成。

[[term-feedback-kind]]
**反馈的五种取值**：**成功**（做成了，是什么）、**错误**（没做成，为什么、能不能重试）、**警示**（正在走向错误，尚未失败：配额将满、连接不稳、数据可能过期）、**提示**（与当前任务无直接因果的信息：新功能、他人改动、系统公告）、**进度**（正在做，还要多久、能否中断）。**"信息提示"与"错误提示"不是两类东西**，是本清单里的两项；警示与进度常常是**同一个动作的前后两拍**（重试前的等待、失败前的降级）。

[[term-layer]]
**层**：反馈的**产生者**，不是显示者——**后端接口层**（校验、业务规则、服务端失败）、**前端/客户端应用层**（编排、重试、会话、离线）、**界面呈现层**（字段、区块、页、全局通道）、**外部通道层**（邮件、短信、推送、IM 机器人）。一条反馈自下而上**只升一层**、并可被上层**改写呈现**，但**不得被上层改掉语义**（`409` 不得在某端显示成"网络错误"）。

[[term-channel]]
**通道**：反馈**出现在哪里**的具名形态——字段旁、页面顶部横幅、页内区块、全局轻提示、通知中心（站内消息台账）、系统通知（客户端/移动端推送）、对话框、整页结果页、日志与服务端台账。同一类反馈在不同通道出现时，**内容可以变短、语义不能变**。

[[term-budget]]
**打扰预算**：主动打断用户的反馈所受的限额——**一次一屏至多一条打断型提示**、**同类提示按对象合并**、**可重复出现的提示要能"不再提示"**。打断型指需要人**停下当前动作去看**的形态（对话框、需要人点的横幅、系统通知）；页内就地出现、不夺焦点的不计入。

[[term-receipt]]
**回执**：一次**已经离开当前界面的操作**（提交、导出、批处理、异步任务）留下的、**事后可查的凭证**——任务编号、结果、失败项与原因。回执是"提示过"与"真的做完了"之间的那一层，缺回执的异步操作等于把结果交给运气。

== 与其他判据的分工（先读，防两套判据并存）

* **接口返回什么结构、用哪个状态码** → `specs/general/coding.adoc`「HTTP 接口语义」（其中"对外错误响应统一结构"那一条给的是下限；本文件给它**上层的分工与可机读要求**）
* **文案怎么写、语气怎么定、五种状态各写什么** → `specs/general/ui-voice.adoc`（本文件判**这条文案该不该出现、出现在哪个通道、能不能消失**）
* **提示长什么样、什么颜色、多大、对比度够不够** → `specs/general/ui.adoc` 与 `specs/general/ui-tokens.adoc`
* **哪些内容不得出现在提示里**（堆栈、SQL、内部路径、口令、个人信息） → `specs/general/security.adoc`「敏感信息」与 `specs/general/desensitize.adoc`
* **服务端记什么日志、分级怎么取** → `specs/general/coding.adoc`「日志」

**边界**：本文件**不规定**具体产品的提示词与配色（那是各项目自己的文案与令牌资源）；也不要求给**每一次**内部函数调用配提示——**反馈只出现在人可见的边界上**（人的操作、异步结果、跨会话的事件）。

== 总纲：五类反馈成套、四层分工、一处登记（先定这三件）

* **五类反馈成套给、不得只做成功一种（L1）**：同一份功能须为**成功、错误、警示、提示、进度**各给出**写出来的**形态与文案（不适用的类别要写明"本功能不产生此类"，而不是留空）。**判定标准（任一命中即违规）**：① 只有成功与错误的文案，警示与进度靠"转圈"代替；② 错误类别里只写了"网络错误"，没有业务规则失败、校验失败、权限不足、超时与不可用这几类；③ 进度只有"加载中"一种，没有区分短等待与可中断的长任务。

* **反馈按层产生、按层呈现，语义不得跨层走样（L1）**：每条反馈须写明**由哪一层产生**（校验/业务/服务端失败/编排/呈现）；上层**只负责换通道与压缩长度**，**不得改写语义**，也不得把两种原因合成一种。**判定标准（任一命中即违规）**：① 后端返回的稳定错误码到了某一端被映射成另一个意思（`409 已存在` 显示成"网络异常，请重试"）；② 同一条失败在两端分别归属不同层（一端判定为校验、一端判定为服务端错误）；③ 前端把后端错误一律替换成自己的兜底文案，丢掉了原错误码。

* **一处登记：错误码与提示文案同一张表（L1）**：所有**人可见的错误**须落在**一张错误码表**里（机器码、HTTP 状态、面向人的标题与说明、可重试与否、下一步动作、所属层），文案从**文案资源一处**取，代码只引码。**判定标准（任一命中即违规）**：① 代码里出现"临时拼一段人话"的错误消息，且同一原因在别处另有文案；② 同一个错误原因在两端各有一份文案、措辞不同；③ 错误码只在后端有，前端靠匹配 message 文本判断类型（文案改一个字就崩）。

**依据方向**：可机读的错误标识是**接口契约的一部分**，不得以人的可读文本充当分支判据（Microsoft REST API Guidelines 把错误码字符串列为"不能变"的契约项，并明确"不要解析 message"；RFC 9457 亦规定客户端**不应**解析 `detail`）。

== 错误与失败：三句话 + 可机读契约 + 可行动性

* **错误说清三件、并且给出出路（L1）**：面错人的错误文案须含**发生了什么**（对象与结果）、**为什么**（可判定的原因类别，不是"系统繁忙"）、**现在能怎么办**（重试、换一条路、改输入、找谁）。**不可恢复**的错误须给出**求助路径**（联系谁、带上什么标识）。**判定标准（任一命中即违规）**：① 出现"操作失败""出错了""系统错误"而无原因与出路；② 可重试的错误没有重试入口，或不可重试的错误却给了"请重试"；③ 需要人找支持的场景没有给可复述的标识（请求号、任务号）。

* **错误按"人能不能自己解决"分类，不按状态码分类（L1）**：每条错误须归入**可自助**（改输入、换操作、重试即可）、**需等待**（限流、超时、维护中——须给时间预期或"稍后从这里回来"）、**需他人**（权限、审批、数据由他人维护）、**不可恢复**（须联系支持并带上标识）四档之一；**这四档决定通道与文案，不决定 HTTP 状态码**（状态码按 `specs/general/coding.adoc` 的语义）。**判定标准（任一命中即违规）**：① 把"需他人"的错误写成"请重试"；② 把"需等待"的错误做成需要人反复手动刷新的死循环；③ 同一原因在不同页面归到不同档。

* **可机读的部分与给人看的部分分开（L1）**：错误响应须同时给出**稳定标识**（错误码/问题类型）、**定位**（哪个字段/哪一条记录/哪一步）、**可重试性**（是否可重试、多久后可试）、**追踪标识**（请求号/任务号）；给人看的措辞**只由前端按文案资源渲染**，后端不回一句"给人看的最终句子"作为唯一依据。**判定标准（任一命中即违规）**：① 只有一段人话、没有稳定标识；② 校验错误不给字段定位（只给"参数错误"）；③ 可重试的错误不给重试提示（`Retry-After` 一类）而让人猜。

* **校验错误就地、批量、逐字段（L1）**：表单校验错误挂在**该字段处**，**一次给全**（不要"改一个报一个"），并给出**怎么改**；页面顶部的汇总**只能作为补充**、且能跳到字段。**判定标准（任一命中即违规）**：① 只有顶部汇总、字段处无标记；② 一次只报一个错误；③ 只说"格式不正确"而不说期望的格式或范围。

* **服务端异常不得把内部细节当提示（L1）**：堆栈、SQL、表名、内部路径、主机名、依赖名一律不出现在**任何**人可见通道；这些只进服务端日志，人看到的是一句什么坏了 + 追踪标识。**判定标准**：任一通道（含客户端弹出的对话框）出现上述内容。**与安全判据的关系**：本条的判定动作以 `specs/general/security.adoc`「敏感信息」为准，本文件只管"它出现在提示里"这一形态。

== 成功、警示、提示、进度：最常被漏掉的四种

* **成功回执写"做成了什么"，并在离开页面后仍可查（L1）**：成功提示须写清**对象与范围**（"已保存 3 条草稿"而不是"操作成功"），且**不得只靠一闪而过的轻提示**承载结果——**会离开当前界面的操作**（提交、批量、异步、跨页）须在**通知中心或任务台账**留下回执，能从里面**回到结果**。**判定标准（任一命中即违规）**：① 批量操作的唯一结果提示是会消失的轻提示；② 提交后跳走、回来无法确认是否成功；③ 成功文案不含对象与数量。

* **警示要早于失败、并给出可执行的一步（L2）**：警示用于**尚可挽回**的状态（配额接近上限、连接不稳、数据可能过期、即将到期），须写清**还剩多少/多久**与**这一步该做什么**；**不是所有警告都要弹窗**——能用就地标记的地方不打断。**判定标准（任一命中即违规）**：① 只在失败之后才提示"其实早就快满了"；② 警示只有"注意"而无数值与动作；③ 常规可预期的状态用打断型通道提示。

* **提示与当前任务无关的信息要能不被看见（L2）**：功能公告、他人改动、运营信息等**与当前任务无因果**的提示，须**可关、可"不再提示"、且不喧宾夺主**（不占主操作区、不夺焦点）；**不得**用它承载**必须被知道**的后果（那属于成功/错误/警示）。**判定标准（任一命中即违规）**：① 公告占据主流程位置、关不掉；② 用"新功能提示"承载计费或数据变更的后果；③ 每次进入都重复同一条已读提示。

* **进度分两档、长任务可中断可离开（L1）**：**短等待**（预期内、人能等）给**就地忙态**（按钮进忙态、区块骨架）；**长任务**（不可预期、几十秒以上、批处理、导入导出）给**有量纲的进度**（已完成/总数或阶段名），给**取消/后台执行**，并允许**离开页面**——离开后结果进回执。**判定标准（任一命中即违规）**：① 长任务用无限转圈且不能取消；② 整屏遮罩盖住已可用的部分；③ 进度只有"处理中"三个字而没有阶段或量纲；④ 离开页面即丢失任务与结果。

* **忙碌与提交要有防重入（L1）**：提交中控件进入忙态并**不接受第二次提交**；重复提交在服务端**也要幂等或去重**（前端忙态只是体验，不是正确性保障）。**判定标准（任一命中即违规）**：① 提交中按钮仍可点、产生两条记录；② 只靠前端禁用而没有服务端幂等/去重（依据：RFC 9110「Idempotent Methods」）。

== 通道与打扰预算（同一件事只在一个地方打扰人）

* **通道按"要不要就地、要不要留痕、要不要打断"三问取（L1）**：**就地能做**（字段、区块、按钮）→ 就地，不弹；**离开界面后还要能查** → 进**通知中心/任务台账**；**必须立刻知道且不能错过**（不可逆操作的确认、会话失效）→ 才用打断型（对话框、系统通知）。**判定标准（任一命中即违规）**：① 用轻提示承载"必须被知道"的后果；② 就地能解决的问题弹对话框；③ 同一件事同时在三个通道出现（轻提示 + 横幅 + 通知中心各一条，且无主次）。

* **一次一屏至多一条打断型提示，同类按对象合并（L1）**：批量失败**不得**逐条弹窗（那是弹窗风暴）；应合并成**一条汇总 + 可展开的失败明细**，明细能定位到条目。**判定标准（任一命中即违规）**：① 一批 N 条失败产生 N 个提示；② 同一原因在同一屏里重复出现多次；③ 汇总提示里没有"看明细"的入口。

* **打断型提示不得吞掉人的输入（L1）**：提示浮层出现时**不得清空表单、不得重置滚动位置到顶部、不得夺走正在输入的焦点**；阻塞型对话框须**可从键盘操作并回到原焦点**。**判定标准**：出现提示后必须重新填写或找不到刚才的位置。

* **打断要有节制：可关、会自己退、同一条不反复（L2）**：轻提示须**自动消失**（时长按字数与语种留量，见 `specs/general/ui-voice.adoc` 的最长语言要求）、**悬停或聚焦时暂停**（否则读屏与慢读用户读不完）；**同类提示重复出现须合并或折叠**，不得每轮轮询各弹一次。**判定标准（任一命中即违规）**：① 轻提示不消失也不可关；② 鼠标移上去仍继续计时消失；③ 轮询失败每 5 秒弹一次同样的话。

* **可重复出现的提示要能"不再提示"并记住（L2）**：能反复触发的提示须提供**"不再提示"**，且该选择**持久保存**、**可撤销**（在一处能重新打开）。**判定标准（任一命中即违规）**：① 每进一次页面就提示一次同一个引导；② "不再提示"只在当前会话有效；③ 关掉后无处恢复。

== 通知、消息与订阅（跨会话、跨端的那一类）

* **通知中心是台账、通知是投递（L1）**：跨会话的事件须先落**站内台账**（通知中心：分未读/已读、可回原处、可批量已读、有时间与来源），**推送/邮件/IM 只是投递通道**；**不得**只投递而不留痕（那样关掉推送就等于没发生）。**判定标准（任一命中已违规）**：① 关掉推送后事件无从查起；② 通知中心里的条目点不进原始对象；③ 未读状态在两端不一致且无法确定哪个为准。

* **未读数只在一处算、各端同源（L1）**：角标与未读数由**一处**（同一接口/同一规则）算出，各端不得各自统计；**清除未读以"看到哪一条"为准，不以"打开了通知中心"为准**。**判定标准（任一命中即违规）**：① 同一时刻两端角标数字不同且都自称正确；② 打开列表即全部置为已读，导致漏掉未看的条目。

* **投递按事件与订阅分档，且尊重渠道偏好（L2）**：同一事件可走多个通道，但须**按事件类别**（安全/计费类须触达、协作类可聚合、运营类可退订）与**人设定的偏好**决定；**同一事件不得在多个通道重复裸弹**。**判定标准（任一命中即违规）**：① 安全类事件被"免打扰"静默；② 同一事件既弹系统通知又弹窗又发邮件且三者内容重复；③ 没有渠道偏好落点。

== 跨端：内容一致、形态按端、打扰按输入设备

* **文案与语义端间一致、形态与打扰可以不同（L1）**：同一反馈在**所有端**用**同一个错误码、同一套文案键、同一个下一步动作**；端之间只允许改**通道与形态**（移动端用底部提示条、桌面用角落轻提示、终端用一行文本），**不得**改意思、不得**少一类反馈**（移动端没有"通知中心"就是缺功能，须给等价物）。**判定标准（任一命中即违规）**：① 同一错误在两端文案不同义；② 某一端省掉进度或回执；③ 端差异落到"某一端不显示错误码"这种语义层。

* **可访问性是基线、不是加分项（L1）**：**打断型提示**用**中断型语义**（立即播报，如 `role="alert"` 一类），**非打断型提示**用**礼貌播报**（不打断当前朗读，如 `role="status"` / `aria-live="polite"` 一类）；提示**不得只靠颜色**表达级别（须有文字或图标）；**焦点不得被提示抢走**（除用户主动触发的对话框）；**指示进度的元素**须能被读屏读到，且忙态有文字。**判定标准（任一命中即违规）**：① 成功与错误都用同一种播报强度（读屏用户每次都被打断）；② 只用红色表示失败；③ 弹出提示后焦点丢失或跳到页首；④ 进度指示没有可读文本。

* **提示文案要能被翻译、长度按最长语言留位（L1）**：文案取**文案资源一处**（键值），**不得**在代码里拼接句子（语序随语种变化，拼接必然出错）；数量、日期、金额走**本地化格式**与**复数规则**；按**最长语言**留位、**不靠截断**（判据在 `specs/general/ui-voice.adoc`）。**判定标准（任一命中即违规）**：① 用字符串拼接造句子（"共 " + n + " 条失败"）；② 时间/数字直接输出原始值；③ 目标语言下提示被截断或被挤成多行破版。

== 记录与可追溯（提示不是日志，但两者必须对得上）

* **人看到的提示与服务端记录须能对上（L1）**：任何**错误**与**需等待**的反馈，服务端须有对应记录，并**共用同一个追踪标识**（请求号/任务号），使"用户报的这句提示"能被查到那条日志。**判定标准（任一命中即违规）**：① 提示里有追踪标识、日志里查不到；② 日志里没有能对应到一次请求的标识；③ 提示说失败、日志说成功（没有一处能解释两者的差异）。

* **记录不得替代提示（L2）**：把失败**只**写进日志/监控而人界面上什么都不显示，等同于没做（人只会看到"没反应"）。**判定标准**：一次失败后界面上没有任何可见变化。

== 落进项目时的核对清单（按序判，命中即改）

. 五类齐不齐：成功、错误、警示、提示、进度各有形态与文案？不适用的写明了没有？
. 错误表：人可见的每条错误是否都在同一张错误码表里（码、状态、文案键、可重试、下一步、所属层）？
. 三句话：错误有原因与出路吗？可重试的有重试入口吗？不可恢复的给了追踪标识与求助路径吗？
. 分层：后端错误码有没有被某一端改写语义？校验错误是不是就地、一次给全、逐字段？
. 回执：离开界面的操作有台账可查吗？批量失败是汇总 + 明细，还是弹窗风暴？
. 通道：这件事是就地、留痕、还是打断？一次一屏只一条打断型提示吗？
. 打扰预算：轻提示会自己退、悬停暂停、同条可合并、能"不再提示"且可撤销吗？
. 通知：台账先落、投递在后？未读数一处算？角标与已读规则两端同源？
. 跨端：文案键与错误码各端一致？端差异只在通道，不在语义？
. 可访问性：打断型/非打断型播报强度分开？不只靠颜色？焦点没被抢？进度有文字？
. 国际化：文案只从资源取、不拼句子？数量日期走本地化、按最长语言留位？
. 对齐：提示里的追踪标识能在服务端记录里查到吗？
. 敏感：任何通道都没有堆栈、SQL、内部路径、口令与个人信息？

== 依据（标准名/编号）
