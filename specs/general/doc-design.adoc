= 设计文档规范（通用层）

以下规范适用于**所有语言、所有项目类型**（业务项目、工具库、脚本等，按实际情况适用）的文档编写维护——既包括独立的设计文档与测试设计文档，也包括**代码内的文档注释**（javadoc / docstring / JSDoc 等，按语言实际机制）。设计文档记录核心功能的方案、取舍、兜底与适用范围；测试设计文档记录测试行为本身的设计与验证规格（测试是功能的验证规格，二者一体）。业务系统（从立项到上线的完整项目）的阶段级文档组织见 link:../general/doc-lifecycle.adoc[]；**模块内文档**（属某具体模块内部的总结/规划内容；类/方法级细节归代码文档注释）在多模块项目下的组织与归属见 link:../general/doc-module.adoc[]。注释/记录的通用原则见 link:../general/doc.adoc[]。

== 设计文档

* 设计文档：核心功能的新增、重构（含行为变更、方案选型、有取舍的设计）必须编写或更新设计文档，记录当时考虑到的所有东西：功能设计（方案是什么、为什么这样做、备选方案及不选原因）、测试设计（测试行为本身的设计：测试架构与组织、测试手法与参考实现、覆盖哪些场景、为什么这样测、测试边界与取舍）、兜底（有哪些兜底、兜底触发条件与边界）、适用范围（适用场景、不适用场景、已知限制与取舍）；功能设计与测试设计放在同一设计文档内（测试是功能的验证规格，二者一体，避免文档分散）；**承载位置可迁移、内容要求不降低**：设计文档承载总结性、规划性内容（模块/功能粒度），不必逐类/逐文件另建文档——**类级与方法级描述进代码内的文档注释**（javadoc / docstring / JSDoc 等，按语言实际机制，见「信息归属」）；**这只是承载位置的变化——要求记录的文档内容一项都不能少，不得减少、省略或"对付"式补写**，总体要求比以往**更严格**（描述须写到代码可及的文档注释中并随代码同步）；文档按模块建立子目录存放：**多模块项目**中，模块内文档放各模块自己的 `doc/` 目录内（`<各模块>/doc/`，组织与归属见 link:../general/doc-module.adoc[]），**不进根 `doc/`**；**业务系统**中：单模块项目置于设计阶段目录下的 `<模块>/` 子目录（如 `doc/<设计阶段>/<模块>/`），多模块项目一律按前者放各模块 `doc/`（见 link:../general/doc-lifecycle.adoc[]）；模块名取核心功能/组件所属模块（如 `core`/`web`/`feign`/`log`，以各项目实际模块划分为准）；**文档命名须与源文件一致**——**仅当成篇文档确实对应到某个具体的代码/脚本/类文件时**，文档名取该源文件名（去掉扩展名）加 `.adoc`，使文档与源文件同名便于查找阅读（如 `Foo.java` → `Foo.adoc`、`check_specs.py` → `check_specs.adoc`）；独立成篇的测试设计文档若对应具体测试类，取该测试类名（如 `FooTests` → `FooTests.adoc`），`Test`/`Tests` 等后缀由源文件自身命名决定、规范不统一改写；**命名风格完全跟随源文件**——源文件是驼峰则文档用驼峰、源文件是中划线则文档用中划线，不得另起命名风格；AsciiDoc 格式；文档随代码演进同步更新，新增、重构时必须处理
* 信息归属（三层分工，同一信息只写一处）：**代码内的文档注释**（javadoc / docstring / JSDoc 等，按语言实际机制）与设计文档按层级分工，禁止同一内容在多处重复表述；**分工只决定"内容写在哪一层"，不减少任何应记录的内容**——
  ** 类级文档注释：一句话定位 + 该类能力清单（目录/总览）+ 指向设计文档的链接；不写实现细节、不写方案取舍
  ** 方法/字段级文档注释：唯一记录该 API 契约的地方——参数语义、返回值、异常、边界、默认值、空值语义、易误用点；**禁止**在此写"为什么这样设计""备选方案"
  ** 设计文档：唯一记录跨方法的设计层面内容——方案与取舍、实现方式、兜底、适用范围、已知限制、受影响范围；**禁止**逐方法罗列 `@param`/`@return` 级入参出参描述（链接到对应方法 javadoc 即可）
  同一事实只允许出现在上述一处，其余位置仅允许"链接 + 一句话摘要"，禁止复制正文；**迁移不要求一步到位**——按代码变更逐步把描述迁到正确层级（改到哪迁到哪，不为此做一次性大迁移）
* 类间关系由代码文档注释互引承载（不靠文档索引、不要求逐类另建文档）：**源文件、测试、性能测试之间在代码文档注释中互相引用**（Java 用 `@see`：源类标注测试类与性能测试类，测试类标注源类与性能测试类，性能测试类标注源类与测试类；其他语言用其文档注释机制等价实现）——类间关系由代码互引表达、可被 IDE 与工具遍历，天然串起结构；**不要求一个源文件/类都另建文档**（更不要求"一文档 + 一测试文档"的逐类配对），**但其内容仍须写进代码文档注释、一项不能少**，也不靠文档目录里的「相关文档」索引来串关系；**互引是"把关系写在代码可及处"，不是削减内容**
* 代码与文档互相引用：代码与设计文档必须**双向可定位**——文档须写明所对应功能的模块与类/方法（从文档能找到代码），代码（类/方法的注释）也须显式引用对应的设计文档相对路径（从代码能找到文档），二者任一处都能顺利跳转到另一处；注释写法见 `specs/stack/` 对应语言文件的注释规范；新增/重构代码时同步补齐双向引用，缺失引用的旧代码发现后直接补，不遗漏
* 设计文档须记录已知缺陷与不足（**设计层面**）：设计文档除记录设计本身，还须显式记录**设计层面**的已知缺陷、不足与注意事项——方法/字段级的易误用点、边界与默认值写在对应**代码文档注释**（见「信息归属」），不在此重复——包括但不限于：
  ** 易误用点：调用方可能踩坑的入参/出参假设、线程安全、可变状态被共享修改等
  ** 边界与异常：异常未处理/吞掉、空值/超长/超大输入等
  ** 默认值：字段/参数的默认值及其语义（如"0 表示未测量 / null 表示未采集"等易混淆约定），默认值可能引发的行为差异与误判
  ** 可能引发的问题：如拼接日志时异常静默导致主流程中断、字段不同步、序列化兼容等
  ** 性能瓶颈：大对象/循环内分配、正则/反射/序列化开销、阻塞 IO、复杂度隐患等
  ** 可能影响的功能：当前缺陷/不足/默认值变更会波及的其它功能、调用方或下游逻辑，须列出受影响范围以便评估改动
  ；记录粒度到**功能/组件**层级，能定位到具体代码或类（方法/字段级细节链接到对应的代码文档注释，不重复叙述）；缺陷内容随代码演进同步更新，**每条缺陷须带状态标记**（如 `待修复` / `已修复(v1.2)`），修复时在统一 changelog 追加对应关闭条目（见下「版本与变更记录」），使缺陷清单可直接当待办看板使用，不遗漏、不依赖记忆

== 版本与变更记录

* 版本号在代码文档注释中维护：源文件的版本号在**代码内的文档注释**中升级——Java 用 `@version` 标签，其他语言用其文档注释机制等价维护（如模块 docstring、文件头注释中的版本标注）；**不要求在文档头部维护 `Version`/`LastModified` 字段**。版本初始 `1.0`，行为、接口、默认值、已知缺陷等任何变更时递增（如 `1.0`→`1.1`，重大重构可 `1.x`→`2.0`）
* 变更日志统一集中一处（时间倒序）：全项目的变更记录在**一个独立的 changelog 文件**中（如项目根 `CHANGELOG.adoc`，命名与位置由项目自定但须唯一、固定），按**时间倒序**记录（最新在最上方，追加时插到顶部）：版本号、日期、变更摘要（改了什么、关联代码/文档/需求），以及已知缺陷的关闭条目（见上「设计文档须记录已知缺陷与不足」）；**不再要求每个设计/测试设计文档各自维护版本字段与文末「变更日志」小节**——变更只在一处记录，避免分散、避免多处不一致
* 适用范围：上述机制**不适用于规范文件（`specs/` 下各 .adoc）**——规范变更由其 git 历史承载，不得混淆。业务系统各阶段级文档的版本与变更同样纳入该项目统一 changelog（见 link:../general/doc-lifecycle.adoc[]）
* 同提交同步与完成定义：版本号、changelog 条目与代码须在**同一提交内**完成同步——改动源文件时，其代码文档注释中的版本号与 changelog 条目须在本提交中一并更新（若存在对应设计/测试设计文档，也须一并同步），**只改一侧的提交视为未完成、禁止提交**（完成定义：源文件有变更时，对应 changelog 条目须出现在本次提交的变更文件列表中）；中间反复修改无需留痕，以最终一次提交为准（见执行原则「未提交前的更改归并」）
* 统一 changelog 参考格式（仅供示意）：
  ```
  = 变更日志

  - 1.1 | 2026-08-21 | 本次变更摘要（最新在上）
  - 1.0 | 2026-08-16 | 初始落地
  ```
