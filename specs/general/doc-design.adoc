= 设计文档规范（通用层）

适用于**所有语言、所有项目类型**的文档编写维护——既包括独立的设计文档与测试设计文档，也包括**代码内的文档注释**。内容要求与迁移方式统一见 `specs/general/doc.adoc`；业务系统阶段级文档组织见 `specs/general/doc-lifecycle.adoc`；模块内文档的组织与归属见 `specs/general/doc-module.adoc`。

== 设计文档

* **编写时机**：核心功能的新增、重构（含行为变更、方案选型、有取舍的设计）必须**记录或更新其设计**——落点按「信息归属」的内容范围决定，**不强制要求存在独立设计文档文件**；内容已完整写入代码文档注释即视为已记录（内容要求不减少）。
* **须记录的内容**：功能设计（方案是什么、为什么这样做、备选方案及不选原因）、兜底（有哪些兜底、兜底触发条件与边界）、适用范围（适用场景、不适用场景、已知限制与取舍）；设计文档须与测试设计**一并编写/更新**（测试是功能的验证规格、二者一体），但**测试内容的落点按其范围分配**（跨类/模块级进测试文档、类/方法级进测试代码文档注释，见 `specs/general/testing.adoc`「测试文档」）。
* **命名与格式**：独立设计文档**按功能/模块命名**（默认不必与某个源文件同名）；**仅当该文档确实只对应某个具体的代码/脚本/类文件时**，才取该源文件名（去扩展名）加 `.adoc`（`Foo.java` → `Foo.adoc`、`check_specs.py` → `check_specs.adoc`）；独立成篇的测试设计文档若对应具体测试类，取该测试类名（`FooTests.adoc`）；**命名风格完全跟随源文件**；AsciiDoc 格式；文档随代码演进同步更新。
* **存放位置**：模块/功能级设计文档放各模块 `doc/`（**不进根 `doc/`**）；业务系统中单模块项目置于设计阶段目录下的 `<模块>/` 子目录，多模块项目一律按前者放各模块 `doc/`。
* **按功能/模块成篇，默认不为每个类各建一篇文档**：一个功能/模块涉及多个类时写一篇功能/模块级文档，涵盖这些类在**设计与取舍层面**的内容，各类的 API 契约细节写在各自类的代码文档注释中；**文档名与源文件同名仅适用于"该文档恰好只对应某个具体源文件"的情形**，且即便同名，其内容仍须是跨类/模块/功能级设计。

=== 信息归属（同一信息只写一处）

判定依据：**按内容范围区分，不按详略程度区分**——"详细设计"一律进代码内的文档注释，**"详细"不是另建文档的理由，独立文档承载的是"范围大"的设计**。

* **类级文档注释**：一句话定位 + 该类能力清单 + 指向设计文档的链接；不写实现细节、不写方案取舍。
* **方法/字段级文档注释**：**唯一记录该 API 契约的地方**——参数语义、返回值、异常、边界、默认值、空值语义、易误用点；**禁止**在此写"为什么这样设计""备选方案"。
* **设计文档**：**唯一记录跨方法的设计层面内容**——方案与取舍、实现方式、兜底、适用范围、已知限制、受影响范围；**禁止**逐方法罗列 `@param`/`@return` 级入参出参描述（链接到对应方法 javadoc 即可）。

同一事实只允许出现在上述一处，其余位置仅允许"链接 + 一句话摘要"，禁止复制正文；**发现既有的重复描述时按 `specs/general/review.adoc`「精炼性」收敛**（该节是精炼性判据的唯一落点：判定标准、收敛形态、与 P3 的边界）；**分工只决定"内容写在哪一层"，不减少任何应记录的内容**。**发现的问题/事项的备注落点同样按"范围"判定**——全局性问题不进类级文档注释（判据见 `specs/general/review.adoc`「问题记录」）。

=== 类间关系与双向引用

* **类间关系由代码文档注释互引承载**：**源文件、测试、性能测试等各类测试之间在代码文档注释中互相引用**（Java 用 `@see`：源类标注其各类测试类，各类测试类标注源类与同被测类的其他测试类，性能测试类标注源类与功能测试类；其他语言用其文档注释机制等价实现）——类间关系由代码互引表达、可被 IDE 与工具遍历。
* **代码与文档互相引用**：代码与设计文档必须**双向可定位**——文档须写明所对应功能的模块与类/方法（从文档能找到代码），代码（类/方法的注释）也须显式引用对应的设计文档（从代码能找到文档）；新增/重构代码时同步补齐，缺失引用的旧代码发现后直接补。

=== 设计层面的已知缺陷与不足

设计文档除记录设计本身，还须显式记录**设计层面**的已知缺陷、不足与注意事项——方法/字段级的易误用点、边界与默认值写在对应**代码文档注释**，不在此重复。包括：

* **易误用点**：调用方可能踩坑的入参/出参假设、线程安全、可变状态被共享修改等。
* **边界与异常**：异常未处理/吞掉、空值/超长/超大输入等。
* **默认值**：字段/参数的默认值及其语义（如"0 表示未测量 / null 表示未采集"），默认值可能引发的行为差异与误判。
* **可能引发的问题**：拼接日志时异常静默导致主流程中断、字段不同步、序列化兼容等。
* **性能瓶颈**：大对象/循环内分配、正则/反射/序列化开销、阻塞 IO、复杂度隐患等。
* **可能影响的功能**：当前缺陷/不足/默认值变更会波及的其它功能、调用方或下游逻辑，须列出受影响范围。

记录粒度到**功能/组件**层级，能定位到具体代码或类；缺陷内容随代码演进同步更新，**每条缺陷须带状态标记**（`待修复` / `已修复(v1.2)`），修复时在统一 changelog 追加对应关闭条目，使缺陷清单可直接当待办看板使用。

== 存量文档收敛（逐类文档 → 代码文档注释）

存量"逐类文档"（`Foo.java` → `Foo.adoc`）**随代码变更逐步收敛、不做一次性大迁移**（迁移方式见 `specs/general/doc.adoc`「注释与文档」）——碰到某个类时，把该类独立文档里属类/方法级的内容迁入其代码文档注释，删除或合并该独立文档。

* **保留/合并/删除判定（两个条件同时看）**：该文档**只对应单个源文件、且内容属类/方法级** → **迁移后删除**；该文档承载的是**跨类的功能/模块级内容** → **保留**（即便它只对应一个源文件也不删），改按功能/模块命名、并按信息归属归并同功能的零散文档。
* **删除前须逐项核对（先迁后删，不得凭记忆）**：迁移是"逐项搬运"而非"重写摘要"——删除/合并独立文档前，须**逐项比对该文档的每个要点都已落入代码文档注释**，核对通过方可删除；核对以原文档原文为准（必要时用 `git show` 取回原文比对），不得先删再补。
* **迁移对照清单（按此逐项搬运、逐项勾选）**：

[cols="2,3",options="header"]
|===
| 独立文档中的段落 | 迁入代码后的落点

| 类定位/一句话说明 | 类级文档注释首句
| 能力清单/目录/总览 | 类级文档注释
| **方法列表/功能说明（逐方法条目）** | **对应方法的文档注释**：职责说明 + `@param`（每个参数）+ `@return` + `@throws`（每个异常）——**逐方法一一对应**
| 字段/属性说明（含义、类型、默认值、配置方式） | 对应**字段**的文档注释
| 参数语义、返回值、异常、边界、空值语义 | 对应方法的文档注释
| 易误用点、注意事项 | 该类/方法的文档注释（就近放在被误用的成员上）
| 设计取舍/为什么这样设计/备选方案 | **不属于**类/方法级——归功能/模块级设计文档（留在独立文档）
| 兜底、适用范围、波及影响 | **不属于**类/方法级——归功能/模块级设计文档
| 版本/变更记录 | 版本号改由代码文档注释承载、变更摘要归项目统一 changelog
|===

* **按上表搬运的口径**：迁移后须确认**原文列出的每个公共方法都有对应的 javadoc**（含职责、`@param`、`@return`、`@throws`），而非只补了类级描述。
* **收敛后独立文档数应趋近"功能/模块数"而非"类数"**；发现两个文档描述同一功能/模块时合并为一篇。

== 版本与变更记录

* **版本号在代码文档注释中维护**：源文件的版本号在代码内的文档注释中升级——Java 用 `@version`，其他语言用其文档注释机制等价维护；**不要求在文档头部维护 `Version`/`LastModified` 字段**。版本初始 `1.0`，行为、接口、默认值、已知缺陷等任何变更时递增。版本号的语义化递增思想参考 Semantic Versioning 2.0.0（本规范采用其主/次版本递增语义，未采用其完整三段式与预发布标识要求）。
* **变更日志统一集中一处（排序方向：时间倒序；默认组织方式：按版本分组）**：全项目的变更记录在**一个独立的 changelog 文件**中（**默认项目根 `CHANGELOG.adoc`**，命名与位置由项目自定但须唯一、固定、并写进项目自身规范或 README 以便定位）；**不再要求每个设计/测试设计文档各自维护版本字段与文末「变更日志」小节**。**排序方向恒为时间倒序（最新在上）；分组口径按项目择一并项目级唯一**（条目撰写与组织形态见 `specs/general/changelog.adoc`）：
** **按版本分组（默认）**：以**发布版本**为一级分组（组内再按变更类型分组，组内条目同样时间倒序）。**版本号即发布标识**（tag / 制品坐标 / 项目自己的发布号）、**日期取该版本的发布日期**；版本是单调递增的，**版本倒序即时间倒序**。
** **按时间流水（次级形态）**：仅在项目**没有发布版本概念**时使用——单层、最新在上、追加时插到顶部。
** 两种**分组口径不并存**（并存即同一改动被记两次）。
* **changelog「记什么、不记什么」的编写规则见** `specs/general/changelog.adoc`（二者配套、不重复表述）。
* **存量版本/变更记录收敛（随文档迁移同步进行）**：项目若在每个文档中维护 `Version`/`LastModified` 字段或文末「变更日志」小节，碰到该文档时收敛——变更摘要并入项目统一 changelog，源文件版本号改由代码文档注释承载，删除文档头部的相关字段与文末小节；若项目尚无统一 changelog 文件，先建立再迁。**重组已有日志属合法动作、不是改写历史**：日志允许被重写，但**只在"组织方式"这一层**——条目的时间、变更点与影响不得被改写或删减，归位后须逐条核对内容不减少。
* **同提交同步（写了条目时）**：版本号、条目与代码改动须在**同一提交内**完成同步，不得只改一侧（依据：ISO 10007 变更控制）。
* **适用范围**：上述机制**不适用于规范文件**——规范变更由其 git 历史承载。业务系统各阶段级文档的版本与变更同样纳入该项目统一 changelog。
* **统一 changelog 参考格式（仅供示意，条目撰写规则与两形态判据见 `specs/general/changelog.adoc`）**：

[listing]
----
= 变更日志

== 1.1（2026-08-21）

- 1.1 | 2026-08-21 | 本次变更摘要（最新在上）

== 1.0（2026-08-16）

- 1.0 | 2026-08-16 | 初始落地
----

== 依赖关系文档（模块间依赖的唯一视图）

模块内文档的组织与归属见 `specs/general/doc-module.adoc`。

**识别特征（涉及即加载、涉及即须核对）**：**多模块结构**（构建文件声明了多个模块/子项目，如 Maven 的 `<modules>`、Gradle 的 `include`、npm 的 workspaces），或**动手增删依赖、新增模块、编写/调整代码、改包或模块结构**。**单模块项目（哪怕包很多）不在本条范围**——没有模块边界就没有模块间依赖关系可画。

**背景（真实失效）**：编辑代码时**加重复依赖**——模块**已经（直接或间接）依赖**了某库，却在它的依赖清单里再声明一次。后果不是功能错误，而是依赖图变脏：版本收敛与统一升级失去唯一入口、可重现性变差、体积与启动开销悄然增加，且每次都要先把依赖树捋一遍才能判断。**根因不是"忘了"**：项目里没有一份**完整依赖关系**的视图。

* **完整依赖关系文档即唯一视图（L1）**：项目存在多模块结构时，须维护一份**完整依赖关系文档**（`<项目根>/doc/dependency.adoc`；单模块项目放 `<模块>/doc/dependency.adoc`）——**完整**指列出**当前项目全部模块之间的依赖关系**（谁依赖谁、方向；模块粒度，**不列第三方库清单**——那是构建工具依赖树的事）。**只存依赖关系**：不写设计说明、不写变更历史。
* **优先用 UML 表述（L1）**：依赖关系**以 UML 图为主**（模块作为组件/包，依赖用依赖箭头表示），使关系可一眼读出；图外可附**模块清单表**（模块 → 直接依赖），便于逐行核对——**不得只写一段文字描述**（文字无法枚举"全部模块对"）。
* **位置须让 AI 直接处理（L1）**：文档须放在多模块项目的**文档根目录**（项目根 `doc/dependency.adoc`），使 `doc/` 索引与站点导航直达、AI 按目录读取即可拿到；文件名固定，便于按固定路径读取与引用。
* **查依赖关系优先查本文档（L1）**：任何任务涉及"模块能不能依赖某模块""这个依赖该不该加、是不是已经在依赖里"时，**先读本视图**；**回答完即止，不重启依赖树解析**。
* **文档缺失则新增，不跳过（L1）**：多模块项目**没有本视图时**，须在本次任务内**新增**（画当前真实依赖关系），不得以"存量还没有"为由跳过；**存在但不完整**时补全后再用。
* **依赖关系变更须与构建文件同一提交内同步（L1）**：模块之间增删依赖、新增/拆分模块、跨模块改包结构后，**同一提交内**更新本视图——视图过期比没有更坏。
* **模块内外部依赖不重复声明（L1）**：读本视图判定"某模块已被（直接或间接）依赖"后，**不得再在它的依赖清单里重复声明同一依赖**（确需显式声明时须写明理由——避免版本漂移、传递路径可能失效）；**新增依赖前先读本视图**，能不加就不加。
* **文档与工具各司其职（L2）**：本视图是**人/AI 可直读的唯一视图**，不替代构建工具（Maven/Gradle 的依赖树只描述**第三方库**的传递关系）；两者结论冲突时以构建文件的实际解析结果为准并**立即修正本视图**。
* **依据（标准名/编号）**：ISO/IEC/IEEE 42010（架构描述）、UML（OMG）、ISO/IEC/IEEE 29148（可追溯性）、The Twelve-Factor App（Dependencies）、Maven 与 Gradle 官方文档。

=== UML 表述规范（依赖关系的画法）

* **元素与关系**：模块用**组件（component）**或**包（package）**表示（或简单矩形 + 模块名）；模块 A 依赖模块 B 画**依赖箭头**（虚线 + 开放式箭头）——**箭头由依赖方指向被依赖方**；被多个模块依赖的公共模块应能一眼看出。
* **可读性**：**一张图只画一种关系、标清方向与必要说明**；**不引入无关元素**（类、方法、时序）；按**层次/分组**摆放（基础模块在下、上层模块在上），使依赖方向与层次一致。
* **文本形态与图同源（可读 + 可核对）**：图为主、**模块清单表为附**（如 `模块 | 直接依赖 | 说明/约束`）——表用于逐行核对"有没有漏、方向对不对"。
* **图的文本源**：用可纳入 git、可逐行 diff 的文本图源（Mermaid `graph`、PlantUML 的 `component`/`package` 图），并写明渲染方式，使图可随代码演进在提交里可见地变化；**不得只放无法 diff 的二进制截图**。

=== 与既有约定的边界（避免第二真源）

* **不重复记录第三方库清单**：模块间依赖才是本视图的内容；某模块引了哪个第三方库、什么版本，属构建文件与 `specs/general/dependency.adoc` 的范围。
* **不替代设计文档**：本视图回答**依赖关系**；跨模块方案与取舍、分层约束的理由按下「信息归属」进设计文档，二者互引。
* **与"类间关系由代码文档注释互引"不冲突**：后者管**类与方法级**关系的可遍历性，本视图管**模块级**依赖关系——粒度不同、互不替代。
