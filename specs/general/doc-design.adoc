= 设计文档规范（通用层）

以下规范适用于**所有语言、所有项目类型**（业务项目、工具库、脚本等）的文档编写维护——既包括独立的设计文档与测试设计文档，也包括**代码内的文档注释**（javadoc / docstring / JSDoc 等，按语言实际机制）。内容要求与迁移方式（内容不减少、逐步迁移）统一见 link:../general/doc.adoc[]；业务系统阶段级文档组织见 link:../general/doc-lifecycle.adoc[]；模块内文档的组织与归属见 link:../general/doc-module.adoc[]；**模块间依赖关系**的唯一视图见下「依赖关系文档（模块间依赖的唯一视图）」。

== 设计文档

* 设计文档的编写时机：核心功能的新增、重构（含行为变更、方案选型、有取舍的设计）必须**记录或更新其设计**——落点按「信息归属」的内容范围决定（跨类/模块级设计内容进设计文档，类/方法级细节进代码文档注释），**不强制要求存在独立设计文档文件**；内容已完整写入代码文档注释即视为已记录（内容要求不减少，见 link:../general/doc.adoc[]「注释与文档」）
* 设计文档须记录的内容：功能设计（方案是什么、为什么这样做、备选方案及不选原因）、兜底（有哪些兜底、兜底触发条件与边界）、适用范围（适用场景、不适用场景、已知限制与取舍）；设计文档须与测试设计**一并编写/更新**（测试是功能的验证规格、二者一体），但**测试内容的落点按其范围分配**（跨类/模块级进测试文档、类/方法级进测试代码文档注释，见 link:../general/testing.adoc[]「测试文档」），不要求把测试内容并入同一份设计文档
* 文档命名与格式：独立设计文档**按功能/模块命名**（**默认不必与某个源文件同名**）；**仅当该文档确实只对应某个具体的代码/脚本/类文件时**（即该功能/模块只由一个源文件承载），才取该源文件名（去扩展名）加 `.adoc`，与源文件同名便于查找阅读（如 `Foo.java` → `Foo.adoc`、`check_specs.py` → `check_specs.adoc`）；独立成篇的测试设计文档若对应具体测试类，取该测试类名（如 `FooTests` → `FooTests.adoc`），`Test`/`Tests` 等后缀由源文件自身命名决定、规范不统一改写；**命名风格完全跟随源文件**（源文件是驼峰则文档用驼峰、源文件是中划线则文档用中划线）；AsciiDoc 格式；文档随代码演进同步更新，新增、重构时必须处理
* 存放位置：模块/功能级设计文档放各模块 `doc/`（`<各模块>/doc/`，**不进根 `doc/`**）；业务系统中，单模块项目置于设计阶段目录下的 `<模块>/` 子目录（如 `doc/<设计阶段>/<模块>/`），多模块项目一律按前者放各模块 `doc/`；模块名取核心功能/组件所属模块（如 `core`/`web`/`feign`/`log`，以各项目实际模块划分为准）。组织、粒度与归属见 link:../general/doc-module.adoc[]、link:../general/doc-lifecycle.adoc[]
* 按**功能/模块**成篇，**默认不为每个类各建一篇文档**——一个功能/模块涉及多个类时写一篇功能/模块级文档，涵盖这些类在**设计与取舍层面**的内容，各类的 API 契约细节写在各自类的代码文档注释中；**文档名与源文件同名仅适用于"该文档恰好只对应某个具体源文件"的情形**，且**即便同名，其内容仍须是跨类/模块/功能级设计**，不得借同名把类级细节搬进独立文档（功能/模块名与类名相同属巧合，不构成逐类建文档的理由）

=== 信息归属（同一信息只写一处）

判定依据：**按内容范围区分，不按详略程度区分**——"详细设计"一律进代码内的文档注释（见下），**"详细"不是另建文档的理由，独立文档承载的是"范围大"的设计**。三层分工如下：

* 类级文档注释：一句话定位 + 该类能力清单（目录/总览）+ 指向设计文档的链接；不写实现细节、不写方案取舍
* 方法/字段级文档注释：**唯一记录该 API 契约的地方**——参数语义、返回值、异常、边界、默认值、空值语义、易误用点；**禁止**在此写"为什么这样设计""备选方案"
* 设计文档：**唯一记录跨方法的设计层面内容**——方案与取舍、实现方式、兜底、适用范围、已知限制、受影响范围；**禁止**逐方法罗列 `@param`/`@return` 级入参出参描述（链接到对应方法 javadoc 即可）

同一事实只允许出现在上述一处，其余位置仅允许"链接 + 一句话摘要"，禁止复制正文；**分工只决定"内容写在哪一层"，不减少任何应记录的内容**（内容不减少与逐步迁移的要求见 link:../general/doc.adoc[]）；测试相关内容的同类分离（跨类/模块级的测试总结与规划进独立测试文档，类/方法级的用例设计思路与依据进测试代码文档注释）见 link:../general/testing.adoc[]「测试文档」。**发现的问题/事项的备注落点同样按"范围"判定**——全局性问题不进类级文档注释（判定标准与落点见 link:../general/review.adoc[]「问题记录」），下「设计层面的已知缺陷与不足」即该判定在设计内容上的具体应用。

=== 类间关系与双向引用

* 类间关系由代码文档注释互引承载（不靠文档目录索引）：**源文件、测试、性能测试等各类测试之间在代码文档注释中互相引用**（Java 用 `@see`：源类标注其各类测试类，各类测试类标注源类与同被测类的其他测试类，性能测试类标注源类与功能测试类；其他语言用其文档注释机制等价实现）——类间关系由代码互引表达、可被 IDE 与工具遍历，天然串起结构
* 代码与文档互相引用：代码与设计文档必须**双向可定位**——文档须写明所对应功能的模块与类/方法（从文档能找到代码），代码（类/方法的注释）也须显式引用对应的设计文档（从代码能找到文档），二者任一处都能顺利跳转到另一处；注释写法见 `specs/stack/` 对应语言文件的注释规范；新增/重构代码时同步补齐，缺失引用的旧代码发现后直接补，不遗漏

=== 设计层面的已知缺陷与不足

设计文档除记录设计本身，还须显式记录**设计层面**的已知缺陷、不足与注意事项——方法/字段级的易误用点、边界与默认值写在对应**代码文档注释**（见「信息归属」），不在此重复。包括但不限于：

* 易误用点：调用方可能踩坑的入参/出参假设、线程安全、可变状态被共享修改等
* 边界与异常：异常未处理/吞掉、空值/超长/超大输入等
* 默认值：字段/参数的默认值及其语义（如"0 表示未测量 / null 表示未采集"等易混淆约定），默认值可能引发的行为差异与误判
* 可能引发的问题：如拼接日志时异常静默导致主流程中断、字段不同步、序列化兼容等
* 性能瓶颈：大对象/循环内分配、正则/反射/序列化开销、阻塞 IO、复杂度隐患等
* 可能影响的功能：当前缺陷/不足/默认值变更会波及的其它功能、调用方或下游逻辑，须列出受影响范围以便评估改动

记录粒度到**功能/组件**层级，能定位到具体代码或类（方法/字段级细节链接到对应的代码文档注释，不重复叙述）；缺陷内容随代码演进同步更新，**每条缺陷须带状态标记**（如 `待修复` / `已修复(v1.2)`），修复时在统一 changelog 追加对应关闭条目（见下「版本与变更记录」），使缺陷清单可直接当待办看板使用，不遗漏、不依赖记忆

== 存量文档收敛（逐类文档 → 代码文档注释）

存量"逐类文档"（如 `Foo.java` → `Foo.adoc`）**随代码变更逐步收敛、不做一次性大迁移**（迁移方式见 link:../general/doc.adoc[]「注释与文档」）——碰到某个类时，把该类**独立文档里属类/方法级**的内容迁入其代码文档注释，删除或合并该独立文档，不为此专门发动全库搬迁。

* 保留/合并/删除判定（**两个条件同时看**）：该文档**只对应单个源文件、且内容属类/方法级** → **迁移后删除**；该文档承载的是**跨类的功能/模块级内容** → **保留**（即便它只对应一个源文件也不删），改按功能/模块命名、并按「设计文档不是逐类产出物」归并同功能的零散文档
* 删除前须逐项核对（**先迁后删，不得凭记忆**）：迁移是"逐项搬运"而非"重写摘要"——删除/合并独立文档前，须**逐项比对该文档的每个要点都已落入代码文档注释**，核对通过方可删除；**不得凭记忆判断"应该都写了"**（凭记忆必然漏，如漏掉全部公共方法的职责/参数/返回/异常）。核对以原文档原文为准（必要时用 `git show` 取回原文比对），不得先删再补
* **迁移对照清单（按此逐项搬运、逐项勾选）**：独立文档的常见段落与对应的代码落点如下，迁移时**按段落逐条落位**，一条不漏；**内容记什么以 link:../general/doc.adoc[]「注释与文档」的必记录项为准**，本表只定"搬到哪"：

[cols="2,3",options="header"]
|===
| 独立文档中的段落 | 迁入代码后的落点

| 类定位/一句话说明 | 类级文档注释首句
| 能力清单/目录/总览 | 类级文档注释（能力清单、目录）
| **方法列表/功能说明（逐方法条目）** | **对应方法的文档注释**：职责说明 + `@param`（每个参数）+ `@return` + `@throws`（每个异常）——**逐方法一一对应，不得只写类级就了事**
| 字段/属性说明（含义、类型、默认值、配置方式） | 对应**字段**的文档注释（含义 + 默认值 + 配置方式）
| 参数语义、返回值、异常、边界、空值语义 | 对应方法的文档注释（`@param`/`@return`/`@throws` 及正文）
| 易误用点、注意事项 | 该类/方法的文档注释（就近放在被误用的成员上）
| 设计取舍/为什么这样设计/备选方案 | **不属于**类/方法级——归功能/模块级设计文档（**留在独立文档**，不迁入代码注释）
| 兜底、适用范围、波及影响 | **不属于**类/方法级——归功能/模块级设计文档（**留在独立文档**）
| 版本/变更记录 | 版本号改由代码文档注释承载、变更摘要归项目统一 changelog（见下「版本与变更记录」）
|===

* 按上表搬运的口径（**逐方法条目 → 逐方法 javadoc 是最易漏的一项**）：迁移后须确认**原文列出的每个公共方法都有对应的 javadoc**（含职责、`@param`、`@return`、`@throws`），而非只补了类级描述
* 收敛后独立文档数应趋近"功能/模块数"而非"类数"；发现两个文档描述同一功能/模块时合并为一篇，原文档用 git 规范要求的方式处理（见 link:../general/git.adoc[]）

== 版本与变更记录

* 版本号在代码文档注释中维护：源文件的版本号在**代码内的文档注释**中升级——Java 用 `@version` 标签，其他语言用其文档注释机制等价维护（如模块 docstring、文件头注释中的版本标注）；**不要求在文档头部维护 `Version`/`LastModified` 字段**。版本初始 `1.0`，行为、接口、默认值、已知缺陷等任何变更时递增（如 `1.0`→`1.1`，重大重构可 `1.x`→`2.0`）——版本号的语义化递增思想参考 Semantic Versioning 2.0.0（本规范采用其主/次版本递增语义，未采用其完整三段式与预发布标识要求）
* 变更日志统一集中一处（时间倒序）：全项目的变更记录在**一个独立的 changelog 文件**中（**默认项目根 `CHANGELOG.adoc`**，命名与位置由项目自定但须唯一、固定、并写进项目自身规范或 README 以便定位），按**时间倒序**记录（最新在最上方，追加时插到顶部）：版本号、日期、变更摘要（改了什么、关联代码/文档/需求），以及已知缺陷的关闭条目；**不再要求每个设计/测试设计文档各自维护版本字段与文末「变更日志」小节**——变更只在一处记录，避免分散、避免多处不一致
* **changelog「记什么、不记什么」的编写规则（重点/细枝末节取舍）见 link:../general/changelog.adoc[]**——本条只定版本记录机制，条目的取舍口径与书写方式以该文件为准（二者配套、不重复表述）
* 存量版本/变更记录收敛（**随文档迁移同步进行**）：项目若在**每个文档**中维护 `Version`/`LastModified` 字段或文末「变更日志」小节，属存量做法——**碰到该文档时收敛**（不为此一次性全库改造）：① 各文档的变更摘要**并入项目统一 changelog**（按时间倒序整理，保留原日期与摘要），② 源文件版本号改由**代码文档注释**承载（Java 用 `@version`），③ 删除文档头部的 `Version`/`LastModified` 字段与文末「变更日志」小节；若项目尚无统一 changelog 文件，**先建立**（项目根 `CHANGELOG.adoc`）再迁
* **同提交同步（写了条目时）**：本次若写了 changelog 条目，版本号、条目与代码改动须在**同一提交内**完成同步，不得只改一侧（条目的取舍与书写口径见 link:../general/changelog.adoc[]）；**设计/测试设计文档与代码的同提交要求**不因本次是否写条目而变，见 link:../core/execution.adoc[]「文档与代码对应同步」；中间反复修改无需留痕，以最终一次提交为准（见执行原则「未提交前的更改归并」）
* 适用范围：上述机制**不适用于规范文件（`specs/` 下各 .adoc）**——规范变更由其 git 历史承载，不得混淆。业务系统各阶段级文档的版本与变更同样纳入该项目统一 changelog（见 link:../general/doc-lifecycle.adoc[]）
* 统一 changelog 参考格式（仅供示意，条目撰写规则见 link:../general/changelog.adoc[]）：
  ```
  = 变更日志

  - 1.1 | 2026-08-21 | 本次变更摘要（最新在上）
  - 1.0 | 2026-08-16 | 初始落地
  ```

== 依赖关系文档（模块间依赖的唯一视图）

模块内文档的组织与归属见 link:../general/doc-module.adoc[]（该文件亦反向指向本节）。

**识别特征**（**涉及即加载、涉及即须核对**）：**多模块结构**（构建文件声明了多个模块/子项目，如 Maven 的 `<modules>`、Gradle 的 `include`、npm 的 workspaces），或**动手增删依赖、新增模块、编写/调整代码、改包或模块结构**——凡**要以模块为单位判断"新依赖该不该加"**的场合都命中。**单模块项目（哪怕包很多）不在本条范围**——没有模块边界就没有模块间依赖关系可画（不要为"包多"新建该文档）。

背景（真实失效）：编辑代码时**加重复依赖**——模块**已经（直接或间接）依赖**了某库，却在它的依赖清单里再声明一次。后果不是功能错误，而是依赖图变脏：版本收敛与统一升级失去唯一入口、可重现性变差（同一直达依赖可能解析到不同版本）、体积与启动开销悄然增加，且**每次都要先把依赖树捋一遍才能判断**——这正是本条要消灭的成本。**根因不是"忘了"**：项目里没有一份**完整依赖关系**的视图，AI 只能临场重建。

* **完整依赖关系文档即唯一视图（L1）**：项目存在多模块结构时，须维护一份**完整依赖关系文档**（`<项目根>/doc/dependency.adoc`，单模块项目放 `<模块>/doc/dependency.adoc`，见 link:../general/doc-module.adoc[]、link:../general/doc-lifecycle.adoc[]）——**完整**指列出**当前项目全部模块之间的依赖关系**（谁依赖谁、方向；模块粒度，**不列第三方库清单**——那是构建工具依赖树的事），使读者不读构建文件、不做依赖解析即可回答"这个模块能不能直接用某个模块的能力"。**只存依赖关系**：不写设计说明、不写变更历史（与「信息归属」一致），与变更日志/设计文档分属不同落点。
* **优先用 UML 表述（L1）**：依赖关系**以 UML 图为主**（模块作为组件/包，依赖用依赖箭头表示；图族与画法见下「UML 表述规范」），使关系**可一眼读出**；图外可附**模块清单表**（模块 → 直接依赖），便于逐行核对——**不得只写一段文字描述**（文字无法枚举"全部模块对"，读者仍要去读构建文件）。
* **位置须让 AI 直接处理（L1）**：文档须放在多模块项目的**文档根目录**（项目根 `doc/dependency.adoc`；单模块时随模块文档同级），使 `doc/` 索引与站点导航直达、AI 按目录读取即可拿到（见 link:../general/doc.adoc[]「文档组织与导航」）；文件名固定，便于按固定路径读取与引用。
* **查依赖关系优先查本文档（L1，读这边）**：任何任务涉及"模块能不能依赖某模块""这个依赖该不该加、是不是已经在依赖里"时，**先读本视图**（`doc/dependency.adoc`）；**回答完即止，不重启依赖树解析**（读取按最小必要，见 link:../core/execution.adoc[]「范围控制」）。本项目规范在依赖规范 link:../general/dependency.adoc[]「引入依赖」的重申落点即本视图。
* **文档缺失则新增，不跳过（L1）**：多模块项目**没有本视图时**，须在本次任务内**新增**（画当前真实依赖关系），不得以"存量还没有"为由跳过（存量含义见 link:../core/execution.adoc[]「规范变更的存量处理」）；**存在但不完整**时补全后再用。
* **依赖关系变更须与构建文件同一提交内同步（L1）**：模块之间增删依赖、新增/拆分模块、跨模块改包结构后，**同一提交内**更新本视图（与同文件「版本与变更记录」的「同提交同步（写了条目时）」口径一致）——视图过期比没有更坏（读者会按它得出错误结论，且不会再去核对构建文件）。**内容不得因承载位置减少**：模块清单、依赖方向、依赖的产生原因（跨模块复用、分层约束）都须在视图或其链接到的落点内。
* **模块内外部依赖不重复声明（L1）**：读本视图判定"某模块已被（直接或间接）依赖"后，**不得再在它的依赖清单里重复声明同一依赖**（判定标准与既有限定见 link:../general/dependency.adoc[]「引入依赖」"传递依赖不直接使用"：确需显式声明时须写明理由——避免版本漂移、传递路径可能失效）；**新增依赖前先读本视图**，能不加就不加。
* **文档与工具各司其职（L2）**：本视图是**人/AI 可直读的唯一视图**，不替代构建工具（Maven/Gradle 的依赖树只描述**第三方库**的传递关系，与"模块间依赖"不是一回事）；两者结论冲突时以构建文件的实际解析结果为准并**立即修正本视图**。

=== UML 表述规范（依赖关系的画法）

依赖关系图**用 UML 表述**（依据：OMG UML 规范对依赖关系的定义与记法）：

* **元素与关系**：模块用**组件（component）**或**包（package）**表示（或简单矩形 + 模块名）；模块 A 依赖模块 B 画**依赖箭头**（虚线 + 开放式箭头）——**箭头由依赖方指向被依赖方**（A → B 表示 A 依赖 B）；被多个模块依赖的公共模块应能一眼看出（多条箭头汇聚到它）。
* **可读性**：**一张图只画一种关系、标清方向与必要说明**（图名写明"模块依赖关系"）；**不引入无关元素**（类、方法、时序），避免图变成"什么都想说、什么都读不出"；按**层次/分组**摆放（基础模块在下、上层模块在上，或按构建模块分组），使依赖方向与层次一致。
* **文本形态与图同源（可读 + 可核对）**：图为主、**模块清单表为附**（如 `模块 | 直接依赖 | 说明/约束`）——表用于逐行核对"有没有漏、方向对不对"（可读性检查与清单检查各司其职，不互相替代）。
* **图的文本源**：用可纳入 git、可逐行 diff 的文本图源（如 Mermaid `graph`、PlantUML 的 `component`/`package` 图），并写明渲染方式（站点/编辑器插件），使**图可随代码演进在提交里可见地变化**；**不得只放无法 diff 的二进制截图**（无法随代码演进核对）。

=== 依赖关系文档与既有约定的边界（避免第二真源）

* **不重复记录第三方库清单**：模块间依赖才是本视图的内容；某模块引了哪个第三方库、什么版本，属构建文件与 link:../general/dependency.adoc[] 的范围——本视图**不复制**构建文件的依赖清单（复制即第二真源，改一处必漏一处）。
* **不替代设计文档**：本视图回答**依赖关系**；跨模块方案与取舍、分层约束的理由、兜底与适用范围按下「信息归属」进设计文档，二者互引（本视图链接对应设计文档，设计文档链接本视图）。
* **与"类间关系由代码文档注释互引"不冲突**：同文件「类间关系与双向引用」管**类与方法级**关系的可遍历性，本视图管**模块级**依赖关系——粒度不同、互不替代（类级细节不得搬进本视图）。
