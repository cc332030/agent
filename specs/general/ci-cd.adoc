= CI/CD 规范（通用层）

适用于 CI/CD（持续集成/部署，含 GitHub Actions、CNB、Jenkins 等流水线）配置的编写与调优；同时约束**开发与验证时使用的运行环境**。某技术栈/平台的构建细节见 `specs/stack/`、`specs/platform/` 对应文件。依据：The Twelve-Factor App（构建/发布/运行分离与配置外置）、GitHub Actions 官方文档、DORA 的交付流水线研究。

== 核心原则

CI/CD 配置核心是**不走弯路**：按**最标准、最准确**的方式一次做对——先确认项目真实的构建/运行时要求再执行，不靠默认值试探、不走"失败后再修正"的弯路。

== 运行时版本一次选对

* **开头即用项目声明的运行时版本**：流水线运行构建/测试前，须**一开始就用项目声明的运行时/构建工具版本**、不得先用默认/最新版本试探——**声明的唯一落点见下节「运行环境须与项目声明一致」，本条不重列**（取值＝声明版本，怎么 setup 属执行动作，不写进规范）。
* **失败先核对版本再换**：构建失败时，先核对所用版本与项目声明是否一致，再决定是否调整。

== 运行环境须与项目声明一致

运行环境（语言运行时与构建工具的版本，如 jdk1.8、python2）在项目里有**唯一声明落点**，开发与验证一律用它——**严禁使用与声明不同的运行环境**，**即使换一个版本也能正常跑通流程，也不得换**。

* **先按项目声明取环境，不得按"能跑通"选版本（L1）**：动手写代码、跑构建、跑测试、执行脚本之前，先取定项目**声明的**运行时/构建工具版本，并**全程用同一个版本**——不得改用其他版本、不得用"等价/兼容/近似"的版本顶替、不得用环境的默认版本或最新版本试探；**"换一个版本也跑得通""流程正常结束"都不构成换版本的理由**（换版本会改变产物、行为与测试结论的可信度）。**判定标准（任一命中即违规）**：① 执行构建/测试/脚本所用版本与项目声明**不一致**（含大版本相同、小版本/补丁版本不同）；② 用"另一个版本也跑通了""CI 上跑的版本不同但绿了"为由继续推进；③ 环境声明缺失时不先确认、直接用环境默认版本开工。依据：ISO/IEC/IEEE 29148（需求须单一、可验证、可追溯）、The Twelve-Factor App（dev/prod parity）、Semantic Versioning 2.0.0。
* **声明落点：只认项目已有的版本声明，不另立第二真源（L1）**：声明＝该项目里**已经声明版本**的那一处（取值形态见下「版本声明的落点」）；**不得**为满足本条另建一份版本声明（多一份必然漂移）；声明之间冲突时**先停下确认**、不得自行择一。依据：ISO 10007（配置项与变更须有单一、受控的来源）。
* **版本声明的落点（L2，取值形态）**：Maven 项目＝其 `pom.xml` 与 toolchains 声明；Node 项目＝其版本文件与包清单声明；Python 项目＝其版本文件、工程元数据与脚本解释器声明；其他栈＝该栈**生态通行的版本文件**；此外项目 README、项目自身规范、CI 配置里写明的"环境要求"**同为声明**。**本集合不列各栈的具体文件名清单**——"该栈的声明落在哪个文件"属**该生态的常识**、不构成规则的边界；边界是**"只取项目已有声明、不另建一份"**。（依据：ISO/IEC Directives Part 2——要求须简明、无歧义、能被独立理解；要求**只定取值形态**，不列外部世界的清单。）
* **环境不可得或未声明时走降级路径，不阻断、也不记作通过（L1）**：① 项目**未声明**运行环境：先按上条再找一遍声明落点，仍找不到时**先确认**要用的版本；② 声明环境在**当前环境确实装不出来**：如实说明"声明环境不可用 + 实际用的环境"，并把该次**验证结论标为未确证**（不得记为通过）；③ 确需临时用另一版本定位问题时**只作诊断**，结论须回到声明环境复核后才能用于交付。**不得**因环境不匹配就跳过验证、改判既有用例或删减用例。
* **与 CI 的关系**：流水线里"开头即用项目声明的版本"见上「运行时版本一次选对」；本节把同一口径扩到**本机开发与所有验证**（两个场景共用一个声明落点）。**验证对象须钉定到具体版本与 commit sha**（见 `specs/general/verify.adoc`「编译/运行验证」）。

== 校验链完整（定义未执行防线）

* **流水线须执行项目的全部既定校验，不得只跑一部分（L1）**：流水线须把项目**声明的全部校验手段**接进 CI——编译/构建、静态检查、**配套测试（单元测试与各专项测试）**、规范/完整性机械校验。**只跑主校验脚本、把配套测试留在本地手工跑，等于"定义了却没执行"**。判定口径：**"项目有测试"≠"CI 跑了测试"**——须在流水线配置里能指出"哪一步跑了哪套测试"。
* **测试文件须能被测试框架自动发现（L1）**：进入 CI 的测试文件，其**命名与位置必须落在所用测试框架的默认发现规则内**（取值＝**可被发现**这一状态；**不得依赖"我本地单独执行过"来证明测试有效**）。**发现规则随生态与本项目已有约定而定，本条不列工具与命令**。**判定标准**：框架的发现结果中，**发现的用例数与实际用例数一致**（判据是这两个数一致，不是用什么命令取）。
* **校验手段依赖的工具须在本地实际装齐、不得因缺工具而静默跳过（L1）**：项目的每项既定校验手段都**依赖具体的工具**（语法/格式编译、静态检查、规范校验脚本的运行时等）——**工具须在执行前齐备**（怎么探测在不在属执行动作，不写进规范）；**缺就装齐再跑——不得把"环境里没有"变成"自动跳过"**：让检查脚本在缺工具时打印一句提示、然后照常以退出码 0 结束，等于**声明的校验手段从未执行、而输出看起来是绿的**（最隐蔽的一类假绿）。**判定标准（任一命中即违规）**：① 检查脚本里对缺工具走"跳过/提示"分支、且该分支不影响退出码；② 校验手段的依赖工具在本地或 CI 里没有任何安装步骤；③ 只在文档里写"建议安装"，脚本与 CI 都不核"工具在不在"。**装了但不够、不算通过（L1）**：同一校验手段可能有**多个实现**，其中**能力不等价**（如某个实现缺少让告警也失败的开关、只拦"编译不过"而放行"只告警不报错"的那一半）——此时**只装了能力弱的那个实现，不等于这条校验做到了**，**不得记作通过**；须装齐**能力完整的实现**再跑，**不得以"装了某个实现、脚本没报错"顶替**（本仓库实证：只装能力弱的实现时，声明的告警级校验长期没跑而脚本照旧报 OK）。**判定标准（任一命中即违规）**：① 声明要拦告警级问题，却只装拦不住告警的实现并据此记通过；② 把"能力弱的实现也能正常结束"当成已满足本条。**降级路径（L2）**：工具确实装不上（离线、无权限、平台不提供）时，按"尽力而为"**如实标『未执行 + 原因 + 替代做法』**，**不得记作通过**（判据见 `specs/general/verify.adoc`「判准维度」）；**"装不上"不是"不用装"**——不得以此为由把这条校验从校验链里删掉。**工具的齐备性须可核对（L1）**：要求"须检查语法"而不落成可核对的取值时，执行者装不上就只能跳过——故本条的取值是**工具齐备**：项目声明的每项校验手段，其依赖工具在本地与 CI 中**都可取用**。**安装方式须随要求一起给出**（取值＝**可据以装齐**：装哪个、从哪装；**具体命令属执行动作，不写进规范**）——只写"须检查语法"而不给安装方式时，执行者装不上就只能跳过。工具确有缺失时按上条降级路径处置。
* **跑得快也是校验链的一部分（L1）**：测试**须按文件并行分片**跑——分片单位取**测试文件**（进程内的模块全局由同一文件的用例共享，按用例切片会让夹具互相污染；按文件切则每一片本就是独立运行的那一份）；**单片自成时限**（并行之后单片挂住等于整步挂住，「在跑」与「卡住」要分辨得出）；**只报结论、不留全量输出**（分片日志落文件、失败时回放尾部，日志量不随套件增长）。**判定标准（任一命中即违规）**：① 流水线用一句`discover` 式命令串行跑全量测试；② 分片没有各自的时限；③ 把分片的全量输出直接灌进CI 日志。依据：ISO/IEC/IEEE 25010（性能效率）、DORA 的交付流水线研究（快反馈是持续交付的前提）。**失效形态**：套件涨到分钟量级后，流水线**一直是绿的、只是慢**，没有任何判据会发现——「慢」始终停留在感受层面、没人把它变成可核对的事实。
* **CI 加的步骤须是确定性且必过的（L2）**：**不在 CI 中调用会给出非确定性结论的外部 AI/网络服务来阻塞构建**——语义审查这类启发式判断交人工 review。
* **CI 只做守护、不代改（L2）**：CI 负责判定与报告，**不默认改动仓库内容、不代为提交、不自动合并**。

== 触发与作用范围

* **触发路径须覆盖校验对象（L1）**：流水线的触发条件必须**覆盖其校验的全部对象**——被校验的文件/目录发生变更时必须能触发该流水线；变更被校验范围后须核对触发路径同步更新。**取值的落点属该平台流水线配置，本条只定取值**。
* **路径过滤与校验范围一致（L2）**：避免两类偏差——① 触发过窄（改了却不跑，漏检）；② 触发过宽（无关改动也跑，浪费核时）。校验对象用集中常量/锚点声明，使两处不易各自漂移。

== 依赖与外部资源可用性

* **上游依赖（镜像/制品/工具）须先确认实际可用（L1）**：流水线引用的容器镜像、制品包、外部工具，须**在配置时确认其真实存在且可取到**，不得凭名称假设可用。选型时优先用**已发布、可访问、版本固定**的产物。
* **依赖/工具版本固定**：CI 中依赖、运行时、构建工具固定到经实际验证的具体版本，不用 `latest`/浮动版本；**取源次序与"先实测再启用"按** `specs/general/dependency.adoc`「包源（包仓库/镜像站）的选用」执行（缺则流水线仍会直连境外源）。

== 临时/中间产物与缓存的清理（本地占用）

适用面：本地项目开发中**构建中间产物、增量缓存、依赖缓存与回收站**长期堆积占用磁盘时，按本节判定"清什么、留什么、何时清、怎么清"。**平台任务单的评论串不属本节对象**——它是任务留证、一律不得删（见 `specs/platform/cnb.adoc`「评论不得删除（L1）」）；`tmp/` 内部怎么排布见 `specs/core/execution.adoc`「tmp/ 的布局与命名」，本节只补它未覆盖的构建与依赖那一面。依据：ISO/IEC/IEEE 25010（性能效率：资源利用）、ISO 10007（配置项状态须可辨识、可追溯）、ISO 9241-110（可控性：清理须可预期、能自行执行、无正当理由不得自动动作）、The Twelve-Factor App（依赖显式声明与 dev/prod 一致性）。**"按归责与可重建性判、不按目录名与时间扫删"是本集合据上述方向做的判据化取舍。**

* **先分三类、各定归责与生命周期（L1）**：清理前先把占用归入三类——① **临时产物**（`tmp/`、脚本临时文件）；② **构建与中间产物**（构建工具产物目录、增量编译目录）；③ **依赖与工具缓存**（包管理器全局缓存与仓库、语言构建工具的用户级缓存、编辑器/系统缓存）。**归责定归属、是清理的第一道判据**：①②属项目、**随项目走**、只在本项目用不到时清；③属**本机共享缓存、跨项目复用**，**不得按"某个项目清了"处置**。**此处"用不到"须按「后续是否还有用」判（见下方「可重建不等于该清」条），不是仅凭"能重建"就认定用不到**，**回收站/回收目录属用户数据，单列一类：不在自动清理范围**。判定标准（任一命中即违规）：以③是"某项目的产物"为由把全局缓存当项目临时文件清、把回收站纳入自动清理、未归类就按目录名动手。
* **可重建性判定：有声明锁得住才可清（L1）**：依赖缓存**只有在"删了能由项目声明原样重建"时才可清**——判据是**锁文件/版本声明在、且与清单一致**（判据本体见 `specs/general/dependency.adoc`「锁文件须提交并保持一致」与「构建可重现」）；**缺锁文件/版本声明的缓存按不可重建处理，不得清**。**可重建只是"可清"的必要条件、不是充分条件——过了这一关仍须判"后续是否还有用"（见下方「可重建不等于该清」条）**，**不可重建物**（用户数据、回收站、未纳入版本库的成果）一律不自动清，须人工确认。判定标准：无锁文件却凭"大抵能重新下载"清依赖缓存、把回收站按"可重建"放行、对用户数据执行自动删除。
* **先定位再动手、走原生命令、禁通配扫删（L1）**：清理动作按序——① **先定位占用**：查明哪个目录占了多少、属于上面哪一类，再定处置；② **用生态自带的清理/修剪命令**（各构建工具的 `clean`、包管理器的缓存修剪子命令、构建工具的缓存清理），**不得**用通配 `rm -rf`/整目录扫删替代原生命令；③ **范围以"本项目的该类产物/本机该生态缓存"为界**，不越界到用户数据与其他项目。判定标准（任一命中即违规）：上来就按目录名扫删、用一条 `rm -rf` 清空多个生态的缓存、清用户回收站、未经定位就删最大目录。
* **清理属本地动作、规范不代为执行（L1）**：本节只定义归责、判据、时机与边界；**是否清由使用者决定**，执行者**不得**在用户未明确要求时自行删除本机目录；执行清理前仍按 `specs/core/execution.adoc`「破坏性操作」核对目标、可回滚与范围。判定标准：以"优化/清一下"为由擅自在本机执行删除、跳过破坏性操作确认。
* **清理时机按有无生命周期锚点分两类定（L1）**：清理的**何时清**按对象能否绑定生命周期锚点取值，不再悬空由临场决定——① **能绑定锚点的**（构建中间产物绑"构建单元结束"、依赖/工具缓存的原生修剪绑"工具退出/维护窗口"、`tmp/` 绑"任务结束"）：**锚点到来＝进入清理判定，不是到期必清**——到点仍须逐项过可重建性与保留价值判定（见「临时产物按保留价值判」与「可重建不等于该清」两条），且**须在对应脚本/流程里写明这一步**、由使用者决定是否启用；② **无锚点的**（回收站、无声明的跨项目缓存、用户数据）：**不设自动时机**，只在"占用已定位 + 归属已确认 + 可重建已判"三件齐备时由人**定点触发**，不预先排期。判定标准（任一命中即违规）：把无锚点对象写进定时/自动清理脚本、**把锚点到来当成"到点就清"跳过保留价值判定**、有锚点对象只在磁盘告急时才想起清、脚本里既不写清理步骤也不说明为何不写。

* **临时产物按保留价值判、不以所在目录或文件形态定去留（L1）**：`tmp/` 里的东西到期是否清，**判据是"是否仍有保留价值"，不是"它在临时目录里""它是不是文档"**——**任何形态**（文档、数据、脚本、配置、外部来源副本、中间产物、二进制产物）一律按同一判据：仍被后续会话、其它任务或交付物用到的（**保留价值未失效**）**保留**，不因"任务结束"或"临时"就清——**但"保留"不等于把 `tmp/` 当持久落点**：需要跨会话继续成立的信息仍须落项目入口文档与任务单（见 `specs/core/execution.adoc`「要跨会话继续成立的信息不落临时产物（L1）」），此处只是说在持久落点承接之前、那份仍在用的原件不先删；确无保留价值的，可重建的（"用毕即删"的"用毕"指保留价值已失效）随锚点清，不可重建的先落持久落点再清。判定标准（任一命中即违规）：以"在 `tmp/` 里"或"不是文档"为由清掉仍有价值的内容、把有保留价值的数据/脚本/副本按"任务结束"一并扫掉、以保留为名无限期囤积明显无用的临时产物。

* **可重建不等于该清，清前一律先判"后续是否还有用"（L1）**：「可重建性判定：有声明锁得住才可清」给出的可重建性只是"可清"的**必要条件、不是充分条件**——**"清了之后后面还有没有用"（即保留价值，「临时产物按保留价值判」给出的判据）跨所有类别统一成立**。**构建/增量中间产物即便能从源码原样重建，也不因"可重建"或锚点到来就清**：**清掉会显著拖慢后续构建（编译速度等）、缓存仍有效（源码/配置未变）、或仍被其它任务/工具引用**的属**后续仍有用**，**保留**——重建代价与被后续依赖**计为一种保留价值**，**不得为腾空间或"到点"就清**。**只有后续已无用**（对应源码/配置已变、缓存已失效、无后续引用）或确需腾挪并经破坏性操作确认的，才按「先定位再动手、走原生命令、禁通配扫删」走生态原生 `clean`/修剪清。判定标准（任一命中即违规）：仅凭"能重建"或"任务结束/锚点到了"就清增量编译目录与构建缓存、清掉源码未变仍被后续构建复用的缓存、明知"重建很慢/后面还要用"仍以"可重建"为由直接清。

== 超时与资源

* **流水线不无界挂起（L1）**：平台流水线的 job/step **须有可判定的超时**，不得长期停在 pending 而不失败——"在跑"与"卡住"必须可分辨。
* **每一步都须能查到时限、且须有可核对的抓手（L1）**：流水线的**每一个执行单位**都须能查到**可判定的时限**——**执行单位即 job、stage、step 这三个层级**——取值＝"该单位含时限键"这一状态（**时限可设在该单位自己身上、也可设在其外层容器上**：平台的时限语义即"最近的那个生效、多个时取更严者"）。**"整条流水线有个大致时限"不算**：要能指出**每一个单位**的时限在哪。"在跑"与"卡住"必须可分辨（本条是上方「流水线不无界挂起」的取值细化，两条不替代）。**判定标准（逐条可核对，任一命中即违规）**：① 某个执行单位查不到时限键；② 核不到时限**却按"它一般很快"记作已设**；③ 以"平台有默认时限"顶替本条（默认值不属"该单位声明了时限"，不同平台默认值还各不相同）。**实现件与用法**：本仓库的抓手是随规范分发的 `script/guard/`（配置侧守卫按各平台配置逐个执行单位核时限；运行侧包装给每次命令执行套墙钟时限），**怎么用属执行动作、写在该工具自己的文档头里，本条只定取值**。
* **长流程须有可判定的进展信号（L1）**：为耗时步骤设可判定的进展标记与超时；等待期间不得空转（见 `specs/general/context.adoc`「执行吞吐」）。
* **非流水线的操作同口径（L1）**：本节两条所定的超时与进展信号口径，对**非流水线的每一次操作**（命令、构建、读取、网络等待等）**同样成立**——包括超时后的处置。**本条只定"流水线之外也适用"**，规则本体（时限取值、超时后排查并换手段继续、判定标准与依据）见 `specs/general/collab.adoc`「操作超时与超时后的处置」，不在此另立一套。
* **资源与并发**：同一模块禁止并行构建（多 agent 或矩阵构建时须串行化冲突步骤）；缓存与制品按需使用，不重复下载（见 `specs/general/context.adoc`「执行吞吐」的『本地缓存与镜像就近取用』）。
