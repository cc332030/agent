= CI/CD 规范（通用层）

以下规范适用于 CI/CD（持续集成/部署，含 GitHub Actions、CNB、Jenkins 等流水线）配置的编写与调优。某技术栈/平台的构建细节见 `specs/stack/`、`specs/platform/` 对应文件。

适用范围：**编写/调优 CI/CD 脚本时即须遵守本规范**（agent 开发、AI 生成或修改流水线时都按本规范一次写对，不得先写出会用默认运行时试探/可能失败的流水线、等跑失败再调）；**CI 内调用 AI 执行任务**（如自动生成/修复脚本、处理构建）时，该 AI 亦须遵守通用 agent 规范与本规范。

== 核心原则

* CI/CD 配置核心是**不走弯路**：按**最标准、最准确**的方式一次做对，**高效率、高质量**完成——先确认项目真实的构建/运行时要求再执行，不靠默认值试探、不走"失败后再修正"的弯路；宁可开始时多花一点时间确认准确配置，也不把核时浪费在反复试错上（下各节为"不走弯路"的具体实践）

== 运行时版本一次选对

* **开头即用构建文件声明的运行时版本**：流水线运行构建/测试前，先从构建配置读取项目**声明的运行时版本**——Java/Maven 读 `pom.xml` 的 `java.version`/`maven.compiler.source`/`<properties>`，Node 读 `package.json` 的 `engines` 或 `.nvmrc`，GitHub Actions 用 `actions/setup-java`/`setup-node` 设对应版本——**一开始就 setup 正确的版本再跑**；**不得先用默认/最新运行时试探**（如默认 JDK17 跑失败再换 JDK8，会白耗整轮核时、拉长等待）
* **失败先核对版本再换**：构建失败时，先核对构建文件声明的运行时版本与实际是否一致，再决定是否调整，避免"换版本→失败→再换"的盲目重试

== 其他实践

* 依赖/工具版本固定：CI 中依赖、运行时、构建工具固定到经实际验证的具体版本，不用 `latest`/浮动版本（浮动版本可能解析到无对应产物的新版，见 link:../general/verify.adoc[]「外部资源可用性验证」）
* 早失败：多步流水线把快速校验（编译、静态检查、关键前置）放前，尽早失败，避免后续无谓执行浪费核时
* 缓存依赖：可复用的依赖缓存（Maven 本地仓库、npm cache 等）用 CI 缓存机制，减少重复下载与核时
