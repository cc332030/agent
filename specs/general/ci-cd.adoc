= CI/CD 规范（通用层）

适用于 CI/CD（持续集成/部署，含 GitHub Actions、CNB、Jenkins 等流水线）配置的编写与调优；同时约束**开发与验证时使用的运行环境**。某技术栈/平台的构建细节见 `specs/stack/`、`specs/platform/` 对应文件。依据：The Twelve-Factor App（构建/发布/运行分离与配置外置）、GitHub Actions 官方文档、DORA 的交付流水线研究。

== 核心原则

CI/CD 配置核心是**不走弯路**：按**最标准、最准确**的方式一次做对——先确认项目真实的构建/运行时要求再执行，不靠默认值试探、不走"失败后再修正"的弯路。

== 运行时版本一次选对

* **开头即用构建文件声明的运行时版本**：流水线运行构建/测试前，先从构建配置读取项目**声明的运行时版本**——Java/Maven 读 `pom.xml` 的 `java.version`/`maven.compiler.source`，Node 读 `package.json` 的 `engines` 或 `.nvmrc`，GitHub Actions 用 `actions/setup-java`/`setup-node` 设对应版本——**一开始就 setup 正确的版本再跑**；**不得先用默认/最新运行时试探**。
* **失败先核对版本再换**：构建失败时，先核对构建文件声明的运行时版本与实际是否一致，再决定是否调整。

== 运行环境须与项目声明一致

运行环境（语言运行时与构建工具的版本，如 jdk1.8、python2）在项目里有**唯一声明落点**，开发与验证一律用它——**严禁使用与声明不同的运行环境**，**即使换一个版本也能正常跑通流程，也不得换**。

* **先按项目声明取环境，不得按"能跑通"选版本（L1）**：动手写代码、跑构建、跑测试、执行脚本之前，先取定项目**声明的**运行时/构建工具版本，并**全程用同一个版本**——不得改用其他版本、不得用"等价/兼容/近似"的版本顶替、不得用环境的默认版本或最新版本试探；**"换一个版本也跑得通""流程正常结束"都不构成换版本的理由**（换版本会改变产物、行为与测试结论的可信度）。**判定标准（任一命中即违规）**：① 执行构建/测试/脚本所用版本与项目声明**不一致**（含大版本相同、小版本/补丁版本不同）；② 用"另一个版本也跑通了""CI 上跑的版本不同但绿了"为由继续推进；③ 环境声明缺失时不先确认、直接用环境默认版本开工。依据：ISO/IEC/IEEE 29148（需求须单一、可验证、可追溯）、The Twelve-Factor App（dev/prod parity）、Semantic Versioning 2.0.0。
* **声明落点：按项目实际形态取，不另立第二真源（L1）**：一律取项目**已有声明**的落点——Java/Maven 取 `pom.xml` 的 `java.version`/`maven.compiler.release`/`maven.compiler.source`/`maven.compiler.target`、Maven Toolchains 的 `toolchains.xml`；Node 取 `.nvmrc`/`.node-version`/`package.json` 的 `engines`；Python 取 `.python-version`/`pyproject.toml` 的 `requires-python`/`setup.py` 的 `python_requires`/shebang；其他栈取 `.sdkmanrc`、`.ruby-version`、`.tool-versions`、`go.mod` 的 `go`；此外项目的 README/项目自身规范/CI 配置里写明的"环境要求"同为声明。**不得**为满足本条另建一份版本声明（多一份必然漂移）；声明之间冲突时**先停下确认**、不得自行择一。依据：ISO 10007（配置项与变更须有单一、受控的来源）。
* **环境不可得或未声明时走降级路径，不阻断、也不记作通过（L1）**：① 项目**未声明**运行环境：先按上条再找一遍声明落点，仍找不到时**先确认**要用的版本；② 声明环境在**当前环境确实装不出来**：如实说明"声明环境不可用 + 实际用的环境"，并把该次**验证结论标为未确证**（不得记为通过）；③ 确需临时用另一版本定位问题时**只作诊断**，结论须回到声明环境复核后才能用于交付。**不得**因环境不匹配就跳过验证、改判既有用例或删减用例。
* **与 CI 的关系**：流水线里"开头即用项目声明的版本"见上「运行时版本一次选对」；本节把同一口径扩到**本机开发与所有验证**（两个场景共用一个声明落点）。**验证对象须钉定到具体版本与 commit sha**（见 `specs/general/verify.adoc`「编译/运行验证」）。

== 校验链完整（定义未执行防线）

* **流水线须执行项目的全部既定校验，不得只跑一部分（L1）**：流水线须把项目**声明的全部校验手段**接进 CI——编译/构建、静态检查、**配套测试（单元测试与各专项测试）**、规范/完整性机械校验。**只跑主校验脚本、把配套测试留在本地手工跑，等于"定义了却没执行"**。判定口径：**"项目有测试"≠"CI 跑了测试"**——须在流水线配置里能指出"哪一步跑了哪套测试"。
* **测试文件须能被测试框架自动发现（L1）**：进入 CI 的测试文件，其**命名与位置必须落在所用测试框架的默认发现规则内**（Python `unittest discover -p '*_test.py'` 要求模块名可导入，含连字符的文件名无法被导入、会被静默跳过；Java/Maven 须落在 surefire/failsafe 的默认 includes 内）。**不得依赖"我本地单独执行过"来证明测试有效**——须用框架的发现命令核对"发现到的用例数与实际用例数一致"。
* **校验手段依赖的工具须在本地实际装齐、不得因缺工具而静默跳过（L1）**：项目的每项既定校验手段都**依赖具体的工具**（语法/格式编译、静态检查、规范校验脚本的运行时等）。**动手跑校验之前先探测这些工具在不在**；**缺就装齐再跑——不得把"环境里没有"变成"自动跳过"**：让检查脚本在缺工具时打印一句提示、然后照常以退出码 0 结束，等于**声明的校验手段从未执行、而输出看起来是绿的**（最隐蔽的一类假绿）。**判定标准（任一命中即违规）**：① 检查脚本里对缺工具走"跳过/提示"分支、且该分支不影响退出码；② 校验手段的依赖工具在本地或 CI 里没有任何安装步骤；③ 只在文档里写"建议安装"，脚本与 CI 都不核"工具在不在"。**降级路径（L2）**：工具确实装不上（离线、无权限、平台不提供）时，按"尽力而为"**如实标『未执行 + 原因 + 替代做法』**，**不得记作通过**（判据见 `specs/general/verify.adoc`「判准维度」）；**"装不上"不是"不用装"**——不得以此为由把这条校验从校验链里删掉。**安装方式须随要求一起给出**（命令级，且落到 CI 的可执行步骤）：只写"须检查语法"而不写"用什么检查、怎么装"时，执行者装不上就只能跳过。**示例（本仓库的取值）**：AsciiDoc 语法验证用 `gem install asciidoctor`（Ruby 实现，带 `--failure-level=WARN`）；只想用 Python 时 `pip install asciidoc` 亦可，但它**没有** `--failure-level`（缺 `include::` 目标时只告警、仍返回 0），故这一半效力降级。
* **CI 加的步骤须是确定性且必过的（L2）**：**不在 CI 中调用会给出非确定性结论的外部 AI/网络服务来阻塞构建**——语义审查这类启发式判断交人工 review。
* **CI 只做守护、不代改（L2）**：CI 负责判定与报告，**不默认改动仓库内容、不代为提交、不自动合并**。

== 触发与作用范围

* **触发路径须覆盖校验对象（L1）**：流水线的触发条件（`on.push.paths`/`on.pull_request.paths`）必须**覆盖其校验的全部对象**——被校验的文件/目录发生变更时必须能触发该流水线；变更被校验范围后须核对触发路径同步更新。
* **路径过滤与校验范围一致（L2）**：避免两类偏差——① 触发过窄（改了却不跑，漏检）；② 触发过宽（无关改动也跑，浪费核时）。校验对象用集中常量/锚点声明，使两处不易各自漂移。

== 依赖与外部资源可用性

* **上游依赖（镜像/制品/工具）须先确认实际可用（L1）**：流水线引用的容器镜像、制品包、外部工具，须**在配置时确认其真实存在且可取到**，不得凭名称假设可用。选型时优先用**已发布、可访问、版本固定**的产物。
* **依赖/工具版本固定**：CI 中依赖、运行时、构建工具固定到经实际验证的具体版本，不用 `latest`/浮动版本；**取源次序与"先实测再启用"按** `specs/general/dependency.adoc`「包源（包仓库/镜像站）的选用」执行（缺则流水线仍会直连境外源）。

== 超时与资源

* **流水线不无界挂起（L1）**：平台流水线的 job/step **须有可判定的超时**，不得长期停在 pending 而不失败——"在跑"与"卡住"必须可分辨。
* **长流程须有可判定的进展信号（L1）**：为耗时步骤设可判定的进展标记与超时；等待期间不得空转（见 `specs/general/context.adoc`「执行吞吐」）。
* **资源与并发**：同一模块禁止并行构建（多 agent 或矩阵构建时须串行化冲突步骤）；缓存与制品按需使用，不重复下载（见 `specs/general/context.adoc`「执行吞吐」的『本地缓存与镜像就近取用』）。
