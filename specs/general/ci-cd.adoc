= CI/CD 规范（通用层）

以下规范适用于 CI/CD（持续集成/部署，含 GitHub Actions、CNB、Jenkins 等流水线）配置的编写与调优。某技术栈/平台的构建细节见 `specs/stack/`、`specs/platform/` 对应文件。（依据：The Twelve-Factor App 关于"构建/发布/运行"分离与配置外置的原则，GitHub Actions 官方文档 关于 setup/缓存/版本固定的实践，DORA 关于交付流水线的研究）

适用范围：**编写/调优 CI/CD 脚本时即须遵守本规范**（agent 开发、AI 生成或修改流水线时都按本规范一次写对，不得先写出会用默认运行时试探/可能失败的流水线、等跑失败再调）；**CI 内调用 AI 执行任务**（如自动生成/修复脚本、处理构建）时，该 AI 亦须遵守通用 agent 规范与本规范。

== 核心原则

* CI/CD 配置核心是**不走弯路**：按**最标准、最准确**的方式一次做对，**高效率、高质量**完成——先确认项目真实的构建/运行时要求再执行，不靠默认值试探、不走"失败后再修正"的弯路；宁可开始时多花一点时间确认准确配置，也不把核时浪费在反复试错上（下各节为"不走弯路"的具体实践）

== 运行时版本一次选对

* **开头即用构建文件声明的运行时版本**：流水线运行构建/测试前，先从构建配置读取项目**声明的运行时版本**——Java/Maven 读 `pom.xml` 的 `java.version`/`maven.compiler.source`/`<properties>`，Node 读 `package.json` 的 `engines` 或 `.nvmrc`，GitHub Actions 用 `actions/setup-java`/`setup-node` 设对应版本——**一开始就 setup 正确的版本再跑**；**不得先用默认/最新运行时试探**（如默认 JDK17 跑失败再换 JDK8，会白耗整轮核时、拉长等待）
* **失败先核对版本再换**：构建失败时，先核对构建文件声明的运行时版本与实际是否一致，再决定是否调整，避免"换版本→失败→再换"的盲目重试

== 运行环境须与项目声明一致

运行环境（语言运行时与构建工具的版本，如 jdk1.8、python2）在项目里有**唯一声明落点**，开发与验证一律用它——**严禁使用与声明不同的运行环境**，**即使换一个版本也能正常跑通流程，也不得换**（"能跑通"不是换版本的正当理由，见下「判定标准」）。

* **先按项目声明取环境，不得按"能跑通"选版本（L1）**：动手写代码、跑构建、跑测试、执行脚本之前，先取定项目**声明的**运行时/构建工具版本，并**全程用同一个版本**——不得改用其他版本、不得用"等价/兼容/近似"的版本顶替、不得用环境的默认版本或最新版本试探；**"换一个版本也跑得通""流程正常结束"都不构成换版本的理由**（换版本会改变产物、行为与测试结论的可信度，跑通只是"这次没暴露"）。判定标准（任一命中即违规）：①执行构建/测试/脚本所用版本与项目声明**不一致**（含大版本相同、小版本/补丁版本不同）；②用"另一个版本也跑通了""CI 上跑的版本不同但绿了"为由继续推进；③环境声明缺失时不先确认，直接用环境默认版本开工。依据：ISO/IEC/IEEE 29148（需求须单一、可验证、可追溯——"用哪个版本"须可追溯到项目声明）；The Twelve-Factor App（dev/prod parity，开发与运行环境须一致）；Semantic Versioning 2.0.0（行为有变即不是同一版本）。
* **声明落点：按项目实际形态取，不另立第二真源（L1）**：运行环境版本一律取项目**已有声明**的落点——Java/Maven 取 `pom.xml` 的 `java.version`/`maven.compiler.release`/`maven.compiler.source`/`maven.compiler.target`、Maven Toolchains 的 `toolchains.xml`；Node 取 `.nvmrc`/`.node-version`/`package.json` 的 `engines`；Python 取 `.python-version`/`pyproject.toml` 的 `requires-python`/`setup.py` 的 `python_requires`/`requirements` 注释/shebang；其他栈取 `.sdkmanrc`、`.ruby-version`、`.tool-versions`、`go.mod` 的 `go` 等对应清单；此外项目的 README/项目自身规范/CI 配置里写明的"环境要求"同为声明。**不得**为满足本条另建一份版本声明（多一份必然漂移）；声明之间冲突时**先停下确认**、不得自行择一。依据：ISO 10007（配置项与变更须有单一、受控的来源）。
* **环境不可得或未声明时走降级路径，不阻断、也不记作通过（L1）**：①项目**未声明**运行环境：先按上条再找一遍声明落点，仍找不到时**先确认**要用的版本，确认前不得自行假定；②声明环境在**当前环境确实装不出来**（版本已下架、镜像/制品不可取、平台只提供其他版本）：如实说明"声明环境不可用 + 实际用的环境"，并把该次**验证结论标为未确证**（不得记为通过、也不得记为"已按声明环境验证"）；③确需临时用另一版本定位问题（如确认"是不是版本导致的失败"）时，**只作诊断**：结论须回到声明环境复核后才能用于交付。**不得**因环境不匹配就跳过验证、改判既有用例或删减用例。依据：评审与验证须可追溯到可核对的对象（ISO 10007）；判准的"尽力而为"口径见 link:verify.adoc[]「判准维度：严格执行 / 尽力而为」。
* **与 CI 的关系**：流水线里"开头即用项目声明的版本"见上「运行时版本一次选对」；本节把同一口径扩到**本机开发与所有验证**（两个场景共用一个声明落点，不得出现"CI 用声明版本、本地用默认版本"）。**验证对象须钉定到具体版本与 commit sha**（见 link:verify.adoc[]「编译/运行验证」），使"用哪个环境、跑的哪份代码"都可复核。

== 校验链完整（定义未执行防线）

* **流水线须执行项目的全部既定校验，不得只跑一部分（L1）**：流水线须把项目**声明的全部校验手段**接进 CI——编译/构建、静态检查、**配套测试（单元测试与各专项测试）**、规范/完整性机械校验等。**只跑主校验脚本、把配套测试留在本地手工跑，等于"定义了却没执行"**（实证：某 CI job 只运行 `check-specs.py`，配套测试从未在 CI 跑过，其中一个测试文件因命名无法被自动发现、其全部用例长期"零执行"，直到人工 review 才暴露）。判定口径：**"项目有测试"≠"CI 跑了测试"**——须在流水线配置里能指出"哪一步跑了哪套测试"。
* **测试文件须能被测试框架自动发现（L1）**：进入 CI 的测试文件，其**命名与位置必须落在所用测试框架的默认发现规则内**（如 Python `unittest discover -p '*_test.py'` 要求模块名可导入，含连字符的文件名**无法被导入**、会被静默跳过；Java/Maven 须落在 surefire/failsafe 的默认 includes 内）。**不得依赖"我本地单独执行过"来证明测试有效**——须用框架的发现命令核对"发现到的用例数与实际用例数一致"（实证：命名带连字符使 `discover` 只发现 23 例、另一文件的 4 例从未被任何自动运行发现）。
* **CI 加的步骤须是确定性且必过的（L2）**：CI 的失败应可归因、可复现。**不在 CI 中调用会给出非确定性结论的外部 AI/网络服务来阻塞构建**——语义审查这类启发式判断交人工 review，否则构建会因"模型这次说了什么"而随机红绿。
* **CI 只做守护、不代改（L2）**：CI 负责判定与报告，**不默认改动仓库内容、不代为提交、不自动合并**（合并与内容决策交人；参见 link:verify.adoc[]「运行契约」③可控性）。

== 触发与作用范围

* **触发路径须覆盖校验对象（L1）**：流水线的触发条件（`on.push.paths`/`on.pull_request.paths` 等）必须**覆盖其校验的全部对象**——被校验的文件/目录发生变更时必须能触发该流水线，否则改坏了也不跑（如校验某目录，触发路径就须含该目录下的全部文件模式；新增校验目录时同步补触发路径）。变更被校验范围后须核对触发路径同步更新。
* **路径过滤与校验范围一致（L2）**：避免两类偏差——①触发过窄（改了却不跑，漏检）；②触发过宽（无关改动也跑，浪费核时）。校验对象用集中常量/锚点声明，使两处不易各自漂移。

== 依赖与外部资源可用性

* **上游依赖（镜像/制品/工具）须先确认实际可用（L1）**：流水线引用的容器镜像、制品包、外部工具，须**在配置时确认其真实存在且可取到**，不得凭名称假设可用（实证：某流水线在 `Prepare` 阶段 `docker pull` 报 `resource not found: package ... not found`，整条构建在准备阶段即失败，与被校验的内容无关）。选型时优先用**已发布、可访问、版本固定**的产物。
* **依赖/工具版本固定**：CI 中依赖、运行时、构建工具固定到经实际验证的具体版本，不用 `latest`/浮动版本（浮动版本可能解析到无对应产物的新版；外部资源须实际验证可用见 link:verify.adoc[]「编译/运行验证」）。
* **镜像与语言运行时的下载源同样按次序选、先实测（L1）**：流水线里 `docker pull` 的镜像、`setup-*` 动作下载的语言运行时/SDK、系统包（`apt`/`apk`/`yum`）、语言包源（Maven/npm/pip…）都按 link:dependency.adoc[]「包源（包仓库/镜像站）的选用」取源——**先就近（平台内已优化的源，如云厂商内网 registry mirror）→ 境内公共源 → 邻近境外源 → 更远境外源**，**每级启用前先实测可用**（取一个确定存在的产物），**已配置过即沿用**；镜像站与源地址的**实测取值与取样条件**属依据，落点见图书馆「包源与镜像源」主题（**依据名：包源与镜像源（推荐次序与实测记录）**；**图书馆不在公共引用面内**，此处只留依据名与判据，不给可点开的路径）。
* **镜像源的改动须写进流水线配置、不靠每次临时手写（L1）**：换源要**一次配置到位**（写进 `.cnb.yml`/workflow 的装配步骤或项目配置），**不得**在每次运行时临时拼命令或反复重试同一个源（重复重试是核时与往返的重复开支）；换源后仍要**跑一次真实取用**确认配置真的生效（"换了源但配置没被工具读到"是高频失效形态）。
* **失败须指向可归因的阶段（L2）**：外部依赖不可用导致的失败，应在报告里能区分"环境/依赖问题"与"被校验内容问题"——前者不应被误读为"内容不合格"，后者也不得被当成"环境抖动"忽略。

== 超时与资源

* **每次执行须有可判定的超时（L1）**：job/step 须设**可判定的时限**（数值按任务正常耗时的若干倍取值），到点即失败并给出超时信息——**不得让任务无限等待**（实证：某任务长期停在 `pending`、阶段耗时 0 推进 1 小时以上，发起方只能人工中止；无超时机制时"卡住"与"在跑"无法区分）。子 agent/外部调用同理（见 link:collab.adoc[] 的失联感知与硬超时条）。
* **资源量级与任务匹配（L2）**：并发、并行度、缓存与超时设置按任务规模取值，不设"看着办"的默认值；机制自身的开销须可核对（见 link:verify.adoc[]「验证总纲」②性能维度）。

== 其他实践

* 早失败：多步流水线把快速校验（编译、静态检查、关键前置）放前，尽早失败，避免后续无谓执行浪费核时
* 缓存依赖：可复用的依赖缓存（Maven 本地仓库、npm cache 等）用 CI 缓存机制，减少重复下载与核时
* **CI 配置本身也守规范（L2）**：CI 脚本/配置的命名、行尾、编码、注释等按通用脚本规范（link:script.adoc[]）与编码规范（link:encoding.adoc[]）执行——如 `.bat`/`.ps1` 行尾按平台取值，YAML 用 LF。
