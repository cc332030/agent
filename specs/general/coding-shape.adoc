= 通用编码规范·写法与结构（通用层，跨语言）

本文件是通用编码规范的一族之一（**按主题拆分**，其余见同目录 `coding.adoc`、`coding-objects.adoc`、`coding-ui.adoc`、`coding-runtime.adoc`、`coding-source.adoc`、`coding-file-role.adoc`）：表达式与调用的写法、类设计与命名；数据与对象见 `coding-objects.adoc`。

== 表达式与调用写法

* **实参不内联复杂逻辑与对象（L1）**：方法调用实参只传简单值或已算好的局部变量，不内联复杂逻辑（三元表达式、方法调用嵌套、多级 `.xxx()` 串联），也禁止内联对象初始化后直接作为入参；复杂计算与对象必须先创建为局部变量再传入。无参构造除外。
* **三元表达式为最低优先级（L1）**：只要存在其他可替代写法（工具方法、if-else、辅助函数、`||`/`or` 兜底），就**绝不用三段式**；仅当既无现成工具方法、又无更清晰的替代写法时才允许用，且**只允许简单三元**——`条件 ? 值 : 值` 三个位置各是一个原子（变量、字面量、常量或字段取值），**三个位置都不带任何运算、不带任何函数调用**。带运算或调用的（`a + b`、`x?.y()`、`i++`、长度/大小取值、多级 `.xxx()` 串联）、嵌套三元、多分支一律改用 if-else 或工具方法，可读性优先于行数。**怎么判「简单」（任一命中即不是简单三元）**：把三个位置分别取出来，各自能一眼读成「一个东西」才算过——① 任一位置出现运算符（算术、比较、拼接、自增自减）；② 任一位置出现调用括号（含工具方法与标准库方法）；③ 任一位置出现索引/属性串联，或本身是嵌套三元、分支超过两支。

**重构也照此办（L1）**：本节全部条款对**任何**写下来的代码生效，**不区分「写新代码」与「重写既有代码」**——重构、搬动、拆分、整理结构、改措辞、顺手清理时**写下的那一段同样是本次写的代码**，该换工具方法就换、该改 if-else 就改，**不得**因为「我只把它搬了个位置」「原来就这么写的」「改动越小越好」而把三段式原样带过去。**判定标准（任一命中即违规）**：① 本次**新增或改写**的那一行里出现三段式（含把原三段式搬进新方法、新分支、新变量）；② 以「保持原样、减少 diff」为由保留该处三段式。

**例外与边界（L2）**：① 本次改动**只搬动、不改内容**时，先按本节判「换不换得动」——换得动就换，确实换不动（该语言无现成工具方法、表达式本身就是单个原子取值）时**原样搬动**，这是本节的正当例外、不算违规；② **未触达的存量**照旧随动迁移，不为清三段式发动全库改造（见 `specs/core/execution.adoc`「规范变更的存量处理」）。

**理由**：此前缺的不是「知不知道这条」，而是**「写新代码」与「重写代码」被当成了两套规则**——重构时只盯着行为不变，同一句三段式被原样搬进新结构，读的人在新代码里看到的仍是旧写法，这条规则对本次写的代码等于不成立。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性、可分析性）、ISO/IEC/IEEE 29148（判定须可验证）、Martin Fowler《Refactoring》（重构的取值是「行为不变而结构变好」，不是「原样搬过来」）。**「重构时写下的那一段同样受本节约束、换得动就换」是本集合的判据化取值**——Fowler 只要求行为不变，**未**规定写法判据在重构里还适不适用。
* **不得新增只做条件取值的方法（L1）**：**新增方法时，不得让方法体只剩一处条件取值**——即方法的存在只为在一个表达式里挑一个值（本次改动的取值来自多个来源、按空值或取值有无二选一，典型是「传进来一个对象就取它的、为空就取外层/默认的」）。

**理由**：这类方法**没有自己的语义**（名字只是把那次挑选复述一遍）、只把同一个取值逻辑从调用点搬了个位置，**每次取值都要多跳一次**；而「空则取默认值」在标准库、项目自有工具类与已引入工具库（`defaultIfNull`/`defaultIfEmpty`/`emptyToDefault` 一类）里**已有现成入口**，缺的只是**加一个通用工具方法**（一处定义、全项目复用），不是就地为这一次调用造一个专用方法。**判定标准（任一命中即违规）**：① 新增的方法体只有一处条件表达式（三元、`if/else` 后 `return`、`??`/`or` 兜底之一）且其中一支只是「取另一个来源的同一个值」；② 以「调用点会更短」「复述一下意图」「这个方法以后可能有用」为由抽取该方法。**不得反向放大**：**有自身语义的取值方法（做计算、转换、多来源合成、按业务规则决定取值）不受本条约束**。

**例外与边界（L2）**：① **该处已有先例**（同类专用方法在本项目里已成惯例）时跟随先例；② 该语言/框架**没有现成的兜底入口、也无通用工具方法可用**时，**先加通用工具方法**（一处、可复用），仍不成立才允许就地抽取；③ **响应式/流式管线**（在链式操作符里取值）等写不进通用工具的场合不受本条约束。

**存量边界（L1）**：**既有此类方法**保持原样，改到哪处才顺带调整；**不得**据此发动全库改造（批量内联、批量删方法）（随动迁移，见 `specs/core/execution.adoc`）。
* **链式调用一律换行（L1）**：调用链（同一表达式里连续的方法/属性调用，如 `a.b().c().d()`、`o.getX().getY()`、流式 `stream()...collect(...)`、builder 链、可选链 `?.`）**每个环节各占一行、`.` 起头**；**长度不是判据**——再短的链也换行，**不得**因为「这行放得下」而写成一行。**判定标准（任一命中即违规）**：① 同一行里出现**两处及以上**的调用链环节；② 以「很短」「一屏放得下」「拆开反而更占行数」为由保持单行。

**例外（L2）**：该链是**单个不可再分的原子表达式**的一部分（如仅一层调用 `a.b()`、链本身就是语言内置的惯用写法如 `String.valueOf` 一类纯取值、注解或常量声明里受语法限制的场合），以及**测试断言**里单层的 `assertXxx(x.y())`。

**边界（防反用）**：本条**只规定换行形态、不改变求值语义与调用顺序**，不得借换行把一条链拆成多个中间变量而丢失链式语义时仍声称「已换行」；也不得据此要求把链改写成分步 `return`（那是另一件事）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性、可分析性：一屏内的结构信息量与最小惊讶原则）、ISO/IEC/IEEE 29148（判定须可验证）、Google Java Style Guide 与《阿里巴巴 Java 开发手册》（链式调用换行属通行风格要求）。**「哪怕很短也要换行」是本集合的判据化取值**——通行风格指南通常按**行宽**决定是否换行，本条取更严的单一形态，免去「多短算短」的裁量。
* **判空/默认值兜底优先用工具方法**：对"空则取默认值"这类兜底，有现成工具方法（`defaultIfNull`/`defaultIfEmpty`/`emptyToDefault` 之类）时**强制使用**；**没有现成工具方法时，取值的去向是「加一个通用工具方法」，而不是就地写三段式或就地为这一次调用抽一个专用方法**（通用工具方法一处定义、全项目复用；上条「不得新增只做条件取值的方法」同此去向）；该语言无通用工具可加时，才退回语言内置兜底（`||`/`or`）或 if-else；以上均不可用时才退回三段式。**判定标准（任一命中即违规）**：① 已有等价工具方法（标准库、项目自有、已引入工具库）仍手写三段式；② 多次需要同一兜底时逐处内联或逐处抽专用方法，而未收敛到一个通用工具方法。

**例外与边界（L2）**：**该处已有先例**（项目里同类兜底已统一走某个方法）时跟随先例，不再另立一个通用方法。

**存量边界**：见上条（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：Martin Fowler《Refactoring》（重复代码与「数据泥团」的取向是收敛到一处）、ISO/IEC 25010（可维护性）、ISO/IEC/IEEE 29148（判定须可验证）。**「没有现成工具方法就加一个通用方法、不就地抽专用方法」是本集合自己的判据化取舍**——通行做法只要求「不必重复手写」，**未**规定去向是通用工具方法而非专用方法。

== 类设计

* **纯数据结构类中不写逻辑**：仅保留字段与简单的字段读写，不做计算、组装、格式转换、对外部对象的访问；需要时下沉到工具类或独立服务。识别特征：以 bean/model/pojo/dto/vo/entity 等命名的类，其方法中出现非字段读写的计算/转换/组装逻辑。
* **配置类不写逻辑（L1）**：各类承载配置的类（如 Spring `@ConfigurationProperties`、`@Configuration`）除声明配置项与按配置装配对象外，**不得包含任何逻辑**——任何情况都不允许，无例外；配置类只保持纯数据对象（POJO）的基本功能（字段及其访问器；`@Configuration` 另可按需声明 `@Bean` 装配方法），需计算/转换/组装时下沉到工具类或服务中。**判定标准**：① 不得出现条件分支（`if`/`switch`/三元等）与循环；② 不得做格式转换、数据加工、对外部对象或远程资源的访问；③ `@Bean` 方法须是「构造/装配」形态——构造依赖由容器注入、不得自行查找（如 `getBean`），装配只允许配置项到构造参数的传递（取值时按「表达式与调用写法」用工具方法或语言内置写法，不写分支、不做计算）。识别特征：以 Config/Properties/Options/Settings 等命名的类。

**存量处理**：本条严于框架常规用法（随动迁移，见 `specs/core/execution.adoc`）。
* **有开关控制的逻辑**：先判断开关，开关关闭时直接跳过，不在开关外做耗时操作（取时间戳、拼字符串、访问外部资源）；开关关闭即零成本。识别特征：布尔配置项之后接的代码块，整段逻辑应包在开关判断内，或开关判断前置 `return`。
* **工具类不继承另一个工具类（L1，任何语言）**：承载**通用静态工具方法**的类（下称工具类，各语言里以 `Utils`/`Util`/`Helper` 一类命名、只放静态方法的类）**不得继承另一个工具类**——不得以 `extends`/`:` 继承、也不得让一个工具类派生自另一个工具类；**继承链里不得出现两个工具类相邻**。

**理由**：工具类的能力面应当是**平铺、可按名直接找到**的一组静态入口——一个抽象基类把「哪些方法从哪来」藏进继承链后，调用点读到的方法不属于它自己的类、搜索与跳转都落不到定义处，同一个方法还会随继承关系出现多个可达路径；而工具类本就**无状态、无多态**（不需要被按父类型使用），继承能给的只是「少写一次签名」，换来的是一层**隐藏的、只增不减的**耦合（改基类即改全部子类）。**工具类的公共部分用两个入口收敛**：① **组合**——把公共逻辑放进**被调用的那个工具类**，由另一处工具方法直接调用它；② **静态导入**——同语言支持时按名直接引用。**判定标准（任一命中即违规）**：① 被继承者与继承者都是工具类（不论继承者是否另加了方法、是否为 `abstract`）；② 以「公共方法抽到基类里」为由建工具类基类；③ 以前缀、导入清单或「方法都还调得到」为由不处理。

**边界（L2，防反用）**：本条**只管工具类之间的继承**——非工具类的正常继承（模板方法、抽象基类、框架基类）、以及工具类**实现接口**（如 `Comparable`、框架要求的回调接口）不受本条约束；工具类里对一个**第三方工具库同名类**的扩展/对应类（如 JDK 静态类的补齐类）按项目既有约定处理，不据此改名或改建。

**存量边界（L1）**：**既有这类继承**保持原样，改到哪处才顺带调整；**不得**据此发动全库改造（批量拆基类、批量挪方法）（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性、可分析性——能力面须可直接定位）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Effective Java「组合优于继承」（继承是「实现复用」的捷径，但把复用写进类型层级后即锁死演进）。**「工具类不得继承工具类」是本集合自己的判据化取舍**——通行材料只给「组合优于继承」的方向，未把工具类单列。
* **没有多态时不得为 service 类加同方法父接口（L1，任何语言）**：一个 **service 类**（承载业务逻辑的服务实现类，控制器调用的那一层）**只有它一个实现**、且没有人按父类型使用它时，**不得**为它另建一个**声明了同样的方法**的父接口——即不为「接口 + 唯一实现」这种两件套而建接口：类上写 `implements XxxService`（或各语言的等价形态）、接口里逐条重复该类的公开方法签名，属本条禁止面。**「没有多态」的判据**：本次改动里**只有一个实现类**实现该接口，**且没有任何注入点、参数、返回值或集合以该接口类型声明**（注入/声明全用实现类本身即命中）。

**理由**：接口的全部价值是**让调用方只依赖契约、由多态决定跑哪一份实现**——没有第二个实现、也没有调用方按父类型依赖时，接口**不承担任何替换与解耦**，能给的只剩「多一个文件、多一份方法清单」；而这份清单还会与类**逐条重复**，改方法即改两处（漏一处则编译不过、看着像"有保障"，实际只是把同一次改动抄两遍），读的人却要在两个文件之间来回对照才能知道这个方法到底是干什么的。**没有多态时的去向是「直接用该类」**——需要区分能力面时用该类的**自己的一组成员方法**表达，不为凑形态而拆接口。

**例外（L2，须写清理由并说明用了哪一条）**：① **存在（或本次一并引入）第二个实现**，或接口是**实现方按契约提供、由调用方按父类型取用**的场合（如 Spring Data 仓储接口这类**框架由接口生成实现**的契约、声明式 HTTP 客户端契约、RPC 服务契约）——这些接口的**实现不写在本次代码里、父类型本来就成立**，不受本条约束；② **接口上挂了框架能力**（事务/校验/代理/切面等注解或框架按接口生成代理的能力）；③ **该处已有先例**（本项目同类 service 一律「接口 + 实现」成对出现）时跟随先例，**不为此把已发布的接口删掉**。

**判定标准（任一命中即违规）**：① 新增（或本次重构新抽出）的 service 接口**只有一个实现类**，且**没有任何注入点/参数/返回值/集合以该接口类型声明**，接口成员与该实现类的公开方法**一一对应**；② 以「面向接口编程」「以后可能换实现」「团队规范这么写」为由自我豁免，而未落到例外；③ 把本条读成「所有接口都不能有唯一实现」而删掉上面例外清单里的契约（**反向误用**：框架由接口生成实现、或接口上挂了框架能力的，不属本条禁止面）。

**边界（防反用）**：本条**只管 service 类的父接口**——工具类、数据对象、枚举、异常类不受本条约束；也**不规定**已有接口必须删除（见下条存量边界）。**「父接口」指被实现的那个接口**，service 类实现框架要求的回调/标记接口（如 `Serializable`）不在本条核对面内。

**存量边界（L1）**：**既有这类接口**保持原样，改到哪处才顺带处置（该处正好重构到、且确无多态时，可并入实现类）；**不得**据此发动全库改造——**批量删接口、批量把注入类型改成实现类**都属此列（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：同一份方法清单只有一个来源）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Robert C. Martin《Clean Code》与 Martin Fowler《Refactoring》（抽象应当由**实际存在的多个实现或替换需求**驱动，而不是为形态而建）、SOLID 的接口隔离原则（契约的价值在调用方只依赖所需能力，无调用方依赖时契约为空转）。**「没有多态时不为 service 类加同方法父接口」是本集合自己的判据化取舍**——通行材料只给「面向接口编程」的方向，**未**规定唯一实现且无人按父类型依赖时该不该留接口。
* **原则上不允许使用内部类**，除非无法代替（回调/监听器、临时组合数据、实现局部接口等确需承载的场景）；能抽为独立顶层类的应抽出去。

== 命名与代码质量

* **NPE 原则**：NPE 问题原则上必须修复（存在取舍时在代码注释中说明取舍依据与边界）。
* **兼容性与平衡**：不因局部小优化牺牲兼容性（语言/运行时版本、操作系统、环境依赖等）；优化与健壮性、可维护性、实用性之间保持平衡。
* **接口/类/注解成员排序**（大小 + 时间 + 复杂度，可同处一个类）：① **按大小**——字段/方法按可存储数据大小/位宽顺序排列（整数按位宽递增、浮点按位宽递增、再 boolean、最后 Object）；② **按时间**——存在逻辑时序时按流程先后、数据加工顺序排列；③ **按复杂度**——简单的在前、复杂/组合/高级用法在后。**不按使用频率、字母序或历史追加顺序随意摆放**。
* **成员与方法次序（L1，任何语言）**：**新增**成员/方法/函数时，其**位置**按「**流程次序**」定——**调用方在前、被调用方在后**（**先初始化的在前**、**先被用到的在前**、**被依赖者在前**：后面的依赖前面的，如 `RestTemplate` 依赖 `ObjectMapper` 时 `ObjectMapper` 排在前）；允许把新增的方法加在**已有成员的前面（含最前面）或中间**，**不得**为「不动已有顺序」而一律追加到类/文件末尾。**重载成员**（同名不同参数）**一律紧邻已有同名成员**（与它相邻），**重载之间的次序同样按流程次序**。**例外（L2）**：① **数据转换方法**（把数据库实体与返回模型互转的那一类）**默认写在查询它的那个接口/方法之后**——**先把查询写出来、再写转换**，不按「被调用者在前」把它提到查询方法**之前**；② 成员次序**决定语义时**（初始化顺序、字段依赖、语言/框架规定的执行顺序）以语义正确为准，本条不适用。

**理由**：位置本身表达「谁先谁后」，读者按读序就能建立流程与依赖链；按「改动追加在末尾」摆放时，同一个类里会出现**多套互相无关的次序**（历史追加序、字母序、随手序），且**新增的位置不报错**、只是次序无声漂移。**判定标准（任一命中即违规）**：① 新增成员被一律追加到类/文件**末尾**，而按其流程次序本可在其他成员**之前或之间**；② 新增成员的调用方排在它**后面**、或它依赖的成员排在它**后面**（如把 `RestTemplate` 写在其依赖的 `ObjectMapper` 之前）；③ 新增**重载**成员与已有同名成员**不相邻**（被别的成员隔开）；④ 数据转换方法排在其**查询接口之前**；⑤ 以「不改动已有顺序」为由自我豁免、把位置选择推给读者。

**边界（防反用）**：本条**只管新增成员的落点位置**——**不要求**为满足本条而**重排**既有成员（那是「存量边界」）；也**不**据此评判既有代码的次序。

**存量边界（L1）**：本条**只对新增成员生效**，**不改动**既有成员的位置，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）；review 时对既有成员的位置不提出问题（全局口径见 `specs/general/review.adoc`「review 的默认检查面」，本条不复述）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：位置即次序信息，同一处不产生第二个次序来源）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Google Java Style Guide 3.4.2（成员次序须是**逻辑次序**、维护者能解释，且**禁止**「新方法习惯性追加到末尾」这类「按加入日期」的次序）。**「按流程次序、可插前面或中间 + 重载相邻 + 转换跟随查询」是本集合的判据化取值**——Google 只禁止「追加在末尾」这一形态、未规定具体落点次序。
* **静态字段排在类最前（L1）**：类中的**静态字段一律排在类体最前面**——在所有实例字段与方法之前，作为整类共享的常量/状态集中可见。**例外（L2，仅此一条）**：某静态字段被**某个方法**直接使用时，允许把它放在**该方法的紧前面**（相当于插在方法之间），使"定义与唯一使用点"相邻；**放与不放都合规**——未这样放**不构成问题**，不得据此判违规（开发者自主决定）。**边界**：例外只放宽**位置**，不放宽"静态字段优先于实例字段"的次序本身；一处静态字段只能有一个位置，不得为迁就多个使用点而复制或反复挪动。**存量边界**：改到某类时才顺带调整其成员/注解次序，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）；某语言**没有静态成员概念**（如纯函数式语言）时本条自然不适用
* **实体类字段按数据库顺序（L1，任何语言）**：映射数据库表的**实体类**（以该语言的持久化映射方式标注——如注解、装饰器、映射声明/映射文件，或项目约定以 entity/model 命名并对应数据表的类）的**字段顺序跟随其映射表的列顺序**（以建表语句/迁移脚本/映射声明中的列序为准），不套用上面的通用次序——便于与表结构、DDL、查询结果逐列对照。**本条覆盖**通用成员排序中"字段次序"的部分；实体类的**注解次序**、**方法的排序**仍按通用规则。若映射表列序无法确定（如由 ORM 自动建表且无显式列序），退回通用次序。
* **链式赋值顺序随字段顺序（L1，任何语言）**：**链式调用**（含 builder 链）里的**赋值环节**（代码里给字段赋值的那些环节，如 lombok 链式 setter、builder 的 `.xxx(...)`），**书写顺序须与字段顺序一致**；**字段顺序**取该条已定义者——**实体类**按「实体类字段按数据库顺序」取映射表的列序，**其他类**按「接口/类/注解成员排序」取该类的成员次序。

**理由**：字段次序是这类对象上唯一已经定下的次序，赋值再排一个序就是同一份字段清单的第二个来源——按字段顺序走，读的人不必回看类定义即可与字段、表结构逐项对照；否则同一次构建里会出现两种次序，且只改了字段、忘了赋值处时**不报错**、只是次序无声漂移。**判定标准（任一命中即违规）**：① 同一处构建的赋值环节次序与字段顺序不一致（含按字母序、按使用频率、按改动追加的次序）；② 以「这样读起来更顺」「顺手先设这两个」为由自行排列；③ 把「字段顺序」读成「本条的专用顺序」而不回指上两条（那等于本条自成第二个来源）。

**例外（L2）**：① 赋值环节的**执行次序决定语义**时（后一次赋值覆盖前一次、后设的值依赖前设的值）以语义正确为准，本条不适用；② 只赋值其中一部分字段、或同一字段赋值多次时，**按所选字段在字段顺序里的相对先后**核对，不要求把它们排成连续的一段。

**边界（防反用）**：本条**只规定赋值环节的书写次序、不改变求值语义**，也不要求为满足本条的次序而多写一次赋值或拆成多个中间变量。

**存量边界**：改到哪处才顺带调整该处的次序，**不发动全库重排**（随动迁移，见 `specs/core/execution.adoc`）。

**依据（标准名/编号）**：ISO/IEC 25010（可维护性：同一份字段清单只有一个次序来源）、ISO/IEC/IEEE 29148（判定须可验证）、Google Java Style Guide 3.4.2（成员次序须是**逻辑次序**、维护者能解释）、《阿里巴巴 Java 开发手册》（按表结构逐列对照属通行做法）。**「赋值顺序随字段顺序」是本集合的判据化取值**——通行风格指南未规定赋值次序须跟随字段次序。
* **注解/装饰器排序（L2）**：同一目标（类、字段、方法、参数等）上叠加**多个注解**时，**先比重要性、重要的排在下面**——重要性按以下次序判定（上者更重要）：① 影响**数据存储/持久化映射**的（`@Id`、`@Column`、`@TableName`）——**数据库/持久化注解一律排在最下面**（本条最重要的约束：与库表结构相关的注解除外，其余注解都在其上方）；② 影响**对外契约/序列化**的（`@JsonProperty`、`@ApiModelProperty`）；③ 影响**校验/约束**的（`@NotNull`、`@Valid`）；④ **框架注入/装配**的（`@Autowired`、`@Bean`）；⑤ 余下的**生成/工具类**注解（lombok 的 `@Data`、`@Builder`）。**重要性相同时再比名长**——**名字短的在上面、长的在下面**；**长度只算注解名本身**（如 `@Data` 算 `Data` 四个字符），**不含其后的属性/参数列表**。**次序完全确定**：先比重要性（重要在下），重要性相同时再比名长（短在上）——两步即可唯一定序，无歧义。**同档次内不得按名长跨档插队**：同档注解之间才比名长——`@NotNull`（档③，名长 7）属校验档，仍排在建档②的 `@JsonProperty`（名长 13）**下面**，不得因为名字更短而越过档位。**数据库优先于名长**：`@Id`（名长 2）虽短，仍因属①档而排在 `@Data`（名长 4）**下面**；不得以「名字更短」为由把数据库注解提到上面。**本条的运行前提**：注解次序不影响语义——若某语言/框架**对注解次序敏感**（有先后依赖、后者覆盖前者），**以语义正确为准**，本条不适用。
* **注解/装饰器属性排序**：① 与数据存储字段顺序保持一致（主键/必填在前）；② 常用/必传属性在前，省略属性名时默认赋值的属性排最前；③ 其余按使用频率或逻辑顺序排列。
* **Feign 接口命名带所属域/项目前缀（L1）**：**Feign 声明式 HTTP 客户端接口**（本次**只此一类**，REST Controller、RPC 服务契约等**其他对外接口**不适用、不据本条改名，也不得据此扩张判定面）命名须为「**前缀 + 接口业务名 + `Api`**」，前缀由**接口所属的域/项目**决定——**先取该域已存在的固定前缀（先例优先）**，没有先例才按项目名取词首字母组合（`user-center` → `Uc`、`open-user-center` → `Ouc`，即 `UcUserApi`、`OucUserApi`）。**判定（任一命中即违规）**：① 所属域已有固定前缀却另取一套；② 同类接口有的带前缀有的不带；③ 把业务名或所属服务全名当前缀（如 `UserCenterUserApi` 一类**拼全名**的写法）。

**存量边界**：不发动全库改名（存量口径见 `specs/core/execution.adoc`）。Java 落点见 `specs/stack/java.adoc`「命名」。
* **接口/抽象类的实现类命名**：实现类应有**标识性名字**（体现具体实现方式/策略/用途），接口/基类使用简单名字；除非实现类是继承链中的一环，否则各实现类严禁同名。
* 依据（标准名/编号）：**成员与注解排序**一条为**本集合自身的判据化取舍**——Google Java Style Guide 3.4.2（Ordering of class contents）明确指出成员次序"**没有唯一正确的配方**"，只要求"每类使用某种**逻辑次序**、维护者能解释即可"，并禁止"按追加时间堆在末尾"；阿里巴巴 Java 开发手册亦无"静态字段必须在最前"或"注解按名长排"的明文。故"静态字段在类最前""实体类按数据库列序""链式赋值顺序随字段顺序""注解先按重要性（数据库映射注解在最下）、同重要性再按名长升序"四条是**本集合在上述"须为逻辑次序"的下限之上自定的更严取值**（理由是"整类共享状态集中可见""与表结构逐列对照""同一份字段清单只有一个次序来源""数据库关注点收尾扫读"），**不得**读成某标准的规定。**须注意的语义差异**：Google 只要求"逻辑次序"，未规定具体次序（**也未**规定赋值环节的书写次序须跟随字段次序）；本集合给出具体次序，属**加严**，且已按 `specs/core/execution.adoc`「规范变更的存量处理」**随动迁移**（不发动全库重排）。

== 注释

* **注释的形式与承载位置**：面向结构的说明用什么机制写、详细设计写在哪一层、没有文档注释机制时退回什么形态、脚本的例外，**唯一落点在本节**（`specs/general/doc.adoc`「注释与文档」管**内容与承载层**；形式规则不在那边另写一份——两处各写一遍时，改一处必漏另一处）。
* **代码注释的内容下限（放错层会同一件事写两遍）**：**结构说明用文档注释、普通注释只写方法体内的局部实现**（为什么这样写、局部决策、边界取舍）；**详细设计（参数、返回值、异常、边界、默认值、空值语义、易误用点、已知缺陷、性能、线程安全）写进源码的文档注释、不另建独立文档**（落层判定见 `specs/general/doc-design.adoc`「信息归属」）。
* **脚本的落点与粒度（脚本例外）**：脚本默认**脚本单打独斗**、文档随脚本落盘、不逐脚本另建独立文档（**不允许一个脚本对应一个文档**），承载方式按**多行文档注释 → 多行普通/块注释 → 普通注释**的优先级取值（判据见 `specs/general/script.adoc`「脚本文档的承载位置与协作粒度（默认写进脚本自身）」）——**这是"普通注释仅限方法体内"的唯一例外**。
