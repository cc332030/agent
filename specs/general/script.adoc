= 脚本规范（通用层，跨语言）

以下规范适用于**所有脚本语言**编写的脚本文件（bash/sh、Python、Node.js、PowerShell、Perl 等）的格式与编写。脚本泛指用于执行一次性或自动化任务的程序文件（区别于作为项目主体的应用代码）。某语言/技术栈专属的脚本规则见 `specs/stack/` 对应文件。

== 文件格式与编码

* 编码与换行：脚本文件一律 UTF-8 编码（通用编码要求见 link:../general/doc.adoc[]「文件格式与编码」；行尾按下表取值，权威判据见 link:../general/encoding.adoc[]「换行符」）
* 可执行标识：Unix/Linux 下的脚本文件须在首行写明 shebang（如 `#!/usr/bin/env bash`、`#!/usr/bin/env python3`），明确解释器；须设置可执行权限（git 中 `chmod +x`），确保可直接以 `./脚本名` 方式运行
* 行尾（**按脚本类型取值、不得混用**，权威判据见 link:../general/encoding.adoc[]「换行符」）：**Python、Node.js 等能自主识别两种行尾的脚本用 LF**；**Windows 批处理 `.bat`/`.cmd` 必须 CRLF**（LF-only 在 `cmd.exe` 下直接执行失败，见该条）；`bash`/`sh`/PowerShell 见各自栈文件。**CRLF 只允许出现在强制要求它的少量例外上**，其余一律 LF
* 缩进与格式：缩进风格随脚本语言惯例统一，同一文件内保持一致

== 文件命名

脚本文件名**默认使用中划线**（kebab-case，小写 + 连字符 `-`），如 `check-specs.sh`、`deploy-run.sh`。仅当某脚本语言**机制上不支持中划线**时（如 Python 的模块名/标识符不能含连字符，会导致脚本无法被 `import` 复用、无法被 `unittest discover` 自动发现），才回退使用**该语言自身的命名规则**（如 Python 用下划线 snake_case，`check_specs.py`、`clean_tmp.py`）——即「默认中划线、语言不支持则用语言自身规则」，不再逐一列举各语言脚本该用何种命名。

* 命名须**自洽**：测试文件命名（link:../general/testing.adoc[]「用例编写」`foo.py → foo_test.py`）与被测文件名保持同一套字符规则（Java 测试类沿用该语言的 `Tests` 后缀定式，见 link:../stack/java-testing.adoc[]），避免同一语言内出现两套命名风格或需靠「例外」绕开
* 脚本内部变量、函数、模块名等标识符仍遵守语言/编码规范（如 Python 用下划线 `snake_case`，见 link:../general/coding.adoc[] 与对应技术栈文件）
* 脚本对应文档命名：**独立文档不逐脚本另建**（脚本的定位、用法、参数、环境变量、行为边界等写在其头部注释中，见下「脚本头部注释」）；确有脚本专属的独立文档时，按 link:../general/doc-design.adoc[]「设计文档」命名条处理——**默认按功能命名、不必与脚本同名**，仅当该文档确实只对应某个脚本文件时才取脚本文件名（去扩展名）+ `.adoc`（测试文档取**测试脚本文件名**，不另行追加或改写后缀）；命名风格跟随脚本

== 脚本头部注释（文档头）

* 头部注释必须说明脚本的**定位、用法与关键约定**，让读者（含 agent 与后续维护者）无需阅读源码即可掌握使用方法。建议在文件开头以块注释形式写明：
  ** 脚本名称与用途（一行概括做了什么）；
  ** 用法：调用方式、命令行参数（含参数含义与示例）；
  ** 环境变量（如有）：每个环境变量的含义、是否必填、默认值；
  ** 行为/副作用：脚本会做什么、写入/生成哪些文件、依赖哪些外部命令或资源；
  ** 安全保证或重要边界（如删除类脚本须写明"只操作某范围、绝不越界"）。
* 头部注释使用脚本语言自身的注释语法；注释内容遵守文档规范（link:../general/doc.adoc[]「注释与文档」）：记录决策、边界与用法要点，不追求完整叙述

== 参数处理

* 统一使用脚本语言标准的参数解析机制（如 Python 的 `argparse`、Node 的 `commander`），避免手写脆弱的字符串解析
* 参数须有默认值或显式必填校验：必填参数缺失时输出清晰错误并退出非 0，不静默使用空值
* 提供 `--help`/`-h` 能力（由标准解析机制自带或手动实现），说明全部参数用法
* 帮助类/未知参数：解析到未知参数时提示并退出非 0，不忽略

== 退出码约定

* 退出码 0 表示成功，非 0 表示失败；不同失败类型可用不同非 0 退出码区分（如参数错误、执行失败、未满足前置条件），并在头部注释或文档中说明各退出码含义（依据：POSIX 对进程退出状态的规定及 BSD `sysexits.h` 的退出码约定，即 FreeBSD `sysexits(3)`）
* 脚本被调用方依赖退出码判断成败（尤其被 CI、流水线或其他脚本调用时），不得"失败也返回 0"
* 出错时向标准错误（stderr）输出错误信息，正常结果输出到标准输出（stdout），便于区分与重定向

== 错误处理与健壮性

* 关键步骤失败须显式检查并处理：依赖外部命令/资源时检查其成败，失败即按约定退出非 0，不继续执行后续依赖步骤
* 脚本应尽量"安全失败"：出错时不留下半成品或破坏性结果；涉及删除、覆盖、写外部资源等有副作用操作时，先校验边界并（必要时）要求显式确认
* 抑制非必要输出：日常无参数运行时保持安静，仅在 `-v/--verbose` 或显式请求时输出详细过程

== 安全

* 路径处理：脚本处理文件路径时，须校验目标位于预期范围内，防路径穿越（`../`、绝对路径、符号链接指向外部等），尤其对删除类、写文件类脚本——先校验边界再操作，越界即拒绝
* 不信任外部输入：参数、环境变量、文件内容等外部输入不可直接当作命令或路径拼接执行，须校验/转义；禁止把未经处理的用户输入直接拼入 shell 命令
* 临时文件：脚本产生的临时文件放入目标项目 `tmp/` 目录，用完即清理；不得写入项目正式目录（临时产物的定义与提交约束见 link:../core/execution.adoc[]「临时产物」）

== 临时产物清理（脚本约定）

* **目录级清理走项目提供的清理脚本，不手写 `rm -rf`（L2）**：清理 `tmp/` 下的临时产物时，优先使用项目提供的清理脚本；脚本须**内置路径校验**（仅允许清理 `tmp/` 下的目标、拒绝 `../` 与绝对路径越界，见上「安全」），并在头部注释写明用法。清理的**触发条件**（默认不清理、仅在用户声明或产物确实不会再用到时清理）见 link:../core/execution.adoc[]「临时产物」，本处只约定脚本形态
* **脚本可远程执行、不必下载到目标项目（L3）**：此类一次性工具脚本无需复制到目标项目——Linux/macOS 直接以 stdin 方式远程执行（如 `curl -s <脚本地址> | python3 -`），Windows 用 `Invoke-WebRequest` 取回后执行；要求脚本**以当前工作目录为项目根**、不依赖自身所在位置

== 跨环境脚本（入口 + 跨平台逻辑 + 实现语言取舍）

同一份脚本功能要在**多个操作系统**上跑（最典型是 Windows 与 Linux）时，**不得把逻辑写两遍**——逻辑只写一份，各平台的入口文件只负责调用它。**两层都要选好语言、并把“跑起来”的成本压到零**：逻辑层选**跨平台**语言（见下「实现语言取舍」），入口层选**该平台开箱可用**的语言（见下「入口语言取舍」）；入口与逻辑**同处一目录、同名不同扩展名**，调用方**只给脚本名**就能跑（不加解释器名、不加解释器选项、不做前置动作）。

* **入口层（薄壳）**：平台专属的入口文件，职责只有三件——**定位逻辑代码、把它自己的全部命令行参数转交过去、把逻辑代码的退出码作为自己的退出码返回**（外加"解释器/运行时找不到"时报一句错并退出非 0）。Windows 用 `.bat`/`.cmd`（需要 PowerShell 时用 `.ps1` + 同名 `.bat`，见 link:../stack/batch.adoc[]「作为跨环境入口（Windows 与 Linux 并存时）」与 link:../stack/powershell.adoc[]「启动脚本」）；Linux/macOS 用 `.sh`（`#!/usr/bin/env bash`）。
* **逻辑层（跨平台逻辑层，一份）**：**一份跨平台逻辑代码**，用跨平台语言写（见下「实现语言取舍」），承载**全部**实际逻辑；它由入口调用，也可单独直接运行。
* **入口层须与逻辑代码同处一目录、同名不同扩展名（L1）**：入口文件与逻辑代码**放在同一个目录下**，主名（去扩展名）**必须相同**——`foo.py`（逻辑）配 `foo.sh`（Linux 入口）、`foo.bat`/`foo.cmd`（Windows 入口），需要 PowerShell 时再加 `foo.ps1`。**不得**把入口另放 `bin/`、`script/`、`windows/`、`linux/` 一类目录（“按平台分目录”正是逻辑写两遍的温床：入口一分散，改逻辑时就会连带把入口也改一遍、改出第二份）；同名让“这个入口调的是哪份逻辑”一眼可读，也使入口定位逻辑代码不需要维护一张映射表。**判定标准**：入口与逻辑代码主名不同（如 `run.sh` 调 `foo.py`）/ 两者不在同一目录 / 为平台各建一个目录——任一命中即违规。
* **入口脚本须能直接执行，调用方不加前后命令（L1）**：入口文件**必须能在自己平台的默认命令行里直接执行**——`./foo.sh`（shebang `#!/usr/bin/env bash` + 可执行位）、`foo.bat`/`foo.cmd`（双击或在 `cmd.exe` 里直接跑；POSIX 侧 `./run/foo.sh`、Windows 侧 `run\foo.bat` 都由用户直接给出脚本名）；需要 PowerShell 时由同名 `.bat` 承接（`.ps1` 受执行策略限制，见 link:../stack/powershell.adoc[]「启动脚本」）。**不得**要求调用方在脚本名前后**再加命令或参数**才能跑通——典型违规：让用户输 `bash foo.sh`（说明缺 shebang 或可执行位）、`sh foo.sh`、`python3 ./foo.py`（说明拿逻辑代码当入口、或入口没写明解释器）、`powershell -File foo.ps1`、`powershell -ExecutionPolicy Bypass -File foo.ps1`。**例外（必要参数除外）**：脚本自身功能所需的参数（如 `./foo.sh --target prod`）不算本条所禁的“前后命令”，本条禁的是为**跑起来**而必须加的**解释器名与解释器选项**；为**规避本平台自身限制**而固定写进入口内部的解释器调用（`.bat` 里的 `powershell -ExecutionPolicy Bypass -File "%~dp0foo.ps1"`）、或脚本按自身需要决定以 `start`/`nohup`/`&` 方式启动自己，属入口**内部实现**、**不**是对调用方的要求——判据是“**用户拿到脚本名，能不能直接跑起来**”。
* **入口语言按平台默认具备者选（L1）**：入口脚本语言**按平台取“开箱可用”的那一种**——Windows 取 `.bat`/`.cmd`（需要 PowerShell 能力时加 `.ps1`、由同名 `.bat` 用 `-ExecutionPolicy Bypass` 承接），Linux/macOS 取 `.sh`（POSIX shell 或 bash）。**不得**为一侧的入口引入该平台默认不具备的运行时（如 Windows 入口用要另装 Python 的 `.py`、Linux 入口用要另装 PowerShell 的 `.ps1`）——入口是“进门的门”，门本身要求先装东西，等于把环境差异与安装步骤推给调用方；入口**跨平台**另有一种取值：逻辑层用**编译型**语言且产物是原生可执行文件时，**同一个二进制可以直接兼作两平台的入口**（此时不必再有 `.sh`/`.bat`，见下「实现语言取舍」单文件分发）。**判定标准**：入口需要本平台默认不具备的解释器/运行时才能启动（脚本按自身功能在运行时自行安装的依赖不属此列）；入口需要调用方先做一步配置（改执行策略、装运行时、导出变量）才能执行——任一命中即违规。
* **入口脚本不得为“跑逻辑”自加命令、也不得给逻辑代码塞参数（L1）**：入口**只转交调用方原样给的参数**，不得为了“让逻辑跑起来”而**在调用前后自加命令或参数**——典型违规：入口里先 `cd`/`mkdir`/`chmod`/`git pull`/`pip install` 再调逻辑、给逻辑代码固定加上调用方没给的参数（`--workdir "$(pwd)"`、`--config ...`）、把逻辑代码当“被包装的命令”串进管道（`curl … | python3 -` 形态只允许出现在“脚本可远程执行”这一场景，见上「临时产物清理」L3，不适用于本地入口）。**例外**：为规避平台限制而必需的**入口内部**解释器调用（`powershell -ExecutionPolicy Bypass -File "%~dp0foo.ps1"`）与“定位逻辑代码”的路径拼接（`%~dp0`、`$(dirname "$0")`）属**薄壳三件事**之内、不算自加命令；脚本功能参数的默认值由**逻辑层**按参数默认值机制给（见上「参数处理」），不由入口预置。**判定标准**：入口里出现调用逻辑代码**之前**的其他命令（`cd`/`mkdir`/`chmod`/安装/下载/提交/校验），或转交时参数与调用方给的**不一一对应**（多加了固定参数、改写了某个值、丢了一个）——任一命中即违规。
* **入口脚本不得要求调用方先做前置动作（L1）**：入口**不设前置步骤**——不要求调用方先 `cd` 到项目根、先设某个环境变量、先 `chmod +x`、先装依赖、先解压；这些若确有必要，由**逻辑层**在运行时自行判断与处理（并在头部注释写明它需要什么）。入口对**解释器/运行时缺失**这一唯一“外部原因”只做“报一句错、退出非 0”（见上「入口层（薄壳）」）。**判定标准**：入口或它的头部注释里出现“请先……”这类对调用方的前置要求（`cd` 到某目录、导出变量、安装运行时）——命中即违规；“用 `%~dp0`/`$(dirname "$0")` 定位自身所在目录”不受此限（那是入口自证位置，不是要求调用方）。
* **入口层不得承载逻辑（L1）**：入口文件里**不得**出现判定分支、文件遍历、字符串处理、参数解析、错误处理等流程性代码，也不得复述逻辑层的选择/取参规则。**判定标准**：整份入口文件可以逐行解释为上述三件事（外加解释器缺失时的报错退出），多出任何一件即违规；同一段逻辑在两个入口文件里各出现一次（"复制过去的"，哪怕只有几个分支）同样违规——改了逻辑只改一处，这才是本条要的东西。
* **入口层不重写逻辑代码的那一套（L1）**：**不得**在 `.sh` 里再写一遍给 Linux 用的逻辑（"Windows 的我可以不写、顺手写个 sh 版本更快"正是本条要防的形态）。入口文件**只允许**一份薄壳，逻辑一律在逻辑层；每个平台的入口都只是"调用器"，不是"该平台版本"。
* **入口层不为逻辑层添第二套选项语义（L1）**：入口只做**转交**，不解释参数含义、不设自己的默认值、不重命名选项、不吞掉它不认识的参数（如"这个项目用不到，就不往下传了"）——否则同一个逻辑代码在不同平台的入口下行为不同。**例外（应当遵守）**：`cmd.exe`/PowerShell 无法原样承载某些字符，此时入口**可以**按平台语法转义，但**不得改变参数的值**。**判定标准**：入口读取/判断参数值、给某选项填默认值、丢掉一个参数、把两个参数合并——任一命中即违规。
* **入口层须让退出码可判定（L1）**：入口须把逻辑代码的退出码**原样返回**（调用方可能是人、CI 或另一个脚本，它只认退出码，见上「退出码约定」）；`cmd.exe` 用 `exit /b %errorlevel%`（不写则批处理的退出码是最后一条命令的，不等于逻辑代码的）、`sh` 用 `exec`（或 `exit $?`）、PowerShell 用 `exit $LASTEXITCODE`。**判定标准**：入口返回值与逻辑代码退出码不一致（含"总是成功"与"总是失败"）——命中即违规。
* **入口文件按各自平台规范落盘（L1）**：`.bat`/`.cmd` 与 `.ps1` 落盘 CRLF、`.sh` 用 LF；编码一律 UTF-8，`.bat` 用纯 ASCII（批处理的判据见 link:../stack/batch.adoc[]「编码与行尾」，`.ps1` 的见 link:../stack/powershell.adoc[]「编码与行尾」，行尾的权威口径见 link:../general/encoding.adoc[]「换行符」）。
* **逻辑代码不得假设自身所处目录（L1）**：逻辑代码的当前工作目录由**调用方**决定，**不得**假设它是项目根——需要项目根时按约定的参数取值或由入口在调用前约定；入口侧以**绝对路径**调用逻辑代码（`.sh` 用 `"$(dirname "$0")/foo.py"` 一类形态）、**不得** `cd` 到脚本目录去改掉调用方的工作目录。**判定标准**：入口里出现 `cd` 到脚本目录、或逻辑代码按相对路径读输入却既不校验也不取项目根——命中即违规。

**入口语言取舍（L1，与下方逻辑层语言取舍不同层）**：入口层的语言**不是自由选择**——它由“该平台默认可用”决定，取的是本地平台上无需额外安装即可解释执行的那一种。故 **Windows 取 `.bat`/`.cmd`**（`cmd.exe` 是 Windows 自带；需要 PowerShell 能力时加 `.ps1`，由同名 `.bat` 用 `-ExecutionPolicy Bypass` 承接），**Linux/macOS 取 `.sh`**（POSIX shell 或 bash 是系统自带；`#!` 由 link:../stack/bash.adoc[] 约定）。**不得**反过来按“逻辑层用什么语言”给入口选语言（逻辑用 Python 就写 `foo.py` 当 Windows 入口）、也**不得**给入口引入对方平台要另装的运行时——入口的职责只是“找到并调用”逻辑代码，为此要求用户先装一个运行时，等于把本条想消除的平台差异又搬回用户面前。**唯一例外**是入口与逻辑**合而为一**：逻辑用编译型语言（Go/Rust）产出**原生可执行文件**时，同一份二进制本身就是两平台可直接执行的入口，不再需要 `.sh`/`.bat`（见下条“单文件分发”）。
* **入口语言的可判定取值**：Windows 侧 `.bat`/`.cmd`（可选加 `.ps1` + 同名 `.bat`）、Linux/macOS 侧 `.sh`；两侧都**不带**“需要先装某运行时才能启动”的前提。**判定标准**：入口的扩展名/解释器在这台机器上不是默认可得的（如 Linux 上的 `.ps1`、Windows 上的 `.sh`）、或入口脚本头部写着需要先安装某运行时——命中即违规。

**实现语言取舍（L2，默认取向、非硬约束）**：逻辑层优先用**为写脚本而生**的跨平台语言。默认取 **Python 3** 或 **Node.js**（含 Deno/Bun）——两者都是"装了运行时就有"、标准库即覆盖参数解析与文件/网络、生态最广、过程式写起来不需要项目脚手架。需要**单文件分发**（目标机不想装运行时）时改用 **Go** 或 **Rust** 编译成单个可执行产物（代价是引入编译链、需在 CI 里交叉编译）；此时该**原生可执行文件同时兼作两平台入口**（不再需要 `.sh`/`.bat`，也就不存在“入口语言”一题）——这是入口与逻辑合一的唯一正当形态，交付时按平台产物命名一致（如 `foo.exe` 与 `foo`），落点仍是同一目录。

* **取舍判据**：**环境好搭建**（只需"装上运行时"一步，不要求系统级依赖）、**代码不易出错**（有语法与类型检查，错误在运行前暴露）、**好维护**（过程式为主、无需项目脚手架、改一处不影响其他）、**兼容性**（两平台行为一致、不依赖 Unix 专有命令）、**效率**（启动与执行开销可接受）。按这五条判，**不要因为"语言更纯粹"而选编译型语言**，也**不要为"少装一个运行时"把逻辑写进 shell**（见下条）。
* **默认不拿裸 shell 当逻辑层（L2）**：把逻辑写进 `.sh`/`.bat` 等于把平台差异带进逻辑层本身——`bash` 在 Windows 上要么不可得、要么来自 Git Bash/WSL（行为与原生不一致），`cmd` 在 Linux 上不可用，于是"一份逻辑"必然变成两份。**shell 作为入口是恰当的**（它天生擅长"找到并调用"），作为逻辑层则不恰当。**例外（可以）**：逻辑确实只有几行、且平台差异本身就是逻辑的全部内容时，两个入口各自写完即可——一旦要写第二遍、或有任何分支与数据处理，就回到"一份跨平台逻辑代码"。
