= 脚本规范（通用层，跨语言）

适用于**所有脚本语言**（bash/sh、Python、Node.js、PowerShell、批处理等）的脚本文件格式与编写。脚本指用于执行一次性或自动化任务的程序文件（区别于作为项目主体的应用代码）。某语言/技术栈专属规则见 `specs/stack/` 对应文件。

== 文件格式与编码

* **编码与换行**：脚本文件一律 UTF-8 编码；行尾按脚本类型取值（权威判据见 `specs/general/encoding.adoc`「换行符」）——**Python、Node.js 等能自主识别两种行尾的脚本用 LF**；**Windows 批处理 `.bat`/`.cmd` 必须 CRLF**；`bash`/`sh` 用 LF、PowerShell `.ps1` 用 CRLF（见各自栈文件）。
* **可执行标识**：Unix/Linux 下的脚本须在首行写明 shebang（`#!/usr/bin/env bash`、`#!/usr/bin/env python3`），须设置可执行权限（git 中 `chmod +x`）。
* **缩进与格式**：缩进风格随脚本语言惯例统一，同一文件内保持一致。

== 文件命名

* **脚本文件名默认使用中划线**（kebab-case，小写 + 连字符 `-`），如 `check-specs.sh`、`deploy-run.sh`；仅当某脚本语言**机制上不支持中划线**时（Python 的模块名/标识符不能含连字符，会导致无法 `import` 复用、无法被 `unittest discover` 自动发现），才回退用**该语言的命名规则**（Python 用下划线 `snake_case`，`check_specs.py`）。
* **命名须自洽**：测试文件命名与被测文件名保持同一套字符规则，避免同一语言内出现两套风格。
* **脚本内部标识符**（变量、函数、模块名）仍遵守语言规范（Python 用 `snake_case`）。
* **脚本对应文档命名**：**独立文档不逐脚本另建**（见下「脚本文档的承载位置」）；确有脚本专属独立文档时按 `specs/general/doc-design.adoc`「设计文档」命名条处理，命名风格跟随脚本。

== 脚本文档的承载位置与协作粒度（默认写进脚本自身）

* **脚本默认"单打独斗"（脚本单打独斗），文档随脚本落盘（L1）**：脚本多数情形下单独存在——它是一次性/自动化任务的执行体，不与某个应用主体成篇；拆成多个脚本时**各脚本之间相互独立**，彼此不构成同一模块。故脚本的文档**默认直接写在脚本里、不另建独立文档**，承载方式按**多行文档注释（优先级高）→ 多行普通/块注释（优先级中）→ 普通注释（优先级低）**取值：有文档注释机制的语言（Python 的模块 docstring、JS/TS 的 JSDoc）一律用**文档注释**承载；无该机制的语言（bash/sh、批处理、PowerShell 的普通注释）用**多行块注释**；只有零散的补充说明才用普通单行注释。**判定标准（任一命中即违规）**：① 脚本的定位/用法/参数/边界写在脚本之外的独立文档里，而脚本头部没有或只有一句话；② 有文档注释机制的语言用普通注释或块注释承载文档头；③ 为单个脚本新建 `.adoc`/`.md` 文档来放它的定位、用法与参数（唯一例外见下条）。
* **"独立文档不逐脚本另建"与"内容超容量时移交"的衔接（L1）**：只有一种情形可以（且应当）另建独立文档——**内容确已超出头部块注释的容量**（出现多个功能模块/子命令各自的方案取舍、成段的设计叙述或对照材料）。判据在**内容量**而不在"能不能拆成两处写"：内容放得下脚本头部时**一律写在脚本里**；确需成篇时按功能命名另建，并在脚本头部**留一行链接**回指。
* **大规模团队式协作是例外，不是默认（L2）**：只有确实出现**规模化的团队式协作**（多脚本长期共建一个软件栈、脚本之间有真实的公共契约与角色分工）时，才按普通项目的文档组织处理——走 `specs/general/doc.adoc`「文档组织与导航」与 `specs/general/doc-design.adoc`「信息归属」的分工，并按"只改当前项目"改到哪补到哪。**判定标准**：为"可能以后会有人一起维护"给脚本建独立文档、或把相互独立的脚本当成同一个模块来组织文档——命中即违规。

== 脚本头部注释（文档头）

* **文档头先行（头部注释必须先行，L1）**：**动手写脚本的第一件事是先把头部注释写出来**——把这份文件的**用途、用法、参数、环境变量、行为边界与设计决策**先定在文档头里，再据此写实现。**判据**：① 先写文档头（不是"写完顺手补"的收尾动作，开写前就已有内容）；② 不得只留待办占位（`TODO`/`待补`/空标题不算写了）；③ 实现改完头部注释同步——改动使头部注释里的任一项失真时，在**同一提交内**改过来。
* **脚本必须写文档头（L2）**：凡承担实际功能的脚本（新写的与本次改到的）都须有条目化的文档头（不是一句"干某事"）；只有一次性、几行的临时命令可省，且仍须有一行用途说明。
* **头部注释的条目（缺一项即未达要求）**：
** 脚本名称与用途（一行概括做了什么）；
** 用法：调用方式、命令行参数（含参数含义与示例）；
** 环境变量（如有）：每个环境变量的含义、是否必填、默认值；
** 行为/副作用：脚本会做什么、写入/生成哪些文件、依赖哪些外部命令或资源；
** **关键约定与设计决策**（**不得省略**）：含约定与出处、为什么这么做与放弃了哪些备选做法、兜底与已知限制；格式/边界/常量取值的约定与出处；**为什么这么做**与**放弃了哪些备选做法**（方案取舍，只写决定不写理由＝没有记录）；**兜底与已知限制**；
** 安全保证或重要边界（删除类脚本须写明"只操作某范围、绝不越界"）。
* **设计决策写成可核对的记录，不写成叙述（L1）**：每条取舍写成**决策 + 理由 + 边界**，使后续维护者能据此判断"这条约定今天还成不成立"。**判定标准（任一命中即未达要求）**：① 头部注释只见"怎么做"、没有一处讲"为什么这么做"，或只有一句"（原因见某处）"而无处可查；② 记录了已被否掉的备选方案却不说不选它的理由；③ 只写决定不写依据或理由。
* **注释里的取值：写抽象描述或常量名、不写硬编码数值（L1）**：头部注释不得写"超时 30 秒""最多重试 3 次""落点 `tmp/<名称>/`"这类把实现取值抄进注释的说法——改代码不改注释即产生"文档说谎"。写抽象描述或常量名（`TIMEOUT_SECONDS`、`MAX_ATTEMPTS`、`DEFAULT_OUT`），数值与默认值以代码中的常量为唯一来源。**判定标准（任一命中即违规）**：① 注释里出现带单位的字面数值而代码里对应的是常量；② 注释写死了目录名/命令名/参数默认值而代码里是变量或可被参数覆盖；③ 同一取值在注释与代码里各写一遍。
* **决策进头部/文件级文档注释，不写进方法体（L1）**：头部注释（及有文档注释机制语言的 docstring）承载**跨方法的文件级决策**——定位、用法、行为与副作用、关键约定与设计决策、兜底与限制；**方法体内部**的普通注释只记方法内部的局部决策与边界；**禁止**把方案取舍、适用范围、已知限制塞进方法体。判定："**为什么这样设计**"型文字出现在方法体内而不在头部或 docstring。
* **超过头部块注释容量的内容移交独立文档（L1）**：内容确已超出头部块注释的容量时，不得把文档头堆成一篇长文，须按功能命名另建独立 `.adoc`，**文档头保留条目化要点并一行链接到该文档**。**判据**：文档头出现成段设计叙述或第二次罗列同一份取舍而未给出链接——命中即"该移交而未移交"。
* **头部注释写在承载文档注释的位置，行数不设限（L1）**：Python 放在**模块 docstring**（shebang 之后的第一个语句），JS/TS 放在文件头的 JSDoc 块，不另起普通块注释（两处各写一半＝同一事实两个来源）；头部注释**不设行数上限**（内容要求不因"写短点"删减、也不因超长而判不合格）。
* **入口的注释边界（L1）**：跨环境时**入口只做薄壳**（见下「跨环境脚本」），其头部注释**只写入口自身的用法与它调用的逻辑代码**（一条指向逻辑代码的链接/路径），**不得复述**逻辑层的参数语义、默认值、行为与副作用——同一份契约写两处即两处真源。**判定标准**：入口注释里出现第二个平台入口或逻辑层已有的参数说明、默认值、退出码表——命中即违规。

== 参数处理

* **统一使用语言标准的参数解析机制**（Python 的 `argparse`、Node 的 `commander`），避免手写脆弱的字符串解析。
* **参数须有默认值或显式必填校验**：必填参数缺失时输出清晰错误并退出非 0，不静默使用空值。
* **提供 `--help`/`-h` 能力**，说明全部参数用法。
* **帮助类/未知参数**：解析到未知参数时提示并退出非 0，不忽略。

== 退出码约定

* **退出码 0 表示成功，非 0 表示失败**；不同失败类型可用不同非 0 退出码区分（参数错误、执行失败、未满足前置条件），并在头部注释或文档中说明各退出码含义（依据：POSIX 对进程退出状态的规定及 BSD `sysexits.h` 的退出码约定）。
* **不得"失败也返回 0"**：脚本被调用方依赖退出码判断成败（尤其被 CI、流水线或其他脚本调用时）。
* **出错时向标准错误（stderr）输出错误信息**，正常结果输出到标准输出（stdout），便于区分与重定向。

== 错误处理与健壮性

* **关键步骤失败须显式检查并处理**：依赖外部命令/资源时检查其成败，失败即按约定退出非 0，不继续执行后续依赖步骤。
* **脚本应尽量"安全失败"**：出错时不留下半成品或破坏性结果；涉及删除、覆盖、写外部资源等有副作用操作时，先校验边界并（必要时）要求显式确认。
* **抑制非必要输出**：日常无参数运行时保持安静，仅在 `-v/--verbose` 或显式请求时输出详细过程。

== 安全

* **路径处理**：处理文件路径时须校验目标位于预期范围内，防路径穿越（`../`、绝对路径、符号链接指向外部），尤其对删除类、写文件类脚本——先校验边界再操作，越界即拒绝。
* **不信任外部输入**：参数、环境变量、文件内容等外部输入不可直接当作命令或路径拼接执行，须校验/转义；禁止把未经处理的用户输入直接拼入 shell 命令。
* **临时文件**：脚本产生的临时文件放入目标项目 `tmp/` 目录，用完即清理；不得写入项目正式目录。

== 临时产物清理（脚本约定）

* **目录级清理走项目提供的清理脚本，不手写 `rm -rf`（L2）**：清理 `tmp/` 下的临时产物时优先使用项目提供的清理脚本；脚本须**内置路径校验**（仅允许清理 `tmp/` 下的目标、拒绝 `../` 与绝对路径越界），并在头部注释写明用法。清理的**触发条件**（默认不清理、仅在用户声明或产物确实不会再用到时清理）见 `specs/core/execution.adoc`「临时产物」。
* **脚本可远程执行、不必下载到目标项目（L3）**：此类一次性工具脚本无需复制到目标项目——Linux/macOS 直接以 stdin 方式远程执行（`curl -s <脚本地址> | python3 -`），Windows 用 `Invoke-WebRequest` 取回后执行；要求脚本**以当前工作目录为项目根**、不依赖自身所在位置。

== 跨环境脚本（入口 + 跨平台逻辑 + 实现语言取舍）

同一份脚本功能要在**多个操作系统**上跑（最典型是 Windows 与 Linux）时，**不得把逻辑写两遍**——逻辑只写一份，各平台的入口文件只负责调用它。两层都要选好语言、并把"跑起来"的成本压到零。

**入口层（薄壳）**：平台专属的入口文件，职责只有三件——**定位解释器或逻辑代码、把它自己的全部命令行命令行参数转交过去、把逻辑代码的退出码作为自己的退出码返回**（外加"解释器/运行时找不到"时报一句错并退出非 0）。Windows 用 `.bat`/`.cmd`（需要 PowerShell 时用 `.ps1` + 同名 `.bat`）；Linux/macOS 用 `.sh`。

**逻辑层（跨平台逻辑层，一份）**：**一份跨平台逻辑代码**，用跨平台语言写，承载**全部**实际逻辑；它由入口调用，也可单独直接运行。

* **入口层须与逻辑代码同处一目录、同名不同扩展名（L1）**：入口文件与逻辑代码放在同一个目录下，主名（去扩展名）**必须相同**——`foo.py`（逻辑）配 `foo.sh`（Linux 入口）、`foo.bat`/`foo.cmd`（Windows 入口）。**不得**把入口另放 `bin/`、`script/`、`windows/`、`linux/` 一类目录（"按平台分目录"正是逻辑写两遍的温床）；同名让"这个入口调的是哪份逻辑"一眼可读。**判定标准**：入口与逻辑代码主名不同 / 两者不在同一目录 / 为平台各建一个目录——任一命中即违规。
* **入口脚本须能直接执行，调用方不加前后命令（L1）**：入口文件必须能在自己平台的默认命令行里直接执行；**脚本自身功能所需的参数属**必要参数**（例外）、不算本条所禁的前后命令**——`./foo.sh`（shebang + 可执行位）、`foo.bat`/`foo.cmd`（双击或在 `cmd.exe` 里直接跑）。**不得**要求调用方在脚本名前后**再加命令或参数**（`bash foo.sh`、`python3 ./foo.py`、`powershell -ExecutionPolicy Bypass -File foo.ps1`）。**例外**：脚本自身功能所需的参数不算"前后命令"；为规避本平台自身限制而固定写进入口内部的解释器调用、或脚本按自身需要决定以 `start`/`nohup`/`&` 方式启动自己，属入口**内部实现**。**判据是"用户拿到脚本名，能不能直接跑起来"**。
* **入口语言取舍（L1）**：入口语言**按平台默认具备者选**——Windows 取 `.bat`/`.cmd`（必要时加 `.ps1`、由同名 `.bat` 用 `-ExecutionPolicy Bypass` 承接），Linux/macOS 取 `.sh`。**不得**为一侧的入口引入该平台默认不具备的运行时（Windows 入口用要另装 Python 的 `.py`、Linux 入口用要另装 PowerShell 的 `.ps1`）。**唯一例外**：逻辑用编译型语言（Go/Rust）产出**原生可执行文件**时，同一份二进制本身就是两平台可直接执行的入口，不再需要 `.sh`/`.bat`。**判定标准**：入口需要本平台默认不具备的解释器/运行时才能启动、或需要调用方先做一步配置（改执行策略、装运行时、导出变量）才能执行——命中即违规。
* **入口脚本**不得为“跑逻辑”自加命令**、也不得给逻辑代码塞参数（L1）**：入口**只转交**——入口**只转交调用方原样给的参数**——不得在调用前后自加命令或参数（先 `cd`/`mkdir`/`chmod`/`git pull`/`pip install` 再调逻辑、给逻辑代码固定加上调用方没给的参数、把逻辑代码当"被包装的命令"串进管道）。**例外**：为规避平台限制而必需的入口内部解释器调用与"定位逻辑代码"的路径拼接（`%~dp0`、`$(dirname "$0")`）属薄壳三件事之内；脚本功能参数的默认值由**逻辑层**给。**判定标准**：入口里出现调用逻辑代码之前的其他命令，或转交时参数与调用方给的不一一对应——任一命中即违规。
* **薄壳之外不得多做，但可以做"把逻辑层当命令直接跑"的薄壳（L1）**：入口层不得承载逻辑**（不得出现判定分支、文件遍历、字符串处理、参数解析、错误处理等流程性代码），但**"把逻辑层当命令直接跑"与逻辑层调用等价**、属允许形态。**判定标准**：入口里出现与"把调用方给的参数交给逻辑代码"**不等价**的动作即违规。**判定标准**：整份入口文件可以逐行解释为上述三件事（外加解释器缺失时的报错退出），多出任何一件即违规；同一段逻辑在两个入口文件里各出现一次同样违规。
* **入口层不重写逻辑代码的那一套（L1）**：**不得**在 `.sh` 里再写一遍给 Linux 用的逻辑（"Windows 的我可以不写、顺手写个 sh 版本更快"正是本条要防的形态）；入口文件**只允许**一份薄壳**、不得为该平台另写一遍逻辑——每个平台的入口都只是"调用器"，不是"**该平台版本**"。
* **入口层不为逻辑层添第二套选项语义（L1）**：入口只做**转交**，不解释参数含义、不设自己的默认值、不重命名选项、不吞掉它不认识的参数。**例外**：`cmd.exe`/PowerShell 无法原样承载某些字符时，入口**可以**按平台语法转义，但**不得改变参数的值**。**判定标准**：入口读取/判断参数值、给某选项填默认值、丢掉一个参数、把两个参数合并——任一命中即违规。
* **入口层须让退出码可判定（L1）**：入口须把逻辑代码的退出码**原样返回**；`cmd.exe` 用 `exit /b %errorlevel%`（不写则批处理的退出码是最后一条命令的）、`sh` 用 `exec`（或 `exit $?`）、PowerShell 用 `exit $LASTEXITCODE`。**判定标准**：入口返回值与逻辑代码退出码不一致——命中即违规。
* **入口文件按各自平台规范落盘（L1）**：`.bat`/`.cmd` 与 `.ps1` 落盘 CRLF、`.sh` 用 LF；编码一律 UTF-8，`.bat` 用纯 ASCII（见 `specs/stack/batch.adoc`「编码与行尾」）。
* **逻辑代码不得假设自身所处目录（L1）**：逻辑代码的当前工作目录由**调用方**决定，不得假设它是项目根——需要项目根时按约定的参数取值或由入口在调用前约定；入口侧以**绝对路径**调用逻辑代码、**不得** `cd` 到脚本目录去改掉调用方的工作目录。**判定标准**：入口里出现 `cd` 到脚本目录、或逻辑代码按相对路径读输入却既不校验也不取项目根——命中即违规。
* **薄壳不得为"让逻辑跑起来"改变系统状态（L1）**：入口**不得**安装/下载/解压任何运行时、包或依赖（这些**都不属**薄壳）（含 `apt`/`apk`/`yum`/`pip`/`winget`、`curl | sh` 一类）——**代为获取运行时不是入口的职责**，它要么由**人**按本平台既有的软件分发方式完成、要么在**人已交互登录、能看见命令与报错**的正常会话里由 agent 完成，不得在入口或非交互执行里静默发生（依据：ISO 9241-110 的可控与可预期）。"先探测解释器、一个都没有就报错退出非 0"仍属薄壳。
* **入口脚本不得要求调用方先做前置动作（L1）**：入口**不设前置步骤**——不要求调用方先 `cd` 到项目根、先设环境变量、先 `chmod +x`、先装依赖；这些若确有必要由**逻辑层**在运行时自行判断与处理。入口对**解释器/运行时缺失**这一唯一"外部原因"只做"报一句错、退出非 0"。**判定标准**：入口或它的头部注释里出现"请先……"这类对调用方的前置要求——命中即违规；"用 `%~dp0`/`$(dirname "$0")` 定位自身所在目录"不受此限。

**实现语言取舍（L2，默认取向、非硬约束）**：逻辑层优先用**为写脚本而生**的跨平台语言——默认取 **Python 3** 或 **Node.js**（含 Deno/Bun）；需要**单文件分发**（目标机不想装运行时）时改用 **Go** 或 **Rust** 编译成单个可执行产物（此时该原生可执行文件同时兼作两平台入口）。

* **取舍判据**：**环境好搭建**（只需"装上运行时"一步，不要求系统级依赖）、**代码不易出错**（有语法与类型检查）、**好维护**（过程式为主、无需项目脚手架）、**兼容性**（两平台行为一致、不依赖 Unix 专有命令）、**效率**（启动与执行开销可接受）。**不要因为"语言更纯粹"而选编译型语言**，也**不要为"少装一个运行时"把逻辑写进 shell**。
* **默认不拿裸 shell 当逻辑层（L2）**：把逻辑写进 `.sh`/`.bat` 等于把平台差异带进逻辑层本身——"一份逻辑"必然变成两份。**shell 作为入口是恰当的**（它天生擅长"找到并调用"），作为逻辑层则不恰当。**例外**：逻辑确实只有几行、且平台差异本身就是逻辑的全部内容时，两个入口各自写完即可——一旦要写第二遍、或有任何分支与数据处理，就回到"一份跨平台逻辑代码"。
* **`.sh` 是逻辑层的通配入口（L1）**：逻辑层不需要解释器（原生可执行文件、或该平台自带的解释器）时，`.sh` 是各平台里**通配的那一侧**——`exec ./foo`、`exec node "$(dirname "$0")/foo.js" "$@"`、`exec python3 "$(dirname "$0")/foo.py" "$@"` 都是同一件事的等价形态。故逻辑层有解释器（如 Python）时，一份 `.sh` 入口就够、不必再为每个解释器各写一份入口。
* **`.bat` 里调别的解释器要另留一个入口（L1）**：`cmd.exe` 的 `PATH` 解析、`.cmd`/`.bat` 启动器、引号规则与 `sh` 的 `exec` **语义不同**——在 `.bat` 里直接调 `node`/`python` 要自己处理这些差异。故此时另留一个只写"跑逻辑"的入口脚本反而是首选（如 `foo-node.bat`：只做定位 `node` 与转交 `%*` 两件事）。

== 规则与脚本的隔离（规则数据外置）

**校验/检查类脚本**的规则本体（要核哪些条目、条目里的锚点、缺失时的说明、节名与落点路径）**须与脚本代码分离**：规则数据放**独立的配置文件**，脚本只保留"读文件 → 取节 → 逐组核锚点 → 报错"的通用原语。理由：规则会随需求反复调整，而**改规则是内容编辑、不是改程序**——规则散落在代码里时，任何一条规范措辞的调整都要动脚本（且同一段实现被复制几十遍、改一处判据要改 N 处）。

* **规则数据外置、脚本不承载措辞（L1）**：规则数据（条目名、锚点、说明、落点）**须**放在独立配置文件里；脚本里只留**引擎**与**接线**（"哪道防线由哪些规则组成"）。**判定标准（任一命中即违规）**：① 新增/调整一条规则时需要改 `.py` 而非只改配置文件；② 同一段"取文本 → 核锚点 → 报错"的实现被复制多份（各有微差）；③ 规范条文的关键措辞（锚点文字）以字面量出现在脚本源码里。
* **规则文件是纯数据（L1）**：配置文件须是**纯数据格式**（TOML/YAML/JSON 一类，不含可执行代码、不 import、不参与逻辑）——维护规则的人改措辞时**不可能顺手改出脚本行为**。**不得**把规则数据写成"同模块的 `.py` 常量"（数据与代码仍在同一模块里，改规则仍要动脚本，"隔离"只剩形式）。
* **格式取 TOML（L2，本集合的选用）**：本集合的规则文件取 **`.toml`**。判据：① **纯数据性**与 JSON 同样成立、且**重复表头由语法直接拒绝**（同名防线/同名名单不必等加载期才发现"两处各写一半"）；② **多行长锚点串可读性更好**（锚点是整句中文条文，逐条带尾括号的 JSON 极难读）；③ **解析器随标准库**（`tomllib`，Python 3.11+）——为读配置装第三方依赖等于"缺工具就静默跳过"，与 `specs/general/ci-cd.adoc`「校验链完整」相悖。**不得**为同一批规则同时维护两种格式的真源（改一处漏一处）。
* **配置缺失即报错、不得静默空转（L1）**：配置文件缺失、格式非法或引用了未知的规则项时，脚本须**报错退出非 0**，不得退回硬编码、也不得跳过——"核不到"与"核过且通过"必须分得清（与 `specs/general/verify.adoc`「验证的效力等级」的确定项一致：跳过已声明的校验手段即等于没有该校验）。
* **报错文案随规则数据走（L2）**：规则条目缺失时的说明（"为什么会失效"）属**规则数据**的一部分，须随规则数据外置并**逐字保留**；缺省时才用引擎的通用文案——说明丢了，防线虽在，读者也不知道自己破坏了什么。
* **生成的接线可核对（L2）**：脚本里的"哪道防线用哪些规则"须能与配置文件**一一对应**（防线名 ↔ 配置键）；对不上时（配置里多出的、脚本里没接的）须报错，防"规则写了却没人执行"（校验手段的接线完整性见 `specs/general/verify.adoc`「改完规范必做的五件事」）。
* **同一道防线只执行一遍（L1）**：一道防线的规则可能被多处落点共用（同一段文本在几个文件里被引用），而防线函数会**按落点分几处**判断——此时须保证同一道防线的规则在**同一次校验里只跑一遍**。理由：规则步骤自身已声明各自核对的落点（文件缺失由步骤自报），按落点重复执行只会把**同一条问题重复报出 N 遍**，把真正的问题埋进噪音里（本仓库实测：一处缺失被报出 3 遍，12 条报错里只有 4 条是不同问题）。**判定标准（任一命中即违规）**：① 同一次校验里同一处缺失被报出多于一条；② 防线函数体里出现多次同名 `run_rule_guard(...)` 接线（重复接线不产生新判据）。
* **一类规则一个文件（L1）**：规则数据**按被测落点切分**——一个文件只承载一类（通常就是一份被测文件）的规则，**不得把全部文件的规则堆进同一个文件**。理由：堆在一起时文件名与"这条规则管谁"脱节，改一处规范要在一个巨型文件里定位；且多个改动方在同一文件里各改一段、**冲突面同源**（兄弟规则极易互相覆盖、合并时错并）。**判定标准（任一命中即违规）**：① 单个规则文件同时承载两份及以上**互不相关**被测落点的规则；② 新增一条规则时新规则被塞进已有文件而不是按落点归位；③ 规则文件里出现按落点分节的痕迹（"=== 某文件"一类），说明它本来就该拆开。
* **按落点自动扫描加载（L1）**：加载侧登记**规则目录**、按目录自动扫描其中的规则文件，**不得**在脚本里逐个列出规则文件名。理由：逐文件登记时，加一个规则文件又要动脚本——那正是"规则与脚本隔离"要治的形态（改规则要改代码）。**判定标准（任一命中即违规）**：① 脚本里出现规则文件名的字面量清单；② 新增一个规则文件时必须改 `.py` 才能生效；③ 目录里存在规则文件而未被加载（静默漏载＝该批规则空转）。
* **扫描与合并须确定、冲突须显式（L1）**：自动扫描的目录须按**文件名排序**加载（次序稳定、同一次输入得同一结果）；多文件合并时**同名键（同一防线名/同一名单名）一律报错**，不得"后者覆盖前者"——静默覆盖会让人以为新写的那条在跑，而实际生效的是另一个文件里的那一条（与"配置缺失即报错"同源：分不清"在跑的是哪一份"就等于规则失效）。
