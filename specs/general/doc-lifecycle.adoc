= 业务系统全生命周期文档规范（通用层）

适用于**业务系统**（从立项到上线的完整项目）的全生命周期文档组织。文档粒度从模块级提升到阶段级，按生命周期阶段组织，每个阶段对应一个独立目录，文档先行贯穿始终。模块级设计文档与测试设计文档的组织方式见 `specs/general/doc-design.adoc`；多模块项目下模块内的总结性/规划性文档放各模块 `doc/`，归属见 `specs/general/doc-module.adoc`。**项目当前具备哪些功能、每个功能到今天为止的样子**不随阶段推进而变，落点与判据见本文「功能全览（项目现有行为的唯一视图）」。

* **与模块级文档规范的关系（并存不互斥）**：业务系统若同时是多模块项目，两条规范同时适用——根 `doc/` 的阶段目录只放**全局/阶段级**文档，模块内部细节文档一律下沉各模块 `doc/`；同一份文档不得在根 `doc/` 阶段目录与模块 `doc/` 两处重复存放。

**本规范是总体大纲，只限定必要规则，不限制项目自主性**——具体阶段划分、目录命名、文档文件名由各项目按其实际生命周期自行确定，项目可增删、合并、重命名阶段与文档。

== 阶段划分与目录结构（大纲）

业务系统文档根目录为 `doc/`，按生命周期阶段建立子目录。**阶段划分由项目按其实际生命周期自行确定**，仅要求满足以下规则：

* 阶段目录用**编号-阶段名**命名，保证顺序清晰、可扩展（如 `1-initiation/`、`2-requirements/`）。
* 顺序推进的阶段用递增编号；持续迭代类阶段（如运维）可不设编号。
* 阶段目录下**应放**该阶段的 `README.adoc` 说明该阶段文档（索引页要求见 `specs/general/doc.adoc`「文档组织与导航」）。
* 外部系统文档统一放 `doc/external/`，独立于本系统生命周期。

参考：常见生命周期阶段（立项、需求、设计、开发、测试、部署、验收、上线、运维）与示例目录结构如下（仅示意，非强制）：

[listing]
----
doc/
├── 1-initiation/     # 立项阶段
├── 2-requirements/   # 需求阶段
├── 3-design/         # 设计阶段
├── 4-development/    # 开发阶段
├── 5-testing/        # 测试阶段
├── 6-deployment/     # 部署阶段
├── 7-acceptance/     # 验收阶段
├── 8-go-live/        # 上线阶段
├── operations/       # 运维阶段（持续迭代，可不设编号）
├── external/         # 外部系统文档（独立于本系统）
└── README.adoc       # 说明各目录用途与关键文档索引
----

== 各阶段文档（内容要点 + 文件名示例）

每个阶段应产出覆盖该阶段核心内容的文档；**文档文件名由项目自行确定**，下表列出的文件名仅作示例（可增删、拆分、合并、重命名）。各阶段应涵盖的内容要点：

* **立项阶段**：项目背景、目标、范围、投入产出、可行性（技术/经济/风险）。示例：`project-proposal.adoc`、`feasibility-report.adoc`。
* **需求阶段**：功能需求、非功能需求、业务规则、用例、调研纪要、竞品分析。示例：`requirements-spec.adoc`、`requirements-survey.adoc`。
* **设计阶段**：架构设计、模块划分、数据库设计、接口设计、技术选型与取舍。示例：`architecture.adoc`、`database-design.adoc`、`api-design.adoc`。
* **开发阶段**：开发规范、环境搭建、关键实现说明、编码约定。
* **测试阶段**：测试计划、测试用例、测试报告、缺陷记录。
* **部署阶段**：部署架构、部署步骤、环境配置、回滚方案。
* **验收阶段**：验收标准、验收记录、验收报告。
* **上线阶段**：上线计划、上线检查单、上线记录。
* **运维阶段**：运维手册、监控告警、应急预案、故障复盘。

* **内容要点与落点**：各阶段的核心内容要点须在其阶段目录下有落点；**类/方法级细节不进阶段文档**（一律进代码文档注释），阶段文档承载**全局/阶段级**的总结与规划。
== 外部系统文档

* **位置与结构**：外部系统文档目录 `doc/external/` 存放与本系统有交互的**外部系统**的文档，独立于本系统生命周期；按系统名称建子目录 `doc/external/<系统名称>/`，每个系统下的文档结构由各系统自行确定。
* **内容**：包括但不限于对接协议、接口说明、数据格式、依赖关系、调用方式。
* **维护**：由各系统负责人自行管理，本系统仅做引用和归档，确保对接信息可追溯。

== 存量文档迁移与阶段关联

* **存量文档随项目开发逐步迁移**（声明要改这部分时才迁移），不做系统性一次迁移；迁移的内容要求（**内容不减少**）见 `specs/general/doc.adoc`「注释与文档」。
* **文档先行与阶段关联**：每个阶段开始前必须先完成对应阶段文档（**阶段级产物**）的编写或更新；**模块/类/方法级内容不属阶段文档**——按 `specs/general/doc.adoc`「注释与文档」的落点承载（含代码内的文档注释），与代码在**同一提交内**补齐即可。
* **前后阶段互为输入**：前一阶段的文档是本阶段工作的输入，本阶段文档是前一阶段的延续与细化。
* **阶段间双向可追溯**：需求条目在设计中须有对应方案，设计中的方案在测试中须有对应用例。
* **跨阶段变更同步**：变更跨越多个阶段时，须同步更新所有受影响阶段的文档，不得只改一处。
* **版本与变更记录**：业务系统各阶段文档的版本与变更遵循 `specs/general/doc-design.adoc`「版本与变更记录」——阶段文档**不设**固定的头部 `Version`/`LastModified` 字段，变更统一记录到项目的独立 changelog（时间倒序）；各阶段文档之间版本无须一致，但须在 changelog 条目中注明关联文档的变更。

== 功能全览（项目现有行为的唯一视图）

**识别特征（涉及即加载、涉及即核对）**：要回答"这个项目有哪些功能"、改动/移除一个功能、判定"这两处描述的是不是同一个功能"，或新接入一个项目要一份全貌。

**背景（真实失效）**：需求阶段的文档回答"当初要了什么"，是一条**按时间排的事件流**——每个 Issue、每次提需求各占一段。它能证明"这条被要过"，却答不上"项目现在有什么"：同一个功能被要求过三次，就有三段互不相同的说法；两个功能同在一个模块、边界不清，从事件流里根本读不出来。于是"这个功能还在不在、现在长什么样"只能靠在事件流里翻找——而这正是删改能静默溜过去的地方。

* **产物＝按功能组织的全览，不是需求事件流（L1）**：项目须有一份**功能全览**，以**功能**为条目（不是以需求、Issue、时间或提交为条目）——每项写它**现在的样子**，而不是"谁在什么时候提过它"。**判定标准（任一命中即违规）**：① 条目按时间/编号排列，靠读标题才知道讲的是哪一块功能；② 同一功能散在多条里、没有一条能单独读成"它现在的样子"；③ 要答"某功能还在不在"必须回溯任务单或对话。**需求事件流（发布说明、变更日志、逐轮记账）不承担这一职责，也不得被当作全览**。
* **每项须能定位到实现与反证（L1）**：全览的每一项都要给出**代码或配置的落点**与**能反证它还在的判据**（哪条用例、哪个快照/清单/接口契约）——摘掉实现或判据时，条目读起来仍然成立即不合格。**判据本体不在此处**：验收标准怎么写见 `specs/general/spec.adoc`「规格写到什么程度（内容与判据）」，用例的覆盖要求见 `specs/general/testing.adoc`「覆盖要求」——本条只要求全览的每项**指得到**它们。
* **细节按归属分写，全览只做入口（L1）**：全览自身写**功能级**的事实（边界、入口、对外可观察行为、落点、判据在哪）；类与方法的接口约定、算法与取值细节按 `specs/general/doc-design.adoc`「信息归属」写在代码文档注释与设计文档里，全览只引其名称与落点。**判定标准**：全览里出现**逐方法的参数表**或实现过程，即越界。
* **行为变了就同一提交内改全览（L1）**：新增、改变或移除功能时，全览与实现**同一提交内**同步；**移除功能须在全览里显式处置**（删条目并写明去向，或标记为已移除及理由）。**全览过期比没有更坏**——读者按它读会与代码背离。
* **落点与形态（L1）**：落点按 `specs/general/doc-module.adoc`「全局文档与模块文档的分界」分——跨模块的功能写项目根 `doc/` 下的功能全览；只属某个模块的功能写该模块 `doc/` 下的全览，根全览只引它（一行入口）；**单模块项目**即项目根 `doc/` 下那一份。条目数不分份；**分份须按功能边界分，不得按时间或改动批次分**。
* **依据（标准名/编号）**：ISO/IEC/IEEE 29148（要求须单一、无歧义、可验证、可追溯，且可被独立理解）、ISO/IEC/IEEE 42010（架构描述须给出一致的功能与边界视图）、ISO 10007（配置项与其状态的成文信息须有唯一落点）。**"按功能组织而不是按需求事件流组织""每项须指得到反证"是本集合的判据化取舍**——上述材料给的是下限（要求可追溯、视图须一致），未规定全览该长什么样。
