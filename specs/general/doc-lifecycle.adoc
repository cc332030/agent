= 业务系统全生命周期文档规范（通用层）

以下规范适用于**业务系统**（从立项到上线的完整项目）的全生命周期文档组织。文档粒度从模块级提升到阶段级，按生命周期阶段组织，每个阶段对应一个独立目录，文档先行贯穿始终。模块级设计文档与测试设计文档的组织方式见 link:../general/doc-design.adoc[]；**多模块项目**下模块内的总结性/规划性文档放各模块 `doc/`（类级与方法级描述写在**代码内的文档注释**中、不另建文档），不在本根 `doc/` 阶段目录内，归属见 link:../general/doc-module.adoc[]；注释/记录的通用原则见 link:../general/doc.adoc[]。

* 与模块级文档规范的关系（并存不互斥、同一结论）：业务系统若同时是多模块项目，两条规范同时适用——根 `doc/` 的阶段目录只放**全局/阶段级**文档，模块内部细节文档一律下沉各模块 `doc/`（见 link:../general/doc-module.adoc[]）；同一份文档不得在根 `doc/` 阶段目录与模块 `doc/` 两处重复存放

**本规范是总体大纲，只限定必要规则，不限制项目自主性**——具体阶段划分、目录命名、文档文件名由各项目按其实际生命周期自行确定，项目可增删、合并、重命名阶段与文档，不被本规范写死。

== 阶段划分与目录结构（大纲）

业务系统文档根目录为 `doc/`，按生命周期阶段建立子目录。**阶段划分由项目按其实际生命周期自行确定**，仅要求满足以下规则：

* 阶段目录用**编号-阶段名**命名，保证顺序清晰、可扩展（如 `1-initiation/`、`2-requirements/`）
* 顺序推进的阶段用递增编号；持续迭代类阶段（如运维）可不设编号
* 阶段目录下可放该阶段的 `README.adoc` 说明该阶段文档
* 外部系统文档统一放 `doc/external/`（见下「外部系统文档」），独立于本系统生命周期

参考：常见生命周期阶段（立项、需求、设计、开发、测试、部署、验收、上线、运维）与示例目录结构如下（仅示意，非强制）：

```
doc/
├── 1-initiation/     # 立项阶段
├── 2-requirements/   # 需求阶段
├── 3-design/         # 设计阶段
├── 4-development/    # 开发阶段
├── 5-testing/        # 测试阶段
├── 6-deployment/     # 部署阶段
├── 7-acceptance/     # 验收阶段
├── 8-go-live/        # 上线阶段
├── operations/       # 运维阶段（持续迭代，可不设编号）
├── external/         # 外部系统文档（独立于本系统）
└── README.adoc       # 说明各目录用途与关键文档索引
```

== 各阶段文档（内容要点 + 文件名示例）

每个阶段应产出覆盖该阶段核心内容的文档；**文档文件名由项目自行确定**，下表列出的文件名仅作示例（可增删、拆分、合并、重命名），文件名不是强制要求。各阶段应涵盖的内容要点如下：

* 立项阶段：项目背景、目标、范围、投入产出、可行性（技术/经济/风险）。示例文件名：`project-proposal.adoc`、`feasibility-report.adoc`
* 需求阶段：功能需求、非功能需求、业务规则、用例、调研纪要、竞品分析。示例文件名：`requirements-spec.adoc`、`requirements-survey.adoc`
* 设计阶段：系统架构、技术选型、模块划分、部署架构、数据库、接口。示例文件名：`system-architecture.adoc`、`database-design.adoc`、`api-design.adoc`
  ** 模块级功能设计与测试设计的组织方式（测试设计是功能设计的验证规格、二者一体；文档承载总结性/规划性内容，不要求逐类建文档），见 link:../general/doc-design.adoc[]
* 开发阶段：实现细节、关键算法、性能优化、兼容性处理、项目特有约定、本地开发环境。示例文件名：`technical-solution.adoc`、`development-notes.adoc`
* 测试阶段：测试范围、策略、资源安排、环境要求、测试结果、缺陷统计、质量评估。示例文件名：`test-plan.adoc`、`test-report.adoc`
* 部署阶段：环境要求、部署步骤、配置说明、依赖服务、初始运维手册。示例文件名：`deployment-plan.adoc`、`operations-manual.adoc`
* 验收阶段：验收标准、验收结果、遗留问题、签字确认。示例文件名：`acceptance-report.adoc`
* 上线阶段：上线步骤、验证清单、回滚方案、应急预案。示例文件名：`go-live-plan.adoc`、`rollback-plan.adoc`
* 运维阶段（持续迭代）：变更记录、故障处理、定期检查、监控指标与告警。示例文件名：`operations-log.adoc`、`monitoring.adoc`

== 外部系统文档

* 外部系统文档目录 `doc/external/` 用于存放与本系统有交互的**外部系统**的文档，独立于本系统生命周期
* 外部系统文档按系统名称建立子目录：`doc/external/<系统名称>/`，每个系统下的文档结构由各系统自行确定，本规范不做约束
* 外部系统文档的内容包括但不限于：对接协议、接口说明、数据格式、依赖关系、调用方式
* 外部系统文档的维护由各系统负责人自行管理，本系统仅做引用和归档，确保对接信息可追溯

== 存量文档迁移

* 存量文档随项目开发逐步迁移（声明要改这部分时才迁移），不做系统性一次迁移

== 文档先行与阶段关联

* 每个阶段开始前，必须先完成对应阶段文档的编写或更新，经评审通过后方可进入下一阶段
* 前一阶段的文档是本阶段工作的输入，本阶段的文档是前一阶段文档的延续和细化
* 阶段间文档须保持双向可追溯——需求文档中的条目在设计中须有对应实现方案，设计中的方案在测试中须有对应验证用例
* 变更跨越多个阶段时，须同步更新所有受影响阶段的文档，不得只改一处

== 版本与变更记录

* 业务系统各阶段文档的版本与变更遵循 link:../general/doc-design.adoc[] 中「版本与变更记录」的机制：文档版本随变更递增（版本号由源码的代码文档注释承载，如 javadoc `@version` / docstring，不设固定头部字段）；**变更统一记录到项目的独立 changelog 文件（时间倒序）**，不再要求每个阶段文档各自维护文末「变更日志」小节
* 各阶段文档之间的版本无须保持一致，但须在 changelog 条目中注明关联文档的变更（如"需求 v2.1 变更导致设计 v1.3 同步更新"）
