= 版本管理规范（通用层）

适用于**任何版本管理工具**（git、Subversion/SVN、Mercurial、Perforce、TFVC 等）上的任务开发与提交历史管理：约束"冲突处理"与"提交历史整理（压缩提交）"两件事的**共同口径**。本文件只写**工具无关**的规则本体；**具体工具的落地判据**在对应文件——git 的见 `specs/general/git.adoc`（本文件与它分工：本文件说"做什么、怎么判"，它说"在 git 上用什么命令判"）；平台侧的追加口径见 `specs/platform/cnb.adoc`。

**识别特征**：要解决冲突、要压缩提交/整理提交历史、要判定"提交该有几个""解冲突后内容有没有丢"。

== 为什么把"版本管理"与"某个工具"分开写

"版本管理"是**工具无关的概念**：所有版本管理工具都提供同一组动作——取两方改动、报冲突、提交、整理历史。而**冲突的失效形态也由工具无关的部分决定**：任何版本管理工具对冲突**只能报"哪里对不上"**，报不出"哪些行再也回不来"。故规则本体写在这里，引用方用 git 还是 SVN 都读得到；工具专名（`--ours`/`--theirs`、`git mv`、`git diff -M`）与具体命令只写在各工具自己的文件里——**不得把某工具的命令当成规则前提**。

== 冲突处理

* **有冲突须解决，不搁置（L1）**：并行改动同一处导致冲突时，须**自动解决冲突**（逐处保留双方有效改动、按既有约定合并），不搁置、不要求用户人工介入。**判定标准**：留下冲突标记、或把冲突原样交回给用户即不合规。
* **冲突与压缩提交同时提出时：先解冲突、再压缩，最终只有一个提交（L1）**：用户同时（或先后）提出"有冲突"与"压缩提交/压成一个提交"时，这是**一件事的两个动作**——① **先解决冲突**（在当前工作副本/分支内完成，逐处保留双方有效改动），② **再整理提交历史（压缩）**，③ 交付形态是**本次任务交付的那条线上最终只有一个提交**。**判定标准（逐条可核对，任一命中即不合规）**：① 拿"还有冲突"当不做压缩的理由，或反过来拿"要压缩"当不解冲突的理由（两者都落地才算完成）；② 解冲突与压缩各自留了一个提交，最终仍有两个及以上提交；③ 只解了冲突、没压缩，或只压缩、冲突仍在。
* **"只被要求压缩、没被要求解决冲突"也要先解冲突（L1）**：触发面**不限于用户同时或先后提出两件事**——用户**只要求**"压缩提交/压成一个提交"、**没提**解决冲突，而当前分支与目标分支**实际存在冲突**时，同样须**先解决冲突、再压缩**。**不得**把"用户没提解决冲突"读成"不用做"：没被要求不等于可以搁置，**冲突照常自动解决**（口径见上一条『有冲突须解决，不搁置』），且**处理次序不可颠倒**（先解冲突、后整理历史）。**判定标准（任一命中即不合规）**：① **报"已压缩提交"却对冲突只字未提**（既没说有冲突、也没落实处置）；② **以"用户没提解决冲突/没被要求"为由只压不解决**，或把冲突留到压缩之后再议；③ 把"解决冲突"做成**照抄目标分支的文件内容后另起一个单亲提交**（工作副本看起来一致、差异为空，但目标分支**并非本分支的祖先**，平台侧仍报冲突）；④ 拿"要求里只写了压缩"当不做冲突处置的挡箭牌。**与「有冲突须解决，不搁置」的关系**：本条**不是新要求**，而是把那条的**触发面写全**——两条同源，冲突处置不因"用户没提"而免除。
* **解决冲突后须核查是否丢失内容（L1）**：冲突是**同一处被两方改过**的产物，版本管理工具**只能报"哪里对不上"、报不出"哪些行再也回不来"**；故解冲突（以及随后的压缩）之后，**不得凭"没有冲突标记了"就认为解决完毕**，须核查**两侧内容一条未丢**。**判定标准（任一命中即不合规）**：① 用"**整体取一侧**"（放弃另一侧的整份改动）收尾、不做逐处对照；② 只核"文件能编译/没有冲突标记"，就宣称内容完整；③ 汇报"冲突已解决"却不给出可核对的核查判据。**该用哪些判据随对象定（三档）**：
** **文本类冲突**——按内容侧对照：两侧改动**逐处并集**，合并前后的差异与两侧各自的改动清单**逐条对得上**（把"两侧分别改了什么"先各自列一份，再核合并结果是否两份都在）。
** **改名/移动/删除与文件数**——按版本管理工具对"移动"的识别口径强制核对（在 git 上即 `specs/general/git.adoc`「文件移动与重命名」的强制核对：应保留历史的文件不得显示为"删除 + 新增"、应被识别为改名）。**文件总数与各侧清单**须一致：一侧删了、一侧改了同一文件时，"删除"与"改后保留"必须逐条裁决并写明，不得静默取一侧。
** **版本文档类**（依赖清单与锁文件、版本号声明等）——**逐条核对两侧条目的并集**：这类文件**一"整体取一侧"就会静默丢掉另一侧新增/升级的条目**，故须把两侧条目各列一份、核合并结果是否两份都在。

== 压缩提交（提交历史整理）

本节只写**工具无关**的判据；平台侧（如 CNB）的推送与对象钉定口径见 `specs/platform/cnb.adoc`「压缩提交」。

* **压缩＝提交历史整理，内容零变化（L1）**：用户要求"压缩提交/压成一个提交"时，压缩**只改变提交的分组与信息**，**内容逐字节不变**（判据：整理前后工作副本差异为空）。**判定标准**：压缩前后内容出现任何差异，即不是压缩、是改内容。
* **压缩对象只有本次任务尚未合入的临时中间提交（L1）**：压缩对象是**本次任务产生的、尚未合入目标分支的临时中间提交**（多次试跑的修正、迭代补丁、过程性提交）。**禁止的压缩形态（L1）**：① 把**他人（或其它任务）的提交**一并压缩；② 压缩**已合入目标分支**的历史（改写公共历史）；③ 压缩后**内容出现任何差异**；④ 以"压缩提交"为由**扩大范围**（顺带整理无关文件、重排他人提交、改提交信息里的他人署名）。
* **压缩不等于解冲突（L1）**：把冲突处的文件**整体取一侧**后压成一个提交，是把"丢内容"藏进了一个干净的提交里——**压缩不能替代解冲突**；有冲突时须先按「冲突处理」解决并核查内容未丢，再压缩。
* **解决冲突后的核查不可省（L1）**：压缩**不豁免**「冲突处理」的解冲突后核查——压缩后的形态仍须满足"两侧内容一条未丢"，且核查判据须可核对（见「解决冲突后须核查是否丢失内容」的三档判据）。

== 依据

* 变更与工作须受控、可追溯（ISO 10007、ISO 9001）：压缩是**受控变更**，须可追溯——故压缩前后的对象（旧标识 → 新标识）须有对应关系，且**该标准只要求"变更可追溯、可定位"，未规定"提交必须压成一个"**。
* 版本管理工具对冲突的表达边界：工具报"冲突位置"，**不表示"内容完整性"**——完整性须由内容侧逐处对照来判；"整体取一侧"是不可逆的内容丢弃，故须先核查再收尾。
