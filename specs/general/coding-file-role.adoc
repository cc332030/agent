= 通用编码规范·文件的角色（通用层，跨语言）

本文件是通用编码规范的一族之一（**按主题拆分**，其余见同目录 `coding.adoc`、`coding-shape.adoc`、`coding-objects.adoc`、`coding-ui.adoc`、`coding-runtime.adoc`、`coding-source.adoc`）：一个落点会不会被并行改动，决定它怎么排布。

== 文件的角色（会不会被并行改动，决定它怎么排布）

**本节的归属（L1，先定条件再谈强制）**：本节是 `specs/general/coding-source.adoc`「源码管理方法」**并发档**的执行细则——**取常规档的项目不适用本节**（按职责与体量排布即可，冲突现场解）；取并发档的项目适用本节，且本节所有条目都要落实。取哪一档只看一处：`specs-config.toml` 的 `[source-management].mode`（取值见该文件；本仓库取的是并发档，故走本节）。**判定标准（任一命中即违规）**：① 项目取常规档，却在 review/交付里按本节要求别人分份、配合并策略、改生成物；② 项目取并发档，却仍有落点按常规档办（两个解各用一半）；③ 把"本项目取常规档"读成本节所述做法**错了**——它是**另一档**，不是**错误**。

**任何语言、任何项目**都适用，但**只在多任务需要并行改动同一份代码**时才显出后果：一处落点被两个改动同时碰，合并就必然冲突——**这不是谁手滑，是结构决定的**。

**识别判据（先判这是不是一个并行热点）**：把最近若干次合入**按文件数一遍**——改到它的次数占改动次数的**很大比例**，且每次改的都是**同一片区域**（同一个位置持续被追加、整段被重排），即本条所指的并行热点。**反例**：一份按主题分节、各处各改各的正文，改动散在不同节里，不算热点。

**为什么要先做这个判定**：热点与"文件大"是两件事——**大而各处各改各的不撞，小而每轮都往里追加一行的必然撞**。按体量拆（见上一节）解决不了它；能解决它的是**按"谁在写、写在哪一片"切落点**。

* **先给文件一个角色、再决定它能不能并行改（L1）**：给一份文件定性——它属于下面哪一类，后面所有排布与改法都由这一条推出来：
** **独占落点**：这件事**天然只有一处、只做一次**（全量清单、全局序号、总基线单值、校验脚本的执行序列本身）。**判据**：改它必须与另一处同时改才算完整，或它的值是"整份的唯一一个数"。
** **并行落点**：**每一轮任务都会往里加自己那一份**的落点（一份防线/一条规则/一个用例组/一行记账）。**判据**：它按"份"组织，各份之间无次序依赖。
** **只读落点**：别人写、本方只取用（依赖清单、第三方副本、生成产物）。**判据**：它不是本仓库维护的东西。
** 判定标准（任一命中即违规）**：① 说不出这份文件属于哪一类；② 把装着多份东西的并行落点当成独占落点往里追加（每一轮都在同一片区域插行）；③ 把独占落点拆成多处存放、再靠人记得同步（那是"取值的唯一来源"与本条同时违规）。
* **并行落点按‘份’切、不按‘条’切（L1）**：并行落点**按"份"切开、一份一个文件或一次追加到文件尾**——一道规则一份、一个主题一份、一个号段一份、一轮记账一份；**不得**把各份挤在同一段、靠"顺延编号"表达次序，**也不得**把一份里的每一条各切成一个文件。**判定标准（任一命中即违规）**：① 新增一份要改动同一文件里既有各份的编号或位置（其后整段位移）；② 两份互不相干的东西共用一个文件，且每一轮都往同一片区域追加；③ 以「反正只有一个文件」为由继续往里追加，而不判它是不是并行落点。
* **切口的单位是"份"，不是"行"（L1）**：一份文件应当有**独立的身份**——能被单独读到、单独改动、单独说明它为什么在、单独被引用。**"份"由身份定，不由行数定**：一份落点要能回答"这一份是什么"——一个主题、一个号段、一轮记账、一道防线各算一份，哪怕它里面只有几条；反过来，只是某张表里的一行、离了这张表就指不出来是什么的，**不是**一份——它是那张表的内容，表是它的落点。**独立身份也不是"分成一行一份"的理由**：只有一行的文件，`git log`/`git blame` 只会告诉你"这个文件被改过"，说不出改的是哪一条；它也没有"份"该有的**上下文**——判据、例外、依据无处可放，读的人仍要跳到别处去拼。**判定标准（任一命中即违规）**：① 拆出来的文件**没有独立身份**：翻到它、引用它时说不清"这一条是什么"，只能靠文件名或"它在表里第几行"定位；② 拆到这一粒度之后，新增一条仍要同时改一个汇总处的 `include` 或登记行——冲突只是从"改一行字"变成"加一个文件 + 改那一行"，**冲突面没缩小**；③ **一条一份**（每份只有一行正文）：冲突面没缩小、可读性与历史追溯都退化了，只换来"改动看起来分散"。本仓库实测：把一张 187 行的防线清单拆成 187 个单行文件、把 123 条检查项拆成 123 个单行文件（其中 91 份只有一行条目名），两轮都被用户当场否掉并要求整体回滚——按号段分份仍要"改那一份里的同一片区域"，而多出来的上百个文件只是把 `git log`/`git blame`/IDE 跳转一起废掉。
* **能靠合并策略解决的，不靠拆分解决（L1）**：落点的冲突成因是"两边各加一份、位置相邻"时，先看有没有**不需要动落点的解法**（版本控制的按行合并策略一类的配置，对**只增不改**的清单有效），冲突到此为止；拆分解决的是"改的是不同内容"，不是"改在同一位置"。**判定标准（任一命中即违规）**：① 为消冲突把只增不改的清单拆碎，而"不动落点"的解法试都没试；② 拆完之后仍要求各份之间有顺序依赖（那说明拆错了轴——该按"删掉次序"拆，不是按"内容分片"拆）。
* **独占落点只做一次、且要能被机械核（L1）**：独占落点**允许只有一处**，但那一处必须**被一道机械判据核住**（清单与实际收集结果逐项相等、序号与执行序列逐一同序、总基线不减少）——**"只有一处"不等于"靠人记得改那一处"**：没有判据的独占落点是下一次静默漂移的入口。**判定标准（任一命中即违规）**：① 独占落点没有对应的机械判据（只能靠人核对）；② 为了让改动"看起来不冲突"而把独占落点复制成两份（两份必然各写一半）。
* **并行落点之间不得有次序依赖（L1）**：按份切开的落点，其**合并结果不得依赖文件名、目录序或写入先后**——要表达次序时，次序写在**唯一那一处独占落点**（执行序列、索引表）里，各份自己只声明身份。**判定标准（任一命中即违规）**：① 两份内容相同、仅文件名不同，脚本读到的先后会影响结果；② 各份里各写一个序号、靠序号倒推出次序（两份改了序号就冲突，等于把独占落点又摊回并行落点）。
* **热点在生成侧：能由规则现算的，就不要列成清单（L1）**：一份清单若**能从目录或收集规则现算**（某目录下全部文件、某前缀下全部规则文件），就**不许**再手写一份并列清单——手写清单是本条最典型的并行热点（每加一份都要插一行）。清单只留**收集规则**那一处，条目由它现算；确实必须手写的部分（例外名单、锚点取值）按主题分到各自那一份里。**同一个成因还有一格：序号**——按次序排的清单，**序号由**现算**给出、不写进条目里**：写着数字，插入一项就得把其后每一项的数都改一遍（位置变、数也变），那与"清单要人工同步"是同一件事，只是把同步量从"加一行"换成"改 N 行"。**判定标准（任一命中即违规）**：① 目录里有什么、清单里就抄一遍，且两者靠人同步；② 例外或配置里出现"当前已知的那几个文件"这类备注（未列入者永远是盲区）；③ 条目里手写着由别处现算即可得到的序号，插入一项要连带改其后各条。
* **三种冲突各归各的正解（L1）**：「并行热点怎么消」先前只落在一条上（拆分成份），而冲突其实有三类，拆只对其中一类有效——**按冲突的形态取**：**① 两边各加一项、位置相邻**（只增不改的清单、表行、并列配置项）取**合并策略**（版本控制侧的按行合并配置，登记在仓库根的属性文件里）：两边各加的行自动都在，不动任何既有行；**② 两边改的相邻几行、合并时只要都留**（多行条目、连续段）与 **③ 两边改的同一行/同一处**（必须人判哪个对）都没有"配置就能解决"的答案：机制是**两边各留、撞在同一行时人工取并集**——把两边的改动**逐处合并**（不取单侧、不整段覆盖），并在改动说明里写明合了哪两侧；不该做的是**为躲这种冲突去拆文件**（拆了也不解决"同一行被两处改"）。**判定标准（任一命中即违规）**：① 只增不改的清单仍在靠拆碎文件躲"两边各加一行"（合并策略一条都没配）；② 解冲突时**整段取一侧**（另一侧新增的内容静默丢失，而全部校验全绿）；③ 为躲"两边改同一行"去拆文件或改落点（那一格本就要人判，拆了只是把判的位置挪远）。
* **存量边界（L1）**：本条**只管新增、以及本次改到的那些落点**——改到哪处才顺带按本条排布该处，**不发动全库改造**；已存在但本次不触达的热点不动（随动迁移，见 `specs/core/execution.adoc`）。
* **例外（L2，须写清理由并说明用了哪一条）**：① **一次动作本身就必须同时改多处**（新增一条规则要同时改执行序列、索引表与总基线）：那**不是并行热点、是独占动作**——按独占落点办、各轮排队做，不为一处改动去拆另一处；② **该落点的格式由外部工具或平台规定**（一份必须整份提交的清单文件）：按外部格式办，并把派生内容**下沉**到并行落点，主文件只留引用。
* **逐行登记面：表里只留身份，别的一概不做（L1）**：一张**逐行登记**的表（一道一条、一行一项）按「一份一行」拆开，会掉进本节的第三条判定标准；整份留着又掉进"每一轮都往同一片区域追加"。正解是**把这张表压到最小**：每行只留一句 `include::` 指回**它自己那一份正文**（**正文按身份分份**：一份一行正文，文件名承接身份——防线名、条目名，而不是"第几行"），表体由判据整段现写、人在表里一个字节都不碰。**表里不写的东西**（写了就是同一份事实的第二处，且全都要人维护）：① **序号**——次序就是行的位置，写数字就得在插入一项时改其后每行；② **任何现算得出来的格子**（"谁在用"、条数、状态）——由收集规则、调用关系推出来；③ **别人的行**——新增一项只碰自己那一份正文与执行序列里自己那一行。**判定标准（任一命中即违规）**：① 逐行登记面里手写着序号（插入一项要连带改其后各行）；② 那一份的**文件名只承接坐标**（"第 30 行"），离开表就说不出它是哪一条；③ 新增一项仍要求在汇总表里插一行、或改一个汇总清单；④ **汇总表本身要人一行一行维护**（留一句"记得同步表里那一行"的，等于把热点原样留着——两个并行改动都往中段加一行时，改的是同一处，**没有任何合并策略能解**）。
* **不做：靠文件与目录就能回答的，不另立一处回答（L1）**：`specs/general/coding-source.adoc`「源码管理方法」说"能由规则现算的不列清单"，这一条是它的前一格——**很多问题本来就不该有"一处"**：文件在不在、它属于谁、它挨着谁，这些都由**目录与文件名**已经回答完毕。再立一份清单、一个编号、一个总数值去回答同一个问题，就是给这份事实开了第二个来源（两份必然漂移，且那一处必是并行热点）。**判定标准（任一命中即违规）**：① 立一份"当前有哪些份"的清单，而它们的落点本来就在同一个目录里（目录里有什么，判据扫一遍就知道）；② 立一个**总数/总量**（用例数、条数、基线）去代表"这一批还在不在"，而这个数可由代码数出来——总数还多一个毛病：同文件内删一条加一条就能维持它，**删了什么一个也看不见**（要看"还在不在"，看那一份文件在不在，那是目录能答的）；③ 为一组坐标相同的条目立一个**索引文件**（"谁在第几行""谁和谁一对"），而这个对应关系由**同层同名、同前缀**这类命名约定就能推出来；④ 以"这样查起来方便"为由保留第二处——方便是给读者的，来源必须只有一处。**本仓库实测**：反例用例的类数先是一个全局常量、后来按防线分片成一张表（11 份），两次都是把"可由测试类名数出来"的数抄一份——最后这一格整个去掉，改成按目录看"这一份在不在"。
* **可以依赖的约定关系（L1，按可靠程度排序）**：想让"来源只有一处"，就得让**结构本身**承载关系。可靠程度从高到低：① **上下级目录**——"这一份属于这个主题"由它在哪个目录里表达，最稳（目录层级是文件系统的一部分，不会被正文改错）；② **文件名/前缀**——"这两份是一对"由同名不同后缀表达（`<身份>.toml` 与 `<身份>.adoc`）、"这一批是一类"由同前缀表达；③ **文件在不在**——"这一份还在不在"用目录里有几份回答，不用一个数回答；④ **篇幅与位置**——"这一份很短"不该被当成"它不算一份"的理由（见上一节"切口的单位是份，不是行"），但"这一份只有标记、话在别处"是正当的（零字节标记文件就是这一档）；⑤ **执行顺序**——次序由唯一的序列给出，"第几个"不写进各份。**判定标准（任一命中即违规）**：① 一处关系本可由目录或文件名表达，却另立清单/索引/编号去表达（两份会漂移）；② 同一份内容既写在落点里、又写在标记/索引里（那是同一段话两处写法，`specs/general/review.adoc`「精炼性」同一条）；③ 把"文件名/目录"当成**只给机器看**的东西、正文另抄一份配对表（配对表是第二来源，改一处必漏另一处）。
* **规则数据按主题分份、一份里一道防线（L1）**：规则文件（判据措辞与锚点清单的落点）若**每一轮改动都要往里插一组**，它就是一个并行热点——按"一份防线一组"切：`<主题>/guards/<防线名>.toml`，加载侧按目录**递归扫描**（登记目录、不登记文件名）。**判定标准（任一命中即违规）**：① 同一份规则文件里堆着多道防线，且新增一道防线要往这份文件的**任意位置**插一组；② 为了让新文件被读到而改脚本里的文件名清单（那是把"目录即清单"换成了清单）；③ 同一条判据的措辞在**两个规则文件里各写一份**（合并期须报错，不得后者静默覆盖前者）。**本仓库实测**：同一张防线清单先被拆成 187 个「一行一份」（否掉），再按主题收成 8 份（仍要插行、仍要改数字），最后落到本条——行正文按防线名分份、序号现算。
* 依据（标准名/编号）：ISO/IEC 25010（可维护性：模块化、可分析性与可修改性——一处改动的影响面应当可控）、ISO 10007（配置项须可辨识、变更须受控）、ISO/IEC/IEEE 29148（判定须单一、无歧义、可验证）、Martin Fowler《Refactoring》（按职责抽取、重复出现才收敛）；软件配置管理中的"独占检出/合并冲突"是版本控制的基本事实（同一落点被两处并发修改即需人工合并）。**「先给文件定性（独占/并行/只读）、再决定能不能并行改」「独占落点必须配机械判据」「能现算的不列清单」「靠文件与目录就能回答的不另立一处回答」「独占动作不为一处改动去拆另一处」「按冲突形态选解法（各加一项→合并策略，改同一处→人工取并集）」是本集合的判据化取舍**——通行材料讲"别把什么都塞进一个文件"（按体量拆），**未**给出"按会不会被并行改动来定性排布"这一轴；版本控制系统只提供合并策略与冲突标记，**未**规定"哪些关系该由目录与文件名承载、哪些该由清单承载"。
