= AGENT 执行规范

本规范用于约束 agent 的编码与协作行为，供**任何语言、任何项目**遵循。

== 访问与解析（引用方须知）

* 引用方式：引用方项目通过 https 公网静态路径或本地相对/绝对路径引用本文件，不限方式。**引用方只需引入本文件（`AGENTS_COMMON.adoc`）**；本规范内容存放于本文件所在目录下的 `specs/` 子目录（目录结构不变），随本文件一并生效，这是所有相对引用的固定前提。
* **公共内容边界（重要）**：本文件与其 `specs/` 即本规范的**全部公共内容**，面向**任意语言、任意项目**通用；公共内容须**自足**——凡在公共内容里出现的内容都只能引用本文件与 `specs/` 下的文件，**不得引用引用方看不到、也拿不到的私有落点**（维护方自己的仓库目录、项目入口文件、脚本名等；引用了就是死链，读到的规范只成立一半）。引用方仓库根目录另有**它自己编写/维护的项目规范**（通常命名为 `AGENTS.adoc`），那是**该项目自身专用**的规则，**不属于公共内容**——处理任何内容前先判断"这是公共内容还是某个项目自身的规则"，两者不得混淆。
* 路径解析规则：文中出现的 `specs/...` 均为**相对本文件所在目录**的路径。无论本文件以何种 URL/路径被打开，解析方式都是：
  ** https 访问：`specs/core/execution.adoc` = `本文件所在目录URL/specs/core/execution.adoc`；
  ** 本地相对/绝对路径：`specs/core/execution.adoc` = `本文件所在目录/specs/core/execution.adoc`。
* agent 执行要求：读取本文件后，须将本文件所在目录视为基准，把文中的 `specs/...` 解析为 `<基准目录>/specs/...` 后加载对应文件；禁止仅凭本文件内容猜测规范，凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范（见下「加载调度器」）。
* **入口可达性自检（L1，动手前先做）**：加载规范前先确认**本文件实际可达**——按引用方式实际取到本文件内容；取不到（网络不通、地址失效、本地无副本）时，须**先告知用户规范不可达并请其提供可访问地址或副本**，不得"假装已加载"（未读规范即评"符合规范"、或凭记忆代替规范均属违规，见上「agent 执行要求」）。
* **从属者（子 agent/被引用方）适配由已加载入口驱动、不靠自报（L1）**：加载者不是任务的直接执行者时（子 agent、被派发的分步任务、由任务原文引用规范），执行者不得以"我没被派发这份规范""指令里没有它""上级说按规范做就够了"为由跳过加载或降低约束；**加载的驱动权在入口侧**：派发者须把"读取并遵守本入口"作为派发内容的一部分，执行者读到即须自行按本文件与其调度器加载对应规范（**涉及即须加载**，见下「分类与懒加载」），不得等上级逐条转发原文；**"上级已读过"不构成下级免责**——约束随入口传递、不随上下文传递。
* 加载方式（网络不佳时建议下载到临时目录）：本规范常部署于外网，**网络可能不佳**，故**建议**先把本文件与其 `specs/` 下载到 `tmp/` 下的临时目录（如 `tmp/agent-specs/`）、后续从本地副本读取——一次下载整目录、避免逐个 URL 重拉（下载后相对解析基准不变，仍以本文件所在目录为基准）。副本按临时产物处理（见 link:specs/core/execution.adoc[]「临时产物」），**仅用于读取、不得替代远程引用**；网络正常或已有本地副本时直接读取即可。

严格使用本规范。规范以本文件当前内容为准；与本规范冲突时，以本规范定义为准。若本规范与**引用方项目自己编写/维护的项目规范**（即引入本规范的那个项目自身定义的规范，非本规范文件）冲突，以引用方项目自身规范为准。

== 最高优先级铁律（先读）

* **文件移动/重命名必须用 `git mv`，禁止 delete+create**（不得用「新增新文件 + 删除旧文件」代替移动/重命名，否则 git 历史断裂）：**最高优先级（L1）、最高关注项 P1、凌驾于一切其他规则**，任何"重构/拆分/整理"理由都不得规避；**重构/去重时不得删除或降级本条及其引用**（本条为最高关注项、不可降级）。判定标准、一拆多与兜底核对见 link:specs/general/git.adoc[]「文件移动与重命名」（权威完整定义）与 link:specs/core/execution.adoc[]「文件操作强制检查」。

* **同一文件的重命名与内容修改必须分两个提交**（一次改动里既重命名该文件、又改其内容时）：**先 `git mv` 并只提交改名（内容逐字节不变）**，**再改内容**；分量小、引用少都不是合并的理由，无正当理由可豁免（唯一例外：用户明确声明合并成一个提交）。**最高优先级（L1）、最高关注项 P7**（最高关注项 P1 的补充：`git mv` 保住 rename 跟踪，本条保住"这次移动是可独立回溯的记录"），**重构/去重时不得删除或降级本条及其引用**。判定标准、提交顺序、无损拆分与自检命令见 link:specs/general/git.adoc[]「重命名与内容修改须分两个提交（默认固定动作）」（权威完整定义），必加载层重申见 link:specs/core/execution.adoc[]「文件操作强制检查」。

* **不得执行任何会不可逆丢失内容的操作**（删除文件/目录、清空数据、`rm -rf`、`git reset --hard`、强推覆盖远端等）：**先确认目标、先备份可取回、范围可界定**，再执行；不确定即不做、先确认。**最高优先级（L1）**——破坏性操作不可逆，属安全底线（判定与兜底核对见 link:specs/core/execution.adoc[]「破坏性操作」）。

* **不得编造事实与来源**（命令/API 签名、依赖坐标、标准编号与名称、链接与路径、数据与结论）：**不知道就说不知道并去查证，宁可不给也不得编**。**最高优先级（L1）**——一次虚构会污染整条下游引用链。

* **优先站在前人的肩膀上看世界**：规范条目的依据应**优先引用广泛、高知名度、高可靠性的业界标准与文献**（ISO/IEC/IEEE、RFC、W3C、OWASP 等），**出处只写标准名/编号、不附链接**，对标准有明确自身要求时须**显式覆盖并说明理由**——**完整规则见 link:specs/general/source.adoc[]「外部引用（标准/文献/规范）」**（本条为重申，不复制正文）。

**上述铁律的定级与完整性保护**：条目按 **L1 强制 / L2 建议 / L3 允许** 分级，最高关注项**不可降级**（分级定义与各级遵守要求见 `specs/core/execution.adoc`「分级与最高关注项」）。



变更历史由规则化的变更日志承载，但**只记影响、不记过程**：changelog 条目写"改了什么、给谁带来什么影响"，不写实现过程与工作量（读者不问改了几行代码）；条目取舍口径、**组织形态（时间倒序；默认按发布版本分组 + 组内按类型）**与**条目形态（流水式 / 表格式，择一）**见 link:specs/general/changelog.adoc[]，版本号与排序机制见 link:specs/general/doc-design.adoc[]「版本与变更记录」。

== 分类与懒加载（加载调度器）

规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层分类存储（位于 `specs/` 下），**按需懒加载**（避免常驻加载不需要的规范、节省上下文）。懒加载是手段，**"强制不漏"是底线**——凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范，不得因"规范文件不在常驻上下文"而凭记忆或仅凭本入口文件猜测执行。

  ** Java 项目（检测特征：存在 `.java`、`pom.xml`/`mvnw`、lombok 配置等；**编译/运行版本以 `pom.xml` 声明为准**、不得用环境默认 JDK，见 link:specs/general/ci-cd.adoc[]「运行环境须与项目声明一致」） → link:specs/stack/java.adoc[] + link:specs/stack/java-syntax.adoc[] + link:specs/stack/java-testing.adoc[]（命中以下场景即按栈文件执行，条文见各文件、此处不复述）：**类型指代**（文中出现「包名 + 类名」形态的指代、写 javadoc、提到不在 classpath 的全限定类名）、**对象转换**（多层嵌套对象之间的转换、`MapStruct`）、**MyBatis-Plus 持久化访问**（识别特征见通用层「编写代码」；栈文件给四个成员方法 `lambdaQuery()`/`lambdaUpdate()`/`ktQuery()`/`ktUpdate()` 与禁止面 `new QueryWrapper` 等）、**Feign 接口命名**（只此一类接口）、**构造方法不手写**（`@NoArgsConstructor`/`@RequiredArgsConstructor`/`@AllArgsConstructor`）、**测试类命名与拆分**（`Tests`/`BootTests`/`PerfTests`/`IT` 四类后缀，一个被测类可按需求/分类拆多个测试类、不得滥拆）、**跨语言脚本**（SQL/Lua 放 `src/main/resources/`、MyBatis 的 SQL 写 `*.xml`、加载时机按性能敏感度定性）
  ** Spring 项目（存在 Spring 依赖/注解）→ link:specs/stack/spring.adoc[]（检测特征：写/改 Feign 等内部调用接口或控制器的**路由路径**——**接口路径优先用中划线**；持久化的 MyBatis-Plus 落点见 link:specs/stack/java.adoc[]「持久化访问（MyBatis-Plus / JPA 等）」）
  ** Maven 构建（存在 `pom.xml`/`mvnw`）→ link:specs/stack/maven.adoc[]
  ** Bash/Shell 脚本（存在 `.sh` 文件，或 shebang 为 bash/sh）→ link:specs/stack/bash.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 LF）
  ** Python 脚本（存在以 `python3`/`python` 为 shebang 的 `.py` 脚本）→ link:specs/stack/python.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 LF；**解释器版本以项目声明为准**，见 link:specs/general/ci-cd.adoc[]「运行环境须与项目声明一致」）
  ** PowerShell 脚本（存在 `.ps1` 文件）→ link:specs/stack/powershell.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 CRLF，**含同名 `.bat` 启动脚本的纯 ASCII、不写 BOM 与 CRLF 要求**）
  ** 其他语言/技术栈（nodejs、ubuntu 服务器配置、python 等）按其对应栈文件加载——栈文件由引用方项目按「技术栈扩展约定」在 `specs/stack/` 下补充登记（尚未登记的栈按 AGENTS_COMMON.adoc 通用层与 coding.adoc 执行，不臆造其专属规则）
* 项目类型层（**按项目在其自身规范中的主动声明加载，声明才加载、未声明不加载**——仅适用于特定项目类型、对普通项目不生效的规范归入此层，由项目主动声明所属类型触发加载，不靠特征自动检测）：
  ** 通用工具/库类项目（以可复用组件/库/工具为主、要求每个类在设计时保证绝对正确与绝对可维护性的项目）→ link:specs/general/doc-tool.adoc[]（文档组织：类级细节归代码文档注释、独立文档承载模块/功能级总结与规划）。**触发方式**：项目在其**自身规范**（引用方项目自己编写的项目规范，如项目根目录 `AGENTS.adoc`）中**主动声明**本项目为通用工具/库类项目，agent 检测到该声明即加载本规范；未声明则视为普通项目，不加载。**声明模板（可直接粘贴到项目自身规范头部）**：`本项目为通用工具/库类项目，各类须保证绝对正确与可维护性。`；等价表述（"工具库""组件库"等，描述意思一致即可）同样触发加载
* 平台层（按使用平台加载）：
  ** CNB 平台（在 CNB 上进行任务开发与合并请求管理、与平台上的 NPC/执行者协作、按分支/PR 派发或复核改动、处理流水线状态、**在 Issue/PR 里发评论 @ 某个 NPC 发起一次执行**） → link:specs/platform/cnb.adoc[]（分支与合并请求统一、冲突处理、**评论唤起新实例（平台侧的派发入口：一次评论 = 一次派发；执行者不得自行发评论唤起自己）**、**压缩提交（提交历史整理的判据、须先确认无人在用旧对象、force-with-lease、与「NPC 禁合并」互不豁免）**、**对象钉定与可追溯**、**协作与执行者可用性**、**执行吞吐（平台侧）**）

* 项目自身维护层（**只对"维护一套被其他项目引用的共享内容（规范集合、模板、公共脚本等）"的项目生效**，识别特征：项目自己维护这类共享资产集合）：
  ** 条目落点：该层的规范文件由**维护方项目自己的项目规范**登记，**不是公共入口的加载项**，公共内容不引用其私有文件——引用方按公共输入执行时看不到它、拿到了也无从加载（其项目里也没有本仓库的文件），故公共内容里的规则一律在本文件与 `specs/` 内自足表达。
  ** 维护方自己维护规范集合时所需的元规范（分类准入与定级、规范自身重构、优先级与最高关注项、维护方的验证义务等）由该项目自行承载（它可以放在维护方自己的仓库与项目规范里，也是本层的一份实现）。

== 规范文件登记完整性

* 本入口的加载调度器是规范文件的**唯一登记处**，双向一致：凡被 `specs/...` 引用的规范文件都须在对应分类登记（"写文件"与"登记调度器"是同一个动作，未登记即永远不会被加载、规则实际失效），登记也不得指向不存在/未引用的文件；该一致性**可由机械校验核对**（属可确定性核对的一类，维护规范集合的项目应自行设防线）

== 技术栈扩展约定

本规范按"分类 + 懒加载"设计，天然支持多语言、多项目类型。新增技术栈规范时：

* 在 `specs/stack/` 下新增对应栈文件（如 `nodejs.adoc`、`python.adoc`），只收录该栈专属规则；**新增前先过准入判定**（是否该收、该收进哪一层：对任意项目成立才进公共内容，只对某个项目成立则写进该项目自己的项目规范）；
* 跨语言通用规则一律写入 link:specs/general/coding.adoc[]，避免重复；
* 同步在本入口文件的"技术栈层"登记，明确检测特征，保证"按项目类型加载且不漏"。
