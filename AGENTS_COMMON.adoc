= AGENT 执行规范

本规范用于约束 agent 的编码与协作行为，供**任何语言、任何项目**遵循。

== 访问与解析（引用方须知）

* 引用方式：引用方项目通过 https 公网静态路径或本地相对/绝对路径引用本文件，不限方式。**引用方只需引入本文件（`AGENTS_COMMON.adoc`）**；本规范内容存放于本文件所在目录下的 `specs/` 子目录（目录结构不变），随本文件一并生效，这是所有相对引用的固定前提。
* 路径解析规则：文中出现的 `specs/...` 均为**相对本文件所在目录**的路径。无论本文件以何种 URL/路径被打开，解析方式都是：
  ** https 访问：`specs/core/execution.adoc` = `本文件所在目录URL/specs/core/execution.adoc`；
  ** 本地相对/绝对路径：`specs/core/execution.adoc` = `本文件所在目录/specs/core/execution.adoc`。
* agent 执行要求：读取本文件后，须将本文件所在目录视为基准，把文中的 `specs/...` 解析为 `<基准目录>/specs/...` 后加载对应文件；禁止仅凭本文件内容猜测规范，凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范（见下「加载调度器」）。
* 加载方式（网络不佳时建议下载到临时目录）：本规范常部署于外网（https 公网静态路径），**网络可能不佳**，故**建议**先将本文件及其 `specs/` 规范下载到项目根目录 `tmp/` 下的临时目录（如 `tmp/agent-specs/`），后续一律从本地副本读取——可一次下载整目录、避免逐个 URL 反复拉取因网络抖动失败或变慢（下载后 `specs/...` 相对解析基准不变，仍以 `AGENTS_COMMON.adoc` 所在目录为基准）。下载的副本按临时产物处理（见 link:specs/core/execution.adoc[]「临时产物」），**仅用于读取规范、不得以此替代远程引用**（不改变规范入口的指向，与 link:specs/general/verify.adoc[]「编译/运行验证」中『外部资源禁止本地下载引用』不冲突——后者针对被项目代码/构建引用的外部资源，本条针对 AI 读取规范）；网络正常或已存在本地副本时直接读取即可，不必强制下载。

严格使用本规范。规范以本文件当前内容为准；与本规范冲突时，以本规范定义为准。若本规范与**引用方项目自己编写/维护的项目规范**（即引入本规范的那个项目自身定义的规范，非本规范文件）冲突，以引用方项目自身规范为准。

== 最高优先级铁律（先读）

* **文件移动/重命名必须用 `git mv`，禁止 delete+create**：不得用「新增新文件 + 删除旧文件」代替移动/重命名——这会使 git 历史断裂（旧文件历史丢失）。此为**最高优先级、凌驾于一切其他规则**的禁止项，任何"重构""拆分""整理"等理由都不得作为规避借口。完整规则见 link:specs/core/execution.adoc[]「最高优先级铁律」与 link:specs/general/git.adoc[]「文件移动与重命名」。

== 分类与懒加载（加载调度器）

规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层分类存储于 `specs/` 下，**按需懒加载**（避免常驻加载不需要的规范、节省上下文）。懒加载是手段，**"强制不漏"是底线**——凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范，不得因"规范文件不在常驻上下文"而凭记忆或仅凭本入口文件猜测执行。

加载规则：

* 必加载层（每次工作都须加载）：
  ** 执行原则：link:specs/core/execution.adoc[]
* 通用层（涉及对应活动时加载，不得跳过）：
  ** 编写代码 → link:specs/general/coding.adoc[]（通用编码，跨语言）
  ** 编写/修改脚本（bash/sh、Python、Node、PowerShell 等脚本文件） → link:specs/general/script.adoc[]（通用脚本规范，跨语言）
  ** 写注释/文档/格式（含代码内文档注释 javadoc/docstring/JSDoc 的地位与"内容不减少"要求） → link:specs/general/doc.adoc[]
  ** 设计文档/测试设计文档/文档分层（核心功能新增、重构、行为变更、方案选型；判定"内容写在哪一层"） → link:specs/general/doc-design.adoc[]
  ** 业务系统全生命周期文档（**项目按生命周期阶段组织文档**，识别特征：`doc/` 下存在按阶段编号的子目录（如 `1-initiation/`、`3-design/`、`operations/`），或项目涉及需求→设计→开发→测试→部署→验收→上线的完整流程、存在需求规格/测试报告/部署方案/验收报告等阶段级文档、或存在 `doc/external/` 外部系统文档目录） → link:specs/general/doc-lifecycle.adoc[]
  ** 模块级文档组织（存在**多模块结构**，或涉及"模块文档放哪、根 `doc/` 放什么"的归属判定） → link:specs/general/doc-module.adoc[]
  ** git/版本控制操作 → link:specs/general/git.adoc[]
  ** code review → link:specs/general/review.adoc[]
  ** 多 agent 协作 → link:specs/general/collab.adoc[]
  ** 跑测试/补测试 → link:specs/general/testing.adoc[]（公共测试规范，跨语言）
  ** 编译/运行/分步验证 → link:specs/general/verify.adoc[]
  ** 配置/编写 CI/CD 流水线（存在 `.github/workflows/`、`.gitlab-ci.yml`、CI 平台流水线配置等，或涉及流水线运行时/步骤调优） → link:specs/general/ci-cd.adoc[]
* 技术栈层（按项目实际使用的语言/技术栈加载，**检测到即必须加载，不得遗漏**）：
  ** Java 项目（存在 `.java`、`pom.xml`、`mvnw`、lombok 配置等）→ link:specs/stack/java.adoc[] + link:specs/stack/java-syntax.adoc[] + link:specs/stack/java-testing.adoc[]
  ** Spring 项目（存在 Spring 依赖/注解）→ link:specs/stack/spring.adoc[]
  ** Maven 构建（存在 `pom.xml`/`mvnw`）→ link:specs/stack/maven.adoc[]
  ** Bash/Shell 脚本（存在 `.sh` 文件，或 shebang 为 bash/sh）→ link:specs/stack/bash.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载）
  ** Python 脚本（存在以 `python3`/`python` 为 shebang 的 `.py` 脚本）→ link:specs/stack/python.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载）
  ** PowerShell 脚本（存在 `.ps1` 文件）→ link:specs/stack/powershell.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载）
  ** 其他语言/技术栈（nodejs、ubuntu 服务器配置、python 等）按其对应栈文件加载——栈文件由引用方项目按「技术栈扩展约定」在 `specs/stack/` 下补充登记（尚未登记的栈按 AGENTS_COMMON.adoc 通用层与 coding.adoc 执行，不臆造其专属规则）
* 项目类型层（**按项目在其自身规范中的主动声明加载，声明才加载、未声明不加载**——仅适用于特定项目类型、对普通项目不生效的规范归入此层，由项目主动声明所属类型触发加载，不靠特征自动检测）：
  ** 通用工具/库类项目（以可复用组件/库/工具为主、要求每个类在设计时保证绝对正确与绝对可维护性的项目）→ link:specs/general/doc-tool.adoc[]（文档组织：类级细节归代码文档注释、独立文档承载模块/功能级总结与规划）。**触发方式**：项目在其**自身规范**（引用方项目自己编写的项目规范，如项目根目录 `AGENTS.adoc`）中**主动声明**本项目为通用工具/库类项目，agent 检测到该声明即加载本规范；未声明则视为普通项目，不加载。**声明模板（可直接粘贴到项目自身规范头部）**：`本项目为通用工具/库类项目，各类须保证绝对正确与可维护性。`；等价表述关键词放宽匹配"通用工具/库类项目""通用工具类项目""工具库""可复用组件库""组件库项目"等，描述意思一致即可
* 平台层（按使用平台加载）：
  ** CNB 平台 → link:specs/platform/cnb.adoc[]

== 规范文件登记完整性

* 本入口的加载调度器是规范文件的**唯一登记处**：凡被其他规范文件以 `specs/...` 引用的规范文件，都必须在调度器对应分类中登记；新增规范文件时"写文件"与"登记调度器"是同一个动作，禁止只建文件不登记（未登记的文件永远不会被加载，其中规则实际失效）
* 双向一致：调度器**不得登记不存在的文件**，也**不得漏登记已存在/被引用的文件**；技术栈层登记与 `specs/stack/` 实际文件的一致性、调度器登记集合与被引用集合的包含关系，均由校验脚本机械核对（本仓库校验工具见根目录 `AGENTS.adoc`）

== 技术栈扩展约定

本规范按"分类 + 懒加载"设计，天然支持多语言、多项目类型。新增技术栈规范时：

* 在 `specs/stack/` 下新增对应栈文件（如 `nodejs.adoc`、`python.adoc`），只收录该栈专属规则；
* 跨语言通用规则一律写入 link:specs/general/coding.adoc[]，避免重复；
* 同步在本入口文件的"技术栈层"登记，明确检测特征，保证"按项目类型加载且不漏"。
