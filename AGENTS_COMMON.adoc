= AGENT 执行规范

本规范用于约束 agent 的编码与协作行为，供**任何语言、任何项目**遵循。

== 访问与解析（引用方须知）

* 引用方式：引用方项目通过 https 公网静态路径或本地相对/绝对路径引用本文件，不限方式。**引用方只需引入本文件（`AGENTS_COMMON.adoc`）**；本规范内容存放于本文件所在目录下的 `specs/` 子目录（目录结构不变），随本文件一并生效，这是所有相对引用的固定前提。
* **公共内容边界（重要）**：本文件与其 `specs/` 即本规范的**全部公共内容**，面向**任意语言、任意项目**通用；公共内容须**自足**——凡在公共内容里出现的内容都只能引用本文件与 `specs/` 下的文件，**不得引用引用方看不到、也拿不到的私有落点**（维护方自己的仓库目录、项目入口文件、脚本名等；引用了就是死链，读到的规范只成立一半）。引用方仓库根目录另有**它自己编写/维护的项目规范**（通常命名为 `AGENTS.adoc`），那是**该项目自身专用**的规则，**不属于公共内容**——处理任何内容前先判断"这是公共内容还是某个项目自身的规则"，两者不得混淆。
* 路径解析规则：文中出现的 `specs/...` 均为**相对本文件所在目录**的路径。无论本文件以何种 URL/路径被打开，解析方式都是：
  ** https 访问：`specs/core/execution.adoc` = `本文件所在目录URL/specs/core/execution.adoc`；
  ** 本地相对/绝对路径：`specs/core/execution.adoc` = `本文件所在目录/specs/core/execution.adoc`。
* agent 执行要求：读取本文件后，须将本文件所在目录视为基准，把文中的 `specs/...` 解析为 `<基准目录>/specs/...` 后加载对应文件；禁止仅凭本文件内容猜测规范，凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范（见下「加载调度器」）。
* **入口可达性自检（L1，动手前先做）**：加载规范前先确认**本文件实际可达**——按引用方式实际取到本文件内容；取不到（网络不通、地址失效、本地无副本）时，须**先告知用户规范不可达并请其提供可访问地址或副本**，不得"假装已加载"（未读规范即评"符合规范"、或凭记忆代替规范均属违规，见上「agent 执行要求」）。
* **从属者（子 agent/被引用方）适配由已加载入口驱动、不靠自报（L1）**：当本规范的加载者不是任务的直接执行者——子 agent、被主 agent 派发的分步任务、由任务原文引用规范的场景——执行者不得以"我没被派发这份规范""我的指令里没有它""上级说按规范做就够了"为由跳过加载或降低约束；**加载的驱动权在入口侧**（项目根 `AGENTS.adoc`/`AGENTS_COMMON.adoc` 是持久入口）：派发者须把"读取并遵守本入口"作为派发内容的一部分，执行者读到即须自行按本文件与其调度器加载对应规范，**凡工作涉及对应主题或项目具备对应技术特征即须加载**（见下「分类与懒加载」），不得等待上级逐条转发规范原文；**"上级已读过"不构成下级免责**——约束随入口传递、不随上下文传递。
* 加载方式（网络不佳时建议下载到临时目录）：本规范常部署于外网（https 公网静态路径），**网络可能不佳**，故**建议**先将本文件与其 `specs/` 规范下载到项目根目录 `tmp/` 下的临时目录（如 `tmp/agent-specs/`），后续一律从本地副本读取——可一次下载整目录、避免逐个 URL 反复拉取因网络抖动失败或变慢（下载后 `specs/...` 相对解析基准不变，仍以 `AGENTS_COMMON.adoc` 所在目录为基准）。下载的副本按临时产物处理（见 link:specs/core/execution.adoc[]「临时产物」），**仅用于读取规范、不得以此替代远程引用**（不改变规范入口的指向）；网络正常或已存在本地副本时直接读取即可，不必强制下载。

严格使用本规范。规范以本文件当前内容为准；与本规范冲突时，以本规范定义为准。若本规范与**引用方项目自己编写/维护的项目规范**（即引入本规范的那个项目自身定义的规范，非本规范文件）冲突，以引用方项目自身规范为准。

== 最高优先级铁律（先读）

* **文件移动/重命名必须用 `git mv`，禁止 delete+create**（不得用「新增新文件 + 删除旧文件」代替移动/重命名，否则 git 历史断裂）：**最高优先级（L1）、最高关注项 P1、凌驾于一切其他规则**，任何"重构/拆分/整理"理由都不得规避；**重构/去重时不得删除或降级本条及其引用**（本条为最高关注项、不可降级）。判定标准、一拆多与兜底核对见 link:specs/general/git.adoc[]「文件移动与重命名」（权威完整定义）与 link:specs/core/execution.adoc[]「文件操作强制检查」。

* **不得执行任何会不可逆丢失内容的操作**（删除文件/目录、清空数据、`rm -rf`、`git reset --hard`、强推覆盖远端等）：**先确认目标、先备份可取回、范围可界定**，再执行；不确定即不做、先确认。**最高优先级（L1）**——破坏性操作不可逆，属安全底线（判定与兜底核对见 link:specs/core/execution.adoc[]「破坏性操作」）。

* **不得编造事实与来源**（命令/API 签名、依赖坐标、标准编号与名称、链接与路径、数据与结论）：**不知道就说不知道并去查证，宁可不给也不得编**。**最高优先级（L1）**——一次虚构会污染整条下游引用链。

* **优先站在前人的肩膀上看世界**：规范条目的依据应**优先引用广泛、高知名度、高可靠性的业界标准与文献**（ISO/IEC/IEEE、RFC、W3C、OWASP 等），让读者知其所以然、能举一反三；**标注出处只写标准名/编号、不附链接**（链接会失效或指向非官方来源；标准名称唯一、AI 可自行检索；个人项目、知名度很低、仅此一处者除外），仅在项目对标准有**明确的自身要求**时才显式覆盖并说明理由。以标准为参照调整规范时，须保证**完整性、同义性**（规则与边界不丢、要求不变）。

**上述铁律的定级与完整性保护**：条目按 **L1 强制 / L2 建议 / L3 允许** 分级，最高关注项**不可降级**（分级定义与各级遵守要求见 `specs/core/execution.adoc`「分级与最高关注项」）。



变更历史由规则化的变更日志承载，但**只记影响、不记过程**：changelog 条目写"改了什么、给谁带来什么影响"，不写实现过程与工作量（读者不问改了几行代码）；条目取舍口径见 link:specs/general/changelog.adoc[]，版本号与统一 changelog 的机制见 link:specs/general/doc-design.adoc[]「版本与变更记录」。

== 分类与懒加载（加载调度器）

规范按"必加载层 / 通用层 / 技术栈层 / 项目类型层 / 平台层"分层分类存储（位于 `specs/` 下），**按需懒加载**（避免常驻加载不需要的规范、节省上下文）。懒加载是手段，**"强制不漏"是底线**——凡工作涉及对应主题或项目具备对应技术特征，必须加载对应规范，不得因"规范文件不在常驻上下文"而凭记忆或仅凭本入口文件猜测执行。

加载规则按下列分层执行（涉及即加载，不得跳过）：

* 必加载层（每次工作都须加载）：
  ** 执行原则（含「任务生命周期与节点自查」：任务从提出到收尾各节点各查什么、何时不设这些节点；以及「规范变更的存量处理」：规范新增/调整后存量**随动迁移、不一次性变更**，除非主动声明收敛）：link:specs/core/execution.adoc[]
* 通用层（涉及对应活动时加载，不得跳过）：
  ** 编写代码 → link:specs/general/coding.adoc[]（通用编码，跨语言）
  ** 编写/修改脚本（bash/sh、Python、Node、PowerShell 等脚本文件，含 Windows 批处理 `.bat`/`.cmd`） → link:specs/general/script.adoc[]（通用脚本规范，跨语言；**行尾按脚本类型取值**——LF 基准、`.bat`/`.cmd` 必须 CRLF，判据见下文编码条目）
  ** 写注释/文档/格式（含代码内文档注释 javadoc/docstring/JSDoc 的地位与**文档质量六项：准确/完整/可执行/有价值/简洁/可验证**、"内容不减少"要求，以及禁止无意义/划水/凑字数文档、多余文档去除） → link:specs/general/doc.adoc[]
  ** 写/更新变更记录（changelog，识别特征：存在 `CHANGELOG.adoc`/`CHANGELOG.md`/`CHANGELOG.txt` 等变更日志文件、`changelog` 目录或项目自身规范/README 声明的统一变更日志，或本次改动涉及版本号/changelog 条目） → link:specs/general/changelog.adoc[]
  ** 设计文档/测试设计文档/文档分层（核心功能新增、重构、行为变更、方案选型；判定"内容写在哪一层"） → link:specs/general/doc-design.adoc[]
  ** 业务系统全生命周期文档（**项目按生命周期阶段组织文档**，识别特征：`doc/` 下存在按阶段编号的子目录（如 `1-initiation/`、`3-design/`、`operations/`），或项目涉及需求→设计→开发→测试→部署→验收→上线的完整流程、存在需求规格/测试报告/部署方案/验收报告等阶段级文档、或存在 `doc/external/` 外部系统文档目录） → link:specs/general/doc-lifecycle.adoc[]
  ** 模块级文档组织（存在**多模块结构**，或涉及"模块文档放哪、根 `doc/` 放什么"的归属判定） → link:specs/general/doc-module.adoc[]
  ** git/版本控制操作 → link:specs/general/git.adoc[]
  ** code review → link:specs/general/review.adoc[]
  ** 多 agent 协作 → link:specs/general/collab.adoc[]
  ** 编写跨语言通用规则、注释/文档/日志的措辞与语言无关性，或**涉及文件编码与换行符**（识别特征：`specs/` 通用内容、面向使用方的说明文档、多语言项目；或新增/编辑文件、跨 Linux 与 Windows 协作、写 Windows 批处理 `.bat`/`.cmd`、出现"换行符不一致"提示、需要配置 `.gitattributes`） → link:specs/general/encoding.adoc[]（**换行符权威判据：仓库内容以 LF 为基准、`.bat`/`.cmd` 必须 CRLF、`.ps1` 用 CRLF**，且须由 `.gitattributes` 固定、不靠人工手动调整）
  ** 编写涉及安全边界的代码（**涉及外部输入、认证/授权、敏感信息、文件路径、命令执行、加密随机数、对外接口与错误响应之一即加载**） → link:specs/general/security.adoc[]
  ** 引入/调整/升级依赖（识别特征：`pom.xml`/`build.gradle`/`package.json`/`requirements.txt` 等依赖清单或锁文件发生变化、需要选型引入第三方库） → link:specs/general/dependency.adoc[]
  ** 跑测试/补测试 → link:specs/general/testing.adoc[]（公共测试规范，跨语言）
  ** 读取范围、长会话上下文治理、**公共内容被未知项目加载时的可控性（运行契约）**（**任务开始时即加载**；识别特征：任何需要读取项目文件/资料的执行任务，所在会话已执行过多个任务、上下文明显变长；或**新增/调整会被引用方项目加载的公共内容（规范、提示词、随规范分发的工具）**） → link:specs/general/context.adoc[]（读取范围与长会话治理的逐条判据同见 link:specs/core/execution.adoc[]「范围控制」；运行契约本体见 link:specs/general/verify.adoc[]「运行契约」）
  ** 执行任何非平凡任务（需读完再动手的多步骤任务，含文档/代码/脚本），或涉及**动手前的自检**（指令是否逐字落实、触发的规范是否已实际加载、规划是否已落盘、读取是否在最小必要信息集内、证据是否已核实、完成如何验证） → link:specs/general/self-check.adoc[]（执行前/过程/完成前自检清单、知识边界与环境能力自评）
  ** 产出规范、文档、汇报、review 意见等涉及**引用与事实**的内容（标准编号与名称、文献、命令与 API、链接与路径、数据与结论） → link:specs/general/source.adoc[]（内部引用、外部标准、事实数据与"无法确证时怎么办"）
  ** 编译/运行/分步验证（构建/测试的实际统计、分步隔离复核、外部资源须实测可用）与未知项目加载可控性 → link:specs/general/verify.adoc[]「验证与运行契约的落点」
  ** 配置/编写 CI/CD 流水线（存在 `.github/workflows/`、`.gitlab-ci.yml`、CI 平台流水线配置等，或涉及流水线运行时/步骤调优） → link:specs/general/ci-cd.adoc[]
* 技术栈层（按项目实际使用的语言/技术栈加载，**检测到即必须加载，不得遗漏**）：
  ** Java 项目（存在 `.java`、`pom.xml`、`mvnw`、lombok 配置等）→ link:specs/stack/java.adoc[] + link:specs/stack/java-syntax.adoc[] + link:specs/stack/java-testing.adoc[]（测试类命名契约：`Tests` 常规、`BootTests` 启动型、`PerfTests` 性能、`IT` 端到端，后两者不随常规测试执行）
  ** Spring 项目（存在 Spring 依赖/注解）→ link:specs/stack/spring.adoc[]
  ** Maven 构建（存在 `pom.xml`/`mvnw`）→ link:specs/stack/maven.adoc[]
  ** Bash/Shell 脚本（存在 `.sh` 文件，或 shebang 为 bash/sh）→ link:specs/stack/bash.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 LF）
  ** Python 脚本（存在以 `python3`/`python` 为 shebang 的 `.py` 脚本）→ link:specs/stack/python.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 LF）
  ** PowerShell 脚本（存在 `.ps1` 文件）→ link:specs/stack/powershell.adoc[]（结合通用脚本规范 link:specs/general/script.adoc[] 加载；行尾 CRLF，**含同名 `.bat` 启动脚本的编码与 CRLF 要求**）
  ** 其他语言/技术栈（nodejs、ubuntu 服务器配置、python 等）按其对应栈文件加载——栈文件由引用方项目按「技术栈扩展约定」在 `specs/stack/` 下补充登记（尚未登记的栈按 AGENTS_COMMON.adoc 通用层与 coding.adoc 执行，不臆造其专属规则）
* 项目类型层（**按项目在其自身规范中的主动声明加载，声明才加载、未声明不加载**——仅适用于特定项目类型、对普通项目不生效的规范归入此层，由项目主动声明所属类型触发加载，不靠特征自动检测）：
  ** 通用工具/库类项目（以可复用组件/库/工具为主、要求每个类在设计时保证绝对正确与绝对可维护性的项目）→ link:specs/general/doc-tool.adoc[]（文档组织：类级细节归代码文档注释、独立文档承载模块/功能级总结与规划）。**触发方式**：项目在其**自身规范**（引用方项目自己编写的项目规范，如项目根目录 `AGENTS.adoc`）中**主动声明**本项目为通用工具/库类项目，agent 检测到该声明即加载本规范；未声明则视为普通项目，不加载。**声明模板（可直接粘贴到项目自身规范头部）**：`本项目为通用工具/库类项目，各类须保证绝对正确与可维护性。`；等价表述关键词放宽匹配"通用工具/库类项目""通用工具类项目""工具库""可复用组件库""组件库项目"等，描述意思一致即可
* 平台层（按使用平台加载）：
  ** CNB 平台 → link:specs/platform/cnb.adoc[]

* 项目自身维护层（**只对"维护一套被其他项目引用的共享内容（规范集合、模板、公共脚本等）"的项目生效**，识别特征：项目自己维护这类共享资产集合）：
  ** 条目落点：该层的规范文件由**维护方项目自己的项目规范**登记，**不随公共内容分发**，公共内容不引用其私有文件——引用方看不到、拿到了也无从加载，故公共内容里的规则一律在本文件与 `specs/` 内自足表达。
  ** 维护方自己维护规范集合时所需的元规范（分类准入与定级、规范自身重构、优先级与最高关注项、维护方的验证义务等）由该项目自行承载（它可以放在维护方自己的仓库与项目规范里，也是本层的一份实现）。

== 规范文件登记完整性

* 本入口的加载调度器是规范文件的**唯一登记处**，双向一致：凡被 `specs/...` 引用的规范文件都须在对应分类登记（"写文件"与"登记调度器"是同一个动作，未登记即永远不会被加载、规则实际失效），登记也不得指向不存在/未引用的文件；该一致性**可由机械校验核对**（属可确定性核对的一类，维护规范集合的项目应自行设防线）

== 技术栈扩展约定

本规范按"分类 + 懒加载"设计，天然支持多语言、多项目类型。新增技术栈规范时：

* 在 `specs/stack/` 下新增对应栈文件（如 `nodejs.adoc`、`python.adoc`），只收录该栈专属规则；**新增前先过准入判定**（是否该收、该收进哪一层：对任意项目成立才进公共内容，只对某个项目成立则写进该项目自己的项目规范）；
* 跨语言通用规则一律写入 link:specs/general/coding.adoc[]，避免重复；
* 同步在本入口文件的"技术栈层"登记，明确检测特征，保证"按项目类型加载且不漏"。
